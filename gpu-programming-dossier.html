How to read this

This document teaches four things in one line of argument: how an NVIDIA GPU runs a program; how to write that program in CUDA and read it again as PTX and SASS; how bpftime puts an eBPF program inside a GPU kernel you did not write; and how a large language model server uses the GPU to produce text, so that you know where to point those probes. It follows one matrix-vector multiply from the first chapter to the last.

Chapter 0 · Prologue

One multiply, three ways to watch it

~13 min · HW LLM — Where we are: nowhere yet. This chapter picks the one object every later chapter follows, a matrix-vector multiply, and sets out the three ways anyone can watch a GPU while it runs one.

The object we follow

A large language model writes text one piece at a time. Each piece is a token: a short run of characters, often a whole word, sometimes part of one. "Linux" might be one token or two ("Lin" and "ux"). To produce one token, the model runs a long, fixed sequence of arithmetic, and most of that arithmetic is a single operation repeated hundreds of times.

That operation needs three words. A vector is an ordered list of numbers. A matrix is a grid of numbers in rows and columns. A dot product multiplies two vectors of the same length element by element and adds up the results. The dot product of (1, 2, 3) and (4, 5, 6) is 1·4 + 2·5 + 3·6 = 32.

A matrix-vector multiply, written matvec from here on, takes a matrix W and a vector x and produces a vector y. Each number in y is the dot product of one row of W with x. If W has d rows and n columns, then x has n numbers and y has d. We write it y = W·x.

W = | 1 2 3 |     x = | 1 |     y = | 1·1 + 2·0 + 3·2 |  =  |  7 |
    | 4 5 6 |         | 0 |         | 4·1 + 5·0 + 6·2 |     | 16 |
                      | 2 |

Doing the same thing for many vectors at once, stacked side by side as the columns of a second matrix, is a matrix-matrix multiply, written matmul. A matmul is many matvecs that share one W.

Our matvec has d = n = 4096 and stores each number in 4 bytes. W is then 4096 × 4096 × 4 = 67,108,864 bytes, which is 64 MiB. Computing y takes 4096 × 4096 = 16,777,216 multiplications and as many additions. The program that does it is lab/gpu/matvec.cu, and every listing of machine code in this document was compiled from that one file.

One property of this operation decides how fast it can ever run, and you can see it already in the diagram. Every number in W is read from memory, used in exactly one multiply and one add, and never touched again. The arithmetic is trivial. The cost is moving 64 MiB to wherever the arithmetic happens. The memory chapter turns that sentence into a number, and the language-model chapters show that this number sets the speed of every LLM server that answers one user at a time.

Why a GPU

A GPU, a graphics processing unit, is a chip with thousands of small arithmetic units, built to run one short function over a large amount of data at once. It sits on the PCIe bus and has its own memory. In GPU programming the CPU side, with its operating system and its memory, is the host. The GPU with its memory is the device.

The function that runs on the device is a kernel. One launch of a kernel starts thousands of copies of the same function, and each copy works on a different part of the data. The word collides with the Linux kernel, so this document always says host kernel for the operating system. A bare "kernel" is always GPU code.

The CPU and the GPU are built for opposite goals. Latency is how long one piece of work takes from start to finish. Throughput is how much work finishes per second. A CPU core spends its transistors on latency: large caches, branch prediction, out-of-order execution, all so that one thread finishes soon. A GPU spends them on throughput: many simple units, and enough independent work queued up that some of it is always ready while the rest waits for memory. Our matvec is 16.8 million multiplications that do not depend on each other, and 4096 sums that can be split into pieces in any order we like. That is exactly the kind of work a GPU is for.

The software that makes an NVIDIA GPU programmable is CUDA. It is a dialect of C++ for writing kernels, a compiler for that dialect, and two libraries that every CUDA program loads. The CUDA runtime (libcudart.so) is the convenient API most programs call. Under it sits the CUDA driver library (libcuda.so), which talks to the GPU driver in the host kernel. The GPU-sharing dossier follows those two libraries down to the hardware in How a launch reaches the silicon (chapter 2). This document starts from the programmer's side and goes down from there.

Three ways to watch it

Suppose the matvec runs inside a program you did not write, and you want to know how long it takes and why. There are three places to stand.

On the host, watching the calls. A uprobe on cudaLaunchKernel in libcudart.so fires every time the program asks for a kernel to run. This is ordinary eBPF, and you already know how to write it. The problem is that a launch is asynchronous: the call puts the work in a queue for the GPU and returns, usually within a few microseconds. The GPU may not start the kernel for a long time after that. A host-side probe sees the request. The kernel's start, its running, and its end all happen somewhere the probe cannot see.

Asking the vendor. NVIDIA's profilers are the Nsight tools. The library under them is CUPTI, the CUDA Profiling Tools Interface. Together they read counters built into the GPU and record exactly when each kernel ran and what it did. They are precise and heavy. The detailed per-kernel tool replays each kernel several times to collect all its counters, which is not something you do to a production server. And they move on without old hardware: the current version of that detailed tool does not support the customer's Pascal card at all.

Inside the kernel. bpftime is a userspace eBPF runtime from the eunomia-bpf project. One of the things it can do is rewrite a kernel's GPU code while the program is loading it, so that an eBPF program you wrote runs inside that kernel, in every thread of the kernel, at the kernel's entry or exit. The probe can read the GPU's own clock and the thread's position on the chip, and write into maps that a host process reads. It sees what the first two places cannot: which threads of the kernel were slow, and where on the chip they ran.

Recap

We follow one matvec, y = W·x, with W a 4096 × 4096 matrix of 4-byte numbers: 64 MiB of data and 16.8 million multiply-adds, with every number of W used exactly once. A GPU is a throughput machine on the PCIe bus; a kernel is the function it runs, launched from the host through the CUDA runtime and driver libraries. You can watch a kernel from the host, which sees only the asynchronous request; through NVIDIA's profilers, which are precise but heavy; or from inside the kernel with bpftime, which runs your eBPF in every thread of the kernel.

Check yourself

1. Predict the value: for our matvec (d = n = 4096, 4-byte numbers), how many multiply-adds are done per byte of W read? What happens to that ratio if you make W 8192 × 8192?

Answer

One multiply-add per 4 bytes, so 0.25 per byte, and it stays 0.25 at 8192 × 8192. The 4096 case is 16,777,216 multiply-adds over 67,108,864 bytes. The 8192 case is four times the work (67,108,864 multiply-adds) over four times the bytes (268,435,456).

The mechanism is in diagram 0.1: each number of W meets x once and is never used again, however big W gets. The tempting wrong answer is that a bigger matrix gives "more reuse". For a matvec it gives none. Only x is reused, once per row, and x is tiny next to W.

2. A uprobe on cudaLaunchKernel shows each call taking about 4 µs. The step of the program that makes those calls takes 30 ms of wall-clock time, and a CPU profile says most of that 30 ms is spent inside one other CUDA call. What is the program doing during that time, and why can the uprobe not tell you?

Answer

The program is waiting for the GPU. The GPU work is the 30 ms; the 4 µs is only the time to queue each launch.

Launches are asynchronous (diagram 0.3): cudaLaunchKernel appends to the GPU's queue and returns. The program then blocks in a call whose only job is to wait for the GPU to finish, and that call is where a CPU profile puts the time. The near-miss is "the driver is slow because that call takes 30 ms". The call does nothing while it waits. The time belongs to kernels the uprobe never saw run.

3. "A matmul is many matvecs that share one W, so it moves the same number of bytes per multiply-add as a matvec." Where does that sentence stop being true?

Answer

It stops being true as soon as the matmul reads each number of W once and uses it for all the vectors before moving on. With k vectors, each number of W then feeds k multiply-adds per read, so the ratio becomes 0.25 × k per byte instead of 0.25.

The sentence is true only for a matmul written as k separate matvecs, each one reading W again from memory. The condition that makes the reuse real is that a number of W stays somewhere fast while all k vectors use it. That condition is what the memory chapter is about, and batching many users' requests together in an LLM server is this same trick.

Chapter 1

Four ways to be parallel

~12 min · HW — Last chapter we chose our object: a matvec made of 16.8 million multiplications that do not depend on each other. This chapter asks how a machine can do many of them at once. The answer comes in four shapes, and the GPU uses a fifth that borrows from two of them.

Flynn's four boxes

In 1972 Michael Flynn sorted computers by two counts, and the sorting is still the clearest way in. The first count is instruction streams: how many separate sequences of instructions the machine follows at once, each with its own program counter. The second is data streams: how many separate pieces of data those instructions work on at once. One or many, times one or many, gives four boxes. This is Flynn's taxonomy.

SISD, single instruction stream and single data stream, is one plain CPU core running ordinary code. The inner loop of our matvec, sum += w[j] * x[j], compiled without vector instructions, does one multiply-add per instruction. SIMD, single instruction and multiple data, is one instruction that works on several numbers side by side. MIMD, multiple instructions and multiple data, is several independent processors, each following its own program: the eight cores of the laptop's Ryzen are MIMD. The fourth box, many instruction streams on one data stream, is almost never built, and nothing here needs it.

SIMD on the CPU you already have

The laptop's CPU is a Ryzen 7 8845HS, and it has AVX-512. A vector register is a wide register that holds several numbers. An AVX-512 register (zmm0 to zmm31) is 512 bits wide, which is sixteen 4-byte floats. Each slot is a lane. One instruction then works on all sixteen lanes at once. Here is one row of our matvec written with AVX-512 intrinsics, and the inner loop that gcc -O2 -mavx512f made of it:

__m512 acc = _mm512_setzero_ps();
for (int j = 0; j < n; j += 16)
    acc = _mm512_fmadd_ps(_mm512_loadu_ps(w + j), _mm512_loadu_ps(x + j), acc);
return _mm512_reduce_add_ps(acc);

    vmovups      (%rdi,%rax,4), %zmm2          # 16 numbers of the row of W
    vfmadd231ps  (%rsi,%rax,4), %zmm2, %zmm0   # 16 multiply-adds, one instruction

Listing 1.1 — one row of the matvec, as CPU SIMD. Compiled on this laptop with gcc.

Two things about SIMD matter for what follows. First, the program is written in vectors. The code says "sixteen at a time", the loop steps by 16, and the data has to be laid out so that sixteen useful numbers sit next to each other in memory. Second, lanes cannot easily go their own way. If some lanes should skip a step, the programmer uses a mask: a set of bits, one per lane, that switches lanes off for one instruction. AVX-512 has eight mask registers for this, k0 to k7. Every branch has to be turned into masks by hand or by the compiler.

SIMT: write one thread, run thirty-two

A GPU programmer writes code for one thread. A GPU thread is one running copy of the kernel's function, with its own registers and its own index number, and that index is how it knows which part of the data is its own. In our first kernel, thread number row computes y[row] with a plain scalar loop. Nothing in the source says "thirty-two at a time".

The hardware groups the threads anyway. Thirty-two threads with consecutive index numbers form a warp, and the GPU fetches and issues each instruction once for the whole warp. Each thread of the warp occupies one lane, so one multiply-add instruction does thirty-two multiply-adds, exactly as one AVX-512 instruction does sixteen. NVIDIA calls this SIMT, single instruction, multiple threads.

The difference from SIMD is where the grouping lives. In SIMD it is in the program: the code is written in vectors. In SIMT it is in the hardware, and the program describes one thread. Each lane can load from its own unrelated address, which SIMD can only do with special gather instructions. And each lane can take its own side of a branch, which SIMD handles only through masks the program builds. A GPU builds those masks itself.

When threads disagree: divergence

Lanes may disagree at a branch. Some threads of a warp take the if, the others take the else. That is divergence. The warp still issues one instruction at a time, so it runs the two sides one after the other. While it runs one side, the lanes that chose the other side are switched off by an active mask, the GPU's own per-lane on/off bits. When both sides are done, the paths meet again and the warp continues with all lanes on. That meeting point is reconvergence.

The cost is simple to state: a divergent branch costs the time of both sides added together, and every lane waits for the slower combination. Diagram 1.2 shows one warp running if (lane < 20) A(); else B();, where A takes 10 cycles and B takes 20.

Our matvec barely diverges, and you can check that in the source. The naive kernel's only branch is if (row >= d) return;, which with d = 4096 threads launched in groups of 256 is never true for any thread. The warp-per-row kernel ends with if (lane == 0) y[warp] = sum;, which idles 31 lanes for exactly one store. Divergence becomes expensive in code with data-dependent branches inside loops. It also matters to probes later: an eBPF program injected into a kernel runs in every lane, and an if in your probe diverges like any other.

One program counter per warp, or one per thread

How does the warp remember which lanes are waiting, and where? Before 2017, NVIDIA GPUs kept one program counter per warp, plus a small stack of masks that the compiler pushed at each branch and popped at each reconvergence point. Pascal works this way. Starting with Volta in 2017, and so on Ada and Hopper, each thread has its own program counter and call stack in hardware. This is independent thread scheduling. The warp still issues one instruction for the lanes that share a program counter, but the scheduler can now switch between the divergent groups whenever it likes, rather than finishing one side before starting the other.

That sounds like a detail until two lanes of one warp wait for each other. Suppose lane 0 takes a lock and lane 1 spins on it:

if (lane == 0) { lock(); work(); unlock(); }
if (lane == 1) { while (!try_lock()) ; work(); unlock(); }

Listing 1.2 — two lanes of one warp and one lock. Illustrative.

With one program counter per warp, the hardware runs one group of lanes until it reaches the reconvergence point. If it picks lane 1's spin loop first, lane 1 spins forever, because lane 0 can only run after lane 1's side is done, and lane 1's side is never done. On Pascal this kernel can hang. With independent thread scheduling the scheduler eventually runs lane 0, lane 0 releases the lock, and lane 1 gets it. This is why every warp-level intrinsic in modern CUDA takes an explicit mask of which lanes take part, and why code that sends one request at a time from a warp, as bpftime's helper calls do, walks the lanes in a deliberate loop.

Across warps, there was never any lockstep. Different warps are independent: one can be inside a branch while another is at the top of the loop. Counted warp by warp, a GPU is a MIMD machine with a very large number of instruction streams. Counted lane by lane inside one warp, it is SIMD with masks it manages itself. SIMT is the name for that combination.

Recap

Flynn's taxonomy sorts machines by instruction streams and data streams: SISD is a scalar core, SIMD is one instruction over many lanes, MIMD is many independent programs. A GPU is SIMT: the program is written for one thread, the hardware groups 32 threads into a warp and issues each instruction once for all of them. When lanes disagree at a branch, the warp runs both sides one after the other under an active mask and reconverges afterwards, so divergence costs both sides' time. Since Volta, and so on Ada and Hopper but not on Pascal, each thread has its own program counter, which lets lanes of one warp wait on each other without hanging.

1. Predict the value: a warp runs if (lane < 8) A(); else B();. A takes 10 cycles and B takes 30. How many cycles does the warp spend in the branch, and what fraction of its lane-cycles do useful work?

Answer

40 cycles, and 62.5% of lane-cycles are useful. The two sides run one after the other (diagram 1.2), so 10 + 30 = 40. Useful lane-cycles are 8 × 10 + 24 × 30 = 800, out of 32 × 40 = 1280 available.

The near-miss is 30 cycles, "the slower side". That would be true only if the two groups of lanes ran at the same time. Within one warp they never do, even with independent thread scheduling: that feature lets the groups interleave, but each instruction still issues for one group at a time.

2. A kernel in which lane 1 of each warp spins on a flag that lane 0 sets inside an if finishes on the laptop and hangs on the customer's P5000. Same source, same data. What is different?

Answer

Pascal has one program counter per warp. If it starts lane 1's spinning side first, it will not run lane 0's side until the spinning side reaches reconvergence, which it never does. The warp hangs.

Ada has independent thread scheduling (listing 1.2 and the table above), so the scheduler eventually switches to lane 0's group, the flag is set, and the spin ends. The near-miss is "the P5000 is slower, so it is a timeout". No amount of waiting helps: lane 0's instruction is never issued at all.

3. "With SIMT the programmer writes scalar code, so warps never need to be thought about." Name two situations from this chapter where that sentence stops being true, and the mechanism behind each.

Answer

First, speed with data-dependent branches: lanes of one warp that disagree make the warp pay for both sides, because it issues for one group at a time under the active mask. Second, correctness when lanes of one warp wait on each other: on Pascal, one program counter per warp can hang such code. With independent thread scheduling it makes progress, but warp-level operations still need an explicit mask of participating lanes.

A third, which the next chapters add: which addresses neighbouring lanes load together decides how fast memory runs. The sentence is only safe for code whose lanes take the same path and never talk to each other.

Chapter 2

Inside a streaming multiprocessor

~12 min · HW — Last chapter grouped our matvec's threads into warps of 32. Now we find where a warp runs: the streaming multiprocessor, the unit a GPU is built from twenty copies of on the laptop and 132 on the H100.

Optional neighbour: the GPU-sharing dossier's The silicon (chapter 1) maps the whole die, with its graphics clusters, memory controllers and copy engines. This chapter zooms into one of the units on that map and looks at it as a programmer.

The chip is made of SMs

A GPU is mostly many copies of one block, the streaming multiprocessor, or SM. Each SM is a complete processor for warps: it fetches instructions, keeps the registers of every thread it is running, and has its own arithmetic units and its own on-chip memory. The laptop's RTX 4050 has 20 SMs. The customer's P5000 also has 20. An H100 SXM5 has 132. The rest of the die is wiring between the SMs and memory, plus a few fixed-function engines.

When a kernel launches, its threads are handed out to SMs in groups, and each SM runs many warps at once. A warp that has been placed on an SM is a resident warp. It stays on that SM, with its registers allocated there, until every thread in it has finished. Under normal running nothing moves it elsewhere.

One SM, opened up

An Ada SM is split into four SM sub-partitions, and almost everything is per sub-partition. Each one has a warp scheduler, which every cycle picks one resident warp that is ready to go and issues one instruction for it. That one chance per cycle to start an instruction is an issue slot. With four schedulers, an SM can start up to four warp-instructions per cycle.

Each sub-partition also has its own slice of the register file, the SM's store of registers for every resident thread: 16,384 registers of 32 bits, 64 KB per sub-partition and 256 KB for the whole SM. That is larger than the SM's cache, and it is the reason the next section works. Each sub-partition has 32 FP32 lanes, FP32 being the 4-byte floating-point format, and each lane does one multiply-add per cycle; on Ada, 16 of them can also do integer arithmetic. So one multiply-add instruction for a warp fills one sub-partition's lanes for one cycle.

The remaining units are fewer and more specialised. A tensor core does a small matrix multiply, for example 16 × 8 × 16, as one instruction for a whole warp. It matters enormously for matmul and not at all for our matvec. A special function unit, or SFU, computes things like exponentials, sines and reciprocal square roots. The language-model chapters need its exponentials. A load/store unit turns a warp's memory instructions into requests to the memory system.

Below the four sub-partitions sits one pool of fast on-chip storage, 128 KB on Ada. Part of it is the L1 cache, a cache of recently used memory, managed by hardware like a CPU's. The rest is shared memory, a scratchpad the kernel's own code reads and writes directly, which the threads of one launch group can use to hand data to each other. The kernel says how it wants the pool split, up to 100 KB of shared memory on Ada.

Latency hiding: why the register file is so big

A load from the GPU's main memory takes hundreds of cycles to come back. The microbenchmark papers in the reading list measure it per generation. A CPU core attacks that wait inside one thread, with caches, prefetching and out-of-order execution. An SM does something else: when one warp has to wait for its data, the scheduler issues an instruction from a different warp that is ready. If enough warps are resident, there is always one ready, and the arithmetic units never sit idle. This is latency hiding.

The switch costs nothing. A CPU switching threads has to save one set of registers and load another. An SM keeps the registers of every resident warp in the register file at the same time, so "switching" just means the scheduler picks a different warp's instruction on the next cycle. That is what the 256 KB of registers per SM buys.

Diagram 2.2 runs a tiny model of one scheduler. Every warp loops over the same five instructions: two independent arithmetic instructions, a load, then two instructions that use the loaded value and so must wait for it. The load takes 14 cycles here. Real memory takes far longer, which only makes the effect stronger.

The model also shows the limit. Eight warps leave six idle cycles in 44. An Ada sub-partition can hold at most 12 resident warps (48 per SM), and real latencies are much longer than 14 cycles. So warps alone cannot hide everything. The other half of the answer is giving each warp several independent loads in flight before it needs the first result. The compiler does this for our naive matvec by unrolling its loop. In the machine code for Ada, which a later chapter reads line by line, each thread issues twenty-two loads before its first multiply-add.

Occupancy, and the version number of an SM

Occupancy is the number of resident warps on an SM divided by the most the SM can hold. On Ada the maximum is 48 warps; on Pascal and Hopper it is 64. Several resources cap it, and registers are the first one you meet. The 65,536 registers of an SM are shared by every resident thread, so a kernel whose threads each need many registers fits fewer warps.

You can read the register count of every kernel out of the compiled file. For the three kernels of lab/gpu/matvec.cu compiled for Ada, cuobjdump -res-usage reports 38, 40 and 53 registers per thread for the naive, warp-per-row and float4 versions. Registers are handed out per warp, rounded up to a multiple of 8 per thread. The warp-per-row kernel then needs 40 × 32 = 1,280 registers per warp, and 65,536 / 1,280 = 51 warps would fit. The SM's cap of 48 binds first, so registers do not limit it. The float4 kernel rounds 53 up to 56, needs 1,792 per warp, and fits 36 warps: 75% occupancy before any other limit is applied. The scheduling chapter adds the other limits, and one of them lowers that number again.

Higher occupancy means more warps to choose from when hiding latency. It does not always mean faster code, because a kernel with fewer, busier warps and more loads in flight per warp can hide latency just as well.

Each SM design has a version number, its compute capability, written major.minor. Pascal's GP104 is 6.1, Ada is 8.9, Hopper is 9.0. The number decides which instructions exist and what every limit in this chapter is. The compiler spells it sm_61, sm_89, sm_90, and the compiler chapter explains why there is also a second spelling.

2. A profiler says all 48 warps on an SM are resident, but its schedulers issue an instruction on only a quarter of the cycles. What are the warps doing, and why would raising occupancy not help?

Answer

They are waiting. A scheduler can only issue from a warp whose next instruction is ready, and here most warps are stuck on a load whose data has not arrived (the grey cycles in diagram 2.2, with many more warps).

Occupancy is already at its maximum, 48 of 48, so there are no more warps to add. What helps is more independent work per warp before it needs the data, such as several loads in flight, or less waiting per load. The near-miss is "occupancy is too low": being resident and being ready are different states, and the profiler counted the first.

3. "Switching between warps costs nothing." Where does that stop being true?

Answer

It is true only between resident warps, because only their registers are already in the register file. A warp that is not yet on the SM cannot be switched in at all: it has to wait until enough resident threads finish to free their registers and their place.

The cost has also moved rather than gone away. Every resident warp occupies registers all the time, so a kernel pays for free switching with a cap on how many warps fit, which is occupancy. And switching between different programs that share one GPU is a real save-and-restore, which the GPU-sharing dossier's time-slicing chapter covers.

Chapter 3

Memory and the bandwidth wall

~13 min · HW — Last chapter put our matvec's warps on SMs and showed the SM hiding the wait for memory by switching warps. Hiding the wait does not shorten it. This chapter follows the 64 MiB of W from memory to the lanes, and ends with a number: the shortest time our matvec can possibly take on each bench.

Optional neighbour: The silicon (chapter 1) of the GPU-sharing dossier shows where the L2 slices and memory controllers sit on the die. This chapter only needs to know that they exist and how fast they are.

The ladder

A GPU has the same kind of memory ladder as a CPU, with a different emphasis. At the top are registers, private to one thread and free to use. Below them is the SM's 128 KB pool, split between L1 cache and shared memory. Below that is the L2 cache, one cache for the whole chip, shared by every SM. At the bottom is the global memory: the GPU's own DRAM, gigabytes of it, visible to every thread of every kernel. W lives there.

Two kinds of DRAM appear in our benches. GDDR (graphics double data rate) memory sits as separate chips on the board around the GPU. The laptop has 6 GB of GDDR6 on a 96-bit bus and the P5000 has 16 GB of GDDR5X on a 256-bit bus. HBM (high-bandwidth memory) is stacks of DRAM dies placed in the same package as the GPU, with a very wide bus. The H100 has 80 GB of HBM3 on a 5,120-bit bus. Bus width is most of the difference in speed between these three.

Two more names refer to places in that same DRAM, treated specially. Local memory is per-thread storage that lives in global memory. The compiler uses it when a thread's variables do not fit in registers. Constant memory is a small read-only region, 64 KB, with its own cache that is fastest when every lane of a warp reads the same address. The kernel's arguments are placed there, which is why the machine code in a later chapter reads the pointer W from c[0x0][0x160] and the size n from c[0x0][0x178]: bank 0 of constant memory, at fixed offsets.

Sectors, and why neighbouring lanes should read neighbouring bytes

Memory is never fetched one float at a time. The unit of transfer between DRAM, L2 and L1 is a sector of 32 bytes. Caches track memory in cache lines of 128 bytes, four sectors each. When a warp issues a load, the load/store unit collects the 32 lanes' addresses and works out which sectors they touch, then fetches each sector once. If neighbouring lanes read neighbouring 4-byte floats, 32 lanes touch exactly four sectors, one cache line, and every byte fetched is used. That is a coalesced access, and getting it is called coalescing.

Our two matvec kernels differ in exactly this. In the warp-per-row kernel, lane i of the warp reads W[row][j + i]: thirty-two neighbours. In the naive thread-per-row kernel, lane i is working on row row + i, so the warp's 32 addresses are 4096 × 4 = 16 KiB apart. Each lane lands in a different sector. One warp-wide load now fetches 32 sectors, 1,024 bytes, to deliver 128 useful bytes.

The naive kernel is saved partly by that last sentence. The same lane reads the next float of its row on the next iteration, which is in the sector it already fetched. If the sector is still in L1, the read is cheap. With dozens of resident warps each pulling 32 different lines through a 128 KB pool, many sectors are evicted before they are used again, and the extra traffic is real. How much it costs is a measurement, and the lab program makes it.

Shared memory has a different rule. It is split into 32 banks, each 4 bytes wide, and consecutive 4-byte words sit in consecutive banks. A warp can read 32 words in one go if they are in 32 different banks. If two lanes want different words in the same bank, that is a bank conflict, and the accesses to that bank are done one after another. The classic case is a warp reading one column of a 32 × 32 float tile: every element of a column is in the same bank, so a single read becomes 32. Our matvec does not use shared memory. The attention kernels of the language-model chapters do.

Bandwidth, and how many FLOPs a byte buys

Bandwidth is how many bytes per second a level of memory can deliver. Peak DRAM bandwidth is the bus width times the transfer rate. The H100's datasheet says 3,352 GB/s and the P5000's says 288 GB/s. NVIDIA does not publish a figure for the laptop chip, but 96 bits at 18 Gbit/s per pin gives about 216 GB/s, and the lab program will confirm the real one. A real kernel reaches perhaps 80 to 90% of peak.

Arithmetic is counted in FLOP, floating-point operations, and its rate in FLOPS, per second. A multiply-add counts as two FLOP. The laptop has 2,560 FP32 lanes at up to 2.345 GHz, each doing one multiply-add per cycle: 2,560 × 2 × 2.345 GHz ≈ 12 TFLOPS. Numbers come in several sizes. FP32 is the ordinary 4-byte float. FP16 is a 2-byte float with less range and precision. BF16, "brain float", is a 2-byte float with FP32's range and even less precision. Language models store their weights in BF16 more often than in anything else, and that halves the bytes of every W.

The ratio between the two is the key quantity. Arithmetic intensity is FLOP done per byte moved from memory. Our FP32 matvec does 2 FLOP per 4-byte weight: 0.5 FLOP per byte. The laptop can do 12,000 GFLOPS of arithmetic but only receive 216 GB of data per second. To keep its lanes busy, a kernel would need 12,000 / 216 ≈ 56 FLOP for every byte. Our matvec offers 0.5. The lanes will be idle more than 99% of the time, waiting for W, however good the code is.

The roofline

That argument has a standard picture, the roofline (Williams, Waterman and Patterson, 2009). The horizontal axis is arithmetic intensity, the vertical axis is attainable FLOPS, and both are logarithmic. A kernel can never beat bandwidth × intensity, which is the sloped line, nor the arithmetic peak, which is the flat line. The corner where they meet is the ridge point. A kernel to the left of the ridge is memory-bound: its speed is set by bandwidth, and only moving fewer bytes makes it faster. A kernel to the right is compute-bound: its speed is set by arithmetic, and only fewer or cheaper FLOP make it faster.

The roofline turns the prologue's sentence into a prediction. Our matvec must move at least 64 MiB of W plus 32 KiB of x and y, about 67.1 million bytes. At 216 GB/s that takes at least 311 µs on the laptop, and no kernel can beat it. The compiler, the warps, the registers and the scheduler all decide how close a kernel gets to 311 µs, and none of them can get below it. The same arithmetic gives the other two benches in the table below. Store W in BF16 instead and every number halves.

This chapter skips DRAM refresh, bank groups, and the memory controllers' scheduling. They explain why real kernels reach 80 to 90% of peak and not 100%, and nothing here needs more than that.

2. A profiler reports, for the main load instruction of one matvec kernel, about 32 sectors requested per warp-wide load, and about 4 for another kernel. Both load one 4-byte float per lane. Which is the naive kernel, and what does its number cost?

Answer

The 32-sector one is the naive thread-per-row kernel. Its lanes read addresses 16 KiB apart, so each lane needs its own sector (diagram 3.2). The warp-per-row kernel's lanes read 32 neighbours, which is 4 sectors.

The cost is up to 8 times as many bytes moved per useful byte: 1,024 fetched for 128 used. The real penalty is smaller only to the extent that L1 still holds each sector when the lane comes back for its next float. Since the kernel is memory-bound, extra bytes become extra time almost one for one. The near-miss is "the naive kernel does more arithmetic". Both do the same 16.8 million multiply-adds.

3. "A matvec is memory-bound, so its time is set by DRAM bandwidth." Give a case from this chapter where the second half stops being true, and what sets the time instead.

Answer

When W is small enough to stay in the L2 cache from one call to the next. For example, a 1024 × 1024 FP32 W is 4 MiB, which fits in the H100's 50 MB L2. It does not fit in the P5000's 2 MB. Repeated calls then read W from L2, whose bandwidth is several times DRAM's, so the time is set by L2 bandwidth, and the measured "GB/s" can exceed the DRAM peak.

The kernel is still memory-bound: its intensity is still 0.5 FLOP per byte. What changed is which rung of diagram 3.1 the bytes come from. The other way out is the green point of diagram 3.3: reuse each weight for many vectors, which raises the intensity itself.

Chapter 4

CUDA: writing the matvec

~13 min · CUDA — The machine part (Part I) gave us warps on SMs, fed by a memory that puts a 311 µs floor under our matvec on the laptop. Now we write the matvec for that machine, three times. Each version fixes what the one before got wrong, and all three are in lab/gpu/matvec.cu.

The shape of a launch

A CUDA source file mixes host code and device code, and three keywords say which is which. A function marked __global__ is a kernel: it runs on the device and is launched from the host. A function marked __device__ runs on the device and can only be called from device code; our warp_sum helper is one. Anything unmarked is ordinary host code.

One launch creates a grid: every thread that launch will run. The grid is cut into thread blocks, usually just "blocks", of up to 1,024 threads each. A block is the unit placed on an SM: all its threads run on the same SM, can use the same shared memory, and can wait for each other. In NVIDIA's lower-level documents a block is called a CTA, a cooperative thread array, and the two names mean the same thing. Inside the block, the hardware cuts the threads into warps of 32, in order.

Each thread finds its place through four built-in variables. threadIdx is the thread's index within its block. blockIdx is the block's index within the grid. blockDim is the number of threads per block, and gridDim the number of blocks. Each has .x, .y and .z parts, for problems that are naturally two- or three-dimensional; a matvec only needs .x. The usual first line of a kernel turns them into one global index:

int row = blockIdx.x * blockDim.x + threadIdx.x;    // matvec.cu:45

The host starts a kernel with a launch configuration in triple angle brackets: matvec_naive<<<16, 256>>>(W, x, y, n, d) asks for 16 blocks of 256 threads. Two more optional values can go inside the brackets, the bytes of shared memory per block and a queue to launch into. The host-side chapter covers the second.

The host half

Device code can only read device memory, so the host has to put W and x there first. cudaMalloc allocates global memory and returns a device pointer. cudaMemcpy copies between host and device memory, in a direction you name. cudaFree gives the memory back. The lab program's main does exactly that (matvec.cu:153–159), launches each kernel, and copies y back to compare it with cuBLAS.

Errors need care because the launch is asynchronous. A bad launch configuration is reported by cudaGetLastError() straight after the launch. A fault while the kernel runs, such as reading outside an allocation, is reported by whatever CUDA call comes next, often a copy many lines later. The lab wraps every call in a CHECK macro that prints the file and line and exits, which is the minimum for code you want to debug.

Version one: a thread per row

__global__ void matvec_naive(const float *__restrict__ W, const float *__restrict__ x,
                             float *__restrict__ y, int n, int d)
{
	int row = blockIdx.x * blockDim.x + threadIdx.x;
	if (row >= d)
		return;
	float sum = 0.0f;
	for (int j = 0; j < n; j++)
		sum += W[(size_t)row * n + j] * x[j];
	y[row] = sum;
}

It is the C loop with the outer loop removed: the grid is the outer loop. __restrict__ promises the compiler that the three arrays do not overlap, and together with const that lets it read W and x through a read-only path; a later chapter shows the instruction this becomes. The if guards against a grid with more threads than rows. Its problem is the one diagram 4.1 marks in orange. Lanes of one warp walk 32 different rows in step, so every warp-wide load touches 32 sectors. It has a second, quieter problem, which the first question below asks you to find.

Version two: a warp per row, and a shuffle

Give each row to a whole warp. Lane i adds up columns i, i + 32, i + 64 and so on, so at every step the 32 lanes read 32 neighbouring floats, the coalesced pattern. Each lane ends with a partial sum of 128 products, and the 32 partial sums must be added into one.

Adding many values into one is a reduction. Within a warp it can be done without touching memory, with a warp shuffle: an instruction that lets each lane read a register of another lane in the same warp. __shfl_down_sync(mask, v, offset) gives each lane the value of v held by the lane offset places above it. The mask names the lanes taking part, all 32 here, which is the explicit mask the previous chapter said modern code must pass.

__device__ __forceinline__ float warp_sum(float v)
{
	for (int offset = 16; offset > 0; offset /= 2)
		v += __shfl_down_sync(0xffffffff, v, offset);
	return v;
}

Two more tools belong here, though this kernel does not need them. If a whole block, rather than one warp, shared a row, the warps would have to combine their results through memory they can all see. That memory is __shared__: a variable declared with that keyword lives in the SM's shared memory, one copy per block. And the warps would have to wait for each other between writing and reading it. __syncthreads() is that wait: a barrier that every thread of the block must reach before any of them continues. It covers one block only. Threads in different blocks have no barrier inside a kernel; the end of the kernel is the only point where all of them have finished.

Version three: sixteen bytes per lane

matvec_warp4 (matvec.cu:82–100) is version two with one change: it reinterprets W and x as arrays of float4, a 16-byte struct of four floats, so each lane loads four neighbouring floats in one instruction. A warp-wide load then fetches 512 bytes, four full cache lines, instead of 128. The bytes moved are exactly the same. What shrinks is the number of load instructions, and with it the address arithmetic and loop overhead per byte. It requires that every row starts on a 16-byte boundary, which holds because cudaMalloc returns well-aligned memory and n is a multiple of 4.

The loop for (j = lane; j < n; j += 32) is a small case of a common pattern. A grid-stride loop lets a fixed number of threads cover any amount of work: each thread starts at its own index and steps by the total number of threads, for (i = id; i < N; i += gridDim.x * blockDim.x). Our lanes stride by the 32 threads of their warp instead of the whole grid, but the idea is the same.

Or call the library

Most production code writes none of this. cuBLAS is NVIDIA's library of tuned dense linear algebra, following the old BLAS interface (Basic Linear Algebra Subprograms). Its matvec is called GEMV, general matrix-vector multiply, and its matmul GEMM, general matrix-matrix multiply. The lab calls cublasSgemv (S for single precision, FP32) as the correct answer and as the speed to beat. One trap: cuBLAS stores matrices column by column, the Fortran way, so our row-major W looks to it like the transpose, and the call asks for CUBLAS_OP_T (matvec.cu:166). LLM servers call cuBLAS, or its newer sibling cuBLASLt, for most of their matmuls, which is why knowing its names matters when you are looking for kernels to probe.

1. Predict the value: the naive kernel is launched as 16 blocks of 256 threads on the laptop's 20 SMs. At most how many SMs have any work at all, and what is the best occupancy any SM can reach during that launch?

Answer

At most 16 SMs have work, so at least 4 sit idle, and the best occupancy is 8 / 48 ≈ 17%. A block is the unit placed on an SM and is never split across SMs, so 16 blocks can occupy at most 16 SMs. Each block is 256 / 32 = 8 warps, so an SM holding one block has 8 of its 48 warp places filled.

That is the quieter problem of listing 4.1: too little parallelism to hide latency (diagram 2.2), on top of uncoalesced loads. The near-miss is to think the 4,096 threads spread evenly over all 20 SMs. Threads only travel in blocks.

2. Someone tidies matvec_warp by deleting the if (lane == 0) in front of the final store, so all 32 lanes execute y[warp] = sum;. The results are now wrong by large, varying amounts. Using diagram 4.3, say what each row of y ends up holding.

Answer

Each row holds a partial sum from whichever lane's store the hardware happened to apply. After the five shuffles only lane 0 holds the whole row's total; lane k holds a sum over some subset of lanes, and the upper lanes hold little more than their own 128 products (diagram 4.3, the grey boxes). All 32 lanes store to the same address in one warp-wide instruction, and when lanes of one store collide, CUDA does not promise which value lands.

The near-miss is "a race between warps". No other warp writes y[warp]. The collision is inside one instruction of one warp, which is why the original code lets exactly one lane store.

3. "__syncthreads() makes every thread of the kernel wait for the others." Where does that stop being true, and what do you use when you need every thread of the grid to have finished a step?

Answer

It is true only within one block. __syncthreads() is a barrier for the threads of the block that calls it. Other blocks may not have started yet, because they are waiting for an SM, or may already have finished. A barrier across blocks inside one kernel could wait for blocks that cannot start until the waiting ones leave.

To make every thread finish a step, end the kernel and launch the next one. Launches on the same queue run in order, so the second kernel sees everything the first wrote. That boundary is the only grid-wide barrier this chapter gives you. The language-model chapters show that real servers split their work into many kernels partly for this reason.

Chapter 5

From .cu to machine code

~14 min · CUDA ISA — Last chapter we wrote the matvec three times in CUDA C++. Before an SM can run any of them, the source has to become machine code, be packed into the executable, and be found again by the driver when the program starts. This chapter follows matvec_warp through all three steps, because each step is a place where bpftime later reaches in.

Two instruction sets, one virtual and one real

NVIDIA GPUs have two instruction sets, and the difference between them explains most of this chapter. PTX, Parallel Thread Execution, is a virtual instruction set. It looks like assembly, but it is written for an imaginary GPU with unlimited registers, and it stays stable from one hardware generation to the next. SASS is the real instruction set of one particular SM design: the bits the hardware decodes. NVIDIA documents its opcodes but not its encoding, and it changes with almost every generation. PTX is to SASS roughly what LLVM IR is to x86 machine code, except that PTX is a documented, versioned language that programs ship.

The compiler names targets in two matching spellings. A virtual architecture, compute_89, names a PTX feature level: the PTX may only use features that compute capability 8.9 has. A real architecture, sm_89, names a SASS target: code for that SM design. nvcc -arch=sm_89 is shorthand for "make PTX at compute_89, make SASS for sm_89 from it, and ship both".

The compilation trajectory

NVIDIA calls the path from .cu to executable the compilation trajectory. nvcc is a driver program that runs the real tools in order. nvcc --dryrun prints them without running anything. For the lab program they are:

$ nvcc -O3 -arch=sm_89 --dryrun matvec.cu -lcublas -o matvec 2>&1 | (tool names only)
gcc  cudafe++  gcc  cicc  ptxas  fatbinary  gcc  nvlink  fatbinary  gcc  g++

Listing 5.1 — the tools nvcc 13.4 runs, in order, on this laptop.

Each one has a single job. cudafe++ splits the source into its host half and its device half, and writes small host functions, host stubs, that stand in for each kernel on the CPU side: calling matvec_warp<<<…>>> in host code calls the stub. cicc is NVIDIA's device compiler, which NVIDIA calls NVVM. It is built on LLVM and turns the device half into PTX. ptxas is the PTX assembler: it turns PTX into SASS for one real architecture, allocating real registers and scheduling instructions. Its output is a cubin, an ELF file holding the SASS of one real architecture.

fatbinary packs cubins and PTX text together into a fatbin, a container that can hold code for several architectures at once, and the host gcc compiles that fatbin into the host object file as plain data. At link time nvlink runs a device-link step and fatbinary runs again on its output. That is why the finished executable holds two sm_89 cubins: the second is a small linked image whose temporary file is named …_dlink.sm_89.cubin. Last, g++ links everything, including the CUDA runtime. By default nvcc links the runtime statically into the executable, a detail that matters very much to bpftime, as the end of this chapter shows.

There is a second road to PTX that does not use NVIDIA's compiler at all. LLVM itself has an NVPTX backend, an LLVM target that emits PTX from LLVM IR, LLVM's own typed intermediate language. Clang can compile CUDA through it. That road matters twice here. It is how this document produces real Pascal PTX, since CUDA 13.4 can no longer target Pascal. And it is the road bpftime takes to turn eBPF bytecode into PTX.

The kernels inside are named by their C++ mangled names. C++ encodes a function's parameter types into its symbol so that overloads get distinct names: _Z11matvec_warpPKfS0_Pfii is _Z, an 11-character name matvec_warp, then the parameter list: pointer to const float (PKf), the same again (S0_), pointer to float (Pf), int, int. c++filt undoes it. Mangled names are what the driver uses to find a kernel. They are also what you write in a bpftime probe's section name, so you will be reading them a lot.

From bytes in a file to a kernel on the device

The host stubs also contain a static constructor, which runs before main. It calls two functions in the CUDA runtime. __cudaRegisterFatBinary hands the runtime a pointer to the fatbin. __cudaRegisterFunction is then called once per kernel, with the address of the kernel's host stub and its mangled device name. From then on the runtime can turn "the host called the stub at this address" into "launch the device function with this name". The stub's own launch goes through the runtime too. In a CUDA 13 binary it calls an internal entry, __cudaLaunchKernel; older runtimes have the stub call the public cudaLaunchKernel. Which entry a binary uses matters to any tool that intercepts launches.

At the first real CUDA call, the runtime creates a CUDA context, the driver's per-process state for one GPU: its address space on the device, its loaded code, its queues. A loaded piece of device code inside a context is a module, and one kernel inside a module is a function. The runtime does this through the CUDA driver API, the C interface of libcuda.so, whose functions start with cu: cuModuleLoadData loads a module from bytes in memory, and cuModuleGetFunction finds a kernel in it by its mangled name. Programs that generate code at run time, like the Triton compiler in the language-model part (Part V), call those functions directly.

When the driver loads a module from a fatbin, it picks the code for this GPU. If there is a cubin whose SASS this GPU can run, it uses that. If there is none but there is PTX at or below this GPU's compute capability, the driver runs its own built-in copy of ptxas: JIT compilation, just in time. The result is saved in the compute cache, by default ~/.nv/ComputeCache, so the next run of the same program skips the compile. Since CUDA 12.2, loading is also lazy on Linux by default: a module is loaded only when one of its kernels is first launched.

One build detail decides whether a tool can reach those moments. Because nvcc links the runtime statically by default, __cudaRegisterFatBinary in the lab binary is a local symbol: nm marks it with a lower-case t. A preloaded library cannot interpose on a function that is not exported. Build with nvcc -cudart shared and the registration calls go through libcudart.so, where they can be hooked. bpftime's own examples are all built that way.

Recap

PTX is NVIDIA's stable virtual instruction set; SASS is the real one, different per SM design. nvcc runs cudafe++ to split the source, cicc (NVVM) to make PTX, ptxas to make SASS in a cubin, and fatbinary to pack cubins and PTX into a fatbin inside the executable's .nv_fatbin section. Clang, and anything else on LLVM, reaches the same PTX through the NVPTX backend. Before main, host stubs register the fatbin and every kernel's mangled name with the runtime. At the first launch the driver loads a module into the context, using matching SASS if it has it and JIT-compiling PTX into the compute cache if not; a statically linked runtime keeps the registration functions out of reach of a preloaded hook.

1. Predict the outcome: matvec_multi from listing 5.3 is copied to four machines: the laptop, an H100, a newer GPU of compute capability 10.0, and the customer's P5000. On each, which code runs, or what goes wrong?

Answer

The laptop runs the sm_89 cubin directly and the H100 runs the sm_90 cubin. The 10.0 GPU has no matching cubin, so the driver JIT-compiles the compute_89 PTX: PTX can be compiled for any compute capability at or above its own. 2. On a fresh machine, a program sits for about 40 seconds before its first kernel runs. The second run starts at once. Deleting ~/.nv/ComputeCache brings the 40 seconds back. What is happening, and how would you remove the delay for good?

Answer

The driver is JIT-compiling PTX at the first launch because the fatbin holds no SASS for this GPU, and then it caches the result (diagram 5.3, the else branch). Large libraries can take this long, because every kernel is compiled.

Removing the cache removes the stored result, so the compile happens again. The lasting fix is to build with a real architecture for this GPU, for example adding -gencode arch=compute_89,code=sm_89, so the driver finds SASS and skips the JIT. You can confirm it with cuobjdump -lelf: no ELF line for your sm_ means JIT. The near-miss is "the GPU or the driver warming up". Nothing warms up; a compiler runs.

3. "PTX is forward-compatible, so PTX shipped today will run on any newer NVIDIA GPU." Give two conditions under which that stops being true.

Answer

First, arch-specific targets. PTX built for a virtual architecture with an a suffix, such as compute_90a, may use instructions that exist only on that one design. Hopper's largest tensor-core matrix instructions are the best-known case, and that PTX cannot be compiled for any other GPU.

Second, the driver has to understand the PTX. PTX carries a .version line (9.4 from CUDA 13.4, 8.8 from clang 22). An older driver that predates that PTX version cannot JIT it, even on a GPU it supports. That is a live risk on a Pascal machine held on an old driver branch. The sentence is true for plain compute_XX PTX, compiled by a driver at least as new as the toolkit that wrote it.

Chapter 6

Reading PTX

~14 min · ISA — Last chapter showed PTX as the point where NVIDIA's compiler and LLVM produce the same kind of text, and the point where bpftime will splice its code into ours. Now we learn to read that text, on the PTX of matvec_warp itself and on a few lines of the PTX that bpftime injects.

The frame of a PTX file

Every PTX file opens with three lines. .version 9.4 is the PTX ISA version, the edition of the language this file is written in; CUDA 13.4 writes 9.4, clang 22 writes 8.8, and bpftime's own trampoline file says 8.1. .target sm_89 is the virtual architecture, the feature level the code may use. .address_size 64 says pointers are 64 bits.

Then come functions. A kernel is declared with .entry: an entry point the host can launch. A device function that other device code calls is a .func. .visible makes the name visible outside this file, which is how the driver finds it by its mangled name. The kernel's arguments are declared in the .param state space, one line each, with the type of each argument:

.visible .entry _Z11matvec_warpPKfS0_Pfii(
	.param .u64 _Z11matvec_warpPKfS0_Pfii_param_0,     // const float *W
	.param .u64 _Z11matvec_warpPKfS0_Pfii_param_1,     // const float *x
	.param .u64 _Z11matvec_warpPKfS0_Pfii_param_2,     // float *y
	.param .u32 _Z11matvec_warpPKfS0_Pfii_param_3,     // int n
	.param .u32 _Z11matvec_warpPKfS0_Pfii_param_4      // int d
)
{
	.reg .pred 	%p<13>;
	.reg .f32 	%f<40>;
	.reg .b32 	%r<43>;
	.reg .b64 	%rd<40>;

Listing 6.1 — the head of matvec_warp, from nvcc -ptx -arch=sm_89 (CUDA 13.4). Comments added.

The four .reg lines declare virtual registers: as many as the code wants, each with a type. %p registers are predicates, one bit each. %f registers hold 32-bit floats, %r 32-bit untyped bits, %rd 64-bit values such as addresses. %r<43> means "43 of these". The PTX for this kernel uses about 140 virtual registers. ptxas will fit them into 40 real ones, the number cuobjdump reported in the SM chapter.

State spaces: every address says where it points

A state space is PTX's name for a kind of storage, and every load and store names one. .reg is registers. .param holds kernel and function arguments. .global is global memory. .shared is the block's shared memory. .local is per-thread memory in DRAM. .const is constant memory. So a load from global memory is ld.global, a load of an argument is ld.param, a store to shared memory is st.shared. The instruction's suffix then gives the type: ld.global.f32 loads one 32-bit float.

C pointers do not carry a state space, so PTX also has generic addresses, which can point into global, shared or local memory and are resolved by hardware. The kernel receives its pointers as generic addresses and converts them once at the top with cvta.to.global.u64, "convert address to the global space". After that it can use the faster ld.global directly.

Reading the body

The kernel's first job is to work out who it is. It reads special registers: read-only registers the hardware fills in for each thread. %tid is threadIdx, %ntid is blockDim, %ctaid is blockIdx and %nctaid is gridDim. Others give the thread's place in the hardware: %laneid its lane, %warpid its warp slot on the SM, %smid which SM it is running on, %globaltimer a 64-bit nanosecond clock and %clock64 the SM's cycle counter. Branches work through predicates. setp.ge.s32 %p1, %r2, %r14 sets predicate %p1 to "warp ≥ d". @%p1 bra … is a guarded instruction: it runs only in the lanes whose %p1 is true. Any PTX instruction can carry a guard, branches and arithmetic alike, and this is the instruction-level form of the divergence in the SIMT chapter. Lanes that disagree about %p1 take the branch differently, and the hardware's active mask does the rest.

The inner loop shows two things that earlier chapters predicted. The addresses step by 128 bytes per copy, 32 lanes × 4 bytes, so each warp-wide load is one cache line: coalescing, visible in the offsets. And the loads are ld.global.nc. The .nc means non-coherent: the load may go through a read-only cache that does not keep up with writes made during the kernel. The compiler may only use it because const and __restrict__ promised that W and x do not change while the kernel runs. The float4 kernel's loads are ld.global.nc.v4.f32 {%f13, %f14, %f15, %f16}, [%rd35]: a vector load, four registers filled by one instruction. fma.rn.f32 is a fused multiply-add, one rounding for the whole a × b + c, rounding to nearest.

When threads must agree: atomics, fences and scopes

Our matvec never needs two threads to coordinate. bpftime does, so here is the minimum. An atomic instruction reads, modifies and writes one memory location so that no other thread's access can land in between. atom.global.cas.b32 is compare-and-swap, atom.global.add.f32 an atomic add, atom.global.exch.b32 an exchange.

A memory scope names the set of threads a guarantee covers. .cta is one block. .cluster is a group of blocks, on Hopper only. .gpu is every thread on this GPU. .sys is the whole system: this GPU, the host CPUs, and other GPUs. An atomic at .gpu scope is atomic for every thread on the device and makes no promise about the CPU. A fence, written membar in its oldest form, orders one thread's own memory accesses: everything before it becomes visible, to everyone in the named scope, before anything after it. membar.sys is the strongest. On Volta and later, PTX also has fence and loads and stores with acquire and release semantics, which give finer control. Pascal has only membar.

Now read the code bpftime injects when a GPU probe has to ask the host for something. This is its own PTX, from trampoline_ptx.h:

Every piece is from this chapter. A compare-and-swap loop is a spinlock, and the lock is one word in global memory, so it serialises every thread on the GPU that reaches this code. The request is written to memory that the host can also see, and membar.sys makes sure the host sees the request before it sees the flag. Calls

A .func is called with call. Arguments and the return value travel through .param variables that the caller declares, and ptxas later decides which real registers carry them. bpftime's helpers are .funcs with names like _bpf_helper_ext_0502, which returns the value of %globaltimer. Recap

A PTX file declares its ISA version, its target and its address size, then .entry kernels and .func device functions with arguments in the .param space and unlimited typed virtual registers. Every memory instruction names a state space (.global, .shared, .local, .const, .param), and generic C pointers are converted once with cvta. Threads learn who they are from special registers such as %tid, %ctaid, %smid and %globaltimer. Branches are predicates plus guarded instructions. Coordination uses atomics and fences at a named scope, .cta to .sys, and bpftime's call to the host is a .gpu-wide spinlock and .sys fences around a request in memory both sides can see.

Check yourself

1. Predict the value: in the unrolled loop of listing 6.2, the address registers step by 512 bytes per loop iteration. For the float4 kernel, which loads 16 bytes per lane and is unrolled the same four times, what would you expect the step to be, and why?

Answer

2,048 bytes. Per copy of the loop body, each of the 32 lanes moves 16 bytes, so the warp advances 32 × 16 = 512 bytes. Four copies per iteration make 4 × 512 = 2,048. The PTX agrees: the float4 loads use offsets like [%rd38+-1024], two copies' worth (1,024 bytes) behind the address register.

The near-miss is 512, which is the step for the scalar loop. The rule behind both numbers is lanes × bytes per lane × unroll factor. It is worth being able to read a loop's stride straight out of PTX, because the stride is how you see whether a warp's loads are coalesced.

2. A probe uses atom.global.add.u64 at the default scope to count events into a counter in memory that the host can read directly. The host polls the counter while the kernel runs, and its last reading, taken as the kernel ends, is sometimes lower than the true count. Using diagram 6.2, what is missing?

Answer

System scope. A plain atom.global is atomic among GPU threads, at .gpu scope, and makes no promise about when or in what order a host thread sees the result. A host reading during the kernel can see stale values. For a true total, use atom.sys on memory the host can see, or read only after the host has synchronised with the kernel's end.

This is what membar.sys does in listing 6.3. The near-miss is to suspect lost atomic updates. Atomics on the GPU are never lost; the host is reading before the updates are guaranteed to be visible to it.

3. "PTX is the same on every GPU, so a PTX file written for Ada can be used for Pascal." Where does that stop being true? Use the table.

Answer

It stops at two points. First, the .target: PTX targeting sm_89 may use features that 6.1 lacks, and the driver will not JIT it downward at all (the compiler chapter's rule). Second, the instructions themselves. Code that uses fence, acquire loads or scoped loads needs sm_70 or later, and .cluster needs sm_90.

The language is shared; the feature set is versioned. That is exactly why bpftime compiles its trampoline for sm_61 and uses only membar and scoped atom, which work on all three benches (listing 6.3's .target sm_61).

Chapter 7

SASS: what the SM runs

~13 min · ISA — Last chapter we read matvec_warp as PTX, the virtual instruction set that is the same on every bench. Now ptxas turns it into SASS for one real SM, and the three benches finally stop looking alike. This is the code the warp scheduler of the SM chapter issues.

What ptxas decides

PTX left four decisions open, and ptxas makes all of them. It maps about 140 virtual registers onto real ones, a job called register allocation. It chooses the real instructions. It orders them so that slow operations start early. And it writes, into every instruction, the timing hints the scheduler needs. The result for Ada is cuobjdump -sass's listing, and here is the start of matvec_warp:

Read it against listing 6.2 and every line has a twin. S2R reads a special register: SR_TID.X is %tid.x. IMAD is integer multiply-add, and c[0x0][0x0] is blockDim.x, which lives in constant bank 0 next to the kernel's arguments; d is at c[0x0][0x17c]. ISETP sets a predicate, and @P0 EXIT is the guarded early return. Registers are named R0 to R254, predicates P0 to P6, and RZ and PT are a register that always reads zero and a predicate that is always true.

Two kinds of names have no PTX twin. ULDC and the UR4 it writes belong to the uniform datapath, which Turing introduced: a small set of registers and instructions for values that are the same in every lane of a warp, such as a base address. Computing such a value once per warp instead of 32 times saves ordinary registers and lane work. And BSSY B0, 0xaf0 with its later partner BSYNC B0 marks a convergence barrier: lanes that split up inside the region wait at BSYNC until all of them arrive. This is the reconvergence of the SIMT chapter, written as two instructions. Pascal SASS uses an older pair, SSY and SYNC, that pushes and pops the mask stack instead.

Timing hints and scoreboards

A CPU core discovers at run time which instructions are ready, with large out-of-order hardware. An SM does very little of that, because the compiler has already written the answer down. Each SASS instruction on Volta and later carries control codes in spare bits of its 128-bit encoding. They are not shown by cuobjdump; the microbenchmark papers in the reading list decoded them. They say how many cycles to wait before this warp's next instruction can issue, whether the scheduler should prefer to switch warps here, and which scoreboard to use.

A scoreboard is a small counter the hardware keeps per warp for operations whose latency is not fixed, such as memory loads and shuffles. The instruction that starts such an operation names a scoreboard to set. The instruction that needs its result names the scoreboards to wait on. Until the data arrives, that warp is not ready, and the scheduler issues from another one. Fixed-latency arithmetic like FFMA needs no scoreboard: the compiler knows it takes a few cycles and writes a stall count instead.

Registers, spills and occupancy

Every register a thread holds is multiplied by every resident thread. Using more registers can make one warp faster, through more unrolling and more loads in flight, and the SM slower, through fewer resident warps. Diagram 7.3 draws the rule from the SM chapter for every register count from 16 to 128.

You can push back. -maxrregcount=N caps the registers of every kernel in a file. __launch_bounds__(threads, blocks) on one kernel tells ptxas to fit that many blocks of that size per SM. If the code needs more registers than allowed, ptxas stores some values in local memory and reloads them later. That is a spill, and spills go to DRAM, through the caches. Recap

ptxas turns PTX into SASS for one SM design. It allocates real registers, picks real instructions, orders them so that slow ones start early, and writes control codes into each instruction: stall counts for fixed-latency arithmetic, and scoreboards that variable-latency loads set and their consumers wait on. For our matvec on Ada it unrolled the loop sixteen times and issued twenty-two loads before the first FFMA, reconverged divergent paths with BSSY and BSYNC, and used the uniform datapath for warp-wide values. More registers mean fewer resident warps, and capping them causes spills to local memory, visible as STL and LDL. The same PTX on Hopper becomes different SASS with fewer registers.

That fits inside Ada's cap of 48, and this kernel can be fully resident (diagram 7.3), so there is room to spare. 2. A colleague adds __launch_bounds__(1024, 2) to a kernel to "raise occupancy". It gets slower, and -Xptxas -v now reports spill stores and loads. Explain the chain from the attribute to the slowdown.

Answer

Two blocks of 1,024 threads is 2,048 threads per SM, so ptxas must fit every thread into 65,536 / 2,048 = 32 registers. If the code wants more, it spills the excess to local memory (listing 7.4). Local memory is DRAM, so a memory-bound kernel gains extra traffic on the resource that limits it, and the extra warps cannot make up for that.

On Ada there is a second problem: the SM holds at most 1,536 threads (48 warps), so the second block cannot be resident anyway, and the cap buys nothing. The near-miss is "more occupancy is always better". Occupancy only helps if latency was the limit and it does not add bytes.

First, register counts and spills, and so occupancy. An injected probe adds code to the kernel and can push it over a register boundary (diagram 7.3), costing warps or causing spills that the PTX gives no sign of. Second, the real order of instructions: loads hoisted twenty-two deep, the loop unrolled sixteen times. A probe's timing and the kernel's own timing are both shaped by it.

Others count too: kernel arguments at architecture-specific constant-bank offsets, BSSY/BSYNC regions, and Hopper's memory descriptors. The sentence is right that the meaning is fixed in PTX. It is wrong that the cost is.

Chapter 8

The host side: streams, pinned memory, the launch path

~13 min · CUDA — The language part (Part II) turned our matvec into SASS inside a fatbin, and showed the driver loading it into a context. Now the program runs it. This chapter is everything that happens on the host between "launch matvec_warp" and the first warp starting: the queues, the memory the host and the GPU can both see, and the path a launch takes down to the hardware.

Optional neighbours: the GPU-sharing dossier's How a launch reaches the silicon (chapter 2) follows the same launch below the driver, through channels and pushbuffers. The SR-IOV dossier's Just enough PCIe (chapter 1) covers the DMA and MMIO that this chapter uses as words.

Two APIs, one driver

The CUDA runtime is a convenience layer: every runtime call becomes one or more driver API calls. The runtime creates a context for you, the primary context, one per GPU per process. It loads modules from the registered fatbins, and it turns kernel<<<g, b>>>(args) into a driver launch. With the driver API you do each step yourself: cuCtxCreate or retain the primary context, cuModuleLoadData, cuModuleGetFunction to get a CUfunction, the driver's handle for one kernel in one loaded module, and cuLaunchKernel. Both roads end in cuLaunchKernel-like entry points in libcuda.so, which is why a tool that hooks the driver sees launches from both.

Streams and events

A stream is an ordered queue of GPU work: kernel launches, copies, memory sets. Work in one stream runs in the order it was queued, each item starting only after the one before has finished. Work in different streams has no order between them, so the GPU may run it at the same time. Every launch and every asynchronous copy names a stream; the fourth value inside <<<…>>> is the stream.

If you name none, you get the default stream, and it has a historical quirk. The legacy default stream waits for work in every other stream of the context and makes them wait for it, which serialises programs that thought they were concurrent. Compiling with --default-stream per-thread gives each host thread its own default stream that behaves like an ordinary one. The runtime then exports per-thread variants of its entry points, with a _ptsz suffix such as cudaLaunchKernel_ptsz, which is why bpftime hooks both names.

An event is a marker queued into a stream. When the GPU reaches it, it records a timestamp. cudaEventRecord queues one, cudaEventSynchronize waits until it has been reached, and cudaEventElapsedTime gives the milliseconds between two of them. The lab program times every kernel this way (matvec.cu:104–122): one event before 200 launches, one after, both measured on the GPU's own clock, so host-side noise stays out.

Memory the host and the GPU can both see

Copies between host and device are done by the GPU's copy engines, DMA engines that move data across PCIe while the SMs do other work. A DMA engine needs host memory that stays at a fixed physical address for the whole transfer. Ordinary pageable memory, from malloc, can be moved or swapped out by the host kernel at any time. So cudaMemcpy from a pageable buffer first copies it, with the CPU, into a hidden buffer the driver has locked, and DMAs from there. Pinned memory, also called page-locked, is host memory locked in place so that the copy engine can read it directly. cudaMallocHost allocates it; cudaHostRegister pins memory you already have. Pinned memory is what makes cudaMemcpyAsync truly asynchronous, and what lets copies overlap kernels.

Pinned memory can go one step further. Mapped memory, or zero-copy memory, is pinned host memory that is also mapped into the GPU's address space. A kernel can then load and store it directly: every access crosses PCIe, so it is slow for bulk data, but no copy is needed at all, and the host sees the writes. bpftime relies on exactly this. Its shared-memory segment, the one that holds the request area of listing 6.3, is registered in the target process with one call:

cudaError_t err =
        cudaHostRegister(base_addr, seg_size, cudaHostRegisterMapped);

Listing 8.1 — bpftime/runtime/src/bpftime_shm_internal.cpp:1243–1244. The whole bpftime shared segment, pinned and mapped into the GPU's address space.

Three more kinds complete the picture. Unified virtual addressing (UVA) puts host and device allocations in one 64-bit address space, so the value of a pointer says which memory it is in, and cudaMemcpy can work out the direction itself. Managed memory, from cudaMallocManaged, is a single allocation valid on both sides: pages move between host and GPU on demand, when one side touches a page the other side holds, through hardware page faults that Pascal introduced. And CUDA IPC lets one process share a device allocation with another, through a handle from cuIpcGetMemHandle that the other process opens. bpftime's GPU array maps use it: the bpftime process that loads the probe allocates them in device memory, and the process being probed opens them (runtime/src/bpf_map/gpu/nv_gpu_per_thread_array_map.cpp:74).

The launch, all the way down

Here is one launch of matvec_warp, from the call to the first warp. The runtime finds the CUfunction for the stub, packs the five arguments, and calls into the driver. The driver writes the launch, as GPU commands, into a pushbuffer: a ring of commands in memory the GPU can read, belonging to one hardware queue. Then it writes the new end position to a doorbell, a register on the GPU mapped into the process's address space. The GPU's front end sees the doorbell change, fetches the commands, and hands the grid to the block scheduler, which places blocks on SMs.

Notice what is missing. After setup there is no system call. The pushbuffer and the doorbell were mapped into the process when the context and its queues were created, so a launch is a few memory writes in user space. That is why a launch costs only a few microseconds of CPU time. It is also why a uprobe on cuLaunchKernel sees every launch and a probe in the host kernel sees none of them.

The time from the launch call to the first warp running is launch latency. On an idle GPU it is microseconds. When a stream already has work queued, the new kernel also waits for everything ahead of it. bpftime's launchlate example measures exactly this gap, with a uprobe on cudaLaunchKernel on the host side and a GPU probe at the kernel's entry. For a kernel like ours, which takes a few hundred microseconds, a few microseconds of launch cost is noise. For the tiny kernels a language model runs for each new token, which can take tens of microseconds each, the CPU's launch work can become the limit: the GPU finishes each kernel before the CPU has queued the next.

CUDA graphs: launch a whole sequence at once

A CUDA graph records a fixed sequence of kernels and copies, with their dependencies, once, and then launches the whole sequence with a single call. You can build one node by node, or capture it: begin capture on a stream, run your normal launches, end capture. The launches are recorded rather than run. cudaGraphInstantiate prepares the graph for launch, and cudaGraphLaunch runs it, as often as you like. The CPU cost of a hundred launches becomes the cost of one.

Graphs matter twice in this document. vLLM captures the step that makes each new token as CUDA graphs, which is a large part of why it is fast. And a graph launch does not call cudaLaunchKernel once per kernel, so a uprobe on that function sees nothing while a graph runs. A tool that wants to change which kernel runs has to act when the graph is built. bpftime does it in two places. Launches made during stream capture still go through its launch hooks, so the captured graph records the patched kernel. Graphs built node by node go through cuGraphAddKernelNode and the calls that set node parameters, which bpftime also hooks to swap in the patched kernel (attach/nv_attach_impl/nv_attach_impl_frida_setup.cpp:625–776). A graph captured before bpftime attached keeps the original kernel.

Chapter 9

Scheduling, from grid to warp

~14 min · HW TOOLS — The last chapter got our launch as far as the GPU's front end. This one follows it the rest of the way: who decides which kernel runs, which SM gets each block, and which warp issues on each cycle. It also finishes the occupancy sum that the SM chapter left open.

Optional neighbours: the GPU-sharing dossier's Time-slicing (chapter 4) and MPS (chapter 5) cover the top level of this chapter, sharing one GPU between processes, in depth. This chapter skips graphics work, MIG, and green contexts, CUDA's newer way to give a stream a fixed set of SMs.

Five levels, five clocks

Scheduling on a GPU happens at five levels, and each one works on its own time scale. At the top, contexts from different processes take turns. The GPU's runlist scheduler gives each context a time slice of the whole GPU, in the millisecond range, and two contexts never run kernels on the SMs at the same instant unless MPS has merged them. Within a context, streams feed a fixed set of hardware work queues. NVIDIA calls this Hyper-Q. A context gets 8 queues by default, and CUDA_DEVICE_MAX_CONNECTIONS sets anywhere from 1 to 32. When there are more busy streams than queues, two streams share a queue and their work is serialised, a false dependency that no line of your code asked for.

Below the queues, the GPU's front end takes kernels from the queues and hands them to the work distributor, the block scheduler. Up to 128 kernels can be resident on Ada and Hopper, and 32 on the P5000's compute capability 6.1. The work distributor places each block on an SM that has room for all of it. The block then stays on that SM until it finishes. At the bottom, each SM sub-partition's warp scheduler picks one eligible warp per cycle, as in the SM chapter.

Where a block fits: finishing the occupancy sum

The work distributor places a block on an SM only when four resources all have room for the whole block. These are warp slots (48 per SM on Ada), block slots (24 per SM), registers (65,536 per SM) and shared memory (100 KB per SM). The number of blocks that fit is the smallest of the four limits. A block is never split, so the remainder of a resource that cannot hold a whole block goes unused. That is the limit the SM chapter promised, and it lowers the float4 kernel's 36 warps.

Waves, and the tail

Our matvec_warp launch is 512 blocks. The laptop's 20 SMs hold 6 blocks each, 120 at a time. So the grid runs as 512 / 120 = 4.27 waves: four rounds in which every block slot of the GPU is busy, and a fifth in which only 32 blocks are left for 120 slots. The time when only that last partial wave is running is the tail. During it most of the GPU is idle while the kernel is still "running". NVIDIA's kernel profiler reports the number as launch__waves_per_multiprocessor, and its documentation warns that partial waves cause exactly this.

Real blocks do not run in lockstep rounds. A new block starts whenever an old one finishes, so the boundaries between waves blur after the first. The model is still the right first estimate, and the tail at the end is real. It costs most when there are few waves, because then the partial one is a large share of the whole. Now move the same launch to an H100. It has 132 SMs, and at sm_90's 32 registers per thread each SM holds 8 of these blocks: 1,056 slots. Our 512 blocks fill less than half of one wave.

There are three ways out of a tail. You can give the GPU more, smaller pieces of work, so the partial wave is a small share. You can do more work per launch, which is what batching does for LLM serving. Or you can write a persistent kernel: launch exactly as many blocks as fit at once, 120 on the laptop, and have each block loop, taking the next piece of work from a counter in global memory with an atomic add until none is left. A persistent kernel has no waves and no per-launch cost after the first. In exchange it holds every SM until it is done, so nothing else from the same context runs beside it. CUDA does not promise that 20 blocks land on 20 different SMs. bpftime's threadscheduling example reads %smid from inside the kernel and shows you where they went.

What a warp does while it waits

Once its block is placed, each warp is in one of a few states on every cycle. It can be selected, issuing an instruction. It can be eligible but not selected, ready while another warp of the same sub-partition issues. Or it can be stalled, because its next instruction cannot issue yet. A stall always has a reason, and NVIDIA's kernel profiler samples the warps' states and names the reasons. These are the stall reasons, reported as metrics like smsp__pcsamp_warps_issue_stalled_long_scoreboard and attributed to the instruction that was waiting.

Kernels side by side, and preemption

Two kernels in different streams of one context can be resident at the same time, but only if the first leaves room. Our 512-block matvec fills every slot for four waves. A second kernel's blocks get slots only as the first kernel runs out of blocks, so in practice concurrent kernels mostly overlap in each other's tails. Streams pay off most with small kernels that each fill only a few SMs, which is the shape of the work a language model does for each new token.

A running block can also be stopped. When a context's time slice ends, or cuda-gdb halts a kernel, the GPU preempts the running blocks: it saves each warp's registers and the block's shared memory to device memory, and restores them later. On Ada and Hopper this happens at instruction granularity. For Pascal the sources disagree. The GP104 whitepaper says Pascal preempts CUDA compute at instruction level. NVIDIA's Pascal tuning guide calls it a GP100 feature, and the P5000 is a GP104. The lab program now prints cudaDevAttrComputePreemptionSupported; run it on the P5000 before relying on either. A preempted block may resume on a different SM. That is why the PTX manual says %smid may change during execution, and why a probe should treat it as a sample.

9 blocks of 4 warps, 36 warps, 75% occupancy. A block now needs 56 × 128 = 7,168 registers, and 65,536 / 7,168 = 9.14, so 9 blocks fit by registers. Warp slots allow 48 / 4 = 12 and block slots 24, so registers bind at 9. With 256-thread blocks only 4 fitted, 32 warps.

The block size changed the answer because a block is placed whole: smaller blocks waste less of the register file at the end. The near-miss is to think occupancy depends only on registers per thread. It depends on registers per block too, which is why block size is a tuning knob.

2. You run bpftime's threadscheduling probe against matvec_warp on the laptop and on an H100. The laptop shows all 20 SMs with about 25 or 26 blocks each. The H100 shows every SM with 3 or 4 blocks. A colleague concludes the H100 is "barely used". What do the two histograms show, and what can they not show?

Answer

They show placement: 512 / 20 ≈ 25.6 blocks per laptop SM over about 4.3 waves, and 512 / 132 ≈ 3.9 blocks per H100 SM in a single partial wave (diagram 9.2). A count of blocks per SM has no time in it, so it cannot show whether the blocks ran together, in waves, or in a tail.

Nor can it show whether 24 to 32 warps per SM were enough to keep the H100's memory busy, which is the question that matters for a memory-bound kernel. For that you need time: the kernel's duration against the 20 µs bandwidth floor of the memory chapter, or timestamps from %globaltimer in the probe. The near-miss is to read low occupancy as slow. It can be, and that is a measurement.

3. Your probe records %smid at a block's first instruction and again at its last, and on a shared GPU a few blocks report two different SMs. Is the probe broken?

Answer

No. Those blocks were preempted, most likely at the end of a time slice when another process had work on the GPU, and resumed on a different SM. The PTX manual documents that %smid may change during execution for exactly this reason.

Treat %smid as a sample taken when you read it, and read it once per event you care about. On a GPU used by one process the effect should be rare; on a shared GPU it is normal. The near-miss is to suspect the helper. Helper 509 reads the register correctly; the block moved.

Measuring: the tools and what each one sees

~12 min · TOOLS — Every number so far has been a prediction: 311 µs at best, 4.27 waves, mostly long_scoreboard stalls. This chapter is about the tools that turn predictions into measurements. Each one sees some layers of the system and is blind to others, and the most common measuring mistake is asking a question of a tool that cannot see the layer it is about.

Seven layers, six kinds of tool

Diagram 10.1 is the map for this chapter. The rows are the layers you might want to measure, from your program's own code down to single instructions inside a kernel, plus the device as a whole. The columns are the tools. Read it by row: first decide which layer your question is about, then pick a tool with a dot in that row. The last column, bpftime, is what the eBPF part (Part IV) builds; it is here to show which gap it fills.

The whole device: nvidia-smi, NVML, DCGM

nvidia-smi is a command-line front end to NVML, the NVIDIA Management Library. NVML reports device-wide numbers that the driver samples: memory used, clocks, power, temperature, PCIe traffic, and utilization. nvidia-smi dmon prints them once a second, and nvidia-smi pmon does the same per process.

The utilization number is the trap. NVML defines GPU utilization as the "percent of time over the past sample period during which one or more kernels was executing on the GPU" (/opt/cuda/targets/x86_64-linux/include/nvml.h:245). That is time with a kernel running, whatever the kernel uses. Our naive matvec, which leaves 4 of 20 SMs empty and the rest at 17% occupancy, shows 100% while its loop runs.

DCGM, NVIDIA's Data Center GPU Manager, adds profiling fields that answer the question people meant to ask. Field 1002 is the share of cycles in which an SM has at least one warp resident, field 1003 is occupancy, and field 1005 is the share of cycles in which the memory interface is busy. They are still device-wide and sampled, so they cannot tell one kernel from another, but they are cheap enough to export to Prometheus from every server, with NVIDIA's dcgm-exporter.

The timeline: Nsight Systems, NVTX and CUPTI

Nsight Systems, nsys, records a timeline of everything the program does with the GPU: each CUDA API call on each host thread, each kernel and copy on the GPU with its start and end time, and, if you ask, calls into OS libraries. It costs little per event, so you can trace a whole program run. Its default treats a CUDA graph as one item; --cuda-graph-trace=node shows each kernel in it, at higher cost. NVTX is a small annotation library: code that calls nvtxRangePush("load_weights") and nvtxRangePop() gets a named bar on the timeline. PyTorch exposes it as torch.cuda.nvtx.

Underneath Nsight Systems and Nsight Compute sits CUPTI, the CUDA Profiling Tools Interface. It is a library with several parts. The Activity API delivers buffered records of kernels and copies with GPU timestamps. The Callback API calls your function on entry to and exit from every CUDA API call. PC sampling and PM sampling read the hardware's samplers, and the range profiler collects counters. The tools load a small injection library into your process, and that library uses CUPTI. If you want an always-on timeline of every kernel in your own service, CUPTI's Activity API is the conventional answer. It works without changing kernels, and it sees start and end only.

One kernel, all its counters: Nsight Compute

Nsight Compute, ncu, answers "why is this kernel as fast as it is". It reads hundreds of hardware counters, but the hardware can count only a limited set at once, so ncu runs the kernel several times, one replay pass per group of counters. Before the first pass it saves all the GPU memory the kernel can reach; before each later pass it restores the part the kernel wrote, so every pass sees the same inputs.

Three defaults make ncu durations differ from real ones. It locks the GPU clocks, to boost by default in current versions. It flushes the caches before every pass. And it runs each profiled kernel alone, with kernels serialised. Its sections map onto this document's chapters. SpeedOfLight gives achieved compute and memory throughput as a share of peak, the two axes of the roofline in the memory chapter. LaunchStats and Occupancy give the limits of the scheduling chapter, and WarpStateStats its stall reasons. MemoryWorkloadAnalysis shows traffic through each cache level, and SourceCounters puts stall samples on individual SASS lines. Nsight Compute supports Turing and newer. For the P5000 it dropped Pascal in 2020.1, and the profiler for Pascal is the older nvprof from a CUDA 12.x toolkit, which CUDA 13.0 removed.

Correctness and instrumentation: compute-sanitizer, cuda-gdb, NVBit

compute-sanitizer runs a program under one of four checkers. memcheck finds out-of-bounds and misaligned accesses, racecheck finds races on shared memory, initcheck finds reads of device memory nobody wrote, and synccheck finds invalid uses of barriers. Run it on every new kernel once; it is slow, and it is right. cuda-gdb is gdb extended to stop inside kernels, switch between blocks and threads, and step through code. The 13.x release needs compute capability 7.5 or newer, so the P5000 needs a 12.x toolkit's version.

NVBit, from NVIDIA Research, is a library for writing your own instrumentation tools. An NVBit tool is loaded into the application. When each kernel's machine code is loaded onto the GPU for the first time, NVBit lets the tool inspect its SASS and insert calls to the tool's own device functions before or after chosen instructions. It needs no source and no PTX, so it works on any compiled application, and it supports compute capability 3.5 to 12.1, Pascal included. NVBit is bpftime's nearest relative, and the difference between them is where in the pipeline each one edits.

Host eBPF: what the kernel can see

From the host kernel, eBPF sees two layers. Uprobes on libcudart.so and libcuda.so see every API call with its arguments, as the host-side chapter showed. Each hit traps into the kernel, so a uprobe on a call made a hundred thousand times a second is a cost you can measure. Kprobes on the NVIDIA driver see its system calls. The open kernel module's ioctl handler is nvidia_unlocked_ioctl, so a kprobe there sees context creation, memory allocation, pinning, and the waits that sleep in the kernel. It does not see launches, which never enter the kernel. And nothing on the host sees what happens inside a kernel after it starts. That gap, the empty bottom-right of diagram 10.1, is what the eBPF part fills.

Chapter 11

Three generations: Pascal, Ada, Hopper

~12 min · HW ISA — Every chapter so far has ended with a table across the three benches. This one puts them side by side on purpose: what stayed the same from 2016 to 2022, what the P5000 lacks, and what only the H100 has. It ends with the support matrix that decides which software runs where.

What stayed the same

Start with what did not change, because it is most of the machine. All three benches run warps of 32 threads. Each SM has 65,536 registers and 128 FP32 lanes. The P5000 and the laptop both have 20 SMs. The programming model, the grid, blocks, warps and shared memory, is the same, and so is the idea of PTX as a portable layer above each generation's SASS. Our three matvec kernels compile for all three from the same source. What changed is how much memory bandwidth feeds those lanes, what the SM can do besides FP32 arithmetic, and the tools and drivers that still support each one.

Diagram 11.1 puts the three benches on one roofline. From the P5000 to the H100, memory bandwidth grew 11.6 times, from 288 to 3,352 GB/s, and FP32 throughput 7.5 times. The tensor cores grew far more: the H100's dense FP16 matrix throughput is about 1,000 TFLOPS. Our matvec, at 0.5 FLOP per byte, sits on the sloped part of every roof, so on every bench its speed is set by bandwidth alone. The red point is a preview of the LLM chapters. Even 64 sequences decoding at once, which turns the matvec into a small matrix multiply with 64 FLOP per byte, leaves the H100 memory-bound.

Pascal: what the P5000 does not have

Pascal predates three things the rest of this document takes for granted. First, independent thread scheduling. A Pascal warp has one program counter for all 32 lanes. After a divergent branch, the hardware runs one path to completion, then the other, with no interleaving. The SASS shows it as SSY and SYNC where Ada and Hopper have BSSY and BSYNC. Code that waits inside a divergent branch for another lane of its own warp can hang on Pascal and work on Volta and later.

Second, tensor cores, and with them any fast low-precision path. On the P5000's GP104, FP16 arithmetic runs at 1/64 of the FP32 rate. What Pascal does have, from compute capability 6.1, is dp4a, an instruction that multiplies four pairs of 8-bit integers and adds the four products to a 32-bit sum in one step. That is why llama.cpp keeps a Pascal path: its quantised weights are small integers, and dp4a gives four multiply-adds per instruction (the llama.cpp chapter). Its build adds Pascal's 61-virtual only when the toolkit is older than CUDA 13 (llama.cpp/ggml/src/ggml-cuda/CMakeLists.txt:43–44).

Third, current software. CUDA 13.0 removed offline compilation for Pascal, so the P5000 needs a 12.x toolkit. The open kernel modules start at Turing, so it needs the proprietary module, and the R580 branch is reported as the last driver branch with Pascal support. Nsight Compute dropped Pascal in 2020.1, and vLLM needs compute capability 7.5. The P5000 customer runs llama.cpp.

For bpftime, Pascal is the baseline. Its kprobe pass compiles every eBPF probe to PTX for sm_61 (bpftime/attach/nv_attach_impl/pass/ptxpass_kprobe_entry/main.cpp:55), so the probe code itself uses nothing newer than Pascal. The final compile of the patched module is for the GPU it runs on. On the P5000 that compile needs a PTX compiler that still accepts sm_61, so expect to build bpftime against a CUDA 12.x toolkit there. That is untested here.

Ada: the laptop

The laptop's Ada SM is closest to the SM this document has been describing all along, so it needs the least new vocabulary. Compared with Pascal it has independent thread scheduling, a uniform datapath for values that are the same in every lane, and fourth-generation tensor cores that accept FP8 as well as FP16, BF16 and INT8. It also has cp.async, from the Ampere generation. A warp issues an asynchronous copy from global to shared memory and keeps working until it needs the data, instead of loading into registers and storing to shared memory itself. Its limits are lower than the other two in one place: 48 resident warps per SM against 64, as the scheduling chapter's occupancy sums showed.

What Ada lacks is everything in the next section. Code compiled for sm_90 or sm_90a does not run on it, because compute capability 8.9 is older than 9.0.

Hopper: what only the H100 has

Hopper adds a level to the scheduling hierarchy and two new ways to move data. A thread block cluster is a group of blocks that the work distributor guarantees to run at the same time on one GPC, a group of neighbouring SMs. The portable maximum is 8 blocks per cluster, and the H100 allows 16 if the kernel opts in. Blocks of one cluster can load, store and do atomics on each other's shared memory. That is distributed shared memory, faster than a round trip through global memory, and it gives blocks a way to cooperate that the scheduling chapter's blocks never had.

The Tensor Memory Accelerator (TMA) is an asynchronous copy unit. One thread describes a tile of a tensor of 1 to 5 dimensions. The TMA moves the tile between global and shared memory, or between the shared memories of a cluster, and counts the arriving bytes on an mbarrier, a barrier object in shared memory that warps wait on. The warps compute no addresses and issue no loads. A kernel can dedicate a few warps to issuing TMA copies and leave the rest to compute.

The compute side is wgmma, warpgroup matrix multiply-accumulate. A warpgroup is four contiguous warps whose first warp's rank is a multiple of 4. Together they issue one asynchronous matrix multiply on the tensor cores, reading its operands from shared memory, where the TMA left them; one operand may come from registers instead. Hopper's tensor cores also take FP8.

There is a catch in the target name. wgmma needs the target sm_90a, with a letter on the end. The PTX manual explains the suffix: generations normally follow an "onion layer model" in which code for one target runs on all later ones, and targets ending in a are the exception. PTX or SASS for sm_90a runs on compute capability 9.0 and nothing else, ever. A library shipped with only sm_90a code needs a rebuild for the next generation.

It matters for bpftime in a specific way. bpftime picks the target for its final compile from the device's compute capability, which on an H100 gives the string sm_90 (bpftime/attach/nv_attach_impl/nv_attach_utils.cpp:94–160). An application whose PTX uses wgmma cannot be compiled for sm_90. The environment variable BPFTIME_SM_ARCH overrides the choice, so expect to set it to sm_90a for such applications. This is also untested here, and it is the first thing to try on the H100.

Two processes and a segment

A bpftime session has two processes. The loader is an ordinary libbpf program, the kind you would run against the kernel, started with LD_PRELOAD=libbpftime-syscall-server.so. When libbpf calls bpf() or perf_event_open(), the preloaded library answers instead of the kernel. It writes the programs, the maps and the attach requests, which bpftime calls handlers, into a named shared-memory segment. The target is the program you want to observe, started with LD_PRELOAD=libbpftime-agent.so. When the agent starts inside it, it maps the same segment, compiles each program and hands each handler to the attach implementation registered for its type.

The segment is what lets this work without the kernel. It is a Boost.Interprocess shared-memory region whose name both sides take from BPFTIME_GLOBAL_SHM_NAME. Inside the target, the agent pins the whole segment and maps it into the GPU's address space, with the cudaHostRegister(…, cudaHostRegisterMapped) call of listing 8.1. So the segment is also memory that GPU code can read and write directly.

libbpf turns that section name into a perf_event_open() call on the kprobe event type, with the function name attached, and then attaches the program to the returned descriptor. In the loader, the syscall server records it as a kprobe handler carrying the name (bpftime/runtime/syscall-server/syscall_context.cpp:843–888). In the target, handler types are numbers, and a kprobe is BPF_TYPE_KPROBE = 8 (bpftime/runtime/include/bpftime_shm.hpp:59). The agent registers the GPU attach implementation for exactly the types ATTACH_CUDA_PROBE and ATTACH_CUDA_RETPROBE, which are 8 and 9 (bpftime/runtime/agent/agent.cpp:1039–1046). So every kprobe handler goes to nv_attach_impl, with the kernel name as its argument, and every kretprobe becomes a probe at the kernel's exit.

The cost of the trick is that there are no real kprobes in a bpftime session. Inside bpftime, a kprobe means a GPU kernel. A loader can still use the real kernel's eBPF for other programs: with BPFTIME_RUN_WITH_KERNEL=1, the syscall server passes ordinary kprobes through to the kernel, and treats only names that start with cuda_ as GPU probes.

The compiler, and the verifier that is not there

bpftime compiles eBPF with llvmbpf, its own library. llvmbpf translates eBPF bytecode into LLVM IR. From there, LLVM's x86 backend produces machine code for host probes, and LLVM's NVPTX backend produces PTX for GPU probes, the same road to PTX as the compiler chapter's clang line. The GPU path is the subject of the next chapter.

The verifier is the part to be careful about. bpftime can run programs through PREVAIL, a userspace eBPF verifier, but its build option ENABLE_EBPF_VERIFIER is off by default (bpftime/cmake/StandardSettings.cmake:95). When it is on, BPFTIME_VERIFIER_LEVEL chooses strict checking, warnings only, or none. In a default build, nothing checks that a probe terminates or stays inside its memory. In the kernel the verifier is what makes eBPF safe to load. Here a probe is code you inject into someone else's GPU kernel, with the same power as that kernel's own code. A loop that never ends hangs the kernel it is in. Helper 507 exits the calling thread on purpose. Treat a GPU probe the way you would treat a patch to the application, because that is what it is.

Maps: where the data lives

Ordinary maps, hash and array and ring buffer, live in the shared segment, and the loader reads them with libbpf as usual. GPU code can reach the segment through the mapping, but a hash table in it is a host data structure that needs host code to search it. So a lookup from a GPU probe in an ordinary map becomes a request to the host, through the protocol the next two chapters take apart.

bpftime therefore adds GPU maps, with type numbers from 1500 (bpftime/runtime/include/bpftime_shm.hpp:122–132). Their data lives where GPU code can index it directly. The per-thread array map gives every GPU thread its own copy of each value, like a per-CPU map with a GPU thread in place of a CPU. The loader allocates it in device memory with cuMemAlloc and shares it with the target through a CUDA IPC handle (bpftime/runtime/src/bpf_map/gpu/nv_gpu_per_thread_array_map.cpp:61–74). The shared GPU array map has one copy, and there are a GPU ring buffer and a GPU hash map. For platforms without CUDA IPC, such as NVIDIA's Tegra boards, host-memory variants do the same job through pinned, mapped memory.

The per-thread map has a sizing rule that matters for our matvec. Each value is stored once per GPU thread, for as many threads as BPFTIME_MAP_GPU_THREAD_COUNT allows. The default is 1,024 (bpftime/runtime/include/bpftime_shm.hpp:42–45). Our matvec_warp launch has 131,072 threads. Reading the map back is one copy of every thread's slot for the key, so the map also costs host time in proportion to the thread count.

Check yourself

1. Predict the value: you put a per-thread array map with 4 keys of 8-byte values on matvec_warp's 131,072 threads. How large must BPFTIME_MAP_GPU_THREAD_COUNT be, how much device memory does the map take, and how many bytes does one bpf_map_lookup_elem from the loader copy?

Answer

At least 131,072; the map takes 4 × 131,072 × 8 bytes = 4 MiB of device memory; one lookup copies 131,072 × 8 bytes = 1 MiB. Every key holds one 8-byte slot per thread, and the loader's lookup returns all of a key's slots at once, the way a per-CPU map returns one value per CPU.

With the default of 1,024 the trampoline prints a warning and computes addresses past the end of the buffer for every thread above 1,023, so the setting is not optional. The near-miss is to size the map by the number of warps or blocks. It is indexed by the global thread index.

2. A colleague loads a bpftime loader with an ordinary kernel kprobe on do_sys_openat2 next to a GPU probe, and the kernel kprobe never fires. Explain, and say what they could do.

Answer

Under the syscall server, every kprobe becomes a bpftime handler of type 8, and type 8 is the GPU probe. The request never reached the kernel; inside the target, bpftime looked for a GPU kernel called do_sys_openat2 and found none.

They can run the loader in bpftime's "run with kernel" mode, where ordinary kprobes go to the kernel and only names starting with cuda_ become GPU probes. Or they can split the two into separate loaders, one under bpftime and one plain. The near-miss is a missing symbol in the kernel. The kernel was never asked.

3. Why does a lookup in an ordinary hash map from a GPU probe need the host at all, when the map's memory is mapped into the GPU's address space?

Answer

Because mapped memory gives access to bytes, while a lookup needs an algorithm. The hash map is a host data structure in the segment, built with host pointers and searched by host code. GPU code could read its bytes, but it has no compiled lookup function that understands the layout, and the host might be changing the map at the same moment.

So the probe writes the key into the request area and waits while a thread in the agent runs the real lookup. GPU maps avoid this by having a layout that a GPU thread can index with arithmetic. The near-miss is "mapped memory is slow". It is slow, but the reason is that the GPU cannot run the lookup itself.

Chapter 13

Getting inside someone else's kernel

~13 min · EBPF ISA — The last chapter ended with a handler in shared memory: a kprobe on _Z11matvec_warpPKfS0_Pfii, and the eBPF bytecode to run there. This chapter follows that handler until the probe is running inside every thread of our kernel. Nine steps, all in the target process, most of them before main. Every one of them uses something from the language part (Part II).

The plan: edit the PTX, compile it again, swap the function

bpftime cannot change a kernel that is already loaded on the GPU, and it does not try to edit SASS. Instead it makes a second copy of the kernel with the probe built in, and arranges for launches to use the copy. The copy is made from the kernel's PTX, which the compiler chapter showed is stored in the fatbin next to the SASS. PTX is a documented text language, so a probe can be inserted with string edits, and ptxas then does the hard parts: register allocation and instruction scheduling for the kernel and the probe together.

Steps 1 and 2: catching the fatbin

The agent's GPU attach implementation installs Frida listeners on the runtime's registration functions: __cudaRegisterFatBinary, __cudaRegisterFunction, __cudaRegisterVar and __cudaRegisterFatBinaryEnd (bpftime/attach/nv_attach_impl/nv_attach_impl.cpp:369–390). It finds the first one with dlsym(RTLD_NEXT, …), which works only when the program uses the shared CUDA runtime. That is why every bpftime GPU example builds with nvcc -cudart shared. A statically linked runtime keeps these functions as local symbols, as the compiler chapter found with nm.

When a registration arrives, the listener walks the fatbin's entries, each starting with the magic number 0xBA55ED50, copies the bytes, and extracts every PTX entry (bpftime/attach/nv_attach_impl/nv_attach_impl_frida_setup.cpp:254–290). The SASS entries are ignored. If the fatbin has no PTX, there is nothing to patch, and the kernel runs unprobed.

There is a second way in, for programs that were already running or registered their fatbins before the probe was attached. When a probe is attached, bpftime starts a background scan of every ELF module loaded in the process, looking for .nv_fatbin and .nvFatBinSegment sections (nv_attach_impl.cpp:1800, started at line 227). Until that scan finishes, launches use the original kernels (nv_attach_impl_frida_setup.cpp:509–512). So the first launches after a late attach are not probed.

Step 3: the passes

The editing is done by passes, small shared libraries that bpftime loads with dlopen. Each exports two functions, print_config and process_input, and its configuration says which handlers it serves: the kprobe_entry pass takes section names matching ^kprobe/.*$ and attach type 8, the kretprobe pass takes ^kretprobe/.*$ and type 9 (bpftime/attach/nv_attach_impl/configs/ptxpass/kprobe_entry.json). For each probe and each kernel it names, bpftime sends the pass a JSON request: the whole PTX file, the kernel's name, the eBPF instructions, and the names of two symbols that the probe will need. The pass answers with new PTX. Answers are cached by the SHA-256 of the request (nv_attach_impl.cpp:889–1046).

The entry pass does two things (bpftime/attach/nv_attach_impl/pass/ptxpass_kprobe_entry/main.cpp:45–97). First it compiles the eBPF program with llvmbpf into a PTX function called __probe_func__ followed by the kernel's name, for target sm_61. Then it finds the kernel's body and inserts a call to that function just after the opening brace. The exit pass compiles its program the same way and inserts a call before every ret or exit in the body, keeping any predicate and any label on that line, so that branches to the epilogue still pass through the probe (pass/ptxpass_kretprobe/main.cpp:37–64). Steps 4 to 6: trampoline, compile, load

The probe functions call helpers by name, _bpf_helper_ext_0502 and so on, and read two globals: constData, the GPU address of the request area in the shared segment, and map_info, a table describing up to 1,024 maps. All of these are defined in the trampoline, a CUDA file (trampoline/default_trampoline.cu) compiled to PTX and committed to the repository as a C string in trampoline_ptx.h. bpftime prepends that PTX to the patched file (bpftime/attach/nv_attach_impl/nv_attach_utils.cpp:19–22). Listing 6.3, the spinlock at the heart of helper calls, is from it.

Then the file is compiled for the GPU it will run on. bpftime rewrites the PTX's .target line to the detected architecture, sm_89 on the laptop, and compiles it with NVIDIA's PTX compiler library at -O3 (bpftime/attach/nv_attach_impl/nv_attach_fatbin_record.cpp:103–188). This is ptxas in library form. It allocates registers for each kernel and the probe it now calls, so the patched kernel can need more registers than the original, with the occupancy consequences of the scheduling chapter. Finally cuModuleLoadDataEx loads the result as a second module in the program's context, and bpftime copies the request-area address and the map table into the module's constData and map_info (nv_attach_fatbin_record.cpp:229–268). The original module is untouched, and both now exist side by side.

Steps 7 to 9: swapping the function at launch

The last step happens at every launch. bpftime replaces cudaLaunchKernel, cudaLaunchKernel_ptsz and cuLaunchKernel with its own versions, and hooks the graph-node calls that the host-side chapter described (nv_attach_impl.cpp:421–450). For a driver launch, its version finds the name of the CUfunction being launched, looks for a patched function with the same name, and if there is one, launches that instead, with the same grid, block and arguments (nv_attach_impl_frida_setup.cpp:489–527). Runtime launches are matched by the host stub's address, which step 1 recorded with the kernel's name, and relaunched through cuLaunchKernel with the patched function (nv_attach_impl_frida_setup.cpp:165–192). The patched kernel has the same parameter list as the original, because the probe lives inside the body, so the arguments fit unchanged.

Check yourself

1. Predict the value: after patching, ptxas reports 48 registers per thread for matvec_warp instead of 40. With 256-thread blocks on the laptop, how many blocks and warps fit per SM now, and how many waves does the 512-block launch take?

Answer

5 blocks, 40 warps, and 5.12 waves. A block needs 48 × 256 = 12,288 registers, and 65,536 / 12,288 = 5.33, so 5 blocks fit, against 6 before. That is 40 of 48 warps, 83% occupancy. 512 / (5 × 20) = 5.12 waves, against 4.27, so the launch now has six rounds, the last one almost empty.

For a memory-bound kernel, 40 warps may still hide latency well, so the time may barely change. The point is that a probe can cost time without executing a single slow instruction, by changing how the original kernel fits. The near-miss is to count only the probe's own instructions as its cost.

2. Your probe on a cuBLAS GEMV kernel, called from the lab program, never fires, while the same probe on matvec_warp works. Give three causes from this chapter that could explain it, and the order in which you would check them.

Answer

First the name: cuBLAS kernels have long templated C++ names, so copy the real one from cuobjdump -symbols. Second, PTX: run cuobjdump -lptx on the library. On this laptop's CUDA 13.4, every PTX entry in libcublas.so is for sm_120, and the SASS covers sm_75, 80, 86, 90, 100 and 120, so the laptop runs sm_86 SASS. bpftime would have to retarget sm_120 PTX to sm_89 by rewriting its .target line, which compiles only if those kernels use nothing newer. The first two checks need no GPU. Whether cuBLAS's kernels are reachable at all is a bench test for this document. The near-miss is to blame the probe code, which ran fine on the other kernel.

3. NVBit edits SASS; bpftime edits PTX. Give one thing bpftime's choice buys and one thing it costs, with a concrete example of each from this chapter.

Answer

It buys a stable, documented language and a real compiler for the combined code. The pass inserts one line of text, and ptxas allocates registers and schedules the kernel and the probe together, for whichever generation is present, the same pass on Pascal, Ada and Hopper. NVBit has to work in each generation's undocumented SASS and save and restore state around each inserted call.

It costs the dependency on PTX and a recompile. A library that ships only SASS cannot be probed, the patched kernel's register allocation can change (question 1), and every patched module is compiled at start-up. The near-miss is to call one approach better. They make different trade-offs, which diagram 10.3 placed on either side of ptxas.

What a probe costs

A probe's cost has four parts, and each comes from a mechanism you have already seen.

The first is instructions, paid by whole warps. Every thread executes the probe, and its first branch, if (tx & 31), splits each warp: 31 lanes return while lane 0 runs the rest. Under SIMT the warp as a whole waits for lane 0 (diagram 1.2), so every warp pays for the longest path once. Limiting the work to lane 0 saves memory traffic and map space, and saves no issue slots. The GPU helpers are separate functions in the trampoline, marked __noinline__, and the ones that return three values do so through pointers into the probe's stack, which in PTX is local memory: the STL and LDL of the SASS chapter.

The second is registers. ptxas compiles the kernel and the probe together, and the combined kernel can need more registers than the original, with fewer blocks per SM as a result (the last chapter's first question).

The third is the one that can be enormous: helpers that need the host. A lookup in an ordinary map, bpf_printk, bpf_get_current_pid_tgid, bpf_perf_event_output and helper 501 all go through make_helper_call. That function takes the active lanes of the warp one at a time. Each takes a single spinlock shared by every thread on the GPU, writes its request into the host-memory request area, sets a flag, and spins until the host answers (bpftime/attach/nv_attach_impl/trampoline/default_trampoline.cu:131–172). On the host, the agent's watcher thread checks the flag, handles at most one request, and then sleeps for a millisecond, every time round its loop (bpftime/runtime/src/attach/bpf_attach_ctx_cuda.cpp:118–276).

Put together, those two pieces of code serve at most one host call per watcher wake-up, about a thousand per second for the entire GPU, each taking up to a millisecond. While they wait, the other threads that want a host call spin on the lock, issuing atomic operations that use the SMs and the memory system. Diagram 14.2 draws five lanes asking at once.

The fourth is start-up. Every fatbin with a probed kernel is patched and compiled by the PTX compiler library at registration, before main, so a program with thousands of kernels starts noticeably slower. The cost is paid once per process; within a process, results are cached by hash.

Adding a helper

The finish line asked for enough understanding to add a helper. Here is helper 512, which returns the SM's cycle counter. The PTX manual documents %clock64 as a 64-bit cycle counter. By contrast, it describes %globaltimer, behind helper 502, as a register "intended for use by NVIDIA tools" whose behaviour is target-specific, so a second clock is useful. The work has four steps, all of them in bpftime's tree.

First, implement it in the trampoline, next to the others, with the five 64-bit parameters every helper takes:

extern "C" __noinline__ __device__ uint64_t
_bpf_helper_ext_0512(uint64_t, uint64_t, uint64_t, uint64_t, uint64_t)
{
	// get this SM's cycle counter
	uint64_t cycles;
	asm volatile("mov.u64 %0, %%clock64;" : "=l"(cycles));
	return cycles;
}

Adding a kind of attach point

The other extension is a new kind of attach point, such as a probe before every bar.sync, the PTX of __syncthreads. That is a new pass. A pass is a shared library that exports print_config, returning JSON with its name, attach type and name patterns, and process_input, taking the JSON request of the last chapter and returning new PTX. bpftime loads the libraries listed in BPFTIME_PTXPASS_LIBRARIES, colon-separated, or its built-in list, each with dlmopen in its own namespace (bpftime/attach/nv_attach_impl/nv_attach_impl.cpp:501–530).

The simplest way to give the new pass a name needs no change to libbpf or the loader. Claim a pattern inside the kprobe namespace, as the memory-capture pass does with ^kprobe/__memcapture$. The catch is the matching rule. For each handler, bpftime picks the first pass whose attach type and pattern match (nv_attach_impl.cpp:173–193), and kprobe_entry claims every ^kprobe/.*$ except __memcapture. Its exclusion list, in pass/ptxpass_kprobe_entry/main.cpp:29–30, must also exclude your new pattern, or the entry pass will take your probes first.

1. Predict the value: a colleague adds bpf_printk in lane 0 at the exit of matvec_warp, one call per row. Using the model of diagram 14.2, about how long does one launch take now, against about 330 µs without the probe?

Answer

2. Restricting the probe to lane 0 does not save issue slots, as this chapter said. Then why do it, and what would go wrong if every thread wrote its own record into a per-thread array map instead?

Answer

It saves memory traffic and map space, and it records exactly the unit the question is about, a row. One record per row is 4,096 records of 24 bytes; one per thread is 131,072, each a store into device memory competing with the kernel's own loads, in a kernel that is memory-bound.

A per-thread array map would also need BPFTIME_MAP_GPU_THREAD_COUNT of at least 131,072 (the bpftime chapter's first question), and the loader would copy 32 identical-in-meaning start times per row. The near-miss is that "fewer lanes means a faster probe". The warp pays for lane 0's path either way.

3. You add helper 512 to the trampoline and regenerate the header, but forget the line in core.cpp. Where does it fail, and what do you see? Then: why is comparing two %clock64 values from a thread's entry and exit only meaningful if you also compare its two SM IDs?

Answer

It fails when the pass compiles the probe: llvmbpf has no helper 512 registered and reports "Ext func not found: _bpf_helper_ext_0512". The pass fails, that kernel is left unpatched, and the program runs without the probe, so you see the error only in bpftime's log.

%clock64 is a cycle counter on the SM that reads it, and different SMs' counters are not the same clock. If a preemption moved the block between entry and exit, the two readings come from different counters and their difference means nothing. Recording the SM at both ends, as the tail probe does, lets you discard those records. The near-miss is to treat %clock64 like %globaltimer, which is one clock for the whole GPU.

Chapter 15

Just enough transformer

~14 min · LLM — This part is about LLM servers, the programs you want to observe. To observe one you need to know what it computes, and this chapter teaches that from zero, with one model, Qwen2.5-0.5B-Instruct, and one source file, llama.cpp's graph for it. By the end, the whole model will turn out to be the prologue's matrix-vector multiply, repeated 169 times per token, with two other operations in between.

This chapter skips training entirely: how the weights got their values, gradients, loss functions. For serving, the weights are fixed numbers loaded from a file, and the model is a function from a list of tokens to a guess at the next one.

From text to vectors

A language model does not see characters. A tokenizer first cuts the text into tokens, pieces that are often whole words or parts of words, and replaces each by its number in a fixed vocabulary. Qwen2.5's vocabulary has 151,936 tokens. The model's input is a list of token numbers, and its output is a guess at the next number.

Inside the model, each token is a vector. The embedding matrix has one row per vocabulary entry, and each row is a vector of 896 numbers for Qwen2.5-0.5B. Turning a token into its vector is a lookup of one row, which llama.cpp writes as ggml_get_rows(ctx0, tok_embd, inp->tokens) (llama.cpp/src/llama-graph.cpp:2409). That 896 is the model's hidden size. From here until the very end, every token is represented by one vector of that size, its hidden state, which each layer of the model reads and updates.

The model in one page

Qwen2.5-0.5B is 24 layers with the same structure and different weights, stacked one after another. llama.cpp builds the whole computation for it in one function, a loop over the layers with a short preamble and postscript (llama.cpp/src/models/qwen2.cpp:53–154). Each layer has two halves, attention and the feed-forward network. Each half starts with a normalisation and ends by adding its result back onto its input.

RMSNorm divides the hidden state by its root mean square, the square root of the average of its squared entries, and multiplies each entry by a learned weight. It keeps the numbers in a stable range from layer to layer. The residual addition (qwen2.cpp:110 and 127) means that a layer adjusts the hidden state rather than replacing it, which is what lets 24 layers be stacked.

Attention: where tokens meet

Everything else in the model handles each token on its own. Attention is where a token takes information from the tokens before it. For the new token, three matvecs make three vectors from its normalised hidden state: a query q, a key k and a value v. Think of the query as what this token is looking for, a key as what a token offers to be found by, and a value as what it hands over if found. That analogy is all this chapter uses; from here on the arithmetic carries it.

The new token's query is compared with the key of every token so far, including itself, by a dot product. Each score is divided by √64, the square root of the vector length, to keep the numbers moderate. A softmax then turns the scores into weights that are positive and sum to 1: exponentiate each score, divide by the total. The output is the weighted sum of the tokens' values. Tokens never attend to later tokens. During generation there are no later tokens yet; when a whole prompt is processed at once, a causal mask hides them.

The model does this several times in parallel, in heads. Qwen2.5-0.5B splits its 896-entry query into 14 heads of 64, each comparing in its own 64-entry space, and joins the 14 outputs back into 896 before the output matvec. Its keys and values have only 2 heads of 64 each, shared by the query heads seven at a time. That is grouped-query attention (GQA): the key and value matvecs are 896 to 128 instead of 896 to 896, and, more importantly for the next chapter, there is seven times less key and value data per token to keep.

One more step gives tokens a sense of order. Plain dot products do not care where a token sits in the text. RoPE, rotary position embedding, rotates pairs of entries in q and k by angles proportional to the token's position, so that the score between two tokens depends on how far apart they are (qwen2.cpp:86–96). In llama.cpp, attention itself is build_attn. It first stores the new token's k and v into the cache and fetches the layer's keys and values for all tokens so far (llama-graph.cpp:2923–2928). Then it either multiplies the keys by the query, applies the softmax with the mask and the 1/√64 scale, and multiplies by the values (llama-graph.cpp:2696–2740), or does all three in one fused flash-attention kernel (llama-graph.cpp:2668).

The feed-forward network: the same little machine for every token

The second half of each layer handles each token alone, with three matvecs. Two of them, gate and up, widen the 896-entry vector to 4,864 entries each. The gate result goes through SiLU, the function z × sigmoid(z), which passes large positive values almost unchanged and squashes negative ones towards zero. The result is multiplied entry by entry with the up result. This combination is called SwiGLU (llama-graph.cpp:1872). The third matvec, down, narrows the 4,864 entries back to 896. Most of the model's weights live here: 13.1 million of each layer's 14.9 million.

From the last vector to the next token

After the last layer, a final RMSNorm, and then one more matvec turns the 896-entry hidden state into 151,936 numbers, one per vocabulary entry, called logits. A softmax over the logits gives a probability for each possible next token. Qwen2.5-0.5B has tied embeddings: this last matrix is the embedding matrix itself, reused, and a server that loads the original weights, as vLLM does, keeps one copy. The official files for llama.cpp, in its single-file model format GGUF, carry a second copy named output.weight, so llama.cpp loads both, and reuses the embedding matrix only when that tensor is missing (qwen2.cpp:26–31). Only the last token's logits are needed to choose what comes next, so at the last layer llama.cpp keeps just the rows it will need (qwen2.cpp:106–109).

Choosing the token from the probabilities is sampling. Greedy sampling takes the most likely token. Temperature divides the logits by a number before the softmax, flattening or sharpening the distribution, and top-p samples only from the smallest set of tokens whose probabilities add up to p. The chosen token is appended to the list and the whole model runs again for the next one. Producing text one token at a time, each depending on all the previous ones, is called autoregressive generation, and it is why generation is a loop.

2. Qwen2.5-0.5B has 14 query heads but only 2 key-value heads of 64 entries. How many bytes of keys and values does one token add per layer and for the whole model in BF16, and how many would 14 key-value heads need?

512 bytes per layer and 12,288 bytes for the model; 14 heads would need 86,016 bytes. Each layer keeps a key and a value of 2 heads × 64 entries × 2 bytes, so 2 × 128 × 2 = 512 bytes, and 24 layers make 12,288.

GQA makes the stored data seven times smaller while keeping 14 different queries, and the next chapter shows that this stored data is what limits how many users a server can hold, more than the weights do. The near-miss is to think GQA saves arithmetic. It saves a little; mostly it saves memory.

3. When llama.cpp processes a 1,000-token prompt, it keeps all 1,000 positions through layers 1 to 23 but only the last position after attention in layer 24 (qwen2.cpp:106–109). Why can it drop the other 999 there, and not earlier?

Answer

Because after layer 24's attention, a position's hidden state is used only to compute that position's logits, and only the last position's logits choose the next token. In earlier layers, every position's output is the input to the next layer, where it makes that position's key and value, which every later token will attend to.

So all positions must go through every layer up to the last attention, and only the final position needs the rest. The near-miss is to think earlier positions are needed for their own predictions. During generation nobody asks what came after "The"; we already know.

Chapter 16

Prefill, decode and the KV cache

~11 min · LLM — The last chapter ran the model for one new token. A real request runs it on a whole prompt first, then once per generated token, and the two runs have opposite characters: one is limited by arithmetic, the other by memory. This chapter names the two phases, introduces the cache that makes the second one affordable, and turns both into the latency numbers servers report: time to first token and time per token.

Two phases with opposite characters

A request arrives with a prompt of P tokens. The server first runs the model once over all P tokens together. This is prefill. Every weight matrix now multiplies a matrix with P columns, one per token, instead of a single vector: a matrix-matrix multiply, a GEMM. Each weight is read once and used P times, so in 16-bit the arithmetic intensity is about P FLOP per byte. A prompt of a few hundred tokens is already past the H100's tensor-core ridge, so prefill is compute-bound. Prefill leaves two results. Its logits for the last position give the first generated token. And every layer's key and value for every prompt position are kept, as the next section explains.

Then the server generates. Each step runs the model on one new token per sequence. This is decode, and for a single sequence it is exactly the last chapter's 169 matvecs: memory-bound, about 1 FLOP per byte. Decode repeats until the model emits an end-of-sequence token or reaches a length limit.

The two phases map onto the two numbers every LLM server reports. Time to first token (TTFT) is the time from the request's arrival to its first token: waiting in the queue, then prefill, then sampling. Inter-token latency (ITL), also called time per output token, is the time between later tokens, which is one decode step. vLLM measures TTFT from the moment the request arrived at the engine (vllm/v1/metrics/stats.py:473, with the arrival time set at vllm/v1/engine/input_processor.py:370), so queueing counts.

The KV cache

Diagram 15.2 showed that when a new token attends, the keys and values of the earlier tokens are exactly what they were when those tokens were new. So the server computes each token's key and value once, in every layer, and keeps them. The store is the KV cache. Each decode step writes one new key and value per layer and reads all the stored ones. Without the cache, step t would recompute keys and values for all t tokens so far, and generating n tokens would cost work growing with n².

The cache's size per token follows from the model's shape: a key and a value, in every layer, for every key-value head, of the head's length, in the cache's number format. For Qwen2.5-0.5B in 16-bit that is 2 × 24 layers × 2 heads × 64 × 2 bytes = 12,288 bytes per token. In llama.cpp the cache is two tensors per layer, one for keys and one for values, each with one row of 128 entries per token slot (llama.cpp/src/llama-kv-cache.cpp:233–234). It is F16 unless you choose otherwise (llama.cpp/common/common.h:589), and its size is printed at start-up (llama-kv-cache.cpp:300–303).

What one decode step reads

A server rarely decodes one sequence at a time. It runs a batch of B sequences in each step, and the weights are read once for the whole batch: every weight matrix multiplies a B-column matrix, and the intensity rises to about B FLOP per byte. The cache is different. Each sequence has its own keys and values, and each step reads all of them. So one decode step moves, at least, the weights once plus every cached token of every sequence in the batch.

Put numbers on it for Llama-3.1-8B in BF16 on an H100. The weights are about 16 GB. A token reads all of them except the embedding table, of which it reads one row, so about 15 GB, which take 4.5 ms to read at 3,352 GB/s. One sequence with 4,096 tokens of context adds 512 MiB of cache, another 0.16 ms. Sixty-four such sequences add 34 GB, 10.3 ms. So a step for 64 users takes at least about 15 ms instead of 5. Each user sees a token every 15 ms instead of every 5. The server makes 64 tokens per step instead of one, about 4,300 tokens per second instead of 200. Batching buys throughput with latency, and at long contexts the cache is most of what each step reads.

Prefill on the same machine is the other extreme. A 4,096-token prompt for Llama-3.1-8B is about 2 × 8 billion × 4,096 ≈ 66 TFLOP for the matrices, plus attention. Attention's work grows with P², because each of P tokens attends to all those before it, about P²/2 pairs. At the H100's roof of about 1,000 TFLOPS that is some 70 ms at best, and real kernels reach a fraction of the roof. So one long prompt takes as long as about 14 decode steps of a single sequence, or several of a full batch of 64, and every sequence in the same batch waits for it. That is the tension the next chapter's scheduler has to manage.

Where the time goes, for observation

Put the last two sections together and you have the map the language-model part (Part V) has been building towards. TTFT is queue time plus prefill. Prefill time is large GEMMs, whose speed is set by the tensor cores, plus attention over P²/2 token pairs. ITL is one decode step for the whole batch. It is set by memory: the weights once, through GEMV-like kernels with B columns, and the cache of every sequence, through attention kernels whose time grows with context. A probe that times the GEMMs and the attention kernels separately, for each step, can tell you which of those is moving when latency changes. The observing chapter builds exactly that.

3. A user reports that TTFT for a 32,000-token document is far more than 8 times the TTFT for a 4,000-token one, while ITL afterwards is only somewhat worse. Explain both halves.

Answer

Each decode step reads the weights once and the cache once. The cache is now 8 times larger, but the weights did not change, so the step grows by the cache's share only, and the user sees "somewhat worse". The near-miss is to call prefill purely compute-bound and linear. It is compute-bound, and its attention part is quadratic.

Chapter 17

Serving many users: vLLM

~14 min · LLM — The last chapter ended with a tension. Batching raises throughput, but every request in a step waits for the slowest work in it, and the KV cache fills memory. vLLM is a server built around managing that tension, step by step, for hundreds of requests at once. This chapter reads its V1 engine, at commit ccda909: the processes, the scheduler, the paged cache, preemption, CUDA graphs and the metrics, and ends with the sentence this whole document was written to make readable.

This chapter skips multi-GPU serving (tensor and pipeline parallelism), speculative decoding, LoRA adapters, multimodal inputs, and splitting prefill and decode onto different machines. All are real; none changes the single-GPU picture that observation starts from.

Three processes and one loop

A vLLM server is several processes. The API server speaks HTTP, turns text into tokens and back, and streams results to clients. The engine core is a separate process that owns the scheduler and the KV-cache bookkeeping and runs a loop. One or more workers own the GPUs; each runs a model runner that prepares inputs, runs the model and samples tokens. The engine core's loop is short enough to read whole:

scheduler_output = self.scheduler.schedule(self._should_throttle_prefills())
future = self.model_executor.execute_model(scheduler_output, non_block=True)
grammar_output = self.scheduler.get_grammar_bitmask(scheduler_output)
with (…):
    model_output = future.result()
    if model_output is None:
        model_output = self.model_executor.sample_tokens(grammar_output)
…
engine_core_outputs = self.scheduler.update_from_output(
    scheduler_output, model_output
)

Listing 17.1 — vllm/v1/engine/core.py:640–656, from EngineCore.step. Schedule, execute, sample, update: one step of the model for every request in the batch.

The scheduler: a token budget, no phases

The scheduler's own comment is the best summary of its design: "There's no 'decoding phase' nor 'prefill phase' in the scheduler. Each request just has the num_computed_tokens and num_tokens_with_spec." (vllm/v1/core/sched/scheduler.py:565–568). A request has some tokens whose keys and values are already in the cache and some that are not yet. Each step, the scheduler gives requests a number of new tokens to process so that they catch up, within a token budget for the whole step.

It serves the running requests first, then the waiting ones (scheduler.py:629 and 873). A running request in decode needs one token. A new request needs its whole prompt, and if that does not fit in what is left of the budget, it gets a piece of it. That is chunked prefill, on by default in V1. A long prompt is prefilled over several steps while the decodes continue in each of them (scheduler.py:1111–1125). Requests join the batch the step after they arrive and leave the step after they finish, which is called continuous batching. The defaults depend on the GPU: for the API server, an H100 gets a budget of 8,192 tokens and up to 1,024 requests per step, and other GPUs, such as the laptop's, 2,048 tokens and 256 requests (vllm/engine/arg_utils.py:2866–2895).

Diagram 17.2 is the last chapter's tension handled. A step's time is set by its total work, so the budget bounds every step and therefore ITL. The price is paid by the long prompt, whose TTFT now spans three steps. The two knobs that move the balance are the budget, --max-num-batched-tokens, and the number of requests per step, --max-num-seqs.

PagedAttention: the cache in blocks

At start-up, vLLM loads the weights, measures how much memory a step needs, and claims most of the rest for the KV cache: by default, everything up to 92% of the GPU's memory (vllm/config/cache.py:101). It divides that space into blocks of 16 tokens' keys and values, for every layer (cache.py:71). A request does not get one contiguous region sized for its longest possible length. It gets blocks one at a time as it grows, from a pool (vllm/v1/core/block_pool.py:136, get_new_blocks at line 669), through the KV-cache manager's allocate_slots (vllm/v1/core/kv_cache_manager.py:371). Each request has a block table that maps its logical blocks, in order, to physical blocks anywhere in the pool. The attention kernels follow the block table when they read the cache. This is PagedAttention: the cache is managed like virtual memory, with blocks for pages.

Paging is what lets the cache hold many requests without reserving each one's maximum length in advance, and it is what makes the next two mechanisms cheap: sharing blocks between requests, and taking them away.

Prefix caching: computing a prompt's start once

Many requests to a server begin the same way: a system prompt, a long document, the earlier turns of a conversation. vLLM gives every full block a hash computed from the previous block's hash and the tokens in this block, so that equal hashes mean equal prefixes (the vLLM documentation on automatic prefix caching). When a request arrives, get_computed_blocks looks for the longest run of its blocks that are already in the cache and starts the request after them (kv_cache_manager.py:264–300). If the whole prompt is cached, its last token is computed again, because the next token needs its logits, and since allocation works in whole blocks that can mean the whole last block (lines 289–295). When a request finishes, its blocks go onto a free queue with their contents and hashes intact. They stay findable until a new allocation takes them, least recently used first, with each request's last blocks queued ahead of its first ones, because a longer prefix is less likely to be shared. Prefix caching is on by default (cache.py:140), and a hit removes those tokens from prefill, so it shortens TTFT directly.

Preemption: when the blocks run out

Requests grow by a block every 16 tokens, and the pool is finite. When a running request needs a block and none is free, the scheduler preempts another running request, by default the most recently admitted one. It frees all of that request's blocks, sets the request's count of computed tokens back to zero, and puts it at the front of the waiting queue (scheduler.py:748–810, victim chosen at line 803, and _preempt_request at 1540–1582). When it is scheduled again, its prompt and the tokens it had already generated are prefilled again, with help from prefix caching if its blocks have not been reused. To the user, a preempted request shows up as a long pause, and as a TTFT or end-to-end latency far out in the tail. To the operator it shows up as the counter vllm:num_preemptions.

The model runner and its CUDA graphs

On the GPU side, execute_model (vllm/v1/worker/gpu_model_runner.py:4117) turns the scheduler's decisions into one batch. _prepare_inputs (line 1935) lays all the requests' new tokens end to end with their positions, and builds the block tables and the cache slots each new token's key and value will be written to. Then it runs the model once over the whole batch, and sample_tokens (line 4498) picks the next token for each request that needs one.

Decode steps launch many small kernels, which is the host-side chapter's case for CUDA graphs (chapter 8). At start-up, capture_model (line 6740) records graphs for a set of batch sizes, and at each step the dispatcher picks one that fits (vllm/v1/cudagraph_dispatcher.py:233). By default it captures two kinds. A full graph covers a whole step and is used for batches that are pure decode. Piecewise graphs cover everything except attention, for mixed batches, with attention launched normally in between (docs/design/cuda_graphs.md:43–48). Two facts from the host-side chapter and the attach-pipeline chapter (chapter 13) now apply. Kernels inside a graph do not pass through the launch functions, and a graph captured before a probe attached keeps the original kernels.

2. A dashboard shows vllm:num_preemptions_total climbing, the 99th percentile of TTFT jumping, and ITL steady. What is happening, and name two changes that would help.

Answer

The KV cache is full. Running requests need new blocks, the scheduler frees others' blocks to provide them, and the preempted requests go back to waiting and must be prefilled again, which lands in the tail of TTFT and end-to-end latency. The requests that keep running are unaffected, so ITL stays steady.

Fewer concurrent requests (--max-num-seqs), a shorter maximum context (--max-model-len), more memory for the cache (a larger memory share, or a smaller weight format), or a smaller cache format such as an 8-bit KV cache all help. Prefix caching softens the cost of each recomputation. The near-miss is to treat it as a compute problem and add batch. That makes it worse.

3. Why does chunked prefill protect ITL, what does it cost, and who pays?

Answer

A step's duration is set by the work in it, and every running request waits for the whole step to get its next token. Without chunking, a 5,000-token prompt makes one step about two and a half times larger than the budget allows, and 40 users' next tokens wait for it. With chunking, no step exceeds the budget, so ITL has a ceiling (diagram 17.2).

The cost falls on the long prompt itself. Its prefill spans several steps, each shared with the decodes, so its TTFT is longer than if it had run alone. The near-miss is "chunking makes prefill faster". It makes prefill fairer, and slightly slower for the request being chunked.

One machine: llama.cpp and ggml

Of the two, it is the only one that runs on the P5000. Two libraries: llama and ggml

llama.cpp is two layers. ggml is a tensor library: tensors, operations on them, a graph of operations, and backends that run a graph on a CPU or a GPU. libllama sits on top. It loads models, keeps the KV cache, and builds a ggml graph of the model for each batch, using the builder the transformer chapter (chapter 15) walked through (src/models/qwen2.cpp:53–154). The programs you run, llama-completion, llama-bench and llama-server, all submit work through libllama's llama_process, or the older llama_decode, which ends in the same place.

A call to llama_process splits its batch into micro-batches: up to 2,048 tokens per call by default, and 512 at a time on the device (common/common.h:453–454). For each micro-batch it builds the graph, and the CUDA backend walks it node by node. Each node becomes one kernel launch, or several nodes become one fused kernel, such as a matrix-vector multiply with its bias add (ggml/src/ggml-cuda/ggml-cuda.cu:4134–4142).

GGUF: one file holds the model

A llama.cpp model is one GGUF file, the format the transformer chapter downloaded. It starts with the four bytes GGUF and a version number, 3 (ggml/include/gguf.h:41–42). Then come key-value metadata (the architecture, the number of layers, the context length the model was trained with, the tokenizer's 151,936 tokens), a table of tensors with each one's name, shape, type and offset, and the tensor data, aligned to 32 bytes (line 46). By default llama.cpp maps the file into memory and copies the tensors to the GPU from there (common/arg.cpp:2693).

The tensor table is enough to know what a decode step reads, before running anything. Reading the first megabytes of the two official files of our model gives this:

Quantization: small integers with a scale

Each of these types stores weights as small integers in fixed-size blocks, with one or two scale factors per block. Q8_0, the transformer chapter's file, takes 32 weights, stores one FP16 scale d and 32 signed 8-bit integers, and a weight is d × q: 34 bytes per 32 weights, 8.5 bits per weight (ggml/src/ggml-common.h:251–256). Q5_0 does the same with 5-bit integers, 22 bytes per 32 weights. The k-quants work on super-blocks of 256 weights. Q4_K stores two FP16 numbers for the super-block, a 6-bit scale and a 6-bit minimum for each of its eight sub-blocks of 32, and 4 bits per weight: 144 bytes per 256, 4.5 bits per weight (ggml-common.h:320–338).

A name like Q4_K_M names a recipe for a whole file. Most tensors get Q4_K, and in 12 of the 24 layers, chosen by a fixed rule, attn_v and ffn_down get the larger Q6_K (src/llama-quant.cpp:452–454, 590–591 and 646–651). On Llama-3-8B the recipe averages 4.89 bits per weight (tools/quantize/README.md:167). But k-quants need each row's length to be a multiple of 256, and our model's rows have 896 entries, which is 3.5 × 256. The quantizer then falls back: Q4_K becomes Q5_0 and Q6_K becomes Q8_0 (llama-quant.cpp:396–418). Only ffn_down, whose rows have 4,864 = 19 × 256 entries, keeps its k-quants. The file's name says what was asked for; the tensor table says what you got.

One multiply, five kernels to choose from

Every matrix multiply in the graph goes through ggml_cuda_mul_mat (ggml-cuda.cu:1822–1875), which picks a kernel from the weight type and the number of columns in the batch.

Decode is the top-left cell. Before mul_mat_vec_q runs, ggml quantizes the activation vector too, to 8-bit integers in blocks of 32 with a scale (ggml/src/ggml-cuda/mmvq.cu:1506). Each thread then loads four weights and four activations packed into two 32-bit registers and multiplies them with one instruction, dp4a: four 8-bit products, summed into a 32-bit integer (vecdotq.cuh:246–258). The scales are applied once per block, in floating point. ggml calls dp4a from compute capability 6.1, Pascal's GP104, and multiplies byte by byte below that (common.cuh:51 and 740–746). A three-line kernel shows the instruction in PTX and in SASS:

// out[i] = __dp4a(w[i], x[i], 0);   nvcc 13.4, -arch=sm_89

       ld.global.u32   %r3, [%rd9];

SASS:  LDG.E R2, [R2.64] ;

This is the prologue's matvec again, with bytes in place of floats. Each weight is still used for one multiply-add, but it takes about a quarter of the FP32 matvec's bytes in Q8_0, a sixth in Q5_0 and a seventh in Q4_K. Decode is bound by bytes, so that is where the speed comes from.

Prefill is the matrix path. mul_mat_q multiplies tiles of quantized weights with tiles of the 512 activation columns, on int8 tensor cores from Turing on (mmq.cu:371–373), and with dp4a on Pascal (lines 375–387).

CUDA graphs, and the launch path on Hopper

llama.cpp builds ggml with CUDA graphs on (CMakeLists.txt:169–171), and ggml switches them off below Volta, so on the P5000 every kernel is launched one by one (ggml-cuda.cu:4430–4436). The environment variable GGML_CUDA_DISABLE_GRAPHS turns them off anywhere (common.cuh:1289). ggml captures a graph once two calls in a row have identical nodes: the same shapes, strides and data pointers (ggml-cuda.cu:2597–2637 and 4459–4481). After that it replays the graph until something changes, then runs one call directly and captures again. The part of the KV cache that attention reads is padded to a multiple of 256 tokens (src/llama-kv-cache.cpp:1265–1270), so a decode loop can replay one graph for up to 256 tokens. Every capture goes through the launch functions, so a probe loaded with the process sees each capture, as the host-side chapter (chapter 8) described.

Hopper adds programmatic dependent launch: a kernel may start before the kernel ahead of it in the same stream has finished, and waits inside for the data it needs. NVIDIA's guide says it is available from compute capability 9.0, and that the dependent kernel must be launched with the extensible launch call, cudaLaunchKernelEx. ggml uses it for every kernel whose PTX was compiled for 9.0 or newer (common.cuh:1670–1701). bpftime at commit a900f85 replaces cudaLaunchKernel, its _ptsz variant and cuLaunchKernel (nv_attach_impl.cpp:421–429), and nothing named LaunchKernelEx. So on an H100 build for 90, ggml's launches skip bpftime's redirect. GGML_CUDA_PDL=0 sends them through the normal launch (common.cuh:1693–1696). This follows from the source; it has not been run on an H100.

llama-server: slots in a fixed cache

llama-server serves several conversations at once, each in a slot. By default it creates 4 slots that share one cache (tools/server/server.cpp:160–165, common/arg.cpp:1403), and continuous batching is on (arg.cpp:2570). Each step, update_slots (tools/server/server-context.cpp:2793) adds one sampled token for every slot that is generating (line 3096), adds waiting prompt tokens until the batch holds 2,048 (line 3108), and calls llama_process. That is vLLM's step in miniature, with a batch size where vLLM has a token budget.

The cache is one buffer of token cells, allocated at start-up. Its size is -c, by default the context length the model was trained with, 32,768 here, reduced to fit free memory when --fit is on, which is the default (common/common.h:452 and 478). When a step finds no free cells, the server halves the batch and tries again (server-context.cpp:3728–3733). A request that arrives while all slots are busy is deferred until one frees up (server-context.cpp:2405–2407). A new request goes preferably to a slot whose last prompt shares at least 10% of its own, and the shared start is reused from that slot's cache (arg.cpp:3796–3797, common.h:697).

Recap

llama.cpp is libllama on top of ggml: llama_process splits a batch into micro-batches, builds a ggml graph of the model for each, and the CUDA backend runs one kernel per node or per fused group. A model is one GGUF file whose weights are blocks of small integers with scales; Q4_K_M is a recipe, and for rows that are not a multiple of 256 its k-quants fall back to Q5_0 and Q8_0. Each multiply picks a kernel, dp4a vector kernels for decode and tiled kernels on tensor cores or dp4a for prefill, and CUDA graphs are captured once shapes repeat, except below Volta. On Hopper, ggml launches with cudaLaunchKernelEx, which bpftime does not hook. llama-server runs slots in a fixed cache, halves its batch when the cache is full, and reports throughput but no latency histograms.

Check yourself

1. Predict the value: using the tensor table above, roughly how many bytes does one decode step read from the Q4_K_M file, and what is the ceiling in tokens per second for one sequence on the laptop and on the P5000? The F32 vectors and the tokenizer are small enough to ignore.

Answer

About 392 MB, so about 550 tokens per second on the laptop and about 735 on the P5000. The tensors add up to about 485 MB, and the 94 MB Q5_0 embedding table is read one row at a time, which leaves about 392 MB. Most of it is Q5_0, plus the 145 MB Q8_0 output copy and the Q4_K and Q6_K ffn_down layers. 0.392 GB / 216 GB/s ≈ 1.8 ms, and 0.392 GB / 288 GB/s ≈ 1.4 ms.

The near-miss is to multiply 494 million weights by 4.89 bits, which gives about 300 MB and a ceiling near 715 tokens per second on the laptop. It uses a Llama-3-8B average for a file that is mostly Q5_0 and holds a second Q8_0 copy of the largest matrix.

2. A uprobe on cudaLaunchKernel during llama-bench's generation test shows a steady stream of calls on the P5000, and on the laptop a burst every now and then with almost nothing in between. Explain both.

Answer

ggml disables CUDA graphs below Volta, so on the P5000 every node of every token's graph is an ordinary launch: a few hundred calls per token, steadily. On the laptop, ggml captures a graph once two calls in a row have identical nodes, and replays it with one cudaGraphLaunch, which does not call cudaLaunchKernel.

The bursts are the captures, plus the step that runs directly before each one. They come when something in the graph changes, for example when the padded length of cache that attention reads crosses a multiple of 256 tokens. The near-miss is that the laptop's GPU is idle between bursts. It is busy the whole time, running kernels whose launches no longer pass through the probed function.

3. Users of a llama-server with 4 slots report a time to first token of several seconds, but every response's timings.prompt_ms is under 200 ms. Where did the time go, which metric shows it, and what would you change?

Answer

The time went to waiting for a slot. prompt_ms measures only the prefill, so a request that waited behind four long generations shows a small prompt_ms and a long TTFT. llamacpp:requests_deferred above zero, with requests_processing at 4, shows requests queueing.

More slots help, with -np, as long as the cache is large enough for them: each slot needs room for its context. So do shorter outputs, or a second server. The near-miss is to tune prefill, for example with a larger batch. Prefill was never the slow part.

A probe for each step

For llama.cpp, the step loop is a C function with a stable name, which makes it the best single place to probe. At this commit the programs submit a step with llama_process(ctx, LLAMA_PROCESS_TYPE_DECODE, batch): llama-server at tools/server/server-context.cpp:3682, llama-bench at tools/llama-bench/llama-bench.cpp:2186. The older llama_decode converts its batch and ends in the same method (src/llama-context.cpp:4383–4386, 4401–4404 and 4477–4483). One detail decides where the probe's end goes. The call returns before the GPU has finished: it queues the step and an asynchronous copy of the logits (line 1948), and the wait happens in llama_synchronize, which the server calls right after (server-context.cpp:3682–3685) and the sampler calls before it samples (common/sampling.cpp:594). So a step runs from llama_process's entry to the return of the next llama_synchronize on the same thread.

Recap

Five layers can observe a request: the socket, the server's own metrics and traces, the step loop, the driver, and the GPU. Only the socket sees what the user sees, and only the GPU layer sees inside a step. llama.cpp's step can be timed from llama_process's entry to the return of llama_synchronize, because the call itself returns before the GPU finishes; vLLM's from the gaps between CUDA graph launches in its engine-core process. A bpftime probe needs PTX, a hooked registration and launch, and a graph captured after attach. llama.cpp built from source meets all four; stock PyTorch, vLLM, cuBLAS, Triton and FlashAttention 3 kernels miss at least one, which leaves stock vLLM to host-side eBPF and NVIDIA's tools.

1. Predict the value: in the Try-it, one slot is generating with about 1,000 tokens of context, and then four slots are, each with about 1,000. Using the bandwidth floor alone, how long is a decode step in each case on the laptop, and how many tokens per second does the server produce?

Answer

About 2.5 ms and 2.7 ms, so about 400 and 1,500 tokens per second. A step reads the 525 MB of weights once, whatever the batch, plus each slot's cache: 1,000 tokens × 12,288 bytes ≈ 12 MB per slot in F16. One slot moves about 537 MB, 2.5 ms at 216 GB/s; four move about 574 MB, 2.7 ms, and produce four tokens per step.

Four users cost each other about 7% here, because the weights dominate and are shared; mul_mat_vec_q takes up to 8 columns and reads each weight block once for all of them. The near-miss is to expect the step to take four times as long.

2. A bpftime probe on a vLLM attention kernel loads without errors and never fires. Give three causes in the order you would check them, and how to check each.

Answer

First, the kernel has no PTX or never passes through bpftime's registration hook: run cuobjdump --list-ptx on the library it lives in, and if it is a Triton kernel, it was loaded with cuModuleLoadData as a cubin. Second, it is launched through a call bpftime does not replace: a uprobe on cuLaunchKernelEx* in libcuda.so.1 shows whether it fires.

Third, the kernel runs inside a CUDA graph captured before the probe was attached, which vLLM does at start-up; restart the server with the agent loaded. On an H100, FlashAttention 3's sm_90a code is a fourth cause. The near-miss is to suspect the eBPF program itself, which loaded fine.

3. A client measures a 99th-percentile ITL of 120 ms. The server's vllm:inter_token_latency_seconds says 30 ms. Where can the other 90 ms come from, and which layer settles it?

Answer

From between the engine and the client: the API server falling behind in turning tokens into chunks, a proxy that buffers the stream, or TCP holding small writes back, for example Nagle's algorithm waiting on a delayed acknowledgement. The engine's metric stops at the engine, before any of these.

The socket layer settles it. Timestamps of tcp_sendmsg on the server's connection show whether chunks leave every 30 ms. If they do, the delay is in the network or the proxy; if they leave in clumps, it is the API server. The near-miss is to tune the GPU, whose steps are already 30 ms.

Epilogue: traps, limits, what comes next

~9 min · EBPF LLM — The matvec has made the whole trip: one line of CUDA, PTX and SASS, the SMs, a probe inside it, and every token a server produces. This last chapter collects what can still go wrong at each stage, what the tools cannot do, the tests this document has not been able to run, and two directions the field has taken since the hardware in it was new.

The trip, and the trap at each stage

Every chapter ended with a trap or two in its tables. Diagram 20.1 lines them up along the trip the matvec took, so that a symptom can be placed at its stage. Most of them have the same shape: a layer that looks transparent turns out to decide something. The build decides whether there is PTX. The runtime's linking decides whether registration can be seen. The launch call decides whether a hook runs. The capture time of a graph decides which kernels it holds.

Honest limits

bpftime's GPU probes, at commit a900f85, have five limits that no amount of care in the probe removes. A probe gets no arguments. It can read the block and thread indices, the block and grid sizes, the SM, warp and lane it runs on, and the global timer (helpers 502 to 511, attach/nv_attach_impl/pass/ptxpass_core/src/core.cpp:213–224), and its maps. The kernel's own parameters and registers are out of its reach. Helpers that call the host are served one at a time by a thread that sleeps a millisecond per loop, about a thousand calls per second for the whole GPU, as the probe-cost chapter (chapter 14) worked out from the source. The verifier is compiled out by default (cmake/StandardSettings.cmake:95), so a GPU probe is trusted code. Only kernels that arrive through a hooked registration, with PTX, are patched. And only the three replaced launch functions redirect to the patched copy.

This document has limits of its own. Its numbers are floors, computed from bytes and bandwidth, and every "Try it" asks you to measure where the floor is not the answer. Its Pascal and Hopper paths were checked against sources and documentation, but never run, because neither card was on the bench. And it is longer than planned, because each layer needed its mechanism explained before its probe could make sense; the reading times in the contents are measured from the text.

What came next: Blackwell's families

CUDA 12.9 added a third kind of target. Besides portable code and the architecture-specific a targets of the generations chapter (chapter 11), there are family-specific f targets: code built for compute_100f runs on any GPU of compute capability 10.x, today 10.0 and 10.3, and on future ones in the same family (NVIDIA's blog on family-specific features). Blackwell's fifth-generation tensor cores bring their own on-chip Tensor Memory, 512 columns by 128 lanes of 32-bit cells per block on sm_100a and sm_100f, used by the tcgen05 instructions (PTX ISA, section 9.7.18.1). ggml already lists NVIDIA's FP4 format among the types its quantized matrix kernel takes (ggml/src/ggml-cuda/mmq.cu:318–352).

For probing, this extends a rule the document already met with sm_90a. bpftime rewrites a kernel's PTX target to the detected architecture, without a suffix (nv_attach_utils.cpp:94–160), so any kernel whose PTX needs an a or f target is out of its reach, and those are the tensor-core kernels where the time goes. A bpftime that kept the suffix it found would close part of the gap. That is a small, concrete change of the kind this document's finish line asked you to be able to make.

What came next: the cache on the network

vLLM can run prefill and decode in different instances and move the KV cache between them, which it calls disaggregated prefilling. Its documentation gives two reasons: to tune TTFT and ITL separately, and to control the tail of ITL, which mixed steps like diagram 17.2's lengthen. It adds that the feature does not improve throughput (docs/features/disagg_prefill.md). The cache travels through a connector; NIXL, one of them, can use UCX, which runs over RDMA, and GPUDirect Storage.

For observation, this adds a sixth row to diagram 19.1, under the GPU and across machines: a request's keys and values crossing the network between its prefill and its first decode step. A TTFT now includes a transfer, and the tools for that row are the network's. The RDMA side is in the ConnectX and mlx5 chapter (chapter 5) of the SR-IOV dossier, which is where this document hands over.

Recap

The traps cluster between source and GPU: whether a build carries PTX, whether registration and launch pass through bpftime's hooks, and when a graph was captured. bpftime's probes get no arguments, call the host about a thousand times a second at most, run unverified by default, and reach only kernels with PTX and a hooked path. The document's Pascal and Hopper paths, its two step probes and its bench predictions wait to be run. Blackwell's family-specific and architecture-specific targets widen the set of kernels a target-rewriting tool cannot touch, and disaggregated serving puts part of TTFT on the network.

Check yourself

1. Trace the path: a probe on a llama.cpp kernel prints on the laptop, but on an H100, with the same source tree, the same bpftime and a build for 90, it prints nothing. Go from the build to the launch, and name the most likely cause and its fix.

Answer

The build embeds PTX for compute capability 9.0, so the fat binary is registered and bpftime patches the kernel as before. At launch, ggml checks the kernel's PTX version, finds 90, and launches it with cudaLaunchKernelEx to use programmatic dependent launch. bpftime does not replace that call, so the original kernel runs and the patched copy never does.

Setting GGML_CUDA_PDL=0 sends launches through the ordinary path. The near-miss is sm_90a: ggml has no wgmma or TMA code at this commit, so its kernels build for plain sm_90, and bpftime can compile them.

2. A probe must record which row of W each warp of the matvec computes, and when it finishes. What can the probe read, what can it not, and how does the probe-cost chapter's probe get the row?

Answer

It can read the block and thread indices, the block and grid sizes, the SM, warp and lane ids, and the global timer, all through helpers, plus its own maps. It cannot read the kernel's arguments, such as the pointers to W and x, or its registers. So the probe computes the row.

The probe-cost chapter's probe lets only lane 0 of each warp continue, computes the row as block index × block size plus thread index, divided by 32, and writes the global timer and SM id into a GPU array map at that row. The near-miss is to reach for the kernel's own row variable, which lives in a register the probe never sees.

3. Of the traps in diagram 20.1, which ones would a pure CPU eBPF user, who has never written a GPU probe, also meet, and why?

Answer

The launch-path and measurement traps. A uprobe on cudaLaunchKernel misses graph replays and cudaLaunchKernelEx launches just as bpftime's hooks do, because it watches the same functions. NVML's utilization misleads anyone who reads it as SM activity, and a llama_process return is not the end of a step for any tool.

The PTX traps, the static-cudart registration trap, sm_90a, and the probe's missing arguments belong to code that runs inside the kernel. The near-miss is to think host-side eBPF escapes the GPU's asynchrony. Every host-side timestamp is a submission or a wait, never the work itself.

The stored keys and values of every earlier token, in every layer.
batch
The set of sequences processed together in one step.

Tokens produced per second across all sequences.
