Chapter 0 · Prologue

Why steal hardware for a VM?

~10 min · layer: VIRT · The Virtual Function does not exist yet. First we need to see the problem it was invented to solve.

Picture a small program whose whole job is to move packets. A firewall, a 5G user-plane function, a load balancer, a packet capture box. It does almost no computing. It reads a packet, looks at a few bytes, and sends it somewhere else. Millions of times per second.

Now put that program inside a virtual machine. A virtual machine (VM) is a fake computer built by software on top of a real one. The real machine is the host. The fake one is the guest. The software that builds and supervises the guest is the hypervisor, also called the VMM (Virtual Machine Monitor). On Linux the usual pair is KVM, a kernel part that uses the CPU's own virtualization features, plus QEMU, a user-space program that pretends to be all the chips a computer needs. We will meet both properly in the VFIO chapter (chapter 7).

The guest needs a network card. There are three ways to give it one, and the difference between them is the reason this whole dossier exists.

Way one: pretend to be a real card

The oldest trick is emulation. QEMU pretends to be a network card that really existed in the world — often an Intel e1000. The guest boots, finds what looks like an e1000, and loads its normal e1000 driver. The driver has no idea it is being lied to.

The lie is expensive. When the guest driver writes to what it believes is a hardware register, the CPU cannot let that write go to real hardware. It stops the guest and jumps into the hypervisor. That stop is called a VM exit: the CPU leaves guest mode, saves state, and hands control to the host. A VM exit costs on the order of a microsecond once you count the work around it — small, but not small enough to do a few times per packet at millions of packets per second. Then the hypervisor has to decode what the driver meant, copy the packet out of guest memory, and hand it to the host network stack. Copies and exits, for every single packet.

Way two: stop pretending, agree on a protocol

The next idea: if the guest knows it is a guest, stop imitating old silicon and invent a device that is easy to virtualize. That is paravirtualization — the guest cooperates with the hypervisor instead of being fooled by it. The standard paravirtual network card is virtio-net, part of the virtio family of standard paravirtual devices (disks, consoles, network cards, more). Guest and host share a ring of buffers in memory and agree on rules for who writes what. Instead of one exit per register poke, the guest can fill many buffers and then ring the bell once. A kernel helper called vhost moves the host end of that ring into the kernel so packets do not have to travel up into QEMU at all.

virtio-net is good. It is the sane default for most workloads, it is portable, and it makes moving a running VM to another host easy. But the host CPU is still touching every packet: some host thread must pull from the ring, run the packet through a software switch, and push it to the physical card. At high packet rates you end up burning whole CPU cores just to be a switch, and latency has a floor you cannot get under.

Way three: give the guest a real card

The third way is blunt: take a physical device, remove it from the host, and hand it to the guest. This is passthrough (also called device assignment). The guest runs the real vendor driver and talks to real registers. Nothing on the host runs per packet, and nothing copies the bytes. Performance is essentially bare metal.

The catch is obvious. A server has maybe two network ports. Passthrough gives one port to exactly one VM. You cannot run forty VMs on a machine with two cards. And there is a scarier catch, which the IOMMU chapter (chapter 2) is entirely about: a device given to a guest can read and write memory by itself, and a guest is not to be trusted with that power.

The tension, and the trick

So we want two things that fight each other. We want the guest to talk to hardware directly, with nothing in between. And we want many guests to share one card, each one isolated from the others and from the host.

The industry's answer is SR-IOV — Single Root I/O Virtualization, a standard from PCI-SIG, the group that governs the PCI Express bus. The idea in one sentence: build the sharing into the device itself. Instead of one card that software must divide, make a card that presents itself to the computer as many cards. Each one can be passed through to a different guest, and the card's own silicon keeps them apart.

Those many faces have names. The real, full-featured one is the Physical Function (PF). The lightweight clones are Virtual Functions (VFs). "Single Root" in the name means one host computer at the root of the bus tree, sharing its own devices — as opposed to a multi-root setup where several hosts share one device over a shared fabric, which is a different and much rarer thing.

One VF is the subject of this dossier. Over the next ten chapters we will watch it be created from a capability structure in silicon, become a device Linux can see, get put on a leash by the memory unit, be handed to a virtual machine, become a countable resource that a Kubernetes scheduler can allocate, and finally carry a packet from a guest driver to the wire without the hypervisor ever seeing it.

But we cannot talk about any of that yet, because we have not defined the words. A VF is a "PCI Express function". You need to know what that is, and that is the PCIe chapter (chapter 1).

Try it

On any Linux machine, run lspci | grep -i ethernet. Every line is one network device the computer can see. Keep that output around — by the end of the SR-IOV capability chapter (chapter 3) you will be able to read every field in it, and by the kernel chapter (chapter 6) you will be creating new lines in that list with a single write to a file.

Recap

Emulated network cards make the guest pay a VM exit and a copy for nearly every packet. Paravirtual virtio-net removes most of the exits by having guest and host share memory rings, but the host CPU still handles every packet. Passthrough gives the guest the real device and real speed, but a device can only be given away once, and giving hardware to an untrusted guest raises a safety problem. SR-IOV resolves the sharing half of that problem by making one card advertise itself as many devices: one Physical Function plus many Virtual Functions. The safety half needs one more piece of hardware, and that is the IOMMU chapter (chapter 2).

Check yourself

1. Why does an emulated network card cost more host CPU per packet than virtio-net does?

Answer

Because every register write the guest driver makes traps into the hypervisor as a VM exit, and an e1000 driver makes several per packet. QEMU must then decode the write, copy the packet out of guest memory and hand it to the host stack. virtio-net replaces those per-register traps with a shared ring: the guest fills many buffers and signals once, and vhost consumes them in the host kernel without waking QEMU.

Check it with perf kvm stat live on a host running both device types; the exit count per packet is the difference. The near miss is saying virtio-net is faster because it "avoids copies". It does not. The host CPU still touches every packet; what it avoids is the exit per register poke.

2. What exactly does passthrough buy you, and what does it cost you?

Answer

It buys the guest the real vendor driver talking to real registers, so nothing on the host runs per packet and nothing copies the bytes. It costs you sharing and safety: a physical function can be given away once, so two ports means two guests, and a device that can DMA anywhere is now driven by an untrusted guest.

The "given away" state is visible: after a device is bound to vfio-pci, lspci -k shows no host driver for it and ip link shows no interface. The near miss is thinking passthrough removes the hypervisor from the machine. It removes it from the data path only. QEMU still emulates the device's config space at boot.

3. In one sentence: what problem is SR-IOV solving that plain passthrough cannot?

Answer

SR-IOV lets one physical card present itself as many PCIe functions, so many guests can each be given a real device while sharing one port. Plain passthrough hands over the whole function, and a card has only one or two. The mechanism is the SR-IOV capability in the Physical Function's configuration space, which the kernel programs to make Virtual Functions appear on the bus.

Check it with lspci -vvv on a capable card: the capability lists a TotalVFs count. The near miss is claiming SR-IOV solves the safety half too. A VF can still DMA anywhere unless an IOMMU confines it, and that is the next chapter.

Chapter 1

Just enough PCIe

~11 min · layer: HW · Last chapter we decided we want to hand a piece of a network card to a guest. Before our Virtual Function can be a "piece of hardware", we need to know what a piece of hardware even is to a computer.

PCI Express (PCIe) is the bus that connects a modern CPU to its network cards, disks controllers, and GPUs. "Bus" is historical wording; PCIe is really a tree of point-to-point links with switches in it. That does not matter to us.

Let me say plainly what this chapter skips: lanes and link widths (x8, x16), link training, gen speeds, electrical signalling, packet framing on the wire, credit-based flow control. All real, all irrelevant here. SR-IOV lives entirely in the software-visible part of PCIe: how a device identifies itself, how the CPU reaches its registers, and how the device reaches memory. That is what follows.

Functions and their addresses

The unit of "a device" in PCIe is not a card. It is a function. A function is one addressable, independently-driven thing that the operating system can bind a driver to. A cheap card has one function. A dual-port network card usually has two functions, one per port, and Linux loads the driver twice. A combo card could have a network function and a storage function on the same board.

Every function has an address, written as BDF — Bus, Device, Function. You have seen it: 0000:03:00.1. Reading right to left: function 1, device (also called slot) 00, bus 03, and in front, 0000, the PCI domain or segment — a whole separate numbering space, almost always 0000 on ordinary servers. Within one device number there are only three bits of function number, so classically a device could have at most 8 functions. Remember that number; it becomes a problem in the SR-IOV capability chapter (chapter 3).

BDF is how everything in this dossier names hardware. In the Kubernetes chapter (chapter 8), a piece of Kubernetes will hand a pod a string like 0000:03:00.4, and that is the same kind of address as the one in your lspci output.

Configuration space: the ID card

Every function carries a small block of standardised registers called configuration space. Think of it as the device's ID card and control panel, laid out in a format defined by the PCI specification so that the operating system can read it without knowing anything about the device. The first 256 bytes are the classic PCI config space; PCIe extends it to 4096 bytes, and the extra area is called extended configuration space.

The first few entries are the ones you already half-know. The Vendor ID says who made the chip (15b3 is Mellanox, now NVIDIA; 8086 is Intel — yes, that is the 8086 chip's name used as a joke). The Device ID says which chip. Together they are what Linux matches against a driver's table of supported devices; this is literally how the kernel decides which driver should take the card in slot 3. There is also a class code saying "this is an Ethernet controller", a command register with switches like "allow this device to respond to memory reads" and "allow this device to start its own transfers", and a status register.

The clever part is what comes after the fixed header: the capability list. Rather than reserving space for every optional feature a device might have, PCI keeps a linked list. A pointer in the header says "the first capability is at offset X". At offset X you find a small structure whose first byte is an ID ("I am the MSI-X capability") and whose second byte is the offset of the next capability. You walk the chain until the next pointer is zero. Extended config space has its own longer chain, the extended capability list, in the same style.

This is exactly how a device announces "I can do SR-IOV". SR-IOV is one entry in the extended capability chain. Nothing more mystical than that: a structure in a linked list in config space, which the kernel finds by walking the chain.

BARs: how the CPU reaches the device

Config space is small and slow. Real work happens through the device's own registers and buffers, and those are reached through BARs — Base Address Registers. A BAR is a field in config space where the device says "I need this much address space", and the firmware or kernel writes back "fine, you live here". After that, that range of physical addresses no longer goes to RAM; the CPU's memory controller routes reads and writes there to the device instead.

This is MMIO — Memory-Mapped I/O. The device's registers appear as memory addresses. When the driver does what looks in C like storing a number into a pointer, the store actually travels down the PCIe tree and arrives in a register on the chip. A network card typically has one big BAR holding thousands of registers, plus one small page per queue whose purpose the NIC internals chapter (chapter 4) will explain.

Here is the fact to hold on to for later: BARs are the reason a passed-through device is fast. If the hypervisor can arrange for guest addresses to point straight at the device's BAR, the guest driver's stores reach the hardware with no software in between and no VM exit. That is the whole trick of the VFIO chapter (chapter 7), and it only works because devices are reached through plain memory addresses.

DMA: how the device reaches memory

Traffic goes the other way too, and this is the important direction. A network card does not want the CPU to feed it every byte. It wants to be told "there is a packet at physical address 0x1f3a4000, 1500 bytes, send it", and then fetch those bytes itself. A device reading and writing system RAM on its own initiative is DMA — Direct Memory Access.

A device can only do this if the "bus master" switch in its command register is on; the kernel turns it on when a driver claims the device. Once on, the device issues memory transactions with addresses in them, and historically those addresses were raw physical addresses. Read that again. A network card, with bus mastering on, can name any physical address in the machine, and the memory controller will obey. This is wonderful for performance and terrifying for security, and it is why the IOMMU chapter (chapter 2) exists.

MSI-X: how the device gets attention

When a packet arrives, the card must tell the CPU. Old devices had a physical interrupt wire. Modern ones use MSI-X, Message Signalled Interrupts, eXtended, which is really just DMA with a special meaning: to raise an interrupt, the device writes a specific small value to a specific address that the CPU's interrupt controller owns. The device holds a table of such address-and-value pairs, one per vector, and can have many vectors — commonly dozens or hundreds. That matters because it lets a card give each receive queue its own interrupt landing on its own CPU core.

Interrupts being memory writes is a detail worth remembering. It means interrupts, like data, are just DMA — so anything that can filter DMA can also filter interrupts. The IOMMU chapter (chapter 2) uses that.

Try it

Run sudo lspci -vvv -s <BDF> on any device (drop the -s to see everything). You will see Region 0: Memory at ... — those are BARs and their assigned addresses. You will see Capabilities: [40] Power Management, [70] Express and so on — the number in brackets is the offset, so you are reading the linked list itself. Capabilities with offsets of 0x100 or more are extended ones. On a Mellanox card you may already see Single Root I/O Virtualization (SR-IOV) in that list, waiting for the SR-IOV capability chapter (chapter 3).

Recap

An operating system drives PCIe functions, and a card may hold several. Each function is addressed by its BDF. Every function carries configuration space: a standard header identifying it, plus a linked list of capability structures announcing optional features — SR-IOV is one entry in that list. The CPU reaches a device through BARs, which map device registers into physical memory addresses (MMIO). The device reaches memory on its own through DMA, and signals the CPU with MSI-X, which is itself just a DMA write to a special address. Two facts drive everything later: device registers are ordinary memory addresses, which makes fast passthrough possible; and DMA lets a device name any physical address, which makes passthrough dangerous.

Check yourself

1. Your card is at 0000:03:00.0. What are its bus, device, and function numbers, and how many functions could device 00 on bus 03 classically have?

Answer

Bus 03, device 00, function 0, in domain 0000. Classically a device can have 8 functions, numbered 0 to 7, because the function field is three bits wide. Read the address right to left: function, then device (also called slot), then bus, with the domain as the separate leading field.

Check it with lspci -s 03:00., which lists every function under that device number. The near miss is reading left to right and calling 03 the device. The order is bus, device, function, and the domain in front is almost always 0000.

2. How does the kernel discover that a device supports SR-IOV without knowing anything about that specific chip?

Answer

It walks the extended capability list in the function's configuration space and finds an entry whose ID says "SR-IOV". The list is a chain of small structures, each with an ID and a pointer to the next, in a layout the PCI specification fixes for every device. Generic PCI code therefore finds the capability before any vendor driver loads.

Check it with lspci -vvv: the bracketed numbers are the offsets of each entry, and the SR-IOV entry sits at 0x100 or above. The near miss is answering "the driver knows its own hardware". The Vendor and Device ID table picks the driver; the capability list is what announces the feature.

3. Why is "a device can DMA to any physical address" both the reason passthrough is fast and the reason it is dangerous?

Answer

Fast, because the card fetches descriptors and packet bytes itself, so the CPU never copies data and never mediates per packet. Dangerous, because the address in a descriptor is whatever the driver wrote, and with bus mastering on the memory controller obeys. If an untrusted guest writes the descriptors, it can name the host kernel's memory or another guest's.

The bus master bit is in the command register; lspci -vvv shows it as BusMaster+. The near miss is locating the danger in the guest reaching the card's registers. Those are the card's own. The danger is the card reaching everybody else's memory on the guest's behalf.

Chapter 2

The IOMMU: putting device DMA on a leash

~11 min · layer: HW KERNEL · Last chapter we learned that a PCIe function can read and write any physical address by itself. Our Virtual Function will one day be driven by an untrusted guest. This chapter is the reason that is allowed to be safe. It is the security keystone of the whole dossier — if you skim one chapter, do not skim this one.

Let us be concrete about the danger. Suppose we pass a network card through to a guest, as the prologue (chapter 0) described. The guest now owns the card's registers. The guest driver tells the card: "send the 1500 bytes at physical address X". Nothing stops the guest from choosing an X that belongs to the host kernel, or to another VM. The card obeys — it is a machine, it does not know what a VM is. One write to a register and the guest reads or scribbles on any memory in the server. Passthrough without protection is equivalent to giving the guest root on the host.

The fix is a piece of hardware sitting between devices and memory.

An MMU, but for devices

You may know that CPUs do not let programs touch physical memory either. A program uses virtual addresses, and a unit called the MMU (Memory Management Unit) translates them to physical ones through page tables the kernel controls. A program cannot reach memory the kernel did not map for it. That is the foundation of process isolation.

The IOMMU — Input/Output Memory Management Unit — is the same idea applied to devices. It sits on the path between the PCIe tree and the memory controller. Every DMA transaction a device issues passes through it and is translated, or rejected. Intel's implementation is called VT-d (Virtualization Technology for Directed I/O); AMD's is AMD-Vi; ARM calls its version an SMMU. They differ in registers and details. The idea is the same.

The addresses a device uses are therefore no longer physical addresses. They are IOVAs — I/O Virtual Addresses. An IOVA means nothing on its own; it only means something together with the identity of the device that issued it. And the IOMMU knows that identity, because every PCIe transaction carries the requester ID of the function that started it — which is, in practice, its BDF. So the IOMMU can keep a separate set of page tables per function.

One more word before the picture. A guest believes it has physical memory starting at zero, but that belief is a fiction the host maintains; the addresses the guest thinks are physical are guest physical addresses, and the host knows which real page backs each one. Keep the two apart in your head, because the IOMMU's job is precisely to translate between them.

That single fact is what makes SR-IOV work. Each Virtual Function has its own BDF, so each VF gets its own IOMMU page tables, so each VF can be pointed at exactly one guest's memory and nothing else. Hold that thought until the SR-IOV capability chapter (chapter 3).

What the host actually programs

In the passthrough case the mapping the host installs is deliberately simple: for each chunk of the guest's memory, map "guest physical address" to "the host physical page that backs it". The guest driver then hands the device addresses that are correct from the guest's point of view, the IOMMU corrects them, and nobody has to rewrite anything at packet time. This is the second half of why passthrough is fast: the PCIe chapter (chapter 1) gave us BARs so the CPU can reach the device without help, and the IOMMU gives us DMA that reaches the right place without help.

Non-virtualized drivers use the IOMMU too, by the way. When an ordinary kernel driver calls the DMA mapping API, it is asking for an IOVA to be created for a buffer. On a machine with the IOMMU on, that address is a translated one, and a buggy device cannot corrupt memory outside what was mapped. Same hardware, different purpose.

Interrupt remapping, briefly

The PCIe chapter (chapter 1) warned that MSI-X interrupts are just DMA writes to a special address. That means a malicious device — or a guest that controls one — could forge an interrupt aimed at any CPU with any vector number, which is a fine way to attack a host. So IOMMUs also implement interrupt remapping: writes into the interrupt address range are not taken literally. They are treated as an index into a host-controlled table, and the host decides which real vector and which real CPU each device is allowed to signal. Without interrupt remapping enabled, Linux will refuse to do device assignment safely (you can force it, and the kernel will tell you clearly that you are unsafe). It is one paragraph of theory and one line of firmware settings, and it is not optional.

IOMMU groups: the unit you can give away

Here is where theory meets messy reality. We would like the finest possible granularity: one function, one set of page tables, one owner. Sometimes the hardware cannot promise that.

Two problems get in the way. First, some PCIe topologies let two devices behind the same switch talk to each other directly, peer-to-peer, without the transaction ever reaching the IOMMU. If device A can DMA straight into device B, then giving A to a guest also effectively gives it B. The capability that lets a switch force such traffic upward to be checked is called ACS (Access Control Services), and plenty of consumer boards either lack it or lie about it. Second, some devices and bridges do not put their own correct requester ID on transactions — old PCI devices behind a bridge all appear as the bridge, so they are indistinguishable to the IOMMU.

Linux handles this by computing, at boot, the smallest sets of devices that are truly isolated from each other, and calling each set an IOMMU group. The rule is blunt and worth memorising: the IOMMU group is the smallest unit of hardware that can be safely given to a guest. If your GPU shares a group with a USB controller, you assign both or neither.

You can read these groups directly from sysfs, the kernel's file-tree view of its own internals:

$ ls /sys/kernel/iommu_groups/
0  1  2  3  4  ... 42  43  44

$ ls /sys/kernel/iommu_groups/43/devices/
0000:03:00.0

$ ls /sys/kernel/iommu_groups/44/devices/
0000:03:00.4

Good news for us: SR-IOV Virtual Functions are usually well behaved here. A VF is a real PCIe function with its own requester ID, produced by a card that was designed for exactly this purpose, so on server hardware each VF typically ends up in a group of its own. That is not an accident. It is the point.

Try it

Check whether your machine even has the IOMMU switched on: ls /sys/kernel/iommu_groups/ | wc -l. Zero means it is off — usually because of a BIOS setting (VT-d / AMD-Vi / "IOMMU") or a missing kernel command line option (intel_iommu=on on older Intel setups; AMD and recent Intel enable it by default). Then dmesg | grep -i -e DMAR -e IOMMU. DMAR is the name of the firmware table that describes Intel's IOMMU hardware to the OS; seeing it means the platform is telling the kernel the unit exists.

Recap

A device with DMA can name any physical address, so handing one to a guest is unsafe without help. The IOMMU is that help: an address translator for devices, called VT-d on Intel and AMD-Vi on AMD, which turns device-issued IOVAs into physical addresses using page tables the host controls, per requester ID. For a guest, the host maps guest physical addresses to real ones, so the guest can drive the device with its own addresses and still be caged. Interrupt remapping applies the same discipline to MSI-X, which is just DMA to a special address. Because some hardware allows unmediated peer-to-peer traffic or hides requester IDs, Linux computes IOMMU groups, and the group is what can be safely assigned to a guest.

Check yourself

1. A guest driver programs a device with a buffer address. Which component makes sure that address cannot point at the host kernel, and how does it know which guest to check against?

Answer

The IOMMU. Every DMA transaction passes through it and is translated with page tables the host chose, so an address with no mapping is refused and reported rather than obeyed. It knows which tables to use because every PCIe transaction carries the requester ID of the function that issued it, in practice the function's BDF, and the host installed one set of tables per requester ID.

Check it in /sys/kernel/iommu_groups/*/devices/, which shows which requester IDs share one translation domain. The near miss is answering "the hypervisor checks the address". The hypervisor is asleep during DMA. The check is in hardware, on every transaction.

2. Why is an IOMMU group sometimes larger than one function, and what does that mean practically when you want to assign a device?

Answer

Because the platform cannot always prove two functions are isolated. Two causes: a switch without ACS lets devices behind it talk peer-to-peer without the IOMMU seeing the traffic, and some devices or bridges do not stamp their own requester ID, so the IOMMU cannot tell them apart. Linux computes the smallest provably isolated sets at boot and calls each one a group. Practically, every device in the group goes to the same guest or none does.

Check it with ls /sys/kernel/iommu_groups/<n>/devices/; more than one entry means a shared group. The near miss is thinking unbinding the other devices from their host drivers is enough. They must be bound to vfio-pci too, or VFIO refuses to open the group.

3. Why does interrupt remapping matter, given that we already translate DMA addresses?

Answer

Because MSI-X interrupts are DMA writes to the interrupt controller's address range, and address translation alone would still deliver whatever vector value the device wrote. A guest controlling a device could forge an interrupt to any CPU with any vector, which is a way to attack the host. Interrupt remapping treats writes into that range as an index into a host-controlled table, so the host decides which real vector and CPU each device may signal.

Check it with dmesg | grep -i 'interrupt remapping'; without it Linux refuses safe device assignment unless you force it. The near miss is filing remapping under performance. It is a permission check, applied to the one kind of DMA that address translation does not fully constrain.

Chapter 3

SR-IOV proper: one device, many faces

~10 min · layer: HW · Last chapter gave us a leash for devices, and told us the leash is attached per requester ID. Now our Virtual Function finally comes into existence: this chapter is where it becomes a PCIe function with a BDF of its own, which is exactly what the leash needs.

We know what we want. We want one physical card to appear as many independent PCIe functions, each with its own BDF, so that each one can get its own IOMMU page tables and be given to a different guest. SR-IOV is the standard way for hardware to offer precisely that.

The capability

The PCIe chapter (chapter 1) said SR-IOV is one entry in the extended capability list. Let us look at what that entry contains, described by what each field does.

It contains, first, some numbers the device is telling us: TotalVFs, the most Virtual Functions this function could ever create, burned in by the vendor and sometimes further limited by firmware settings. Second, a number we write: NumVFs, how many we actually want right now. Third, a switch, VF Enable. Fourth, a small set of fields describing how the VFs' addresses are computed, which we will get to. And that is more or less the whole mechanism.

The function that owns this capability is the Physical Function (PF). A PF is an ordinary, complete PCIe function — it has its full config space, its BARs, its own driver, and it can be used as a normal network port with no virtualization at all. It just happens to also carry the power to create children.

Write a number into NumVFs, set VF Enable, and the device begins responding, on the bus, as that many additional functions. Those are the Virtual Functions (VFs). They did not exist a moment ago. Nothing was plugged in. From the operating system's point of view, several new PCIe devices have appeared, and it must go enumerate them and find drivers for them — exactly as if someone had hot-plugged cards into the machine.

What a VF is, and what it is not

A VF is deliberately poor. It is a function with just enough of a config space to be discoverable and drivable, and no more. It has a Vendor ID and a Device ID (typically a different Device ID from its parent, so the kernel can pick the VF driver rather than the PF driver). It has BARs. It has an MSI-X capability so it can raise interrupts. It has a PCI Express capability. What it does not have is control over anything shared: it cannot set the physical link speed, cannot reconfigure the port, and in most designs cannot even set its own MAC address without asking permission. Many of its config registers read as zero or are ignored on write.

Think of the PF as the person who owns the flat and the VFs as tenants with keys to one room each. A tenant can furnish their room and cannot touch anything shared.

The important thing a VF does have is its own requester ID, because it has its own BDF. The IOMMU chapter (chapter 2) told us what that buys: its own IOMMU page tables, its own leash, its own guest. Everything else about SR-IOV is plumbing around that one fact.

Where do the addresses come from?

Two questions have to be answered by hardware: what BDF does each VF get, and where do its BARs live?

For BDFs, the capability holds two fields with self-explaining names: First VF Offset and VF Stride. The rule is arithmetic: the first VF's routing number is the PF's number plus the offset, and each following VF is one stride further along. If the PF is 03:00.0 with offset 4 and stride 1, the VFs are 03:00.4, 03:00.5, 03:00.6, and so on, walking through the function-number space and then, when that runs out, spilling onto higher bus numbers — which is why an SR-IOV-capable slot is often given a range of bus numbers rather than just one. There is no per-VF configuration to do here; the numbering is a formula, and the kernel evaluates it.

For BARs, the design is neat. VFs do not each negotiate their own BAR from the operating system. Instead the SR-IOV capability itself declares BAR sizes on behalf of all the VFs, and the OS allocates one contiguous region big enough for all of them. Each VF's BAR is then a slice of that region, at a fixed stride. So enabling 64 VFs costs one large address-space reservation, laid out in a predictable grid, instead of 64 separate negotiations. Each VF still sees, through its own BAR, only its own slice — and since the VFIO chapter (chapter 7) will map exactly that slice into a guest, the guest can reach its registers and no one else's.

Getting past eight functions

The PCIe chapter (chapter 1) mentioned that the function number is three bits, so a device can classically have only eight functions. Eight VFs would be a sad limit; real cards offer 64, 127, 256. The escape hatch is ARI — Alternative Routing-ID Interpretation — another extended capability. With ARI, the hardware stops treating those bits as "5-bit device number plus 3-bit function number" and reinterprets them as a single 8-bit function number, giving 256 functions behind one device number. Enabling ARI needs support from the upstream port as well as the device, which is why high VF counts sometimes work in one slot and not another. That is all of it; you may now forget ARI until it appears in a log message.

The punchline

Let us state the payoff sentence of this entire dossier, now that every word in it is defined:

A Virtual Function is a PCIe function with its own BDF, therefore its own requester ID, therefore its own IOMMU page tables, therefore it can be handed to one untrusted guest safely, and because it has its own BARs and its own MSI-X vectors, that guest can drive it directly at full speed.

Everything from here on is either about what the card does with those VFs internally, in the NIC internals and ConnectX chapters (chapters 4 and 5), or about the software chain that creates them, guards them, and delivers them to the right VM in the right pod, from the kernel chapter to the KubeVirt chapter (chapters 6 to 9).

Try it

On a server with a modern network card: lspci -vvv -s <PF BDF> | grep -A6 SR-IOV. You will see Total VFs and Number of VFs, plus VF offset and stride. Do the arithmetic yourself and predict the BDF the first VF will have. In the kernel chapter (chapter 6) you will create it and check whether you were right.

Recap

SR-IOV is one extended capability structure in the config space of a Physical Function. It advertises how many Virtual Functions the device can create, accepts a number saying how many to create now, and describes how those VFs will be addressed. Enabling it makes new PCIe functions appear on the bus with no physical change to the machine. A VF is intentionally minimal — it can move packets and raise interrupts, but it cannot touch anything shared — yet it has the one thing that matters: its own BDF, and therefore its own IOMMU protection domain. VF BDFs come from an offset-and-stride formula, VF BARs are equal slices of one region reserved by the PF, and ARI is the trick that lets a device have more than eight functions.

Check yourself

1. A PF at 05:00.0 reports First VF Offset 8 and VF Stride 2. What is the BDF of VF number 1 (the second VF)?

Answer

05:01.2. The arithmetic runs on the eight-bit routing number, which is device times 8 plus function. The PF is device 0, function 0, so 0. Add the offset 8 for VF 0, giving 8, which is device 1, function 0, written 05:01.0. Add one stride of 2 for VF 1, giving 10, which is device 1, function 2, written 05:01.2.

Check it with lspci -vvv -s 05:00.0 | grep -A6 SR-IOV for the offset and stride, then lspci after creating two VFs. The near miss is treating the stride as a function increment only and answering 05:00.a. Function numbers stop at 7 and carry into the device field.

2. Why can a VF not change the link speed of the physical port, and why is that a feature rather than a limitation?

Answer

Because the registers and firmware commands that control shared state are absent from the VF. A VF's config space and BAR contain only its own queues, doorbells and interrupt table; writes to anything else are ignored or have nowhere to go. The PF owns the port, the eswitch tables and the resource pools. That is a feature because the VF will be driven by an untrusted guest, and isolation that depends on the guest's good behaviour is not isolation. The wall is in silicon, so it costs no cycles and cannot be argued with.

Compare lspci -vvv output for the PF and a VF: the VF's capability list is shorter and many of its registers read zero. The near miss is assuming the hypervisor filters these writes. It does not see them; the MMIO path has no software on it.

3. Complete the chain: a VF has its own BDF, therefore its own ___, therefore its own ___, therefore it can be given to a guest safely.

Answer

Its own requester ID, therefore its own IOMMU page tables. The requester ID is derived from the BDF and stamped on every transaction the VF issues, and the IOMMU keeps one set of page tables per requester ID. So the host can point exactly one VF at exactly one guest's memory.

Check it under /sys/kernel/iommu_groups/: the group directory for a VF contains only that VF's BDF. The near miss is answering "its own BARs, therefore its own MMIO". Those make the VF fast, because the guest can reach its registers directly. They do not make it safe. Safety comes from the DMA side, and the DMA side is keyed on the requester ID.

Chapter 4

Inside the NIC: the parts drivers talk to

~12 min · layer: HW · Our Virtual Function now exists as a PCIe function with its own BDF and its own BARs. But what is behind those BARs? A VF is a slice of a network card — this chapter is about what a slice actually consists of, and about the small switch inside the card that decides where each packet goes.

Same discipline as the PCIe chapter (chapter 1). We only look at the parts a driver touches and the parts that make SR-IOV behave the way it does. Everything about physical layer encoding, cable diagnostics, temperature sensors and clock domains stays closed.

Rings and descriptors: how a driver hands over a packet

A driver never hands a packet to a card by copying it into the card. It hands over an address. The structure holding that address, plus the length and some flags, is a descriptor: a small fixed-size record, laid out in a format the hardware understands, that says "there is a buffer at this address, this many bytes long, do the thing".

Descriptors live in a descriptor ring — a circular array in host RAM, shared between driver and device. The driver writes descriptors at the tail and advances a producer index. The device consumes from the head. When the ring wraps past the end it goes back to the start, hence "ring". There are separate rings for the two directions: a TX ring for transmit, where the driver posts packets it wants sent, and an RX ring for receive, where the driver posts empty buffers in advance for the card to fill when packets arrive. A matched TX and RX pair is often called a queue pair.

How does the driver learn that work is finished? Through a completion queue: another ring, written by the device, where it posts small records saying "descriptor number N is done, and by the way the received packet is 342 bytes and its checksum was correct". The driver reads completions, recycles the buffers, and posts more. Interrupts (MSI-X from the PCIe chapter) exist mainly to wake the driver when a completion queue goes from empty to non-empty; under heavy load drivers switch to polling and turn interrupts off, because at millions of packets per second an interrupt per packet would be madness.

Notice what all of that requires: DMA. The card reads descriptors from RAM, reads packet data from RAM, writes packet data to RAM, writes completions to RAM. Every one of those accesses goes through the IOMMU when it is enabled. A VF's rings are in the guest's memory, and the guest's memory is exactly what the VF's IOMMU page tables permit. The isolation from the IOMMU chapter (chapter 2) is doing continuous work here, on every packet, in hardware, at zero cost.

Doorbells: the one write that starts everything

After the driver has written descriptors into RAM, the card still does not know. Something must tell it. That something is a doorbell: a register in the card's BAR that the driver writes to announce "I have advanced the producer index of ring 7 to 4102". One MMIO store. The card reads it, then goes and fetches the new descriptors by DMA.

Doorbells are why a network card's BAR is much larger than the number of its control registers would suggest. Cards give each queue its own doorbell in its own memory page, so that different queues — and, crucially for us, different VFs — can be rung independently without sharing a page. Pages are the unit the CPU and the IOMMU can protect, so "one doorbell page per owner" is what allows a guest to be given the ability to ring its own doorbells and nothing else.

Hold on to that image, because it is the last step of the packet walk. In the KubeVirt chapter (chapter 9) we will trace a packet, and it begins with a guest's driver writing one value to one doorbell page mapped directly into the guest, with nothing on the host running.

Receive steering: deciding whose packet this is

Transmit is easy: whoever posted the descriptor owns the packet. Receive is the hard direction. A packet arrives from the wire with a destination MAC address, maybe a VLAN tag, and the card must decide which ring to put it in — and with SR-IOV, which owner's rings those are.

Cards do this with filter tables. A MAC filter table maps destination MAC addresses to destinations inside the card. A VLAN table does the same for VLAN tags — the 12-bit identifier in an Ethernet header that separates one virtual LAN from another. Multicast lists, broadcast rules and a promiscuous mode ("give me everything") sit alongside. When a VF is created, the card is told: this MAC address, and optionally this VLAN, belong to VF 3. Packets matching go to VF 3's rings and nowhere else.

Within one owner there is a second level of spreading, RSS (Receive Side Scaling): the card hashes the packet's addresses and ports and uses the hash to pick one of several receive rings, so traffic spreads across CPU cores while all packets of one connection stay on one core. RSS is orthogonal to SR-IOV, but each VF has its own RSS setup, because each VF is a whole small network card.

The embedded switch

Now put it together. Inside the card there is one physical port and many owners: the PF and its VFs. Something must move packets between them. That something is a real Layer 2 switch implemented in the silicon, called the embedded switch, or eswitch, or by its standard name a VEB (Virtual Ethernet Bridge).

Its ports are: the physical port facing the wire, plus one internal port per function — the PF and each VF. It forwards by MAC address and VLAN, exactly like the switch in your office ceiling, only smaller and much faster. Three consequences follow, and all three surprise people:

First, VF-to-VF traffic never leaves the card. If VM A on VF 3 sends to VM B on VF 4 on the same card, the eswitch forwards it internally at silicon speed. It does not touch the wire, and it does not touch the host CPU. Your external switch and your network monitoring will never see it — a fact that has caused many confused afternoons.

Second, the eswitch is where per-VF policy is enforced. Because every packet from a VF passes through it, it is the natural place to check things. Anti-spoofing (often called spoofchk) means the eswitch drops a transmitted packet whose source MAC does not match the MAC the host assigned to that VF, and equivalently for VLAN tags. A guest with root access cannot lie about who it is, because the lie is caught in hardware after the guest's driver has already sent it. Per-VF rate limiting lives here too: a maximum, and on many cards a minimum guaranteed, transmit rate per VF, enforced by hardware schedulers that the guest cannot bypass.

Third, the eswitch's forwarding tables are programmed by the PF driver, never by a VF. So a VF that wants a new MAC address has to ask the PF for it, because only the PF can write the table. The kernel chapter (chapter 6) shows the channel through which it asks.

Try it

On a host with a network card, ethtool -l <iface> shows how many queue pairs, or "combined channels", the driver has set up, and ethtool -x <iface> prints the RSS table that maps hash values to those queues. ethtool -S <iface> | head -40 lists per-queue counters. You are looking at exactly the structures described above, on a real card.

Recap

A driver gives a card work by writing descriptors, each an address plus a length, into a ring in RAM, then ringing a doorbell register in the card's BAR. The card fetches everything by DMA and reports back through a completion queue, with MSI-X interrupts only as a wake-up. Incoming packets are sorted by MAC and VLAN filter tables, and spread over rings by RSS. All of the owners inside one card, the PF and every VF, are ports on a small Layer 2 switch built into the silicon, the eswitch. That switch forwards VF-to-VF traffic without touching the wire or the host, and it is where anti-spoofing and rate limiting are enforced, in hardware, beyond the guest's reach. Only the PF driver programs its tables.

1. Walk through the eight steps of sending one packet. Which single step involves the CPU writing to the device?

Step 2, the doorbell write. The driver writes a descriptor into the TX ring in RAM (1), then makes one MMIO store to the doorbell page (2). Answer

None on the wire, and no host CPU cycles per packet. The eswitch inside the card forwards by destination MAC, and both VFs are ports on it, so a frame from VF 3 addressed to VF 4's MAC is switched internally and never reaches the physical port. The host CPU is off the path because each guest's driver rings its own doorbell and the card DMAs from each guest's memory through the IOMMU.

Check it by watching your external switch's port counters stay flat while ethtool -S on the VFs climbs, and top on the host shows no softirq load. 3. A guest is root and sets its interface's MAC address to that of the gateway. Why does this attack fail, and where exactly does it fail?

Answer

It fails in the eswitch, at transmit time, because anti-spoofing drops any frame whose source MAC does not match the MAC the host assigned to that VF. The guest's ip link set dev eth1 address appears to succeed locally, but underneath the guest driver asks the PF for the new MAC through the mailbox, the PF driver refuses because the MAC was administratively set, and the filter entry stays as it was. Frames the guest then sends with the forged source MAC are checked against that entry in silicon and dropped.

Check it with ip -d link show <pf>, which shows spoof checking on for the VF, and with the PF driver's per-VF spoofed-packet counter in ethtool -S. The near miss is "the hypervisor filters it". No software sees the frame. Spoofchk must be on for this; some drivers default it off.

Chapter 5

Mellanox and NVIDIA specifics: ConnectX and mlx5

~13 min · layer: HW KERNEL · Our Virtual Function is a port on an embedded switch inside a card. Now we name the card. Everything so far was vendor-neutral; this chapter is about how NVIDIA's ConnectX family in particular presents these ideas, because that is the hardware most people meet.

Mellanox was an Israeli maker of high-speed network adapters, bought by NVIDIA in 2020. Its adapter line for Ethernet and for InfiniBand (a separate high-speed network standard used in supercomputers and AI clusters) is called ConnectX, numbered by generation: ConnectX-4 and ConnectX-5 are the widely deployed older ones, ConnectX-6 and ConnectX-7 the current mainstream at the time of writing in 2026, with ConnectX-8 arriving in newer platforms. Port speeds have climbed from 25 and 40 Gbit/s to 100, 200 and 400. There is also a bigger relative, BlueField, which is a ConnectX plus a cluster of Arm CPU cores on the same board — a DPU, or data processing unit. We will not go into BlueField, but it is worth knowing it exists and that it runs the same driver family.

What stays constant across all these generations, and is the reason one driver covers them all: the card is firmware-heavy. A ConnectX exposes a fairly abstract command interface rather than a big pile of hardware registers. The driver builds a command — "create a queue pair", "add this steering rule", "enable this VF" — writes it into a mailbox area, rings a doorbell, and the card's firmware executes it. Compare with older Intel-style designs where the driver writes many specific registers directly. This design is why so much ConnectX behaviour depends on firmware version and firmware configuration, and it is why the vendor ships a whole tool just for configuring the card's persistent settings.

The driver family

In Linux, the ConnectX-4 and newer generations are driven by mlx5. It is not one module but a family, and understanding the split saves confusion later:

Importantly, the VF driver is the same driver. A VF of a ConnectX presents a mlx5-compatible function, and inside a guest, mlx5_core binds to it and creates a normal network interface. There is no separate "mlx5 VF driver" module to install. Contrast that with Intel, where the PF driver (ice, i40e, ixgbe) and the VF driver (iavf) are different modules entirely.

Turning SR-IOV on: two switches to flip

On a ConnectX, enabling SR-IOV takes two separate acts, and forgetting the first is the most common beginner's problem.

The first act is persistent firmware configuration, stored in the card's own NVRAM (non-volatile memory on the board). The tool is mlxconfig, part of the NVIDIA Firmware Tools package (MFT). You tell the card that it is permitted to have VFs at all, and how many:

# mst start                       # loads the tool's device access module
# mlxconfig -d /dev/mst/mt4125_pciconf0 query | grep -i sriov
         SRIOV_EN                            False(0)
         NUM_OF_VFS                          0

# mlxconfig -d /dev/mst/mt4125_pciconf0 set SRIOV_EN=1 NUM_OF_VFS=16
Apply new Configuration? (y/n) [n] : y
Applying... Done!
-I- Please reboot machine to load new configurations.

This setting is still there after reboots and reinstalls, because it is stored on the card. It also has a real cost: reserving capacity for many VFs consumes card resources whether you use them or not, so do not set NUM_OF_VFS=127 out of enthusiasm.

The second act is the runtime one, done through Linux, and it is the same on every vendor's card: write a number to a file in sysfs. That is the kernel chapter (chapter 6), and we will get there in a moment.

devlink, and the two eswitch modes

The NIC internals chapter (chapter 4) said the card contains an embedded switch. On ConnectX, that switch can run in two quite different modes, and choosing between them is the single most consequential configuration decision in this whole area. The tool for it is devlink, a general Linux interface for configuring device-wide settings that do not belong to any single network interface. Older guides used a module parameter or a vendor tool; devlink is the modern way.

In legacy mode — the default — the eswitch behaves as the NIC internals chapter described: a plain VEB forwarding by MAC and VLAN, configured by the PF driver through the per-VF settings that the kernel chapter (chapter 6) covers. Simple, and enough for many deployments.

In switchdev mode, the card stops pretending to be a fixed switch and starts pretending to be a programmable one that Linux itself can drive. The key new object is the VF representor: for every VF, the host gets an extra ordinary network interface — a host-side puppet standing in for that VF's port on the eswitch. Traffic that the hardware does not know how to handle for that VF pops out of its representor on the host, and packets the host sends into the representor are delivered to the VF.

Why is this wonderful? Because now every existing Linux networking tool applies to VF traffic. You can put representors into an Open vSwitch (OVS) bridge. OVS is the standard software switch used by most cloud platforms, and it forwards by rules installed from a controller. It will do what it always does: see the first packet of a flow, decide the rule, and install it. Except that when OVS installs the rule into the kernel's traffic control subsystem, the mlx5 driver takes that rule and programs it into the card's eswitch hardware instead. After that, the whole flow runs in silicon and neither the host CPU nor the representor sees another packet of it. NVIDIA's brand name for this hardware-offloaded OVS path is ASAP² (Accelerated Switching and Packet Processing).

So: legacy mode gives you a simple fixed switch. Switchdev mode gives you a software-defined switch whose control plane is ordinary Linux and whose data plane is the NIC. For Kubernetes with overlay networks and security policies, switchdev is what makes VFs usable without giving up software networking.

# find the devlink name of the PF, then switch modes
# devlink dev show

Two neighbouring topics, sign-posted only

RDMA. ConnectX cards are equally at home doing RDMA (Remote Direct Memory Access) — letting a remote machine's network card write directly into this machine's memory, with the CPU not involved at all. Over Ethernet this is called RoCE (RDMA over Converged Ethernet). VFs can carry RDMA too, which is why storage and AI workloads care so much about SR-IOV on these cards. It is a large subject with its own vocabulary and we will not open it here.

Subfunctions. Recent mlx5 supports a lighter-weight sharing unit than a VF, created through devlink ports and not consuming a PCIe function at all. It is closely related to the industry direction described in the epilogue (chapter 10), so we defer it.

1. You write to sriov_numvfs on a fresh ConnectX and get an error. What did you most likely forget, and which tool fixes it?

Answer

The persistent firmware setting. 2. What is a VF representor, and what problem would you have without one if you wanted OVS to apply security policy to a VF's traffic?

Answer

A representor is a host-side network interface standing in for one VF's port on the eswitch, created when the eswitch is in switchdev mode. Packets the hardware has no rule for surface through it, and packets the host sends into it are delivered to the VF. Without one, VF traffic is invisible to the host: in legacy mode the eswitch forwards internally by MAC and VLAN, and there is no host interface for OVS to attach a port to. With representors, OVS treats them as ordinary ports, decides on the first packet, and mlx5 offloads the resulting rule into the eswitch.

Check it with devlink dev eswitch show pci/<PF> reporting mode switchdev, and ip link listing interfaces such as eth0_0. The near miss is thinking the representor carries the data path. After offload it carries only misses; the flow runs in silicon.

Answer

Anti-spoofing is universal in behaviour and reached through the same ip link set ... vf N spoofchk on, although each vendor's silicon implements it differently.

Chapter 6

The Linux kernel's role

~11 min · layer: KERNEL · Last chapter our card was configured and its embedded switch put in the mode we wanted. Now the Virtual Function actually comes into existence, with one write to one file — and then the kernel has to keep it honest, because a VF is unprivileged by design.

Everything from the PCIe chapter to the ConnectX chapter (chapters 1 to 5) was about hardware being able to do something. This chapter is about the operating system doing it.

One write to a file

When the kernel finds an SR-IOV capability while walking a function's extended capability list, it creates two files in that device's sysfs directory:

$ ls /sys/bus/pci/devices/0000:03:00.0/ | grep sriov
sriov_drivers_autoprobe
sriov_numvfs
sriov_totalvfs
sriov_vf_device

$ cat /sys/bus/pci/devices/0000:03:00.0/sriov_totalvfs
16
$ cat /sys/bus/pci/devices/0000:03:00.0/sriov_numvfs
0

sriov_totalvfs is read-only: it is TotalVFs from the capability, as limited by firmware settings — on a ConnectX this is where the NUM_OF_VFS you set with mlxconfig shows up. sriov_numvfs is writable, and writing it is what creates the VFs:

# echo 4 > /sys/bus/pci/devices/0000:03:00.0/sriov_numvfs

Transcript is illustrative — device IDs, firmware version and exact wording vary by card and kernel — but this is the shape of what you will see.

Four devices appeared. Nobody opened the machine. Their BDFs are exactly what the offset-and-stride arithmetic of the SR-IOV capability chapter (chapter 3) predicted: offset 4, stride 1, so 03:00.4 through 03:00.7. Their Device ID 101e differs from the PF's, which is how the kernel knows to treat them as VFs.

Underneath, the write reaches the PF driver, which calls pci_enable_sriov(). That kernel function does the mechanical work: sanity-check the count against TotalVFs, program NumVFs and VF Enable in the capability, wait the mandatory settling time, compute each VF's BDF, create a kernel device object for each one, assign each one its slice of the VF BAR region, and add them to the bus so that normal device probing happens. If sriov_drivers_autoprobe is 1 (the default), the kernel then tries to bind a driver to each new VF immediately. Writing 0 to that file before creating VFs is a common trick when you intend to hand the VFs to virtual machines and do not want the host driver to grab them first.

Writing 0 to sriov_numvfs destroys all the VFs. There is no way to remove just one. This is worth knowing before you try it on a machine where other people's VMs are running.

Two drivers, two privilege levels

The PF driver and the VF driver are separate roles even when, as on mlx5, they are the same code. The PF driver owns everything shared: the physical port, the eswitch tables, the resource pools, the firmware command interface. The VF driver owns only its own queues and doorbells.

This split is enforced in silicon. The VF simply does not have the registers or command permissions to touch shared state. And that is exactly what we need, because in the deployment we are heading towards, the VF driver is running inside a guest that we do not trust at all.

The mailbox: asking nicely

But a VF driver does sometimes need privileged things. It needs a MAC address programmed into the eswitch's filter table so packets reach it. It may need a reset after its guest reboots. It needs to know when the physical link goes down. None of these can it do itself.

So every SR-IOV NIC provides a private channel between a VF and its PF, called a mailbox (Intel documentation says mailbox or admin queue, with the message protocol named virtchnl; mlx5 routes such requests through its firmware command interface). Mechanically it is a small shared region plus an interrupt in each direction. Logically it is a request-response protocol: the VF driver posts "I would like MAC aa:bb:cc:dd:ee:ff", the PF driver, running on the host and trusted, receives it, checks its policy, and either programs the hardware and answers yes, or answers no.

The PF driver is therefore a policy checkpoint. It is where "this guest may not choose its own MAC" is implemented. A guest can ask for anything; the answer comes from the host.

The host-side knobs

The host administers VFs through ip link, using a per-VF sub-syntax. These commands act on the PF's interface and identify the VF by its index:

# ip link set enp3s0f0 vf 0 mac aa:bb:cc:00:00:01
# ip link set enp3s0f0 vf 0 vlan 101
# ip link set enp3s0f0 vf 0 spoofchk on
# ip link set enp3s0f0 vf 0 trust off
# ip link set enp3s0f0 vf 0 state auto
# ip link set enp3s0f0 vf 0 max_tx_rate 5000

# ip -d link show enp3s0f0
5: enp3s0f0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ...
    vf 0     link/ether aa:bb:cc:00:00:01, vlan 101, spoof checking on,
             link-state auto, trust off, max_tx_rate 5000Mbps

What each one does in the hardware we have already described:

It is worth remembering that all of them end here, as an ip link-equivalent call into the PF driver.

Recap

The kernel exposes the SR-IOV capability as sysfs files, and writing a number into sriov_numvfs makes the PF driver call pci_enable_sriov(), which programs the capability and enumerates the new functions with BDFs computed from offset and stride. Whether the host binds drivers to those new VFs is controlled by sriov_drivers_autoprobe, and for passthrough you usually do not want it to. The PF driver is privileged and the VF driver is not, so VFs ask for privileged operations over a mailbox and the PF driver decides. The host sets policy with ip link set <pf> vf N ... — MAC, VLAN, spoofchk, trust, link state, rate — and every one of those becomes hardware state in the embedded switch that the guest cannot override.

2. A guest wants to receive traffic for a second MAC address. Describe the full path of that request and who decides the answer.

Answer

The guest's VF driver posts a request into the mailbox, the private VF-to-PF channel (a shared region plus an interrupt; mlx5 carries it through its firmware command interface, Intel through virtchnl on an admin queue). The PF driver on the host receives the interrupt and message and checks policy: is the VF trusted, and was its MAC administratively set? If allowed, it programs the eswitch MAC filter table with the new entry for that VF and replies accepted; otherwise it replies rejected and the guest driver reports "not permitted". The PF driver decides, and behind it the host administrator, through ip link set <pf> vf N trust and mac.

Answer

With it off, the VFs appear on the bus with no driver, which is exactly the state VFIO wants.

Chapter 7

Handing the VF to a VM: VFIO, KVM, QEMU, libvirt

~11 min · layer: VIRT · Our Virtual Function exists, has a MAC the host chose, and sits on the bus with no driver attached. This is the chapter where it leaves the host and enters a virtual machine.

We have all the pieces. The VF is a PCIe function with its own BDF, its own BAR slice, its own MSI-X vectors, its own IOMMU group. What we lack is the software that takes such a device away from the kernel and lends it to a user-space program safely. That software is VFIO.

vfio-pci: a driver whose job is to give the device away

VFIO stands for Virtual Function I/O — an unfortunate name, since it long predates any relationship with SR-IOV Virtual Functions and works with any device. Think of it as "the framework for safe user-space device access".

vfio-pci is a real Linux PCI driver, and you bind it to a device the same way you bind any driver. But it does not drive the device. It exposes it: a program that opens the right file descriptors can read and write the device's config space, map its BARs into its own address space, receive its interrupts as events, and ask for DMA mappings to be installed in the IOMMU. And it can do none of that outside what the IOMMU permits.

Binding looks like this. The VF at 03:00.4 currently has mlx5_core attached, because autoprobe was on:

# echo vfio-pci > /sys/bus/pci/devices/0000:03:00.4/driver_override
# echo 0000:03:00.4 > /sys/bus/pci/drivers/mlx5_core/unbind
# echo 0000:03:00.4 > /sys/bus/pci/drivers_probe

$ lspci -k -s 03:00.4
03:00.4 Ethernet controller: Mellanox Technologies ConnectX Family mlx5Gen Virtual Function
	Kernel driver in use: vfio-pci
	Kernel modules: mlx5_core

driver_override is a sysfs file that says "no matter what the ID tables say, this device belongs to this driver". It is the tidy modern way; older guides tell you to add device IDs to vfio-pci by hand, which also affects every other device with the same ID and is best avoided.

The moment vfio-pci is bound, the host has no network interface for that VF any more. It has a device node instead.

Groups and containers, in plain terms

VFIO refuses to let you cheat on the IOMMU chapter (chapter 2). You do not open "a device". You open the VFIO group, which corresponds one-to-one with the IOMMU group, and you can only use it if every device in that group is bound to vfio-pci. If your VF shares a group with something still driven by the host, VFIO says no. This is the isolation rule from the IOMMU chapter, enforced as a permission check on a file.

Above groups sits the container: an address space. You create a container, add one or more groups to it, and then say "map this range of my process memory at this IOVA". Those calls program the IOMMU page tables. Two groups in the same container share an address space — which is what you want if one VM has two assigned devices — and groups in different containers cannot see each other's memory at all.

As of 2026, the kernel also offers iommufd, a newer and cleaner interface that replaces the container concept with explicit I/O address-space objects, and QEMU can use either. The mental model is unchanged: something groups devices, something owns an address space, and the IOMMU is programmed through it.

What QEMU does at start-up

Now the interesting part. QEMU is given the VF and must make the guest believe it has a network card. Here is what it sets up, once, before the guest runs at speed:

It builds a fake config space. The guest must see a PCI device at some address inside its own virtual PCIe topology, which has nothing to do with 03:00.4. QEMU reads the real config space through VFIO, presents most of it to the guest, and quietly intercepts the parts the guest must not really control — BAR sizing and placement, and the MSI-X table. Guest accesses to config space are emulated, and that is fine: config space is touched at boot and almost never again.

It maps the BARs. This is the crucial one. QEMU asks VFIO to mmap the VF's BAR into its own process memory, then tells KVM: "when the guest accesses this range of guest physical addresses, do not exit — the CPU's second-level page tables should point straight at these host pages." The CPU feature doing that is Intel's EPT (Extended Page Tables) or AMD's NPT (Nested Page Tables), the hardware that translates guest physical to host physical. The result is that the guest driver's write to its doorbell page is a plain store instruction that reaches the card. Nothing on the host runs.

It programs the IOMMU with the guest's memory map. For every region of guest RAM, QEMU issues a VFIO map call: IOVA equal to the guest physical address, target equal to the host memory backing it. Now the guest can put its own addresses into descriptors and the card will reach the right pages — and only those pages. This is the IOMMU translation diagram (diagram 2.1) made real.

It wires up interrupts. The guest's MSI-X table writes are intercepted, and for each vector QEMU sets up an eventfd — a simple kernel notification object — that VFIO signals when the interrupt fires. KVM can be told to consume that eventfd directly through a mechanism called irqfd and inject the interrupt into the guest's virtual CPU without QEMU waking up at all.

After all this, QEMU has almost nothing left to do. The guest boots, its PCI enumeration finds a Mellanox VF, it loads mlx5_core, and the driver has no idea it is in a VM.

libvirt: the declarative wrapper

Nobody types QEMU command lines in production. libvirt is the management layer that turns an XML description of a virtual machine into the right QEMU invocation, and it knows about VFIO. There are two ways to ask:

<!-- plain device assignment: give the guest this PCI function -->
<hostdev mode='subsystem' type='pci' managed='yes'>
  <source>
    <address domain='0x0000' bus='0x03' slot='0x00' function='0x4'/>
  </source>
</hostdev>

<!-- network-aware assignment: same thing, plus per-VF host configuration -->
<interface type='hostdev' managed='yes'>
  <source>
    <address type='pci' domain='0x0000' bus='0x03' slot='0x00' function='0x4'/>
  </source>
  <mac address='aa:bb:cc:00:00:01'/>
  <vlan><tag id='101'/></vlan>
</interface>

managed='yes' tells libvirt to do the unbinding and vfio-pci binding itself when the VM starts, and to give the device back to the host driver when it stops. The second form is the interesting one: it is a hybrid. libvirt performs the host-side configuration from the kernel chapter (chapter 6), setting the VF's MAC and VLAN through the PF, before assigning the device, then does the ordinary passthrough. That is the same policy path we already know, driven from a VM definition instead of a shell.

The KubeVirt chapter (chapter 9) will show a Kubernetes controller generating exactly this XML, from a Kubernetes object, for a VM running inside a pod.

Try it

Even without VMs: ls /dev/vfio/ after binding something to vfio-pci shows numbered files, and those numbers are IOMMU group numbers from the IOMMU chapter (chapter 2). That directory listing is the clearest possible demonstration that the group is the unit of assignment.

Recap

vfio-pci is a driver that claims a device in order to hand it safely to a user-space program, and it enforces the IOMMU group rule: you get the whole group or nothing. QEMU uses it to build a virtual machine that owns the VF — reading and faking its config space, mapping its BARs into guest physical memory through the CPU's second-level page tables so guest register writes reach hardware without an exit, programming the IOMMU so that guest physical addresses in descriptors resolve to the right host pages, and routing MSI-X interrupts through eventfd and irqfd. All of that is start-up work; the per-packet path involves no hypervisor. libvirt wraps it in XML, and <interface type='hostdev'> additionally applies the host-side VF settings from the kernel chapter (chapter 6).

Check yourself

1. Why does binding a VF to vfio-pci make its host network interface disappear, and why is that desirable?

Answer

Because a PCI device has one driver at a time, and vfio-pci does not drive the device; it exposes it. Binding it means unbinding mlx5_core, which tears down the netdev. What appears instead is a device node under /dev/vfio/, named after the IOMMU group. That is desirable because two drivers on one device would be two owners of the same rings and doorbells, and because the guest must be the only party issuing DMA for that requester ID.

Check it with lspci -k -s 03:00.4, which shows Kernel driver in use: vfio-pci, while ip link no longer lists the interface. The near miss is expecting the interface to come back while the VM runs. It returns only when libvirt, with managed='yes', rebinds the host driver at VM shutdown.

2. A guest driver writes to a doorbell. List every software component that runs as a result. Then list the ones that run when it writes to its PCI config space instead.

Answer

For the doorbell: none. The guest's store hits a guest physical address that EPT (or NPT) maps straight to the VF's BAR page, so the CPU forwards it to the card with no VM exit; QEMU, KVM and the host kernel are all idle. For config space: KVM takes the VM exit and hands it to QEMU, and QEMU's VFIO code services the access, reading the real config space through the vfio-pci file descriptor or answering from its emulated copy for the parts it fakes, BAR placement and the MSI-X table.

Check it against the slow-path versus fast-path table in this chapter, and with perf kvm stat live showing no exits during steady traffic. The near miss is listing vfio-pci as running on the doorbell path. It set up the mapping once and is not on the store's path.

3. What is the practical difference between <hostdev> and <interface type='hostdev'>, in terms of the kernel chapter's knobs?

Answer

<interface type='hostdev'> lets libvirt apply the host-side per-VF settings from the kernel chapter (chapter 6) before assigning the device: the <mac> element becomes ip link set <pf> vf N mac, and <vlan><tag id> becomes the vlan knob, both programmed through the PF driver into the eswitch. Plain <hostdev> does only the VFIO hand-over and leaves the VF with whatever MAC and VLAN the host last set. Both do the same unbinding, BAR mapping and IOMMU programming.

Check it with virsh dumpxml on a running domain, then ip -d link show <pf> for the resulting VF settings. The near miss is thinking <interface type='hostdev'> routes packets through libvirt or a bridge. It is still full passthrough; only setup differs.

Chapter 8

Kubernetes: VFs as schedulable resources

~11 min · layer: K8S · Last chapter one human bound one Virtual Function to vfio-pci and wrote one XML file. Now we have three hundred VFs on forty machines and a scheduler that must hand them out. This chapter is about turning our VF into something Kubernetes can count, allocate and plug in.

Kubernetes was built with a simple picture of a pod's network: one interface, an address from the cluster network, and a software path through the node. Nothing in that picture has a place for "this pod owns PCIe function 0000:03:00.4". Four separate pieces were added over the years to fix that, and the confusing part for newcomers is that they are four independent projects that must agree with each other. Let us take them in order.

Piece one: device plugins, so the scheduler can count VFs

Kubernetes knows about CPU and memory natively. For anything else — GPUs, FPGAs, our VFs — it has the device plugin interface. A device plugin is a small program, normally running as a DaemonSet pod on every node, that registers itself with the kubelet (the Kubernetes agent on each node) over a local socket and then does two things.

First, it reports a list of devices it manages, and keeps that list up to date. The kubelet turns that into an extended resource on the node — a countable, node-level resource with a name like openshift.io/mlx_fast and a quantity like 8. Extended resources are integers and cannot be over-committed: eight means eight, and the scheduler will place at most eight pods that each asked for one. That is exactly the semantics a VF needs.

Second, when the kubelet is about to start a container that asked for one of these, it calls the plugin's Allocate method with the device IDs it picked. The plugin answers with instructions for the container runtime: device nodes to expose, mounts, and environment variables. This is the hook through which a pod learns which VF it got.

The SR-IOV network device plugin is the implementation for our case. It scans the node's PCI devices, selects the ones matching a configured filter (by vendor and device ID, by PF name, by driver), and groups them into named pools. Each pool becomes one extended resource. For each allocated device it injects an environment variable holding the PCI addresses, named after the resource — for the resource intel.com/sriov the variable is PCIDEVICE_INTEL_COM_SRIOV=0000:03:02.1,0000:03:04.3. If the VF is bound to vfio-pci, the plugin also arranges for the right /dev/vfio device node to be present in the container, which is what makes the VFIO chapter's hand-over (chapter 7) possible inside a pod.

Piece two: Multus, so a pod can have a second interface

A device plugin gets the hardware into the pod, but it does not configure networking. And a pod normally has exactly one network interface, created by the cluster's CNI plugin (Container Network Interface — the standard by which Kubernetes asks an external program to set up a pod's networking).

Multus is a CNI meta-plugin: Kubernetes calls Multus, and Multus calls several other CNI plugins in turn. The first is the cluster's normal one, giving the pod its ordinary cluster network. The others are extras, requested per pod through an annotation. So Multus is "the thing that lets a pod have a second NIC".

Multus takes its extra-network definitions from a custom resource called a NetworkAttachmentDefinition, standardised by the Kubernetes Network Plumbing Working Group. A NetworkAttachmentDefinition is little more than a name and a blob of CNI configuration. A pod asks for one by name in the annotation k8s.v1.cni.cncf.io/networks.

Piece three: the SR-IOV CNI, which does the actual plugging in

When Multus reaches the extra network, it calls the SR-IOV CNI plugin, and passes it the PCI address the device plugin allocated. That plugin does the work we did by hand in the kernel and VFIO chapters (chapters 6 and 7), per pod:

It applies the per-VF configuration through the PF (MAC, VLAN, spoof checking, trust, rate limits) using the same kernel calls that ip link set ... vf N ... makes. Then, if the VF is a normal kernel network device, it moves that interface into the pod's network namespace (the kernel's per-pod isolated view of interfaces, routes and addresses), renames it to something like net1, and gives it an address. If instead the VF is bound to vfio-pci, there is no interface to move, and the CNI's job is limited to the hardware-level configuration, and the device itself reaches the pod through the device plugin. Remember that fork; the KubeVirt chapter (chapter 9) uses the vfio-pci branch of it.

Piece four: the operator, because doing all this by hand is miserable

Someone still has to create VFs on every node, bind them to the right driver, write the device plugin's configuration, and keep it all consistent as nodes come and go. The sriov-network-operator does that. You describe intent in custom resources and it converges the cluster.

Two resources matter. The first, SriovNetworkNodePolicy, is node-side intent: on these nodes, on these cards, create this many VFs, bind them to this driver, and advertise them under this resource name.

apiVersion: sriovnetwork.openshift.io/v1
kind: SriovNetworkNodePolicy
metadata:
  name: policy-mlx-fast
  namespace: sriov-network-operator
spec:
  nodeSelector:
    feature.node.kubernetes.io/network-sriov.capable: "true"
  resourceName: mlx_fast          # becomes openshift.io/mlx_fast
  numVfs: 8
  deviceType: vfio-pci            # the choice that matters for virtual machines
  nicSelector:
    vendor: "15b3"                # Mellanox / NVIDIA
    pfNames: ["enp3s0f0"]

The API group is sriovnetwork.openshift.io/v1 even on plain upstream Kubernetes, and the default resource prefix is openshift.io — a historical artefact of the operator's origin in OpenShift. You do not need OpenShift to use it. Both the prefix and the namespace are configurable. The standalone device plugin, used without the operator, defaults to the prefix intel.com instead. As of 2026 this is still the situation; check your operator's own documentation for the version you run.

The second, SriovNetwork, is the pod-side intent: given that pool of VFs, define a named network with these settings. The operator's reward for creating one is that it generates the matching NetworkAttachmentDefinition for you, in the namespace you name.

apiVersion: sriovnetwork.openshift.io/v1
kind: SriovNetwork
metadata:
  name: fast-net
  namespace: sriov-network-operator
spec:
  resourceName: mlx_fast
  networkNamespace: my-apps       # where the NetworkAttachmentDefinition appears
  vlan: 101
  spoofChk: "on"
  trust: "off"

Look at those last three fields and recognise them. vlan, spoofChk, trust are the knobs from the kernel chapter (chapter 6), unchanged, having travelled from a hardware filter table, through netlink (the socket-based interface through which ip link and every other tool talks to the kernel's network stack), through a CNI plugin, into a YAML file that a platform team edits. The whole stack is one long game of passing the same settings down.

Putting a pod on it

apiVersion: v1
kind: Pod
metadata:
  name: packet-mover
  annotations:
    k8s.v1.cni.cncf.io/networks: fast-net
spec:
  containers:
  - name: app
    image: registry.example.com/packet-mover:1.4
    resources:
      requests:
        openshift.io/mlx_fast: "1"
      limits:
        openshift.io/mlx_fast: "1"

The annotation and the resource request must agree — the annotation says which network, the resource says which pool of hardware. Getting one without the other is the classic failure, and it shows up as a pod stuck in ContainerCreating with a CNI error.

Try it

On any cluster with SR-IOV configured: kubectl get node <node> -o jsonpath='{.status.allocatable}' | tr ',' '\n' | grep -i -e sriov -e mlx shows the extended resources the device plugin advertised. Then kubectl describe node <node> | grep -A5 Allocated shows how many are in use. Those numbers are, quite literally, VFs on a card.

Recap

Four independent pieces cooperate. The device plugin interface lets a program advertise VFs to the kubelet as countable extended resources and inject their PCI addresses into containers at allocation time; the SR-IOV network device plugin is that program. Multus lets a pod have more than one interface, driven by NetworkAttachmentDefinition objects and a pod annotation. The SR-IOV CNI plugin applies the per-VF hardware settings and, for kernel-driver VFs, moves the interface into the pod's network namespace. The sriov-network-operator creates VFs, binds drivers and generates configuration from two custom resources, SriovNetworkNodePolicy and SriovNetwork. The deviceType: vfio-pci choice in the policy decides whether a pod receives a network interface or a raw assignable device — and the next chapter needs the second.

Check yourself

1. Which component ensures that only eight pods are scheduled onto a node with eight VFs, and how does it know the number?

Answer

The kube-scheduler, using the node's extended resource count, which the kubelet published after the SR-IOV device plugin reported its device list. The plugin scans PCI, matches VFs against its selector, and streams the list to the kubelet over the plugin socket; the kubelet then advertises openshift.io/mlx_fast: 8 in the node's allocatable resources. Extended resources are integers with no overcommit, so the scheduler subtracts one per requesting pod and stops placing at zero.

Check it with kubectl get node <node> -o jsonpath='{.status.allocatable}'. The near miss is crediting the device plugin with the decision. It counts and allocates on the node and never sees the scheduler's queue; its Allocate call runs only after placement, when the kubelet asks which specific VF to hand over.

2. A pod requests the resource but has no network annotation. What happens, and why?

Answer

The pod schedules and starts. It receives the VF's PCI address in a PCIDEVICE_... environment variable, and a /dev/vfio node if the VF is bound to vfio-pci, but no second network interface appears. The resource request drives the device plugin path only; the annotation k8s.v1.cni.cncf.io/networks is what makes Multus call the SR-IOV CNI, and without it Multus sets up the default cluster network and stops. Nothing configures the VF's MAC or VLAN through the PF, and a kernel-netdev VF stays in the host namespace.

Check it with kubectl exec <pod> -- env | grep PCIDEVICE, which shows the address, while ip link inside the pod shows only eth0. The near miss is expecting a scheduling failure. The scheduler is satisfied and the failure is silent. The reverse mistake, annotation without resource, fails loudly with a CNI error and a pod stuck in ContainerCreating.

3. Where in this chain does the equivalent of ip link set enp3s0f0 vf 0 vlan 101 actually run?

Answer

Inside the SR-IOV CNI plugin, on the node, during pod network setup. Multus calls the CNI with the PCI address the device plugin allocated and with the settings from the NetworkAttachmentDefinition, which the sriov-network-operator generated from the SriovNetwork's vlan: 101. The CNI makes the same netlink call to the kernel that ip link would, addressed to the PF's interface with the VF's index, and the PF driver programs the eswitch.

Check it with ip -d link show enp3s0f0 on the node after the pod starts; it shows vf 0 ... vlan 101. The near miss is placing the call in the operator or the device plugin. The operator only writes YAML into a NetworkAttachmentDefinition, and the device plugin only hands out addresses. The one component that touches hardware is the CNI.

Chapter 9

KubeVirt: the VM inside the pod gets the VF

~11 min · layer: KUBEVIRT · Our Virtual Function is now a countable resource that a scheduler can hand to a pod. The last step of its life: inside that pod there is a virtual machine, and the VF must end up as a network card inside it. Then we follow a packet all the way out.

KubeVirt is an add-on that lets Kubernetes run virtual machines as if they were pods. It does this in the most literal way imaginable: for each running VM it creates an ordinary pod, and inside that pod it runs libvirt and QEMU. The pod is the VM's container in the "shipping" sense — the scheduler, the resource accounting, the networking and the lifecycle are all Kubernetes', while what runs inside is a full guest operating system.

The main objects are: a VirtualMachine, which is the desired long-lived definition, and a VirtualMachineInstance (VMI), which is one running copy. The pod that hosts a VMI is called the virt-launcher pod. On every node a virt-handler DaemonSet acts as the per-node agent, roughly KubeVirt's counterpart to the kubelet.

Once you see that shape, the SR-IOV part is short: everything from the Kubernetes chapter (chapter 8) delivers a VF into the virt-launcher pod, and everything from the VFIO chapter (chapter 7) happens inside it.

Asking for it

A VMI declares interfaces and networks separately and joins them by name. For SR-IOV, the interface has an sriov: {} binding, and the network points at a NetworkAttachmentDefinition through Multus:

apiVersion: kubevirt.io/v1
kind: VirtualMachineInstance
metadata:
  name: packet-mover-vm
spec:
  domain:
    devices:
      interfaces:
      - name: default
        masquerade: {}          # ordinary cluster network, software path
      - name: fast
        sriov: {}               # our VF
    resources:
      requests:
        memory: 8Gi
  networks:
  - name: default
    pod: {}
  - name: fast
    multus:
      networkName: my-apps/fast-net

Note that no PCI address, resource name or MAC appears here. The VMI says "give me an SR-IOV interface on the network called fast-net", and the machinery resolves that into a resource request on the virt-launcher pod, which the scheduler then satisfies. Notice also that a VM usually keeps a normal cluster interface alongside — the fast path is for data, and ordinary Kubernetes traffic keeps working the boring way.

Why it must be vfio-pci

The Kubernetes chapter (chapter 8) ended on a fork: a VF can be a kernel network interface moved into the pod, or a device bound to vfio-pci. For KubeVirt's SR-IOV path it must be vfio-pci. Your SriovNetworkNodePolicy must say deviceType: vfio-pci, and if it does not, nothing will work and the error will not be obvious.

The reason is the VFIO chapter (chapter 7) in one sentence: QEMU cannot assign a device to a guest unless that device is available through VFIO, because VFIO is the only interface that can map BARs and program the IOMMU on a user-space process's behalf. A network interface in the pod's namespace is useless to QEMU — it belongs to the host kernel's network stack, which is precisely the thing we are trying to bypass. So the VF must be handed over as a raw PCI device, and the device plugin makes the corresponding /dev/vfio node available in the pod.

This is also why KubeVirt VMs with SR-IOV need the pod to be allowed to lock memory: assigning a device means the guest's entire RAM must be pinned, since the card may DMA into any of it at any moment and pages cannot be moved out from under it. That memory is real and reserved for the lifetime of the VM.

What happens between YAML and guest

The chain, once, at VM start:

KubeVirt's controller translates the VMI into a virt-launcher pod specification, adding the resource request for the right extended resource and the Multus annotation for the right network. The scheduler places that pod on a node that still has a free VF. The kubelet calls the device plugin, which allocates a specific VF — say 0000:03:00.4 — and injects its address and the VFIO device node into the pod. Multus and the SR-IOV CNI apply the MAC, VLAN and policy through the PF, as in the Kubernetes chapter.

Then virt-handler and virt-launcher take over. They read which PCI addresses were allocated, and generate a libvirt domain XML containing a <hostdev> element pointing at that device — the same XML we wrote by hand in the VFIO chapter (chapter 7). libvirt starts QEMU. QEMU opens the VFIO group, maps the VF's BAR into the guest, programs the IOMMU with the guest's memory map, and wires the MSI-X vectors.

Inside the guest, a PCI device appears at some guest-side address such as 00:07.0. The guest kernel reads its Vendor and Device IDs, matches mlx5_core (or iavf on an Intel card), loads it, and creates eth1. That driver is doing exactly what the NIC internals chapter (chapter 4) described: allocating rings, posting descriptors, ringing doorbells. It cannot tell that it is inside a VM, inside a pod, on a node, in a cluster.

The packet walk

Here is the moment the dossier has been building to. A program in the guest calls send(). Follow the bytes.

Now the list that is the whole point of this dossier. Here is what that packet did not touch:

It did not cause a VM exit. It did not enter QEMU. It bypassed the host kernel entirely: the network stack, any bridge, Open vSwitch, virtual ethernet pairs and the firewall layer all saw nothing. The only entity that read the bytes was the network card itself. It did not consume a single cycle on any host CPU core. The host's only contribution was made minutes earlier, when it wrote some page tables.

And yet the guest is still contained. It cannot DMA outside its own memory, because of the IOMMU page tables from the IOMMU chapter (chapter 2). It cannot forge a source MAC, because of the anti-spoofing check from the NIC internals chapter (chapter 4). It cannot leave its VLAN, because the eswitch inserts the tag set in the kernel chapter (chapter 6). It cannot exceed its rate limit, cannot reconfigure the port, cannot see the other VFs' traffic. Every one of those walls is silicon, and none of them costs a cycle.

That is SR-IOV. One capability structure in a config space, and an entire stack arranged around the consequences.

Try it

Inside a running KubeVirt guest with an SR-IOV interface: lspci -k shows the assigned VF with its guest-side BDF and the driver bound to it, and ethtool -i eth1 confirms mlx5_core. On the host, ls -l /proc/$(pgrep -f qemu | head -1)/fd | grep vfio shows the very file descriptors the VFIO chapter (chapter 7) described. Two commands, two ends of the same device.

Recap

KubeVirt runs each VM inside an ordinary pod called virt-launcher, with libvirt and QEMU inside it, so the entire Kubernetes chain from the Kubernetes chapter (chapter 8) delivers the VF into that pod and the entire virtualization chain from the VFIO chapter (chapter 7) happens within it. A VMI asks for an SR-IOV interface with sriov: {} plus a Multus network, and the machinery resolves that into an extended resource request; the VFs must be bound to vfio-pci, because only VFIO can give a device to QEMU. virt-handler writes the domain XML with a hostdev, QEMU maps and programs, and the guest loads the ordinary vendor driver. From then on packets travel from the guest's doorbell write, through the card's own DMA and embedded switch, to the wire, with nothing on the host on the path, while still being fenced in by the IOMMU and the eswitch's policy checks.

Check yourself

1. Why must the SriovNetworkNodePolicy say deviceType: vfio-pci for KubeVirt, when a plain container pod is often happier with a kernel netdev?

Answer

Because QEMU can only assign a device it can reach through VFIO, and VFIO requires the device to be bound to vfio-pci. QEMU maps the VF's BAR into the guest and programs the IOMMU through the VFIO file descriptors; a netdev in the pod's namespace belongs to the host kernel's network stack and offers neither. A container pod wants to send packets from ordinary sockets, and for that a kernel netdev moved into its namespace is exactly right.

Check it by getting it wrong: with a kernel-netdev policy, the virt-launcher pod starts but libvirt cannot find /dev/vfio/<group>, and the VMI never reaches Running. The near miss is thinking KubeVirt could bridge the netdev into the VM. That would put the host network stack back on the data path, which is the thing SR-IOV exists to remove.

2. Name every software component that runs while the guest transmits one packet. Then name five that do not.

Answer

Running: the application and the mlx5_core driver inside the guest, and nothing else. The doorbell store goes through EPT to the VF's BAR and the card does the rest in silicon. Not running: QEMU, KVM, the host kernel's network stack, Open vSwitch or any software bridge, the SR-IOV CNI, Multus, the kubelet, libvirt, virt-handler. Any five of those.

Check it against the packet walk (diagram 9.2), which has no column for any of them, and on the host with ls -l /proc/$(pgrep -f qemu | head -1)/fd | grep vfio, the descriptors that were used once at setup. The near miss is listing the IOMMU or the eswitch as software. They are on the path and they do work, but they are hardware; that is the point.

3. The guest is root and tries to change its MAC address, disable its VLAN tag and read another VM's memory. Which mechanism stops each attempt?

Answer

The MAC change is refused by the PF driver over the mailbox, because the MAC was administratively set through the SR-IOV CNI, and any frame sent with a forged source MAC is dropped by the eswitch's anti-spoofing check. The VLAN cannot be disabled because the eswitch inserts and strips the tag under the PF's per-VF setting; the guest sees untagged traffic and cannot reach the tagging logic. Reading another VM's memory fails in the IOMMU: the VF's requester ID selects page tables that map only this guest's RAM, so a DMA anywhere else has no translation and is blocked and logged.

Check it with ip -d link show <pf> for the VF's MAC, VLAN and spoof-checking state, and dmesg on the host for DMAR fault messages. The near miss is crediting QEMU with any of these. It is not on the path; all three walls are hardware.

Chapter 10 · Epilogue

Traps that remain, and where the industry went next

~11 min · layers: HW KERNEL VIRT K8S KUBEVIRT · Our Virtual Function has completed its life: created from a capability structure, leashed by the IOMMU, handed to QEMU, counted by a scheduler, and now moving packets for a guest. Time to be honest about what it costs you.

SR-IOV is not a free upgrade. It is a trade, and the things you give up are exactly the things that software indirection was providing. Here they are, in the order you usually meet them.

Live migration becomes hard

Live migration — moving a running VM from one host to another without stopping it — is the feature that makes virtualized infrastructure pleasant to operate. You can drain a node for maintenance. Schedulers can rebalance. With a passed-through device, all of that becomes difficult.

The problem is state. When you migrate, you copy the guest's memory and CPU state to the new host. But part of your guest's state is now inside the network card: queue positions, in-flight descriptors, filter table entries, hardware counters. The hypervisor cannot read that state, because it deliberately arranged not to be involved. And the destination host has a different card with different addresses.

The workarounds are all unpleasant in some way. You can hot-unplug the VF before migrating and hot-plug a new one after, usually with a bonded virtio-net interface in the guest carrying traffic across the gap — this works, but requires guest cooperation and loses the fast path during the move. Newer efforts add device-specific migration drivers in the kernel, which let a compatible card save and restore its own VF state; support is real but narrow, and depends on the exact card and driver as of 2026. As things stand, treat "VMs with SR-IOV do not migrate easily" as the planning assumption, and check your specific hardware if you need better.

In Kubernetes this shows up bluntly. As of 2026, KubeVirt cannot hot-plug an SR-IOV interface into a running VM in the ordinary way, because the device plugin interface has no way to allocate an extra device to an already-running pod; the supported route is migration-based.

VFs are static, and there are never enough

The number of VFs is decided long before any workload arrives: partly in the card's firmware settings, partly by a write to sriov_numvfs that destroys every existing VF if you change it. You cannot grow the pool under load. So capacity planning is real work, and mistakes are disruptive.

The counts are also modest relative to container density. A card offering 64 or 128 VFs sounds generous until you compare it with the number of pods a modern node runs. SR-IOV is a tool for the small number of demanding workloads on a node. Ordinary pods should stay on the software path.

NUMA locality suddenly matters

Big servers are NUMA machines — Non-Uniform Memory Access, meaning the machine is built from several nodes, each with its own CPU cores and its own memory, and reaching another node's memory is slower. A PCIe card is physically attached to one of those nodes.

When your data path went through the host kernel, this was somebody else's problem. Now the card writes directly into your guest's memory. If the guest's memory and CPUs are on NUMA node 1 and the card hangs off node 0, every packet crosses the interconnect, and you can lose a large fraction of the performance you bought the card for. The fix is to make the scheduler place the VM's CPUs and memory on the same node as the card — in Kubernetes, that means the kubelet's topology manager with a suitable policy, plus CPU and memory management policies to match. This is real configuration work, and skipping it is the most common reason an SR-IOV deployment underperforms.

Security: better than you fear, worse than you hope

The good news is genuine: the IOMMU contains DMA, interrupt remapping contains interrupts, anti-spoofing contains identity, and VLAN enforcement contains reach. A guest with full root cannot escape those.

The caveats are worth stating plainly.

Trust mode gives away much of it. Setting trust on for a VF lets the guest enable promiscuous mode and change its own MAC. On a shared card this means a guest can potentially see traffic it should not. Treat it like giving a container CAP_NET_ADMIN on the host: sometimes necessary, never casual.

Spoof checking must actually be on. It is a per-VF setting, off in some paths by default, and it silently does nothing if you never set it. Check it, do not assume it.

The card is shared silicon. A guest driving a VF is exercising the same firmware and the same hardware queues as its neighbours. Denial of service through resource exhaustion, and firmware bugs reachable from a VF, are real categories of problem. Rate limiting helps with the first. Keeping firmware current helps with the second.

The guest sees real hardware. That is the point, but it also means your guests learn your hardware inventory, and driver bugs in guests can wedge a device in ways that need a PF-side reset.

Where the industry went: vDPA

Look back at the three-ways diagram (diagram 0.1). virtio-net was flexible but had the host CPU in the data path. SR-IOV removed the host CPU but pinned the guest to a specific vendor's device, which is what broke migration. vDPA — virtio Data Path Acceleration — is the attempt to get both.

The idea: build hardware whose data path speaks the virtio ring format natively, then pass that data path through to the guest while keeping the control path in the host. The guest loads a plain virtio-net driver, with no vendor driver or vendor device ID, and its descriptor rings are consumed directly by the card. Because the guest only ever sees a standard virtio device, the host is free to swap what is behind it: a different vendor's card, or even a software implementation, which restores live migration. Linux gained a vDPA framework in 2020, and mlx5 implements it, which is what the mlx5_vdpa module in the ConnectX chapter (chapter 5) was for. The cost is that the card must implement virtio's ring format in hardware, and that the control path is more complex than either alternative.

Where the industry went: Scalable IOV

The other complaint about SR-IOV is the one from earlier in this chapter: VFs are heavy, few, and static, because each one is a real PCIe function with real config space and a real slice of BAR space. Scalable IOV (Intel's specification, often written SIOV) attacks that directly.

Instead of minting PCIe functions, an SIOV device exposes many lightweight Assignable Interfaces — essentially just sets of queues and doorbell pages, with no config space of their own. Config space, when a guest needs it, is emulated in host software by a component the specification calls the Virtual Device Composition Module. Isolation still comes from the IOMMU, using a finer identifier than the requester ID alone — the device tags transactions with a process address space identifier, so many interfaces behind one function can have separate translations. The result is thousands of assignable pieces instead of dozens, created and destroyed dynamically, at the price of a little host software on the control path. The mlx5 subfunction feature mentioned in the ConnectX chapter (chapter 5) is a closely related idea, exposed through devlink ports.

Recap

SR-IOV trades flexibility for speed. Live migration becomes hard because guest state now lives partly inside the card, and in KubeVirt this shows up as SR-IOV interfaces not being hot-pluggable in the ordinary way. VF counts are fixed in advance and modest, so capacity planning matters. NUMA locality becomes your problem, because the card writes into guest memory directly. The security model is strong — IOMMU, interrupt remapping, anti-spoofing, VLAN enforcement — but trust mode gives much of it away and spoof checking must be explicitly on. vDPA keeps the hardware data path while showing the guest a standard virtio device, restoring portability and migration; Scalable IOV replaces heavyweight PCIe functions with many light assignable interfaces plus a little host software. Both exist because of the limits in this chapter, and neither has displaced SR-IOV.

Check yourself

1. Why is live migration hard for a VM with an assigned VF, in terms of where state lives?

Answer

Because part of the guest's state is inside the network card: queue positions, in-flight descriptors, filter table entries, counters. The hypervisor cannot read it, because it deliberately arranged to be off the path. Migration copies memory and CPU state; device state has to be extracted by something that understands the device, and the destination has a different card with different addresses.

Check it in the KubeVirt hotplug documentation, and in the kernel's vfio-pci variant drivers such as mlx5_vfio_pci, which exist precisely to save and restore VF state. The near miss is blaming the IOMMU mappings. Those are host-side and can be rebuilt on the destination. The hard part is the state the device holds internally and the guest driver's assumptions about it.

2. Your SR-IOV VM performs at half the expected rate and the host is otherwise idle. What is the first thing to check, and why did this problem not exist with a software data path?

Answer

NUMA placement: whether the VM's CPUs and memory sit on the same NUMA node as the card. The card now DMAs straight into guest memory, so if the guest lives on node 1 and the card hangs off node 0, every packet crosses the inter-socket interconnect. With a software path, the host kernel's threads did the copying and their placement was the host's problem, so the guest never noticed.

Check it by comparing cat /sys/bus/pci/devices/<VF>/numa_node with numactl -H for the VM's pinned CPUs; in Kubernetes, look at the kubelet's topology manager policy. The near miss is reaching for rate limits or spoofchk. Those cost nothing per packet. A steady half rate with an idle host is the signature of memory crossing the interconnect.

3. What does vDPA keep from SR-IOV, and what does it keep from virtio-net?

Answer

From SR-IOV it keeps the hardware data path: the card consumes the guest's descriptor rings directly by DMA, with no host CPU per packet. From virtio-net it keeps the guest-facing device model: the guest loads the standard virtio-net driver and sees a standard virtio device, so it does not depend on the vendor, and the host can swap what stands behind the device, which is what restores live migration. The new requirement is a card whose data path speaks virtio's ring format natively, plus a host-side control path (the vDPA framework and mlx5_vdpa) that turns virtio control operations into vendor commands.

Check it against the design-space diagram (diagram 10.1). The near miss is thinking vDPA removes the vendor driver from the host. It moves the vendor driver to the host's control path and removes it from the guest.
