Chapter 0 · Prologue

One GPU, many tenants

~10 min · HW — Where we are: nowhere yet. Two tenants want one very expensive GPU. In this chapter we pick the single kernel launch we will follow for the rest of the document, and we meet the four families of tricks that let strangers share the machine.

An H100 costs as much as a nice car. Most of the time, in most clusters, it sits mostly idle. An inference service that answers a request every few hundred milliseconds might keep the chip busy 15% of the time. The other 85% is money evaporating. So the obvious question: can a second workload use the gaps?

On a CPU, this question was answered fifty years ago and nobody thinks about it anymore. The operating system interrupts whatever is running a hundred times a second, saves its registers, and hands the core to someone else. Memory is virtual, paged, and swappable. Two processes share a CPU so completely that neither can tell the other exists.

On a GPU, none of that machinery comes for free. This whole document is about what NVIDIA built instead, layer by layer, and what each option costs you in isolation, performance, and operational pain.

The object we follow

First, one word with two meanings, and we have to defuse it now. In GPU programming, a kernel is a function that runs on the GPU — one function, launched once, executed by thousands of threads in parallel. It has nothing to do with the Linux kernel. In this document, "kernel" or "the launch" always means the GPU function; the operating system is always "the host kernel".

We follow one kernel launch. Tenant A runs an inference service inside a container; somewhere in its code, a library calls into CUDA (Compute Unified Device Architecture, NVIDIA's programming model and software stack) and asks it to launch a kernel that multiplies two matrices. Tenant B, a stranger, wants the same physical GPU at the same time. Every chapter that follows watches this one launch travel a little further: into the driver, through the firmware, onto the silicon — and watches what stands between it and Tenant B at each layer.

Two more words we need before anything else. The GPU's compute power lives in an array of identical units called SMs — streaming multiprocessors. An SM is the closest thing a GPU has to a CPU core: it has schedulers, arithmetic units, registers, and a chunk of fast local memory. An A100 has 108 of them. And the GPU carries its own on-board memory, VRAM — tens of gigabytes soldered next to the die, separate from system RAM. Kernels read and write VRAM; getting data into VRAM from the host is a separate, explicit step.

Why a GPU does not share like a CPU

Three concrete reasons, and they shape everything downstream.

One: the state is enormous. When the host kernel preempts a CPU process, it saves a few hundred bytes of registers. A running GPU kernel has state spread across 108 SMs — registers for tens of thousands of threads, local memory, in-flight cache lines. Stopping it mid-flight and swapping in someone else is possible on modern chips, but it is a heavyweight event that happens at millisecond scale. The time-slicing chapter (chapter 4) measures this.

Two: VRAM does not swap. There is no page-out path to disk that anyone would tolerate. If Tenant A allocates 35 GB of a 40 GB card, Tenant B gets 5 GB and no negotiation. Whoever controls sharing must decide, up front, who gets how much physical memory — or lie to the tenants about it, and we will see both approaches.

Three: the GPU trusts its input. A process talks to the GPU through a per-process bundle of GPU-side state called a context. Think of it as the GPU's version of an OS process; the launch-path chapter (chapter 2) makes this precise. Within a context, the hardware executes what it is given at full speed. Fine-grained supervision of the kind an OS does (checking, metering, intervening) would destroy exactly the throughput people buy GPUs for. So isolation has to be built in coarser, cheaper ways: walls in the silicon, walls in the driver, or a chaperone in the software stack.

This is the tension behind the whole field: utilization pulls you toward packing tenants tightly onto one chip; isolation pulls you toward giving each tenant its own walls — and every wall wastes some silicon. Each technique in this document is one point on that trade-off line.

Four families of sharing

Everything you will meet — and every product name you have seen on this topic — belongs to one of four families.

Take turns. The GPU runs Tenant A's work, then Tenant B's, alternating. Nobody is walled off; the hardware just switches between contexts. This is time-slicing, the GPU's default behaviour, and the time-slicing chapter (chapter 4) shows it is both older and stranger than you expect. A cooperative variant, MPS (Multi-Process Service), lets multiple processes run simultaneously on the SMs by funnelling them through one shared context; that is the MPS chapter (chapter 5).

Split the silicon. Draw a wall through the chip: these SMs and this slice of VRAM are yours, those are mine, and the two halves run at the same time without touching. This is MIG (Multi-Instance GPU), a hardware feature of A100 and newer, and it is the MIG chapter (chapter 6).

Fake whole GPUs. Give each virtual machine what looks like a complete GPU — its own device, its own driver inside the guest — while the host multiplexes them onto one physical chip. This is vGPU, NVIDIA's GPU virtualization product, and if you are coming from the SR-IOV dossier you will recognise the shape of the vGPU chapter (chapter 7) immediately.

Police the library calls. Change nothing in the hardware or driver. Instead, slip an interception layer between the tenant's code and CUDA, and have it enforce made-up limits: refuse allocations past a memory quota, slow a tenant that used too much compute. This is what HAMi, an open-source Kubernetes middleware, does, and the HAMi chapter (chapter 9) dissects how a pure software trick can impersonate a hardware feature.

One honest warning before we start descending. These families compose (you can run vGPU on top of MIG, or time-slicing inside a MIG slice), and the marketing names do not tell you which layer does what. Untangling exactly that is one of this document's jobs, and by the vGPU chapter (chapter 7) you will have a single diagram that settles it.

What this document skips, deliberately: graphics, display, and video workloads (we are compute-only); multi-GPU topics (NVLink, NVSwitch, tensor parallelism), which are about combining GPUs, a different problem; AMD and Intel GPUs; and the economics of buying versus renting. All real, all out of scope.

Recap

A GPU cannot be shared the way a CPU is: its execution state is too big to swap cheaply, its VRAM does not page, and per-instruction supervision would destroy throughput. Every sharing scheme is one of four families, take turns (time-slicing, MPS), split the silicon (MIG), fake whole GPUs (vGPU), or police the library calls (HAMi), each trading isolation against utilization differently. We will follow one kernel launch from Tenant A's container down to the silicon, and watch what separates it from Tenant B at every layer.

1. For each of the four families: does Tenant A ever physically hold the whole GPU, and does Tenant A ever see anything other than a whole GPU?

Answer

2. Your workload allocates 35 GB on a 40 GB card and your neighbour needs 20 GB. Which of the three "why GPUs don't share like CPUs" reasons applies here, and which families can even express a rule about it?

Answer

The second reason: VRAM does not swap. There is no page-out path, so once 35 GB is allocated the remaining 5 GB is all the neighbour can get, and its 20 GB request fails with an out-of-memory error. Only families that decide memory up front can express a rule. Split the silicon (MIG) makes it a hard hardware limit per instance. Fake whole GPUs (vGPU) fixes VRAM per profile. Chapter 1

The silicon: what there is to slice

~11 min · HW — Last chapter we chose the object we follow: one kernel launch, headed for the GPU. Before we can follow it, we need a map of the machine it is about to enter, because every sharing technique later is a different way of carving up exactly the units named here.

This chapter is a guided tour of a data-center GPU die, using the A100 as the reference model and noting where the H100 differs. We stay functional: what each unit does and how many there are. No transistor counts, no clock domains, no electrical anything. The reason for the tour is blunt: MIG, in the MIG chapter (chapter 6), is a list of which of these units each tenant gets, and it makes no sense until you can name them.

The compute hierarchy

The SMs from the prologue come in a strict hierarchy of identical, repeated blocks. From the top: the die contains 8 GPCs, graphics processing clusters, the largest repeated block, each effectively a small self-contained GPU. Each GPC contains up to 8 TPCs, texture processing clusters, and each TPC contains 2 SMs. Full GA100 silicon would give 8 × 8 × 2 = 128 SMs; the A100 you can buy ships with 108 enabled (chip yields are never perfect, so some blocks are fused off). The H100 SXM ships with 132.

Inside an SM are the execution resources: thousands of registers, schedulers, a slab of fast local memory, 64 CUDA cores (the plain arithmetic units, working in FP32, the 32-bit floating-point format that is the everyday precision of GPU arithmetic) and 4 tensor cores, wide matrix-multiply units that do the heavy lifting for machine learning. The SM executes threads in fixed bundles of 32 called warps: 32 threads marching through the same instruction together. When our kernel launches with, say, a million threads, the hardware chops them into thread blocks, fixed-size groups of threads, sized by the programmer, that the hardware places on one SM as a unit. It hands blocks to SMs, and each SM runs its blocks warp by warp.

One unit sits above all the GPCs: the work distributor (NVIDIA's manuals call it the GigaThread Engine), the dispatcher that takes an incoming kernel launch and deals its thread blocks out to SMs with free capacity. Remember it — it is a chokepoint every sharing scheme has to reckon with, because all compute work enters through it.

The memory system

VRAM on these cards is HBM — high-bandwidth memory — DRAM dies stacked vertically and placed on the same package as the GPU, millimetres from the die. An A100 carries 40 or 80 GB of it in five or six stacks; H100 moves to faster HBM3. The reward for the exotic packaging is bandwidth: about 2 TB/s on A100, roughly twenty times a server CPU's memory bandwidth.

Between the SMs and the HBM sit two things. First, a 40 MB L2 cache (50 MB on H100), and the detail that matters for us is that it is physically built as independent slices, each slice caching one region of VRAM. Second, the memory controllers, each driving one portion of the HBM. A wide crossbar, an any-to-any on-die switch, connects every SM to every L2 slice. So one byte travelling from an SM to VRAM crosses: SM → crossbar → L2 slice → memory controller → HBM stack.

Now the observation this chapter exists for. Compute comes in 8 repeated blocks (GPCs). The L2 comes in slices. The HBM hangs off independent controllers. For MIG's purposes, the memory system divides into 8 equal memory slices: one eighth of the VRAM plus the L2 slices and controller bandwidth that serve it. Nothing on this die is one monolithic lump; it is all countable, repeated units, and a wall between tenants only needs to decide which units fall on which side. That is a consequence of how you must build anything this big, and it is the entire hardware basis of the MIG chapter (chapter 6).

The other engines

SMs are not the only things that do work. The die carries a set of independent engines that run alongside compute. The ones that matter here: copy engines — DMA engines that move data between host RAM and VRAM (and between GPUs) while the SMs keep computing; and NVDEC units — fixed-function video decoders, plus JPEG decoders and an optical-flow unit, which matter to anyone feeding video into a model. If "DMA engine" rings an SR-IOV bell: same idea as a NIC's DMA, a device-side unit that reads and writes host memory across PCIe without the CPU touching a byte.

Counts again, because they will matter: the A100 has 5 NVDEC decoders; the H100 has 7. Seven is also the maximum number of MIG tenants, and the H100 count was chosen so that every tenant can get a decoder of its own, which the A100 could not offer.

The way in

Everything above is inside the chip. The way in is the host interface: the GPU's PCIe endpoint logic. From the SR-IOV dossier you already know what lives here — configuration space and BARs. The GPU exposes its control registers through BAR0, and something we did not see on NICs: a large BAR1 aperture, a PCIe window through which the host can read and write VRAM directly. The host interface also contains the machinery that fetches and dispatches commands from host memory — how exactly a kernel launch gets from a process's memory through this interface and onto the work distributor is the whole of the launch-path chapter (chapter 2).

Your laptop GPU has the same anatomy at smaller scale. nvidia-smi --query-gpu=name,memory.total,clocks.sm --format=csv shows the card and its VRAM. For the SM count, build deviceQuery from the CUDA samples (github.com/NVIDIA/cuda-samples) and look for "Multiprocessors" — a laptop RTX 4060 reports 24 SMs to an A100's 108. Same hierarchy, same warp size of 32; only the counts change.

Recap

A data-center GPU is a hierarchy of repeated units: 8 GPCs holding TPCs holding SMs (108 on A100), fed by a work distributor that deals thread blocks to free SMs. Memory is stacked HBM behind memory controllers and a sliced L2, reachable from any SM through a crossbar; for partitioning purposes it divides into 8 equal memory slices. Independent copy engines and video decoders work alongside compute. The host reaches all of it through the PCIe host interface via BAR0 registers and the BAR1 VRAM aperture. Everything is countable — which is precisely what makes hardware partitioning possible.

Check yourself

1. Trace one byte from an SM to VRAM: name the four things it crosses, in order.

Answer

Crossbar, L2 slice, memory controller, HBM stack. The SM issues the access into the crossbar, the any-to-any on-die switch, which routes it to the L2 slice responsible for that address range. On a miss the slice forwards to the memory controller that drives the portion of HBM holding the address, and the controller reads or writes the stacked DRAM.

Check it against the die map (diagram 1.1), where the arrows run GPC to crossbar to L2 to memory controllers to HBM. The near miss is putting the work distributor on the path. It dispatches thread blocks to SMs before any of this and never sees a data access. A second near miss is letting each SM talk to "its" L2; every SM can reach every slice, which is why the crossbar exists.

2. The H100 has 7 NVDECs and the A100 has 5. Predict why 7, and predict which tenants on an A100 must go without one.

Answer

Seven is the maximum number of MIG instances per GPU, so with 7 decoders every instance can own one. On an A100 with 5 decoders and seven 1g.5gb instances, two instances get no decoder, and any workload that decodes video on those two must fall back to the CPU or fail. Which two depends on the placement the firmware chooses, so treat it as "at most five of seven".

Check it in the MIG User Guide's per-profile tables, which list the engine counts each profile receives on A100 and on H100. The near miss is assuming decoders are shared across instances under MIG. They are engines, and a GPU instance's engines are private to it; that is what makes the count matter.

3. Which single unit does every kernel launch pass through before any SM sees work, and why does that make it interesting for the time-slicing chapter's kind of sharing?

Answer

The work distributor, NVIDIA's GigaThread Engine. Every launch, whatever context it came from, arrives there as a grid of thread blocks to be dealt out to SMs with free capacity. It matters for time-slicing because the granting of engine time happens just upstream of it: the runlist scheduler decides whose commands reach the work distributor, and while one TSG holds its turn the distributor deals only that tenant's blocks. It is also why MIG must give each instance its own work distributor, or two instances could not launch in the same instant.

Check it against the die map (diagram 1.1), where the work distributor is the only box between the host interface and the GPCs. The near miss is naming the host interface. It carries commands in, but which SMs run which blocks is the distributor's decision.

Chapter 2

How a launch reaches the silicon

~10 min · CUDA KERNEL — Last chapter gave us the map of the die. Now our kernel launch finally moves: from a line of Python in Tenant A's container, through two libraries and one device file, to the work distributor. Watch closely where the host kernel appears on this path — and where it disappears.

Everything in this chapter happens on one machine, inside one process, with no sharing in sight. That is deliberate. You cannot understand how five different technologies interpose on the launch path until you have seen the undisturbed path once. This chapter is the "before" picture.

Two libraries and a device file

Tenant A's code calls a framework, the framework calls CUDA. That call arrives in the CUDA runtime, libcudart, the convenient high-level library that most applications link. The runtime is a wrapper; the real work happens one layer down in the CUDA driver API, libcuda.so, a proprietary library that ships with the driver; applications never bundle it. Its functions have a cu prefix, and the one we care about is cuLaunchKernel: it takes a function handle, a grid of thread blocks, and an argument buffer. Every kernel launch on every NVIDIA GPU, whatever the framework, funnels through this one narrow API. Hold that thought: a chokepoint that every process must pass through in its own address space is exactly where the HAMi chapter's technology (chapter 9) will choose to stand.

Below libcuda, the operating system. The driver exposes the GPU as device files: /dev/nvidiactl (the control node), /dev/nvidia0 (the first GPU), and /dev/nvidia-uvm (memory management, more on it below). libcuda opens these and speaks to the kernel driver through ioctls — the catch-all "do something" system call on a device file. Through those ioctls it builds, once at startup, everything the process needs. Then it mostly stops calling the kernel. That "mostly" is the punchline of this chapter.

The context: a process, GPU-side

The prologue (chapter 0) promised a precise definition of the context. Here it is: a context is the GPU-side mirror of an OS process, created through those setup ioctls, made of three things.

First, an address space. The GPU has its own MMU, the GMMU, with its own page tables living in VRAM. Each context gets its own page tables, hence its own private GPU virtual address space — pointer 0x7f0 in Tenant A's context and the same pointer in Tenant B's context resolve to different physical VRAM, exactly like two host processes and the host MMU. This is the memory-isolation floor for everything in this document: even the crudest sharing scheme inherits it. When a kernel dereferences a bad pointer, the GMMU faults it — the GPU equivalent of a segfault.

Second, channels — next section. Third, a bag of bookkeeping state on the die and in the driver: engine state, fault buffers, settings.

There is a second memory system worth naming now: UVM — unified virtual memory, served by /dev/nvidia-uvm. It lets a process allocate "managed" memory that both CPU and GPU can touch; pages migrate to whichever side faults on them. It is optional and most inference workloads skip it, but it will make two cameo appearances later: squeezing more into VRAM than it physically holds, and one of the calls HAMi must intercept.

Channels, pushbuffers, doorbells

Now, how does cuLaunchKernel actually tell the GPU anything? If you are guessing "an ioctl per launch", that is the wrong answer, and the right one should feel familiar from the SR-IOV dossier.

Work reaches the GPU through a channel: a command queue in memory that the GPU's host interface reads. The commands sitting in that queue are called the pushbuffer: a stream of instructions like "set up this kernel, this grid, these arguments, go". During setup, the driver maps the channel's ring and its control registers directly into the process's address space, through the BARs. To submit work, libcuda writes pushbuffer commands into the ring with plain memory writes, then performs one MMIO write to a special register to say "there is new work". NVIDIA calls that register a doorbell, literally, in their own hardware documentation.

You have seen this machine before. A NIC's transmit path is a descriptor ring in memory plus a doorbell register; the driver writes descriptors, rings the doorbell, and the NIC's DMA engine fetches. Swap "descriptor" for "pushbuffer command" and it is the same design, for the same reason: per-operation system calls are too slow, so the kernel sets up a shared-memory mailbox once and gets out of the way. After setup, a kernel launch involves zero system calls. Run strace on a busy CUDA process and you will see it: a storm of ioctls at startup, then near-silence while the GPU runs flat out.

Let us say the absence list out loud, because it is the most consequential paragraph in this chapter. On the per-launch path, the only things that run are user-space memory writes and hardware. The host kernel, the driver and the CPU-side scheduler are all absent, and nobody with root privileges inspects a launch on its way to the silicon. Whatever polices tenants must therefore live somewhere else: inside the process as a library (the HAMi chapter, chapter 9), inside the hardware's own scheduler (the time-slicing and MIG chapters, chapters 4 and 6), or underneath the whole VM (the vGPU chapter, chapter 7). The host kernel had its chance at setup time, and setup time only.

Who runs next: TSGs and the runlist

One GPU, many contexts, each with channels demanding work. Something on the die must pick whose channel gets executed. Two structures do it. A context's channels are grouped into a TSG, a time-slice group: channels that share one scheduling turn (they belong to the same context, so there is nothing to protect between them). And the hardware keeps a runlist: the ordered list of TSGs the GPU's runlist scheduler, part of the host interface, walks through, giving each TSG its turn on the engines. The driver writes the runlist at setup; the hardware walks it at runtime, alone.

When the runlist scheduler grants a TSG its turn, that TSG's pushbuffer commands flow to the work distributor from the silicon chapter (chapter 1), which deals thread blocks to SMs. And with that, our launch has arrived: Python call → runtime → cuLaunchKernel → pushbuffer write → doorbell → runlist turn → work distributor → 108 SMs lighting up.

The counter shows hundreds of ioctls — nearly all from startup — while a thousand matrix multiplies add almost none. Then look at ls -l /dev/nvidia* to see the device files this chapter named.

Recap

A launch goes framework → CUDA runtime → CUDA driver API (cuLaunchKernel). The host kernel sees setup and nothing else, so tenant policing must live in the process, in the hardware, or under the VM.

2. Why can't the host kernel enforce a per-tenant compute quota by inspecting launches? What fact about the runtime path makes that structurally impossible?

Answer

Because a launch never enters the host kernel. No. The GMMU, the GPU's own memory management unit, translates every access through per-context page tables in VRAM, and Tenant B's context has mappings only for Tenant B's allocations. Chapter 3

The driver and the firmware: who is in charge

~9 min · KERNEL FW — Our launch crossed the host kernel exactly once, at setup. This chapter opens the box it crossed: the driver modules, the resource manager inside them, and the surprise that most of "the driver" no longer runs on the CPU at all.

Every sharing technology from the time-slicing chapter (chapter 4) onward is configured, enforced, or mediated by the software in this chapter. Time-slicing policy? Set here. MIG partitions? Created here. vGPU? Is, to a first approximation, a licensed extension of here. So before any of that, we need to know who "here" is.

Three kernel modules and one big brain

Run lsmod | grep nvidia on a GPU box and you will see the cast: nvidia.ko, the main driver; nvidia-uvm.ko, which implements UVM behind /dev/nvidia-uvm; and nvidia-modeset.ko plus nvidia-drm.ko for display — irrelevant on a server, ignored from here on.

Inside nvidia.ko is the core of the driver: the Resource Manager, RM for short, NVIDIA's name for the logic that owns the GPU. RM is an object system: contexts, channels, memory allocations and engines are all objects with handles, created and wired together by those setup ioctls from the launch-path chapter (chapter 2). When libcuda asked for a context, it was RM that allocated the GMMU page tables, carved out the channel, registered the TSG on the runlist. RM is also where the vocabulary of that chapter stops being per-process and becomes global: RM sees all contexts, all channels, all of VRAM.

Historically RM was infamous for its size — a million-plus lines of closed code in the kernel. Keep that thought; it explains what happened next.

GSP: the driver moves onto the GPU

The silicon chapter's die tour skipped one unit, on purpose. Modern NVIDIA GPUs, Turing generation (2018) and everything after, carry a GSP, a GPU System Processor: a RISC-V CPU core embedded on the GPU die itself. And since the Turing generation, NVIDIA's answer to "where should RM run?" has been: on the GPU's own core.

At boot, the kernel driver loads a firmware blob (find it at /lib/firmware/nvidia/<version>/gsp*.bin, tens of megabytes) onto the GSP. That firmware is GSP-RM: most of the Resource Manager, compiled for RISC-V, running on the GPU. What remains on the host is a thin client. When libcuda issues a setup ioctl, the host-side driver mostly packages it into an RPC message, posts it to a shared-memory queue, and waits for GSP-RM to do the real work — build the page tables, program the runlist — and reply. NVIDIA's driver documentation states the default plainly: "The GSP firmware will be used by default for all Turing and later GPUs" (toggle: the module parameter NVreg_EnableGpuFirmware).

Why move it? Two reasons, one boring and one that matters for this document. The boring one: offload and consistency. Driver logic is in one place, CPU overhead drops, and behaviour is identical across operating systems. The important one: it puts the GPU's management logic behind a hardware boundary. Code running on the host, even root, even a compromised kernel, cannot reach into GSP-RM's private state; it can only send messages. When the vGPU chapter (chapter 7) needs to give untrusted virtual machines pieces of a GPU, "the privileged manager runs on the die, out of everyone's reach" is exactly the foundation it stands on. If GSP-RM reminds you of the firmware-heavy design of ConnectX NICs from the SR-IOV dossier, the card that is really a small computer running its own OS, that is the correct instinct.

This modernisation is also what made NVIDIA's 2022 open-sourcing move possible: the open GPU kernel modules (github.com/NVIDIA/open-gpu-kernel-modules) publish the host-side kernel code under MIT/GPL — and they run only in GSP mode, because the proprietary logic stayed in the firmware blob. The proof of the GSP's instruction set is right there in that repository: the file kernel_gsp_tu102.c "prepares RISCV core to run GSP-RM". Note what stayed closed: the firmware itself, and the entire userspace (libcuda). Open kernel modules do not mean an open driver.

NVML: the management path

One more component. Everything so far served the data plane, getting work onto silicon. Administration goes through a separate library: NVML, the NVIDIA Management Library. It is the C library behind nvidia-smi (which is a CLI wrapper around it), and behind every Kubernetes component you will meet in the Kubernetes plumbing chapter (chapter 8). Query temperature, list processes, set clocks, and, crucially for us: create and destroy MIG partitions, configure vGPU, read per-tenant utilization. NVML calls travel the slow path (library, ioctl, RM, mostly GSP-RM) and that is fine, because management is rare and slow by nature.

So the full picture of "the driver" is a two-plane system, and it is worth one diagram before the sharing chapters start carving it up.

Chapter 4

Time-slicing: sharing by default

~10 min · HW KERNEL — We know the undisturbed launch path. Now Tenant B finally shows up with work of its own, and we configure precisely nothing: this chapter is what the hardware already does when two contexts want one GPU.

Here is a fact that surprises people who came to GPUs recently: two processes could always share an NVIDIA GPU, with no flags, products or Kubernetes involved. Start two CUDA programs on one card and both make progress. This zero-configuration behaviour is sharing family 1 from the prologue (chapter 0), it is what "time-slicing" means in every vendor document, and understanding exactly what it does, and the three things it refuses to do, is the baseline every later chapter improves on.

Two TSGs walk into a runlist

Rewind to the undisturbed launch path (diagram 2.1). Tenant A has a context, its channels grouped into a TSG, sitting on the runlist. Tenant B starts; the driver (GSP-RM, per the driver-and-firmware chapter) builds a second context and adds a second TSG to the runlist. Now the runlist scheduler has a decision to make, and its policy is unglamorous: round-robin. Grant TSG A the engines for one time slice — millisecond scale — then TSG B, then A again.

The crucial word is the engines, plural but exclusive: while TSG A holds its turn, A's kernels own the SMs. Two contexts do not execute compute simultaneously under time-slicing: Tenant B's beautifully parallel kernel waits its full turn even if Tenant A is using three SMs out of 108. The GPU alternates between tenants wholesale. This is the single most important sentence in the chapter, because it is the exact inefficiency the MPS and MIG chapters (chapters 5 and 6) exist to fix.

What a context switch costs

At the end of A's slice, the hardware performs a GPU context switch: save everything the running context has on the engines, restore B's. "Everything" is far more than a CPU's few hundred bytes of registers. It is the architectural state of up to 108 SMs — register files for tens of thousands of live threads, shared memory contents, scheduler state — written out to dedicated preemption buffers in VRAM, megabytes of it. A GPU context switch is a bulk memory operation. It works, it is invisible to the tenants, and it is orders of magnitude heavier than what your OS does between processes.

And there is a subtler question: when can the hardware interrupt a running kernel? On Kepler and Maxwell (pre-2016), the honest answer was "at thread-block boundaries": a kernel whose blocks each ran for minutes could not be preempted mid-block, so one tenant's long kernel blocked everyone. Pascal fixed this in silicon. The P100 whitepaper states it plainly: compute tasks can now be "preempted at instruction-level granularity, rather than thread block granularity as in prior Maxwell and Kepler GPU architectures". This is compute preemption: stop a kernel between any two instructions, save state, resume later as if nothing happened. Every GPU in this document (Turing onward) has it, and it is the quiet hardware foundation that makes time-slicing between strangers tolerable at all.

The three refusals

Now the honest ledger. Time-slicing gives each tenant the whole GPU, alternately, with the GMMU keeping their address spaces private. What it refuses to do:

It refuses to partition memory capacity. Both contexts allocate from the same physical VRAM pool, first come, first served. Tenant A takes 35 GB of a 40 GB card; Tenant B's cudaMalloc for 10 GB returns an out-of-memory error, full stop. Nothing arbitrates: the driver has no quota to apply and no eviction path, because, as the prologue said, VRAM does not swap.

It refuses to guarantee performance. Round-robin shares turns; what each tenant gets from its turns depends on who else is running. Add a third tenant and everyone's throughput drops by a third with no warning; a tenant that launches storms of kernels gets exactly as many turns as one that sips. Nothing meters compute consumed.

It refuses to fully contain failures. Time to define a word you will grep for in anger one day. When the driver hits a serious error, it logs an Xid — a numbered error report in the kernel log (dmesg | grep Xid), each number a diagnosis. Many are contained: an illegal memory access kills the offending context and the neighbour never notices. Some are not: an Xid reporting the GPU fell off the PCIe bus, or a firmware halt, takes down every context on the card, innocent or not. Under time-slicing, tenants share one blast radius for the worst failures.

Kubernetes discovers the oldest trick

The Kubernetes plumbing chapter (chapter 8) owns the full Kubernetes picture, but one piece belongs here because it is pure time-slicing under a different name. The NVIDIA device plugin normally advertises each physical GPU as one nvidia.com/gpu. Its time-slicing mode is a config entry:

version: v1
sharing:
  timeSlicing:
    resources:
    - name: nvidia.com/gpu
      replicas: 4

One physical GPU now advertises as four schedulable replicas — oversubscription, turned into scheduler inventory. What enforcement machinery stands behind that number? None. Four pods are scheduled onto the node, each opens a context, and the hardware round-robins them exactly as this chapter described: same unpartitioned VRAM, same shared blast radius. The replicas count is an admission-control fiction for the scheduler; the device plugin even has a config flag (failRequestsGreaterThanOne) whose only job is to stop users from believing that requesting two replicas gets them two GPUs' worth of anything. Time-sliced replicas are a fine tool for packing forgiving dev workloads, and an honest operator documents them as exactly that.

Recap

With zero configuration, the runlist scheduler round-robins TSGs in millisecond turns; whoever holds a turn owns all the engines, so tenants alternate rather than overlap. Compute preemption (Pascal onward) lets the hardware stop kernels between instructions and swap megabytes of SM state to VRAM, making the alternation safe even mid-kernel. Time-slicing refuses three things: VRAM capacity quotas (allocation is first come, then OOM), performance guarantees (turns are equal, outcomes are not), and containment of the worst Xid failures. Kubernetes time-sliced replicas are this same behaviour behind a scheduler-side count that enforces nothing.

Chapter 5

MPS: many processes, one context

~9 min · CUDA — The time-slicing chapter (chapter 4) ended on an inefficiency: tenants alternate wholesale, so Tenant A's three busy SMs block Tenant B's hundred idle ones. This chapter commits the obvious sin (if separate contexts cannot overlap, put everyone in one context) and then inspects the bill.

The inefficiency has a shape worth stating precisely. The runlist scheduler's unit of granting is the TSG, and TSGs belong to contexts. Different contexts always mean different turns. But within one context, the work distributor runs many kernels at once, filling SMs from whatever streams have work. A stream is the ordered queue of kernels a CUDA program submits into, and one context may hold many streams that the hardware is free to run at the same time. So the whole serialization problem is an artifact of tenants arriving in separate contexts. The Multi-Process Service, MPS, family 1's cooperative variant from the prologue, is NVIDIA's official way to collapse that separation.

The architecture: a daemon, a server, and trusting clients

MPS is three processes and a rendezvous. An administrator starts the MPS control daemon (nvidia-cuda-mps-control -d). From then on, any CUDA process on that machine — now called an MPS client — checks a well-known pipe directory at startup (CUDA_MPS_PIPE_DIRECTORY, default under /tmp/nvidia-mps); finding a daemon, its libcuda connects instead of building a standalone context. The daemon spawns one MPS server process per user, and it is the server that owns the one real GPU context everybody will share.

On pre-Volta hardware this was an ugly funnel: clients shipped work to the server, the server submitted everything, one address space for all, one bad pointer away from chaos. Volta rebuilt it in hardware, and the modern version is the only one worth learning: each client gets its own GPU address space (the MPS documentation says clients "own their own GPU address space instead of sharing GPU address space") and each client submits work directly to the GPU through its own channels, with no server hop on the hot path. The undisturbed launch path (diagram 2.1) is still intact, per client. What clients share is the context's scheduling identity: to the runlist scheduler, everyone inside MPS is one TSG family, one turn, so the work distributor packs all clients' kernels onto SMs simultaneously. Tenant A's three SMs and Tenant B's hundred now coexist in the same microsecond.

The knobs: provisioning

Sharing SMs concurrently raises an obvious fear: one greedy client fills the machine. MPS answers with what its documentation carefully calls limited execution resource provisioning. The env var CUDA_MPS_ACTIVE_THREAD_PERCENTAGE caps the portion of the GPU's threads a client's context may occupy — set 20, and that client's kernels get dealt onto at most a fifth of the execution resources. The administrator can set a default for all clients in the daemon (set_default_active_thread_percentage), and a client's own env var can only shrink its share further, never grow past the daemon's ceiling. The lower value wins.

Memory got its knob later: CUDA_MPS_PINNED_DEVICE_MEM_LIMIT, per-device caps like 0=8G, the first VRAM quota in this document. Note the shape of both knobs: environment variables and daemon settings, applied at client startup. This is provisioning among processes that could have been configured honestly; a tenant who edits their own environment is outside its model. MPS was designed for cooperating processes (think MPI ranks from one job), and its trust model still assumes them. The HAMi chapter (chapter 9) exists because people wanted these two knobs, enforced.

The bill: one blast radius

Address spaces are isolated; failure is not. The MPS documentation is admirably blunt: a fatal GPU fault generated by one client "will be contained within the subset of GPUs shared between all clients" — which, on one GPU, means all clients. One tenant's fatal fault takes down every process in the MPS pool, and the fault report does not even name the culprit. Performance interference is likewise real: provisioning caps SM occupancy, but L2, memory bandwidth, and copy engines stay common property.

So the honest positioning: MPS buys true concurrent packing, the best utilization of any technique so far, at the price of shared fate and advisory limits. Perfect for one team's processes; reckless for strangers. Kubernetes can drive it through the device plugin's MPS mode, which the Kubernetes plumbing chapter (chapter 8) shows, and the same trust caveats apply.

Rerun the time-slicing chapter's two-terminal experiment, but first: nvidia-cuda-mps-control -d. If the two matmul loops previously each doubled in wall time, under MPS with small kernels they overlap — combined time drops toward the solo number. Then set it to 50 and watch a single client cap at half the SMs. GeForce laptop parts sometimes refuse MPS; the H100 will not.

Recap

Contexts never share a scheduling turn, but kernels inside one context pack SMs freely, so MPS merges every client into one server-owned context. Since Volta, each client keeps a private GPU address space and submits directly through its own channels; what is shared is scheduling identity and therefore true SM-level concurrency. Limits exist (active thread percentage for execution resources, a pinned-memory quota for VRAM) but they are provisioning knobs read at startup, shrink-only against a daemon default, and a tenant can edit them. Fatal faults hit every client in the pool, unattributed. Maximum packing, shared fate: family 1 pushed to its logical extreme.

Check yourself

1. Trace Tenant B's kernel launch under MPS from cuLaunchKernel to the SMs. Which steps changed versus the undisturbed launch path, and which process's context does the runlist scheduler see?

Answer

Tenant B's libcuda, having found the control daemon's pipe directory at startup, joined the MPS server's context instead of creating its own, with its own GPU address space and channels. From then on the launch is unchanged: pushbuffer write into B's own channel, doorbell ring, runlist turn, work distributor, SMs. What changed is setup: B's channels belong to the server-owned context's TSG. The runlist scheduler therefore sees one TSG, the MPS server's, for every client, so all clients' kernels are eligible in the same turn and the work distributor packs them onto SMs together.

Check it with nvidia-smi, which shows the nvidia-cuda-mps-server process holding the context, and the MPS architecture page, which states that clients submit work directly since Volta. The near miss is routing every launch through the server process. That was the pre-Volta funnel; the modern hot path has no server hop.

2. The daemon default is 40% active threads; a client sets CUDA_MPS_ACTIVE_THREAD_PERCENTAGE=80. Predict its effective share, and explain why the opposite order of values would behave differently.

Answer

40%. The daemon's default is a ceiling, and a client's own setting can only shrink its share, never grow it past the ceiling. The lower value wins, so 80 requested under a 40 default yields 40. With the values reversed, a daemon default of 80 and a client setting of 20, the client gets 20: its request is below the ceiling and is honoured.

Check it with echo get_default_active_thread_percentage | nvidia-cuda-mps-control, then start a client with the variable set and compare the SM occupancy a profiler reports. The near miss is adding or averaging the two values. There is no arithmetic; it is a minimum. Both settings are read once at client startup, so changing the variable in a running process changes nothing.

3. Under time-slicing, Tenant B's fatal fault usually kills only Tenant B. Under MPS it kills Tenant A too. What structural difference from this chapter explains it, and what does that tell you about running strangers under MPS?

Answer

Under time-slicing each tenant has its own context, and the hardware attributes and contains a fault to the context that raised it. Under MPS every client shares one context, the server's, so the fault domain is the whole context: the MPS documentation says a fatal GPU fault from one client is contained to the set of GPUs shared by all clients, which on one GPU means every client, and the report does not name the culprit. So MPS is for processes that already trust each other, such as MPI ranks of one job, and putting two teams on one daemon converts one team's bug into the other's outage.

Check it on the "When to Use MPS" page in NVIDIA's MPS documentation. The near miss is blaming a shared address space. Since Volta clients have separate address spaces; what is shared is the context's scheduling identity and fault domain.

Chapter 6

MIG: cutting the silicon

~9 min · HW FW — MPS packed our tenants together but left them sharing fate and trusting each other's limits. This chapter finally builds walls, through the exact die we mapped in the silicon chapter (chapter 1), and our kernel launch runs, for the first time, on silicon that is Tenant A's alone.

Everything so far shared the GPU by scheduling it. MIG mode (Multi-Instance GPU, family 2, available on A100 and every data-center generation since) shares it by dividing the hardware: these SMs are yours, that L2 portion and memory controller too, and the neighbour cannot reach them at any time slice, because there is no slice. Both tenants run in the same instant on different transistors.

Slices, assembled into instances

The silicon chapter (chapter 1) supplied the two facts this chapter uses. The compute side of the die comes in repeated blocks, and MIG's unit of compute is the SM slice, roughly one GPC's worth; an A100 offers 7 of them. The memory side divides into 8 memory slices, each an eighth of the VRAM plus the L2 slices and bandwidth serving it (defined in the silicon chapter, doing real work now, as promised).

A tenant's allocation is a GPU instance (GI): a bundle of memory slices, SM slices, and engines. The MIG User Guide's own definition: "a combination of GPU slices and GPU engines (DMAs, NVDECs, and so on)". A GI is the wall: its memory slices, its L2 portion, its copy engine are private. Within a GI there is an optional second cut: compute instances (CIs) subdivide the GI's SM slices while sharing the GI's memory and engines — useful when one tenant wants two workloads with compute separation but a common memory pool. CIs carry a prefix of their own: 2c.3g.20gb names two of a 3g.20gb instance's three SM slices.

You do not draw these shapes freehand. The hardware ships a fixed menu of MIG profiles, named [N]g.[M]gb — N SM slices, M gigabytes. On an H100 80GB the menu includes 1g.10gb (seven of them fit), 2g.20gb (three fit), 3g.40gb (two fit), up to 7g.80gb (the whole card, MIG mode still on). The maximum is seven instances per GPU, and mixes are legal if the slices add up: one 3g.20gb plus two 2g.10gb fills an A100 40GB exactly — 7 SM slices, 8 memory slices, done. Now the silicon chapter's odd arithmetic pays off: 7 SM slices but 5 NVDECs on A100 meant some instances went without a decoder; the H100's 7 NVDECs exist so that every instance can have one.

What the walls are made of

Because a GI owns its memory slices, it gets what neither time-slicing nor MPS could offer: performance isolation. Tenant B hammering its own memory does not consume Tenant A's L2 or memory bandwidth, because those are physically separate slices. The work distributor and runlist machinery are likewise instantiated per instance: each GI schedules its own contexts on its own SM slices. Our launch's path from the undisturbed launch (diagram 2.1), context, channel, doorbell, runlist, work distributor, now exists in a private copy inside Tenant A's instance.

Fault isolation follows the same walls. An illegal memory access, a GMMU fault, most Xids: contained to the instance that caused them, and the MIG design goal is exactly that error containment. And note who enforces all this: partition state is programmed into the hardware by RM, which, per the driver-and-firmware chapter (chapter 3), means GSP-RM firmware. Host software cannot quietly rewire a partition; it can only ask the firmware, through NVML.

What MIG does not do matters just as much. Inside one instance, everything from the launch-path chapter to the MPS chapter (chapters 2 to 5) applies unchanged: multiple contexts time-slice on the instance's SM slices, and you may even run MPS within an instance, because the families compose. And a MIG instance is mostly static: reshaping partitions requires the affected instances to be empty of work; you drain tenants before redrawing their walls. MIG is a wall, and a wall cannot be moved while tenants stand inside it.

How instances appear on the host

Here is where your SR-IOV instincts will mislead you, so let us be explicit. A VF is a new PCIe function: new BDF, new config space, assignable to a VM through VFIO. A MIG instance is a partition inside the GPU, behind the same single PCIe device. Creating one adds no PCIe function and no new /dev/nvidia* node.

What the driver exposes instead is a capability tree: /proc/driver/nvidia/capabilities/ mirrors the GI/CI hierarchy, and access is granted through character devices under /dev/nvidia-caps/: small "permission token" device nodes, one per capability, with their own dynamically allocated major number (visible in /proc/devices). A container that should see only instance 2 gets access to instance 2's cap nodes and nothing else, enforced by the device cgroup, the kernel's per-container allow-list of device nodes. CUDA processes pick their instance by UUID: CUDA_VISIBLE_DEVICES=MIG-<uuid>, one MIG device per process. This is also why plain MIG cannot be handed to a virtual machine the way a VF can, a gap the vGPU chapter (chapter 7) closes.

# carve: one 3g.20gb + two 2g.10gb, with default compute instances

Then the two-terminal experiment from the time-slicing chapter, pinned to different instances: CUDA_VISIBLE_DEVICES=MIG-<uuid-1> in one shell, MIG-<uuid-2> in the other. Unlike under time-slicing, each loop now runs at full private speed, and ls /dev/nvidia-caps/ /proc/driver/nvidia/capabilities/gpu0/mig/ shows the permission-token plumbing this chapter described.

Recap

MIG divides the hardware itself: SM slices (7 on A100) and memory slices (8) assemble into up to seven GPU instances per card, shaped only by the fixed profile menu ([N]g.[M]gb), optionally subdivided into compute instances that share the instance's memory. Each GI owns its L2 portion, bandwidth, engines, and scheduling machinery, giving real performance isolation and per-instance fault containment, enforced by GSP-RM in firmware. Instances are internal partitions: they surface as capability nodes under /dev/nvidia-caps/ plus MIG UUIDs, are selected via CUDA_VISIBLE_DEVICES, and reshaping them requires draining. Inside an instance, everything from the launch-path chapter to the MPS chapter replays unchanged.

1. An A100 40GB has 8 memory slices but its largest instance count is 7 × 1g.5gb. Predict which resource runs out first and why the eighth memory slice cannot become an eighth tenant.

Answer

SM slices run out first. An A100 exposes 7 SM slices, and every GPU instance needs at least one, so seven instances exhaust compute. That eighth memory slice cannot become a tenant because a GPU instance is a bundle of memory slices plus SM slices plus engines; memory alone has nothing to execute a kernel. The 1g.5gb profile's 5 GB is one eighth of 40 GB, so seven of them leave exactly one eighth unassigned.

Check it with nvidia-smi mig -lgip, which lists each profile and how many of it fit. The near miss is reasoning from memory slices to tenants. The instance count is bounded by SM slices; memory slices bound only how much each instance can take.

2. Trace our kernel launch inside Tenant A's 3g.20gb: which structures from the undisturbed launch path are now private copies inside the instance, and which still belong to the whole card?

Answer

Private to the instance: the context's GMMU page tables map only the instance's 4 memory slices; the channels and TSG sit on the instance's own runlist, walked by the instance's own runlist scheduler; the instance's own work distributor deals blocks to its 3 SM slices; and the L2 slices, memory bandwidth and copy engine it owns are private. Still whole-card: the PCIe host interface and its BARs (there is one PCIe device), the GSP-RM firmware that programmed the partitions, the kernel driver and device files, and power and clocks.

Check it with ls /proc/driver/nvidia/capabilities/gpu0/mig/, which shows per-instance access tokens while lspci still shows one device. The near miss is thinking the instance is a separate PCIe function. It is a partition behind one device, which is why the vGPU chapter needs a VF to hand it to a VM.

3. Tenant C's process dies of an illegal memory access at the same moment Tenant A is mid-inference. State Tenant A's fate under time-slicing, under MPS, and under this chapter. One word each.

Answer

Time-slicing: continues. The fault is contained to C's context and A's context carries on. MPS: dies. All clients share one context and one fault domain, and the fatal fault takes the pool down. MIG: unaffected. C's fault stays inside C's instance; A's instance has its own fault domain, its own runlist and its own memory slices, so not even A's latency changes.

Chapter 7

vGPU: the VF returns

~11 min · FW KERNEL — MIG walled tenants off, but all of them still trust one host kernel and one driver install. Now the tenants are virtual machines, strangers with root running their own operating systems, and the sharing boundary has to move below everything we have built so far.

From the SR-IOV dossier you already own the endgame for NICs: give each VM a virtual function, let VFIO and the IOMMU guarantee the VM can only DMA into its own memory, and get out of the way. The obvious question: why not exactly that for GPUs? This chapter's answer: eventually yes, partly — but a GPU needs so much more mediation than a NIC that the product built around it, NVIDIA vGPU, is best understood as a licensed, firmware-assisted middle road between paravirtualization and passthrough.

Why passthrough isn't enough, and mdev

Whole-GPU passthrough works today, no license needed: bind the GPU to vfio-pci, hand it to one VM, done — that is the SR-IOV dossier's playbook verbatim. But it shares nothing: one VM owns the card. To multiplex VMs you need per-VM devices, and pre-Ampere GPUs had no VFs to offer. Linux's answer was the mediated device framework, mdev: a VFIO extension where a host driver fabricates virtual PCIe devices out of software. The host driver decides what config space, what BARs, what interrupts each fabricated device shows; VFIO carries it to the VM like any assigned device. Where a VF is silicon pretending to be a device, an mdev is a driver pretending to be one.

NVIDIA's host driver for this is the Virtual GPU Manager, a special driver package installed on the hypervisor; it is separate from the normal driver and is part of the licensed vGPU product. It registers available vGPU types (profiles, again a fixed menu, each pairing a VRAM share with a class letter, like a 10 GB compute-class profile on an A100) and the operator instantiates one per VM through sysfs or mdevctl.

Ampere: the VF returns

On Ampere and later, the promised reunion: the data-center GPU implements SR-IOV. The host enables VFs with a vendor script (/usr/lib/nvidia/sriov-manage -e 0), lspci sprouts virtual functions with real BDFs, and each vGPU now rides a VF instead of a purely fabricated mdev. What the VF contributes is exactly what silicon is good at: a genuine per-VM PCIe identity: its own BARs and MMIO space, so the guest maps its own channels and doorbells and rings them with no hypervisor exit, and its own requester ID, so the IOMMU confines its DMA. The thick runtime path of the undisturbed launch (diagram 2.1) is still there inside a VM, at near-native speed.

Here is where GPUs part company with NICs: the VF is a share of a GPU, and the guest driver knows it. Everything on the control plane (create a context, build page tables, touch the runlist) cannot be trusted to a guest and is absent from the VF. The guest driver packages those requests and sends them to the host's Virtual GPU Manager and the GSP firmware, which validate and execute them on the guest's behalf. That is the same "thin client talks to the real RM" shape as the driver-and-firmware chapter (chapter 3), with the trust boundary now between guest and host instead of kernel and firmware. If you remember the SR-IOV dossier's mailbox, the VF driver asking the PF driver for privileged favours, this is that, scaled up from "set my MAC" to "manage my share of a GPU".

Whose silicon, whose schedule

What does a vGPU's "share" actually mean in hardware? NVIDIA gives two answers, and both should now read as old friends.

Time-sliced vGPU: every VM's work runs on the same engines, and a scheduler in the host manager and firmware rotates them: the time-slicing chapter's machinery (chapter 4) with policies added. Three policies, per NVIDIA's docs: best effort (the default: round-robin among VMs that currently have work, no guarantees, best utilization); equal share, "each running VM receives an equal fraction of GPU time regardless of its load", so your fraction shrinks as VMs power on but idle neighbours donate nothing; and fixed share, "each VM receives a fixed fraction of GPU time, even when other VMs are idle": a reservation, idle cycles burned, perfectly predictable. Time slices are millisecond-scale and tunable, the same latency-versus-throughput dial as every scheduler in this document.

MIG-backed vGPU: each VM's vGPU is bound to a MIG GPU instance: the MIG chapter's walls (chapter 6), with a VM inside them. Spatial isolation, performance isolation, fault containment, now stacked under VM isolation. This is the pairing that finally untangles the marketing: vGPU is the virtualization wrapper; time-slicing or MIG is what it wraps. The question "MIG or vGPU?" is usually malformed: MIG partitions the GPU, vGPU wraps a VM around a partition or a schedule, and they compose.

The paperwork layer

One layer of this stack is a contract: vGPU is a paid product. The Virtual GPU Manager installs only on supported hypervisors, and the guest driver phones a license service — hosted by NVIDIA or run on-site — to activate; unlicensed, it degrades. None of the machinery above changes, but architecture discussions that ignore the license line tend to end in procurement meetings. Since the details drift by release, one table, dated honestly:

Recap

vGPU moves the sharing boundary below untrusted VMs. Pre-Ampere it fabricated per-VM devices in software (mdev); Ampere and later expose real SR-IOV VFs, giving each VM its own BARs, doorbells, and IOMMU-confined DMA, so the data path stays direct and near-native. The control plane stays on the host: guest drivers must ask the host's Virtual GPU Manager and GSP firmware for anything privileged. The GPU share itself is borrowed machinery, time-sliced (best effort, equal share, fixed share) or MIG-backed, because vGPU wraps a VM around a partition or a schedule. And one layer is a contract: matched host and guest drivers and a license service.

Answer

Fixed share: 25%. Each VM has a fixed fraction of GPU time whether the others are running, idle or off, so with four VMs configured the busy one gets one quarter and three quarters go unused. Equal share: 33%. Time is split equally among running VMs, three are powered on, so the busy VM gets one third; the two idle VMs' turns stay reserved for them. Best effort: close to 100%. Round-robin runs only among VMs that currently have work, and only one does, so it takes nearly every turn.

Under MIG-backed vGPU the neighbour's context sits inside its own GPU instance with its own memory slices, runlist and fault domain, so instance-level faults stay on its side of the wall; only whole-card events reach you. Chapter 8

Kubernetes plumbing: from resource to device node

~9 min · K8S — Our launch now works on bare metal under four different sharing regimes. But Tenant A was a pod all along. This chapter builds the bridge: how a line of YAML becomes /dev/nvidia0 and a working libcuda inside a container, and how the scheduler learned to count the slices the four sharing chapters (chapters 4 to 7) created.

Two separate problems hide in "GPU pod", and mixing them up causes most of the confusion in this layer. Problem one: delivery. A container is just a namespaced process; someone must place the device nodes and the driver's userspace into it. Problem two: inventory. The scheduler must know which nodes have what GPU resources, whole or sliced, and stop double-booking them. Kubernetes solves them with different machinery.

Delivery: the toolkit and CDI

Containers share the host kernel, so nvidia.ko and GSP-RM are already running; there is nothing to deliver there. What a container lacks is everything from the launch-path chapter's user space: /dev/nvidiactl, /dev/nvidia0, /dev/nvidia-uvm, and libcuda.so. And here is the detail that explains the whole design: libcuda ships with the driver, and its version must match the loaded kernel module exactly. Baking it into the image would break on every driver upgrade. So it has to be injected at container start, from the host.

The injector is the NVIDIA Container Toolkit: historically a stack of a runtime wrapper and hooks around runc, and these days increasingly just a generator for CDI, the Container Device Interface, a CNCF spec whose README describes it in one line: a specification for container runtimes to support third-party devices. A CDI spec is a JSON or YAML file on the node mapping a device name (nvidia.com/gpu=0, or a MIG instance) to the concrete plumbing it requires: which /dev nodes, which library mounts, which env vars. The runtime reads it and does exactly that; no vendor code executes at container start. If you are thinking "this is CNI's design, for devices instead of networks": yes, explicitly and by intention.

Inventory: the device plugin, stretched to its limits

You know the device plugin protocol from the SR-IOV dossier — register with the kubelet's socket, ListAndWatch a list of device IDs, answer Allocate — and the NVIDIA one behaves exactly as you would expect, advertising nvidia.com/gpu. The sharing chapters plug in as configuration:

If you run GPUs on Kubernetes in 2026, you almost certainly run the operator and configure everything in this chapter through its values file.

The ceiling, and DRA

The device plugin model has a shape, and by now you can see its limits: resources are opaque integers of identical units, sliced at configuration time. The scheduler cannot express "any MIG instance with at least 20 GB", cannot create a partition on demand for a pending pod, cannot share one allocation between two pods deliberately. Every "mode" in the table above is a workaround for the model, configured node-by-node in advance.

DRA, Dynamic Resource Allocation, is Kubernetes' structural answer, GA since v1.34 (August 2025; today's docs mark the feature stable and default-on). The model changes from counted integers to claims: a ResourceClaim is an API object describing what a pod needs from a device class, with structured parameters the scheduler itself can evaluate against what nodes publish: attributes, capacity, partitionable shapes. A driver (NVIDIA ships a DRA driver alongside the plugin) satisfies the claim, and can in principle carve the MIG instance when the claim demands it rather than at provisioning time. Claims can be shared between pods on purpose. As of this writing the ecosystem is mid-migration, with device plugins everywhere and DRA arriving cluster by cluster, but the direction is settled: the integer era is ending. If you ever build your own orchestrator, DRA is the API you would target.

Try it now — laptop, no cluster needed

The delivery half works anywhere: nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml then read the file — every device node and library mount this chapter described, spelled out. Test it: podman run --rm --device nvidia.com/gpu=all ubuntu nvidia-smi. On the H100 later: kubectl describe node shows the advertised nvidia.com/* capacity changing as you switch plugin modes.

Recap

Two problems, two mechanisms. Delivery: libcuda is version-locked to the host driver, so the Container Toolkit injects it and the device nodes at start, declaratively via CDI specs. Inventory: the device plugin advertises countable units (whole GPUs, time-sliced replicas, MPS replicas, or MIG instances via the single and mixed strategies) and the GPU Operator deploys and wires all of it fleet-wide. The plugin model's opaque integers are the ceiling; DRA (GA in v1.34) replaces counting with ResourceClaims and structured parameters the scheduler can reason about, opening on-demand partitioning. Everything in this chapter is setup; no kubelet, plugin, or runtime ever touches a running launch.

Check yourself

1. Why would baking libcuda.so into your container image break after a node driver upgrade, while the same image with CDI injection keeps working? What does that tell you about where CUDA's version boundary really sits?

Answer

Because libcuda.so is part of the driver, and its version must match the loaded nvidia.ko exactly; their private ioctl interface changes between releases. An image carrying a libcuda from driver 550 talking to a 570 kernel module fails at context creation. With CDI, the runtime bind-mounts the host's own libcuda into the container at start, so the pair always matches. The version boundary therefore sits between the CUDA runtime (libcudart, which the application may ship) and the driver API (libcuda, which the host owns).

Check it in the output of nvidia-ctk cdi generate, which lists the library mounts, and with ldconfig -p | grep libcuda inside a running container, which shows a host path. The near miss is blaming the CUDA toolkit version in the image. The toolkit is user space and may be older than the driver; the hard match is libcuda to kernel module.

2. Trace a pod requesting nvidia.com/mig-3g.40gb from YAML to the first successful cuLaunchKernel, naming what each of scheduler, kubelet, device plugin, CDI and GSP-RM contributed, and which one enforced the memory wall.

Answer

The scheduler matched the request against nodes advertising a free nvidia.com/mig-3g.40gb unit and bound the pod. The kubelet called the device plugin's Allocate with the chosen unit. The device plugin, in migStrategy: mixed, returned a CDI device reference for that instance plus CUDA_VISIBLE_DEVICES=MIG-<uuid>. CDI told the runtime which /dev/nvidia* nodes, capability tokens and host libraries to mount. GSP-RM built the process's context inside the instance at container start, with GMMU page tables over the instance's memory slices and a TSG on the instance's runlist; and much earlier, when the MIG manager partitioned the card, GSP-RM built the instance itself. The memory wall is GSP-RM's, in firmware and silicon. Everything above it only named the instance.

Check it against the YAML-to-device-node diagram (diagram 8.1). The near miss is crediting the device plugin or CDI with enforcement. They hand out names, mounts and env vars.

3. A platform team wants "give this pod any instance with ≥20 GB, create it if absent". State precisely why the device plugin model cannot express this and which two DRA concepts can.

Answer

The device plugin model advertises opaque integers under fixed names, sliced at configuration time: a node publishes counts of nvidia.com/mig-3g.40gb and nvidia.com/mig-1g.10gb, and a pod must name one exactly. "At least 20 GB" is a comparison across names the scheduler cannot make, and "create it if absent" needs a partition carved at allocation time, for which the ListAndWatch then Allocate protocol has no hook. DRA expresses it with a ResourceClaim carrying structured parameters, a constraint such as memory of at least 20 GB that the scheduler evaluates against the attributes and capacity each node publishes, and with a DRA driver that satisfies the claim on demand, in principle carving the MIG instance when the claim is scheduled.

Check it in the Kubernetes DRA documentation linked in this chapter. The near miss is proposing more device-plugin modes. Every mode is a workaround inside the integer model.

Chapter 9

HAMi: slicing without hardware help

~10 min · ORCH CUDA — Every wall so far was built by NVIDIA: silicon (MIG), firmware and licenses (vGPU), a daemon with advisory knobs (MPS). This chapter builds walls out of nothing but a shared library and a scheduler, and finally uses the fact the launch-path chapter (chapter 2) established: whoever stands inside the cuLaunchKernel funnel can police every tenant.

The want is concrete: MIG-grade requests — "this pod gets 3 GB of VRAM and 30% of compute" — on GPUs that lack MIG (consumer cards, older parts), without vGPU licenses, at finer granularity than seven slices, reconfigurable per pod with no draining. The price will be equally concrete, and we will read it off the mechanism.

Standing inside the funnel

HAMi (the prologue's family 4; a CNCF project, incubating since July 2026) ships its enforcement as HAMi-core, a library named libvgpu.so. Its README states the position precisely: it operates "by hijacking the API calls between CUDA-Runtime (libcudart.so) and CUDA-Driver (libcuda.so)". Loaded ahead of the real driver API (the LD_PRELOAD trick, industrialized) it exports every cu* symbol, does its bookkeeping, then forwards to the genuine libcuda. Recall the undisturbed launch path (diagram 2.1): every framework, every language, every launch and every allocation in the process squeezes through that one API. Own the funnel, own the tenant.

Memory quotas. The container carries CUDA_DEVICE_MEMORY_LIMIT=3g. The hook intercepts the allocation family (cuMemAlloc_v2, cuMemAllocManaged, the launch-path chapter's UVM cameo, and cuMemAllocHost_v2) and keeps a ledger. A request that would cross the limit never reaches the driver: the hook "directly returns CUDA_ERROR_OUT_OF_MEMORY", in the docs' words. The application experiences a smaller GPU, indistinguishable from the time-slicing chapter's real OOM. And the lie is made self-consistent: the hook also intercepts NVML's nvmlDeviceGetMemoryInfo, so nvidia-smi inside the container reports a 3 GB card. Fake wall, honest mirror.

Compute quotas. CUDA_DEVICE_SM_LIMIT=30 works on the launch side, and here the design is genuinely clever. A token pool (a counter named g_cur_cuda_cores in the source) is debited by a rate limiter that runs before each intercepted kernel launch; an empty pool makes the launch wait (a nanosleep spin) before forwarding. Refilling is a feedback loop: a background watcher thread samples the GPU's actual utilization through NVML and adjusts the refill rate; below your 30%, tokens pour in, and above it the refill slows. What this amounts to is a statistical governor, accurate on average, wobbly at millisecond scale, and blind to a kernel that is already running. It has none of the hardware enforcement of MIG or the scheduler policy of vGPU.

Teaching the scheduler the same lie

A library limits one process; a platform needs the cluster to place pods against those made-up fractions. HAMi's Kubernetes half is four cooperating components, and after the Kubernetes plumbing chapter (chapter 8) each will look familiar. A mutating webhook spots pods requesting HAMi resources and rewrites them to use HAMi's scheduler. The scheduler extender (filter, score and bind hooks on the stock scheduler) keeps its own view of every card's real VRAM and committed fractions, picks a node and a specific GPU, and records the verdict in pod annotations. HAMi's fork of the device plugin reads those annotations at Allocate time and wires the container: device nodes via the usual machinery, plus libvgpu.so mounted and preloaded, plus the two env vars carrying the quota. The pod requests read like this:

resources:
  limits:
    nvidia.com/gpu: 1        # one virtual GPU
    nvidia.com/gpumem: 3000  # 3000 MiB of its VRAM
    nvidia.com/gpucores: 30  # 30% of its compute

Three resource names where the Kubernetes plumbing chapter had one, because the extender, unlike the stock scheduler, treats memory and compute as separate, real quantities on each physical card. That is the actual innovation: admission control that models the GPU, bolted onto enforcement that merely impersonates one.

The price tag, read off the mechanism

Security first, stated plainly because the mechanism makes it unavoidable. HAMi's walls live inside the tenant's own process, held up by symbol interposition. A tenant who controls their image can statically link the driver API, ship their own loader, or scrub the preload, and every limit in this chapter evaporates, with the scheduler still believing its ledger. HAMi documents this openly; it is the definition of family 4. HAMi is multi-tenancy for tenants you employ. If your neighbours are adversaries, the walls must come from the MIG chapter or the vGPU chapter (chapters 6 and 7).

Isolation follows the same logic: shared blast radius (one context-killing Xid still takes everyone down; the time-slicing chapter's rules apply), no L2 or bandwidth separation, and compute limits that wander around their target. In exchange: it works on any NVIDIA card including your laptop, it is free, fractions are of arbitrary size, dozens of tenants fit per GPU, and reconfiguration per pod needs neither a drain nor a license server.

HAMi has company in family 4; the pattern is bigger than the project. Volcano's vGPU mode wires the very same HAMi-core library under its own scheduler (resources volcano.sh/vgpu-number/-memory/-cores). Run:ai (acquired by NVIDIA, its scheduler open-sourced as KAI) does fractional GPUs with the same split: scheduler-modelled fractions, software-side enforcement. When you meet any "GPU fractions" product, ask the two questions this chapter armed you with: who models the fraction, and who enforces it? The first answer is always "a scheduler"; the honesty lives in the second.

Try it now — laptop GPU, no cluster

HAMi-core works standalone. Build libvgpu.so from github.com/Project-HAMi/HAMi-core, then: LD_PRELOAD=./libvgpu.so CUDA_DEVICE_MEMORY_LIMIT=1g python3 -c "import torch; x=torch.rand(20000,20000,device='cuda')" — a ~1.6 GB allocation fails with a CUDA OOM on your 8 GB laptop card. Drop the preload, it succeeds. You have just run sharing family 4 with your own hands, no Kubernetes in sight.

Recap

HAMi enforces made-up limits from inside the tenant's process: libvgpu.so interposes between CUDA runtime and driver API, refuses over-quota allocations with a genuine-looking CUDA_ERROR_OUT_OF_MEMORY, lies consistently through NVML so nvidia-smi agrees, and throttles compute with a token pool refilled by a utilization-sampling feedback thread. Cluster-side, a webhook, a scheduler extender with a real per-GPU model, and a modified device plugin turn gpumem/gpucores requests into placements and preloads. The trade is explicit: any card, any fraction, without a license or a drain, against in-process enforcement a hostile tenant can shed and isolation no better than time-slicing. Volcano reuses HAMi-core outright; Run:ai/KAI plays the same split. Always ask: who models the fraction, who enforces it.

Check yourself

1. Trace torch.zeros(..., device='cuda') in a HAMi pod from the framework call to physical VRAM, naming every library crossed and where the quota check fires.

Answer

PyTorch's caching allocator calls the CUDA runtime, libcudart, which calls the driver API's cuMemAlloc_v2. Because libvgpu.so was preloaded, that symbol resolves to HAMi-core's hook first. The hook consults its memory ledger against CUDA_DEVICE_MEMORY_LIMIT: if the request would cross the limit it returns CUDA_ERROR_OUT_OF_MEMORY and the driver is never called; otherwise it records the size and forwards to the genuine libcuda, which asks RM through an ioctl to allocate VRAM and map it into the context's GMMU page tables. Libraries crossed: libtorch, libcudart, libvgpu.so, libcuda.so. The quota check fires inside the hook, in the tenant's own process, before any driver code runs.

Check it against the HAMi fractions diagram (diagram 9.1), or run with LD_DEBUG=bindings and watch cuMemAlloc_v2 resolve into libvgpu.so. The near miss is placing the check in the device plugin or the kernel. Neither sees allocations.

2. nvidia-smi inside a HAMi container shows 3000 MiB total on an 80 GB card. Name the exact function whose interception produces this, and explain why HAMi must fake it for the memory limit to be operationally usable.

Answer

nvmlDeviceGetMemoryInfo, the NVML call that nvidia-smi and most frameworks use to read total and used memory. HAMi-core exports it too and answers with the quota as the total and the ledger's figure as used. It has to, because frameworks size their caches and batch sizes from that figure. PyTorch would otherwise see 80 GB free, allocate optimistically, and hit the hook's fake OOM at an unpredictable point, while operators saw 80 GB on every dashboard as pods failed at 3 GB. Consistent lying makes the limit behave like a small card, which is the point.

Check it in the HAMi-core README's list of hijacked calls, and by running nvidia-smi with and without the preload in the same container. The near miss is thinking the hook shrinks the card in the driver. The GPU never learns; only the answers given to the tenant change.

3. A tenant statically links against the driver API. State precisely which HAMi guarantees fail, which component still "believes" the tenant is limited, and which chapters' technologies would have kept their limits under the same trick.

Answer

Both enforcement guarantees fail. The memory quota, because cuMemAlloc no longer resolves to the hook, so allocations reach the real driver and RM hands out VRAM until the card is full. The compute cap, because the rate limiter ran only on intercepted launches. The scheduler extender still believes the tenant is limited: its ledger records 3000 MiB committed on that card and keeps placing other pods against the remainder, now overlapping memory the tenant took. MIG and vGPU would have held: MIG's walls are programmed into hardware by GSP-RM, and vGPU's share is enforced by the Virtual GPU Manager and firmware below the VM. MPS would fail as well; its limits are environment variables.

Check it against the "holds against a hostile tenant" row of the epilogue's choosing table. The near miss is expecting the kubelet or device plugin to notice. They ran at start and never look again.

Chapter 10 · Epilogue

Choosing, the traps that remain, and what comes next

~8 min · all layers — Our kernel launch has now travelled every road: alternating turns, a merged context, a walled instance, a virtual machine, and a policed library. Time to stack the whole tower once, walk the launch end to end one last time, and be honest about the traps.

The whole tower, once

Every box below was earned in some chapter. Read it bottom-up if you came for hardware, top-down if you came for Kubernetes.

The last walk

One final trace, on the stack you are most likely to build: a MIG-partitioned H100 behind the GPU Operator. A pod requests nvidia.com/mig-3g.40gb: 1. The scheduler finds a node with a free instance. The kubelet calls the device plugin; the plugin answers with the instance's CDI name and CUDA_VISIBLE_DEVICES=MIG-<uuid>; the runtime mounts the device nodes, the cap nodes, and the host's libcuda. The process starts. libcuda opens the device files, and its setup ioctls travel to GSP-RM, which builds a context inside the instance: private GMMU page tables over 40 GB of walled memory slices, channels in a TSG on the instance's own runlist. Then the application serves traffic: cuLaunchKernel, pushbuffer write, doorbell ring, the instance's runlist scheduler grants the turn, the instance's work distributor deals thread blocks onto the instance's SM slices, and the GMMU translates every access into memory slices no neighbour can reach.

When a pod asks for a slice of a GPU, all the sharing has already happened by the time the doorbell rings: the scheduler chose the card, the device plugin named the instance, CDI mounted the device nodes, GSP-RM built the walls, and the launch itself travels a path that no sharing technology touches.

That sentence is the whole document. Every technology you met differs only in which walls get built at setup (scheduler turns, a merged context, silicon partitions, a virtual machine, a library's ledger) and never in the launch's runtime path, which has been the undisturbed launch path (diagram 2.1) since the launch-path chapter and never changed once.

Traps to respect

The ones that cost real incidents: MIG reshaping requires draining the affected instances, so plan partitions in advance; improvising them per pod does not work (DRA is changing exactly this, slowly). A time-sliced replica number is a promise your hardware never made. MPS between teams turns one team's bug into everyone's outage, unattributed. HAMi's nvidia-smi lies to the tenant by design; teach your users before they file tickets about the shrunken card. vGPU version-locks host and guest drivers, so an upgrade is a coordinated sequence of steps. And every family still shares one physical card: an Xid that announces the GPU fell off the bus takes every tenant down, so monitoring (the exporter for DCGM, NVIDIA's Data Center GPU Manager, which the GPU Operator ships) is not optional at any layer.

Where the field is going

Two currents worth watching from here. First, the scheduling brain is moving up: DRA went stable, NVIDIA's DRA driver can express MIG shapes as claims, and schedulers like KAI treat fractions, topology and preemption as first-class fleet problems; the direction is partitions created on demand for the pod that needs them. Second, the trust boundary is moving down: H100-class hardware added confidential computing modes that encrypt VRAM and attest firmware, aiming sharing at tenants who distrust not just each other but the operator. Both currents deepen the pattern you now know by heart: model the share in a scheduler, enforce it as low in the stack as the hardware allows.

Rerun the sidebars when it arrives, and the Try-it commands become your lab.
