Chapter 0 · Prologue

The chart, the skb, and the tracer

~13 min · LAB · Spine: our skb does not exist yet. Before it is born you need the one object you will follow, the map you already own, and the instruments that make the map move.

The chart is a map of hooks, and a hook is not a function

The netfilter packet-flow chart you have studied is correct, and it is complete for what it draws: the places where netfilter may look at a packet, in order, with the bridge layer below and the routing decisions between them. What it leaves out is everything that is not a hook. The chart says PREROUTING. The kernel says: ip_rcv validates the header, calls a hook macro that walks a list of registered functions, and, if the list says accept, calls ip_rcv_finish, which does the routing lookup that the chart draws as a diamond. The chart says bridging decision. The kernel says: a function pointer stored on the device, consulted from inside one loop, takes the packet away.

When a packet misbehaves, the chart tells you which hook to suspect. Only the functions tell you what to trace. This document is the chart with the function names filled in, and a tracer running next to it so you can watch the names go by in order, on your own kernel.

The one object: the skb

Everything in this document happens to one thing. An skb, short for socket buffer and spelled struct sk_buff in the source, is the kernel's description of one packet: a small block of metadata plus pointers into a separate data buffer that holds the bytes. The struct starts at include/linux/skbuff.h:886. Think of it as the shipping label clipped to a box. The label carries the routing state, the box carries the goods, and most of the kernel only reads and rewrites the label.

Five groups of fields decide where a packet goes, and you will see every one of them again:

FieldWhat it decidesLine in skbuff.h
skb->devWhich network device the packet belongs to right now. Every layer reads it, and virtual devices rewrite it. This one field is most of the veth chapter.894

The reference count matters more than it looks. When two consumers need the same packet, the kernel does not copy the bytes. It bumps the count, or it allocates a second label pointing at the same box. Which of those happens, and where, is a recurring question in chapters 3 and 10.

The stage: devices and namespaces

A net_device, struct net_device, is anything the kernel can hand a packet to: a NIC driver instance, the loopback device lo, one end of a veth pair, a bridge, a bond, a tunnel. Each one has a transmit function the core calls, named ndo_start_xmit in its operations table, and each one may install a receive handler, a function pointer the receive loop consults before it does anything else with a frame from that device. Bridges, bonds and macvlan are all built on that one pointer.

A network namespace, or netns, is a private copy of the whole networking state: its own devices, addresses, routing tables, netfilter tables and sockets. A device belongs to exactly one namespace at a time, so skb->dev also tells you which namespace a packet is in. A container is a process in a namespace whose only device is one end of a veth. The tracer prints the namespace as an inode number, and watching that number change is how you will see a packet cross into a container.

Hooks, and what calling one costs

A netfilter hook is one of five points in the IP code, PRE_ROUTING, LOCAL_IN, FORWARD, LOCAL_OUT and POST_ROUTING (the enum is at include/uapi/linux/netfilter.h:42), where the code calls nf_hook with the skb and a continuation function. Two gates stand before any list is walked (include/linux/netfilter.h:227 onward). First a global jump label, nf_hooks_needed, which is off until some module registers at that hook anywhere on the machine. Second the namespace's own list head for that hook, which is empty in a fresh namespace even on a heavily firewalled host. Only if both pass does nf_hook_slow (net/netfilter/core.c:612) walk the entries in priority order and act on each verdict: accept continues, drop frees the skb, stolen means the entry took the skb and the caller must forget it. Conntrack and NAT are entries on those lists with fixed priorities. That is all chapter 5 is: the lists, the priorities, and what the entries write into skb->_nfct.

The instruments

A kprobe is a breakpoint the kernel plants at the entry of a function; when the function is called, a small program runs and the function then continues. Every tool below is built on kprobes.

pwru, "packet, where are you", plants a kprobe on every kernel function that takes an skb argument. On this kernel that is 1,598 functions, and attaching them takes about a second. You give it a filter in tcpdump syntax; it prints one line each time a matching skb enters a probed function: the skb address, the CPU, the process, the netns inode, the mark, the interface, the protocol, the MTU, the length, the L4 tuple, and the function name. That line, repeated, is the trace you will read in every chapter. Two blind spots matter. It probes only functions built into the kernel image unless you add --kmods veth,bridge or --all-kmods, so a packet crossing a veth appears to jump over the driver until you ask for the module. And it cannot match a packet with no IP header, so unix sockets need the next tool.

bpftrace plants a kprobe on one function you name and runs a one-line program: count by device, print a stack, read a struct field. It is the tool for functions pwru does not cover, for driver internals that take no skb, and for anything in the socket layer.

nft monitor trace works inside netfilter. A rule that says meta nftrace set 1 sets one bit on the skb, skb->nf_trace (include/linux/skbuff.h:1013, written at net/netfilter/nft_meta.c:501), and from then on every chain the skb enters reports each rule it evaluates and the verdict. It shows the rule walk that pwru sees only as one function name.

ftrace with the function_graph tracer records every function call under a chosen root, with entry and exit timing. It is expensive and noisy, and it is the only tool here that shows the call tree rather than a flat list. You will use it once, in the next chapter, to watch an interrupt turn into a packet.

Recap

One object, the skb, is a label pointing at a buffer; its dev, protocol, mark and _nfct fields decide the path. Devices are anything with a transmit function, and some also install a receive handler. Namespaces are private copies of the networking state, identified in traces by inode. A netfilter hook is a list walked by nf_hook_slow, behind a global jump label and a per-namespace list head. pwru prints one line per skb per function; bpftrace fills its blind spots; nft trace shows the rule walk; ftrace shows the call tree.

Check yourself

1. You trace a packet crossing a veth pair and the function list jumps from dev_hard_start_xmit straight to __dev_forward_skb. There is no veth_xmit line. Has the kernel skipped the driver?

Answer

No. pwru probes only functions in the kernel image by default, and veth_xmit lives in the veth module. Re-run with --kmods veth and the line appears right after dev_hard_start_xmit, exactly where xmit_one calls the device's ndo_start_xmit (net/core/dev.c:3890).

The tempting wrong answer is "the compiler inlined it". Inlining does happen to small static helpers, but veth_xmit is the module's transmit entry and a real symbol in veth.ko. When a name is missing from a pwru trace, check whether it belongs to a module before you suspect the compiler.

2. Two processes talk over a unix socket. pwru with a filter of host 127.0.0.1 prints nothing, and neither does a filter on the port. Why, and what do you use instead?

Answer

pwru's filter is compiled from tcpdump syntax into a program that reads IP and L4 headers out of the skb data. A unix socket skb carries no IP header at all, so no filter can match it, even though the unix functions that handle it are probed. Use bpftrace on unix_stream_sendmsg or unix_dgram_sendmsg, which chapter 8 does.

The near miss is "there is no skb for unix sockets, so there is nothing to trace". There is an skb; unix_stream_sendmsg allocates one with sock_alloc_send_pskb (net/unix/af_unix.c:2423) and queues it straight onto the peer socket. What is missing is a network header, and that is what the filter needs.

3. A trace taken inside a freshly created namespace shows ip_rcv, ip_rcv_core, then ip_rcv_finish_core, with no nf_hook_slow between them. The host has hundreds of firewall rules. Is netfilter broken in that namespace?

Answer

No. nf_hook has two gates (include/linux/netfilter.h:227 onward). The global jump label nf_hooks_needed is on, because the host has hooks registered, so the first gate passes. The second gate reads the namespace's own net->nf.hooks_ipv4[hook] list head, and a fresh namespace has nothing registered there, so it is NULL and nf_hook_slow is never called. Load an nftables table into that namespace and the line appears.

The wrong answer is "netfilter is global, so the rules apply everywhere". Hook registration is per namespace; that is why a container can have its own firewall, and why a packet crossing a veth into a namespace with no tables walks no hooks there even though the host is firewalled.

Chapter 1

Birth of an skb: the NIC, the interrupt, NAPI, and the backlog

~13 min · HW · Spine: a frame carrying our TCP segment has just arrived at the network card. There is no skb yet. By the end of this chapter there is one, and it is standing at the door of the L2 receive loop.

This chapter skips link training, PHY negotiation, and the PCIe transaction layer. All real, all irrelevant here. It treats one Ethernet driver, igb for Intel gigabit cards, as the worked example, because its receive loop is short enough to read. Your laptop's Wi-Fi driver takes a longer road through the wireless stack and arrives at the same door; the last section shows where.

The ring: the card writes before anyone asks

The driver does not fetch packets. It prepares empty buffers in advance and the card fills them. The structure that holds this arrangement is the receive ring: a circular array of descriptors, each a small record with the physical address of one buffer and, after the card has used it, the length and status of the frame it wrote there. In igb the ring is struct igb_ring (drivers/net/ethernet/intel/igb/igb.h:319), with the descriptor array at desc, the ring size at count, and two indices: next_to_use, the next slot the driver will hand to the card, and next_to_clean, the next slot the driver expects the card to have filled. The gap between them is the number of frames waiting.

The card writes into those buffers by DMA, direct memory access: it moves bytes into RAM without the CPU touching them, then writes the length into the descriptor. The buffers come from a page pool, a per-ring recycling allocator that hands out page fragments already mapped for DMA, so the driver does not pay a mapping cost per frame. igb_alloc_rx_buffers (igb_main.c:9205) refills empty slots. When the ring is full of unread frames and the card has nowhere to write, it drops on the wire side and increments a counter you read with ethtool -S.

The interrupt does almost nothing

When a frame lands, the card raises an interrupt. The handler that runs, igb_msix_ring (igb_main.c:7153), is a hardirq: it executes with interrupts disabled on that CPU, so it must be short. It does one thing, at line 7160: napi_schedule_irqoff. That marks the ring's NAPI instance as needing service, adds it to this CPU's poll list, raises a software interrupt, and returns. The card's interrupt is left masked. No packet has been looked at.

NAPI, the "new API" that is now twenty years old, is the contract between drivers and the core. Instead of one interrupt per frame, the driver takes one interrupt, then polls the ring in a loop until it is empty or a quota is spent, and only then re-enables the interrupt. Under load the interrupt fires rarely and the CPU spends its time in the poll. Under light load each frame costs an interrupt plus a short poll. The quota per poll call is the NAPI weight, 64 by default.

The softirq: budgets and the poll

A softirq is deferred work that runs with interrupts enabled, either right after the hardirq returns or in the ksoftirqd kernel thread when there is too much of it. Networking receive is NET_RX_SOFTIRQ, and its handler is net_rx_action (net/core/dev.c:7920). It sets two limits at the top: a budget of packets, netdev_budget, default 300 (line 7926), and a time limit, netdev_budget_usecs, default 2,000 microseconds (line 7923). Then it takes NAPI instances off the poll list one at a time and calls napi_poll (line 7958), subtracting what each one processed. When the budget or the time is gone it stops, increments the time squeeze counter (lines 7964 to 7970, visible as the third column of /proc/net/softnet_stat), and re-raises itself so the rest is handled later.

For our ring, napi_poll calls the driver's poll function, igb_poll (igb_main.c:8278), which calls igb_clean_rx_irq with the weight as its budget (line 8300). That function is the loop that turns descriptors into skbs (igb_main.c:9016). Read its head, lines 9035 to 9058: refill the ring if enough slots have been consumed; read the descriptor at next_to_clean; if its length field is zero the card has not written it yet, so stop; otherwise issue a dma_rmb so the CPU does not read the buffer before it has read the length that says the buffer is ready.

The skb is born

Now the skb appears. igb_build_skb (igb_main.c:8664) allocates only the metadata block, through napi_build_skb, and points it at the page fragment the card already filled. The bytes are not copied. This is the general rule for modern drivers: the box was filled by DMA, and the driver only clips a label to it. igb_process_skb_fields (line 9131) fills in the label: skb->protocol from the Ethernet type through eth_type_trans (line 8929), the hardware checksum result, the receive hash, any VLAN tag. Then, at line 9133, the driver hands the skb to the core with napi_gro_receive.

That name is a small lie in 7.2. napi_gro_receive is now an inline wrapper (include/linux/netdevice.h:4311) around gro_receive_skb (net/core/gro.c:638), so when you trace it with bpftrace you probe the second name. What it does is GRO, generic receive offload: it holds back consecutive segments of the same TCP flow and merges them into one larger skb, so the rest of the stack does its work once per merged packet instead of once per wire frame. Merging is bounded at about 64 KB, and the merged skb keeps the original frames as a list of fragments. When a flow's merged skb is complete, or the poll is ending, gro_normal_one (include/net/gro.h:537) adds it to a per-NAPI list, and gro_normal_list (line 519) flushes that list into netif_receive_skb_list_internal after 8 skbs, the gro_normal_batch default.

netif_receive_skb_list_internal (net/core/dev.c:6420) is where the driver's world ends. It checks once whether receive packet steering wants this skb on another CPU (below), and otherwise calls __netif_receive_skb_list, which hands each skb to the L2 receive loop that chapter 3 is about.

The second door: netif_rx and the backlog

Not every skb arrives from a poll. Sometimes a piece of code already holding a fully formed skb wants the receive path to run on it: the loopback driver, a veth, a tunnel decapsulating an inner packet, a driver too old to have NAPI. For those there is netif_rx, and its variant __netif_rx for callers already in softirq context (net/core/dev.c:5778 and 5746). Both call netif_rx_internal (line 5706), and it calls enqueue_to_backlog (line 5381).

The backlog is a per-CPU queue, softnet_data.input_pkt_queue (include/linux/netdevice.h:3622), with a per-CPU fake NAPI instance attached to it, softnet_data.backlog (line 3624). enqueue_to_backlog checks the queue against netdev_max_backlog, default 1,000 (read at line 5396 as net_hotdata.max_backlog), drops if full, appends the skb (line 5414), and if the queue was empty schedules the fake NAPI (line 5413). From there the backlog is a device like any other: net_rx_action polls it, and its poll function is process_backlog (line 6658), which splices the input queue into a processing queue (line 6704) and calls __netif_receive_skb on each skb (line 6680). So netif_rx is not a way around NAPI. It is NAPI with a software queue in front and no hardware behind.

Keep that shape in mind. When chapter 9 shows a packet entering the far end of a veth, the trace will read __netif_rx, netif_rx_internal, enqueue_to_backlog, then __netif_receive_skb. Every one of those names is on this page.

Which CPU: RSS and RPS

RSS, receive side scaling, is the card's job: it hashes each frame's addresses and ports and picks one of several rings, each with its own interrupt and NAPI instance, so flows spread across CPUs while each flow stays on one. RPS, receive packet steering, is the software copy of the same idea for cards with one ring: in netif_receive_skb_list_internal and in netif_rx_internal, get_rps_cpu (lines 6438 and 5721) may pick another CPU, in which case the skb goes to that CPU's backlog through enqueue_to_backlog and an inter-processor interrupt wakes it. That is the one case where a frame from a real NIC shows enqueue_to_backlog in a trace, and it is a diagnostic worth remembering.

Your NIC is a Wi-Fi card

The mt76 driver behind mt7921e uses NAPI too: mt76_dma_rx_poll (drivers/net/wireless/mediatek/mt76/dma.c:1073) is its poll function. But a Wi-Fi frame is not an Ethernet frame; it goes through the mac80211 stack first, which decrypts it and rewrites the 802.11 header into an Ethernet header. The skb re-enters the core in mt76_rx_complete (mac80211.c:1514), through napi_gro_receive at line 1550 when a NAPI instance is attached and through netif_receive_skb_list at line 1544 when one is not. Same door, longer corridor. Everything from this chapter's third section onward is identical.

Recap

The card fills pre-posted buffers by DMA and records lengths in ring descriptors. The hardirq only schedules NAPI. net_rx_action polls under a budget of 300 packets and 2 ms, calling each driver's poll with weight 64. The poll builds skbs around the filled buffers without copying and hands them to GRO, which merges same-flow segments and flushes batches into netif_receive_skb_list_internal. Callers that already hold an skb use netif_rx, which queues into the per-CPU backlog and gets polled the same way. RPS uses that same backlog to move frames between CPUs.

Check yourself

1. Predict the value: a burst of 1,000 frames sits in one ring with weight 64 and default budgets. How many times does igb_poll run inside the first net_rx_action, and how many net_rx_action runs does the burst need?

Answer

Five polls in the first run, and four runs in total. net_rx_action subtracts each poll's work from a budget of 300 and stops when the budget is zero or negative (net/core/dev.c:7958 to 7966): 300 minus 64 four times leaves 44, still positive, so a fifth poll runs and takes the budget to minus 20, then the loop breaks. Five polls of 64 is 320 frames per run; 1,000 frames need three full runs (960) plus one short run.

The near miss is "four polls, because four times 64 is 256 and a fifth would exceed 300". The check is on the budget after the poll, so a poll is allowed to overshoot. Each break also increments time_squeeze, so this burst leaves that counter three higher in /proc/net/softnet_stat.

2. A trace of a packet arriving on your wired Ethernet card shows enqueue_to_backlog and process_backlog before __netif_receive_skb. Nothing in the driver calls netif_rx. What happened?

Answer

Receive packet steering moved the frame to another CPU. netif_receive_skb_list_internal asked get_rps_cpu (net/core/dev.c:6438), it chose a different CPU, and the skb was queued into that CPU's input_pkt_queue by enqueue_to_backlog (line 6444); the far CPU's process_backlog then delivered it. Check /sys/class/net/eth0/queues/rx-0/rps_cpus; a non-zero mask confirms it. The pwru CPU column also changes between the two lines.

The wrong answer is "the driver is a legacy driver without NAPI". Those exist, but you would see netif_rx or netif_rx_internal in the trace before enqueue_to_backlog, and the RPS path does not pass through them.

3. Predict the value: you download 1 MB over TCP with a 1,448-byte payload per segment. Roughly how many skbs does the driver's poll hand to the core with GRO on, and how many with GRO off?

Answer

About 720 with GRO off, and at best around 16 with GRO on. One megabyte at 1,448 bytes per segment is about 724 segments, and with GRO off each becomes its own skb and its own trip through the stack. GRO merges up to about 64 KB per skb (gro_receive_skb, net/core/gro.c:638), so 1,048,576 divided by 65,536 is 16 merged skbs at the ideal. Real numbers land in between, because a merge is flushed whenever the poll ends or a segment arrives out of order.

The near miss is counting GRO as a hardware feature you cannot turn off. It is software in the poll loop, toggled with ethtool -K DEV gro off, and turning it on for a veth is how chapter 9 flips that device into a different receive mode.

Chapter 2

XDP: the hook that runs before the skb exists

~12 min · BPF · Spine: our skb is about to be built inside the driver's poll. One program type is allowed to see the frame before that happens, and it is the reason a packet can be dropped for almost nothing. The veth chapter depends on what this one says about copying, so we take the detour now.

A program on the raw buffer

XDP, the eXpress Data Path, is a BPF program type that a driver runs on a received frame while the frame is still just bytes in a DMA buffer. The program does not receive an skb, because none has been allocated. It receives an xdp_buff (include/net/xdp.h:86): pointers to the start and end of the frame data, a pointer to a small metadata area in front of the data, the size of the buffer, and a reference to the receive queue it came from. That is the whole world the program can see.

It returns one of five verdicts, the enum xdp_action at include/uapi/linux/bpf.h:6576. XDP_PASS lets the driver continue and build the skb. XDP_DROP hands the buffer straight back to the ring for reuse. XDP_TX sends the same buffer back out of the same device, which is how a load balancer answers from the card. XDP_REDIRECT hands the buffer to another device, another CPU, or a user-space socket. XDP_ABORTED is a drop that also fires a tracepoint, meant for program errors.

Here is the absence list, and it is the reason XDP exists. At the moment the program runs there is no skb, no protocol field, no device lookup, no namespace check, no tap, no tc, no netfilter hook, no route, no socket. A frame dropped by XDP has cost the card one DMA write and the CPU one descriptor read and one program run. Everything in chapters 3 to 7 has been skipped. This is wonderful for a flood filter and useless for anything that needs to know what the packet means to a socket.

Three places to attach the same program

The same program object can be attached in three modes, chosen with ip link set dev DEV xdp, xdpgeneric or xdpoffload, all routed through dev_xdp_install (net/core/dev.c:10327).

Native XDP means the driver itself calls the program from inside its poll, on the DMA buffer, before it builds an skb. In igb that call sits in the receive loop of chapter 1, between reading the descriptor and igb_build_skb. Only drivers written for it support it. Offloaded XDP means the card's own processor runs the program and the host never sees dropped frames at all; a handful of cards do this. Generic XDP is the fallback for every other device: the skb is built as usual, and the core runs the program on it at the very top of the L2 receive loop, at net/core/dev.c:6023 to 6035, through do_xdp_generic (line 5670).

Generic mode has to fake the environment native mode gets for free. netif_receive_generic_xdp (line 5590) pushes the Ethernet header back into view (line 6604), then checks whether the skb is cloned, is not linear, or has less than XDP_PACKET_HEADROOM, 256 bytes, of free space in front of the data (lines 5607 to 5610). If any of those hold, netif_skb_check_for_xdp (line 5565) calls pskb_expand_head and skb_linearize (lines 5575 to 5588), which allocate a new head buffer and copy the bytes into it. Only then does bpf_prog_run_generic_xdp run. So generic XDP can be slower than no XDP: the program is cheap, the copy that makes room for it is not. On the veth bench the trace reads exactly that way: __netif_receive_skb_one_core, pskb_expand_head, skb_release_data, bpf_prog_run_generic_xdp, then the tc and IP stations of chapter 3.

One consequence of the position matters for debugging. Generic XDP runs at line 6026, and the tap loop that feeds tcpdump starts at line 6048. A frame dropped by a generic XDP program is never seen by tcpdump on that device. Native XDP drops are invisible even earlier.

Redirect: leaving without an skb

XDP_REDIRECT is the verdict that turned XDP from a filter into a forwarding plane. The program calls the bpf_redirect or bpf_redirect_map helper (net/core/filter.c:4717) naming a target, and after the program returns, the driver calls xdp_do_redirect (line 4593). That function first converts the xdp_buff into an xdp_frame (include/net/xdp.h:294, conversion at line 430), a compact record stored in the buffer's own headroom so the frame can be queued without allocating anything. Then it looks at the target type.

A devmap target (kernel/bpf/devmap.c:552) queues the frame for another device's transmit function, so a frame can enter one card and leave another with no skb ever existing. A cpumap target (kernel/bpf/cpumap.c:793) queues the frame for another CPU, where a kernel thread builds an skb from it with xdp_build_skb_from_frame (net/core/xdp.c:849) and enters the normal receive path there. That is receive packet steering done before the skb rather than after it. An AF_XDP socket target copies or maps the frame into a user-space ring, and the kernel network stack never touches it again; that is the kernel-bypass path, and this document only names it.

Native XDP on a veth: the copy you did not order

A veth supports native XDP, and this is where the chapter earns its place in the spine. A veth does not receive DMA buffers; it receives skbs from its peer. So to run a native XDP program it must turn an skb into an xdp_buff, and it does so in veth_xdp_rcv_skb (drivers/net/veth.c:790) by calling veth_convert_skb_to_xdp_buff (line 751). Read the test at the top of that function, lines 758 to 760: if the skb is shared, if its head is locked, if it is not linear, or if it has less than 256 bytes of headroom, then skb_pp_cow_data (net/core/skbuff.c:942) allocates a fresh page-pool buffer, copies the bytes into it, builds a new skb around it with napi_build_skb, copies the header fields across, and frees the old skb with consume_skb.

A TCP segment always trips that test. TCP transmits a clone of the skb it keeps for retransmission (net/ipv4/tcp_output.c:1563), and a clone's head is locked because the data is shared with the original. So on the bench, with our program attached natively to the receiving end, the trace shows the first skb entering veth_xdp_rcv_skb and dying four lines later in kfree_skbmem. The XDP program line then appears against an address that matches no skb, because it is the address of the xdp_buff. And a second skb, with a new address, appears at eth_type_trans and continues through gro_receive_skb into the stack. Hold on to this. It is the one case in which a veth creates a new skb, and chapter 9 will point back here.

Recap

XDP runs a BPF program on an xdp_buff before any skb exists, and returns pass, drop, transmit, redirect or abort. Native mode runs it in the driver poll on the DMA buffer; generic mode runs it at the top of the L2 loop, after building the skb and after copying its head if the headroom is short; offload runs it on the card. Redirect converts the buffer to an xdp_frame and queues it to another device, another CPU, or a user-space socket. On a veth, native XDP converts the incoming skb and, for any cloned skb, copies it into a page-pool buffer and builds a new skb, freeing the old one.

Check yourself

1. A colleague attaches a generic XDP program that drops all UDP to port 53 on eth0, then runs tcpdump -i eth0 port 53 to confirm and sees nothing at all, including the queries that should be arriving. They conclude the program is dropping everything. What is the mistake?

Answer

The program may be working exactly as written; tcpdump cannot see what generic XDP drops. Generic XDP runs at net/core/dev.c:6023 to 6035, and the tap loop that feeds tcpdump starts at line 6048, after it. A dropped frame never reaches the taps. To confirm the drop, read the program's own counters with bpftool map dump, or use pwru --filter-trace-xdp, which prints the program run and its verdict.

The near miss is "tcpdump sees everything the NIC receives because it runs at L2". It sees everything that reaches the tap loop. Native and generic XDP both sit before it, and so does a hardware drop.

2. Predict the value: a TCP segment crosses a veth pair whose receiving end has a native XDP program attached. How many skbs are allocated for that segment on the receive side, and which line of code decides it?

Answer

One new skb, so two in total counting the one that arrived. veth_convert_skb_to_xdp_buff (drivers/net/veth.c:758 to 760) tests whether the skb is shared, head-locked, non-linear or short on headroom. A TCP segment is transmitted as a clone (net/ipv4/tcp_output.c:1563), and a clone's head is locked, so the test passes and skb_pp_cow_data (net/core/skbuff.c:942) builds a new skb and frees the old one with consume_skb.

The near miss is "zero, because the program returned PASS and nothing was dropped". The copy is not about the verdict. It happens before the program runs, to give it a private, linear, roomy buffer. An ICMP echo from ping is not cloned and has enough headroom, so it would pass the test and keep its skb.

3. In a pwru trace with --filter-trace-xdp, the line naming the XDP program carries an address that appears nowhere else in the trace, before or after. Is the tracer confused?

Answer

No. pwru's first column is the address of the object passed to the probed function. For every kernel function that is an skb. For an XDP program it is the xdp_buff, because at that moment there is no skb to print. On a veth the buffer lives on the stack of veth_xdp_rcv_skb (drivers/net/veth.c:790, the vxbuf local), so its address is reused by every frame and matches no skb group.

The near miss is treating the address as a new skb and concluding that XDP allocated one. XDP allocates nothing. The new skb, when there is one, is built afterwards by skb_pp_cow_data and shows up as its own group starting at eth_type_trans.

Chapter 3

L2 receive: taps, tc ingress, the receive handler, and the protocol demux

~13 min · L2 · Spine: our skb has come through one of the two doors and reached __netif_receive_skb_core. This chapter is that single function, station by station. When it ends, the skb is in the hands of ip_rcv.

One function, six stations

Every frame the kernel receives, from a NIC, a veth, the loopback device or a tunnel, passes through __netif_receive_skb_core (net/core/dev.c:5986). It is about two hundred lines long and its shape is a loop with a label at the top, another_round (line 6017), that two of the stations jump back to after rewriting skb->dev. The stations, in order:

The receive handler comes before the protocol demux, so a bridge port's frames never reach the host's IP layer unless the bridge itself hands them up. Diagram 0.1 drew this as one box called "L2 receive"; the rest of the chapter opens the box.

Taps: how tcpdump gets its copy

A packet socket, socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ALL)), registers a packet type handler on the ptype_all list, either the namespace's list or a single device's list if the socket is bound to one. You can see the registration: /proc/net/ptype in the bench namespace reads ALL vb packet_rcv while the tap is open. The loop at lines 6048 to 6057 walks both lists and calls deliver_skb (line 2486) for each entry. deliver_skb does not clone. It increments skb->users and calls the handler; the handler, packet_rcv, makes its own clone with skb_clone for the socket's receive queue and drops its reference. The trace on the bench reads deliver_skb, packet_rcv, skb_push, skb_clone, consume_skb, and then the original skb carries on to the next station with the same address.

Promiscuous mode is a different mechanism that people fold into the same word. It is a device flag, IFF_PROMISC, that tells the card to accept frames whose destination MAC is not its own. tcpdump turns it on by default. Such a frame arrives at the taps like any other, but eth_type_trans has set skb->pkt_type to PACKET_OTHERHOST, and ip_rcv_core drops it on that field at net/ipv4/ip_input.c:508, after the taps have had their copy. So tcpdump sees the neighbour's traffic and the local IP stack never does.

Transmit has a mirror tap. xmit_one (net/core/dev.c:3878) calls dev_queue_xmit_nit (line 2549) right before it calls the driver, and that function does clone (line 2575). Two consequences: tcpdump's timestamp for an outgoing packet is taken just before the driver, after any queueing, not when the application sent it; and a frame dropped by tc on egress, which runs much earlier in the device transmit function (net/core/dev.c:4812), is never seen by tcpdump on the sending device. Ingress taps see tc drops; egress taps do not.

tc ingress: two mechanisms, one station

tc ingress is the station at lines 6062 to 6070, compiled in under CONFIG_NET_INGRESS and skipped by a static key until some device has an ingress attachment. The function is sch_handle_ingress (line 4465), and it hosts two mechanisms that run in a fixed order. First tcx, the BPF link attachment point added in Linux 6.6: a per-device array of BPF programs run in sequence by tcx_run (line 4444), each returning a code that says continue to the next program or stop with a verdict. Second, only if every tcx program said TC_ACT_UNSPEC (lines 4484 to 4491), the classic tc chain: tc_run walks the filters attached to the device's clsact, the holder object for classic ingress and egress filters, through tcf_classify, and each matching filter runs its actions. A matchall filter with a pass action, the simplest possible, appears in the trace as tc_run, tcf_classify, mall_classify, tcf_action_exec, tcf_gact_act. BPF programs attached the classic way, with tc filter add ... bpf, live in this second chain as a cls_bpf filter.

The tc verdict decides what the station does with the skb. TC_ACT_OK continues to the next station. TC_ACT_SHOT frees the skb. TC_ACT_REDIRECT means a program has already handed the skb to another device with the bpf_redirect helper, and the loop must let go of it; this is the verdict Cilium's programs return when they move a packet straight into a pod's veth, and chapter 14 shows the whole path. TC_ACT_RECLASSIFY and a device rewrite jump to another_round (line 6070). Egress has the same station in the device transmit function, sch_handle_egress (net/core/dev.c:4529), with the same tcx-first ordering (lines 4543 to 4549).

VLAN and the receive handler: rewrite the device and go around again

Two stations share one trick. vlan_do_receive (line 6091) checks whether the frame carries an 802.1Q tag, or whether the card stripped one into the skb's metadata. If so it finds the VLAN sub-device for that tag, sets skb->dev to it, strips the tag, and jumps to another_round. The frame is now "from" the VLAN device, and the taps run again for it, which is why tcpdump on eth0.100 and on eth0 both see the frame.

The receive handler station (lines 6097 to 6116) is the one you met in the prologue: rx_handler = rcu_dereference(skb->dev->rx_handler). A device gets one when a bridge, bond, macvlan, ipvlan or team driver claims it through netdev_rx_handler_register. Any tap that was still pending is delivered first (lines 6099 to 6102), so tcpdump on a bridge port sees the frame before the bridge does. Then the handler runs and returns one of four codes. RX_HANDLER_CONSUMED: the handler owns the skb now, and the loop exits; this is a bridge forwarding a frame to another port, and the host's IP stack is never involved. RX_HANDLER_ANOTHER: the handler rewrote skb->dev, typically to the master device, and the loop jumps to another_round; this is a bond or a macvlan presenting the frame as its own. RX_HANDLER_EXACT: continue, but deliver only to protocol handlers bound to this exact device. RX_HANDLER_PASS: continue as if there were no handler. Chapters 10 to 12 are, mechanically, three different bodies for this one function pointer.

The demux: picking the L3 handler

The last station hands the skb to L3. deliver_ptype_list_skb (lines 6160 to 6177) looks up skb->protocol in the ptype_base hash: 0x0800 maps to ip_rcv, 0x0806 to arp_rcv, 0x86dd to ipv6_rcv, all visible in /proc/net/ptype. The loop uses a small trick worth knowing because it shapes traces: it does not call each handler as it finds it. It remembers the previous match in pt_prev and delivers it only when it finds the next one, so the last handler receives the skb without a reference-count bump and owns it outright. If no handler matches, the skb is freed with a drop reason of unhandled protocol.

One more shape appears in traces and confuses people. When the skb arrived through the GRO door as part of a batch, the core uses the list variant of this loop, groups the skbs by protocol, and calls ip_list_rcv instead of ip_rcv. pwru cannot probe a function whose argument is a list rather than an skb, so such a trace shows ip_rcv_core with no ip_rcv before it. The native XDP trace of chapter 2 had exactly that shape. Same code, different door.

Recap

__netif_receive_skb_core is a loop of six stations. Generic XDP first. Then the taps, where packet sockets get a clone and promiscuous frames are seen before IP drops them. Then tc ingress, tcx programs before classic filters, whose verdict can drop, redirect or loop. Then VLAN untagging and the receive handler, both of which may rewrite skb->dev and go around again, or, for a bridge, take the frame out of the loop entirely. Last, the protocol demux by skb->protocol to ip_rcv. Egress has a mirror tap and a mirror tc station, in the opposite order, so egress tc drops are invisible to tcpdump.

Check yourself

1. You add tc filter add dev vb ingress matchall action drop. Does tcpdump -i vb still show the dropped frames? Then you move the same drop to egress on the sender's device va. Does tcpdump -i va show them?

Answer

Yes on ingress, no on egress. On receive the tap loop (net/core/dev.c:6048 to 6057) runs before sch_handle_ingress (line 6067), so the packet socket has cloned the frame before tc drops it. On transmit the order is reversed: sch_handle_egress runs inside the device transmit function at net/core/dev.c:4812, and the transmit tap dev_queue_xmit_nit is called much later from xmit_one at line 3885, just before the driver. A frame dropped by egress tc never reaches the tap.

The near miss is assuming symmetry, "tcpdump is at L2 so it sees both". The two taps are at different depths on purpose: receive taps see what arrived, transmit taps see what is about to leave.

2. A pwru trace of a frame arriving on a bond slave shows deliver_skb, packet_rcv, then bond_handle_frame, then deliver_skb and packet_rcv again, then ip_rcv. Two tcpdump processes are running. Which devices are they bound to, and why did the frame pass the taps twice?

Answer

One is bound to the slave, one to the bond. The bond's receive handler returned RX_HANDLER_ANOTHER after setting skb->dev to the bond device, and the loop jumped to another_round (line 6107 to 6017). On the second pass the frame is "from" the bond, so the bond's per-device tap list matches and the bond-bound packet socket gets its clone. The slave-bound socket got its clone on the first pass, before the handler ran, because pending taps are delivered at lines 6099 to 6102 before the handler is called.

The near miss is "the frame was duplicated". It is the same skb, same address in the trace, going around the loop twice under two names. Each pass produced one clone for one socket.

3. A frame arrives on a bridge port. Its destination MAC belongs to a host on another port. Trace the path through the stations of this chapter and say which station the frame never reaches.

Answer

Generic XDP if attached, then the taps on the port device, then tc ingress on the port, then the receive handler, which is br_handle_frame because the port is enslaved to the bridge. The bridge looks up the destination MAC, forwards the frame out the other port, and returns RX_HANDLER_CONSUMED (line 6104), so the loop exits. The frame never reaches the protocol demux at lines 6160 to 6177, and ip_rcv never runs for it in the bridge's namespace. Chapter 10 traces the forwarding half.

The near miss is "the bridge forwards after IP has seen it, because the netfilter chart shows bridge and IP hooks together". The chart's IP hooks appear on a bridged path only when the br_netfilter module is loaded, and even then they are called from inside the bridge code, not from ip_rcv.

Chapter 4

L3 receive: ip_rcv, PREROUTING, and the routing decision

~12 min · L3 · Spine: the protocol demux has handed our skb to ip_rcv. This chapter walks the IP receive path up to the routing decision, and then through whichever of two doors it opens: local delivery towards a socket, or forwarding back out.

The checks, and the moment the sender lets go

ip_rcv (net/ipv4/ip_input.c:603) is four lines: call ip_rcv_core, then call the PRE_ROUTING hook with ip_rcv_finish as the continuation (lines 612 to 614). The work is in ip_rcv_core (line 499). It drops frames marked PACKET_OTHERHOST (line 508), the promiscuous leftovers of chapter 3. It makes sure the first 20 bytes are readable (line 523), checks version 4 and a header length of at least five words (line 539), pulls the options if the header is longer (line 549), verifies the header checksum (line 554), and trims the skb to the IP total length. Then it wipes the 48 bytes of scratch space, skb->cb, for IP's own use.

And then, at lines 581 to 583, under the comment "Must drop socket now because of tproxy", it calls skb_orphan. That runs the skb's destructor, which is the sending socket's accounting callback: tcp_wfree for a data segment, sock_edemux for a SYN-ACK built before the connection is fully open (net/ipv4/tcp_output.c:3958). This is the tcp_wfree line you have seen in every trace so far, right after ip_rcv_core. It says something worth knowing: on a veth or on lo, the skb still belonged to the sender's socket until the receiver's IP layer ran, and the sender's send buffer is credited back only here. On a real NIC the driver did this when the card finished sending, long before.

When the skb arrived through the GRO door in a batch, the same steps happen through ip_list_rcv (line 687), which calls ip_rcv_core per skb and then the hook once for the whole list with NF_HOOK_LIST (line 679). That is why a trace from a NAPI device shows ip_rcv_core with no ip_rcv before it.

PRE_ROUTING, as a black box for one more chapter

Between ip_rcv_core and ip_rcv_finish sits the PRE_ROUTING hook. In the fresh namespace of the veth bench the trace goes straight from ip_rcv_core to ip_rcv_finish_core; in the router namespace with one nftables table loaded, eleven function names appear in between. Chapter 5 opens that box. One fact about it belongs here because it shapes the routing decision: every entry in the hook runs before the route lookup. An entry may rewrite the destination address, and the lookup that follows sees the rewritten one. That single ordering is why the chart puts destination NAT in PREROUTING, before the routing diamond.

The routing decision is a function pointer

ip_rcv_finish (line 478) first offers the skb to a VRF master if the incoming device has one, through l3mdev_ip_rcv (line 486); with no VRF this returns the skb untouched, and chapter 11 is where it does not. Then ip_rcv_finish_core (line 361) tries a shortcut, early demux (lines 376 to 400): if net.ipv4.ip_early_demux and tcp_early_demux are on, tcp_v4_early_demux (line 322) looks up an established TCP socket by the four-tuple before any routing happens, and if it finds one, attaches that socket's cached route to the skb so the lookup below is skipped. In the loopback trace this shows as two inet_lhash2_lookup lines before ip_rcv_finish_core: the SYN found only a listener, so the shortcut did nothing, and the full lookup ran.

The full lookup is ip_route_input_noref (line 407), which reaches ip_route_input_slow (net/ipv4/route.c:2286). The name is historical. The route cache it was slow compared to was removed in Linux 3.6, and this is now the normal path for every packet that early demux did not catch. It calls fib_lookup (line 2380), which walks the policy rules that ip rule shows to pick a table (fib4_rule_match, net/ipv4/fib_rules.c:180), then does a longest-prefix match in that table's FIB, the forwarding information base, stored as a level-compressed trie (fib_table_lookup, net/ipv4/fib_trie.c:1420). What comes back is a route type, and the type decides everything.

RTN_LOCAL (checked at line 2397): the destination is one of this host's own addresses, on any interface. The source is validated against reverse-path rules, fib_validate_source, the two lines you see in every trace, and the code jumps to local_input (line 2437), which allocates the route entry with RTCF_LOCAL set, so that rt_dst_alloc (line 1670) stores ip_local_deliver as its input function (line 1693). RTN_UNICAST: the destination is somewhere else. First the forwarding switch is checked, at lines 2405 to 2407: if net.ipv4.ip_forward, or the per-device forwarding sysctl, is off, the packet gets a route whose input function is ip_error. Otherwise ip_mkroute_input leads to __mkroute_input (line 1908), which stores ip_forward as the input function (line 1918).

The result is a dst_entry, the route object, attached to the skb and readable as skb_dst(skb). It carries two function pointers, input and output, and the next hop. When ip_rcv_finish regains control it calls dst_input(skb) (include/net/dst.h:478), which is nothing more than skb_dst(skb)->input(skb). That indirect call is the routing diamond on the chart. The decision was made when the pointer was stored; the diamond is just the call.

Door one: local delivery

ip_local_deliver (net/ipv4/ip_input.c:250) reassembles fragments if the packet is one, then calls the LOCAL_IN hook with ip_local_deliver_finish (line 229) as the continuation. That reaches ip_protocol_deliver_rcu (line 189), which first offers the packet to any raw sockets, raw_local_deliver, then looks up the transport protocol number in inet_protos (line 198) and calls its handler (line 205): tcp_v4_rcv, udp_rcv or icmp_rcv. Watch the length column in a trace at this point. It drops from 60 to 40 for a SYN, because the 20-byte IP header has been pulled and skb->data now points at the TCP header. Chapter 7 picks the skb up there.

Door two: forwarding

ip_forward (net/ipv4/ip_forward.c:83) checks the TTL first (line 118) and answers with an ICMP time exceeded if it is one or less. Then, at line 144, it calls skb_cow: before writing to the header, make sure this skb owns its head privately and has room for the outgoing link-layer header. A TCP segment fails that test, because TCP transmits a clone of the skb it keeps for retransmission (net/ipv4/tcp_output.c:1563), and the clone shares its head with the original. So the router trace shows pskb_expand_head, skb_release_data and skb_headers_offset_update between ip_forward and the FORWARD hook: the header is copied so it can be modified. Then ip_decrease_ttl (line 149), then the FORWARD hook (lines 162 to 164) with ip_forward_finish (line 65) as the continuation, which calls dst_output (line 80): skb_dst(skb)->output, which rt_dst_alloc set to ip_output (route.c:1691). From there the packet is on the transmit path of chapter 6, joining it at the POST_ROUTING hook. No socket was involved. The FORWARD hook is the only place a firewall on this host sees transit traffic.

And when forwarding is off, ip_error (route.c:990) receives the packet instead. Its first branch is for exactly this case: it increments IpInAddrErrors and frees the skb, and it does not send an ICMP error. The client sees nothing and retransmits until it gives up. The bench trace ends with ip_route_input_slow, ip_error, then sk_skb_reason_drop(SKB_DROP_REASON_IP_INADDRERRORS), because pwru prints the drop reason when a function frees the skb.

Recap

ip_rcv_core validates the header and orphans the skb from the sending socket. The PRE_ROUTING hook runs before any route lookup. ip_route_input_slow consults policy rules and the FIB trie and stores one of three input functions in the route: ip_local_deliver for a local address, ip_forward for a remote one when forwarding is on, ip_error when it is off. dst_input is the indirect call through that pointer. Local delivery passes the LOCAL_IN hook and hands the skb to the transport handler. Forwarding checks the TTL, copies a shared header, decrements the TTL, passes the FORWARD hook and calls the route's output function, ip_output.

Check yourself

1. Predict the outcome: the router has net.ipv4.ip_forward=0 and the nftables table of the lab loaded. A client sends a SYN through it. Which chains see the packet, where does it die, and what does the client observe?

Answer

The PRE_ROUTING chains see it; the FORWARD chain never does; the client gets no answer and times out. The forwarding switch is tested inside ip_route_input_slow at net/ipv4/route.c:2405, after the hook has already run, and it makes the route's input function ip_error (line 990). ip_error's first branch, for an incoming device with forwarding disabled, increments IpInAddrErrors and frees the skb without sending ICMP. The trace ends at ip_error with drop reason IP_INADDRERRORS; the nftables forward chain counters do not move.

The near miss is "the router sends ICMP host unreachable". It does that only when forwarding is on and the lookup finds no route. With forwarding off the drop is silent, which is exactly what makes a forgotten sysctl hard to diagnose from the client side.

2. Every trace of a packet arriving over a veth or over lo shows tcp_wfree immediately after ip_rcv_core, in the receiver's namespace. Traces of packets arriving from a real NIC never show it. What does the line mean, and why the difference?

Answer

It is the sender's socket releasing its send-buffer accounting for that skb. ip_rcv_core calls skb_orphan at net/ipv4/ip_input.c:583, which runs the skb's destructor, and a TCP data skb's destructor is tcp_wfree. On a veth or on lo the skb is the very same object the sender's TCP built, handed across with skb->sk still set, so the orphan happens here, in the receiver's IP layer. A frame from a real NIC was built by the driver in chapter 1 and never had an owning socket; the sender's copy was orphaned by the sender's driver once the card had sent it.

The near miss is reading it as "the receiver is freeing the packet". Nothing is freed; the skb continues into ip_rcv_finish_core on the next line. Only the ownership link is cut.

3. In the router trace, every forwarded TCP segment shows pskb_expand_head right after ip_forward, but forwarded ICMP echo requests from ping do not. What is the router copying, and why only for TCP?

Answer

The skb head, so it can write the decremented TTL into a private copy. ip_forward calls skb_cow at net/ipv4/ip_forward.c:144 before ip_decrease_ttl at line 149. skb_cow reallocates when the head is shared or headroom is short. A TCP segment is a clone made by __tcp_transmit_skb (net/ipv4/tcp_output.c:1563), sharing its head with the copy TCP keeps for retransmission, so it is always shared here. An echo request from ping is built once and sent once, is not cloned, and has ample headroom, so skb_cow does nothing.

The near miss is "the veth strips headroom". The headroom is fine; the test that fails is skb_cloned. The same copy happens on a real router with real NICs, for the same reason.

Chapter 5

Netfilter and conntrack: hooks, priorities, tuples, and NAT

~13 min · L3 · Spine: our skb is inside the PRE_ROUTING call that chapter 4 treated as a black box. This chapter opens it: what nf_hook_slow walks, in what order, and what conntrack and NAT write into the skb and into their own tables before the routing decision runs.

The list, and the numbers that order it

Chapter 0 showed the two gates in front of a hook. When both pass, nf_hook_slow (net/netfilter/core.c:612) walks an array of hook entries, each a function pointer and a priority, sorted by priority when the array is rebuilt on registration (nf_hook_entries_grow, line 97). The loop at lines 620 to 640 calls each entry and acts on its verdict: accept moves to the next entry; drop frees the skb with reason NETFILTER_DROP and returns; queue sends the skb to a user-space program and returns; stolen returns without freeing, because the entry now owns the skb. When the loop runs out of entries the macro that called it runs the continuation, ip_rcv_finish for PRE_ROUTING.

The priorities are plain integers, and the whole "raw, mangle, nat, filter" order of the chart is just these numbers from include/uapi/linux/netfilter_ipv4.h:29 to 45:

At PRE_ROUTING on r0 the SYN visits, in order: ipv4_conntrack_defrag, then nft_do_chain_inet for the lab's raw chain, then ipv4_conntrack_in, then nf_nat_ipv4_pre_routing, then nft_do_chain_inet again for the filter chain. An nftables chain is one entry

Each nftables base chain, a chain declared with a hook and a priority, is registered as one entry whose function is nft_do_chain_ipv4 or nft_do_chain_inet (net/netfilter/nft_chain_filter.c:15). It calls nft_do_chain (net/netfilter/nf_tables_core.c:250), which walks the rules (line 275), evaluates each rule's expressions, and acts on the rule's verdict: continue to the next rule, accept or drop the packet, or jump to another chain and come back through a small stack (line 322). When the walk finishes without a verdict, the chain's policy applies.

This is the layer nft monitor trace shows. A rule containing meta nftrace set 1 sets the bit at skb->nf_trace (net/netfilter/nft_meta.c:501), and every chain the skb enters afterwards reports through nft_trace_packet (lines 297 and 340) and nft_trace_notify (net/netfilter/nf_tables_trace.c:238). The bench output for one SYN reads, one line per event: the raw chain saw the packet on r0; the rule that set the trace bit matched with verdict continue; the raw chain's policy was accept; the prerouting chain's policy was accept; the forward chain saw it with iif r0 oif r1; the rule ct state new counter matched; and so on through postrouting. pwru saw those chains as five nft_do_chain_inet lines. The two tools are looking at the same walk from two altitudes.

Conntrack: a tuple, an entry, and a pointer in the skb

The entry at minus 200 is ipv4_conntrack_in (net/netfilter/nf_conntrack_proto.c:208), which calls nf_conntrack_in (net/netfilter/nf_conntrack_core.c:2004). Its first move (lines 2011 to 2018) is to check whether the skb already carries a conntrack pointer; a packet that has been through this hook before, for example one that came back in through lo, is accepted without a second lookup. Otherwise resolve_normal_ct (line 1862) builds the tuple: source and destination address, protocol, source and destination port (nf_ct_get_tuple, line 1876), and looks it up in the conntrack hash table.

On a miss, init_conntrack (line 1898) allocates a conntrack entry, struct nf_conn (include/net/netfilter/nf_conntrack.h:74). The entry holds two tuples in tuplehash (line 96): the original direction, and the reply tuple, which starts as the original with source and destination swapped and is what a returning packet will be matched against. It also holds a status bitmap (line 99) and a timeout (line 89). Then lines 1907 to 1920 classify the packet: a reply-direction match is IP_CT_ESTABLISHED_REPLY; an original-direction match on an entry that has seen a reply is IP_CT_ESTABLISHED; an expected connection is IP_CT_RELATED; a fresh entry is IP_CT_NEW. nf_ct_set (line 1921) packs the entry pointer and that classification into skb->_nfct, the field from chapter 0's table, and nf_ct_get (nf_conntrack.h:169) unpacks it. A protocol handler, nf_conntrack_tcp_packet in the trace, then runs the TCP state machine on the entry.

The entry is not yet in the hash table. It is unconfirmed until the packet reaches the entry with priority INT_MAX, nf_confirm, registered at both LOCAL_IN and POST_ROUTING (nf_conntrack_proto.c:240 to 265), which calls __nf_conntrack_confirm (nf_conntrack_core.c:1179) to insert it. The delay is deliberate. A packet that a filter chain drops never creates an entry, and NAT gets a chance to rewrite the reply tuple before anyone can look it up. Meanwhile every chain with a priority above minus 200 can read ct state from skb->_nfct: that is why ct state new works in a filter chain at zero and matches nothing useful in a raw chain at minus 300, where skb->_nfct is still empty and the expression evaluates to invalid (net/netfilter/nft_ct.c:74).

The conntrack -L line for the lab connection reads the entry back: protocol, timeout, TCP state, the original tuple, then the reply tuple, then [ASSURED] once both directions have been seen. When no NAT is involved the reply tuple is the mirror of the original. The next section changes that.

NAT: decided once, applied every time

NAT is four hook entries, nf_nat_ipv4_ops (net/netfilter/nf_nat_proto.c:766 to 795): destination NAT at PRE_ROUTING and LOCAL_OUT with priority minus 100, source NAT at POST_ROUTING and LOCAL_IN with priority 100. All four call nf_nat_inet_fn (net/netfilter/nf_nat_core.c:898). It reads the conntrack entry from the skb (line 907) and switches on the classification (line 918).

For a NEW packet whose entry has no NAT mapping yet for this direction (lines 918 to 941), it runs the nat chains registered at this hook, the nftables chains declared type nat, through nft_nat_do_chain. A rule such as masquerade calls nf_nat_setup_info (line 765), which chooses the new address and port and rewrites the entry's reply tuple to match. If no rule matched, a null mapping is recorded (lines 942 to 946) so the chains are never consulted again for this connection. Then, for this packet and for every later packet in either direction (the established branch at lines 955 to 960), nf_nat_packet (line 860) calls nf_nat_manip_pkt (nf_nat_proto.c:357) to rewrite the addresses, ports and checksums in the header. The mapping lives in the conntrack entry; the rules were consulted once.

The bench shows it in the tuple column. With a masquerade rule on the router's natpost chain, the SYN reaches POST_ROUTING on r1 reading 10.5.1.2:57158 to 10.5.2.2:8080, passes the filter chain, enters nf_nat_ipv4_out, nf_nat_inet_fn, nft_nat_do_chain, nf_nat_masquerade_ipv4, then nf_nat_manip_pkt and two checksum updates, and from the next line reads 10.5.2.1:57158 to 10.5.2.2:8080. Then nf_confirm inserts the entry with its rewritten reply tuple, which conntrack -L now shows as src=10.5.2.2 dst=10.5.2.1. When the SYN-ACK comes back on r1 addressed to 10.5.2.1, PRE_ROUTING finds the entry by that reply tuple, classifies the packet as an established reply, and nf_nat_inet_fn applies the inverse rewrite through nf_nat_manip_pkt with no chain walk at all; the tuple column flips back to 10.5.1.2 before ip_rcv_finish_core runs. That last clause is the reason the reverse translation lives at PRE_ROUTING: the routing decision must see the real destination, or it would deliver the SYN-ACK to the router's own stack.

Recap

A hook is an array of entries sorted by integer priority, walked by nf_hook_slow. Each nftables base chain is one entry. Conntrack, at minus 200, builds a tuple, finds or allocates an entry with an original and a reply tuple, and stores the entry and its classification in skb->_nfct; the entry is confirmed into the table only at the very end, by nf_confirm at INT_MAX. NAT, at minus 100 and plus 100, consults its chains only for the first packet of a connection, stores the mapping in the entry's reply tuple, and rewrites every packet from that mapping. Destination NAT and the reverse of source NAT run at PRE_ROUTING because the routing decision must see the translated address.

Check yourself

1. You move a ct state new accept rule from a chain with priority filter into a chain with priority raw on the same hook, and it stops matching. Nothing else changed. Why?

Answer

At priority minus 300 the conntrack entry at minus 200 has not run yet, so skb->_nfct is still empty and the ct state expression evaluates to the invalid state (net/netfilter/nft_ct.c:74). Order within a hook is the integer priority, walked ascending by nf_hook_slow (net/netfilter/core.c:620). Anything that reads conntrack state must sit above minus 200; anything that wants to stop tracking, notrack, must sit below it, which is what raw is for.

The near miss is "raw chains cannot use ct expressions". They can; the expression runs and returns invalid. The rule is not rejected, it is silently useless, which is worse.

2. After you add a masquerade rule, the nat chain's counter shows one packet per connection while the filter chain's counter shows dozens. A colleague concludes NAT is being skipped for most packets and the source addresses must be wrong. Are they?

Answer

No. nf_nat_inet_fn (net/netfilter/nf_nat_core.c:918 to 960) runs the nat chains only for a NEW packet whose entry has no mapping yet; it records the mapping in the entry's reply tuple through nf_nat_setup_info, and every later packet in both directions goes straight to nf_nat_packet and nf_nat_manip_pkt without touching a rule. The counter measures rule evaluations, and there is one per connection. Confirm with conntrack -L: the reply tuple carries the translated address for the whole connection.

The near miss is expecting NAT counters to behave like filter counters. Filter chains run per packet; nat chains are a per-connection decision. That is also why changing a nat rule does not affect connections that already exist.

3. Trace the SYN-ACK of a masqueraded connection as it enters the router on r1, addressed to the router's own address 10.5.2.1. Name the entry that rewrites it and explain what would happen if that rewrite ran after the routing decision instead of before it.

Answer

nf_nat_ipv4_pre_routing at priority minus 100, through nf_nat_inet_fn, which finds the entry by the reply tuple, sees an established reply, and calls nf_nat_manip_pkt to put 10.5.1.2 back as the destination. This happens inside ip_rcv's hook call, before ip_rcv_finish runs ip_route_input_slow. If the rewrite came after routing, the lookup would see 10.5.2.1, a local address, return RTN_LOCAL, and deliver the SYN-ACK to the router's own TCP, which has no such connection and would answer with a reset. The bench trace shows the tuple column flip back to 10.5.1.2 two lines before ip_rcv_finish_core.

The near miss is "the reverse NAT happens at POST_ROUTING, mirroring where the forward NAT happened". Source NAT's reverse is a destination rewrite, so it lives with destination NAT, at PRE_ROUTING, on the way in.

Chapter 6

Transmit: from sendmsg to the wire, through the default gateway

~13 min · L3 · Spine: our skb has been delivered, and the server is answering. The reply is a new skb, born in the socket layer rather than in a ring. This chapter follows it down to the driver, and it is also scenario 4: the destination is not on the local link, so the packet has to find the default gateway's MAC address first.

Born in the socket, transmitted as a clone

A write() on a TCP socket ends in tcp_sendmsg (net/ipv4/tcp.c:1446) and tcp_sendmsg_locked (line 1116), which copy the user's bytes into skbs on the socket's write queue. Each skb is allocated with enough headroom for every header that will be added below it, so that no layer needs to reallocate. tcp_push (line 740) hands control to tcp_write_xmit (net/ipv4/tcp_output.c:2964), which decides how many segments the congestion window and pacing allow to leave now, and calls __tcp_transmit_skb (line 1536) for each.

Here is the fact three earlier chapters leaned on. At line 1563, __tcp_transmit_skb clones the skb. The original stays on the write queue until the peer acknowledges it, because TCP may need to retransmit. The clone, sharing the same data buffer, is what travels. That shared buffer is why ip_forward had to copy the header before touching the TTL, and why a native XDP program on a veth forced a copy before it could run. TCP then writes the TCP header into the clone's headroom and calls the address family's transmit function, icsk_af_ops->queue_xmit (lines 1716 to 1718), which for IPv4 is ip_queue_xmit.

Route first, then LOCAL_OUT, then POST_ROUTING

ip_queue_xmit (net/ipv4/ip_output.c:545) leads to __ip_queue_xmit (line 462). Its first job is the route, and for a connected TCP socket it does not look one up: the route was resolved at connect() time and cached on the socket, and the cached dst_entry is reused for every segment. Then it writes the IP header and calls ip_local_out (line 125), which reaches __ip_local_out (line 102). That function calls the LOCAL_OUT hook (lines 121 to 123) with dst_output as the continuation, and dst_output (include/net/dst.h:468) is the same indirect call chapter 4 met, through the route's output pointer, which rt_dst_alloc set to ip_output (net/ipv4/route.c:1691).

Notice the order. The chart shows a routing decision before LOCAL_OUT, and here is why: the route is needed to choose the source address and the outgoing device, so it has to exist before any hook that might read them. A LOCAL_OUT rule that rewrites the destination therefore forces a second lookup, which netfilter does explicitly, and that is the one place the chart's "reroute check" comes from.

ip_output (line 427) calls the POST_ROUTING hook (lines 437 to 440) with ip_finish_output (line 317) as the continuation. This is where a forwarded packet from chapter 4 joined us: ip_forward_finish also ended in dst_output, so locally generated and forwarded packets share everything from here down, and POST_ROUTING is the one hook that sees both. __ip_finish_output (line 296) fragments the packet if it is larger than the path allows and is not marked for hardware segmentation (ip_fragment, line 312), then calls ip_finish_output2 (line 199).

The neighbour: finding a MAC address

The IP layer knows the next hop but not its MAC address. ip_finish_output2 asks the route for the neighbour entry at line 230: ip_neigh_for_gw returns the entry for the gateway if the route has one, or for the destination itself if it is on the local link. A neighbour entry, struct neighbour, is one row of the table ip neigh prints: an IP address, a MAC address, and a state from the set at include/uapi/linux/neighbour.h:63 onward: INCOMPLETE while resolution is in progress, REACHABLE when confirmed, STALE when old but usable, and a few more.

neigh_output (include/net/neighbour.h:547) has a fast path: if the entry is connected and has a cached hardware header, it copies the pre-built 14-byte Ethernet header in front of the IP header and calls dev_queue_xmit. Otherwise neigh_resolve_output (net/core/neighbour.c:1596) calls __neigh_event_send (line 1202). For an entry with no address yet, that function sets the state to INCOMPLETE (line 1224), parks the skb on the entry's arp_queue (line 1265), bounded by unres_qlen_bytes, and calls neigh_probe (line 1084). neigh_probe clones the parked skb, only to lend it to arp_solicit (net/ipv4/arp.c:333) so the ARP request can copy its source address, and arp_solicit builds and sends a separate ARP request skb.

When the reply arrives, arp_rcv (line 967) and arp_process (line 702) update the entry to REACHABLE with the learned MAC address, and the update loop sends every parked skb through the entry's output function. In the bench trace of a SYN to a gateway with an empty neighbour table, that is exactly the shape: neigh_resolve_output, __neigh_event_send, skb_clone, then the ARP exchange, then neigh_resolve_output again for the same skb address, eth_header, skb_push growing the length from 60 to 74, and __dev_queue_xmit. The SYN was never dropped. It waited.

The queueing discipline, and when it is skipped

__dev_queue_xmit (net/core/dev.c:4771) is the device layer's transmit entry, and its stations mirror chapter 3's in reverse. First tc egress, sch_handle_egress (line 4812), tcx programs then classic filters. Then netdev_core_pick_tx (line 4830) picks a transmit queue: multi-queue cards have one ring per CPU or per flow hash, and this is where the choice is made. Then the test at line 4834: if (q->enqueue).

A queueing discipline, or qdisc, is the object between the stack and the driver that decides which packet leaves next and holds the ones that cannot leave yet. Every device has a root qdisc. Virtual devices such as veth, lo and bridges have noqueue, whose enqueue pointer is NULL, so the test fails and the code goes straight to dev_hard_start_xmit (line 4878): there is nothing to queue behind. Real cards have a real qdisc, fq_codel on most modern distributions, pfifo_fast historically, and mq as a parent with one child per transmit queue, and the code enters __dev_xmit_skb (line 4185).

Even then, most packets never sit in the queue. At lines 4200 to 4218 there is a bypass: if the qdisc allows it and is empty, and no other CPU is running it, the skb goes directly to sch_direct_xmit (net/sched/sch_generic.c:344) without being enqueued. The bench trace with fq_codel on the client's veth shows precisely netdev_core_pick_tx then sch_direct_xmit, with no enqueue function between them. The queue only fills when the driver says its ring is full and stops the queue, or when packets arrive faster than the link drains. Then enqueue is called, and __qdisc_run (line 440) dequeues in batches of dev_tx_weight, 64 packets, through qdisc_restart (line 418) and sch_direct_xmit, until the ring is full again or the qdisc is empty. tc -s qdisc show reports the backlog and drops; this is where latency under load accumulates, and why the qdisc you choose matters.

The driver, segmentation, and the last tap

Before the driver sees the skb, validate_xmit_skb runs. Its most important job is GSO, generic segmentation offload: TCP is allowed to build one skb of up to 64 KB and mark it with the segment size, so that the whole stack processes one packet instead of forty. netif_skb_features asks whether the device can segment in hardware, TSO. If it can, the big skb goes down as is. If it cannot, skb_gso_segment splits it here, into MSS-sized skbs, after the qdisc has already counted it as one packet. A veth advertises every segmentation feature, so a 64 KB skb crosses a veth pair intact, and tcpdump on either end shows a 64 KB "packet" that never existed on any wire.

Then dev_hard_start_xmit (line 3895) and xmit_one (line 3878): the transmit tap for packet sockets at line 3885, and finally netdev_start_xmit, which is the device's ndo_start_xmit. For an Ethernet driver that means mapping the skb's buffers for DMA, writing transmit descriptors into the transmit ring at its next_to_use slot, and telling the card there is work. The skb is not freed here. It is freed later, when the card reports the descriptor done and the driver's poll function, igb_clean_tx_irq in our example, walks the completed descriptors and calls napi_consume_skb. That is when the clone dies and tcp_wfree credits the sender's socket. For lo and veth there is no completion: ndo_start_xmit hands the skb straight to the receive path, and chapters 8 and 9 pick it up alive.

Recap

TCP transmits a clone and keeps the original for retransmission. The route is cached on the socket, so LOCAL_OUT runs after a routing decision that already happened; POST_ROUTING is called by ip_output, where forwarded packets join. ip_finish_output2 resolves the next hop's MAC through the neighbour table, parking the packet and sending ARP when the entry is incomplete. __dev_queue_xmit runs tc egress, picks a transmit queue, skips the qdisc entirely for noqueue devices, bypasses it when it is empty, and otherwise enqueues and drains through __qdisc_run. validate_xmit_skb segments large skbs unless the device offloads it, the transmit tap copies, and the driver writes descriptors; the clone is freed on completion.

Check yourself

1. A transmit trace on a device with fq_codel shows netdev_core_pick_tx followed immediately by sch_direct_xmit, and never any fq_codel_enqueue. A colleague says the qdisc is misconfigured and not being used. What is happening?

Answer

The bypass is working as designed. __dev_xmit_skb (net/core/dev.c:4200 to 4218) checks whether the qdisc allows bypass, is empty, and is not being run by another CPU; if so it calls sch_direct_xmit without enqueueing. The enqueue function runs only when a packet cannot leave immediately: the driver has stopped the queue because its ring is full, or another CPU holds the qdisc. The near miss is "an empty qdisc still enqueues and dequeues each packet". That was true of older kernels and is the reason the bypass flag exists; a trace on 7.2 shows the bypass on every idle link.

2. The first connection to a new gateway shows the SYN reaching __neigh_event_send, then skb_clone, then ARP functions, and only afterwards __dev_queue_xmit for that same skb address. Where was the SYN in between, what was the clone for, and when would it have been dropped instead?

Answer

It was parked on the neighbour entry's arp_queue (net/core/neighbour.c:1265) while the entry was INCOMPLETE. The clone was made by neigh_probe (line 1084) and lent to arp_solicit so the ARP request could take its source address; it is freed right after. Once arp_process updates the entry, the parked skb is sent through neigh_resolve_output, which is why the same address reappears at eth_header. It would have been dropped, with reason NEIGH_QUEUEFULL, if the queue already held more than unres_qlen_bytes of unresolved packets, or if resolution failed after the configured number of probes.

The near miss is "the SYN was dropped and TCP retransmitted it". Retransmission would show a second skb allocation and a one-second gap; here the same skb continues within milliseconds.

3. tcpdump on one end of a veth pair shows a single 64 KB TCP segment. The same data captured on a physical Ethernet NIC of another machine appears as 44 segments of 1,448 bytes. Which function made the difference, and where in the transmit path does tcpdump take its copy?

Answer

validate_xmit_skb, through netif_skb_features. A veth advertises all segmentation offloads, so the 64 KB GSO skb TCP built is not split in software and crosses the pair intact; a card without TSO, or a path that segmented earlier, yields wire-sized segments. tcpdump's transmit copy is taken in xmit_one (net/core/dev.c:3885), after validate_xmit_skb has run, so it sees whatever the device will receive: one giant skb on the veth, MSS-sized segments where software GSO split them.

The near miss is "tcpdump on the veth is buggy". It is accurate: no wire is involved, and the 64 KB skb is the real object the peer's receive path gets. Turn off the features with ethtool -K veth0 tso off gso off and the capture changes to 1,448-byte segments, because the split now happens before the tap.

Chapter 7

The socket is a file: from sk_receive_queue to recvmsg

~12 min · SOCK · Spine: chapter 4 handed our skb to tcp_v4_rcv. The program that wants it is asleep inside a read() on a file descriptor. This chapter connects the two: what a socket is as a file, the three queues the skb may land in, and how the sleeper is woken and given the bytes.

Two structs behind one descriptor

socket(2) ends in __sys_socket (net/socket.c:1788) and __sock_create (line 1580), which asks the address family to build the object; for IPv4 that is inet_create (net/ipv4/af_inet.c:259). Two structures come out. struct socket (include/linux/net.h:137) is the file-facing half: a state, a type, a pointer to the struct file, a wait queue wq, and an operations table ops, which for TCP is inet_stream_ops (af_inet.c:1060). struct sock, reached through socket->sk, is the protocol half: the queues, the buffer limits, the callbacks, and a pointer to the protocol's own operations, tcp_prot.

Then sock_alloc_file (net/socket.c:525) makes it a file. It allocates a struct file on sockfs, a pseudo-filesystem that exists only to give sockets inodes, using alloc_file_pseudo with the operations table socket_file_ops (lines 531 to 533), and stores the socket in file->private_data (line 541). That is the entire answer to "a socket is a file": the descriptor names a struct file whose operations table is socket_file_ops (lines 157 to 175), whose read_iter is sock_read_iter, whose poll is sock_poll, whose release is sock_close, and whose private data is the struct socket. ls -l /proc/PID/fd shows the sockfs inode as socket:[12345], and ss -tp prints the same inode next to the process that owns it.

So read(fd) is sock_read_iter (line 1201), then sock_recvmsg (line 1144), then sock_recvmsg_nosec (line 1123), which calls sock->ops->recvmsg (lines 1126 to 1128). That is inet_recvmsg (af_inet.c:884), which calls sk->sk_prot->recvmsg (lines 894 to 895), which is tcp_recvmsg (net/ipv4/tcp.c:2930). recvfrom(2) gets there slightly differently, through __sys_recvfrom (net/socket.c:2277): look up the descriptor (line 2290), check that its file really is a socket with sock_from_file (line 2294), then sock_recvmsg (line 2301). Three indirect calls, and the read has gone from a file to TCP.

Three queues, and who processes them

Now the receive side. tcp_v4_rcv (net/ipv4/tcp_ipv4.c:2070) looks up the socket for the segment's four-tuple, established sockets first, then listeners. The chapter's trace of a SYN ended in tcp_v4_conn_request: a listener was found, and the decision at lines 2236 to 2239 sent the SYN straight into tcp_v4_do_rcv, where TCP creates a small request socket, sends the SYN-ACK, and consumes the skb. For an established connection the interesting decision is at lines 2244 to 2254, and it turns on one question: is a process holding this socket's lock right now?

Not owned by user. tcp_v4_do_rcv (line 1830) runs immediately, in softirq context, and reaches tcp_rcv_established (net/ipv4/tcp_input.c:6500) and tcp_data_queue (line 5607). If the segment is the next one expected, tcp_queue_rcv (line 5532) tries to merge it with the tail of the queue and otherwise appends it with tcp_add_receive_queue (include/net/tcp.h:803 to 807): __skb_queue_tail(&sk->sk_receive_queue, skb). That is the receive queue, sk_receive_queue (include/net/sock.h:411), queue one, the one recvmsg reads. If the segment arrived ahead of a gap, tcp_data_queue_ofo (line 5381) files it in the out-of-order queue, a red-black tree, queue two, and moves it to the receive queue when the gap closes.

Owned by user. A process is inside recvmsg or sendmsg and holds the socket lock. The softirq cannot touch the queues, so tcp_add_backlog (line 1901) appends the skb to the socket backlog, sk_backlog (include/net/sock.h:420 to 425: a head, a tail, a length), queue three, after a size check. When the process releases the lock, __release_sock (net/core/sock.c:3243) drains the backlog (lines 3250 to 3262), calling tcp_v4_do_rcv for each skb, in the process's own context. The same packet is therefore processed either by the softirq or by the reader, depending on timing, and in a pwru trace the CPU and process columns change accordingly. This is the third thing in this document called a backlog: the per-CPU input_pkt_queue of chapter 1, this per-socket list, and the listen backlog below are unrelated structures that share a word.

Every queue has a limit, and the limits are all expressed in skb->truesize, the memory an skb occupies including its metadata and buffer, not in payload bytes. sk_rcvbuf (sock.h:443) is the receive buffer limit, set from net.ipv4.tcp_rmem and grown by autotuning, or fixed by SO_RCVBUF. sk_rmem_alloc counts what is queued. sk_rcvqueues_full (sock.h:1153) adds the backlog length to it and compares. ss -tm prints these as rb and skmem.

Waking the reader

After queueing, tcp_data_queue calls sk->sk_data_ready (line 5660). For a normal socket that is sock_def_readable (net/core/sock.c:3649), which wakes whoever waits on the socket's wait queue, sk_wq (sock.h:447). Two kinds of waiter live there. A process blocked in tcp_recvmsg_locked (tcp.c:2655) at sk_wait_data (line 2794), and an epoll instance whose callback was registered through sock_poll. The woken reader walks sk_receive_queue (lines 2723 to 2726), copies bytes to user space, advances the sequence it has consumed, and frees skbs it has fully drained. That free runs the skb's receive destructor, sock_rfree, which decrements sk_rmem_alloc; in the veth trace of the HTTP response those are the sock_rfree, skb_attempt_defer_free and napi_consume_skb lines after tcp_queue_rcv, executed later, in curl's process context.

UDP, for contrast: one queue, one limit, no backpressure

udp_rcv (net/ipv4/udp.c:2588) finds the socket and reaches udp_queue_rcv_one_skb (line 2349) and __udp_enqueue_schedule_skb (line 1655). It reads sk_rcvbuf (line 1669), and if the queued memory plus this skb's truesize exceeds it (line 1679), the packet is dropped on the spot, counted in UdpRcvbufErrors. Otherwise it goes on the tail of sk_receive_queue (line 1733) and sk_data_ready fires (line 1745). There is no out-of-order tree because UDP has no order, and no socket backlog because UDP does not take the socket lock in its receive path. A UDP reader that falls behind loses packets; a TCP reader that falls behind fills its queues, closes its advertised window, and the sender slows down.

The listen side, briefly

A SYN to a listening socket creates a request socket, not a full one, and the completed handshake's third ACK, matched by tcp_check_req (tcp_ipv4.c:2165), turns it into a full struct sock placed on the listener's accept queue. accept() dequeues it and calls sock_alloc_file for it, which is why a server has one sockfs inode per connection. The length of that queue is the "backlog" argument of listen(), capped by net.core.somaxconn: the third backlog, and the only one an application controls directly.

Expected: the backlog counter is small but not zero, because a reader that is copying data when the next segment arrives sends that segment to queue three. The UDP counter jumps by roughly the number of datagrams that did not fit in the default receive buffer, a few hundred kilobytes, and the rest are still queued for a reader who never came.

Recap

A socket descriptor is a struct file on sockfs whose operations table is socket_file_ops and whose private data is a struct socket, which points at the protocol's struct sock; read() reaches tcp_recvmsg through three indirect calls. tcp_v4_rcv puts an established segment in the receive queue or the out-of-order tree if nobody holds the socket lock, and in the socket backlog if a process does, to be processed by that process when it releases the lock. All limits are in truesize against sk_rcvbuf. Queueing calls sk_data_ready, which wakes the reader or epoll. UDP has one queue and drops on overflow. The accept queue is the listen backlog, a third unrelated meaning of the word.

Check yourself

1. A process is inside recvmsg, copying a large buffer to user space, when three more segments for the same connection arrive on another CPU. Which queue do they enter, in whose context are they eventually processed, and what could make the kernel drop them?

Answer

The socket backlog, in the reader's own context, and the receive-memory limit. tcp_v4_rcv finds sock_owned_by_user true (net/ipv4/tcp_ipv4.c:2248) and calls tcp_add_backlog (line 1901), which appends to sk_backlog. When recvmsg releases the lock, __release_sock (net/core/sock.c:3250 to 3262) runs tcp_v4_do_rcv on each of them, so the reader's thread does the protocol work the softirq would otherwise have done. tcp_add_backlog drops when the backlog plus queued memory exceeds a limit derived from sk_rcvbuf and sk_sndbuf, counted as TCPBacklogDrop in nstat.

The near miss is "they wait in the per-CPU backlog of chapter 1". That queue is before the IP layer and has nothing to do with sockets; these segments have already passed ip_local_deliver.

2. ls -l /proc/4242/fd shows 7 -> socket:[91133]. Starting from that number, name the objects and the function pointers a read(7) passes through before TCP code runs.

Answer

91133 is a sockfs inode. Descriptor 7 names a struct file whose f_op is socket_file_ops (net/socket.c:157) and whose private_data is a struct socket (set at line 541). read calls f_op->read_iter, which is sock_read_iter (line 1201), then sock_recvmsg (line 1144), which calls socket->ops->recvmsg, inet_recvmsg (net/ipv4/af_inet.c:884), which calls sk->sk_prot->recvmsg, tcp_recvmsg (net/ipv4/tcp.c:2930). ss -tp maps the inode back to the process and shows the connection.

The near miss is imagining a socket-specific system call table. There is none; the same read that works on a pipe works here, because the file operations table is the only thing that differs.

3. Predict the outcome: a UDP receiver binds a socket and never calls recv. A sender delivers 5,000 datagrams of 1,400 bytes at line rate. Roughly how many are dropped, which line drops them, and would the same experiment over TCP lose data?

Answer

Most of them, at net/ipv4/udp.c:1679, and TCP would lose nothing. The default sk_rcvbuf comes from net.core.rmem_default, about 208 KB on this kernel, measured in truesize; a 1,400-byte datagram costs roughly 2 KB of truesize, so around a hundred fit and the remaining four thousand nine hundred fail the test rmem + size > rcvbuf and are freed, incrementing UdpRcvbufErrors. Over TCP the receive queue would fill the same way, but then the advertised window would reach zero and the sender's tcp_write_xmit would stop sending; nothing is dropped, the sender waits.

The near miss is "the kernel buffers everything until the reader comes". It buffers up to the limit; the limit is the whole point. Raise it with SO_RCVBUF up to net.core.rmem_max and the number that fit scales with it.

Chapter 8

Two programs on one host: lo, same pod, unix sockets

~13 min · SOCK · Spine: chapters 1 to 7 followed one skb in from a network card and back out. Now both ends live on the same machine and the card is never involved. This chapter shows where that skb goes instead, then removes the device layer entirely.

Three scenarios that collapse into one

Two programs on two ports of one interface; two programs on two different interfaces of one machine; two containers in one Kubernetes pod. Three questions, one answer, because the decision is made in the output route lookup and it does not consult the interface you expect.

ip_route_output_key_hash_rcu (net/ipv4/route.c:2736) runs the FIB lookup, and when the answer is RTN_LOCAL it overrides the device (lines 2872 to 2890):

if (res->type == RTN_LOCAL) {
        /* L3 master device is the loopback for that domain */
        dev_out = l3mdev_master_dev_rcu(FIB_RES_DEV(*res)) ? :
                net->loopback_dev;
        flags |= RTCF_LOCAL;

The matching route entry named a real interface; the output device is overwritten anyway. The bench shows both halves on one node:

# ip route show table local
local 172.18.0.4 dev eth0 proto kernel scope host src 172.18.0.4
# ip route get 172.18.0.4 from 10.128.0.75
local 172.18.0.4 from 10.128.0.75 dev lo table local

The table entry says dev eth0; the lookup answers dev lo. Traffic from one local address to another goes through the loopback device even when the two addresses sit on different physical cards. The interface an address is configured on decides which card answers ARP for it and which card may receive it from outside. It decides nothing about locally generated traffic to it.

One more line matters shortly. RTCF_LOCAL is set here, and rt_dst_alloc (route.c:1670) reads it: rt->dst.output = ip_output at line 1691, and if (flags & RTCF_LOCAL) rt->dst.input = ip_local_deliver at lines 1692 to 1693. The output route is born already knowing what the input side should do.

Down the transmit path and straight back up

The skb then takes the transmit path of chapter 6: LOCAL_OUT, POST_ROUTING, a loopback neighbour that is permanently valid and needs no ARP, and __dev_queue_xmit finding lo set to noqueue, so the driver is called directly. That driver is loopback_xmit (drivers/net/loopback.c:70 to 94), and four lines decide everything:

skb_orphan(skb);                             /* line 80 */
skb_dst_force(skb);                          /* line 85 */
skb->protocol = eth_type_trans(skb, dev);    /* line 87 */
if (likely(__netif_rx(skb) == NET_RX_SUCCESS))    /* line 90 */

skb_orphan releases the sending socket's accounting, which is why the trace shows tcp_wfree here. skb_dst_force takes a real reference on the route. eth_type_trans does what a receive path expects: read the Ethernet header, set skb->pkt_type and skb->protocol, pull the header off. Then __netif_rx hands the skb to the per-CPU backlog of chapter 1. The transmit path ends inside a receive path, same softirq, same skb.

A live SYN on the node, condensed, one skb address on every line:

ip_local_out > nf_hook_slow > ip_output > nf_hook_slow > ip_finish_output2 >
__dev_queue_xmit > dev_hard_start_xmit > loopback_xmit > tcp_wfree >
eth_type_trans > __netif_rx > enqueue_to_backlog > ip_rcv > ip_rcv_core >

Count the nf_hook_slow calls: four. LOCAL_OUT, POST_ROUTING, PRE_ROUTING, LOCAL_IN. The skb walks the netfilter chart twice, in one namespace, and every rule applies both times. A POSTROUTING rule counting bytes that leave the machine counts this packet, which never leaves the machine.

Now what the trace lacks: no ip_route_input_noref and no ip_route_input_slow in the whole 1,631-line capture. The receive half does no routing lookup. skb_dst_force kept the output route attached, that route was built with RTCF_LOCAL so its input function is already ip_local_deliver, and ip_rcv_finish_core looks up a route only when !skb_valid_dst(skb) (net/ipv4/ip_input.c:406, skb_valid_dst at include/net/dst_metadata.h:93). The route the sender computed is the route the receiver uses. Remember this when the next chapter sends the same skb through a veth pair and gets the opposite result.

What a tap on lo sees, and how often

A packet socket on lo sees every packet twice, and this is worth settling by measurement because both answers sound plausible.

xmit_one (net/core/dev.c:3878) calls dev_queue_xmit_nit when a tap is active (lines 3883 to 3884), which clones the skb and sets skb2->pkt_type = PACKET_OUTGOING (line 2597). The ptype_all walk of chapter 3 then delivers it again on the way in, as PACKET_HOST. Two deliveries, one per direction through the device. A suppression mechanism exists and does not apply: packet_rcv (net/packet/af_packet.c:2144), packet_rcv_spkt (line 1893) and tpacket_rcv (line 2273) discard pkt_type PACKET_LOOPBACK, but only dev_loopback_xmit (dev.c:4345) sets that, and it serves multicast and broadcast self-copies.

Measured with a packet socket bound to lo, one local HTTP request gave twenty-four frames for twelve packets, in pairs with identical sequence numbers:

('OUTGOING', 35726, 4240, 1415493697)
('HOST',     35726, 4240, 1415493697)
TOTAL frames seen by the tap: 24

So tcpdump -i lo showing an apparent duplicate of every packet is correct, and pkt_type is how you tell the two apart.

Same pod: one namespace, two containers

Kubernetes gives every container in a pod the same network namespace, and everything follows from that. Two containers of a throwaway pod on the bench:

alpha# readlink /proc/self/ns/net  ->  net:[4026532689]
beta#  readlink /proc/self/ns/net  ->  net:[4026532689]
alpha# ip -br a  ->  lo ..., eth0@if19 10.128.0.82/32
beta#  ip -br a  ->  lo ..., eth0@if19 10.128.0.82/32

Same inode, same device index, same address, so a connection between them addressed to the pod IP is the first scenario of this chapter happening inside the pod. Traced on the node while one container talked to a listener in the other, the capture held 390 events, every one carrying the pod's namespace inode and an interface column reading lo. Searching it for the host-side veth device, for veth_xmit, for any Cilium program name and for nf_hook_slow returned zero lines. The pod's veth device is idle, the BPF program on its host end is never called, and since that namespace has no registered hook entries the four hook points cost nothing. The Cilium chapters show what that program does when it is called.

One detail catches people. ss -tlnp in the container owning a listener prints the socket and the process; in the sibling container it prints the same socket with an empty process column. They share a network namespace and read the same socket table, and they do not share a process namespace, so the second cannot map the socket inode to anything in its own /proc.

Unix sockets: an skb with nothing attached

Now take the device layer away. A unix socket still allocates an skb, which surprises people who expect a plain memory copy, and that skb is the only thing the two paths share.

unix_stream_sendmsg (net/unix/af_unix.c:2377) loops over the caller's data. Each turn calls sock_alloc_send_pskb (line 2437), charging the bytes to the sender's send buffer and blocking at that limit, then skb_copy_datagram_from_iter (line 2467) copies the payload in. Delivery is three lines:

__skb_queue_tail(&other->sk_receive_queue, skb);   /* line 2488 */
unix_state_unlock(other);
READ_ONCE(other->sk_data_ready)(other);            /* line 2492 */

The skb goes on the peer's sk_receive_queue, the list recvmsg drains in chapter 7, and sk_data_ready wakes the reader through sock_def_readable. The reader is unix_stream_read_generic (line 2907). The datagram variant unix_dgram_sendmsg (line 2083) queues at line 2291 and adds peer-wake machinery (unix_dgram_peer_wake_me, line 571) so a sender blocked on a full receiver is woken when the receiver drains.

Containers in one pod share the network namespace, so traffic between them is this same loopback path with no veth device and no BPF program involved. A unix socket keeps the skb and the receive queue and discards the device, the route, the headers and the hooks.

Chapter 9

veth: the mystery, resolved

~12 min · L2 · Spine: chapter 8 sent our skb through the loopback device and it came back up with its route still attached. Now we hand the same skb to the other end of a veth pair, in a different network namespace, and almost everything about that sentence changes except the skb itself.

The payoff sentence

A veth pair does not create a new skb. It points skb->dev at the peer device, erases the state that belonged to the old namespace, and hands the same skb to a receive function, so the receive half of the stack runs again in the peer's namespace while the transmit half ran once in the origin's.

veth_xmit and the choice it makes

__netif_rx is the backlog door of chapter 1. veth_xdp_rx leads to the peer's own NAPI poll. Which one runs is decided per packet by that use_napi expression, and both of its operands have to be true.

The first operand is the napi pointer, which exists only when the peer has GRO enabled or an XDP program attached. The second is veth_skb_is_eligible_for_gro (line 338), whose whole body is:

skb_scrub_packet(skb, !net_eq(dev_net(dev), dev_net(skb->dev)));

__is_skb_forwardable (line 4400) checks that the peer is up and that the frame fits its MTU plus link-layer and VLAN headroom (lines 4413 to 4415), with a deliberate exemption: a GSO skb passes regardless of length (lines 4420 to 4421), because it will be segmented later. An MTU mismatch between the two ends of a pair therefore shows up as a silent rx_dropped on the receiving device rather than as an ICMP message.

Then the important call, whose second argument is the whole question. !net_eq(dev_net(dev), dev_net(skb->dev)) is true when the two devices live in different network namespaces, and that flag is named xnet inside skb_scrub_packet (net/core/skbuff.c:6278). Here is exactly what it clears:

Two rows of that table answer the question people actually have. Because the route is dropped, the peer namespace must do its own routing decision, which is why the trace shows ip_route_input_noref and ip_route_input_slow on the receive side. That is the precise opposite of chapter 8, where loopback_xmit called skb_dst_force and the lookup was skipped. And because the conntrack pointer is reset, conntrack runs again from scratch in the peer namespace, with its own table and its own entry.

The mark is the subtle one. skb->mark is cleared only when the namespace actually changes. A veth pair with both ends in one namespace, which is how a Linux bridge is usually wired, preserves the mark; a pair whose ends straddle a container boundary does not. The last step, after the scrub, is eth_type_trans back in __dev_forward_skb2 (line 2443), and its first statement is skb->dev = dev. That single assignment is the device swap.

The one place a copy happens

Chapter 2 promised this chapter would say when a veth copies. The answer is a single call site. When a native XDP program is attached to the receiving end, veth_convert_skb_to_xdp_buff (veth.c:751) must hand the program a linear buffer it owns, with headroom in front. If any of four conditions holds (lines 758 to 760) it copies:

if (skb_shared(skb) || skb_head_is_locked(skb) ||
    skb_is_nonlinear(skb) ||
    skb_headroom(skb) < XDP_PACKET_HEADROOM) {
        if (skb_pp_cow_data(rq->page_pool, pskb, XDP_PACKET_HEADROOM))

For locally generated TCP this is not a rare case; it is every packet. TCP keeps the original skb on its retransmission queue and transmits a clone, so the head is locked and skb_pp_cow_data (net/core/skbuff.c:942) allocates a fresh page-pool buffer and copies the data into it. The earlier native XDP trace showed exactly that shape: the old skb freed through consume_skb and a new address appearing afterwards. Without an XDP program the skb identity holds end to end, which is what the address column in this chapter's traces shows.

Recap

A veth pair is two devices pointing at each other. veth_xmit (veth.c:347) looks up the peer and calls veth_forward_skb, which runs __dev_forward_skb and then either __netif_rx or the peer's NAPI poll. The NAPI door needs a napi pointer on the peer and an eligible skb, and eligibility reads the sender's segmentation offload, so turning GRO on at the receiver alone changes nothing. skb_scrub_packet drops the route and resets conntrack for every crossing, and clears the mark only when the namespace changes, so the peer namespace repeats the routing decision and conntrack lookup that chapter 8's loopback path skipped. The skb address is unchanged throughout; the only copy is the native XDP path, where a locked TCP clone forces skb_pp_cow_data.

1. You set a firewall mark on a packet in one namespace and expect to match it in the peer namespace after it crosses a veth pair. Sometimes it works and sometimes it does not. What decides, and which line?

Answer

2. Trace the path: a container sends a TCP segment out of its eth0, which is one end of a veth pair. Does conntrack in the host namespace see a new connection or an established one, and why?

Answer

A new one, because skb_scrub_packet called nf_reset_ct (net/core/skbuff.c:6285) and dropped the conntrack pointer the container's namespace had attached. Conntrack state lives per network namespace, and skb->_nfct is the only thing tying an skb to an entry, so the host's nf_conntrack_in finds nothing in the skb, builds the tuple again and allocates its own entry with IP_CT_NEW.

The near miss is "it is established because the container already tracked it". Two independent tables are involved, and neither can see the other's entry; the container's table is not even consulted.

3. Predict the trace: you attach a native XDP program to vb and send one TCP segment from va. Does the skb address stay constant, and what would change if the traffic were UDP from a socket with plenty of headroom?

Answer

It changes for TCP and can stay constant for UDP. veth_convert_skb_to_xdp_buff (veth.c:758 to 761) copies when the skb is shared, head-locked, nonlinear, or short of XDP_PACKET_HEADROOM. TCP transmits a clone of the skb it keeps for retransmission, so the head is locked and skb_pp_cow_data (net/core/skbuff.c:942) allocates a new buffer; the trace shows the old skb freed and a new address appearing. A linear UDP skb with enough headroom fails all four tests and is passed through unchanged.

The near miss is "XDP always copies on veth". The copy is driven by the four properties of that specific skb, and the headroom condition is the one you can influence.

Chapter 10

The bridge, and Docker on it

~12 min · L2 · Spine: chapter 9 delivered our skb into a namespace through a veth pair. Put the host end of two such pairs into a bridge and the skb stops at L2 instead of climbing to IP. This chapter is that stop: who steals the skb, where it is put down, and what changes when br_netfilter drags the IP hooks back into a path that had left them behind.

Two ways a receive handler can end the round

Chapter 3 walked __netif_receive_skb_core and named the receive-handler station. Now look at what the caller does with the answer (net/core/dev.c:6097 to 6116):

rx_handler = rcu_dereference(skb->dev->rx_handler);
if (rx_handler) {
        switch (rx_handler(&skb)) {
        case RX_HANDLER_CONSUMED:  ret = NET_RX_SUCCESS; goto out;
        case RX_HANDLER_ANOTHER:   goto another_round;
        case RX_HANDLER_EXACT:     deliver_exact = true; break;
        case RX_HANDLER_PASS:      break;

Those first two verdicts are the difference between a bridge and every other master device in this document. A bridge answers RX_HANDLER_CONSUMED: it has taken ownership, the core stops, and nothing above L2 runs on this CPU pass. The bond, macvlan and ipvlan devices of the next two chapters answer RX_HANDLER_ANOTHER: they change skb->dev and send the core back to the top of its own function to redo the whole station list against the new device. Same station, two structurally different outcomes.

The bridge registers its handler when a port is added, netdev_rx_handler_register(dev, br_get_rx_handler(dev), p) (net/bridge/br_if.c:619), and the handler is br_handle_frame (net/bridge/br_input.c:339).

Where the bridge puts the skb down

br_handle_frame checks the port's spanning-tree state and, for a forwarding port, calls nf_hook_bridge_pre (br_input.c:267), which runs the NF_BR_PRE_ROUTING hook with br_handle_frame_finish (line 76) as its continuation. That is where the decisions are:

  • Learning, line 144: br_fdb_update(br, p, eth_hdr(skb)->h_source, vid, 0) records the source MAC against the port it arrived on. That table is the forwarding database.
  • Lookup, line 204: dst = br_fdb_find_rcu(br, eth_hdr(skb)->h_dest, vid).
  • A hit whose entry is flagged local means the frame is addressed to the bridge itself, so line 222 calls br_pass_frame_up.
  • A hit on another port, line 226: br_forward.
  • A miss, line 229: br_flood, which walks every port.

Take the forwarding case. br_forward (net/bridge/br_forward.c:144) reaches __br_forward (line 73), and two lines there do the work: indev = skb->dev then skb->dev = to->dev. The skb is now labelled with the outgoing port. It then runs the NF_BR_FORWARD hook with br_forward_finish (line 63) as the continuation, which runs NF_BR_POST_ROUTING with br_dev_queue_push_xmit (line 33) as its continuation. That last function pushes the Ethernet header back on, checks the frame still fits, and calls dev_queue_xmit(skb) at line 53. The skb re-enters the transmit path of chapter 6 on a different device, without ever having reached IP.

The bench shows all of it on one skb address, across three namespaces:

netns pp-l,  dev vl:24    ip_local_out ... veth_xmit > skb_scrub_packet > eth_type_trans
netns root,  dev vl-br:23 __netif_rx > enqueue_to_backlog > __netif_receive_skb_one_core
                          br_handle_frame_finish[bridge] > br_allowed_ingress[bridge]
                          br_forward[bridge] > __br_forward[bridge] > br_handle_vlan[bridge]
netns root,  dev vr-br:25 br_forward_finish[bridge] > br_dev_queue_push_xmit[bridge]
                          skb_push > __dev_queue_xmit > ... > veth_xmit[veth]
                          skb_scrub_packet > eth_type_trans
netns pp-r,  dev vr:26    __netif_rx > enqueue_to_backlog > __netif_receive_skb ...

The device column flips from vl-br to vr-br exactly at br_forward_finish, which is the skb->dev = to->dev assignment becoming visible. And grep -c nf_hook_slow over that entire capture returns zero. A bridge forwarding an IP packet touches no netfilter hook at all. The bridge hook points are traversed, and on a stock host nothing is registered at them.

Two details worth keeping. First, br_handle_frame never appears in the trace: its signature takes struct sk_buff **pskb, a double pointer, so pwru cannot read an skb out of it, and the first bridge function you see is the continuation. Second, flooding is the one place the bridge duplicates. br_flood (line 201) walks the port list calling maybe_deliver (line 176), which carries one port forward and calls deliver_clone (line 120) for the others; deliver_clone is a skb_clone and a recursive __br_forward. The last port gets the original. Local delivery is the mirror image: br_pass_frame_up (line 33) sets skb->dev to the bridge device itself and runs NF_BR_LOCAL_IN with br_netif_receive_skb (line 26) as the continuation, which calls netif_receive_skb. The core runs a second time, from the top, with the bridge as the device, and this time there is no receive handler so the frame climbs to IP.

br_netfilter: putting the IP hooks back

Everything above is why a firewall rule written for FORWARD does not match traffic between two containers on one bridge. The br_netfilter module exists to change that, and it is worth being precise about how, because the mechanism is unusual.

Loading the module registers br_nf_ops (net/bridge/br_netfilter_hooks.c:1047), six entries. Four sit on the bridge hooks: br_nf_pre_routing (line 483) at NF_BR_PRE_ROUTING, br_nf_local_in (line 585), br_nf_forward (line 769) at NF_BR_FORWARD, and br_nf_post_routing (line 925) at NF_BR_POST_ROUTING. Look at what the first one does once it has decided the frame carries IPv4 (lines 536 to 542):

NF_HOOK(NFPROTO_IPV4, NF_INET_PRE_ROUTING, state->net, state->sk, skb,
        skb->dev, NULL,
        br_nf_pre_routing_finish);

return NF_STOLEN;

It calls the IPv4 PRE_ROUTING chain from inside a bridge hook, passing the bridge port as the input device, and then returns NF_STOLEN so the bridge code does not continue on its own. Your nat and raw and filter chains run, conntrack runs, and the bridge's own walk resumes afterwards in the continuation. br_nf_forward_ip (line 673) does the same for NF_INET_FORWARD and br_nf_post_routing (line 925) for NF_INET_POST_ROUTING. The remaining two entries of the array are ip_sabotage_in, registered on IPv4 and IPv6 PRE_ROUTING at the very first priority, whose job is to suppress a second, duplicate run of those chains when the frame later climbs to IP through br_pass_frame_up.

The gate is a sysctl. br_nf_pre_routing starts with if (!brnet->call_iptables && !br_opt_get(br, BROPT_NF_CALL_IPTABLES)) return NF_ACCEPT (lines 516 to 517), and call_iptables is /proc/sys/net/bridge/bridge-nf-call-iptables (.procname at line 1192), defaulted to 1 when a namespace is created (line 1225). That path exists only once the module is loaded, which is the whole reason Kubernetes installation guides tell you to load br_netfilter and then set the sysctl: with the module absent, writing the sysctl fails, and with it present but the sysctl at zero, bridged traffic bypasses every IP rule you wrote.

On the machine this dossier was written on, the kind cluster's three nodes hang off a bridge called br-kind-cilium, and ip -d link show prints nf_call_iptables 0 for it, with no /proc/sys/net/bridge directory at all. That is the unloaded state, and it is why the bench trace above has no hooks in it.

Docker on the same machinery

Docker's default network is this chapter with names on it. docker0 is a bridge; every container gets a veth pair with one end in the container's namespace as eth0 and the other enslaved to docker0. Container to container on one network is the trace above. Container to the outside is different: the bridge has an IP address, the container's default route points at it, so the frame is addressed to the bridge's own MAC, the forwarding database entry is the local one, br_pass_frame_up runs, and the packet climbs to IP on the host and is routed and masqueraded like any other forwarded traffic.

That is where Docker's iptables chains sit. It adds a DOCKER chain for published-port destination NAT and a DOCKER-USER chain placed before its own rules so that operator rules are not overwritten when Docker rewrites its own, plus a masquerade rule for traffic leaving the bridge subnet. All of that lives on the IP hooks, which means it applies to the routed path and, for bridged container-to-container traffic, only when br_netfilter is loaded and the sysctl is on. Turning that sysctl off is a real and occasionally deliberate act: it makes same-bridge traffic invisible to iptables, which is faster and which quietly disables any network policy implemented with iptables rules.

Recap

A bridge port's receive handler returns RX_HANDLER_CONSUMED, so the core stops and the skb never climbs to IP on that pass. br_handle_frame_finish learns the source MAC into the forwarding database, looks up the destination, and either passes the frame up to the bridge device, forwards it to one port, or floods it by cloning to all but the last. Forwarding is skb->dev = to->dev followed by dev_queue_xmit, so the skb leaves on a new device from inside the receive handler; the bench capture shows one skb address across three namespaces and no netfilter hook at all. br_netfilter changes that by calling the IPv4 chains from inside the bridge hooks and returning NF_STOLEN, gated per namespace by bridge-nf-call-iptables. Docker's bridge network is this machinery with docker0, veth pairs and the DOCKER and DOCKER-USER chains on top.

Answer

Twice: once with the port as skb->dev and once with the bridge device. Chapter 11

Master devices: bond and VRF

~11 min · L2 L3 · Spine: the bridge of chapter 10 answered RX_HANDLER_CONSUMED and our skb never climbed to IP. The two devices in this chapter answer the other verdict. They relabel the skb and send the core round again, once at L2 and once at L3, and the visible cost is that the hooks you know run twice.

The bond: one skb, two passes, both directions

A bond enslaves its members the same way a bridge enslaves ports, netdev_rx_handler_register(slave_dev, bond_handle_frame, new_slave) (drivers/net/bonding/bond_main.c:2234). The handler (line 1603) opens with its default answer already chosen, int ret = RX_HANDLER_ANOTHER at line 1610, and ends with two statements that matter: skb->dev = bond->dev, then that return. The core's another_round label sends it back to the top of the station list with the new device, so tc ingress, the receive handler check and the protocol demux all run a second time, and this time the device has no handler.

The bench shows the swap as a single line boundary. Sending to a bonded peer and watching the reply come back:

                 __netif_receive_skb > __netif_receive_skb_one_core
dev pp-bond0:31  qdisc_pkt_len_segs_init > skb_ensure_writable > ip_rcv >
                 ip_rcv_core > sock_wfree > nf_hook_slow > ...

Same skb address on both lines; the device column changes in between. ip_rcv and every netfilter rule after it see pp-bond0, so iif matches name the bond and never the slave. That is the point of the device.

Two things happen before the swap. recv_probe, a function pointer on the bond (include/net/bonding.h:226), is called first if set; it is bond_3ad_lacpdu_recv for LACP mode (set at line 4394) and bond_rcv_validate for the ARP monitor (line 4388), and it is how control frames are consumed before the data path sees them. Then bond_should_deliver_exact_match (line 1589) checks whether this slave is inactive; in active-backup mode the standby slave still receives broadcast traffic, and returning RX_HANDLER_EXACT restricts delivery to packet sockets bound to that exact device rather than letting it into the stack twice.

Transmit is the mirror. bond_start_xmit (line 5596) calls __bond_start_xmit (line 5558), which is one switch on BOND_MODE(bond):

case BOND_MODE_ROUNDROBIN:   return bond_xmit_roundrobin(skb, dev);
case BOND_MODE_ACTIVEBACKUP: return bond_xmit_activebackup(skb, dev);
case BOND_MODE_8023AD:       ... fallthrough;
case BOND_MODE_XOR:          return bond_3ad_xor_xmit(skb, dev);
case BOND_MODE_BROADCAST:    return bond_xmit_broadcast(skb, dev, true);

Each of those picks a slave and calls bond_dev_queue_xmit (line 297), which sets skb->dev to the slave and calls dev_queue_xmit again. So the transmit path of chapter 6 runs twice for one packet, and the trace says so plainly:

dev pp-bond0:31  __dev_queue_xmit > netdev_core_pick_tx > bond_select_queue[bonding] >
                 dev_hard_start_xmit > bond_start_xmit[bonding] > bond_dev_queue_xmit[bonding]
dev pp-s1:28     __dev_queue_xmit > ... > dev_hard_start_xmit > veth_xmit[veth]

This matters for queueing. The bond device itself normally carries no queueing discipline, and the second __dev_queue_xmit is where the slave's real one runs. A shaper attached to the bond is in the wrong place; it belongs on the slaves, or the bond needs an explicit qdisc of its own.

For the modes that spread traffic, the slave is chosen by bond_xmit_hash (line 4287) over __bond_xmit_hash (line 4253), and the transmit hash policy decides which bytes go into the hash: BOND_XMIT_POLICY_LAYER2 uses the MAC addresses, LAYER34 the addresses and ports, LAYER23 the MACs and IP addresses, with encapsulation-aware variants (include/uapi/linux/if_bonding.h:92 to 97). A layer-2 policy between two routers puts every flow on one slave, because every frame carries the same pair of MAC addresses, and that is the commonest reason a bond delivers the bandwidth of exactly one member.

The VRF: the same trick one layer up

A VRF device does at L3 what the bond does at L2, and the machinery is a different hook. ip_rcv_finish (net/ipv4/ip_input.c:478) calls l3mdev_ip_rcv(skb) at line 486, before the routing decision at line 490. For an enslaved device that reaches vrf_l3_rcv (drivers/net/vrf.c:1379) and then vrf_ip_rcv (line 1340), whose first three statements are the whole idea:

skb->dev = vrf_dev;
skb->skb_iif = vrf_dev->ifindex;
IPCB(skb)->flags |= IPSKB_L3SLAVE;

and whose last statement is vrf_rcv_nfhook(NFPROTO_IPV4, NF_INET_PRE_ROUTING, skb, vrf_dev). That helper (line 1132) calls nf_hook for PRE_ROUTING a second time, with the VRF device as the input device. PRE_ROUTING has already run once, back in ip_rcv, with the enslaved device. The bench counts both:

dev pp-ve:34   ip_rcv > ip_rcv_core > nf_hook_slow      <-- PRE_ROUTING, device pp-ve
dev pp-ve:34   vrf_l3_rcv[vrf]
dev pp-vrf:32  nf_hook_slow                             <-- PRE_ROUTING again, device pp-vrf
dev pp-vrf:32  ip_rcv_finish_core > ip_route_input_noref > ip_route_input_slow
dev pp-vrf:32  ip_local_deliver > nf_hook_slow > tcp_v4_rcv

A rule written once in PRE_ROUTING therefore fires twice for a VRF-enslaved packet, once per device. A counter doubles. A notrack or a NAT rule written without an interface match is applied to both passes. This is the single most surprising thing about running a firewall on a VRF host, and it falls straight out of the two lines above.

The table selection is a routing rule rather than code. ip rule show on the bench lists 1000: from all lookup [l3mdev-table], a rule whose action is to consult the table belonging to whichever VRF the packet is associated with; that number comes from vrf_fib_table (line 1119), which returns the device's tb_id. The effect is visible in the table itself:

local 10.12.0.1 dev pp-ve proto kernel scope host src 10.12.0.1

Even the local entry moved out of the global local table into table 10, which is why an address inside a VRF is unreachable from outside it without an explicit route.

Output is symmetric and produces four hook calls for one packet. vrf_l3_out (line 945) reaches vrf_ip_out (line 926), which takes the direct path vrf_ip_out_direct (line 905) when the VRF has the default queueing discipline. That function sets skb->dev = vrf_dev at line 911 and runs LOCAL_OUT with the VRF device at line 913; vrf_output_direct (line 876) then runs POST_ROUTING with it at line 884; vrf_finish_direct hands the skb back, and the ordinary __ip_local_out and ip_output run LOCAL_OUT and POST_ROUTING again with the real device. The trace shows exactly four:

Sockets and the VRF

A VRF only steers packets that are associated with it, and for locally generated traffic that association comes from the socket. ip vrf exec pp-vrf curl ... is the usual way, and it works by putting the process in a cgroup whose BPF program sets SO_BINDTODEVICE to the VRF on every socket it creates. A server is the harder half: a socket bound to the wildcard address in the default VRF does not accept connections arriving through one unless net.ipv4.tcp_l3mdev_accept is 1 (net/ipv4/sysctl_net_ipv4.c:895), with udp_l3mdev_accept (line 1198) as its datagram counterpart. Leaving those at zero and binding one listener per VRF is the stricter arrangement; turning them on gives you one listener serving every VRF, with the input device as the only way to tell clients apart.

Recap

A bond's receive handler sets skb->dev to the bond and returns RX_HANDLER_ANOTHER, so the core restarts its station list and ip_rcv sees the bond rather than the slave; recv_probe takes LACP and ARP-monitor frames out first. On transmit, a mode function picks a slave and bond_dev_queue_xmit calls dev_queue_xmit a second time, which is why the slave holds the queueing discipline that matters. A VRF does the same at L3 through l3mdev_ip_rcv, called from ip_rcv_finish before the routing decision: vrf_ip_rcv relabels the skb, marks it IPSKB_L3SLAVE and calls PRE_ROUTING a second time with the VRF device, and the output path calls LOCAL_OUT and POST_ROUTING twice each. Table selection is the l3mdev routing rule, and even the local address entry lives in the VRF table. Locally generated traffic joins a VRF through the socket, with tcp_l3mdev_accept deciding whether one listener can serve several.

Check yourself

1. You attach a token bucket shaper to bond0 and it has no effect on throughput. Explain why, and say where the shaper has to go.

Answer

The bond device's queueing discipline is bypassed because the packet is re-queued on the slave, and the slave's qdisc is the one that runs. bond_dev_queue_xmit (drivers/net/bonding/bond_main.c:297) sets skb->dev to the chosen slave and calls dev_queue_xmit a second time, which the bench trace shows as two __dev_queue_xmit lines with different devices for one skb. Attach the shaper to each slave, or give the bond an explicit qdisc and accept that the slave still has its own.

The near miss is "the bond is a virtual device so it has no qdisc at all". It has one, the default; the problem is that the second pass gets the last word.

2. Predict the count: you add nft add rule inet f prerouting counter on a host with one VRF, and send one packet in through a VRF-enslaved interface. What does the counter read, and what would make it read one?

Answer

Two, and an interface match makes it one. PRE_ROUTING runs once from ip_rcv with the enslaved device, then ip_rcv_finish calls l3mdev_ip_rcv (net/ipv4/ip_input.c:486), vrf_ip_rcv sets skb->dev to the VRF device (drivers/net/vrf.c:1340) and vrf_rcv_nfhook (line 1132) calls the same hook again. The bench capture shows two nf_hook_slow lines with different devices. Adding iif "pp-ve" or iif "pp-vrf" selects one pass.

The near miss is "two, because the packet was forwarded". No forwarding happened; this is one packet delivered locally, counted twice on the same hook.

3. Both devices relabel skb->dev and both make the stack repeat work. Name the difference in where each one intervenes, and what that means for a packet socket attached to the underlying member.

Answer

The bond intervenes at L2 inside __netif_receive_skb_core and the VRF at L3 inside ip_rcv_finish. The bond's receive handler runs before the protocol demux and returns RX_HANDLER_ANOTHER, so the entire station list including taps and tc ingress repeats with the bond device. The VRF hook runs after ip_rcv and after PRE_ROUTING, so the L2 stations run only once, on the enslaved device. A packet socket on the slave therefore sees bonded traffic normally, and a packet socket on a VRF-enslaved device sees everything because the VRF never took the frame away from it.

The near miss is "both are receive handlers". Only the bond registers one; the VRF uses the l3mdev hook, which is why their costs land on different layers.

Chapter 12

macvlan and ipvlan

~12 min · L2 · Spine: the bond of chapter 11 put many devices under one. These two put many devices on top of one, and they answer the same receive-handler verdict as the bond. The whole difference between them is which field of our skb the handler looks at, and the bench names the function that looks.

One lower device, one handler

Both drivers work by taking over the receive handler of a device you already have, which they call the lower device. macvlan_port_create registers macvlan_handle_frame (drivers/net/macvlan.c:1279); ipvlan_port_create registers ipvlan_handle_frame (drivers/net/ipvlan/ipvlan_main.c:84). Both then answer RX_HANDLER_ANOTHER after changing skb->dev, exactly like the bond.

That shared mechanism has a consequence you meet within a minute of experimenting. Trying to put an ipvlan on a lower device that already carries a macvlan fails on the bench:

# ip link add pp-iv0 link pp-lo0 type ipvlan mode l2
RTNETLINK answers: Device or resource busy

netdev_rx_handler_register (net/core/dev.c:5909) opens with if (netdev_is_rx_handler_busy(dev)) return -EBUSY (lines 5913 to 5914). There is one handler pointer per device, so a device can be a bridge port, or a bond slave, or a macvlan lower, or an ipvlan lower, and never two of those at once. That single field explains most of the "device or resource busy" messages people hit when stacking virtual devices.

The one line that differs

Set the two up on separate lower devices and look at what the kernel reports before sending anything:

lower pp-lo0  a2:b7:4b:50:89:6a   promiscuity 1     macvlan lower
macvlan       12:19:80:52:7e:cc                     its own address
lower pp-lo2  d2:61:13:ff:1b:54   promiscuity 0     ipvlan lower
ipvlan        d2:61:13:ff:1b:54                     the same address as the lower

A macvlan is a new station on the wire. It gets its own MAC address, and because the lower device must now accept frames addressed to an address that is not its own, the lower device is put into promiscuous mode. An ipvlan shares the lower device's MAC address entirely and the lower device is left alone.

Now send one TCP segment to each and compare the traces. They are identical except for a single line, and that line is the answer to the whole chapter:

macvlan, one skb:
  dev pp-lo0:36  __netif_rx > enqueue_to_backlog > __netif_receive_skb_one_core
  dev pp-lo0:36  macvlan_forward_source[macvlan]
  dev pp-mv0:40  qdisc_pkt_len_segs_init > skb_ensure_writable > ...

ipvlan, one skb:
  dev pp-lo2:39  __netif_rx > enqueue_to_backlog > __netif_receive_skb_one_core
  dev pp-lo2:39  ipvlan_get_L3_hdr[ipvlan]
  dev pp-iv0:41  qdisc_pkt_len_segs_init > skb_ensure_writable > ...

The macvlan driver's first move is to look at Ethernet addresses; macvlan_handle_frame (line 460) hashes the destination MAC through macvlan_hash_lookup (line 125) to find which upper device owns it. The ipvlan driver's first move is to parse the network header; ipvlan_handle_frame (ipvlan_core.c:781) calls ipvlan_get_L3_hdr (line 149) and then ipvlan_addr_lookup (line 366) to find which upper device owns that IP address. One demultiplexes on layer 2, one on layer 3, and the trace prints the function that does it.

Neither macvlan_handle_frame nor ipvlan_handle_frame appears in the trace itself, for the reason chapter 10 and chapter 11 met: a receive handler takes struct sk_buff **pskb, and pwru has no skb argument to read. The helper each one calls first is visible, and conveniently it is the one that differs.

macvlan modes, and where the traffic actually goes

Because a macvlan is a station with its own address, the question of whether two of them on one lower device can talk to each other has several answers, which is what the modes are (include/uapi/linux/if_link.h:1229 to 1234, and ip-link(8) documents all five):

ModeBetween two upper devices on one lower
privateNever, even if the switch would reflect the frame back.
vepaOnly if the switch reflects it; the frame goes out and must come back. This is what a hairpin-capable switch is for.
bridgeDirectly in the kernel, without touching the lower device.
passthruOne upper device takes the lower device over entirely, including its MAC.
sourceReceive only frames from a configured list of source MAC addresses.

The transmit side is macvlan_start_xmit (line 585) and macvlan_queue_xmit (line 545), where bridge mode short-circuits to a sibling and everything else hands the frame to the lower device with the macvlan's own source address on it.

ipvlan modes, and the hook the last one adds

ipvlan has three modes and they differ in how much of the stack runs on the upper device. ipvlan_handle_frame switches on the port mode at ipvlan_core.c:787.

l2 behaves like the macvlan comparison above, demultiplexing by address and delivering into the upper device before IP.

l3 changes the transmit side in a way worth being precise about. ipvlan_xmit_mode_l3 (line 603) first checks whether the destination is another ipvlan on the same lower device, and if so delivers it directly. Otherwise, line 627, it calls ipvlan_skb_crossing_ns(skb, ipvlan->phy_dev), moving the skb onto the parent device, and ipvlan_process_outbound (line 536) strips the Ethernet header before ipvlan_process_v4_outbound (line 428) performs its own route lookup with ip_route_output_flow (line 449) and calls ip_local_out (line 460). The comment above that code says it plainly: the packet is processed further in the network namespace of the main device. So an l3-mode ipvlan's outbound traffic runs the parent's LOCAL_OUT and POST_ROUTING chains, not the container's, and the container has no usable link layer of its own.

l3s exists because l3 mode bypasses the parent's connection tracking on the way in. In l3s, ipvlan_handle_frame returns RX_HANDLER_PASS (line 793) and does nothing. The device swap moves to a netfilter hook instead: ipvlan_nf_input (ipvlan_l3s.c:95) is registered at NF_INET_LOCAL_IN with priority INT_MAX (ipvl_nfops, lines 117 to 131), and it sets skb->dev = addr->master->dev at line 104. The consequence is exact: in l3s the parent's PRE_ROUTING, its routing decision and its INPUT chain all run with the lower device, conntrack sees the packet normally, and only at the very end of LOCAL_IN does the skb become the ipvlan device's.

Choosing between them

The rule follows from the MAC addresses in the first measurement. Use macvlan when each endpoint may have its own address on the wire: it gets real DHCP, it appears as a separate host to the rest of the network, and switch port security must be configured to allow several addresses per port. Use ipvlan when exactly one MAC is permitted. The kernel documentation names three such cases: a switch that allows one address per port, a switch whose address table would be exhausted, and untrusted namespaces where letting a container choose its own source MAC is a risk.

Wi-Fi is the case most readers meet first, and the machine this dossier was written on has exactly one physical interface, wlan0. Both drivers will let you create the device, since each only requires the lower device to be Ethernet-like (macvlan.c:1256, ipvlan_main.c:567). The failure is above the kernel: an 802.11 station is associated with the access point under one address, and frames the station sends with a different source address are not forwarded. So macvlan on a laptop's wireless interface builds cleanly and then drops everything, and ipvlan is the one that works. Most cloud network interfaces behave the same way for the same reason, which is why cloud CNI plugins reach for ipvlan or for routed setups rather than macvlan.

Chapter 13

IPVS: the NAT that hides in INPUT

~12 min · L3 · Spine: every chapter so far kept our skb moving forward through the chart. This one sends it backwards. A packet that the routing decision of chapter 4 classified as local, and that is therefore on its way to a socket, is picked up in INPUT, rewritten, and pushed back out through OUTPUT without a socket ever seeing it.

Why INPUT, of all places

IPVS load-balances a virtual service, an address and port clients connect to, across a set of real servers. The virtual address has to be configured as a local address on the director, and that one configuration choice decides everything about where the code runs.

Chapter 4 showed ip_route_input_slow returning RTN_LOCAL for any address the host owns, which stores ip_local_deliver as the route's input function. So a packet to the virtual address is routed for local delivery, runs the LOCAL_IN hooks, and would next be handed to tcp_v4_rcv to find a socket that does not exist. IPVS intercepts it in the last place it can, which is why a load balancer appears in a chain most people associate with host firewalling.

The registrations are ip_vs_ops4[] (net/netfilter/ipvs/ip_vs_core.c:2325 to 2372), six entries, and the priorities are chosen with care:

HookFunctionPriorityJob
LOCAL_INip_vs_out_hookNAT_SRC - 2Reply direction, rewrite the source back to the virtual address
LOCAL_INip_vs_in_hookNAT_SRC - 1Request direction: schedule and send to a real server
LOCAL_OUTip_vs_out_hookNAT_DST + 1Replies from a local real server
LOCAL_OUTip_vs_in_hookNAT_DST + 2Requests from a process on the director itself

Lookup, schedule, rewrite, re-inject

ip_vs_in_hook first asks whether this packet belongs to a connection it already knows, pp->conn_in_get reaching ip_vs_conn_in_get_proto (lines 2176 to 2180). On a miss it schedules: ip_vs_try_to_schedule (line 1648) leads to ip_vs_schedule (line 619), which finds the service, calls the scheduler's sched->schedule (line 706) to pick a real server, and records the decision with ip_vs_conn_new (line 727). The scheduler is a small pluggable module, rr, wrr, least-connection and so on, and it is consulted once per connection.

What ip_vs_conn_new builds is a struct ip_vs_conn (include/net/ip_vs.h:813) holding the client address and port, the virtual address and port, the real server's address and port, and a function pointer packet_xmit (line 877). That pointer is the forwarding method, and it is what the hook calls at line 2257 once the connection is known:

        ret = cp->packet_xmit(skb, cp, pp, &iph);
        /* do not touch skb anymore */

It routes to the real server, makes the header writable with skb_ensure_writable (line 840) because the skb may be shared, calls the protocol's dnat_handler to fix the port and checksums (line 847), then does the rewrite itself:

        ip_vs_notrack(skb);

A packet that is inside LOCAL_IN calls the LOCAL_OUT hooks directly and then dst_output, and the function returns NF_STOLEN so the input path it came from stops. The skb has jumped from one side of the chart to the other without passing through a socket, and it will run POST_ROUTING on the way out as a normal transmitted packet.

skb->ipvs_property (include/linux/skbuff.h:1010, a single bit) is how that does not become a loop: the hooks test it and leave a packet IPVS already owns alone. Chapter 9 met the other half of this bit without needing it, in the list of things skb_scrub_packet clears through ipvs_reset (skbuff.h:5154). An IPVS-owned skb that crosses into another namespace or another device arrives with the flag gone, which is correct, because the new namespace's IPVS knows nothing about it.

The reply, and the three forwarding methods

The return packet from the real server carries its own address as the source, and the client will reject that, so it must be rewritten back to the virtual address. That is ip_vs_out_hook (line 1510), which looks the connection up in the reverse direction with ip_vs_conn_out_get_proto (line 1579) and calls handle_response (line 1439). That applies the protocol's snat_handler and then ip_vs_route_me_harder (line 1483), because changing the source address can change which route and which source address the packet should use.

Masquerading is only one of three methods, and the other two exist to keep the return traffic away from the director entirely:

MethodFunctionWhat it changesReturn path
Masqueradeip_vs_nat_xmit (ip_vs_xmit.c:787)Destination address and portBack through the director, rewritten
Direct routingip_vs_dr_xmit (line 1439)Only the destination MAC addressStraight from the real server to the client
Tunnellingip_vs_tunnel_xmit (line 1147)Wraps the packet in an outer IP headerStraight from the real server to the client

Direct routing leaves the IP header untouched, which means every real server must itself own the virtual address, usually on a loopback alias with ARP suppressed, and must be on the same link as the director. Tunnelling removes the same-link requirement at the cost of an encapsulation header and the reduced usable size that goes with it. Both give up the ability to rewrite ports, and both mean the director sees only half of each connection.

One knob deserves naming. By default IPVS asks conntrack to stay out of the way, which is the ip_vs_notrack branch above. Setting net.ipv4.vs.conntrack to 1 makes it call ip_vs_update_conntrack instead, teaching conntrack about the translation so that other NAT rules and stateful firewall rules behave. The cost is a conntrack entry per connection on a machine whose whole purpose is to carry a great many of them.

kube-proxy in IPVS mode

Kubernetes uses exactly this machinery, and knowing the chapter above makes its odd-looking setup obvious. kube-proxy creates a dummy device, conventionally kube-ipvs0, and adds every service cluster address to it. That is not because anything listens there; it is because the addresses must be local for the routing decision to return RTN_LOCAL and send the packet into LOCAL_IN where ip_vs_in_hook is waiting. Each service becomes a virtual service and each ready endpoint a real server, with masquerading as the forwarding method.

The iptables rules that remain are few, and they use ipsets rather than one rule per service, which is the whole performance argument: adding a service adds a hash-table entry rather than lengthening a chain that is walked linearly for every packet. What the rules still do is mark traffic that needs source NAT, for the cases where the reply would otherwise not come back through the node.

Recap

A virtual address must be local on the director, so the routing decision returns RTN_LOCAL and the packet enters LOCAL_IN, which is where ip_vs_in_hook is registered just below the source-NAT priority. It looks the connection up, and on a miss ip_vs_schedule picks a real server and ip_vs_conn_new records the choice in a struct ip_vs_conn whose packet_xmit pointer is the forwarding method. For masquerading that is ip_vs_nat_xmit, which rewrites the destination and then calls the LOCAL_OUT hooks directly from inside LOCAL_IN, returning NF_STOLEN; skb->ipvs_property marks the skb so the hooks do not act on it twice, and skb_scrub_packet clears that bit at a namespace boundary. Replies are rewritten by ip_vs_out_hook and re-routed. Direct routing and tunnelling avoid the return trip entirely. kube-proxy's kube-ipvs0 dummy device exists only to make service addresses local so this path is reached.

Check yourself

1. Why must the virtual address be configured on a local interface, and what would the packet's fate be if it were not?

Answer

Because IPVS's request-direction hook is registered on LOCAL_IN, and only a local address gets a packet there. ip_route_input_slow returns RTN_LOCAL for an address the host owns, which stores ip_local_deliver as the route's input function; without the address configured, the lookup returns RTN_UNICAST and the packet takes the forward path or is dropped as unroutable, never reaching ip_vs_in_hook (net/netfilter/ipvs/ip_vs_core.c:2097). This is exactly why kube-proxy puts every service address on the kube-ipvs0 dummy device.

The near miss is "something has to listen on it". Nothing listens; the packet is taken one hook before tcp_v4_rcv would look for a socket, which is why ss shows nothing on a working director.

2. Trace the path: a client SYN reaches a director using the masquerading method. List the hooks it visits in order, and name the moment a socket lookup would have happened but did not.

Answer

PRE_ROUTING, then the routing decision, then LOCAL_IN, then LOCAL_OUT, then POST_ROUTING. Inside LOCAL_IN, ip_vs_in_hook schedules and calls ip_vs_nat_xmit (ip_vs_xmit.c:787), which rewrites the destination and calls ip_vs_nat_send_or_cont (line 666); that runs NF_HOOK(..., NF_INET_LOCAL_OUT, ...) followed by dst_output and returns NF_STOLEN. The socket lookup that did not happen is tcp_v4_rcv, which ip_local_deliver_finish would have reached had LOCAL_IN completed normally.

The near miss is "it is forwarded, so it visits FORWARD". FORWARD is never entered; the route type was local, and IPVS provides the crossing itself.

3. A colleague reports that IPVS on their director stops working for traffic that arrives through a veth pair from a container, but works for traffic from the physical interface. Which single bit would you suspect, and which function clears it?

Answer

skb->ipvs_property (include/linux/skbuff.h:1010), cleared by skb_scrub_packet through ipvs_reset (skbuff.h:5154, called at net/core/skbuff.c:6292). Every veth crossing runs __dev_forward_skb and therefore the scrub, so an skb that IPVS had already claimed arrives on the far side with the flag gone and the hooks will act on it again. That is deliberate: the flag is meaningful only within one namespace's IPVS state, which knows nothing of the other's.

The near miss is "conntrack state was lost". Conntrack is also reset by the same scrub, but IPVS does not rely on conntrack by default; ip_vs_notrack is the normal path unless net.ipv4.vs.conntrack is set.

Cilium on one node: the tc hook takes over

~12 min · BPF · Spine: chapter 9 sent our skb through a veth pair and the receive half ran again in the peer's namespace. Attach one BPF program to the host end of that pair and the second half of the journey disappears: the skb is handed to the destination pod's device from inside the first namespace's softirq, and the netfilter chart is never entered.

How the jump is made

Inside Cilium, the path is a chain of tail calls ending in one helper. cil_from_container (bpf/bpf_lxc.c:2212) tail-calls tail_handle_ipv4 (line 2157), which reaches handle_ipv4_from_lxc (line 1591). That function looks the destination up in the ipcache, a map from address to security identity, checks egress policy with policy_can_egress4, and calls ipv4_forward_to_destination (line 1187). When the destination is an endpoint on this node, that reaches ipv4_local_delivery (bpf/lib/local_delivery.h:229), which rewrites the source and destination MAC addresses to the pair the destination pod expects (line 242) and then reaches redirect_ep (line 82):

if (!use_fast_redirect)
        return (int)ctx_redirect(ctx, ifindex, 0);
if (from_tunnel)
        ctx_change_type(ctx, PACKET_HOST);
return ctx_redirect_peer(ctx, ifindex, 0);

ctx_redirect_peer is the bpf_redirect_peer helper, and it is the one that matters. The kernel side is skb_do_redirect (net/core/filter.c:2519), whose peer branch begins at line 2531:

if (flags & BPF_F_PEER) {
        if (unlikely(!skb_at_tc_ingress(skb)))    goto out_drop;
        dev = skb_get_peer_dev(dev);
        if (unlikely(!dev || !(dev->flags & IFF_UP) ||
                     net_eq(net, dev_net(dev))))  goto out_drop;
        skb->dev = dev;
        dev_sw_netstats_rx_add(dev, skb->len);
        skb_scrub_packet(skb, false);
        return -EAGAIN;
}

Four things in nine lines. skb_get_peer_dev (line 2509) calls the device's ndo_get_peer_dev, which is how a veth device names its other end without the caller knowing anything about veth. The namespace test at line 2537 is a drop condition: the peer must be in a different network namespace, so this helper cannot be used to shortcut within one namespace. skb->dev is set to the peer at line 2539. And skb_scrub_packet(skb, false) at line 2541 passes false for the cross-namespace flag, which by chapter 9's table means the route and the conntrack pointer are dropped but skb->mark is kept, even though the namespace really is changing. Cilium relies on that mark surviving.

The return value is the trick. -EAGAIN is not an error; it is a message to the caller. In sch_handle_ingress (net/core/dev.c:4493):

case TC_ACT_REDIRECT:
        __skb_push(skb, skb->mac_len);
        if (skb_do_redirect(skb) == -EAGAIN) {
                __skb_pull(skb, skb->mac_len);
                *another = true;
                break;
        }

and in __netif_receive_skb_core, line 6069, if (another) goto another_round; jumps back to the label at line 6017. This is the same another_round the bond and macvlan of the last two chapters use. The skb re-enters the station list from the top with a new device, that device is the destination pod's eth0, and because that device lives in another namespace the rest of the receive path runs there. No new softirq, no queue, no second driver.

The same program, deciding the other way

Policy is enforced in the same program, before any of that. The cluster carries a policy admitting only one security group to a particular server, and a client outside that group produces a trace with the same opening and a different last line:

The client's curl reports a timeout. The packet is freed inside the tc hook with a drop reason the kernel exposes to tracing, and it never reaches the destination pod, the host stack, or a counter in any iptables chain. Both the permit and the deny happen in the same place, which is the point of doing policy here rather than in the chart.

Host to pod, and pod to host

Traffic between the node itself and a pod cannot use the peer redirect, because the host end of the journey is the node's own namespace. Cilium builds a second veth pair for that, cilium_host and cilium_net, and attaches programs to both ends: cil_from_host on cilium_host egress, cil_to_host on cilium_host ingress and on cilium_net ingress. cilium_host carries the node's router address and has ARP disabled. In the cross-node capture of the next chapter, cil_to_host and cil_from_host appear twenty-five times each, which is the health and node-local traffic using exactly this pair.

One configuration option changes the shape of everything above, and it is worth naming because a great deal of older writing assumes it. With endpoint routes enabled, Cilium also attaches cil_to_container to the egress side of each pod's veth pair and installs a per-pod route in the host, so packets are delivered by the host's routing table rather than by a peer redirect, and ingress policy runs in that second program. The bench cluster has endpoint routes off, which is why no cil_to_container appears in any capture and why ingress policy is resolved by a tail call inside the sender's program instead.

VXLAN, Geneve and native routing

The tunnel protocol changes very little of the above. VXLAN uses UDP 8472 and Geneve 6081 (pkg/defaults/defaults.go:475 and 477), the transmit function becomes vxlan_xmit and the receive one vxlan_rcv, and the identity travels in the VXLAN network identifier. The shape of the path is identical. Geneve adds a variable-length option field for extra metadata alongside the identity.

Native routing removes the tunnel. Instead of the encapsulation branch, ipv4_forward_to_destination takes the host-routing branch (bpf/bpf_lxc.c:1547) and calls fib_redirect_v4 (bpf/lib/fib.h:263) at line 1550, which performs a bpf_fib_lookup and redirects to the physical device. The far node's eth0 receives the pod address directly, cil_from_netdev finds it in the ipcache as a local endpoint, and delivery is the peer redirect of chapter 14. The cluster has to be on a network that will route pod addresses for this to work, which is the trade: no encapsulation overhead, and the fabric has to know about your pod ranges.

Two facts are worth stating plainly. First, the source address changes inside cil_to_netdev, next to a checksum fix-up, and nowhere near a MASQUERADE rule. On a cluster with legacy host routing the world path really does enter the host's PRE_ROUTING, routing decision, FORWARD and POST_ROUTING chains, and an iptables masquerade rule really does do the translation. Recap

For a destination on another node, encap_and_redirect_lxc sets a tunnel key whose identifier is the sender's security identity and whose remote address is the other node, then redirects to cilium_geneve, where cil_to_overlay and geneve_xmit build an outer UDP packet. From there the kernel treats it as ordinary local output, so LOCAL_OUT and POST_ROUTING run for the outer packet; on the far node PRE_ROUTING and LOCAL_IN run for it too, udp_rcv reaches geneve_udp_encap_recv, the headers are pulled, and cil_from_overlay reads the identity back and redirects into the destination pod. Measured on the bench, all 116 hook calls in the receiving node's namespace carried the outer tuple and none carried the inner one. Native routing replaces the tunnel with fib_redirect_v4. For world traffic with BPF host routing on, the same branch redirects straight to the physical device and cil_to_netdev rewrites the source address through snat_v4_nat, giving zero netfilter hook calls inside the node; with legacy host routing the packet takes pass_to_stack and the familiar chains and iptables masquerade apply.

1. You write an iptables rule counting traffic to a pod address on another node and it stays at zero, while a rule counting UDP port 6081 climbs steadily. Explain both observations with one mechanism.

Answer

The near miss is "the rule is on the wrong node". It would read zero on both; the inner addresses are never visible to netfilter on either side.

2. Trace the path: name every point between the two pods where skb->dev changes, for a cross-node connection through the tunnel.

Answer

Four times. First eth_type_trans inside __dev_forward_skb2 sets it to the host end of the source pod's veth pair. Second, skb_do_redirect from cil_from_container sets it to cilium_geneve through the ordinary redirect path. Third, after the outer packet is routed, the transmit path sets it to the physical device, and on the far node the receive path sets it to that node's eth0. Fourth, gro_cells_receive after decapsulation delivers on cilium_geneve, and then skb_do_redirect from cil_from_overlay sets it to the destination pod's eth0. The near miss is counting the wire as a device change. The two kind nodes are containers on one kernel here, so the capture shows the bridge crossing too; on real hardware that hop is a driver and a NIC instead.

Four pieces of machinery that change these answers

The flowtable. nf_flow_offload_ip_hook (net/netfilter/nf_flow_table_ip.c:807) sits on the netdev ingress hook, ahead of everything in the chart. Once a forwarded connection has been offloaded, later packets are matched, rewritten and transmitted from that hook, so FORWARD and conntrack are skipped for the rest of the connection. The symptom is rule counters that stop climbing while traffic continues.

tcx. Chapter 3 met it; the ordering is worth pinning down. In sch_handle_ingress, tcx_run runs at net/core/dev.c:4486 and the legacy tc_run at line 4490 executes only if tcx answered TC_ACT_UNSPEC. tcx programs therefore run first, attach as links, and several can share one device without clobbering each other.

netkit. The device Cilium moves to after veth. netkit_xmit (drivers/net/netkit.c:92) runs a BPF program inside the transmit function and then calls __netif_rx for the peer at line 121, one step earlier than a tc hook on a veth host end, removing a device from the path.

BIG TCP and the ingress hook. gso_ipv4_max_size (include/linux/netdevice.h:2168) carries segmentation-offload sizes past the old 64 KB ceiling, cutting how often everything above runs at all. NF_INET_INGRESS (include/uapi/linux/netfilter.h:49) gives nftables a hook at device ingress, before ip_rcv, where tc and XDP already were.

What this document did not establish

Being honest about the gaps is more useful than pretending there are none.

  • Unix sockets were not traced. pwru filters on IP headers and a unix skb has none; the node has no bpftrace. The bpftrace block in that lab is labelled expected.
  • IPVS was not exercised. ipvsadm is absent and installing it was out of scope, so no virtual service existed. The ip_vs module does load on this kernel; it was loaded once, found inert, and unloaded.
  • br_netfilter was not loaded. Its hooks register globally and the sysctl defaults to on, which would have changed packet handling for the bridge carrying the live cluster. The plain bridge path was measured; that half is from the source.
  • Host labs were not run. Host-side work needs a root password, so those labs are written for you to run and their expected output is marked.
  • VXLAN and native routing were not measured. Both cluster configurations are in lab/ and were deliberately not created.
  • Diagrams were never rendered. No browser on the bench. Their source was checked mechanically for the header line, entity escaping and participant aliases, and nothing more.

One habit is worth taking away. Every claim here that turned out to be wrong was wrong the same way: a name or a line number remembered from an older kernel. The IPVS hooks were renamed, skb_scrub_packet does not clear what folklore says it clears, and a line number in the routing chapter was off by one. Checking a citation costs one sed -n.

Recap

Twelve scenarios reduce to three mechanisms: consume the skb and re-queue it elsewhere, relabel it and restart the core, or call a receive function from inside a transmit function. The netfilter chart is still an accurate map of the stack's middle, and four newer pieces of machinery give packets ways around it: the flowtable skips FORWARD after the first packet, tcx runs before legacy tc and attaches as a link, netkit runs BPF inside the transmit function and removes a device, and BIG TCP reduces how often any of this runs at all. What this document did not measure is listed above rather than glossed.

Circular array of records, each pointing at a buffer; the card writes frame lengths into them.
DMA
The card writing frame bytes into RAM without the CPU.
page pool
Per-ring recycling allocator of DMA-mapped page fragments for receive buffers.
hardirq
The interrupt handler proper; runs with interrupts off; here it only schedules NAPI.
softirq, NET_RX_SOFTIRQ
Deferred work with interrupts on; the receive softirq's handler is net_rx_action.
NAPI, poll, weight
Interrupt once, then poll the ring up to weight (64) frames per call.
budget, time squeeze
net_rx_action's limits: 300 packets or 2,000 us; exceeding them increments time_squeeze.
GRO
Generic receive offload: merging consecutive same-flow segments into one skb inside the poll.
backlog, softnet_data
Per-CPU queue input_pkt_queue plus a fake NAPI; filled by netif_rx, drained by process_backlog.
netif_rx
The entry for callers already holding an skb; queues into the backlog.
RSS, RPS
Hardware and software spreading of flows across CPUs; RPS uses another CPU's backlog.

Chapter 2 · XDP: the hook that runs before the skb exists

XDP

xdp_buff
The program's view of the frame: data start and end, metadata area, buffer size, receive queue.
XDP verdict
XDP_PASS, XDP_DROP, XDP_TX, XDP_REDIRECT, XDP_ABORTED.
native, generic, offload
Where the program runs: in the driver poll, at the top of the core receive loop, or on the card.
XDP_PACKET_HEADROOM
The 256 bytes of free space in front of the data that a program is promised; generic mode copies to get it.
xdp_frame
An xdp_buff converted for queueing, stored in the buffer's own headroom.
devmap, cpumap
Redirect targets: another device's transmit path, or another CPU that builds the skb there.
AF_XDP
A socket that receives redirected frames in user space with no skb; named here only.
skb_pp_cow_data
Copy an skb's bytes into a page-pool buffer and build a new skb; what veth does before native XDP on a cloned skb.
