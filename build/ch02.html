Chapter 2

XDP: the hook that runs before the skb exists

~RT2 min · BPF · Spine: our skb is about to be built inside the driver's poll. One program type is allowed to see the frame before that happens, and it is the reason a packet can be dropped for almost nothing. The veth chapter depends on what this one says about copying, so we take the detour now.

A program on the raw buffer

XDP, the eXpress Data Path, is a BPF program type that a driver runs on a received frame while the frame is still just bytes in a DMA buffer. The program does not receive an skb, because none has been allocated. It receives an xdp_buff (include/net/xdp.h:86): pointers to the start and end of the frame data, a pointer to a small metadata area in front of the data, the size of the buffer, and a reference to the receive queue it came from. That is the whole world the program can see.

It returns one of five verdicts, the enum xdp_action at include/uapi/linux/bpf.h:6576. XDP_PASS lets the driver continue and build the skb. XDP_DROP hands the buffer straight back to the ring for reuse. XDP_TX sends the same buffer back out of the same device, which is how a load balancer answers from the card. XDP_REDIRECT hands the buffer to another device, another CPU, or a user-space socket. XDP_ABORTED is a drop that also fires a tracepoint, meant for program errors.

Here is the absence list, and it is the reason XDP exists. At the moment the program runs there is no skb, no protocol field, no device lookup, no namespace check, no tap, no tc, no netfilter hook, no route, no socket. A frame dropped by XDP has cost the card one DMA write and the CPU one descriptor read and one program run. Everything in chapters 3 to 7 has been skipped. This is wonderful for a flood filter and useless for anything that needs to know what the packet means to a socket.

Three places to attach the same program

The same program object can be attached in three modes, chosen with ip link set dev DEV xdp, xdpgeneric or xdpoffload, all routed through dev_xdp_install (net/core/dev.c:10327).

Native XDP means the driver itself calls the program from inside its poll, on the DMA buffer, before it builds an skb. In igb that call sits in the receive loop of chapter 1, between reading the descriptor and igb_build_skb. Only drivers written for it support it. Offloaded XDP means the card's own processor runs the program and the host never sees dropped frames at all; a handful of cards do this. Generic XDP is the fallback for every other device: the skb is built as usual, and the core runs the program on it at the very top of the L2 receive loop, at net/core/dev.c:6023 to 6035, through do_xdp_generic (line 5670).

Generic mode has to fake the environment native mode gets for free. netif_receive_generic_xdp (line 5590) pushes the Ethernet header back into view (line 6604), then checks whether the skb is cloned, is not linear, or has less than XDP_PACKET_HEADROOM, 256 bytes, of free space in front of the data (lines 5607 to 5610). If any of those hold, netif_skb_check_for_xdp (line 5565) calls pskb_expand_head and skb_linearize (lines 5575 to 5588), which allocate a new head buffer and copy the bytes into it. Only then does bpf_prog_run_generic_xdp run. So generic XDP can be slower than no XDP: the program is cheap, the copy that makes room for it is not. On the veth bench the trace reads exactly that way: __netif_receive_skb_one_core, pskb_expand_head, skb_release_data, bpf_prog_run_generic_xdp, then the tc and IP stations of chapter 3.

One consequence of the position matters for debugging. Generic XDP runs at line 6026, and the tap loop that feeds packet sockets starts at line 6048. A frame dropped by a generic XDP program is never seen by tcpdump on that device. Native XDP drops are invisible even earlier.

Redirect: leaving without an skb

XDP_REDIRECT is the verdict that turned XDP from a filter into a forwarding plane. The program calls the bpf_redirect or bpf_redirect_map helper (net/core/filter.c:4717) naming a target, and after the program returns, the driver calls xdp_do_redirect (line 4593). That function first converts the xdp_buff into an xdp_frame (include/net/xdp.h:294, conversion at line 430), a compact record stored in the buffer's own headroom so the frame can be queued without allocating anything. Then it looks at the target type.

A devmap target (kernel/bpf/devmap.c:552) queues the frame for another device's transmit function, so a frame can enter one card and leave another with no skb ever existing. A cpumap target (kernel/bpf/cpumap.c:793) queues the frame for another CPU, where a kernel thread builds an skb from it with xdp_build_skb_from_frame (net/core/xdp.c:849) and enters the normal receive path there. That is receive packet steering done before the skb rather than after it. An AF_XDP socket target copies or maps the frame into a user-space ring, and the kernel network stack never touches it again; that is the kernel-bypass path, and this document only names it.

Native XDP on a veth: the copy you did not order

A veth supports native XDP, and this is where the chapter earns its place in the spine. A veth does not receive DMA buffers; it receives skbs from its peer. So to run a native XDP program it must turn an skb into an xdp_buff, and it does so in veth_xdp_rcv_skb (drivers/net/veth.c:790) by calling veth_convert_skb_to_xdp_buff (line 751). Read the test at the top of that function, lines 758 to 760: if the skb is shared, if its head is locked, if it is not linear, or if it has less than 256 bytes of headroom, then skb_pp_cow_data (net/core/skbuff.c:942) allocates a fresh page-pool buffer, copies the bytes into it, builds a new skb around it with napi_build_skb, copies the header fields across, and frees the old skb with consume_skb.

A TCP segment always trips that test. TCP transmits a clone of the skb it keeps for retransmission (net/ipv4/tcp_output.c:1563), and a clone's head is locked because the data is shared with the original. So on the bench, with our program attached natively to the receiving end, the trace shows the first skb entering veth_xdp_rcv_skb and dying four lines later in kfree_skbmem. The XDP program line then appears against an address that matches no skb, because it is the address of the xdp_buff. And a second skb, with a new address, appears at eth_type_trans and continues through gro_receive_skb into the stack. Hold on to this. It is the one case in which a veth creates a new skb, and chapter 9 will point back here.

Try it

Build the smallest useful program, attach it both ways on the veth bench, and watch where the skb dies.

cd lab/02-xdp && clang -O2 -g -target bpf -c xdp_pass.c -o xdp_pass.o
sudo lab/09-veth.sh up
# native on the receiving end, then trace with the XDP program included
sudo ip netns exec pp-b ip link set dev vb xdp obj lab/02-xdp/xdp_pass.o sec xdp
sudo pwru --kmods veth --filter-trace-xdp 'tcp and host 10.9.0.2 and port 8080'
# in another terminal
sudo ip netns exec pp-b python3 -m http.server 8080 --bind 10.9.0.2 &
sudo ip netns exec pp-a curl -s -o /dev/null http://10.9.0.2:8080/
# how many frames did the program see
sudo bpftool map dump name xdp_count
# swap to generic and trace again
sudo ip netns exec pp-b ip link set dev vb xdp off
sudo ip netns exec pp-b ip link set dev vb xdpgeneric obj lab/02-xdp/xdp_pass.o sec xdp

In the native trace the SYN's first skb ends with veth_xdp_rcv_skb, consume_skb, kfree_skbmem; a line named after the program follows, tagged [bpf](xdp); then a new skb address starts at eth_type_trans. In the generic trace one skb runs all the way through, and pskb_expand_head appears just before bpf_prog_run_generic_xdp. On your Wi-Fi card only generic mode attaches, because the driver has no native hook.

Recap

XDP runs a BPF program on an xdp_buff before any skb exists, and returns pass, drop, transmit, redirect or abort. Native mode runs it in the driver poll on the DMA buffer; generic mode runs it at the top of the L2 loop, after building the skb and after copying its head if the headroom is short; offload runs it on the card. Redirect converts the buffer to an xdp_frame and queues it to another device, another CPU, or a user-space socket. On a veth, native XDP converts the incoming skb and, for any cloned skb, copies it into a page-pool buffer and builds a new skb, freeing the old one.

Check yourself

1. A colleague attaches a generic XDP program that drops all UDP to port 53 on eth0, then runs tcpdump -i eth0 port 53 to confirm and sees nothing at all, including the queries that should be arriving. They conclude the program is dropping everything. What is the mistake?

Answer

The program may be working exactly as written; tcpdump cannot see what generic XDP drops. Generic XDP runs at net/core/dev.c:6023 to 6035, and the tap loop that feeds packet sockets starts at line 6048, after it. A dropped frame never reaches the taps. To confirm the drop, read the program's own counters with bpftool map dump, or use pwru --filter-trace-xdp, which prints the program run and its verdict.

The near miss is "tcpdump sees everything the NIC receives because it runs at L2". It sees everything that reaches the tap loop. Native and generic XDP both sit before it, and so does a hardware drop.

2. Predict the value: a TCP segment crosses a veth pair whose receiving end has a native XDP program attached. How many skbs are allocated for that segment on the receive side, and which line of code decides it?

Answer

One new skb, so two in total counting the one that arrived. veth_convert_skb_to_xdp_buff (drivers/net/veth.c:758 to 760) tests whether the skb is shared, head-locked, non-linear or short on headroom. A TCP segment is transmitted as a clone (net/ipv4/tcp_output.c:1563), and a clone's head is locked, so the test passes and skb_pp_cow_data (net/core/skbuff.c:942) builds a new skb and frees the old one with consume_skb.

The near miss is "zero, because the program returned PASS and nothing was dropped". The copy is not about the verdict. It happens before the program runs, to give it a private, linear, roomy buffer. An ICMP echo from ping is not cloned and has enough headroom, so it would pass the test and keep its skb.

3. In a pwru trace with --filter-trace-xdp, the line naming the XDP program carries an address that appears nowhere else in the trace, before or after. Is the tracer confused?

Answer

No. pwru's first column is the address of the object passed to the probed function. For every kernel function that is an skb. For an XDP program it is the xdp_buff, because at that moment there is no skb to print. On a veth the buffer lives on the stack of veth_xdp_rcv_skb (drivers/net/veth.c:790, the vxbuf local), so its address is reused by every frame and matches no skb group.

The near miss is treating the address as a new skb and concluding that XDP allocated one. XDP allocates nothing. The new skb, when there is one, is built afterwards by skb_pp_cow_data and shows up as its own group starting at eth_type_trans.
