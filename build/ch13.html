Chapter 13

IPVS: the NAT that hides in INPUT

~RT13 min · L3 · Spine: every chapter so far kept our skb moving forward through the chart. This one sends it backwards. A packet that the routing decision of chapter 4 classified as local, and that is therefore on its way to a socket, is picked up in INPUT, rewritten, and pushed back out through OUTPUT without a socket ever seeing it.

Why INPUT, of all places

IPVS load-balances a virtual service, an address and port clients connect to, across a set of real servers. The virtual address has to be configured as a local address on the director, and that one configuration choice decides everything about where the code runs.

Chapter 4 showed ip_route_input_slow returning RTN_LOCAL for any address the host owns, which stores ip_local_deliver as the route's input function. So a packet to the virtual address is routed for local delivery, runs the LOCAL_IN hooks, and would next be handed to tcp_v4_rcv to find a socket that does not exist. IPVS intercepts it in the last place it can, which is why a load balancer appears in a chain most people associate with host firewalling.

The registrations are ip_vs_ops4[] (net/netfilter/ipvs/ip_vs_core.c:2325 to 2372), six entries, and the priorities are chosen with care:

HookFunctionPriorityJob
LOCAL_INip_vs_out_hookNAT_SRC - 2Reply direction, rewrite the source back to the virtual address
LOCAL_INip_vs_in_hookNAT_SRC - 1Request direction: schedule and send to a real server
LOCAL_OUTip_vs_out_hookNAT_DST + 1Replies from a local real server
LOCAL_OUTip_vs_in_hookNAT_DST + 2Requests from a process on the director itself
FORWARDip_vs_forward_icmp99ICMP for IPVS connections
FORWARDip_vs_out_hook100Reply rewriting on the forwarded path

Both LOCAL_IN entries sit just below NF_IP_PRI_NAT_SRC, so IPVS runs before conntrack's source NAT would; both LOCAL_OUT entries sit just above NF_IP_PRI_NAT_DST, so it runs after conntrack's destination NAT. Note also that the names changed: older material calls these ip_vs_in, ip_vs_reply4 and friends, and in 7.2 there are two family-agnostic hooks, ip_vs_in_hook (line 2097) and ip_vs_out_hook (line 1510), with ip_vs_ops6[] (line 2374) mirroring the table above.

Lookup, schedule, rewrite, re-inject

ip_vs_in_hook first asks whether this packet belongs to a connection it already knows, pp->conn_in_get reaching ip_vs_conn_in_get_proto (lines 2176 to 2180). On a miss it schedules: ip_vs_try_to_schedule (line 1648) leads to ip_vs_schedule (line 619), which finds the service, calls the scheduler's sched->schedule (line 706) to pick a real server, and records the decision with ip_vs_conn_new (line 727). The scheduler is a small pluggable module, rr, wrr, least-connection and so on, and it is consulted once per connection.

What ip_vs_conn_new builds is a struct ip_vs_conn (include/net/ip_vs.h:813) holding the client address and port, the virtual address and port, the real server's address and port, and a function pointer packet_xmit (line 877). That pointer is the forwarding method, and it is what the hook calls at line 2257 once the connection is known:

ip_vs_in_stats(cp, skb);
ip_vs_set_state(cp, IP_VS_DIR_INPUT, skb, pd, iph.len);
if (cp->packet_xmit)
        ret = cp->packet_xmit(skb, cp, pp, &iph);
        /* do not touch skb anymore */

For the masquerading method, packet_xmit is ip_vs_nat_xmit (net/netfilter/ipvs/ip_vs_xmit.c:787). It routes to the real server, makes the header writable with skb_ensure_writable (line 840) because the skb may be shared, calls the protocol's dnat_handler to fix the port and checksums (line 847), then does the rewrite itself:

ip_hdr(skb)->daddr = cp->daddr.ip;
ip_send_check(ip_hdr(skb));

Then the part that makes this chapter's title true, ip_vs_nat_send_or_cont (line 666):

skb->ipvs_property = 1;
if (likely(!(cp->flags & IP_VS_CONN_F_NFCT)))
        ip_vs_notrack(skb);
else
        ip_vs_update_conntrack(skb, cp, 1);
...
NF_HOOK(pf, NF_INET_LOCAL_OUT, cp->ipvs->net, NULL, skb,
        NULL, skb_dst(skb)->dev, dst_output);

A packet that is inside LOCAL_IN calls the LOCAL_OUT hooks directly and then dst_output, and the function returns NF_STOLEN so the input path it came from stops. The skb has jumped from one side of the chart to the other without passing through a socket, and it will run POST_ROUTING on the way out as a normal transmitted packet.

skb->ipvs_property (include/linux/skbuff.h:1010, a single bit) is how that does not become a loop: the hooks test it and leave a packet IPVS already owns alone. Chapter 9 met the other half of this bit without needing it, in the list of things skb_scrub_packet clears through ipvs_reset (skbuff.h:5154). An IPVS-owned skb that crosses into another namespace or another device arrives with the flag gone, which is correct, because the new namespace's IPVS knows nothing about it.

The reply, and the three forwarding methods

The return packet from the real server carries its own address as the source, and the client will reject that, so it must be rewritten back to the virtual address. That is ip_vs_out_hook (line 1510), which looks the connection up in the reverse direction with ip_vs_conn_out_get_proto (line 1579) and calls handle_response (line 1439). That applies the protocol's snat_handler and then ip_vs_route_me_harder (line 1483), because changing the source address can change which route and which source address the packet should use.

Masquerading is only one of three methods, and the other two exist to keep the return traffic away from the director entirely:

MethodFunctionWhat it changesReturn path
Masqueradeip_vs_nat_xmit (ip_vs_xmit.c:787)Destination address and portBack through the director, rewritten
Direct routingip_vs_dr_xmit (line 1439)Only the destination MAC addressStraight from the real server to the client
Tunnellingip_vs_tunnel_xmit (line 1147)Wraps the packet in an outer IP headerStraight from the real server to the client

Direct routing leaves the IP header untouched, which means every real server must itself own the virtual address, usually on a loopback alias with ARP suppressed, and must be on the same link as the director. Tunnelling removes the same-link requirement at the cost of an encapsulation header and the reduced usable size that goes with it. Both give up the ability to rewrite ports, and both mean the director sees only half of each connection.

One knob deserves naming. By default IPVS asks conntrack to stay out of the way, which is the ip_vs_notrack branch above. Setting net.ipv4.vs.conntrack to 1 makes it call ip_vs_update_conntrack instead, teaching conntrack about the translation so that other NAT rules and stateful firewall rules behave. The cost is a conntrack entry per connection on a machine whose whole purpose is to carry a great many of them.

kube-proxy in IPVS mode

Kubernetes uses exactly this machinery, and knowing the chapter above makes its odd-looking setup obvious. kube-proxy creates a dummy device, conventionally kube-ipvs0, and adds every service cluster address to it. That is not because anything listens there; it is because the addresses must be local for the routing decision to return RTN_LOCAL and send the packet into LOCAL_IN where ip_vs_in_hook is waiting. Each service becomes a virtual service and each ready endpoint a real server, with masquerading as the forwarding method.

The iptables rules that remain are few, and they use ipsets rather than one rule per service, which is the whole performance argument: adding a service adds a hash-table entry rather than lengthening a chain that is walked linearly for every packet. What the rules still do is mark traffic that needs source NAT, for the cases where the reply would otherwise not come back through the node.

Try it

Host lab, run as root. Prerequisites: ipvsadm (package ipvsadm), iproute2, curl, pwru, and the ip_vs and ip_vs_rr modules.

sudo lab/13-ipvs.sh up      # pp-vip 10.15.0.100 on a dummy device, two real servers in netns

sudo ipvsadm -Ln                    # the virtual service and its real servers
ip addr show pp-ipvs0               # the virtual address, local, with nothing listening
ip route get 10.15.0.100            # local, dev lo: the routing decision this chapter needs

# the jump: LOCAL_IN, then ip_vs functions, then LOCAL_OUT, with no tcp_v4_rcv
sudo pwru --kmods ip_vs --output-meta 'tcp and host 10.15.0.100' &
curl -s --max-time 2 -o /dev/null http://10.15.0.100:80/

sudo ipvsadm -Lnc                   # the ip_vs_conn entries, one per connection
sudo lab/13-ipvs.sh down

This output is expected rather than observed. The bench for this dossier had no ipvsadm on the host or in the node, and installing it was out of scope, so no virtual service could be configured and nothing was traced. The ip_vs module itself does load on this kernel, which corrects a note made earlier in the project; it was loaded once to check, found inert with no services configured, and unloaded again. Expect the trace to show nf_hook_slow for LOCAL_IN, then ip_vs_in_hook, ip_vs_schedule, ip_vs_conn_new, ip_vs_nat_xmit, then nf_hook_slow again for LOCAL_OUT and POST_ROUTING, and no tcp_v4_rcv anywhere.

Recap

A virtual address must be local on the director, so the routing decision returns RTN_LOCAL and the packet enters LOCAL_IN, which is where ip_vs_in_hook is registered just below the source-NAT priority. It looks the connection up, and on a miss ip_vs_schedule picks a real server and ip_vs_conn_new records the choice in a struct ip_vs_conn whose packet_xmit pointer is the forwarding method. For masquerading that is ip_vs_nat_xmit, which rewrites the destination and then calls the LOCAL_OUT hooks directly from inside LOCAL_IN, returning NF_STOLEN; skb->ipvs_property marks the skb so the hooks do not act on it twice, and skb_scrub_packet clears that bit at a namespace boundary. Replies are rewritten by ip_vs_out_hook and re-routed. Direct routing and tunnelling avoid the return trip entirely. kube-proxy's kube-ipvs0 dummy device exists only to make service addresses local so this path is reached.

Check yourself

1. Why must the virtual address be configured on a local interface, and what would the packet's fate be if it were not?

Answer

Because IPVS's request-direction hook is registered on LOCAL_IN, and only a local address gets a packet there. ip_route_input_slow returns RTN_LOCAL for an address the host owns, which stores ip_local_deliver as the route's input function; without the address configured, the lookup returns RTN_UNICAST and the packet takes the forward path or is dropped as unroutable, never reaching ip_vs_in_hook (net/netfilter/ipvs/ip_vs_core.c:2097). This is exactly why kube-proxy puts every service address on the kube-ipvs0 dummy device.

The near miss is "something has to listen on it". Nothing listens; the packet is taken one hook before tcp_v4_rcv would look for a socket, which is why ss shows nothing on a working director.

2. Trace the path: a client SYN reaches a director using the masquerading method. List the hooks it visits in order, and name the moment a socket lookup would have happened but did not.

Answer

PRE_ROUTING, then the routing decision, then LOCAL_IN, then LOCAL_OUT, then POST_ROUTING. Inside LOCAL_IN, ip_vs_in_hook schedules and calls ip_vs_nat_xmit (ip_vs_xmit.c:787), which rewrites the destination and calls ip_vs_nat_send_or_cont (line 666); that runs NF_HOOK(..., NF_INET_LOCAL_OUT, ...) followed by dst_output and returns NF_STOLEN. The socket lookup that did not happen is tcp_v4_rcv, which ip_local_deliver_finish would have reached had LOCAL_IN completed normally.

The near miss is "it is forwarded, so it visits FORWARD". FORWARD is never entered; the route type was local, and IPVS provides the crossing itself.

3. A colleague reports that IPVS on their director stops working for traffic that arrives through a veth pair from a container, but works for traffic from the physical interface. Which single bit would you suspect, and which function clears it?

Answer

skb->ipvs_property (include/linux/skbuff.h:1010), cleared by skb_scrub_packet through ipvs_reset (skbuff.h:5154, called at net/core/skbuff.c:6292). Every veth crossing runs __dev_forward_skb and therefore the scrub, so an skb that IPVS had already claimed arrives on the far side with the flag gone and the hooks will act on it again. That is deliberate: the flag is meaningful only within one namespace's IPVS state, which knows nothing of the other's.

The near miss is "conntrack state was lost". Conntrack is also reset by the same scrub, but IPVS does not rely on conntrack by default; ip_vs_notrack is the normal path unless net.ipv4.vs.conntrack is set.
