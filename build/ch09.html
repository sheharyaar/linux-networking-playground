Chapter 9

veth: the mystery, resolved

~RT9 min · L2 · Spine: chapter 8 sent our skb through the loopback device and it came back up with its route still attached. Now we hand the same skb to the other end of a veth pair, in a different network namespace, and almost everything about that sentence changes except the skb itself.

The payoff sentence

A veth pair does not create a new skb. It points skb->dev at the peer device, erases the state that belonged to the old namespace, and hands the same skb to a receive function, so the receive half of the stack runs again in the peer's namespace while the transmit half ran once in the origin's.

Every word of that is visible in one bench trace. Two namespaces, pp-a (inode 4026534764, device va, index 21) and pp-b (inode 4026534837, device vb, index 20), and one SYN. The skb address column never changes:

One allocation, one free, two namespaces. The namespace and the device index change on the same line, and that line is the handoff.

veth_xmit and the choice it makes

veth_xmit (drivers/net/veth.c:347) starts by finding the other end, rcv = rcu_dereference(priv->peer) at line 357. The pair is two net_device structures holding pointers to each other, which is the entire data structure. Then it makes one decision, at lines 373 to 374:

use_napi = rcu_access_pointer(rq->napi) &&
           veth_skb_is_eligible_for_gro(dev, rcv, skb);

and calls veth_forward_skb (line 320), which is three lines and contains both doors:

return __dev_forward_skb(dev, skb) ?: xdp ?
        veth_xdp_rx(rq, skb) :
        __netif_rx(skb);

__netif_rx is the backlog door of chapter 1. veth_xdp_rx leads to the peer's own NAPI poll. Which one runs is decided per packet by that use_napi expression, and both of its operands have to be true.

The first operand is the napi pointer, which exists only when the peer has GRO enabled or an XDP program attached. The second is veth_skb_is_eligible_for_gro (line 338), whose whole body is:

return !(dev->features & NETIF_F_ALL_TSO) ||
        (skb->destructor == sock_wfree &&
         rcv->features & (NETIF_F_GRO_FRAGLIST | NETIF_F_GRO_UDP_FWD));

Read the first clause carefully, because it catches people. It tests the features of dev, the transmitting device. Aggregating segments that the sender is about to hand over as one large offloaded blob would be work for nothing, so if the sender has TCP segmentation offload on, the skb is ineligible and the backlog door is taken whatever the receiver has configured.

The bench confirms it in three steps. By default, veth_xmit > __netif_rx > enqueue_to_backlog. With ethtool -K vb gro on and nothing else, the napi pointer now exists but the trace is unchanged: still __netif_rx, still the backlog. Only after ethtool -K va tso off gso off on the sender as well does the door move:

0xffff88dee6a8b2e8  4026534837  20  veth_xdp_rcv_skb[veth]

No __netif_rx, no enqueue_to_backlog, and the skb address is again constant. The pskb_expand_head line is a headroom fix-up before GRO, which reallocates the data buffer and keeps the same skb structure.

This also explains a behaviour that looks like magic. Attaching an XDP program to one end makes the pair start using NAPI, because veth_xdp_set clears the peer's software offloads, peer->hw_features &= ~NETIF_F_GSO_SOFTWARE at line 1622. With the sender's segmentation offload gone, the first clause of the eligibility test is true for every packet. The comment above the function says so in as many words: when XDP is enabled, all traffic is considered eligible, as the transmitting device has segmentation offload off.

What gets erased at the boundary

Before either door, veth_forward_skb calls __dev_forward_skb (net/core/dev.c:2451), which is __dev_forward_skb2 (line 2438) with the MTU check on. That calls ____dev_forward_skb (include/linux/netdevice.h:4440), four lines that matter:

if (skb_orphan_frags(skb, GFP_ATOMIC) ||
    unlikely(!__is_skb_forwardable(dev, skb, check_mtu))) {
        dev_core_stats_rx_dropped_inc(dev); kfree_skb(skb); return NET_RX_DROP;
}
skb_scrub_packet(skb, !net_eq(dev_net(dev), dev_net(skb->dev)));
skb->priority = 0;

__is_skb_forwardable (line 4400) checks that the peer is up and that the frame fits its MTU plus link-layer and VLAN headroom (lines 4413 to 4415), with a deliberate exemption: a GSO skb passes regardless of length (lines 4420 to 4421), because it will be segmented later. An MTU mismatch between the two ends of a pair therefore shows up as a silent rx_dropped on the receiving device rather than as an ICMP message.

Then the important call, whose second argument is the whole question. !net_eq(dev_net(dev), dev_net(skb->dev)) is true when the two devices live in different network namespaces, and that flag is named xnet inside skb_scrub_packet (net/core/skbuff.c:6278). Here is exactly what it clears:

Two rows of that table answer the question people actually have. Because the route is dropped, the peer namespace must do its own routing decision, which is why the trace shows ip_route_input_noref and ip_route_input_slow on the receive side. That is the precise opposite of chapter 8, where loopback_xmit called skb_dst_force and the lookup was skipped. And because the conntrack pointer is reset, conntrack runs again from scratch in the peer namespace, with its own table and its own entry.

The mark is the subtle one. skb->mark is cleared only when the namespace actually changes. A veth pair with both ends in one namespace, which is how a Linux bridge is usually wired, preserves the mark; a pair whose ends straddle a container boundary does not. The last step, after the scrub, is eth_type_trans back in __dev_forward_skb2 (line 2443), and its first statement is skb->dev = dev. That single assignment is the device swap.

The one place a copy happens

Chapter 2 promised this chapter would say when a veth copies. The answer is a single call site. When a native XDP program is attached to the receiving end, veth_convert_skb_to_xdp_buff (veth.c:751) must hand the program a linear buffer it owns, with headroom in front. If any of four conditions holds (lines 758 to 760) it copies:

if (skb_shared(skb) || skb_head_is_locked(skb) ||
    skb_is_nonlinear(skb) ||
    skb_headroom(skb) < XDP_PACKET_HEADROOM) {
        if (skb_pp_cow_data(rq->page_pool, pskb, XDP_PACKET_HEADROOM))

For locally generated TCP this is not a rare case; it is every packet. TCP keeps the original skb on its retransmission queue and transmits a clone, so the head is locked and skb_pp_cow_data (net/core/skbuff.c:942) allocates a fresh page-pool buffer and copies the data into it. The earlier native XDP trace showed exactly that shape: the old skb freed through consume_skb and a new address appearing afterwards. Without an XDP program the skb identity holds end to end, which is what the address column in this chapter's traces shows.

Try it

Host lab, run as root. Prerequisites: iproute2, ethtool (package ethtool), curl, pwru. The --kmods veth flag is required: veth is a module, and pwru probes only built-in functions unless you name it.

sudo lab/09-veth.sh up            # pp-a va 10.9.0.1  <-->  vb 10.9.0.2 pp-b

# door 1, the default. Watch the skb address column stay constant.
sudo pwru --kmods veth --output-meta 'tcp and host 10.9.0.2' &
sudo ip netns exec pp-a curl -s --max-time 2 http://10.9.0.2:9099/   # refused is fine

# GRO at the receiver alone changes nothing: still __netif_rx
sudo ip netns exec pp-b ethtool -K vb gro on
sudo ip netns exec pp-a curl -s --max-time 2 http://10.9.0.2:9099/

# now take segmentation offload off the sender: veth_xdp_rcv_skb appears
sudo ip netns exec pp-a ethtool -K va tso off gso off
sudo ip netns exec pp-a curl -s --max-time 2 http://10.9.0.2:9099/

# restore, then tear down
sudo ip netns exec pp-a ethtool -K va tso on gso on
sudo ip netns exec pp-b ethtool -K vb gro off
sudo lab/09-veth.sh down

All three runs above were measured on the bench and the transcripts in this chapter are their real output. You need no listener: the SYN crosses the pair and is answered with a reset, which exercises the whole path.

Recap

A veth pair is two devices pointing at each other. veth_xmit (veth.c:347) looks up the peer and calls veth_forward_skb, which runs __dev_forward_skb and then either __netif_rx or the peer's NAPI poll. The NAPI door needs a napi pointer on the peer and an eligible skb, and eligibility reads the sender's segmentation offload, so turning GRO on at the receiver alone changes nothing. skb_scrub_packet drops the route and resets conntrack for every crossing, and clears the mark only when the namespace changes, so the peer namespace repeats the routing decision and conntrack lookup that chapter 8's loopback path skipped. The skb address is unchanged throughout; the only copy is the native XDP path, where a locked TCP clone forces skb_pp_cow_data.

New words in this chapter

veth_xmit
The veth transmit function: find the peer, pick a door, forward the same skb.
veth_forward_skb
The three-line function holding both doors, __netif_rx and veth_xdp_rx.
veth_skb_is_eligible_for_gro
The test that reads the sending device's segmentation offload to decide whether aggregating is worth it.
veth_xdp_rcv_skb
The NAPI-side receive function, which runs GRO and enters the IP layer without the backlog.
__dev_forward_skb, ____dev_forward_skb
The shared handoff used by veth and by BPF redirect: check, scrub, then eth_type_trans.
__is_skb_forwardable
The up-and-MTU check, with GSO skbs exempted from the length test.
skb_scrub_packet
Erases the state a packet may not carry into another device or namespace: route, conntrack, input index, and the mark when crossing namespaces.
xnet
The argument telling skb_scrub_packet that the two devices are in different network namespaces.

Check yourself

1. You set a firewall mark on a packet in one namespace and expect to match it in the peer namespace after it crosses a veth pair. Sometimes it works and sometimes it does not. What decides, and which line?

Answer

Whether the two ends are in different network namespaces decides it, at net/core/skbuff.c:6296. ____dev_forward_skb passes !net_eq(dev_net(dev), dev_net(skb->dev)) as the xnet argument (include/linux/netdevice.h:4451), and skb_scrub_packet zeroes skb->mark only under that flag. A pair with both ends in one namespace, the usual bridge wiring, keeps the mark; a pair straddling a container boundary loses it.

The near miss is "the mark is always cleared like the route is". The route is dropped unconditionally at line 6283; the mark is conditional, and that asymmetry is the whole answer.

2. Trace the path: a container sends a TCP segment out of its eth0, which is one end of a veth pair. Does conntrack in the host namespace see a new connection or an established one, and why?

Answer

A new one, because skb_scrub_packet called nf_reset_ct (net/core/skbuff.c:6285) and dropped the conntrack pointer the container's namespace had attached. Conntrack state lives per network namespace, and skb->_nfct is the only thing tying an skb to an entry, so the host's nf_conntrack_in finds nothing in the skb, builds the tuple again and allocates its own entry with IP_CT_NEW.

The near miss is "it is established because the container already tracked it". Two independent tables are involved, and neither can see the other's entry; the container's table is not even consulted.

3. Predict the trace: you attach a native XDP program to vb and send one TCP segment from va. Does the skb address stay constant, and what would change if the traffic were UDP from a socket with plenty of headroom?

Answer

It changes for TCP and can stay constant for UDP. veth_convert_skb_to_xdp_buff (veth.c:758 to 761) copies when the skb is shared, head-locked, nonlinear, or short of XDP_PACKET_HEADROOM. TCP transmits a clone of the skb it keeps for retransmission, so the head is locked and skb_pp_cow_data (net/core/skbuff.c:942) allocates a new buffer; the trace shows the old skb freed and a new address appearing. A linear UDP skb with enough headroom fails all four tests and is passed through unchanged.

The near miss is "XDP always copies on veth". The copy is driven by the four properties of that specific skb, and the headroom condition is the one you can influence.
