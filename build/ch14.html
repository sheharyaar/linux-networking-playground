Chapter 14

Cilium on one node: the tc hook takes over

~RT14 min · BPF · Spine: chapter 9 sent our skb through a veth pair and the receive half ran again in the peer's namespace. Attach one BPF program to the host end of that pair and the second half of the journey disappears: the skb is handed to the destination pod's device from inside the first namespace's softirq, and the netfilter chart is never entered.

The bench, and what is configured

Everything in this chapter and the next was measured on a three-node kind cluster running a Cilium fork at v1.19.6-vpc.18. The configuration matters because it decides which branches run:

Routing:        Network: Tunnel [geneve]   Host: BPF
Attach Mode:    TCX
Device Mode:    veth
Masquerading:   BPF  [eth0]  10.128.0.64/27
KubeProxyReplacement: True

Two throwaway pods on one node, a client at 10.128.0.66 and an nginx server at 10.128.0.82, and one HTTP request between them. Programs are attached with tcx, the newer attachment point chapter 3 introduced, and cil_from_container sits on the ingress side of the host end of each pod's veth pair. Ingress on the host end means packets leaving the pod, which reads backwards until you remember the pair swaps direction.

One redirect, and everything it skips

Here is the measured path for one SYN. Three namespace inodes appear: the client pod, the node, and the server pod. One skb address appears throughout.

netns 4026534894  eth0:42            ip_local_out > ip_output > ip_finish_output2 >
                                     __dev_queue_xmit > dev_hard_start_xmit >
                                     veth_xmit[veth] > __dev_forward_skb2 >
                                     skb_scrub_packet > eth_type_trans
netns 4026533157  ~09ac2395bb83:43   __netif_rx > netif_rx_internal > enqueue_to_backlog >
                                     __netif_receive_skb_one_core >
                                     cil_from_container[bpf](tc) >
                                     skb_ensure_writable x7 > skb_do_redirect
netns 4026534754  eth0:44            skb_scrub_packet > ip_rcv > ip_rcv_core > ...

Compare that against chapter 9's veth trace and the difference is a whole half. There, the skb went veth_xmit into the peer, through the backlog, up through ip_rcv, through a routing decision, and out again through a second veth pair. Here the last line of the node's work is skb_do_redirect, and the next line is already inside the destination pod.

The counts over the whole twelve-packet capture make it precise:

FunctionTimes called, 12 packetsWhat that means
veth_xmit12One veth crossing per packet, pod to host. The destination pod's veth pair is never used.
enqueue_to_backlog12The per-CPU backlog is entered once, not twice.
cil_from_container12One BPF program runs; no other Cilium program is involved.
skb_do_redirect12One redirect per packet.
nf_hook_slow0No netfilter hook is entered anywhere, in any namespace.

That zero is the headline. The host's PRE_ROUTING, FORWARD and POST_ROUTING chains, conntrack, and any iptables rule you have written are not skipped by policy or by a rule that accepts early; they are never reached, because the skb leaves the host's receive path before ip_rcv.

How the jump is made

Inside Cilium, the path is a chain of tail calls ending in one helper. cil_from_container (bpf/bpf_lxc.c:2212) tail-calls tail_handle_ipv4 (line 2157), which reaches handle_ipv4_from_lxc (line 1591). That function looks the destination up in the ipcache, a map from address to security identity, checks egress policy with policy_can_egress4, and calls ipv4_forward_to_destination (line 1187). When the destination is an endpoint on this node, that reaches ipv4_local_delivery (bpf/lib/local_delivery.h:229), which rewrites the source and destination MAC addresses to the pair the destination pod expects (line 242) and then reaches redirect_ep (line 82):

if (!use_fast_redirect)
        return (int)ctx_redirect(ctx, ifindex, 0);
if (from_tunnel)
        ctx_change_type(ctx, PACKET_HOST);
return ctx_redirect_peer(ctx, ifindex, 0);

ctx_redirect_peer is the bpf_redirect_peer helper, and it is the one that matters. The kernel side is skb_do_redirect (net/core/filter.c:2519), whose peer branch begins at line 2531:

if (flags & BPF_F_PEER) {
        if (unlikely(!skb_at_tc_ingress(skb)))    goto out_drop;
        dev = skb_get_peer_dev(dev);
        if (unlikely(!dev || !(dev->flags & IFF_UP) ||
                     net_eq(net, dev_net(dev))))  goto out_drop;
        skb->dev = dev;
        dev_sw_netstats_rx_add(dev, skb->len);
        skb_scrub_packet(skb, false);
        return -EAGAIN;
}

Four things in nine lines. skb_get_peer_dev (line 2509) calls the device's ndo_get_peer_dev, which is how a veth device names its other end without the caller knowing anything about veth. The namespace test at line 2537 is a drop condition: the peer must be in a different network namespace, so this helper cannot be used to shortcut within one namespace. skb->dev is set to the peer at line 2539. And skb_scrub_packet(skb, false) at line 2541 passes false for the cross-namespace flag, which by chapter 9's table means the route and the conntrack pointer are dropped but skb->mark is kept, even though the namespace really is changing. Cilium relies on that mark surviving.

The return value is the trick. -EAGAIN is not an error; it is a message to the caller. In sch_handle_ingress (net/core/dev.c:4493):

case TC_ACT_REDIRECT:
        __skb_push(skb, skb->mac_len);
        if (skb_do_redirect(skb) == -EAGAIN) {
                __skb_pull(skb, skb->mac_len);
                *another = true;
                break;
        }

and in __netif_receive_skb_core, line 6069, if (another) goto another_round; jumps back to the label at line 6017. This is the same another_round the bond and macvlan of the last two chapters use. The skb re-enters the station list from the top with a new device, that device is the destination pod's eth0, and because that device lives in another namespace the rest of the receive path runs there. No new softirq, no queue, no second driver.

The same program, deciding the other way

Policy is enforced in the same program, before any of that. The cluster carries a policy admitting only one security group to a particular server, and a client outside that group produces a trace with the same opening and a different last line:

netns 4026533157  ~96ba345865a7:13  cil_from_container[bpf](tc) >
                                    skb_ensure_writable x7 >
                                    sk_skb_reason_drop(SKB_DROP_REASON_TC_INGRESS)

The client's curl reports a timeout. The packet is freed inside the tc hook with a drop reason the kernel exposes to tracing, and it never reaches the destination pod, the host stack, or a counter in any iptables chain. Both the permit and the deny happen in the same place, which is the point of doing policy here rather than in the chart.

Host to pod, and pod to host

Traffic between the node itself and a pod cannot use the peer redirect, because the host end of the journey is the node's own namespace. Cilium builds a second veth pair for that, cilium_host and cilium_net, and attaches programs to both ends: cil_from_host on cilium_host egress, cil_to_host on cilium_host ingress and on cilium_net ingress. cilium_host carries the node's router address and has ARP disabled. In the cross-node capture of the next chapter, cil_to_host and cil_from_host appear twenty-five times each, which is the health and node-local traffic using exactly this pair.

One configuration option changes the shape of everything above, and it is worth naming because a great deal of older writing assumes it. With endpoint routes enabled, Cilium also attaches cil_to_container to the egress side of each pod's veth pair and installs a per-pod route in the host, so packets are delivered by the host's routing table rather than by a peer redirect, and ingress policy runs in that second program. The bench cluster has endpoint routes off, which is why no cil_to_container appears in any capture and why ingress policy is resolved by a tail call inside the sender's program instead.

Recap

Cilium attaches cil_from_container with tcx to the ingress side of the host end of each pod's veth pair, so it sees every packet leaving that pod. For a destination on the same node the program looks up the ipcache, checks egress policy, rewrites both MAC addresses in ipv4_local_delivery, and calls ctx_redirect_peer. The kernel's skb_do_redirect finds the peer device through ndo_get_peer_dev, requires it to be in another namespace, sets skb->dev, scrubs the skb while keeping the mark, and returns -EAGAIN, which makes __netif_receive_skb_core restart at another_round with the destination pod's device. The measured result for twelve packets is one veth crossing each, one backlog entry each, and zero netfilter hook calls anywhere. A denied packet is freed in the same program with SKB_DROP_REASON_TC_INGRESS. Node-to-pod traffic uses the separate cilium_host and cilium_net pair, and enabling endpoint routes would replace the peer redirect with host routing plus a second program on the pod's veth egress.

The map from IP address to security identity that tells the program what the destination is.

The number Cilium assigns to a set of labels; policy is written between identities rather than addresses.

Check yourself

1. Predict the count: you run a capture over ten pod-to-pod packets on one Cilium node with BPF host routing on, and count veth_xmit, enqueue_to_backlog and nf_hook_slow. Give all three numbers and justify each.

Answer

Ten, ten and zero. veth_xmit runs once per packet for the hop out of the source pod; the destination pod is entered by skb_do_redirect setting skb->dev, so its veth pair is never driven. enqueue_to_backlog runs once, for that same hop. nf_hook_slow is zero because the redirect happens in the tc ingress hook, before ip_rcv, so no netfilter hook point in any namespace is reached. The measured bench run over twelve packets gave 12, 12 and 0.

The near miss is "twenty and twenty, one pair per pod". That is the plain veth answer of chapter 9, and the whole saving here is the half that does not happen.

2. bpf_redirect_peer refuses to work when the target device's peer is in the same network namespace as the current one. Find the line and explain why the restriction is there rather than being a bug.

Answer

net/core/filter.c:2537, where net_eq(net, dev_net(dev)) is one of the conditions that jumps to out_drop. The helper's whole purpose is to cross a namespace boundary in one step, and it achieves that by setting skb->dev and returning -EAGAIN so the core restarts with the new device. Within one namespace that restart would deliver the packet to the same stack it is already in, which the ordinary bpf_redirect already does correctly through __bpf_redirect. The peer branch also requires skb_at_tc_ingress at line 2532.

The near miss is "because the peer might not exist". That is checked too, in the same condition, but it is the !dev half; the namespace test is separate and deliberate.

3. A colleague adds an iptables rule in FORWARD to count traffic between two pods on one node and sees zero. On a second cluster the same rule counts correctly. Name the single configuration difference most likely responsible and how you would confirm it.

Answer

BPF host routing, on in the first cluster and off in the second. With it on, cil_from_container ends in ctx_redirect_peer and the skb leaves the receive path before ip_rcv, so no netfilter hook runs; the bench measured zero nf_hook_slow calls for the whole flow. Confirm with cilium-dbg status --verbose and read the Routing: ... Host: field, which prints BPF or Legacy, and then re-run a capture and count nf_hook_slow.

The near miss is "the rule is in the wrong chain; it should be in PREROUTING". Every chain reads zero, because the packet reaches none of them; moving the rule changes nothing.
