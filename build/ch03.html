Chapter 3

L2 receive: taps, tc ingress, the receive handler, and the protocol demux

~RT3 min · L2 · Spine: our skb has come through one of the two doors and reached __netif_receive_skb_core. This chapter is that single function, station by station. When it ends, the skb is in the hands of ip_rcv.

One function, six stations

Every frame the kernel receives, from a NIC, a veth, the loopback device or a tunnel, passes through __netif_receive_skb_core (net/core/dev.c:5986). It is about two hundred lines long and its shape is a loop with a label at the top, another_round (line 6017), that two of the stations jump back to after rewriting skb->dev. The stations, in order:

StationLinesWho lives thereWhat it may do

The order is the content of this chapter. Taps come before tc, so tcpdump sees frames that tc will drop. tc comes before the receive handler, so a tc program can steal a frame from a bridge. The receive handler comes before the protocol demux, so a bridge port's frames never reach the host's IP layer unless the bridge itself hands them up. Diagram 0.1 drew this as one box called "L2 receive"; the rest of the chapter opens the box.

Taps: how tcpdump gets its copy

A packet socket, socket(AF_PACKET, SOCK_RAW, htons(ETH_P_ALL)), registers a packet type handler on the ptype_all list, either the namespace's list or a single device's list if the socket is bound to one. You can see the registration: /proc/net/ptype in the bench namespace reads ALL vb packet_rcv while the tap is open. The loop at lines 6048 to 6057 walks both lists and calls deliver_skb (line 2486) for each entry. deliver_skb does not clone. It increments skb->users and calls the handler; the handler, packet_rcv, makes its own clone with skb_clone for the socket's receive queue and drops its reference. The trace on the bench reads deliver_skb, packet_rcv, skb_push, skb_clone, consume_skb, and then the original skb carries on to the next station with the same address.

Promiscuous mode is a different mechanism that people fold into the same word. It is a device flag, IFF_PROMISC, that tells the card to accept frames whose destination MAC is not its own. tcpdump turns it on by default. Such a frame arrives at the taps like any other, but eth_type_trans has set skb->pkt_type to PACKET_OTHERHOST, and ip_rcv_core drops it on that field at net/ipv4/ip_input.c:508, after the taps have had their copy. So tcpdump sees the neighbour's traffic and the local IP stack never does.

Transmit has a mirror tap. xmit_one (net/core/dev.c:3878) calls dev_queue_xmit_nit (line 2549) right before it calls the driver, and that function does clone (line 2575). Two consequences: tcpdump's timestamp for an outgoing packet is taken after the queueing discipline, not when the application sent it; and a frame dropped by tc on egress, which runs earlier in __dev_queue_xmit at line 4812, is never seen by tcpdump on the sending device. Ingress taps see tc drops; egress taps do not.

tc ingress: two mechanisms, one station

tc ingress is the station at lines 6062 to 6070, compiled in under CONFIG_NET_INGRESS and skipped by a static key until some device has an ingress attachment. The function is sch_handle_ingress (line 4465), and it hosts two mechanisms that run in a fixed order. First tcx, the BPF link attachment point added in Linux 6.6: a per-device array of BPF programs run in sequence by tcx_run (line 4444), each returning a code that says continue to the next program or stop with a verdict. Second, only if every tcx program said TC_ACT_UNSPEC (lines 4484 to 4491), the classic tc chain: tc_run walks the filters attached to the device's clsact queueing discipline through tcf_classify, and each matching filter runs its actions. A matchall filter with a pass action, the simplest possible, appears in the trace as tc_run, tcf_classify, mall_classify, tcf_action_exec, tcf_gact_act. BPF programs attached the classic way, with tc filter add ... bpf, live in this second chain as a cls_bpf filter.

The tc verdict decides what the station does with the skb. TC_ACT_OK continues to the next station. TC_ACT_SHOT frees the skb. TC_ACT_REDIRECT means a program has already handed the skb to another device with the bpf_redirect helper, and the loop must let go of it; this is the verdict Cilium's programs return when they move a packet straight into a pod's veth, and chapter 14 shows the whole path. TC_ACT_RECLASSIFY and a device rewrite jump to another_round (line 6070). Egress has the same station in __dev_queue_xmit, sch_handle_egress (line 4529), with the same tcx-first ordering (lines 4543 to 4549).

VLAN and the receive handler: rewrite the device and go around again

Two stations share one trick. vlan_do_receive (line 6091) checks whether the frame carries an 802.1Q tag, or whether the card stripped one into the skb's metadata. If so it finds the VLAN sub-device for that tag, sets skb->dev to it, strips the tag, and jumps to another_round. The frame is now "from" the VLAN device, and the taps run again for it, which is why tcpdump on eth0.100 and on eth0 both see the frame.

The receive handler station (lines 6097 to 6116) is the one you met in the prologue: rx_handler = rcu_dereference(skb->dev->rx_handler). A device gets one when a bridge, bond, macvlan, ipvlan or team driver claims it through netdev_rx_handler_register. Any tap that was still pending is delivered first (lines 6099 to 6102), so tcpdump on a bridge port sees the frame before the bridge does. Then the handler runs and returns one of four codes. RX_HANDLER_CONSUMED: the handler owns the skb now, and the loop exits; this is a bridge forwarding a frame to another port, and the host's IP stack is never involved. RX_HANDLER_ANOTHER: the handler rewrote skb->dev, typically to the master device, and the loop jumps to another_round; this is a bond or a macvlan presenting the frame as its own. RX_HANDLER_EXACT: continue, but deliver only to protocol handlers bound to this exact device. RX_HANDLER_PASS: continue as if there were no handler. Chapters 10 to 12 are, mechanically, three different bodies for this one function pointer.

The demux: picking the L3 handler

The last station hands the skb to L3. deliver_ptype_list_skb (lines 6160 to 6177) looks up skb->protocol in the ptype_base hash: 0x0800 maps to ip_rcv, 0x0806 to arp_rcv, 0x86dd to ipv6_rcv, all visible in /proc/net/ptype. The loop uses a small trick worth knowing because it shapes traces: it does not call each handler as it finds it. It remembers the previous match in pt_prev and delivers it only when it finds the next one, so the last handler receives the skb without a reference-count bump and owns it outright. If no handler matches, the skb is freed with a drop reason of unhandled protocol.

One more shape appears in traces and confuses people. When the skb arrived through the GRO door as part of a batch, the core uses the list variant of this loop, groups the skbs by protocol, and calls ip_list_rcv instead of ip_rcv. pwru cannot probe a function whose argument is a list rather than an skb, so such a trace shows ip_rcv_core with no ip_rcv before it. The native XDP trace of chapter 2 had exactly that shape. Same code, different door.

Try it

Put a tap and a tc filter on the receiving veth and watch them appear in order.

sudo lab/09-veth.sh up                       # if not already up
sudo ip netns exec pp-b cat /proc/net/ptype   # ip_rcv, arp_rcv, ipv6_rcv, no ALL entry yet
# a packet socket bound to vb, held open for 40 seconds
sudo ip netns exec pp-b python3 -c 'import socket,time
s=socket.socket(socket.AF_PACKET,socket.SOCK_RAW,socket.htons(3)); s.bind(("vb",0)); time.sleep(40)' &
sudo ip netns exec pp-b cat /proc/net/ptype   # now: ALL  vb  packet_rcv
# a classic tc filter that matches everything and passes it
sudo ip netns exec pp-b tc qdisc add dev vb clsact
sudo ip netns exec pp-b tc filter add dev vb ingress pref 10 matchall action pass
# trace with the classifier and action modules included
sudo pwru --kmods veth,cls_matchall,act_gact 'tcp and host 10.9.0.2 and port 8080'
# then, in another terminal, one request
sudo ip netns exec pp-a curl -s -o /dev/null http://10.9.0.2:8080/

Expected order for the SYN on the receive side: __netif_receive_skb_one_core, deliver_skb, packet_rcv, skb_clone, consume_skb, tc_run, tcf_classify, mall_classify, tcf_action_exec, tcf_gact_act, ip_rcv. Change the action to drop and the trace stops at tcf_gact_act, but the packet socket still got its copy.

Recap

__netif_receive_skb_core is a loop of six stations. Generic XDP first. Then the taps, where packet sockets get a clone and promiscuous frames are seen before IP drops them. Then tc ingress, tcx programs before classic filters, whose verdict can drop, redirect or loop. Then VLAN untagging and the receive handler, both of which may rewrite skb->dev and go around again, or, for a bridge, take the frame out of the loop entirely. Last, the protocol demux by skb->protocol to ip_rcv. Egress has a mirror tap and a mirror tc station, in the opposite order, so egress tc drops are invisible to tcpdump.

Check yourself

1. You add tc filter add dev vb ingress matchall action drop. Does tcpdump -i vb still show the dropped frames? Then you move the same drop to egress on the sender's device va. Does tcpdump -i va show them?

Answer

Yes on ingress, no on egress. On receive the tap loop (net/core/dev.c:6048 to 6057) runs before sch_handle_ingress (line 6067), so the packet socket has cloned the frame before tc drops it. On transmit the order is reversed: sch_handle_egress runs inside __dev_queue_xmit at line 4812, and the transmit tap dev_queue_xmit_nit is called much later from xmit_one at line 3885, just before the driver. A frame dropped by egress tc never reaches the tap.

The near miss is assuming symmetry, "tcpdump is at L2 so it sees both". The two taps are at different depths on purpose: receive taps see what arrived, transmit taps see what is about to leave.

2. A pwru trace of a frame arriving on a bond slave shows deliver_skb, packet_rcv, then bond_handle_frame, then deliver_skb and packet_rcv again, then ip_rcv. Two tcpdump processes are running. Which devices are they bound to, and why did the frame pass the taps twice?

Answer

One is bound to the slave, one to the bond. The bond's receive handler returned RX_HANDLER_ANOTHER after setting skb->dev to the bond device, and the loop jumped to another_round (line 6107 to 6017). On the second pass the frame is "from" the bond, so the bond's per-device tap list matches and the bond-bound packet socket gets its clone. The slave-bound socket got its clone on the first pass, before the handler ran, because pending taps are delivered at lines 6099 to 6102 before the handler is called.

The near miss is "the frame was duplicated". It is the same skb, same address in the trace, going around the loop twice under two names. Each pass produced one clone for one socket.

3. A frame arrives on a bridge port. Its destination MAC belongs to a host on another port. Trace the path through the stations of this chapter and say which station the frame never reaches.

Answer

Generic XDP if attached, then the taps on the port device, then tc ingress on the port, then the receive handler, which is br_handle_frame because the port is enslaved to the bridge. The bridge looks up the destination MAC, forwards the frame out the other port, and returns RX_HANDLER_CONSUMED (line 6104), so the loop exits. The frame never reaches the protocol demux at lines 6160 to 6177, and ip_rcv never runs for it in the bridge's namespace. Chapter 10 traces the forwarding half.

The near miss is "the bridge forwards after IP has seen it, because the netfilter chart shows bridge and IP hooks together". The chart's IP hooks appear on a bridged path only when the br_netfilter module is loaded, and even then they are called from inside the bridge code, not from ip_rcv.
