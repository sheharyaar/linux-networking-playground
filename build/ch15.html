Chapter 15

Cilium across nodes and to the world

~RT15 min · BPF · Spine: chapter 14's redirect worked because the destination was a device on the same machine. Now the destination is on another node, and then outside the cluster entirely. The same program makes both decisions, and this chapter follows one skb across two nodes and watches the address column change twice.

Encapsulation: the same skb, a different tuple

When handle_ipv4_from_lxc finds the destination is an endpoint on another node, ipv4_forward_to_destination takes the tunnel branch and calls encap_and_redirect_lxc (bpf/bpf_lxc.c:1532, defined at bpf/lib/encap.h:382), which reaches __encap_and_redirect_with_nodeid (line 255). Two things are set before the redirect. ctx_set_encap_info4 (bpf/lib/overloadable_skb.h:189) fills a tunnel key:

key.tunnel_id  = get_tunnel_id(seclabel);           /* line 203 */
key.remote_ipv4 = bpf_ntohl(tunnel_endpoint);       /* line 209 */
key.tunnel_ttl  = IPDEFTTL;
ret = ctx_set_tunnel_key(ctx, &key, key_size, BPF_F_ZERO_CSUM_TX);

The remote address is the other node. The tunnel identifier is the sender's security identity, which is the whole reason policy can be enforced on the far side without a lookup: the identity rides in the tunnel header. Then line 278 calls ctx_redirect(ctx, ifindex, 0) with the tunnel device's index, and this is an ordinary bpf_redirect rather than the peer variant, so the kernel takes the __bpf_redirect path and queues the skb for transmit on cilium_geneve.

The bench follows one skb, 0xffff88dfec7e0ae8, from a pod on one node to a pod on another. Watch the tuple column:

netns worker2, eth0:28   ip_local_out ... veth_xmit > skb_scrub_packet > eth_type_trans
netns worker2, lxc:29    cil_from_container > skb_do_redirect > __bpf_redirect
netns worker2, dev 27    __dev_queue_xmit > cil_to_overlay > dev_hard_start_xmit >
  (cilium_geneve)        geneve_xmit[geneve] > geneve_build_gro_hint_opt >
                         skb_tunnel_check_pmtu > geneve_build_skb > skb_scrub_packet >
                         iptunnel_handle_offloads > udp_set_csum > iptunnel_xmit >

        tuple so far:    10.128.0.57:33200 -> 10.128.0.82:80 (tcp)
        tuple from here: 172.18.0.2:62469 -> 172.18.0.4:6081 (udp)
netns worker2, dev 27    ip_local_out > __ip_local_out > nf_hook_slow > ip_output
netns worker2, eth0:2    nf_hook_slow > ip_finish_output2 > __dev_queue_xmit >
                         cil_to_netdev > veth_xmit[veth] > ...

The skb address never changes. The tuple changes because iptunnel_xmit pushed an outer IP and UDP header in front of the packet that was already there, and pwru is reading the outermost headers. From that point the kernel treats this as a locally generated UDP datagram: ip_local_out, LOCAL_OUT, ip_output, POST_ROUTING, a route lookup to the other node, and then the physical device's egress program cil_to_netdev (bpf/bpf_host.c:1506).

Those two nf_hook_slow calls are the important detail, and the measurement makes it exact. In the whole cross-node capture, the receiving node's namespace recorded 116 nf_hook_slow calls. Of those, 116 carried the outer UDP tuple on port 6081 and zero carried the inner TCP tuple. Netfilter on both nodes sees a UDP datagram between two node addresses. It never sees the pod-to-pod connection inside it, so a rule matching pod addresses matches nothing, and conntrack holds one entry for the tunnel rather than one per pod connection.

Decapsulation on the far node

The outer packet arrives on the destination node's eth0, where cil_from_netdev (bpf/bpf_host.c:1298) runs. For tunnel traffic it does nothing special; there is no port check that catches Geneve and shortcuts it, so the packet is passed to the stack as an ordinary UDP datagram:

netns worker, eth0:2     __netif_rx > enqueue_to_backlog > __netif_receive_skb_one_core >
                         cil_from_netdev > ip_rcv > ip_rcv_core > nf_hook_slow >
                         ip_rcv_finish_core > udp_v4_early_demux > ip_route_input_slow >
                         ip_local_deliver > nf_hook_slow > ip_protocol_deliver_rcu >
                         udp_rcv > udp_queue_rcv_one_skb >
                         geneve_udp_encap_recv[geneve] > __iptunnel_pull_header >
                         skb_pull_rcsum > skb_scrub_packet > eth_type_trans
        tuple flips back to 10.128.0.57:33200 -> 10.128.0.82:80 (tcp)
netns worker, cilium_geneve:7
                         gro_cells_receive > netif_rx > enqueue_to_backlog >
                         __netif_receive_skb_one_core > cil_from_overlay >
                         skb_ensure_writable x9 > skb_do_redirect
netns pod                skb_scrub_packet > ip_rcv > ip_rcv_core > ip_route_input_slow >
                         ip_local_deliver > tcp_v4_rcv > __inet_lookup_listener

The route lookup and the two hook calls here belong to the outer packet, delivered locally because the node owns that address. udp_rcv finds the Geneve socket, geneve_udp_encap_recv strips the outer headers with __iptunnel_pull_header, and the skb is handed to the tunnel device through gro_cells_receive, which re-enters the receive path with skb->dev set to cilium_geneve. There cil_from_overlay (bpf/bpf_overlay.c:654) reads the identity back out of the tunnel key, enforces ingress policy against it, and finishes with the same skb_do_redirect as the previous chapter, straight into the destination pod.

So one skb, two nodes, two namespace pairs, and exactly two moments where the stack was entered on purpose: once to transmit the outer packet and once to receive it.

VXLAN, Geneve and native routing

The tunnel protocol changes very little of the above. VXLAN uses UDP 8472 and Geneve 6081 (pkg/defaults/defaults.go:475 and 477), the transmit function becomes vxlan_xmit and the receive one vxlan_rcv, and the identity travels in the VXLAN network identifier. The shape of the path is identical. Geneve adds a variable-length option field for extra metadata alongside the identity.

Native routing removes the tunnel. Instead of the encapsulation branch, ipv4_forward_to_destination takes the host-routing branch (bpf/bpf_lxc.c:1547) and calls fib_redirect_v4 (bpf/lib/fib.h:263) at line 1550, which performs a bpf_fib_lookup and redirects to the physical device. The far node's eth0 receives the pod address directly, cil_from_netdev finds it in the ipcache as a local endpoint, and delivery is the peer redirect of chapter 14. The cluster has to be on a network that will route pod addresses for this to work, which is the trade: no encapsulation overhead, and the fabric has to know about your pod ranges.

Out to the world, and where the masquerade happens

Now a pod on the bench talking to an address outside the cluster, 172.18.0.1. The measured path is shorter than expected:

netns pod,    eth0:42          ip_local_out ... veth_xmit > skb_scrub_packet > eth_type_trans
netns worker, lxc:43           __netif_rx > enqueue_to_backlog > cil_from_container >
                               skb_ensure_writable x4 > skb_do_redirect > skb_pull
netns worker, eth0:2           cil_to_netdev > skb_ensure_writable
        tuple:  10.128.0.66:47446 -> 172.18.0.1:9099
        tuple:  172.18.0.4:47446 -> 172.18.0.1:9099    <-- changes here
netns worker, eth0:2           inet_proto_csum_replace_by_diff > netdev_core_pick_tx >
                               ... > veth_xmit[veth] > eth_type_trans
netns host                     the packet leaves the node

Two facts are worth stating plainly. First, the source address changes inside cil_to_netdev, next to a checksum fix-up, and nowhere near a MASQUERADE rule. This is Cilium's BPF masquerade: handle_nat_fwd (bpf/bpf_host.c:1707) leads to snat_v4_nat (bpf/lib/nodeport_egress.h:407), and the mapping is kept in a BPF map rather than in conntrack. Second, and this is the part that surprises people who know the older behaviour, the count of nf_hook_slow calls inside the node's namespace for this flow is zero. The four in the capture are all in the laptop's own namespace, where the masqueraded packet is received and answered.

The reason is in one branch. ipv4_forward_to_destination checks if (is_defined(ENABLE_HOST_ROUTING)) at bpf/bpf_lxc.c:1547 and calls fib_redirect_v4 at line 1550, redirecting the skb to the physical device. The label pass_to_stack at line 1565, which ends in return CTX_ACT_OK and hands the packet to ip_rcv on the lxc device, is reached only when host routing is off or when the route lookup fails with a not-forwarded result. On a cluster with legacy host routing the world path really does enter the host's PRE_ROUTING, routing decision, FORWARD and POST_ROUTING chains, and an iptables masquerade rule really does do the translation. On this one, neither happens.

So the answer to "where does the skb re-enter the netfilter chart" depends on one setting, and it is worth being able to say which cluster you are looking at:

Recap

For a destination on another node, encap_and_redirect_lxc sets a tunnel key whose identifier is the sender's security identity and whose remote address is the other node, then redirects to cilium_geneve, where cil_to_overlay and geneve_xmit build an outer UDP packet. From there the kernel treats it as ordinary local output, so LOCAL_OUT and POST_ROUTING run for the outer packet; on the far node PRE_ROUTING and LOCAL_IN run for it too, udp_rcv reaches geneve_udp_encap_recv, the headers are pulled, and cil_from_overlay reads the identity back and redirects into the destination pod. Measured on the bench, all 116 hook calls in the receiving node's namespace carried the outer tuple and none carried the inner one. Native routing replaces the tunnel with fib_redirect_v4. For world traffic with BPF host routing on, the same branch redirects straight to the physical device and cil_to_netdev rewrites the source address through snat_v4_nat, giving zero netfilter hook calls inside the node; with legacy host routing the packet takes pass_to_stack and the familiar chains and iptables masquerade apply.

Check yourself

1. You write an iptables rule counting traffic to a pod address on another node and it stays at zero, while a rule counting UDP port 6081 climbs steadily. Explain both observations with one mechanism.

Answer

Encapsulation: by the time any netfilter hook runs, the pod-to-pod packet is the payload of a node-to-node UDP datagram. iptunnel_xmit pushes the outer headers before ip_local_out is called, so LOCAL_OUT and POST_ROUTING on the sending node and PRE_ROUTING and LOCAL_IN on the receiving node all see source and destination node addresses with UDP port 6081. The bench measured 116 of 116 hook calls in the receiving node's namespace carrying the outer tuple and zero carrying the inner one.

The near miss is "the rule is on the wrong node". It would read zero on both; the inner addresses are never visible to netfilter on either side.

2. Trace the path: name every point between the two pods where skb->dev changes, for a cross-node connection through the tunnel.

Answer

Four times. First eth_type_trans inside __dev_forward_skb2 sets it to the host end of the source pod's veth pair. Second, skb_do_redirect from cil_from_container sets it to cilium_geneve through the ordinary redirect path. Third, after the outer packet is routed, the transmit path sets it to the physical device, and on the far node the receive path sets it to that node's eth0. Fourth, gro_cells_receive after decapsulation delivers on cilium_geneve, and then skb_do_redirect from cil_from_overlay sets it to the destination pod's eth0. The bench trace shows all of these on one skb address.

The near miss is counting the wire as a device change. The two kind nodes are containers on one kernel here, so the capture shows the bridge crossing too; on real hardware that hop is a driver and a NIC instead.

3. Predict the value: on a cluster identical to the bench except that bpf.hostLegacyRouting is true, you repeat the pod-to-world capture and count nf_hook_slow inside the node. Is it still zero, and which line in the source decides?

Answer

No, it becomes non-zero, and bpf/bpf_lxc.c:1547 decides. With host routing on, that if (is_defined(ENABLE_HOST_ROUTING)) branch calls fib_redirect_v4 at line 1550 and the skb goes straight to the physical device, which the bench measured as zero hook calls in the node. With legacy routing the branch is not compiled in, execution falls through to the pass_to_stack label at line 1565 and returns CTX_ACT_OK, so the packet enters ip_rcv on the lxc device and traverses PRE_ROUTING, the routing decision, FORWARD and POST_ROUTING, and the masquerade becomes an iptables rule rather than snat_v4_nat.

The near miss is "it is still zero because the masquerade is BPF either way". The masquerade setting and the host-routing setting are independent; legacy host routing sends the packet through the chains even if bpf.masquerade stays on.
