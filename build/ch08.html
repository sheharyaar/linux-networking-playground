Chapter 8

Two programs on one host: lo, same pod, unix sockets

~RT8 min · SOCK · Spine: chapters 1 to 7 followed one skb in from a network card and back out. Now both ends live on the same machine and the card is never involved. This chapter shows where that skb goes instead, then removes the device layer entirely.

Three scenarios that collapse into one

Two programs on two ports of one interface; two programs on two different interfaces of one machine; two containers in one Kubernetes pod. Three questions, one answer, because the decision is made in the output route lookup and it does not consult the interface you expect.

ip_route_output_key_hash_rcu (net/ipv4/route.c:2736) runs the FIB lookup, and when the answer is RTN_LOCAL it overrides the device (lines 2872 to 2890):

if (res->type == RTN_LOCAL) {
        /* L3 master device is the loopback for that domain */
        dev_out = l3mdev_master_dev_rcu(FIB_RES_DEV(*res)) ? :
                net->loopback_dev;
        flags |= RTCF_LOCAL;

The matching route entry named a real interface; the output device is overwritten anyway. The bench shows both halves on one node:

# ip route show table local
local 172.18.0.4 dev eth0 proto kernel scope host src 172.18.0.4
# ip route get 172.18.0.4 from 10.128.0.75
local 172.18.0.4 from 10.128.0.75 dev lo table local

The table entry says dev eth0; the lookup answers dev lo. Traffic from one local address to another goes through the loopback device even when the two addresses sit on different physical cards. The interface an address is configured on decides which card answers ARP for it and which card may receive it from outside. It decides nothing about locally generated traffic to it.

One more line matters shortly. RTCF_LOCAL is set here, and rt_dst_alloc (route.c:1670) reads it: rt->dst.output = ip_output at line 1691, and if (flags & RTCF_LOCAL) rt->dst.input = ip_local_deliver at lines 1692 to 1693. The output route is born already knowing what the input side should do.

Down the transmit path and straight back up

The skb then takes the transmit path of chapter 6: LOCAL_OUT, POST_ROUTING, a loopback neighbour that is permanently valid and needs no ARP, and __dev_queue_xmit finding lo set to noqueue, so the driver is called directly. That driver is loopback_xmit (drivers/net/loopback.c:70 to 94), and four lines decide everything:

skb_orphan(skb);                             /* line 80 */
skb_dst_force(skb);                          /* line 85 */
skb->protocol = eth_type_trans(skb, dev);    /* line 87 */
if (likely(__netif_rx(skb) == NET_RX_SUCCESS))    /* line 90 */

skb_orphan releases the sending socket's accounting, which is why the trace shows tcp_wfree here. skb_dst_force takes a real reference on the route. eth_type_trans does what a receive path expects: read the Ethernet header, set skb->pkt_type and skb->protocol, pull the header off. Then __netif_rx hands the skb to the per-CPU backlog of chapter 1. The transmit path ends inside a receive path, same softirq, same skb.

A live SYN on the node, condensed, one skb address on every line:

ip_local_out > nf_hook_slow > ip_output > nf_hook_slow > ip_finish_output2 >
__dev_queue_xmit > dev_hard_start_xmit > loopback_xmit > tcp_wfree >
eth_type_trans > __netif_rx > enqueue_to_backlog > ip_rcv > ip_rcv_core >
nf_hook_slow > ip_rcv_finish_core > ip_local_deliver > nf_hook_slow > tcp_v4_rcv

Count the nf_hook_slow calls: four. LOCAL_OUT, POST_ROUTING, PRE_ROUTING, LOCAL_IN. The skb walks the netfilter chart twice, in one namespace, and every rule applies both times. A POSTROUTING rule counting bytes that leave the machine counts this packet, which never leaves the machine.

Now what the trace lacks: no ip_route_input_noref and no ip_route_input_slow in the whole 1,631-line capture. The receive half does no routing lookup. skb_dst_force kept the output route attached, that route was built with RTCF_LOCAL so its input function is already ip_local_deliver, and ip_rcv_finish_core looks up a route only when !skb_valid_dst(skb) (net/ipv4/ip_input.c:406, skb_valid_dst at include/net/dst_metadata.h:93). The route the sender computed is the route the receiver uses. Remember this when the next chapter sends the same skb through a veth pair and gets the opposite result.

What a tap on lo sees, and how often

A packet socket on lo sees every packet twice, and this is worth settling by measurement because both answers sound plausible.

xmit_one (net/core/dev.c:3878) calls dev_queue_xmit_nit when a tap is active (lines 3883 to 3884), which clones the skb and sets skb2->pkt_type = PACKET_OUTGOING (line 2597). The ptype_all walk of chapter 3 then delivers it again on the way in, as PACKET_HOST. Two deliveries, one per direction through the device. A suppression mechanism exists and does not apply: packet_rcv (net/packet/af_packet.c:2144), packet_rcv_spkt (line 1893) and tpacket_rcv (line 2273) discard pkt_type PACKET_LOOPBACK, but only dev_loopback_xmit (dev.c:4345) sets that, and it serves multicast and broadcast self-copies.

Measured with a packet socket bound to lo, one local HTTP request gave twenty-four frames for twelve packets, in pairs with identical sequence numbers:

('OUTGOING', 35726, 4240, 1415493697)
('HOST',     35726, 4240, 1415493697)
TOTAL frames seen by the tap: 24

So tcpdump -i lo showing an apparent duplicate of every packet is correct, and pkt_type is how you tell the two apart.

Same pod: one namespace, two containers

Kubernetes gives every container in a pod the same network namespace, and everything follows from that. Two containers of a throwaway pod on the bench:

alpha# readlink /proc/self/ns/net  ->  net:[4026532689]
beta#  readlink /proc/self/ns/net  ->  net:[4026532689]
alpha# ip -br a  ->  lo ..., eth0@if19 10.128.0.82/32
beta#  ip -br a  ->  lo ..., eth0@if19 10.128.0.82/32

Same inode, same device index, same address, so a connection between them addressed to the pod IP is the first scenario of this chapter happening inside the pod. Traced on the node while one container talked to a listener in the other, the capture held 390 events, every one carrying the pod's namespace inode and an interface column reading lo. Searching it for the host-side veth device, for veth_xmit, for any Cilium program name and for nf_hook_slow returned zero lines. The pod's veth device is idle, the BPF program on its host end is never called, and since that namespace has no registered hook entries the four hook points cost nothing. The Cilium chapters show what that program does when it is called.

One detail catches people. ss -tlnp in the container owning a listener prints the socket and the process; in the sibling container it prints the same socket with an empty process column. They share a network namespace and read the same socket table, and they do not share a process namespace, so the second cannot map the socket inode to anything in its own /proc.

Unix sockets: an skb with nothing attached

Now take the device layer away. A unix socket still allocates an skb, which surprises people who expect a plain memory copy, and that skb is the only thing the two paths share.

unix_stream_sendmsg (net/unix/af_unix.c:2377) loops over the caller's data. Each turn calls sock_alloc_send_pskb (line 2437), charging the bytes to the sender's send buffer and blocking at that limit, then skb_copy_datagram_from_iter (line 2467) copies the payload in. Delivery is three lines:

__skb_queue_tail(&other->sk_receive_queue, skb);   /* line 2488 */
unix_state_unlock(other);
READ_ONCE(other->sk_data_ready)(other);            /* line 2492 */

The skb goes on the peer's sk_receive_queue, the list recvmsg drains in chapter 7, and sk_data_ready wakes the reader through sock_def_readable. The reader is unix_stream_read_generic (line 2907). The datagram variant unix_dgram_sendmsg (line 2083) queues at line 2291 and adds peer-wake machinery (unix_dgram_peer_wake_me, line 571) so a sender blocked on a full receiver is woken when the receiver drains.

What makes this fast is everything that is absent:

That last row has its own code. unix_find_other (line 1273) chooses on one condition, if (sunaddr->sun_path[0]) at line 1279. A non-zero first byte means a filesystem path, and unix_find_bsd (line 1189) resolves it through the normal path walk to an inode, so file permissions and the mount namespace control who may connect. A zero first byte means an abstract socket, and unix_find_abstract (line 1254) looks it up in a hash table keyed by name and by network namespace. Abstract unix sockets are scoped by the network namespace although no packet touches a device, which is why two pods can both bind the same abstract name. Alongside, SCM_RIGHTS sends open file descriptors in UNIXCB(skb).fp, refused at line 2478 if the receiver has not opted in, and SOCK_SEQPACKET offers record boundaries with connections and reliability.

Try it

Host lab, run as root. Prerequisites: iproute2, python3, curl, tcpdump (package tcpdump), pwru, and bpftrace (package bpftrace) for the last block.

sudo lab/08-lo-unix.sh up      # adds pp-dummy0 10.8.0.1 and a listener on 8082

# 1. the lookup ignores the interface the address lives on
ip route show table local | grep 10.8.0.1   # says dev pp-dummy0
ip route get 10.8.0.1 from 192.168.1.10     # answers dev lo

# 2. four nf_hook_slow lines for one SYN, one skb address
sudo pwru --output-meta 'tcp and port 8082'
curl -s -o /dev/null --interface 192.168.1.10 http://10.8.0.1:8082/

# 3. every packet twice, once out and once in
sudo tcpdump -i lo -n -Q inout -c 8 'tcp port 8082'

# 4. the unix socket: sendmsg and the wakeup fire, nothing else does
sudo bpftrace -e '
kprobe:unix_stream_sendmsg { @send = count(); }
kprobe:sock_def_readable   { @wake = count(); }
kprobe:__netif_rx          { @rx   = count(); }
kprobe:nf_hook_slow        { @nf   = count(); }
interval:s:5 { exit(); }' &
sudo python3 lab/unix_pair.py
sudo lab/08-lo-unix.sh down

Steps 1 to 3 match what was measured on the bench. Step 4 is expected rather than observed: the send and wake counters should move together while the other two stay still, but the bench node has no bpftrace and the host labs were not run for this dossier.

Recap

An output lookup returning RTN_LOCAL replaces the output device with the namespace's loopback device (route.c:2881), so local-to-local traffic uses lo whatever interface the addresses live on. The same lookup sets RTCF_LOCAL, making rt_dst_alloc store ip_local_deliver as the route's input function (line 1693), and because loopback_xmit calls skb_dst_force the receive half reuses that route and does no lookup. One skb walks the netfilter chart twice in one namespace. A tap on lo sees each packet twice, PACKET_OUTGOING then PACKET_HOST. Containers in one pod share the network namespace, so traffic between them is this same loopback path with no veth device and no BPF program involved. A unix socket keeps the skb and the receive queue and discards the device, the route, the headers and the hooks.

New words in this chapter

loopback_xmit
The loopback driver's transmit function: orphan the skb, pin the route, run eth_type_trans, call __netif_rx.
skb_dst_force
Takes a real reference on the skb's route so it stays valid across the transmit and receive boundary.
skb_valid_dst
The test ip_rcv_finish_core uses to decide whether an input route lookup is needed at all.
PACKET_OUTGOING, PACKET_LOOPBACK
The pkt_type a tap sees on the transmit side, and the one dev_loopback_xmit sets for multicast self-copies so packet sockets discard it.
unix_stream_sendmsg, unix_dgram_sendmsg
The unix socket send paths: allocate an skb, copy the payload, queue it on the peer.
unix_stream_read_generic
The unix socket read path, draining the peer's sk_receive_queue.
sock_alloc_send_pskb
The allocator charging an outgoing skb to the sender's send buffer, which is where unix socket backpressure comes from.
abstract socket
A unix socket whose name begins with a zero byte; it lives in a per namespace hash table rather than on a filesystem.
SCM_RIGHTS, SOCK_SEQPACKET
File descriptors carried in UNIXCB(skb).fp, and the unix socket type with record boundaries plus connections.

Check yourself

1. A machine has 10.0.0.1 on eth0 and 10.0.0.2 on eth1, two cards on two switches. A program binds 10.0.0.1 and connects to 10.0.0.2. Which cards carry the traffic, and which firewall chains can match it?

Answer

Neither card; the packet goes through lo, and OUTPUT, POSTROUTING, PREROUTING and INPUT can all match it. The output lookup returns RTN_LOCAL because 10.0.0.2 is a local address, and net/ipv4/route.c:2881 overwrites the output device with net->loopback_dev whatever interface the route entry named. The bench trace shows four nf_hook_slow calls for one SYN.

The near miss is "it leaves eth0 and comes back on eth1". Nothing reaches a wire, so a rule matching iif eth1 never fires and a capture on either card stays empty.

2. Trace the path: the receive half of a loopback packet reaches ip_rcv_finish_core. Why does it do no routing lookup? Name the state that makes it unnecessary and the call that preserved it.

Answer

The skb still carries the route the sender computed, and that route already says what to do. The output lookup set RTCF_LOCAL, which made rt_dst_alloc store rt->dst.input = ip_local_deliver (route.c:1693); loopback_xmit called skb_dst_force (drivers/net/loopback.c:85) so the route is still attached and refcounted; and ip_rcv_finish_core calls ip_route_input_noref only when !skb_valid_dst(skb) (net/ipv4/ip_input.c:406).

The near miss is "early demux found the socket". Early demux helps an established connection, but the route is reused even for the SYN, before any socket exists to demux to.

3. Predict the count: tcpdump -i lo -c 100 'tcp port 8080' while you drive exactly 30 TCP packets over a local connection. How many lines appear, which field separates them, and does the answer change for a multicast datagram the host sends to itself?

Answer

Sixty lines, separated by skb->pkt_type, and the multicast answer differs. Each packet reaches the tap once from dev_queue_xmit_nit on the way out, stamped PACKET_OUTGOING (net/core/dev.c:2597), and once from the ptype_all walk on the way in as PACKET_HOST; the bench run gave 24 frames for 12 packets. A multicast self-copy goes through dev_loopback_xmit, which sets PACKET_LOOPBACK (dev.c:4345), and packet_rcv discards that (af_packet.c:2144), so it appears once.

The near miss is "thirty, because it is one connection". Loopback is a real device with a real transmit side and a real receive side, and a tap sits on both.
