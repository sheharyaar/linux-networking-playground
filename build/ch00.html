Chapter 0 · Prologue

The chart, the skb, and the tracer

~RT0 min · LAB · Spine: our skb does not exist yet. Before it is born you need the one object you will follow, the map you already own, and the instruments that make the map move.

The chart is a map of hooks, and a hook is not a function

The netfilter packet-flow chart you have studied is correct, and it is complete for what it draws: the places where netfilter may look at a packet, in order, with the bridge layer below and the routing decisions between them. What it leaves out is everything that is not a hook. The chart says PREROUTING. The kernel says: ip_rcv validates the header, calls a hook macro that walks a list of registered functions, and, if the list says accept, calls ip_rcv_finish, which does the routing lookup that the chart draws as a diamond. The chart says bridging decision. The kernel says: a function pointer stored on the device, consulted from inside one loop, takes the packet away.

When a packet misbehaves, the chart tells you which hook to suspect. Only the functions tell you what to trace. This document is the chart with the function names filled in, and a tracer running next to it so you can watch the names go by in order, on your own kernel.

The one object: the skb

Everything in this document happens to one thing. An skb, short for socket buffer and spelled struct sk_buff in the source, is the kernel's description of one packet: a small block of metadata plus pointers into a separate data buffer that holds the bytes. The struct starts at include/linux/skbuff.h:886. Think of it as the shipping label clipped to a box. The label carries the routing state, the box carries the goods, and most of the kernel only reads and rewrites the label.

Five groups of fields decide where a packet goes, and you will see every one of them again:

FieldWhat it decidesLine in skbuff.h
skb->devWhich network device the packet belongs to right now. Every layer reads it, and virtual devices rewrite it. This one field is most of the veth chapter.894
skb->head, data, tail, endThe data buffer and the current cursor into it. data moves forward as headers are consumed and backward as they are added. The offsets mac_header, network_header and transport_header remember where each layer's header starts.1083 to 1095
skb->protocol, pkt_typeThe Ethernet type that picks the L3 handler, and whether the frame was addressed to this host, was broadcast, or was seen only because the device was told to accept every frame.1082, 975
skb->sk, skb->mark, skb->_nfctThe owning socket, the firewall mark, and a pointer to the connection-tracking entry. The last two are what netfilter reads and writes.907, 1069, 933
skb->users, skb->cbA reference count, and 48 bytes of scratch space each layer uses for its own bookkeeping.1097, 919

The reference count matters more than it looks. When two consumers need the same packet, the kernel does not copy the bytes. It bumps the count, or it allocates a second label pointing at the same box. Which of those happens, and where, is a recurring question in chapters 3 and 10.

The stage: devices and namespaces

A net_device, struct net_device, is anything the kernel can hand a packet to: a NIC driver instance, the loopback device lo, one end of a veth pair, a bridge, a bond, a tunnel. Each one has a transmit function the core calls, named ndo_start_xmit in its operations table, and each one may install a receive handler, a function pointer the receive loop consults before it does anything else with a frame from that device. Bridges, bonds and macvlan are all built on that one pointer.

A network namespace, or netns, is a private copy of the whole networking state: its own devices, addresses, routing tables, netfilter tables and sockets. A device belongs to exactly one namespace at a time, so skb->dev also tells you which namespace a packet is in. A container is a process in a namespace whose only device is one end of a veth. The tracer prints the namespace as an inode number, and watching that number change is how you will see a packet cross into a container.

Hooks, and what calling one costs

A netfilter hook is one of five points in the IP code, PRE_ROUTING, LOCAL_IN, FORWARD, LOCAL_OUT and POST_ROUTING (the enum is at include/uapi/linux/netfilter.h:42), where the code calls nf_hook with the skb and a continuation function. Two gates stand before any list is walked (include/linux/netfilter.h:227 onward). First a global jump label, nf_hooks_needed, which is off until some module registers at that hook anywhere on the machine. Second the namespace's own list head for that hook, which is empty in a fresh namespace even on a heavily firewalled host. Only if both pass does nf_hook_slow (net/netfilter/core.c:612) walk the entries in priority order and act on each verdict: accept continues, drop frees the skb, stolen means the entry took the skb and the caller must forget it. Conntrack and NAT are entries on those lists with fixed priorities. That is all chapter 5 is: the lists, the priorities, and what the entries write into skb->_nfct.

The instruments

A kprobe is a breakpoint the kernel plants at the entry of a function; when the function is called, a small program runs and the function then continues. Every tool below is built on kprobes.

pwru, "packet, where are you", plants a kprobe on every kernel function that takes an skb argument. On this kernel that is 1,598 functions, and attaching them takes about a second. You give it a filter in tcpdump syntax; it prints one line each time a matching skb enters a probed function: the skb address, the CPU, the process, the netns inode, the mark, the interface, the protocol, the MTU, the length, the L4 tuple, and the function name. That line, repeated, is the trace you will read in every chapter. Two blind spots matter. It probes only functions built into the kernel image unless you add --kmods veth,bridge or --all-kmods, so a packet crossing a veth appears to jump over the driver until you ask for the module. And it cannot match a packet with no IP header, so unix sockets need the next tool.

bpftrace plants a kprobe on one function you name and runs a one-line program: count by device, print a stack, read a struct field. It is the tool for functions pwru does not cover, for driver internals that take no skb, and for anything in the socket layer.

nft monitor trace works inside netfilter. A rule that says meta nftrace set 1 sets one bit on the skb, skb->nf_trace (include/linux/skbuff.h:1013, written at net/netfilter/nft_meta.c:501), and from then on every chain the skb enters reports each rule it evaluates and the verdict. It shows the rule walk that pwru sees only as one function name.

ftrace with the function_graph tracer records every function call under a chosen root, with entry and exit timing. It is expensive and noisy, and it is the only tool here that shows the call tree rather than a flat list. You will use it once, in the next chapter, to watch an interrupt turn into a packet.

The bench

The host labs run on your laptop as root. A second bench is worth knowing about: a kind node is a privileged container sharing your kernel, so docker exec kind-worker gives you a root shell where namespaces, veths, bridges, bonds and VRFs can be created and torn down without touching your host configuration, and the kernel loads the needed modules from the host when you ask for a device type. Two things differ from the host. The kind image ships no ping, tcpdump or bpftool, so the labs use curl against python3 -m http.server for traffic. And a handful of global knobs under net.core, the ones that tune the receive loop you meet in chapter 1, exist only in the initial namespace, so sysctl inside the node reports them as missing. Every trace transcript in this document was produced on that bench, on the same 7.2 kernel the source citations point at.

Try it

Confirm the bench, then take one look at a trace without trying to read it yet.

sudo lab/00-check.sh                      # tools, modules, BTF, tracefs
# 60 lines of trace for a ping to your default gateway; read the column headers, count distinct function names
GW=$(ip route show default | awk '{print $3; exit}')
sudo pwru --output-limit-lines 60 "icmp and host $GW" & sleep 5; ping -c1 -W1 $GW >/dev/null; wait
# the same bench inside the kind node
docker cp "$(command -v pwru)" kind-worker:/usr/local/bin/pwru
docker cp lab kind-worker:/root/lab

The functions you will see are the subject of chapters 4 and 6. For now, notice that the netns column stays constant, that the interface column names your real device only on the last few lines before the packet leaves, and that the process column names ping for the outgoing echo and a kernel thread or nothing for the reply.

Recap

One object, the skb, is a label pointing at a buffer; its dev, protocol, mark and _nfct fields decide the path. Devices are anything with a transmit function, and some also install a receive handler. Namespaces are private copies of the networking state, identified in traces by inode. A netfilter hook is a list walked by nf_hook_slow, behind a global jump label and a per-namespace list head. pwru prints one line per skb per function; bpftrace fills its blind spots; nft trace shows the rule walk; ftrace shows the call tree.

Check yourself

1. You trace a packet crossing a veth pair and the function list jumps from dev_hard_start_xmit straight to __dev_forward_skb. There is no veth_xmit line. Has the kernel skipped the driver?

Answer

No. pwru probes only functions in the kernel image by default, and veth_xmit lives in the veth module. Re-run with --kmods veth and the line appears right after dev_hard_start_xmit, exactly where xmit_one calls the device's ndo_start_xmit (net/core/dev.c:3890).

The tempting wrong answer is "the compiler inlined it". Inlining does happen to small static helpers, but veth_xmit is the module's transmit entry and a real symbol in veth.ko. When a name is missing from a pwru trace, check whether it belongs to a module before you suspect the compiler.

2. Two processes talk over a unix socket. pwru with a filter of host 127.0.0.1 prints nothing, and neither does a filter on the port. Why, and what do you use instead?

Answer

pwru's filter is compiled from tcpdump syntax into a program that reads IP and L4 headers out of the skb data. A unix socket skb carries no IP header at all, so no filter can match it, even though the unix functions that handle it are probed. Use bpftrace on unix_stream_sendmsg or unix_dgram_sendmsg, which chapter 8 does.

The near miss is "there is no skb for unix sockets, so there is nothing to trace". There is an skb; unix_stream_sendmsg allocates one with sock_alloc_send_pskb (net/unix/af_unix.c:2423) and queues it straight onto the peer socket. What is missing is a network header, and that is what the filter needs.

3. A trace taken inside a freshly created namespace shows ip_rcv, ip_rcv_core, then ip_rcv_finish_core, with no nf_hook_slow between them. The host has hundreds of firewall rules. Is netfilter broken in that namespace?

Answer

No. nf_hook has two gates (include/linux/netfilter.h:227 onward). The global jump label nf_hooks_needed is on, because the host has hooks registered, so the first gate passes. The second gate reads the namespace's own net->nf.hooks_ipv4[hook] list head, and a fresh namespace has nothing registered there, so it is NULL and nf_hook_slow is never called. Load an nftables table into that namespace and the line appears.

The wrong answer is "netfilter is global, so the rules apply everywhere". Hook registration is per namespace; that is why a container can have its own firewall, and why a packet crossing a veth into a namespace with no tables walks no hooks there even though the host is firewalled.
