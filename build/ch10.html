Chapter 10

The bridge, and Docker on it

~RT10 min · L2 · Spine: chapter 9 delivered our skb into a namespace through a veth pair. Put the host end of two such pairs into a bridge and the skb stops at L2 instead of climbing to IP. This chapter is that stop: who steals the skb, where it is put down, and what changes when br_netfilter drags the IP hooks back into a path that had left them behind.

Two ways a receive handler can end the round

Chapter 3 walked __netif_receive_skb_core and named the receive-handler station. Now look at what the caller does with the answer (net/core/dev.c:6097 to 6116):

rx_handler = rcu_dereference(skb->dev->rx_handler);
if (rx_handler) {
        switch (rx_handler(&skb)) {
        case RX_HANDLER_CONSUMED:  ret = NET_RX_SUCCESS; goto out;
        case RX_HANDLER_ANOTHER:   goto another_round;
        case RX_HANDLER_EXACT:     deliver_exact = true; break;
        case RX_HANDLER_PASS:      break;

Those first two verdicts are the difference between a bridge and every other master device in this document. A bridge answers RX_HANDLER_CONSUMED: it has taken ownership, the core stops, and nothing above L2 runs on this CPU pass. The bond, macvlan and ipvlan devices of the next two chapters answer RX_HANDLER_ANOTHER: they change skb->dev and send the core back to the top of its own function to redo the whole station list against the new device. Same station, two structurally different outcomes.

The bridge registers its handler when a port is added, netdev_rx_handler_register(dev, br_get_rx_handler(dev), p) (net/bridge/br_if.c:619), and the handler is br_handle_frame (net/bridge/br_input.c:339).

Where the bridge puts the skb down

br_handle_frame checks the port's spanning-tree state and, for a forwarding port, calls nf_hook_bridge_pre (br_input.c:267), which runs the NF_BR_PRE_ROUTING hook with br_handle_frame_finish (line 76) as its continuation. That is where the decisions are:

  • Learning, line 144: br_fdb_update(br, p, eth_hdr(skb)->h_source, vid, 0) records the source MAC against the port it arrived on. That table is the forwarding database.
  • Lookup, line 204: dst = br_fdb_find_rcu(br, eth_hdr(skb)->h_dest, vid).
  • A hit whose entry is flagged local means the frame is addressed to the bridge itself, so line 222 calls br_pass_frame_up.
  • A hit on another port, line 226: br_forward.
  • A miss, line 229: br_flood, which walks every port.

Take the forwarding case. br_forward (net/bridge/br_forward.c:144) reaches __br_forward (line 73), and two lines there do the work: indev = skb->dev then skb->dev = to->dev. The skb is now labelled with the outgoing port. It then runs the NF_BR_FORWARD hook with br_forward_finish (line 63) as the continuation, which runs NF_BR_POST_ROUTING with br_dev_queue_push_xmit (line 33) as its continuation. That last function pushes the Ethernet header back on, checks the frame still fits, and calls dev_queue_xmit(skb) at line 53. The skb re-enters the transmit path of chapter 6 on a different device, without ever having reached IP.

The bench shows all of it on one skb address, across three namespaces:

netns pp-l,  dev vl:24    ip_local_out ... veth_xmit > skb_scrub_packet > eth_type_trans
netns root,  dev vl-br:23 __netif_rx > enqueue_to_backlog > __netif_receive_skb_one_core
                          br_handle_frame_finish[bridge] > br_allowed_ingress[bridge]
                          br_forward[bridge] > __br_forward[bridge] > br_handle_vlan[bridge]
netns root,  dev vr-br:25 br_forward_finish[bridge] > br_dev_queue_push_xmit[bridge]
                          skb_push > __dev_queue_xmit > ... > veth_xmit[veth]
                          skb_scrub_packet > eth_type_trans
netns pp-r,  dev vr:26    __netif_rx > enqueue_to_backlog > __netif_receive_skb ...

The device column flips from vl-br to vr-br exactly at br_forward_finish, which is the skb->dev = to->dev assignment becoming visible. And grep -c nf_hook_slow over that entire capture returns zero. A bridge forwarding an IP packet touches no netfilter hook at all. The bridge hook points are traversed, and on a stock host nothing is registered at them.

Two details worth keeping. First, br_handle_frame never appears in the trace: its signature takes struct sk_buff **pskb, a double pointer, so pwru cannot read an skb out of it, and the first bridge function you see is the continuation. Second, flooding is the one place the bridge duplicates. br_flood (line 201) walks the port list calling maybe_deliver (line 176), which carries one port forward and calls deliver_clone (line 120) for the others; deliver_clone is a skb_clone and a recursive __br_forward. The last port gets the original. Local delivery is the mirror image: br_pass_frame_up (line 33) sets skb->dev to the bridge device itself and runs NF_BR_LOCAL_IN with br_netif_receive_skb (line 26) as the continuation, which calls netif_receive_skb. The core runs a second time, from the top, with the bridge as the device, and this time there is no receive handler so the frame climbs to IP.

br_netfilter: putting the IP hooks back

Everything above is why a firewall rule written for FORWARD does not match traffic between two containers on one bridge. The br_netfilter module exists to change that, and it is worth being precise about how, because the mechanism is unusual.

Loading the module registers br_nf_ops (net/bridge/br_netfilter_hooks.c:1047), six entries. Four sit on the bridge hooks: br_nf_pre_routing (line 483) at NF_BR_PRE_ROUTING, br_nf_local_in (line 585), br_nf_forward (line 769) at NF_BR_FORWARD, and br_nf_post_routing (line 925) at NF_BR_POST_ROUTING. Look at what the first one does once it has decided the frame carries IPv4 (lines 536 to 542):

NF_HOOK(NFPROTO_IPV4, NF_INET_PRE_ROUTING, state->net, state->sk, skb,
        skb->dev, NULL,
        br_nf_pre_routing_finish);

return NF_STOLEN;

It calls the IPv4 PRE_ROUTING chain from inside a bridge hook, passing the bridge port as the input device, and then returns NF_STOLEN so the bridge code does not continue on its own. Your nat and raw and filter chains run, conntrack runs, and the bridge's own walk resumes afterwards in the continuation. br_nf_forward_ip (line 673) does the same for NF_INET_FORWARD and br_nf_post_routing (line 925) for NF_INET_POST_ROUTING. The remaining two entries of the array are ip_sabotage_in, registered on IPv4 and IPv6 PRE_ROUTING at the very first priority, whose job is to suppress a second, duplicate run of those chains when the frame later climbs to IP through br_pass_frame_up.

The gate is a sysctl. br_nf_pre_routing starts with if (!brnet->call_iptables && !br_opt_get(br, BROPT_NF_CALL_IPTABLES)) return NF_ACCEPT (lines 516 to 517), and call_iptables is /proc/sys/net/bridge/bridge-nf-call-iptables (.procname at line 1192), defaulted to 1 when a namespace is created (line 1225). That path exists only once the module is loaded, which is the whole reason Kubernetes installation guides tell you to load br_netfilter and then set the sysctl: with the module absent, writing the sysctl fails, and with it present but the sysctl at zero, bridged traffic bypasses every IP rule you wrote.

On the machine this dossier was written on, the kind cluster's three nodes hang off a bridge called br-kind-cilium, and ip -d link show prints nf_call_iptables 0 for it, with no /proc/sys/net/bridge directory at all. That is the unloaded state, and it is why the bench trace above has no hooks in it.

Docker on the same machinery

Docker's default network is this chapter with names on it. docker0 is a bridge; every container gets a veth pair with one end in the container's namespace as eth0 and the other enslaved to docker0. Container to container on one network is the trace above. Container to the outside is different: the bridge has an IP address, the container's default route points at it, so the frame is addressed to the bridge's own MAC, the forwarding database entry is the local one, br_pass_frame_up runs, and the packet climbs to IP on the host and is routed and masqueraded like any other forwarded traffic.

That is where Docker's iptables chains sit. It adds a DOCKER chain for published-port destination NAT and a DOCKER-USER chain placed before its own rules so that operator rules are not overwritten when Docker rewrites its own, plus a masquerade rule for traffic leaving the bridge subnet. All of that lives on the IP hooks, which means it applies to the routed path and, for bridged container-to-container traffic, only when br_netfilter is loaded and the sysctl is on. Turning that sysctl off is a real and occasionally deliberate act: it makes same-bridge traffic invisible to iptables, which is faster and which quietly disables any network policy implemented with iptables rules.

Try it

Host lab, run as root. Prerequisites: iproute2, bridge (part of iproute2), curl, pwru, and the br_netfilter module for the second half.

sudo lab/10-bridge.sh up      # pp-l vl 10.10.0.1 -- pp-br0 -- vr 10.10.0.2 pp-r

# the forwarding database, before and after traffic
bridge fdb show br pp-br0 | grep -v permanent

# the whole path on one skb, three namespaces, and no hooks
sudo pwru --kmods bridge,veth --output-meta 'tcp and host 10.10.0.2' &
sudo ip netns exec pp-l curl -s --max-time 2 http://10.10.0.2:9099/

# now put the IP hooks back and run it again
sudo modprobe br_netfilter
cat /proc/sys/net/bridge/bridge-nf-call-iptables       # 1 by default
sudo pwru --kmods bridge,br_netfilter,veth --output-meta 'tcp and host 10.10.0.2' &
sudo ip netns exec pp-l curl -s --max-time 2 http://10.10.0.2:9099/
sudo lab/10-bridge.sh down

The first capture is real bench output and is reproduced above: one skb, three namespaces, zero nf_hook_slow. The second is expected rather than observed. br_netfilter was deliberately not loaded on the bench, because registering br_nf_ops is global and the default of 1 for bridge-nf-call-iptables would have changed packet handling for the bridge carrying the live cluster. Expect br_nf_pre_routing, then nf_hook_slow and the conntrack and chain functions of chapter 5, appearing between br_handle_frame_finish and br_forward.

Recap

A bridge port's receive handler returns RX_HANDLER_CONSUMED, so the core stops and the skb never climbs to IP on that pass. br_handle_frame_finish learns the source MAC into the forwarding database, looks up the destination, and either passes the frame up to the bridge device, forwards it to one port, or floods it by cloning to all but the last. Forwarding is skb->dev = to->dev followed by dev_queue_xmit, so the skb leaves on a new device from inside the receive handler; the bench capture shows one skb address across three namespaces and no netfilter hook at all. br_netfilter changes that by calling the IPv4 chains from inside the bridge hooks and returning NF_STOLEN, gated per namespace by bridge-nf-call-iptables. Docker's bridge network is this machinery with docker0, veth pairs and the DOCKER and DOCKER-USER chains on top.

New words in this chapter

br_handle_frame
The bridge's receive handler, registered per port; it returns RX_HANDLER_CONSUMED.
br_handle_frame_finish
The continuation after the bridge PRE_ROUTING hook, where learning and the forwarding decision happen.
forwarding database
The bridge's MAC-to-port table, read by br_fdb_find_rcu and written by br_fdb_update; bridge fdb show prints it.
br_forward, __br_forward
The one-port forwarding path; __br_forward performs the skb->dev = to->dev assignment.
br_flood, deliver_clone
Delivery to every port for an unknown destination, cloning the skb for all but the last port.
br_dev_queue_push_xmit
Pushes the Ethernet header back and calls dev_queue_xmit on the chosen port.
br_pass_frame_up
Local delivery: set skb->dev to the bridge device and re-enter netif_receive_skb.
NF_BR_ hooks
The bridge family's own hook points, PRE_ROUTING, FORWARD, LOCAL_IN and POST_ROUTING, which ebtables and nftables bridge chains attach to.
br_netfilter
The module that calls the IPv4 and IPv6 chains from inside the bridge hooks and returns NF_STOLEN.
bridge-nf-call-iptables
The per namespace sysctl gating that behaviour; it exists only once br_netfilter is loaded.
ip_sabotage_in
The br_netfilter entry on IP PRE_ROUTING that suppresses a duplicate chain run when a bridged frame later climbs to IP.
DOCKER, DOCKER-USER
Docker's own iptables chains for published-port destination NAT and for operator rules that Docker will not rewrite.

Check yourself

1. Two containers on one Docker bridge talk to each other. Your iptables -I FORWARD -j DROP rule does nothing. Name the verdict that explains it, and the two conditions that would make the rule start working.

Answer

RX_HANDLER_CONSUMED explains it. br_handle_frame returns that verdict at net/core/dev.c:6104, the core stops, and the frame is forwarded from inside the handler by br_dev_queue_push_xmit without ever reaching ip_rcv or the FORWARD hook. The two conditions are the br_netfilter module being loaded, which registers br_nf_forward_ip to call NF_INET_FORWARD (net/bridge/br_netfilter_hooks.c:673), and bridge-nf-call-iptables being 1 in that namespace. The bench capture without the module contains zero nf_hook_slow calls.

The near miss is "the rule is in the wrong chain, it should be INPUT". Chain choice is not the problem; no IP chain of any name runs for this frame.

2. Trace the path: a frame arrives on a bridge port addressed to the bridge's own MAC address. How many times does __netif_receive_skb_core run for it, with which device each time?

Answer

Twice: once with the port as skb->dev and once with the bridge device. The first pass finds the port's receive handler, which consumes the skb; br_handle_frame_finish finds a forwarding-database entry flagged local and calls br_pass_frame_up (net/bridge/br_input.c:33), which sets skb->dev to the bridge device and calls netif_receive_skb through br_netif_receive_skb (line 26). The bridge device has no receive handler, so the second pass runs the whole station list and reaches ip_rcv.

The near miss is "once, the handler just passes it up". RX_HANDLER_PASS would do that, but the bridge returns CONSUMED and re-enters the core from the top, which is why a tap on the bridge device sees the frame separately from a tap on the port.

3. Predict the trace: an unknown unicast frame arrives on a bridge with four ports. How many skbs exist by the time it has left, and which function creates them?

Answer

Three, and deliver_clone creates the extra two. The destination is not in the forwarding database, so br_handle_frame_finish calls br_flood (net/bridge/br_forward.c:201), which walks the port list through maybe_deliver (line 176). The ingress port is skipped by should_deliver, leaving three egress ports; maybe_deliver carries one port forward and calls deliver_clone (line 120) for the earlier ones, so two skb_clone calls happen and the last port receives the original.

The near miss is "four, one per port". The ingress port never receives the frame back, and the final port reuses the original rather than getting a clone of its own.
