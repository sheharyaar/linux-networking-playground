Chapter 4

L3 receive: ip_rcv, PREROUTING, and the routing decision

~RT4 min · L3 · Spine: the protocol demux has handed our skb to ip_rcv. This chapter walks the IP receive path up to the routing decision, and then through whichever of two doors it opens: local delivery towards a socket, or forwarding back out.

The checks, and the moment the sender lets go

ip_rcv (net/ipv4/ip_input.c:603) is four lines: call ip_rcv_core, then call the PRE_ROUTING hook with ip_rcv_finish as the continuation (lines 612 to 614). The work is in ip_rcv_core (line 499). It drops frames marked PACKET_OTHERHOST (line 508), the promiscuous leftovers of chapter 3. It makes sure the first 20 bytes are readable (line 523), checks version 4 and a header length of at least five words (line 539), pulls the options if the header is longer (line 549), verifies the header checksum (line 554), and trims the skb to the IP total length. Then it wipes the 48 bytes of scratch space, skb->cb, for IP's own use.

And then, at lines 581 to 583, under the comment "Must drop socket now because of tproxy", it calls skb_orphan. That runs the skb's destructor, which is the sending socket's accounting callback: tcp_wfree for a data segment, sock_edemux for a SYN-ACK built from a request socket (net/ipv4/tcp_output.c:3958). This is the tcp_wfree line you have seen in every trace so far, right after ip_rcv_core. It says something worth knowing: on a veth or on lo, the skb still belonged to the sender's socket until the receiver's IP layer ran, and the sender's send buffer is credited back only here. On a real NIC the driver's transmit completion did this long before.

When the skb arrived through the GRO door in a batch, the same steps happen through ip_list_rcv (line 687), which calls ip_rcv_core per skb and then the hook once for the whole list with NF_HOOK_LIST (line 679). That is why a trace from a NAPI device shows ip_rcv_core with no ip_rcv before it.

PRE_ROUTING, as a black box for one more chapter

Between ip_rcv_core and ip_rcv_finish sits the PRE_ROUTING hook. In the fresh namespace of the veth bench the trace goes straight from ip_rcv_core to ip_rcv_finish_core; in the router namespace with one nftables table loaded, eleven function names appear in between. Chapter 5 opens that box. One fact about it belongs here because it shapes the routing decision: every entry in the hook runs before the route lookup. An entry may rewrite the destination address, and the lookup that follows sees the rewritten one. That single ordering is why the chart puts destination NAT in PREROUTING, before the routing diamond.

The routing decision is a function pointer

ip_rcv_finish (line 478) first offers the skb to a VRF master if the incoming device has one, through l3mdev_ip_rcv (line 486); with no VRF this returns the skb untouched, and chapter 11 is where it does not. Then ip_rcv_finish_core (line 361) tries a shortcut, early demux (lines 376 to 400): if net.ipv4.ip_early_demux and tcp_early_demux are on, tcp_v4_early_demux (line 322) looks up an established TCP socket by the four-tuple before any routing happens, and if it finds one, attaches that socket's cached route to the skb so the lookup below is skipped. In the loopback trace this shows as two inet_lhash2_lookup lines before ip_rcv_finish_core: the SYN found only a listener, so the shortcut did nothing, and the full lookup ran.

The full lookup is ip_route_input_noref (line 407), which reaches ip_route_input_slow (net/ipv4/route.c:2286). The name is historical. The route cache it was slow compared to was removed in Linux 3.6, and this is now the normal path for every packet that early demux did not catch. It calls fib_lookup (line 2380), which walks the policy rules that ip rule shows to pick a table (fib4_rule_match, net/ipv4/fib_rules.c:180), then does a longest-prefix match in that table's FIB, the forwarding information base, stored as a level-compressed trie (fib_table_lookup, net/ipv4/fib_trie.c:1420). What comes back is a route type, and the type decides everything.

RTN_LOCAL (checked at line 2397): the destination is one of this host's own addresses, on any interface. The source is validated against reverse-path rules, fib_validate_source, the two lines you see in every trace, and the code jumps to local_input (line 2437), which allocates the route entry with RTCF_LOCAL set, so that rt_dst_alloc (line 1670) stores ip_local_deliver as its input function (line 1693). RTN_UNICAST: the destination is somewhere else. First the forwarding switch is checked, at lines 2405 to 2407: if net.ipv4.ip_forward, or the per-device forwarding sysctl, is off, the packet gets a route whose input function is ip_error. Otherwise ip_mkroute_input leads to __mkroute_input (line 1908), which stores ip_forward as the input function (line 1918).

The result is a dst_entry, the route object, attached to the skb and readable as skb_dst(skb). It carries two function pointers, input and output, and the next hop. When ip_rcv_finish regains control it calls dst_input(skb) (include/net/dst.h:478), which is nothing more than skb_dst(skb)->input(skb). That indirect call is the routing diamond on the chart. The decision was made when the pointer was stored; the diamond is just the call.

Door one: local delivery

ip_local_deliver (net/ipv4/ip_input.c:250) reassembles fragments if the packet is one, then calls the LOCAL_IN hook with ip_local_deliver_finish (line 229) as the continuation. That reaches ip_protocol_deliver_rcu (line 189), which first offers the packet to any raw sockets, raw_local_deliver, then looks up the transport protocol number in inet_protos (line 198) and calls its handler (line 205): tcp_v4_rcv, udp_rcv or icmp_rcv. Watch the length column in a trace at this point. It drops from 60 to 40 for a SYN, because the 20-byte IP header has been pulled and skb->data now points at the TCP header. Chapter 7 picks the skb up there.

Door two: forwarding

ip_forward (net/ipv4/ip_forward.c:83) checks the TTL first (line 118) and answers with an ICMP time exceeded if it is one or less. Then, at line 144, it calls skb_cow: before writing to the header, make sure this skb owns its head privately and has room for the outgoing link-layer header. A TCP segment fails that test, because TCP transmits a clone of the skb it keeps for retransmission (net/ipv4/tcp_output.c:1563), and the clone shares its head with the original. So the router trace shows pskb_expand_head, skb_release_data and skb_headers_offset_update between ip_forward and the FORWARD hook: the header is copied so it can be modified. Then ip_decrease_ttl (line 149), then the FORWARD hook (lines 162 to 164) with ip_forward_finish (line 65) as the continuation, which calls dst_output (line 80): skb_dst(skb)->output, which rt_dst_alloc set to ip_output (route.c:1691). From there the packet is on the transmit path of chapter 6, joining it at the POST_ROUTING hook. No socket was involved. The FORWARD hook is the only place a firewall on this host sees transit traffic.

And when forwarding is off, ip_error (route.c:990) receives the packet instead. Its first branch is for exactly this case: it increments IpInAddrErrors and frees the skb, and it does not send an ICMP error. The client sees nothing and retransmits until it gives up. The bench trace ends with ip_route_input_slow, ip_error, then sk_skb_reason_drop(SKB_DROP_REASON_IP_INADDRERRORS), because pwru prints the drop reason when a function frees the skb.

Try it

Bring up the three-namespace router, watch both doors, then close one.

sudo lab/05-router.sh up
sudo ip netns exec pp-s python3 -m http.server 8080 --bind 10.5.2.2 &
# what the router will decide, before sending anything
sudo ip netns exec pp-rt ip route get 10.5.2.2 from 10.5.1.2 iif r0
# trace only the router namespace, then request from the client
sudo pwru --filter-netns /run/netns/pp-rt 'tcp and port 8080'
sudo ip netns exec pp-c curl -s -o /dev/null http://10.5.2.2:8080/
# close the forwarding door and watch where the SYN dies
sudo ip netns exec pp-rt sysctl -w net.ipv4.ip_forward=0
sudo ip netns exec pp-c curl -s -m 3 http://10.5.2.2:8080/ ; echo "exit $?"
sudo ip netns exec pp-rt nstat -az IpInAddrErrors
sudo ip netns exec pp-rt sysctl -w net.ipv4.ip_forward=1

With forwarding on, the SYN reads ip_rcv_finish_core, ip_route_input_noref, ip_route_input_slow, fib_validate_source, ip_forward, pskb_expand_head, then the hook, then ip_forward_finish and ip_output on the far interface. With forwarding off it reads ip_route_input_slow, ip_error, and a drop with reason IP_INADDRERRORS; curl exits 28 after its timeout, and the counter has gone up by the number of retransmitted SYNs.

Recap

ip_rcv_core validates the header and orphans the skb from the sending socket. The PRE_ROUTING hook runs before any route lookup. ip_route_input_slow consults policy rules and the FIB trie and stores one of three input functions in the route: ip_local_deliver for a local address, ip_forward for a remote one when forwarding is on, ip_error when it is off. dst_input is the indirect call through that pointer. Local delivery passes the LOCAL_IN hook and hands the skb to the transport handler. Forwarding checks the TTL, copies a shared header, decrements the TTL, passes the FORWARD hook and calls the route's output function, ip_output.

early demux
Looking up an established socket before routing so its cached route can be reused.

Check yourself

1. Predict the outcome: the router has net.ipv4.ip_forward=0 and the nftables table of the lab loaded. A client sends a SYN through it. Which chains see the packet, where does it die, and what does the client observe?

Answer

The PRE_ROUTING chains see it; the FORWARD chain never does; the client gets no answer and times out. The forwarding switch is tested inside ip_route_input_slow at net/ipv4/route.c:2405, after the hook has already run, and it makes the route's input function ip_error (line 990). ip_error's first branch, for an incoming device with forwarding disabled, increments IpInAddrErrors and frees the skb without sending ICMP. The trace ends at ip_error with drop reason IP_INADDRERRORS; the nftables forward chain counters do not move.

The near miss is "the router sends ICMP host unreachable". It does that only when forwarding is on and the lookup finds no route. With forwarding off the drop is silent, which is exactly what makes a forgotten sysctl hard to diagnose from the client side.

2. Every trace of a packet arriving over a veth or over lo shows tcp_wfree immediately after ip_rcv_core, in the receiver's namespace. Traces of packets arriving from a real NIC never show it. What does the line mean, and why the difference?

Answer

It is the sender's socket releasing its send-buffer accounting for that skb. ip_rcv_core calls skb_orphan at net/ipv4/ip_input.c:583, which runs the skb's destructor, and a TCP data skb's destructor is tcp_wfree. On a veth or on lo the skb is the very same object the sender's TCP built, handed across with skb->sk still set, so the orphan happens here, in the receiver's IP layer. A frame from a real NIC was built by the driver in chapter 1 and never had an owning socket; the sender's copy was orphaned by the sender's driver on transmit completion.

The near miss is reading it as "the receiver is freeing the packet". Nothing is freed; the skb continues into ip_rcv_finish_core on the next line. Only the ownership link is cut.

3. In the router trace, every forwarded TCP segment shows pskb_expand_head right after ip_forward, but forwarded ICMP echo requests from ping do not. What is the router copying, and why only for TCP?

Answer

The skb head, so it can write the decremented TTL into a private copy. ip_forward calls skb_cow at net/ipv4/ip_forward.c:144 before ip_decrease_ttl at line 149. skb_cow reallocates when the head is shared or headroom is short. A TCP segment is a clone made by __tcp_transmit_skb (net/ipv4/tcp_output.c:1563), sharing its head with the copy TCP keeps for retransmission, so it is always shared here. An echo request from ping is built once and sent once, is not cloned, and has ample headroom, so skb_cow does nothing.

The near miss is "the veth strips headroom". The headroom is fine; the test that fails is skb_cloned. The same copy happens on a real router with real NICs, for the same reason.
