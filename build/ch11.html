Chapter 11

Master devices: bond and VRF

~RT11 min · L2 L3 · Spine: the bridge of chapter 10 answered RX_HANDLER_CONSUMED and our skb never climbed to IP. The two devices in this chapter answer the other verdict. They relabel the skb and send the core round again, once at L2 and once at L3, and the visible cost is that the hooks you know run twice.

The bond: one skb, two passes, both directions

A bond enslaves its members the same way a bridge enslaves ports, netdev_rx_handler_register(slave_dev, bond_handle_frame, new_slave) (drivers/net/bonding/bond_main.c:2234). The handler (line 1603) opens with its default answer already chosen, int ret = RX_HANDLER_ANOTHER at line 1610, and ends with two statements that matter: skb->dev = bond->dev, then that return. The core's another_round label sends it back to the top of the station list with the new device, so tc ingress, the receive handler check and the protocol demux all run a second time, and this time the device has no handler.

The bench shows the swap as a single line boundary. Sending to a bonded peer and watching the reply come back:

dev pp-s1:28     __netif_rx > netif_rx_internal > enqueue_to_backlog >
                 __netif_receive_skb > __netif_receive_skb_one_core
dev pp-bond0:31  qdisc_pkt_len_segs_init > skb_ensure_writable > ip_rcv >
                 ip_rcv_core > sock_wfree > nf_hook_slow > ...

Same skb address on both lines; the device column changes in between. ip_rcv and every netfilter rule after it see pp-bond0, so iif matches name the bond and never the slave. That is the point of the device.

Two things happen before the swap. recv_probe, a function pointer on the bond (include/net/bonding.h:226), is called first if set; it is bond_3ad_lacpdu_recv for LACP mode (set at line 4394) and bond_rcv_validate for the ARP monitor (line 4388), and it is how control frames are consumed before the data path sees them. Then bond_should_deliver_exact_match (line 1589) checks whether this slave is inactive; in active-backup mode the standby slave still receives broadcast traffic, and returning RX_HANDLER_EXACT restricts delivery to packet sockets bound to that exact device rather than letting it into the stack twice.

Transmit is the mirror. bond_start_xmit (line 5596) calls __bond_start_xmit (line 5558), which is one switch on BOND_MODE(bond):

case BOND_MODE_ROUNDROBIN:   return bond_xmit_roundrobin(skb, dev);
case BOND_MODE_ACTIVEBACKUP: return bond_xmit_activebackup(skb, dev);
case BOND_MODE_8023AD:       ... fallthrough;
case BOND_MODE_XOR:          return bond_3ad_xor_xmit(skb, dev);
case BOND_MODE_BROADCAST:    return bond_xmit_broadcast(skb, dev, true);

Each of those picks a slave and calls bond_dev_queue_xmit (line 297), which sets skb->dev to the slave and calls dev_queue_xmit again. So the transmit path of chapter 6 runs twice for one packet, and the trace says so plainly:

dev pp-bond0:31  __dev_queue_xmit > netdev_core_pick_tx > bond_select_queue[bonding] >
                 dev_hard_start_xmit > bond_start_xmit[bonding] > bond_dev_queue_xmit[bonding]
dev pp-s1:28     __dev_queue_xmit > ... > dev_hard_start_xmit > veth_xmit[veth]

This matters for queueing. The bond device itself normally carries no queueing discipline, and the second __dev_queue_xmit is where the slave's real one runs. A shaper attached to the bond is in the wrong place; it belongs on the slaves, or the bond needs an explicit qdisc of its own.

For the modes that spread traffic, the slave is chosen by bond_xmit_hash (line 4287) over __bond_xmit_hash (line 4253), and the transmit hash policy decides which bytes go into the hash: BOND_XMIT_POLICY_LAYER2 uses the MAC addresses, LAYER34 the addresses and ports, LAYER23 the MACs and IP addresses, with encapsulation-aware variants (include/uapi/linux/if_bonding.h:92 to 97). A layer-2 policy between two routers puts every flow on one slave, because every frame carries the same pair of MAC addresses, and that is the commonest reason a bond delivers the bandwidth of exactly one member.

The VRF: the same trick one layer up

A VRF device does at L3 what the bond does at L2, and the machinery is a different hook. ip_rcv_finish (net/ipv4/ip_input.c:478) calls l3mdev_ip_rcv(skb) at line 486, before the routing decision at line 490. For an enslaved device that reaches vrf_l3_rcv (drivers/net/vrf.c:1379) and then vrf_ip_rcv (line 1340), whose first three statements are the whole idea:

skb->dev = vrf_dev;
skb->skb_iif = vrf_dev->ifindex;
IPCB(skb)->flags |= IPSKB_L3SLAVE;

and whose last statement is vrf_rcv_nfhook(NFPROTO_IPV4, NF_INET_PRE_ROUTING, skb, vrf_dev). That helper (line 1132) calls nf_hook for PRE_ROUTING a second time, with the VRF device as the input device. PRE_ROUTING has already run once, back in ip_rcv, with the enslaved device. The bench counts both:

dev pp-ve:34   ip_rcv > ip_rcv_core > nf_hook_slow      <-- PRE_ROUTING, device pp-ve
dev pp-ve:34   vrf_l3_rcv[vrf]
dev pp-vrf:32  nf_hook_slow                             <-- PRE_ROUTING again, device pp-vrf
dev pp-vrf:32  ip_rcv_finish_core > ip_route_input_noref > ip_route_input_slow
dev pp-vrf:32  ip_local_deliver > nf_hook_slow > tcp_v4_rcv

A rule written once in PRE_ROUTING therefore fires twice for a VRF-enslaved packet, once per device. A counter doubles. A notrack or a NAT rule written without an interface match is applied to both passes. This is the single most surprising thing about running a firewall on a VRF host, and it falls straight out of the two lines above.

The table selection is a routing rule rather than code. ip rule show on the bench lists 1000: from all lookup [l3mdev-table], a rule whose action is to consult the table belonging to whichever VRF the packet is associated with; that number comes from vrf_fib_table (line 1119), which returns the device's tb_id. The effect is visible in the table itself:

# ip route show table 10
10.12.0.0/24 dev pp-ve proto kernel scope link src 10.12.0.1
local 10.12.0.1 dev pp-ve proto kernel scope host src 10.12.0.1

Even the local entry moved out of the global local table into table 10, which is why an address inside a VRF is unreachable from outside it without an explicit route.

Output is symmetric and produces four hook calls for one packet. vrf_l3_out (line 945) reaches vrf_ip_out (line 926), which takes the direct path vrf_ip_out_direct (line 905) when the VRF has the default queueing discipline. That function sets skb->dev = vrf_dev at line 911 and runs LOCAL_OUT with the VRF device at line 913; vrf_output_direct (line 876) then runs POST_ROUTING with it at line 884; vrf_finish_direct hands the skb back, and the ordinary __ip_local_out and ip_output run LOCAL_OUT and POST_ROUTING again with the real device. The trace shows exactly four:

dev 0          ip_local_out > __ip_local_out > vrf_l3_out[vrf]
dev pp-vrf:32  nf_hook_slow       <-- LOCAL_OUT, VRF device
dev pp-vrf:32  nf_hook_slow       <-- POST_ROUTING, VRF device
dev pp-vrf:32  vrf_finish_direct[vrf]
dev pp-vrf:32  nf_hook_slow       <-- LOCAL_OUT again
dev pp-ve:34   nf_hook_slow       <-- POST_ROUTING, real device
dev pp-ve:34   ip_finish_output > ... > veth_xmit[veth]

Sockets and the VRF

A VRF only steers packets that are associated with it, and for locally generated traffic that association comes from the socket. ip vrf exec pp-vrf curl ... is the usual way, and it works by putting the process in a cgroup whose BPF program sets SO_BINDTODEVICE to the VRF on every socket it creates. A server is the harder half: a socket bound to the wildcard address in the default VRF does not accept connections arriving through one unless net.ipv4.tcp_l3mdev_accept is 1 (net/ipv4/sysctl_net_ipv4.c:895), with udp_l3mdev_accept (line 1198) as its datagram counterpart. Leaving those at zero and binding one listener per VRF is the stricter arrangement; turning them on gives you one listener serving every VRF, with the input device as the only way to tell clients apart.

Try it

Host lab, run as root. Prerequisites: iproute2, curl, pwru. The bonding and vrf modules autoload when the devices are created.

sudo lab/11-bond-vrf.sh up        # pp-bond0 10.11.0.1 and pp-vrf table 10 with pp-ve 10.12.0.1

# the bond: two __dev_queue_xmit for one packet, and the device swap on receive
sudo pwru --kmods bonding,veth,bridge --output-meta 'tcp and host 10.11.0.2' &
curl -s --max-time 2 -o /dev/null http://10.11.0.2:9099/
cat /proc/net/bonding/pp-bond0 | grep -E 'Currently Active|Bonding Mode'

# the VRF: count PRE_ROUTING calls with and without an iif match
ip rule show | grep l3mdev
ip route show table 10
sudo pwru --kmods vrf,veth --output-meta 'tcp and host 10.12.0.2' &
sudo ip vrf exec pp-vrf curl -s --max-time 2 -o /dev/null http://10.12.0.2:9099/

sudo lab/11-bond-vrf.sh down

Every transcript quoted in this chapter is real bench output from exactly these steps. Expect two __dev_queue_xmit lines with different devices for the bond, and four nf_hook_slow lines on VRF output against two on a plain device.

Recap

A bond's receive handler sets skb->dev to the bond and returns RX_HANDLER_ANOTHER, so the core restarts its station list and ip_rcv sees the bond rather than the slave; recv_probe takes LACP and ARP-monitor frames out first. On transmit, a mode function picks a slave and bond_dev_queue_xmit calls dev_queue_xmit a second time, which is why the slave holds the queueing discipline that matters. A VRF does the same at L3 through l3mdev_ip_rcv, called from ip_rcv_finish before the routing decision: vrf_ip_rcv relabels the skb, marks it IPSKB_L3SLAVE and calls PRE_ROUTING a second time with the VRF device, and the output path calls LOCAL_OUT and POST_ROUTING twice each. Table selection is the l3mdev routing rule, and even the local address entry lives in the VRF table. Locally generated traffic joins a VRF through the socket, with tcp_l3mdev_accept deciding whether one listener can serve several.

recv_probe

The slave-selection hash and the choice of which header fields feed it, from MAC-only to addresses and ports.

Check yourself

1. You attach a token bucket shaper to bond0 and it has no effect on throughput. Explain why, and say where the shaper has to go.

Answer

The bond device's queueing discipline is bypassed because the packet is re-queued on the slave, and the slave's qdisc is the one that runs. bond_dev_queue_xmit (drivers/net/bonding/bond_main.c:297) sets skb->dev to the chosen slave and calls dev_queue_xmit a second time, which the bench trace shows as two __dev_queue_xmit lines with different devices for one skb. Attach the shaper to each slave, or give the bond an explicit qdisc and accept that the slave still has its own.

The near miss is "the bond is a virtual device so it has no qdisc at all". It has one, the default; the problem is that the second pass gets the last word.

2. Predict the count: you add nft add rule inet f prerouting counter on a host with one VRF, and send one packet in through a VRF-enslaved interface. What does the counter read, and what would make it read one?

Answer

Two, and an interface match makes it one. PRE_ROUTING runs once from ip_rcv with the enslaved device, then ip_rcv_finish calls l3mdev_ip_rcv (net/ipv4/ip_input.c:486), vrf_ip_rcv sets skb->dev to the VRF device (drivers/net/vrf.c:1340) and vrf_rcv_nfhook (line 1132) calls the same hook again. The bench capture shows two nf_hook_slow lines with different devices. Adding iif "pp-ve" or iif "pp-vrf" selects one pass.

The near miss is "two, because the packet was forwarded". No forwarding happened; this is one packet delivered locally, counted twice on the same hook.

3. Both devices relabel skb->dev and both make the stack repeat work. Name the difference in where each one intervenes, and what that means for a packet socket attached to the underlying member.

Answer

The bond intervenes at L2 inside __netif_receive_skb_core and the VRF at L3 inside ip_rcv_finish. The bond's receive handler runs before the protocol demux and returns RX_HANDLER_ANOTHER, so the entire station list including taps and tc ingress repeats with the bond device. The VRF hook runs after ip_rcv and after PRE_ROUTING, so the L2 stations run only once, on the enslaved device. A packet socket on the slave therefore sees bonded traffic normally, and a packet socket on a VRF-enslaved device sees everything because the VRF never took the frame away from it.

The near miss is "both are receive handlers". Only the bond registers one; the VRF uses the l3mdev hook, which is why their costs land on different layers.
