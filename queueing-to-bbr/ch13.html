Chapter 13 · before you read

Maglev (side path)

~6 min before · pp. 1–13 (~1 h, selected) · ~22 min after · LB
The paper's seven-slot table (Table 1, p. 6): three backends fill it in turns, then backend B1 is removed and we count which slots change hands.

The question this chapter answers

This is a side path. The main chain follows one upload through queues and senders; here we follow it one step further, to the service address it was sent to. Somebody has to choose which backend receives it. The upload is 100 MB at about 9.5 Mbit/s of goodput (the bench rate from the congestion-avoidance chapter), so for about 84 seconds each of its roughly 69,000 data packets must reach that same backend. A backend that never saw the connection's start answers with a reset.

Google had the same problem at a larger scale (pp. 1–2). A hardware load balancer is one box plus a spare. Maglev replaces it with ordinary servers: the router spreads packets over many Maglev machines, and each one picks a backend. Now the choice is made in many places at once. When the set of Maglevs changes, a connection's packets arrive at a machine that has never seen it. When a backend dies, the others must take its connections without disturbing everyone else's.

So the question is: how can many machines that share no state send every packet of a connection to the same backend, keep the backends evenly loaded, and move as few connections as possible when a backend comes or goes? The paper's answer is a table of \(M\) slots per service, filled by a rule that every machine computes the same way. The spine is the smallest such table, the paper's own: seven slots and three backends. You fill it, take one backend away, and count what moved. You asked for this paper because Cilium's kube-proxy replacement ships the same algorithm; the system card reads it in your fork.

Words you will meet

5-tuple
Source IP, source port, destination IP, destination port and protocol number: the five header fields that name one connection (p. 4, footnote 1).
VIP (virtual IP address)
An address that names a service rather than a machine. No single interface owns it; load balancers announce it to the router and many backends serve it (p. 2).
ECMP (equal-cost multipath)
A router with several equally good next hops for one address hashes each packet's 5-tuple to pick one, so a connection stays on one next hop while the set does not change (p. 2).
GRE (generic routing encapsulation)
Wrapping a packet in an outer IP header addressed to the chosen backend. The backend unwraps it and sees the original packet, still addressed to the VIP (p. 2).
DSR (direct server return)
The backend sends its reply from the VIP straight to the router, so replies skip the load balancer (p. 3).
connection tracking table
A fixed-size hash table on each Maglev, one per packet thread, that remembers which backend was chosen for each 5-tuple (pp. 4–5).
consistent hashing
A rule that maps keys to backends so that each backend gets almost the same share (load balancing) and few keys change backend when the set of backends changes (p. 5).
Maglev lookup table
The paper's consistent hash: an array of \(M\) slots per VIP, each naming a backend. A packet's 5-tuple hash modulo \(M\) picks its slot. \(M\) is prime (p. 6).
offset and skip (preference list)
Two numbers hashed from a backend's name. The backend's preference list is the slots \(\text{offset},\ \text{offset} + \text{skip},\ \text{offset} + 2\,\text{skip}, \dots\), each taken modulo \(M\) (p. 6).
disruption (minimal disruption)
The share of table slots that change backend when the set of backends changes. The slots that matter are those of backends that did not leave (pp. 5, 11).
overprovision factor
The busiest backend's load divided by the average load. A pool has to be sized for its busiest backend (p. 9).

Chapter 13 · after you read

The questions you carried in

1. Every Maglev already remembers each connection's backend in its connection tracking table. Why does it also need a consistent hash, and in which situations does the hash decide? pp. 4–5

Answer

Because tracking is local and finite (p. 5). It helps only packets that reach the Maglev holding the entry, and only while the table has room. The hash decides for new connections, for connections that ECMP moves to a Maglev with no entry (a rolling restart changes the set for over an hour), and when the table is full. Every Maglev computes the same table, so the recomputed answer equals the first. Near miss: sharing tracking state between Maglevs, which the paper rejects as too slow (p. 5).

2. How do two numbers per backend become a preference list over the whole table, and why must the table size be prime? p. 6

Answer

A backend hashes its name twice, \(\text{offset} = h_1 \bmod M\) and \(\text{skip} = h_2 \bmod (M-1) + 1\), and its \(j\)-th preference is \((\text{offset} + j \cdot \text{skip}) \bmod M\) (p. 6). Stepping by skip reaches every slot only if skip and \(M\) share no factor. Skip can be anything from 1 to \(M-1\), so \(M\) must be prime. With \(M = 8\) and skip 2 the list is 0, 2, 4, 6, 0, … Near miss: "prime for better hashing". It is there so that every list covers every slot.

3. When backend B1 leaves Table 1, which slots change hands, and what does the paper trade away to keep the backends' shares equal? pp. 6–7, 11

Answer

Slots 0 and 2, B1's, go to B0, and slot 6 moves from B0 to B2 although B0 stayed (p. 7). That extra move buys balance: the survivors take turns again from scratch, so shares stay within one slot. Karger's and rendezvous hashing never move a survivor's slot but need 29.7% and 49.5% overprovisioning at the paper's test size. Maglev moves about 2.3% of the table when 1% of 1,000 backends fail (Fig. 12, p. 11), harmless unless a connection also lost its tracking entry (p. 6).

The chapter on one screen

Google's network load balancer is software on ordinary servers (pp. 1–2). The router spreads a VIP's packets over every Maglev with ECMP; each Maglev picks a backend and sends the packet there in GRE, and the backend replies by DSR (Fig. 2, pp. 2–3). Capacity is machines times what one forwards, so §3.2 is about speed: kernel bypass, batching, about 350 ns per packet (pp. 4–5).

Backend selection has two parts (p. 5). A per-thread connection tracking table remembers each 5-tuple's backend, and a miss consults consistent hashing and records the answer (Fig. 4, p. 4). Tracking fails when the ECMP set changes or the table fills, so the hash must give the same answer on every Maglev.

The hash is Maglev hashing (§3.4, pp. 5–7). Each backend's preference list comes from two hashes of its name, and \(M\) is prime so that every list covers every slot. Backends take turns claiming their next free preference, so shares differ by at most one slot, and \(M > 100N\) keeps that under 1% (p. 6). Table 1 shows seven slots before and after B1 leaves: one survivor's slot moves.

That is the trade: balance first, minimal disruption second (p. 6). With 1,000 backends in 65537 slots, Karger's and rendezvous hashing need 29.7% and 49.5% overprovisioning where Maglev is almost exact. When 1% of the backends fail, about 2.3% of a 65537-slot table moves, and under 0.6% of a 655373-slot one. Google keeps 65537: concurrent failures are rare, tracking comes first, and the bigger table takes 22.9 ms to build against 1.8 ms (p. 11).

One VIP, many Maglevs

Maglev scales by adding machines behind one VIP. Every Maglev announces the VIP at the same cost, the router's ECMP hash spreads connections over them, and the capacity is \(N \times T\), machines times the throughput of one (p. 2). This works only if every packet of a connection reaches the same backend whichever Maglev it lands on. The paper calls that connection persistence.

Put the spine behind a VIP (Diagram 13.1). Three Maglevs each hold B1, B0, B1, B0, B2, B2, B0, so a 5-tuple whose hash is 6 modulo 7 reaches B0 from any of them. GRE keeps the VIP as the inner destination, and B0 replies by DSR, so the reply never meets a Maglev (pp. 2–3).

The capstone's upload is one 5-tuple: about 69,000 data packets of 1448 bytes over 84 s. DSR exists because replies are "typically larger in size" (p. 3); for an upload the large direction is inbound, so every data packet crosses the load balancer and only the acks skip it. Its 825 packets per second are 0.1% of what one Maglev forwards at 10 Gbit/s (p. 4). The worst delay the forwarder adds, a full pool of 3,000 packets drained at 10 Mpps, is \(3000 / 10^7\ \text{s} = 300\ \mu\text{s}\) (p. 5). That is Little's law: time inside = number inside / rate.

Where it matters: Maglevs once ran as active-passive pairs, half of them idle (p. 7). ECMP fixed that and brought the next learning's problem: it keeps a connection on one Maglev only while the set of Maglevs stays the same.

Tracking first, the table second

A Maglev reuses the backend in its connection tracking table when it has an entry and that backend is healthy. Only on a miss does it look the 5-tuple up in the Maglev table, and then it records the result (p. 4). So the table decides exactly where tracking cannot: new connections, connections that arrive at a Maglev with no entry for them, and a full tracking table (p. 5).

A reset needs both failures at once: a lost tracking entry and a moved slot. That is why the paper can accept a few moved slots (p. 6).

The steering module follows the same logic (p. 4). It hashes the 5-tuple to pick a receive queue, instead of using round robin, so a connection's packets stay on one thread: no reordering between threads, and one backend choice with no race against a health update. Reordering matters for the main chain: reordered packets raise duplicate acks, and three make TCP retransmit and halve its congestion window, the loss signal of the congestion-avoidance chapter, with nothing lost. Flow queueing in fq_codel also keeps each flow in one queue, and so in order.

A preference list from two numbers

Each backend's preference list is a permutation of all \(M\) slots, made from two hashes of its name (p. 6):

\[ \begin{aligned} \text{offset} &= h_1(\text{name}) \bmod M, \qquad \text{skip} = h_2(\text{name}) \bmod (M-1) + 1, \\ \text{permutation}[i][j] &= (\text{offset} + j \cdot \text{skip}) \bmod M. \end{aligned} \]

The example gives B0 (3, 4), B1 (0, 2) and B2 (3, 1), with \(M = 7\) (pp. 6–7). Table 1 lists 3, 0, 4, 1, 5, 2, 6; then 0, 2, 4, 6, 1, 3, 5; then 3, 4, 5, 6, 0, 1, 2 (p. 6). Each holds all seven slots once, and two backends may share a first choice, as B0 and B2 share slot 3.

\(M\) must be prime "so that all values of skip are relatively prime to it" (p. 6). A walk that steps by skip returns to its start after \(M / \gcd(\text{skip}, M)\) steps. With \(M = 8\), skip 2 visits 0, 2, 4, 6 and skip 4 visits 0, 4; once those slots fill, Pseudocode 1's inner loop runs off the end of the list.

Derivation · the walk visits every slot exactly when gcd(skip, M) = 1

Two steps \(j \ne j'\) with \(0 \le j, j' < M\) land on the same slot when \((j - j') \cdot \text{skip} \equiv 0 \pmod M\). If \(\gcd(\text{skip}, M) = 1\), skip has an inverse modulo \(M\), so \(j \equiv j'\), which is impossible: the \(M\) steps hit \(M\) different slots. If \(g = \gcd(\text{skip}, M) > 1\), then \(j - j' = M/g\) works, so the walk repeats after \(M/g\) steps and reaches only \(M/g\) slots. For every skip in \(1 \dots M-1\) to have gcd 1, \(M\) must have no factor below itself: \(M\) is prime.

The paper does not name \(h_1\) and \(h_2\) (p. 6). Each backend stores two numbers, and its next preference is one addition. Cilium uses the two 64-bit halves of one seeded MurmurHash3-128 of the backend's address string (pkg/maglev/maglev.go:203–208).

The first printing's slip. The first USENIX PDF (3 March 2016, printed p. 528) names the backends B1–B3 and prints the columns 2, 4, 6, 1, 3, 5, 7 / 1, 5, 2, 6, 3, 7, 4 / 5, 6, 7, 1, 2, 3, 4. Those are the inverse lists, each slot's rank in the backend's list counted from 1, while the text defines \(\text{permutation}[i][j]\) as the \(j\)-th slot. Its Before and After columns were right. The update of 8 March 2016 and Google's copy print the lists themselves and count rows from 0, so the extra move becomes row 6.

Taking turns: shares within one slot

Pseudocode 1 runs in rounds (p. 6). In each round every backend, in a fixed order, claims the first slot in its list that is still empty. A round fills \(N\) slots, so each backend ends with \(\lfloor M/N \rfloor\) or \(\lceil M/N \rceil\), and the first \(M \bmod N\) backends get the extra one. With \(M > 100N\), that one slot is "at most a 1% difference in hash space assigned to backends" (p. 6).

Run it on the spine (Diagram 13.3, left). Round 1: B0 claims 3, B1 claims 0, B2 finds 3 taken and claims 4. Round 2: B0 finds 0 and 4 taken and claims 1, B1 claims 2, B2 claims 5. Round 3: B0 finds 5 and 2 taken and claims 6, and the table is full: B1, B0, B1, B0, B2, B2, B0 (p. 6). The shares are 3, 2, 2, and B0 gets the extra slot because it comes first. The build took 12 probes, and Jain's index of the shares is \(49/51 = 0.96\).

The paper's own test, 1,000 backends in 65537 slots, gives 65 or 66 slots each: a 1.5% difference, outside its own rule, which Fig. 11 still draws as level bars (p. 11).

Derivation · the average build costs about M ln M probes (p. 6)

Treat each preference as a random slot. When \(n\) slots are full, a probe finds an empty slot with probability \((M - n)/M\), so the expected number of probes for the next claim is \(M/(M-n)\). Summing over \(n = 0 \dots M-1\) gives \(M\,(1 + \tfrac12 + \dots + \tfrac1M) = M H_M \approx M(\ln M + 0.577)\), the paper's \(\sum_{n=1}^{M} M/n\). For \(M = 7\) that is 18.15 probes; Table 1 needed 12. For \(M = 65537\) it is about \(7.6 \times 10^5\). The worst case, \(O(M^2)\), needs every backend to share one list with \(N = M\); choosing \(M \gg N\) avoids it.

Weights change "the relative frequency of the backends' turns", which the paper does not describe (p. 6): the quantum idea from DRR, more turns for a heavier backend. Cilium skips a backend's turn while its counter runs ahead of its weight (maglev.go:315–336) and sorts the backends by address string first (:282–287). Order decides who gets the extra slot and what each claims, so nodes with different orders would build different tables. The paper never mentions order.

What moves when a backend leaves

A removal rebuilds the table from scratch. The leaver's slots must move, and a few slots also move between backends that stayed, because the survivors take turns again and reach their preferences in different rounds. The paper accepts these extra moves to keep the balance (pp. 6–7).

Remove B1 (Diagram 13.3, right). In rounds 1 and 2, B0 claims 3 and 0, and B2 claims 4 and 5. In round 3, B0 finds 4 taken and claims 1, and B2 claims 6, which B0 held before. In round 4, B0 finds 5 taken and claims 2. B1's slots 0 and 2 went to B0, as they must, and slot 6 moved between survivors: one extra move among five slots (p. 7). B2 reached slot 6 a round earlier because it no longer waits for B1.

A plain mod-N table (slot \(j\) to backend \(j \bmod N\)) moves two survivors' slots here. At 100 backends the Python lab moves 98% of a mod-N table against 1.3% of a 16381-slot Maglev table.

The docs' slip. Cilium's docs say \(M > 100N\) guarantees "at most 1% difference in the reassignments" on backend changes (Maglev section; in the fork, Documentation/network/kubernetes/kubeproxy-free.rst:499, 523–524, 565). The paper's 1% (p. 6) bounds the difference in hash space between backends: balance. At its default \(M = 16381\) with the docs' 160 backends (\(M/N = 102\)), Cilium's own code moves 1.54% of the table between surviving backends when one backend leaves (mean of 20 removals), and 1.31% at 100 backends. The 1% line is crossed near \(M/N = 300\). The package test that asserts under 1% (pkg/maglev/maglev_test.go:160–162) uses 3 backends in 1021 slots.

Where it matters: with tracking, a moved slot breaks only connections that also lost their entry (Diagram 13.2); without it, every moved slot is a live connection sent to the wrong backend.

Choosing M

A bigger \(M\) improves balance and cuts disruption, and it costs memory and build time for every VIP (pp. 6, 11). Google's default is 65537 (p. 11).

When 1% of 1,000 backends fail, 2.3% of a 65537-slot table moves against 0.57% of a 655373-slot one, and the build time grows from 1.8 ms to 22.9 ms (p. 11). At 100 backends, one removal moves 1.3% at \(M/N = 164\), 0.83% at 327 and 0.56% at 655 (Diagram 13.4). So balance within 1% needs \(M/N \ge 100\), and one removal under 1% needs \(M/N\) near 300.

Cilium stores 4 bytes per slot: 64 KiB per frontend at 16381 and 256 KiB at 65521 (bpf/lib/lb.h:317–332). Its builder also keeps every preference list while it fills, \(N \times M\) 8-byte entries and never fewer than \((M/100) \times M\) (maglev.go:157–162, 358–360): 21 MB of agent memory at 16381 and 343 MB at 65521. The lab's builds took about 1.3 ms for 160 backends at 16381 and 32 ms for 1,000 backends at 65521, on a shared laptop.

Since the paper. Linux added a Maglev scheduler to IPVS in v4.18 (2018, commit 039f32e8cdea), net/netfilter/ipvs/ip_vs_mh.c. It uses the same ten primes (:49–50) and defaults to 4093 slots; your kernel has CONFIG_IP_VS_MH=m with the default index 12. Offset and skip come from two fixed hsiphash keys (:72, 142–147), and it hashes only the source address, plus the source port when a flag is set (:479–484).

Real systems

Meet the system · Cilium's Maglev, in kube-proxy replacement

What it is. Cilium's kube-proxy replacement balances Kubernetes services in BPF instead of iptables. With bpf-lb-algorithm=maglev, the agent builds one Maglev table per service frontend and the datapath hashes each new connection into it.

Why it exists. A NodePort or LoadBalancer packet can arrive at any node, and nodes share no connection tracking. The default, random, picks differently on each node; Maglev makes them agree without talking (Cilium docs). It arrived in Cilium 1.9, in 2020.

The parts you need.

  • The builder, pkg/maglev/maglev.go: offset and skip from a seeded MurmurHash3-128 of a string such as [10.244.1.5:8080/TCP,State:active] (:203–208, 229–253), sorted by that string (:282–287), filled by Pseudocode 1 (:315–336).
  • The map cilium_lb4_maglev: per service ID, an array of \(M\) backend IDs (bpf/lib/lb.h:317–332), replaced whole on every update (pkg/loadbalancer/maps/lbmaps.go:625–646).
  • The lookup lb4_select_backend_id_maglev: a seeded jhash of source address, ports and protocol, modulo \(M\) (lb.h:1847–1874, bpf/lib/hash.h:12–17).

Where this chapter lives inside it. One VIP, many Maglevs: each node is a Maglev, a NodePort or LoadBalancer frontend is the VIP, and ECMP is whatever routes clients to the nodes. Maglev covers only traffic that enters a node from outside: a pod connecting to a service is balanced at connect() by the socket load balancer, which picks a random slot (bpf/bpf_sock.c:124–128, 408). So the capstone's upload meets Maglev only if it enters the cluster at a node. Tracking first: in lb4_local, CT_NEW picks from the table and records it (lb.h:2133–2155); an existing entry is reused, a backend that is no longer active keeps its connections' non-SYN packets, and a deleted one gets a fresh pick (:2167–2199). Preference lists and taking turns: getOffsetAndSkip and computeLookupTable, in sorted order so that every node agrees. What moves: each backend change recomputes the table from the active backends (bpf_reconciler.go:1053–1058, 1348–1363). Your fork goes further than the paper. Its VPC public entry keeps no per-flow state and relies on Maglev alone to reach the same backend from whichever node holds the address (bpf/lib/vpc_dsr.h:30–33, 498–503), and drops ICMP errors for frontends without Maglev (:353–354): §3.3's argument with the tracking layer removed.

Hint 1 · direction

populate() is Pseudocode 1 with three pieces of state: a pointer per backend, the table, and a count of filled slots. Compute each preference when you need it; an \(N \times M\) array at 1,000 backends and 65537 slots would hold 65 million numbers.

Hint 2 · mechanism

Inside while True, loop for i, (off, sk) in enumerate(os_). Probe c = (off + nxt[i] * sk) % M; while entry[c] >= 0, advance nxt[i] and probe again. Return as soon as the count reaches \(M\), even in the middle of a round.

Hint 3 · nearly there

extra_moved() walks both tables slot by slot and skips slots whose old owner left: sum(1 for b, a in zip(before, after) if b != a and b not in dead), as a percent of len(before).

Solution 
def populate(os_, M):
    N = len(os_); nxt = [0] * N; entry = [-1] * M; n = 0
    while True:
        for i, (off, sk) in enumerate(os_):
            c = (off + nxt[i] * sk) % M
            while entry[c] >= 0:              # taken: try the next preference
                nxt[i] += 1
                c = (off + nxt[i] * sk) % M
            entry[c] = i; nxt[i] += 1; n += 1
            if n == M:
                return entry

def extra_moved(before, after, dead):
    moved = sum(1 for b, a in zip(before, after) if b != a and b not in dead)
    return 100 * moved / len(before)

Check yourself

Answer out loud first, then open.

1. Predict the value: with Cilium's default 16381 slots, how many slots does each backend get with 160 backends, and with 200? Which breaks the paper's 1% rule?

Answer

With 160, 102 or 103 (\(16381 = 160 \times 102 + 61\)), a \(1/102 = 0.98\%\) difference. With 200, 81 or 82 (\(16381 = 200 \times 81 + 181\)), a \(1/81 = 1.2\%\) difference: that breaks \(M > 100N\) (p. 6), which allows at most 163 backends here. Near miss: reading 1.2% as the share of connections that move when a backend leaves. That is disruption, already 1.5% at 160 backends (the lab's Go run).

2. Here is a symptom: during an hour-long rolling restart of the Maglevs, one backend fails. Hundreds of long connections to other, healthy backends are reset; none were in the hour before. Why?

Answer

Two changes overlapped. The restart moved connections to Maglevs with no tracking entry, so those Maglevs used the table (p. 5). The failure rebuilt the table, which moved a few percent of the survivors' slots too, like row 6 in Table 1 (p. 7). A connection that changed Maglev and sat on a moved slot reached a backend that never saw it: "resets are proportional to the number of lookup table disruptions" (p. 6). Near miss: blaming the failed backend; these connections were on healthy ones.

3. Here is a symptom: with bpf-lb-algorithm=maglev, cilium-dbg bpf lb maglev list shows tables for a service's NodePort frontends, none for its ClusterIP, and pod-to-service connections still spread at random. Is Maglev broken?

Answer

No. Pod-to-service traffic never reaches the table: the socket load balancer picks a random slot at connect() (bpf/bpf_sock.c:124–128, 408), and the docs exclude east-west traffic from Maglev. A ClusterIP frontend gets a table only with bpf-lb-external-clusterip (bpf_reconciler.go:1179–1184). The paper's problem is traffic from outside, where many machines must agree (p. 2). Near miss: a missing hash seed; it changes which backend wins a slot, never whether a table exists.

4. Here is a symptom, predicted from your fork's code: in the VPC public load balancer path, scaling a service from 160 to 159 backends would reset about 1.5% of the connections to backends that stayed. A plain NodePort service would reset none. Why?

Answer

The public entry keeps no tracking. vpc_dsr.h holds no per-flow state at the entry and runs the Maglev lookup on every packet (:30–33, 498–503), so every moved slot sends live connections elsewhere, and a rebuild at 160 backends in 16381 slots moves 1.54% of the table between survivors. A plain NodePort finds its service conntrack entry first and keeps the old backend (lb.h:2104, 2167–2199), the paper's two-part strategy (p. 5). Remedies: a larger \(M\), or state at the entry.

5. Choose and defend: 300 backends behind ECMP and a rolling update every day. Keep \(M = 16381\), or raise it to 65521?

Answer

Raise it. At 16381, \(M/N = 55\): 54 or 55 slots, a 1.9% imbalance outside the paper's rule (p. 6), and about 2.5% of the table moving per removed backend (Diagram 13.4). At 65521, \(M/N = 218\): a 0.5% imbalance and about 1.1% moving. The cost: 256 KiB per frontend instead of 64 KiB, at least 343 MB of builder scratch, and a restart of every agent to change it, which briefly mixes tables across nodes (docs). With tracking in front and rare updates, the default is defensible.

Recap

Maglev spreads a VIP over many machines with ECMP and keeps each connection on one backend in two steps: a local connection tracking table, and, where tracking cannot help, a Maglev table every machine builds the same way. Each backend's preference list is offset plus multiples of skip modulo a prime \(M\); backends take turns claiming free slots, so shares differ by at most one slot and \(M > 100N\) keeps that within 1%. A removal moves the leaver's slots and a few others, about 1.5% at Cilium's defaults, which matters only where tracking is lost too. Cilium runs the same algorithm, conntrack first, for traffic entering a node.
