## Spine and strands
Spine: "One 185,000-byte packet against a 120 ns budget" — Dumazet's `gso_max_size 185000` against the 123 ns of a 1,538-byte frame at 100 Gbit/s; on the bench one 184,298-byte IPv6 skb.
**120 ns check (brief asked):** the sources do not use a bare 1,500-byte packet. LWN §2 and Isovalent §1 both use 1,538 bytes, the wire frame of a 1,500-byte MTU (+14 header, +4 FCS, +8 preamble, +12 gap): 1,538 × 8 / 10^11 = 123.04 ns, 8.13 Mpps, which LWN rounds to "about 120ns" (Brouer 2015 in LWN 629155 says "about 120ns … 8.15 million"). A bare 1,500-byte packet is exactly 120.0 ns. The hub line stays right as "about 120 ns"; the page says 123 ns and quotes LWN's rounding.

## Measured on the bench
Rootless, kernel 7.2.6-arch2-1, 2026-10-02, own two-namespace veth pair (`labs/ch14-big-tcp/bigpair.sh`, offloads on). Data and README in `labs/ch14-big-tcp/data/`. Shared machine (11–21% busy; pinned CPUs 0.14–0.28 CPU-s/s busy at idle).
- All four knobs settable rootless up to 524,280; 524,281 → "Error: too big gso_max_size." (exit 2); dummy refuses 185,000; gso_max_size 32000 drags gso_ipv4_max_size to 32000.
- Frame sizes at the receiver: 64,346 / 65,226 B at 65,536; 184,298 / 183,962 B at 185,000 (IPv6 / IPv4), exactly as predicted from (knob − 321) // MSS. 99.8% of skbs had IP length field 0; no HBH.
- tcpdump 4.99.6: IPv4 `length 183948 [was 0, presumed TSO]`; IPv6 `payload length 0) … [|tcp]`.
- Bulk flow, 5 reps × 8 s: IPv6 55.8 → 69.1 Gbit/s, 0.2175 → 0.1552 CPU-s/GB; IPv4 54.6 → 69.2, 0.2212 → 0.1558. Fit: ~6.2 µs per skb + 0.12 ns per byte.
- MSG_ZEROCOPY at 185,000: max 69,698 / 69,718 B = 17 × 4096 + headers.
- GRO path (sender TSO off, receiver NAPI GRO): 184,298 / 183,962 B at ~23 Gbit/s; behind 10 Mbit/s tbf: median 1,514 B, 4,858 of 5,000 single frames.
- Open connection keeps 65,226 B after the knob is raised; the next connection gets 183,962 B.
- ss: segs_out/segs_in ≈ 43 (65,536) and ≈ 119 (185,000): about one ack per skb.

## Errata and since-the-paper notes
- Erratum shipped (Isovalent §1): "assuming a MTU of 1,538 bytes" — the MTU is 1,500; 1,538 is the frame on the wire.
- Erratum shipped (Isovalent §5.2): "between 5,000 and 6,000 packets per seconds" / "between 10,000 and 11,000" / "a whopping 50%" — netperf TCP_RR counts transactions per second, and the post's own output reads 7,102.21 and 10,304.92 (+45%).
- Not shipped: Isovalent §5.1 "42% increase in transactions" while its own IPv6 transcript gives 8,663.99 / 6,587.63 = +31.5% (the 42% may come from the KubeCon chart); LWN §7 ties jumbo packets to the MTU (stated in the page as a clarification, not as an erratum); Isovalent §1 "Transmit Segmentation Offload" (TSO is TCP segmentation offload).
- Since: v7.0 dropped HBH (1fdad81d8803, Feb 2026, by Alice Mikityanska of Isovalent, part 1 of BIG TCP for UDP tunnels); replaced by payload_len 0 + `ipv6_payload_len()` reading skb->len, as IPv4's `iph_totlen()` does since v6.3. Real on-wire jumbogram parsing stays (exthdrs.c:993). Cilium 1.20.2 docs still describe the temporary HBH.
- Since: MAX_SKB_FRAGS 45 dropped in v2 of the 2022 series; `CONFIG_MAX_SKB_FRAGS` (17–45, default 17) in v6.4 (3948b05950fd); Arch builds 17.
- Since: Cilium fork probes BIG TCP for UDP tunnels via Geneve's tso_max_size (c9c5d4f9da, Jan 2026; "pending kernel commit … geneve: Enable BIG TCP packets", not in v7.2: Geneve shows 65,536, measured rootless). Cilium docs add `ice` to the NIC list.

## Requests to the coordinator
- **Capstone line needs a boundary.** "GRO hands the far end 185 KB skbs (BIG TCP)" is true only when the far end receives at multi-gigabit rate. On the capstone's 10 Mbit/s, 40 ms path, measured here: GRO handed up single 1,514-byte frames (median), because each NAPI poll finds one packet; and TCP autosizing at 10 Mbit/s builds 2-segment skbs. Suggested capstone wording: "On the pod's own node, BIG TCP lets GRO hand the far end 184 KB skbs; across the 10 Mbit/s bottleneck GRO gets one frame per poll, so BIG TCP changes nothing for this upload."
