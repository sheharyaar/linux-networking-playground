## Measured on the bench
Rootless qnet, kernel 7.2.6-arch2-1, 2026-10-02; data in `labs/ch06-pacing/data/` (README there). Bench: `netem rate 10mbit limit 21` (no delay) on rtr:r1, `netem delay 20ms` on rtr:r0 and rcv:c0 (ack path), s0 = pfifo 10000 or fq, `initcwnd 1`, MSS 536 (576-byte packets, 590-byte frames, pipe 84.7 packets, buffer = pipe/4), Reno, 8 flows started by a barrier.
Scaling: the paper's 50-flow case has BDP 1250, buffer 312 = BDP/4, ≈ 25 packets per flow. The bench keeps buffer = pipe/4 and the paper's packet size (which raises the 10 Mbit/s, 40 ms pipe from 33 to 85 packets) and uses 8 flows (≈ 10.6 packets each, enough for fast retransmit). Linux's IW10 is never paced (tcp_output.c:1458), so 8 × 10 packets at once would overflow a 21-packet buffer before either sender acts; the route's initcwnd 1 matches the paper's start (PDF p. 2).
- Eight flows, buffer 21, 5 runs each (means): first epoch 6/8 unpaced (every run), 8/8 fq, 8/8 TCP timer, 8/8 fq at 100/100; first loss at 0.183 s unpaced, 0.244 s fq and timer, 0.287 s at 100/100 (identical across runs to ±10 ms); peak sum of windows 157 / 188 / 188 / 279 (pipe + buffer 106); RTOs 0 in all SACK runs; goodput first 2 s 7.66 / 7.77 / 7.86 / 7.71 Mbit/s; whole 15 s 8.24 / 8.41 / 8.38 / 8.21 (payload ceiling 8.88); after 3 s: summed window mean 94.8 / 97.1 / 96.4 / 96.0, swing 0.164 / 0.132 / 0.141 / 0.138; epochs with ≥ half the flows 60% / 73% / 72% / 83%; retransmissions 538 / 548 / 522 / 639; Jain whole run 0.98–0.99, 1 s windows 0.90–0.92 for all.
- SACK off: unpaced 6/8, 4.8 RTOs per run (1–9), 6.76 Mbit/s first 2 s; fq 8/8, 0 RTOs, 7.19.
- Buffer 85 (one pipe): both 8/8; peaks 335 unpaced, 344 fq (2 × 170 = 340); 8.80 Mbit/s both; epochs ≥ half 64% / 85%.
- One flow, 3 runs each: unpaced first drop in the 32→64 round, 34 drops in slow start, ssthresh 51; fq: queue 0–3 packets until the 64→128 round, 74 drops (71 in one run), ssthresh 86; both peak at 106 in steady state; goodput 7.50 / 7.40 over 10 s.
- fq counters after an eight-flow 15 s run: fastpath 11102, throttled 7713, latency 11.4 us (31,909 packets ≈ 16,000 two-segment skbs).
- ss trap: eight unpaced pfifo flows each print pacing_rate (0.93–2.72 Mbit/s); first line cwnd 11, ssthresh 7, send 1.010 Mbit/s, pacing_rate 1.212 Mbit/s = 120%.
- Wrong turn: `netem delay 20ms rate 10mbit limit 21` on r1, one fq flow: 2.49 Mbit/s, 40 drops.
- Mixed, 300-packet flows (Fig. 14 size), pfifo, TCP's timer paces the K flows with SO_MAX_PACING_RATE, 24 runs per point: first-epoch loss paced 99–100% against unpaced 66–71% (K = 1, 2, 4); completion paced 1.32 / 1.34 / 1.28 s against unpaced 1.21 / 1.18 / 1.17 s, ratio unpaced/paced 0.92 / 0.88 / 0.91 (Fig. 15: 0.65–0.76); loss events per flow about equal (≈ 2); retransmits per flow paced 5.5–6.4 against 17–19. At K = 7 the lone unpaced flow is the slow one (1.39 s, ratio 1.10). At 100/100 ratios, K = 4: ratio 0.92.
- Mixed, 15 s bulk flows, 4 runs per point: paced flows get more at every mix (K = 4: 1.18 against 0.94 Mbit/s; fair share 1.11), with fewer loss events (31 against 38) and fewer retransmits (56 against 78). The paper's short-flow penalty does not carry into steady state on this bench.
- ss slash: a socket with SO_MAX_PACING_RATE prints `pacing_rate X/1000000000bps` (ss-pacing-rate-paced2.txt); an unpaced one prints the bare rate. The slash shows the cap was set, which is the only `ss` hint that TCP's own timer is in use on a non-fq qdisc.
- Slow-start drops over the first 1.3 s with 8 flows were 132 unpaced against 109 fq (more, smaller overflows unpaced); not used in the page, where the single-flow 34 against 74 is the clean comparison.

## Errata and since-the-paper notes
- Erratum shipped (verified on the rendered PDF p. 5 at 300 dpi and Fig. 4 at 300 dpi; Mathis p. 68–69 rendered): footnote 1's T_cycle = RTT²·BW/packet_size gives 10.85 s = 108.5 RTT for Fig. 4's flow; Fig. 4 repeats every 75 RTT; the formula is Mathis's Eq. 4 bound with C = 1 (delayed acks) turned into a period (1/p packets per cycle at BW/MSS); with every-packet acks (the paper's setting, p4) Mathis's derivation gives (2/3)·RTT²·BW/MSS = 72.3 RTT. A queue-aware sawtooth (P² + PB + B²)/(2P) = 69.6 RTT + ~1 RTT of recovery agrees. Consequence stated in the page only for the quarter-BDP case (≈ 1.5 sawtooths per Fig. 5 flow).
- Since the paper: Linux Reno has SACK + PRR (RFC 6937, tcp_input.c:2962–2985) + RACK (RFC 8985, default at tcp_ipv4.c:3475), which turn a synchronized loss into one halving per flow; BLUE → sch_sfb (header cites the same CSE-TR-387-99); Linux pacing ratios 200/120 (tcp_input.c:1154–1159; history left to ch05).
- Documentation note (not shipped): ip-sysctl.rst says the ss ratio applies "in slow start", while the code switches at cwnd < ssthresh/2 (already noted in ch05's word list).
