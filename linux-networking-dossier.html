Chapter 0 — prologue

Two programs, one wire

~9 min · WIRE · Our packet has not been born yet. A program is about to ask the kernel to send some bytes. Before we can follow them anywhere, we have to agree on what "some bytes" means.

The machine you are sitting at

A real laptop, listing the places it can send and receive:

$ ip -br addr
lo               UNKNOWN        127.0.0.1/8 ::1/128
enp0s31f6        DOWN
wlp0s20f3        UP             192.168.1.110/24 fe80::1959:18d2:356b:16e/64
docker0          DOWN           172.17.0.1/16
br-817f796b1e66  DOWN           172.18.0.1/16

Five lines. Four different address ranges. One piece of hardware with a radio in it.

Each line is an interface: a named place where the kernel takes bytes to send and hands you bytes that arrived. Some interfaces sit on top of a network interface card, or NIC, which is hardware that turns bytes into signals. Most of the interfaces on this laptop have no hardware under them. The kernel invented them. They behave like NICs, because behaving like a NIC is all an interface has to do.

A link is what sits on the other side of an interface: the medium it can reach directly, with nobody forwarding on its behalf. For the wifi card, the link is the air between the laptop and the access point. The frame chapter is about what travels across a link. The routing chapter is about what happens when the thing you want is somewhere else.

Now the tension. Start a container on this laptop and it gets the address 172.17.0.2. Run curl inside it and a web server on the other side of the world answers. But nobody on the internet knows how to reach 172.17.0.2. That range is reserved for private use, and routers throw it away on sight. Something between the container and the wifi card is replacing that address on the way out. This document is an account of what does the replacing, where it happens, and why it is needed.

What is on the wire

Bytes. That is the answer, and people skip past it too fast. Most confusion about networking comes from imagining that something richer is travelling.

The bytes are arranged as a header followed by a payload. The header is a fixed set of agreed fields that the machinery reads: who this is for, who sent it, how long it is, what kind of thing follows. The payload is everything after the header. To the machinery reading that header, the payload is cargo it never opens.

The trick that makes networking work is that the cargo is usually another header and payload. This is encapsulation. One layer's complete message becomes the next layer's payload. Envelopes inside envelopes, and each machine along the way opens only as many as its job needs.

The envelopes have names. The outermost one, the one a NIC transmits, is a frame. Inside it sits a packet, which crosses many links and keeps its addresses the whole way. Inside that sits whatever the two programs are saying to each other. When that piece belongs to a reliable conversation, it is a segment.

The three get numbers. The frame is layer 2, written L2, and its job is one hop across one link. The packet is layer 3 or L3, and its job is to get from one end to the other across many links. The segment is layer 4 or L4, and its job is to make a stream of separate packets look like a conversation. The numbering comes from a model nobody implements faithfully. You will meet things that sit between two layers, and things that sit in none of them. Treat the numbers as a way of filing ideas.

That diagram is also a sum you can check. 56 bytes of data, plus an 8-byte message header, plus a 20-byte packet header, plus a 14-byte frame header, gives 98. Hold on to it. Several times in this document, a number you can work out in advance turns up as the number the kernel reports. Working it out first is the quickest way to tell whether you have understood a layer or only read about it.

What this document skips, and why

You can relax once you can see the fence, so here is the fence.

We skip physics, which means radio, cable, voltages and error correction. We skip how a reliable stream is made reliable: the retransmissions, the window, the congestion control. We skip everything above the conversation: TLS, HTTP semantics, and every DNS record type beyond the one lookup our packet needs. All of that is real. None of it changes the road our packet takes or the rules it passes.

What is left is the part that breaks. When a container cannot reach a service, the protocol is almost never at fault. The fault is in some piece of kernel plumbing, wired differently from the way you pictured it. That plumbing is what we are here for.

The itinerary

One packet, followed all the way. It starts as a few bytes a program wants to send. It picks up its L2 and L3 envelopes, crosses a software switch, passes five places where the kernel may interfere, has its addresses rewritten, gets wrapped in a second complete set of envelopes to cross between machines, and arrives at a container whose address was invented by a program that started ten seconds earlier.

Try it

Run ip -br addr on your own machine and name every line out loud: hardware or software, up or down, and who gave it that address. Then run ip -br link and look at the six-byte hardware addresses. At least one of them almost certainly starts with a byte whose second-lowest bit is set: 02, 0e, 5a, aa, fe. That bit carries a meaning, and the frame chapter says what it is.

Recap

An interface is a named place where the kernel takes and delivers bytes, and most interfaces on a modern Linux machine are software. A link is what an interface reaches without help from anyone. What travels is bytes, arranged as a header followed by a payload, and the payload is usually another header and payload. That nesting is encapsulation. The outermost envelope is a frame, and it crosses one link. Inside it a packet crosses many. Inside that a segment carries a conversation. The layer numbers are a way of filing ideas. A container on this laptop holds an address the internet cannot reach, and something on the way out is rewriting it.

Check yourself

1. Predict the value: you run ping -c 1 with its default settings and capture the result. The capture tool reports the frame as 98 bytes. Your data was 56 bytes. Account for every one of the other 42 bytes.

Answer

14 + 20 + 8 = 42. The frame header is 14 bytes, the packet header is 20 bytes, and the ICMP message header is 8 bytes. So 56 + 8 = 64 is the message, 64 + 20 = 84 is the packet, and 84 + 14 = 98 is the frame.

Check it against the envelope diagram (diagram 0.1), and against the real capture in the frame chapter, where ping prints 56(84) bytes of data and tells you the data size and the packet size in one line.

The near miss is answering 42 without splitting it, or putting the frame header at 18 bytes. Some frame formats do carry an extra 4-byte tag and a 4-byte checksum at the end, but the hardware generates and strips that checksum, so a capture taken inside the kernel never shows it.

2. The laptop above has docker0 at 172.17.0.1/16 and a wifi interface at 192.168.1.110/24. A container at 172.17.0.2 fetches a page from a public web server and it works. Using only the prologue, say what must be true of the bytes leaving the wifi card, and what that forces to be true of the bytes coming back.

Answer

The sender's address in the outgoing packet header can no longer be 172.17.0.2. The reply has to find its way back, and no router beyond this laptop carries that address. So something on the laptop put 192.168.1.110 there instead.

That forces a second requirement, and it is the interesting half. The reply arrives addressed to 192.168.1.110. The same something has to remember the substitution and undo it, or the reply lands in the laptop instead of the container. Rewriting one direction is easy. The bookkeeping that brings the answer home is the NAT chapter.

The near miss is "the container shares the laptop's address", which is close and hides the bookkeeping. The container has its own address and believes it used it. You will capture both views side by side in the NAT chapter.

Chapter 1

The frame, the hardware address, and the question ARP answers

~10 min · WIRE · The prologue left us with a nest of envelopes and a sum to check. Now we open the outermost envelope, the one the card transmits, and find out how a machine decides whose name to write on it.

Fourteen bytes

The frame header is three fields. Six bytes of destination, six bytes of source, two bytes saying what the payload is. Those are the 14 bytes the prologue asked you to account for.

The six-byte addresses are MAC addresses, from media access control. A MAC address identifies an interface on a link, and only on that link. It carries no meaning one hop further on. Written out, it is six bytes in hexadecimal: 5a:d6:1f:40:a6:ba, the real address of the wifi router on the laptop from the prologue.

Two bits of the first byte carry meaning. The lowest bit says whether the address means one interface or a group of them. The next bit up says whether a manufacturer assigned the address or whether it was made up locally. Look at the addresses that laptop is using right now:

gateway   5a:d6:1f:40:a6:ba     0x5a = 0101 1010  -> locally administered
docker0   5e:a7:86:94:02:48     0x5e = 0101 1110  -> locally administered
broadcast ff:ff:ff:ff:ff:ff     0xff = 1111 1111  -> group, and every group

Both real addresses have that second bit set, because no vendor burned either of them into a chip. docker0 is a software interface that Linux invented at boot and gave a random address to. The home router is doing the same thing for its own reasons. Once you can read that bit, a lot of virtual networking stops looking mysterious. Software interfaces generate their own addresses and set that bit, so they can never collide with a vendor's range.

An address meant for one interface is unicast. The all-ones address ff:ff:ff:ff:ff:ff is broadcast, and every interface on the link must accept it. Addresses with the group bit set but not all ones are multicast, meaning a subscribed subset. The set of interfaces that will see a broadcast is the broadcast domain. It is the most useful boundary in this document: inside one, machines reach each other by broadcasting; outside one, they need a router.

The last two header bytes are the EtherType, which names the payload so the receiver knows which piece of code to hand it to. You need two values. 0x0800 means an IP packet. 0x0806 means the protocol we are about to meet.

The 1500

The payload limit has a name. The MTU, or maximum transmission unit, is the largest payload an interface will carry in one frame. On ordinary Ethernet it is 1500 bytes. It is a per-interface setting rather than a protocol constant, and every interface on the laptop from the prologue reports mtu 1500. For now, file it as "the biggest thing that fits". In the overlay chapter it becomes the commonest cause of a network that passes every quick test and then hangs on real traffic.

The question L2 cannot answer

Here is the gap. A program wants to reach 10.10.0.2. That is an L3 address, the subject of the routing chapter. But the card can only transmit a frame, and a frame header has nowhere to put 10.10.0.2. It has room for a six-byte MAC address. The sender knows who it wants to reach, and lacks the one fact it needs to address the envelope.

The fix is to ask the link. ARP, the Address Resolution Protocol, is one question and one answer: whoever holds this L3 address, tell me your MAC address. The question goes to the broadcast address, because the asker has no idea which interface will answer. The answer comes back unicast, because by then the answerer knows exactly who asked. The question contained the asker's own addresses.

Below is that exchange, captured on a link between two machines with an empty neighbour table. Nothing has been simplified. These are four consecutive frames. The interface name looks odd because both "machines" are on one laptop; how that was done is the namespace chapter, and nothing in the capture depends on it.

$ tcpdump -e -n -i veth-b 'arp or icmp'

fe:17:29:ac:56:79 > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42:
    Request who-has 10.10.0.2 tell 10.10.0.1, length 28
52:a2:59:ff:54:91 > fe:17:29:ac:56:79, ethertype ARP (0x0806), length 42:
    Reply 10.10.0.2 is-at 52:a2:59:ff:54:91, length 28
fe:17:29:ac:56:79 > 52:a2:59:ff:54:91, ethertype IPv4 (0x0800), length 98:
    10.10.0.1 > 10.10.0.2: ICMP echo request, id 25, seq 1, length 64
52:a2:59:ff:54:91 > fe:17:29:ac:56:79, ethertype IPv4 (0x0800), length 98:
    10.10.0.2 > 10.10.0.1: ICMP echo reply, id 25, seq 1, length 64

Read it in order. Frame one goes to everyone and asks a question. Frame two comes back to one interface with the answer. Only in frame three does the ping the user asked for get sent, addressed to 52:a2:59:ff:54:91, a value that did not exist anywhere on the sending machine a millisecond earlier.

Two numbers confirm the prologue's sum. The ARP frames are length 42: 14 bytes of frame header plus a 28-byte ARP message, the size the protocol has specified since 1982 for four-byte L3 addresses and six-byte MAC addresses. The ping frames are length 98, the number we worked out. And the EtherTypes are the two values from the frame-header diagram (diagram 1.1), printed by name.

The neighbour table

The answer is cached, in the neighbour table. Linux shows it with ip neigh, and each entry carries a state:

$ ip neigh show                       # on the asking machine, after the exchange
10.10.0.2 dev veth-a lladdr 52:a2:59:ff:54:91 REACHABLE

$ ip neigh show                       # on the answering machine, same moment
10.10.0.1 dev veth-b lladdr fe:17:29:ac:56:79 DELAY

REACHABLE means the mapping was confirmed recently. DELAY and STALE mean it is old enough that the kernel wants to re-check it before trusting it again. The states exist because a MAC address can move. A machine can be replaced, an interface can fail over, and a cache that never expired would break silently and permanently.

The interesting state is the failure. Ask for an address nobody holds and you get this:

$ ping -c 1 -W 2 10.10.0.99
1 packets transmitted, 0 received, 100% packet loss

# on the wire:
fe:17:29:ac:56:79 > ff:ff:ff:ff:ff:ff, ARP, Request who-has 10.10.0.99 tell 10.10.0.1
fe:17:29:ac:56:79 > ff:ff:ff:ff:ff:ff, ARP, Request who-has 10.10.0.99 tell 10.10.0.1
fe:17:29:ac:56:79 > ff:ff:ff:ff:ff:ff, ARP, Request who-has 10.10.0.99 tell 10.10.0.1

$ ip neigh show
10.10.0.99 dev veth-a INCOMPLETE

Three broadcasts about a second apart, no answer, and an INCOMPLETE entry. Look at what never happened: the ping itself was never transmitted. Not one ICMP frame left the machine.

That matters because of how it looks on a real system. You get a silent failure at L3, with the evidence sitting one layer down in a table most people never check. INCOMPLETE in ip neigh means "the address you are asking about is not on this link, or the machine holding it is not answering". That is a far more precise complaint than "100% packet loss".

Try it

On your own laptop, against your real wifi link. Start with what you already know: ip neigh show. You will probably see one entry, your router. Now watch a resolution happen from scratch. In one terminal start sudo tcpdump -e -n -i wlp0s20f3 arp. In another run sudo ip neigh flush all followed by ping -c 2 192.168.1.1, using your own interface name and gateway from ip route. You should see the broadcast question and the unicast answer, then nothing further for that address. Run the ping again and no ARP appears at all. That is the cache doing its job.

Recap

A frame header is 14 bytes: destination MAC, source MAC, EtherType. A MAC address names an interface on one link and means nothing beyond it. Two bits of its first byte say whether it is a group address and whether it was made up locally, and software interfaces set that second bit. Everything that receives a broadcast forms one broadcast domain. The EtherType names the payload: 0x0800 for a packet, 0x0806 for ARP. ARP closes the gap between knowing an L3 address and needing a MAC address, with a broadcast question and a unicast answer, cached in the neighbour table with a state. When nobody answers, the ping is never transmitted, and the evidence is an INCOMPLETE neighbour entry.

Check yourself

1. Trace the path: machine A wants to ping machine B, both on the same link, and A's neighbour table is empty. How many frames cross the link before B's operating system sees the first byte of the ping, and what is the destination MAC address of each one?

Answer

Two frames go first, so the ping is the third. Frame one is A's ARP request, addressed to ff:ff:ff:ff:ff:ff. Frame two is B's ARP reply, addressed to A's own MAC address, because A's MAC was inside the request. Frame three is the ping, addressed to B's MAC address.

Check it against the four-frame capture in this chapter. The ping is the third line and the fourth is the reply coming back.

The near miss is answering "one", which counts only the ping, or answering "two broadcasts". The reply is unicast. That asymmetry gives ARP its efficiency: one machine bothers everybody once, and after that two machines talk privately.

2. Here is a symptom. A colleague says "the host is up, I can see it in the switch, but ping gives me 100% packet loss and tcpdump on the sender shows nothing going out at all." The cable is fine and the firewall is empty. What do you check, and what do you expect to find?

Answer

Check ip neigh show on the sender and expect an INCOMPLETE entry for the target address.

A packet cannot be handed to the card until the destination MAC address is known, so a failed ARP resolution suppresses the transmission. That is why tcpdump "shows nothing". There is nothing to show at L3. Look for the repeated broadcast requests with tcpdump -e -n arp and you will see the sender asking about once a second and nobody replying.

The near miss is "the packets are being dropped somewhere", which points you at firewalls and routers and costs you an afternoon. Nothing was dropped. Nothing was ever sent. Telling dropped apart from never transmitted is one of the most useful habits you can carry into a debugging session.

Chapter 2

The prefix, and the decision every packet forces

~11 min · WIRE · The frame chapter ended with a machine broadcasting on a link to find one MAC address. It only knew to broadcast because something had already decided the destination was on that link. That decision is this chapter. Everything the kernel does with a packet afterwards depends on it.

The packet header, and the four fields that matter

The L3 envelope is 20 bytes. Here is a real one, printed in full by a capture tool:

(tos 0x0, ttl 63, id 16081, offset 0, flags [DF], proto ICMP (1), length 84)
    10.30.1.2 > 10.30.2.2: ICMP echo request, id 104, seq 1, length 64

Four of those fields do work you need to follow. The source and destination are IP addresses: 32 bits each, written as four decimal bytes. A MAC address names an interface on one link. An IP address is meant to identify a machine anywhere. length 84 is the whole packet, header included, and it matches the prologue's sum. proto ICMP (1) is the EtherType idea one layer up: a number naming the payload, so the receiver knows which code to call.

The fourth is TTL, "time to live". It counts hops rather than time. Every machine that forwards a packet reduces it by one, and any machine that reduces it to zero throws the packet away instead of forwarding it. It exists because routing loops happen. Two misconfigured machines can each believe the other is the way to somewhere, and without TTL that packet would circulate until somebody pulled a cable. The value above is 63, one below the usual starting value of 64. That missing 1 is the subject of the second half of this chapter.

A prefix is a claim about a range

Addresses are handed out in blocks. A block is written as an address plus a prefix length: 192.168.1.110/24. The number after the slash says how many leading bits are fixed. Those fixed bits are the network part, and the rest identifies a machine inside it. The block is a subnet, and the notation is called CIDR, classless inter-domain routing. "Classless" because an older scheme fixed the split at 8, 16 or 24 bits, and this one lets it fall anywhere.

Work one through by hand. The arithmetic is the vocabulary.

192.168.1.110/24172.17.0.1/16
fixed bits2416
netmask255.255.255.0255.255.0.0
network address192.168.1.0172.17.0.0
broadcast address192.168.1.255172.17.255.255
usable for machines.1 to .254, so 25465,534
how many addresses2(32-24) = 2562(32-16) = 65,536

The netmask holds the same information as the prefix length, written as an address with the fixed bits set to 1. Two machines share a subnet when masking both addresses gives the same result. The kernel performs that test on every outgoing packet, and it is where this chapter is going.

The routing decision

The kernel keeps a routing table: a list of prefixes, each with instructions. Here is the real table from the laptop in the prologue:

$ ip route
default via 192.168.1.1 dev wlp0s20f3 proto dhcp src 192.168.1.110 metric 600
172.17.0.0/16 dev docker0 proto kernel scope link src 172.17.0.1 linkdown
172.18.0.0/16 dev br-817f796b1e66 proto kernel scope link src 172.18.0.1 linkdown
192.168.1.0/24 dev wlp0s20f3 proto kernel scope link src 192.168.1.110 metric 600

Read the fields. dev is the interface to send on. via names a next hop, another machine on that interface's link that has agreed to carry the packet onward. scope link says the opposite: destinations in this prefix sit on the link directly and need no next hop. proto kernel means the kernel installed the entry by itself the moment an address was assigned, so every interface with an address gets one for free. And default is shorthand for 0.0.0.0/0, the prefix with zero fixed bits, which matches every address in existence.

If default matches everything, why does anything else ever get used? Because of longest prefix match: among all entries that match, the one with the most fixed bits wins. A packet to 192.168.1.5 matches both 192.168.1.0/24 and 0.0.0.0/0, and 24 beats 0. A packet to 8.8.8.8 matches only the default. The default route is the entry that is always true and always loses, which is what "the way out when nothing else applies" should mean.

Three outcomes are possible, and Linux will tell you which one it picked for any address you name, without sending anything:

$ ip route get 8.8.8.8
8.8.8.8 via 192.168.1.1 dev wlp0s20f3 src 192.168.1.110       # via a next hop

$ ip route get 192.168.1.5
192.168.1.5 dev wlp0s20f3 src 192.168.1.110                   # on-link, no via

$ ip route get 172.17.0.5
172.17.0.5 dev docker0 src 172.17.0.1                          # on-link, different interface

$ ip route get 192.168.1.110
local 192.168.1.110 dev lo src 192.168.1.110                   # that is us

$ ip route get 127.0.0.1
local 127.0.0.1 dev lo src 127.0.0.1                           # also us

Learn this command. Whatever you believe about your routing, ip route get tells you what the kernel will do, and it settles arguments every time. Look at the fourth answer especially. A packet addressed to the machine's own wifi address does not leave the wifi card and come back. The kernel delivers it internally over the loopback interface. Machines do not talk to themselves over the wire.

Every one of those answers has the same shape: an interface, a source address to use, and either a next hop or nothing. And now the fact that makes the frame chapter click into place. ARP is performed on the next hop. When this laptop sends to 8.8.8.8, it broadcasts asking for the MAC address of 192.168.1.1. It never asks about 8.8.8.8, and would get no answer if it did. The packet header says 8.8.8.8. The frame header says the router's MAC address. Those two facts are independent.

Forwarding, and what changes at a hop

A machine that accepts a packet addressed to somebody else and sends it onward is forwarding. Linux will not do this unless you tell it to. The switch is net.ipv4.ip_forward, and it holds 0 on an ordinary desktop and 1 on anything acting as a router. Every container host you meet has it set to 1. In the NAT chapter you will set it yourself and discover that it is not enough on its own.

Here is a three-machine setup: host A on 10.30.1.0/24, host B on 10.30.2.0/24, and a router R with a foot in each. A pings B, and we capture on B's side of the second link. These are the four hardware addresses involved:

A's interface        12:36:b3:18:a5:c5
R's interface facing A   4e:7d:bd:95:63:6a
R's interface facing B   32:af:87:b3:3e:4b
B's interface        c6:79:01:63:1a:ce

And this is what arrived at B:

32:af:87:b3:3e:4b > c6:79:01:63:1a:ce, ethertype IPv4 (0x0800), length 98:
    (tos 0x0, ttl 63, id 16081, offset 0, flags [DF], proto ICMP (1), length 84)
    10.30.1.2 > 10.30.2.2: ICMP echo request, id 104, seq 1, length 64

Compare it with what A sent. The source MAC address now belongs to R's second interface. The destination MAC address is B's. Neither value appeared anywhere in the frame A transmitted. The IP addresses are untouched: still 10.30.1.2 to 10.30.2.2, as A wrote them. And the TTL is 63, because R decremented it.

That is the division of labour the layered scheme exists to create. L2 addresses get rewritten at every hop. L3 addresses are written once by the sender and carried to the end. A frame is a one-hop envelope, thrown away and rebuilt. A packet is the letter inside, and only the postmark changes.

Try it

Do the arithmetic before the command. Take your own address from ip -br addr, say 192.168.1.110/24, and write down on paper whether 192.168.1.200 and 192.168.2.5 are on your link. Then ask the kernel: ip route get 192.168.1.200 and ip route get 192.168.2.5. One should come back bare and one should come back with via. Then run ip route get against your own address and against 8.8.8.8. Finish with cat /proc/sys/net/ipv4/ip_forward to see whether your laptop is willing to be a router. On the machine in the prologue it prints 1, because Docker turned it on.

Recap

A packet header carries source and destination IP addresses, a protocol number, a length, and a TTL that every forwarder decrements. Addresses come in blocks written as a prefix length, which holds the same information as a netmask, and the arithmetic of network address, broadcast address and usable range follows from it. For every packet the kernel makes one decision against the routing table using longest prefix match, and gets one of three answers: it is mine, it is on this link, or send it via a next hop. ip route get shows you that decision without sending anything. ARP then resolves the next hop. A forwarding machine rewrites both MAC addresses and decrements the TTL, and leaves both IP addresses as the sender wrote them.

Check yourself

1. Trace the path: the laptop in this chapter sends a packet to 8.8.8.8. Name the destination IP address in the packet header, the destination MAC address in the frame header, and the address ARP was performed on. Then say which of the three would change if the destination were 192.168.1.5.

Answer

Destination IP 8.8.8.8. Destination MAC the router's, 5a:d6:1f:40:a6:ba. ARP was performed on 192.168.1.1, the next hop. For 192.168.1.5 all three change: the destination IP is 192.168.1.5, ARP is performed on 192.168.1.5 itself because the route is scope link, and the destination MAC is whatever that machine replies with.

Confirm the branch with ip route get 8.8.8.8 against ip route get 192.168.1.5. One prints via and one does not, and that single word decides what gets ARPed. The routing-decision flowchart (diagram 2.1) shows the same fact.

The near miss is saying ARP was performed on 8.8.8.8. Nothing on the link holds that address, so nobody would answer and the packet would never be sent, which is the INCOMPLETE failure from the frame chapter. The default route exists so that this question never gets asked.

2. Predict the value: host A sends a ping with TTL 64 to host B, four routers away. What TTL does B see, and what does B put in the TTL field of its reply?

Answer

B sees 60: 64 minus one for each of the four forwarding machines. B's reply starts fresh at its own default, which on Linux is 64. The reply is a new packet, and the inbound TTL has no influence on it.

You can watch the subtraction in this chapter's capture: one router, ttl 63. And you can see the reply's independence in the frame chapter's four-frame capture, where both directions are ordinary packets in their own right.

The near miss is thinking the TTL gets copied or mirrored into the reply. It does not. That is why ping output showing ttl 64 tells you the distance from them to you, and why a starting value of 255 on some systems makes the returned number look alarming when nothing is wrong.

Chapter 3

Namespaces and veth: more machines without more machines

~10 min · NETNS · The routing chapter needed three machines to show one TTL decrement, and the frame chapter needed two machines on a clean link. You have one laptop. This chapter is how those captures were made, and it is also how a container gets a network.

One kernel, many stacks

Everything in the frame and routing chapters was kernel state: a list of interfaces, a routing table, a neighbour table. A running Linux kernel normally keeps one of each. A network namespace is a second complete copy of that state, and a third, and a hundredth.

It pays to be precise about what "complete" means, because the surprises hide in the gaps people assume. A network namespace has its own:

  • set of interfaces, and an interface belongs to one namespace at a time
  • routing tables, including the default route
  • neighbour table
  • firewall rules, which is the hooks chapter
  • connection tracking table, which is the NAT chapter
  • listening sockets, so two namespaces can both have something on port 80
  • /proc/net contents
  • network-related kernel settings

The last one catches everybody, including the author of this document. While preparing the overlay chapter I turned IPv6 off with sysctl -w net.ipv6.conf.default.disable_ipv6=1, then captured traffic in a namespace and found the capture full of IPv6 chatter anyway. The setting had worked. It applied to the namespace I ran it in, and the namespace I was capturing in had its own copy, still at the default. A kernel setting that looks global is namespaced, and it fails quietly.

A namespace does not get its own filesystem, process list or users. Those are separate namespace types with their own rules. A container is a process that was started with a fresh set of several namespaces at once: its own filesystem view, its own process numbering, and its own network stack. When people say a container "has its own network", this is the mechanism. No virtual machine is involved, and no emulated hardware.

Making one, and getting inside it

A namespace lives as long as something holds a reference to it: a running process, or a named file handle. The ip netns family manages the second kind.

# ip netns add ns1
# ls -l /var/run/netns/
-r--r--r--    1 root     root             0 Sep 16 06:26 ns1

That zero-byte file is the handle. Opening it gives the kernel a reference to the namespace, so deleting the file destroys the namespace when no process is using it. ip netns exec ns1 command runs a command with its network namespace set to that one. Everything else about the process stays as it was: its files, its user, its memory.

Namespaces are identified by an inode number, and every process advertises the ones it is in.

# readlink /proc/self/ns/net
net:[4026532869]
# ip netns exec ns1 readlink /proc/self/ns/net
net:[4026533113]

Two different numbers, two different stacks. This is how you answer "are these two processes on the same network" for any two processes on a machine. You will make exactly this check in the pod-network chapter, where several containers turn out to share one namespace on purpose.

The virtual cable

A fresh namespace is completely isolated. It has a loopback interface and nothing else: no way in and no way out. To connect it to anything you need a veth pair: two interfaces created together and permanently wired to each other, so that every frame written to one arrives immediately on the other. It is a cable with two plugs, and it is the only kind of cable in this document you can create with a command.

The two ends are called peers. They start life in the same namespace and you move one.

# ip link add veth-a type veth peer name veth-b
# ip link set veth-a netns ns1
# ip link set veth-b netns ns2
# ip netns exec ns1 ip addr add 10.10.0.1/24 dev veth-a
# ip netns exec ns2 ip addr add 10.10.0.2/24 dev veth-b
# ip netns exec ns1 ip link set veth-a up
# ip netns exec ns2 ip link set veth-b up

Seven commands, and you have the two machines on one link that the frame chapter needed. Look at what the kernel did for free.

# ip netns exec ns1 ip -br link
lo          UNKNOWN   00:00:00:00:00:00 <LOOPBACK,UP,LOWER_UP>
veth-a@if3  UP        aa:71:3e:84:35:ee <BROADCAST,MULTICAST,UP,LOWER_UP>

# ip netns exec ns1 ip route
10.10.0.0/24 dev veth-a proto kernel scope link src 10.10.0.1

Three things to see here. The interface generated its own MAC address, aa:71:3e:..., with the frame chapter's locally-administered bit set, so no vendor was involved. The routing table has an entry nobody typed: assigning an address with a prefix tells the kernel the whole subnet sits on-link through that interface, and that is the routing chapter's proto kernel scope link route, installed without anyone asking. And the interface is called veth-a@if3, where 3 is the index of its peer. That suffix is how you find the other end of any veth on a busy machine, and you will use it in the Docker chapter to match a container to its cable.

The capture from the frame chapter

Ping across it and this happens.

# ip netns exec ns2 tcpdump -e -n -i veth-b 'arp or icmp'
fe:17:29:ac:56:79 > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42:
    Request who-has 10.10.0.2 tell 10.10.0.1, length 28
...

That is the ARP exchange diagram (diagram 1.2) made real, and it is the same capture, because this is where it came from. There was no second laptop. The capture was clean, four frames and nothing else, because this link genuinely had nothing else on it.

One more behaviour, because it produces a confusing symptom. Take one end down and look at the other.

# ip netns exec ns1 ip link set veth-a down
# ip netns exec ns2 ip -br link show veth-b
veth-b@if4  DOWN  82:6e:fa:69:82:f7 <NO-CARRIER,BROADCAST,MULTICAST,UP>

Read the flags carefully. The state says DOWN, the flag list still says UP, and there is a NO-CARRIER. Those are two separate facts. UP is the administrative state: you asked for this interface to work. NO-CARRIER is the operational state: nothing is plugged in. A veth has no carrier unless its peer is up, which mirrors a real cable. When a container's interface shows NO-CARRIER, the broken thing sits at the other end of the cable, in another namespace, and no amount of configuration inside the container will reach it.

Try it

Build the whole thing yourself. It costs nothing and it deletes cleanly.

sudo ip netns add ns1
sudo ip netns add ns2
sudo ip link add veth-a type veth peer name veth-b
sudo ip link set veth-a netns ns1
sudo ip link set veth-b netns ns2
sudo ip netns exec ns1 ip addr add 10.10.0.1/24 dev veth-a
sudo ip netns exec ns2 ip addr add 10.10.0.2/24 dev veth-b
sudo ip netns exec ns1 ip link set veth-a up
sudo ip netns exec ns2 ip link set veth-b up
sudo ip netns exec ns1 ping -c 2 10.10.0.2

Then prove the isolation. sudo ip netns exec ns1 ip route shows one route and no default, so ping 8.8.8.8 from inside fails with "Network is unreachable". That is a different failure from the frame chapter's silence, and you should see it once. Clean up with sudo ip netns del ns1 && sudo ip netns del ns2. The veth pair goes with them, because deleting a namespace destroys the interfaces inside it.

Recap

A network namespace is a complete second copy of the kernel's network state: interfaces, routes, neighbours, firewall rules, sockets, and the settings, which are namespaced too and fail quietly when you forget it. A container is a process started with a fresh set of namespaces. Namespaces are identified by inode, and a named one is a handle file under /var/run/netns. A veth pair is a two-ended virtual cable whose ends can live in different namespaces. Each end generates its own locally-administered MAC address, and assigning an address installs an on-link route automatically. The @ifN suffix names the peer's index. An end whose peer is down reports NO-CARRIER while staying administratively UP.

Check yourself

1. You add a firewall rule on your laptop that drops all outbound traffic to port 443. Then you start a container and curl https://example.com from inside it, and it works. No rule was removed. Why did the container ignore your rule, and where would the rule have to live to apply?

Answer

Firewall rules are per-namespace, and the container has its own. Your rule sits in the initial namespace's ruleset. The container's namespace has a separate, empty one, so nothing there matched.

The rule would have to live inside the container's namespace, or on the path the traffic takes through the initial namespace once it leaves the container. That second location is real, and it is where Docker and Kubernetes put all their rules. It exists because the container's packets are forwarded through the host, which is the hooks chapter.

The near miss is "the container bypasses the host firewall", which sounds the same and points the wrong way. Nothing was bypassed. The packets do traverse the host and can be filtered there. They cannot be caught by a rule written for locally-generated traffic, because the host did not generate them.

2. Trace the path: you create a veth pair, move one end into ns1, and give both ends addresses in 10.10.0.0/24. You bring up only the end inside ns1. From inside ns1, ping 10.10.0.2 fails. Say what ip -br link inside ns1 will show, what ip neigh will show, and which chapter's failure mode this is.

Answer

ip -br link shows the interface in state DOWN with NO-CARRIER among its flags, alongside the UP flag, because its peer is down. ip neigh shows an INCOMPLETE entry for 10.10.0.2, or nothing at all.

It is the frame chapter's failure. ARP got no answer, so the ping was never transmitted. The difference is that here you can name the cause: the far end of the cable is not up, so no frame can reach anything.

The near miss is expecting "Network is unreachable". That message comes from the routing decision failing, and the routing decision here succeeds. The on-link route was installed when you assigned the address, and it does not care whether the link has carrier. Routing says yes; L2 says nothing came back.

Chapter 4

The bridge: a switch made of software

~11 min · NETNS · The namespace chapter gave us a cable with two ends, which connects two namespaces. Every container host needs to connect dozens. This chapter is the object that makes that possible, and it ends with a failure you are meant to hit.

Why cables do not scale

A veth pair joins two namespaces. To join three so that all of them can talk, you need three pairs. Four needs six. Ten needs forty-five, and every namespace needs nine interfaces with nine addresses. The count is N(N−1)/2, and it becomes hopeless well before you reach a realistic number of containers.

Physical networks solved this long ago by inventing a box that every machine plugs into once. Linux has that box built in. A bridge is a software switch: a virtual device that other interfaces attach to, and it forwards frames between them using the rules from the frame chapter.

# ip link add br0 type bridge
# ip link set br0 up

Interfaces attached to it are its bridge ports. Attaching is called setting the bridge as the interface's master.

# ip link set b1 master br0
# ip link set b2 master br0
# ip link set b3 master br0
# bridge link show
4: b1@if5: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br0 state forwarding priority 32 cost 2
6: b2@if7: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br0 state forwarding priority 32 cost 2
8: b3@if9: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br0 state forwarding priority 32 cost 2

Each of those is one end of a veth pair whose other end sits inside a namespace. The @if5 suffix from the namespace chapter tells you which. Structurally, this is every container host you have ever used: one bridge, one veth pair per container, one end of each pair in the container.

A port in state forwarding is carrying traffic. The priority and cost values belong to a loop-avoidance protocol we will name in a moment and then leave alone.

What a switch actually does

A bridge's job is three rules, applied to every frame that arrives on a port.

  1. Note the source MAC address, and remember which port it came from. This is learning.
  2. Look up the destination MAC address. If it is known, send the frame out of that one port and no other.
  3. If it is unknown, or if it is a broadcast or multicast address, send it out of every port except the one it arrived on. This is flooding.

The table it learns into is the forwarding database, or FDB. Those three rules give a switch its most important property, and you can demonstrate it instead of taking it on trust. Three namespaces on one bridge. ns1 pings ns2 three times. ns3 captures everything it can see for the whole duration.

# ip netns exec ns1 ping -c 3 10.20.0.2
3 packets transmitted, 3 received, 0% packet loss

# and this is EVERY frame ns3 saw, start to finish:
4e:ec:5e:37:9c:5d > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42:
    Request who-has 10.20.0.2 tell 10.20.0.1, length 28

One frame. Six ICMP frames crossed that bridge, three requests and three replies, and ns3 saw none of them. It saw the opening broadcast, because a broadcast has to go everywhere. After that the bridge had learned where both participants were and delivered the rest privately. That is the difference between a switch and a shared wire, and it is why capturing traffic on a switched network shows you so much less than people expect.

The table afterwards confirms who is where.

# bridge fdb show br br0    (learned entries only)
4e:ec:5e:37:9c:5d dev b1 master br0
8e:6e:20:3e:8b:46 dev b2 master br0

ns1's MAC is 4e:ec:5e:37:9c:5d   -- learned on port b1
ns2's MAC is 8e:6e:20:3e:8b:46   -- learned on port b2

Learned entries carry no flag. Entries marked permanent were configured instead of learned, and entries marked self belong to the bridge device itself. In the overlay chapter you will meet a deliberately configured permanent entry, for a case where flooding cannot discover the far end.

Learned entries expire. The default is visible in the bridge's settings.

# cat /sys/class/net/br0/bridge/ageing_time
30000        # centiseconds, so 300 seconds
# cat /sys/class/net/br0/bridge/stp_state
0

Five minutes without hearing from a MAC address and the bridge forgets it. The next frame for that address gets flooded again, and the answer re-learns it. Expiry is what lets a machine move to a different port without anyone intervening.

The second value is the Spanning Tree Protocol, or STP: a protocol switches use to find loops between themselves and disable redundant ports. It is off, and for the bridges in this document it should stay off. A container bridge has one path to anywhere and no loops to find. It is named here so that the priority and cost columns in bridge link show stop being mysterious.

A bridge is also an interface

Here is the piece that confuses people, so let us be blunt about it. br0 is two things at once. It is a switch, forwarding frames between its ports. It is also an ordinary interface belonging to whichever namespace created it, and you can give it an address.

# ip addr add 10.20.0.254/24 dev br0

Doing that plugs the host itself into the switch, as one more machine on that link. The host now has an on-link route for 10.20.0.0/24 and every namespace on the bridge can ping it. This is what docker0 is: a bridge whose ports are container veths, holding the address 172.17.0.1 so the host is reachable from every container and can act as their way out. The Docker chapter takes that apart on a live system.

The trap

Build the three-namespace bridge above on a laptop that runs Docker and the pings may simply fail. They failed on the machine this document was written on. Here is the evidence.

# cat /proc/sys/net/bridge/bridge-nf-call-iptables
1

# with one rule present that discards traffic being forwarded from 10.20.0.0/24:
# ip netns exec ns1 ping -c 2 10.20.0.2
2 packets transmitted, 0 received, 100% packet loss

# and the rule's own counter afterwards:
counter packets 2 bytes 168 drop

Read that carefully, because it should not make sense yet. ns1 and ns2 sit on the same subnet. The routing chapter says no routing decision is involved. This is pure L2 switching, one hop, and a rule about forwarding should be irrelevant. But the counter says two packets hit it, and the pings are gone.

That setting is the reason. When bridge-nf-call-iptables holds 1, frames crossing a bridge are also shown to the machine's IP-level packet filter, as though they were being routed. It is on by default on any machine with a container runtime installed, because container runtimes need it to enforce anything at all. And on that same machine, the packet filter's default answer for traffic being forwarded is to throw it away.

So the fix is one of two things. Turn the setting off with sysctl -w net.bridge.bridge-nf-call-iptables=0, or write a rule that permits your bridge's traffic. Which one is correct depends on what else is using the machine, and the reasoning needs vocabulary you do not have yet. That vocabulary is the next chapter, and this failure is the reason to read it.

Try it

Build it and watch the table fill. If your pings fail, you have hit the trap above. That is the intended outcome, and the hooks chapter explains it.

sudo ip link add br0 type bridge
sudo ip link set br0 up
for i in 1 2 3; do
  sudo ip netns add ns$i
  sudo ip link add v$i type veth peer name b$i
  sudo ip link set v$i netns ns$i
  sudo ip link set b$i master br0
  sudo ip link set b$i up
  sudo ip netns exec ns$i ip addr add 10.20.0.$i/24 dev v$i
  sudo ip netns exec ns$i ip link set v$i up
done
sudo bridge fdb show br br0 | grep -v permanent | grep -v self   # empty
sudo ip netns exec ns1 ping -c 2 10.20.0.2
sudo bridge fdb show br br0 | grep -v permanent | grep -v self   # two entries

Then run the capture that proves the point: sudo ip netns exec ns3 tcpdump -e -n -i v3 in one terminal and the ping in another. Clean up with for i in 1 2 3; do sudo ip netns del ns$i; done && sudo ip link del br0.

Recap

Connecting N namespaces with cables needs N(N−1)/2 of them, so Linux provides a software switch instead. A bridge has ports, which are ordinary interfaces given the bridge as their master. It learns source MAC addresses into a forwarding database, forwards known destinations to one port, and floods broadcasts and unknown destinations everywhere else. A capture proves it by showing a third namespace one frame out of seven. Learned entries age out after five minutes. A bridge is a switch and an interface at the same time, and giving it an address plugs its own host into the link, which is what docker0 is. And on a machine with a container runtime, bridged frames also reach the IP-level packet filter, which can throw them away for reasons that make no sense at L2.

Check yourself

1. Predict the value: three namespaces sit on one bridge with an empty FDB. ns1 pings ns2 three times, successfully. How many frames does ns3 receive, and which ones?

Answer

One: the ARP request. Six ICMP frames cross the bridge, three requests and three replies, and ns3 sees none of them.

The ARP request is a broadcast and has to be flooded to every other port, and it is the only broadcast in the exchange. It also teaches the bridge which port ns1 is on, and the ARP reply that follows teaches it ns2's port. Every frame after the first has a known destination and goes to one port.

Check it against this chapter's capture, which is that experiment: one line of output for the whole run. The near miss is answering seven, or "all of them", which is what a hub would do. A hub repeats every frame to every port and learns nothing. The FDB is the difference, and bridge fdb show is where you watch it happen.

2. Here is a symptom. Two containers on the same host and the same bridge, in the same subnet, cannot ping each other. bridge fdb show lists both their MAC addresses on the right ports. ip neigh inside one container shows the other as REACHABLE with the correct MAC address. Nothing is down. What is happening, and which file would you read to confirm it?

Answer

The frames reach the bridge and the machine's IP-level packet filter throws them away, because bridged traffic is being handed to it. Read /proc/sys/net/bridge/bridge-nf-call-iptables and expect 1.

The give-away is that the neighbour entry says REACHABLE with the correct address. ARP completed, so frames cross the bridge in both directions perfectly well, and the evidence you were handed has already proved the L2 path healthy. Only something above L2 can drop the ICMP while letting ARP through, and ARP gets through because the IP-level filter has no opinion about a protocol that is not IP.

The near miss is suspecting the bridge or the FDB, which the evidence has cleared. This is the failure at the end of this chapter, and the counter that proves it sits in the hooks chapter's territory.

Chapter 5

Netfilter: five places the kernel lets you interfere

~11 min · FILTER · The bridge chapter ended with two pings vanishing between namespaces on the same subnet, and a counter proving something had thrown them away on purpose. This chapter is the machinery that did it. By the end you will be able to say why a rule about forwarding caught a frame that was never routed.

Hooks

As a packet moves through the kernel it passes a small number of fixed points where other code may look at it and decide its fate. Those points are netfilter hooks, and the IP path has five. Everything in this document that filters, rewrites, redirects or counts a packet is code registered at one of those five places. There is no sixth.

The names describe position relative to one event, and the event is the routing decision from the routing chapter.

  • prerouting — every packet that arrives, before the kernel has decided whether it is for this machine.
  • input — packets the routing decision said were for this machine, on their way up to a local process.
  • forward — packets the routing decision said were for somewhere else.
  • output — packets a local process just generated, straight after the routing decision for them.
  • postrouting — everything on its way out of an interface, forwarded or locally generated.

Read that list again with the routing chapter's three outcomes in mind and the shape falls out. A packet is for us, or it is for somebody else, or we made it. Those are the only three possibilities, and they give three paths through the five hooks.

The experiment

You do not have to take this on trust. Take the three-machine setup from the routing chapter, host A, router R and host B, and put a counter at all five hooks inside R, matching ping requests only. Then send one ping along each of the three possible paths, resetting between runs.

### A pings the ROUTER ITSELF        -- traffic FOR this machine
    prerouting   packets 1  #
    input        packets 1  #
    forward      packets 0
    output       packets 0
    postrouting  packets 0

### A pings B                        -- traffic THROUGH this machine
    prerouting   packets 1  #
    input        packets 0
    forward      packets 1  #
    output       packets 0
    postrouting  packets 1  #

### the ROUTER pings B               -- traffic FROM this machine
    prerouting   packets 0
    input        packets 0
    forward      packets 0
    output       packets 1  #
    postrouting  packets 1  #

Three paths, and every packet takes one of them. Inbound-for-us visits two hooks. Passing-through visits three. Locally-generated visits two and never sees prerouting at all. That last fact is the commonest reason a rule "does not work": it was written at prerouting, and the traffic it was meant to catch came from a process on the same machine.

Writing something at a hook

The modern interface is nftables, driven by the nft command. Four words of vocabulary and you can read any ruleset.

A table is a namespace for your rules, with a family (ip, ip6, inet, bridge) and a name you choose. A chain is a list of rules. A chain attached to a hook is a base chain, and it declares three things: which hook, what priority, and what policy, the verdict for packets that reach the end without matching anything. A rule is a set of conditions followed by a verdict: accept, drop, jump somewhere else, or counter, which counts and carries on.

table ip hookdemo {
        chain forward {
                type filter hook forward priority 0;
                icmp type echo-request counter
        }
}

That is the whole language for our purposes: attach a chain to forward at priority 0, and count ping requests. Priority matters because several chains can attach to the same hook, and the lower number runs first. The kernel has conventional names for the standard values, and nft prints them back at you.

NamePriorityWhat conventionally lives there
raw−300decisions taken before connection tracking
(connection tracking)−200the NAT chapter's bookkeeping

filter0allow and deny
srcnat100rewriting the source

Those names are the same concepts the older iptables command calls "tables". If you have typed iptables -t nat, you were choosing a priority. Take that in now, because the NAT chapter contains a result that only makes sense once you know that rewriting the source happens at priority 100 and your own rule at priority 400 runs after it.

Two commands, one engine

Modern distributions ship an iptables that is a translation layer. Check yours.

$ iptables --version
iptables v1.8.11 (nf_tables)

The suffix is the important part. This iptables does not drive the old engine. It writes nftables rules. The two commands are two languages describing one ruleset, and you can see the seam. Docker writes its rules with iptables, and asking nft to show them produces this.

chain PREROUTING {
        type nat hook prerouting priority dstnat; policy accept;
        xt match "addrtype" counter packets 2 bytes 740 jump DOCKER
}

Native nftables would express that condition in its own syntax. The xt match is a compatibility wrapper around the older implementation, and seeing it tells you at once that an iptables-speaking program wrote the rule instead of a person. You will meet a great deal of this. Docker speaks iptables, Kubernetes speaks iptables, and your distribution's firewall probably speaks nft. All three are editing the same thing.

The practical consequence: never assume a ruleset is empty because your preferred command shows nothing. nft list ruleset shows everything. iptables-save shows only what the older language can express.

The trap from the bridge chapter, explained

Now the promised payoff. Two namespaces on the same subnet, on the same bridge, pinging each other. Pure L2 switching, no routing decision, and a rule at the forward hook counted them and threw them away.

The cause is a kernel module called br_netfilter. When it is loaded and net.bridge.bridge-nf-call-iptables holds 1, frames crossing a bridge get pushed through the IP hooks as if they had been routed. Bridged traffic between two ports takes the prerouting, forward, postrouting path, matching the middle column of the counter experiment above.

This is deliberate behaviour. It is the only way to filter traffic between containers on the same bridge, which every container runtime needs to do, and it is why br_netfilter is loaded on any machine with Docker installed. It has one unfortunate consequence. A rule you wrote about routed traffic now governs switched traffic too, and Docker sets the default for forwarded traffic to discard.

So the two fixes from the bridge chapter can now be stated properly. Setting bridge-nf-call-iptables to 0 stops bridged frames visiting the IP hooks at all. It is simple, and it disables container isolation on every bridge on the machine. Adding an accept rule for your bridge's traffic at the forward hook is narrower and leaves everything else intact. For a scratch bridge you built by hand to learn on, either will do. On a machine doing real work, write the rule.

Try it

First look at what is already there. sudo nft list ruleset | head -60 on a laptop with Docker running shows you several hundred lines you did not write. Then run the counter experiment on the bridge you built in the bridge chapter.

sudo nft add table ip demo
sudo nft add chain ip demo fwd '{ type filter hook forward priority 0; }'
sudo nft add rule ip demo fwd ip saddr 10.20.0.0/24 counter
sudo ip netns exec ns1 ping -c 3 10.20.0.2
sudo nft list table ip demo        # the counter proves bridged frames came through

Then add accept to that rule and watch the bridge chapter's failure disappear: sudo nft add rule ip demo fwd ip saddr 10.20.0.0/24 accept. Remove it all with sudo nft delete table ip demo. To watch a single packet's whole path, combine sudo nft monitor trace with a meta nftrace set 1 rule and it prints every hook and rule the packet touches.

Recap

The IP path has five netfilter hooks, and their names are positions relative to the routing decision. A packet is for this machine, for somewhere else, or made here, and those three cases give three paths: prerouting-input, prerouting-forward-postrouting, and output-postrouting. A counter at each hook proves it. Rules live in base chains attached to a hook with a priority, and the conventional priorities have names: dstnat at −100, filter at 0, srcnat at 100. Those names are what the old iptables "tables" really were. Modern iptables is a translation layer over the same engine, and xt match in nft output is the seam showing. And br_netfilter pushes bridged frames through the IP hooks, so the bridge chapter's pings died at the forward hook without ever being routed.

Chapter 6

Connection tracking and NAT: where the addresses get rewritten

~13 min · FILTER · The prologue asked how a container at 172.17.0.2 gets an answer from the public internet, and said something must be replacing its address. The hooks chapter gave us five places where that could happen. This chapter is the replacement, the bookkeeping that makes it work, and the hook it happens at.

The easy half and the hard half

Rewriting the source address of an outgoing packet is easy. Two lines of code at the postrouting hook: overwrite four bytes, fix the checksum, transmit.

The reply is the problem. It comes back addressed to the rewritten address, which belongs to the machine that did the rewriting. Nothing in the reply says who it was really for. If the machine has forgotten the substitution, the reply goes to a local process that never asked for it, and the original sender waits forever.

So address rewriting is a memory feature with address rewriting attached. The memory is called connection tracking, usually shortened to conntrack.

What conntrack remembers

For each flow it tracks, conntrack stores two tuples. A tuple is the set of fields identifying one direction of a flow: protocol, source address, destination address, and for TCP and UDP the source and destination ports. The original tuple is how the first packet looked. The reply tuple is what a packet coming back must look like to belong to this flow.

Here are two real entries from a machine with one namespace behind it at 10.40.0.2, masquerading out of an interface holding 172.17.0.2.

$ conntrack -L
icmp 1 29 src=10.40.0.2 dst=1.1.1.1 type=8 code=0 id=28 \
          src=1.1.1.1 dst=172.17.0.2 type=0 code=0 id=28 mark=0 use=1

tcp  6 119 FIN_WAIT src=10.40.0.2 dst=1.1.1.1 sport=58978 dport=80 \
          src=1.1.1.1 dst=172.17.0.2 sport=80 dport=58978 [ASSURED] mark=0 use=1

Read the TCP one slowly. Everything in this chapter is inside it. The fields are: protocol name, protocol number, seconds until the entry expires, the connection's state, the original tuple, the reply tuple, then flags.

Original tuple: src=10.40.0.2 dst=1.1.1.1 sport=58978 dport=80. That is what the namespace sent.

Reply tuple: src=1.1.1.1 dst=172.17.0.2 sport=80 dport=58978.

Now compare them. Swap the two ends of the original tuple and you would get src=1.1.1.1 dst=10.40.0.2. The stored reply tuple says dst=172.17.0.2 instead, the address the packet was rewritten to. The gap between a plain swap and the stored reply tuple is the rewriting, written down. That sentence is the mechanism. Everything else in this chapter follows from it.

States

Conntrack also gives each flow a state, which rules can match on. Four matter here.

  • new — packets have been seen in one direction only.
  • established — valid packets have been seen in both directions.
  • related — a separate flow that an existing one legitimately spawned, such as an error message about it.
  • invalid — the packet fits no flow and cannot start one.

This is what makes a firewall stateful. You write one rule that accepts anything established, and then you only have to think about what may start a conversation. You saw this exact rule on a live machine in the hooks chapter's Docker output, and here it is in the older syntax.

-A DOCKER-CT -o docker0 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT

Connection tracking registers at priority −200, which the hooks chapter's table puts before every conventional rule location. By the time any of your rules see a packet it already has a state, and if it belongs to a known flow its rewriting has already been decided.

Building it, one failure at a time

The quickest way to see what each piece contributes is to add the pieces one at a time. A namespace at 10.40.0.2, a default route pointing at the host, and the host holding 172.17.0.2 with working internet.

# the namespace has a route to the world. Is that enough?
# ip netns exec ns1 ip route
default via 10.40.0.1 dev in-ns1
10.40.0.0/24 dev in-ns1 proto kernel scope link src 10.40.0.2

# ip netns exec ns1 ping -c 1 -W 2 1.1.1.1
1 packets transmitted, 0 received, 100% packet loss

# turn on forwarding. Enough now?
# sysctl -w net.ipv4.ip_forward=1
# ip netns exec ns1 ping -c 1 -W 2 1.1.1.1
1 packets transmitted, 0 received, 100% packet loss

# add ONE rule:
#   ip saddr 10.40.0.0/24 oifname "eth0" masquerade
# ip netns exec ns1 ping -c 2 -W 2 1.1.1.1
2 packets transmitted, 2 received, 0% packet loss
rtt min/avg/max/mdev = 25.116/25.139/25.163/0.023 ms

Three states, and the middle one teaches the most. With forwarding on, the request left the machine and reached 1.1.1.1. The reply never came back, because 1.1.1.1 was asked to answer 10.40.0.2, an address no router on the path will carry. Forwarding gets your packets out. Rewriting gets the answers home.

Four ways to rewrite

The operations have names, and the names say which end they touch.

OperationHook it belongs atWhat it changesTypical use
SNATpostroutingthe source address, to one you specifya router with a fixed public address
masqueradepostroutingthe source address, to whatever the outgoing interface currently holdslaptops, containers, anything on DHCP
DNATpreroutingthe destination address and portpublishing a container port; every Kubernetes Service
redirectpreroutingthe destination, to this machinetransparent proxies

Masquerade is SNAT that picks the address at transmit time instead of reading it from the rule. Every container runtime uses it, because the host's address may change and the rule should not have to. It costs slightly more per flow and it drops its flows when the interface goes down. Both are the right trade for a machine whose address is not guaranteed.

The hooks chapter's diagram forces the hooks. Rewriting the destination has to happen at prerouting, before the routing decision, or the kernel routes the packet using an address you were about to change. Rewriting the source has to happen at postrouting, after every decision that might have depended on the real source. So NAT has exactly two places it can live, and the conventional priorities are called dstnat and srcnat.

NAT sees only the first packet

Here is a result to predict before you read it. Put a counter on the masquerade rule, then send traffic in three bursts.

                                 nat-chain counter
baseline                                 0
after ping -c 5                          1
after a SECOND ping -c 5                 2
after one HTTP connection                3

Five pings moved the counter by one. Five more moved it by one again. A whole HTTP connection, handshake and request and response and teardown, a dozen packets, moved it by one.

The NAT machinery runs once per flow. The first packet of a flow traverses the nat chain, a decision gets made, and that decision is written into the conntrack entry as the reply tuple. Every later packet matches the entry and has the stored rewriting applied directly, without consulting your rules again.

Two consequences follow, and people get caught by both. NAT rules are cheap: a thousand rules cost you once per connection instead of once per packet. And, more painfully, editing a NAT rule leaves existing flows alone. They carry their decision in the conntrack table. If you have ever fixed a rule and watched the old behaviour continue, this is the reason, and conntrack -D to flush the affected entries is the step you were missing.

Where in the order your rule sits

Now a result that looks like a bug and is working as designed. Three counters, all at the postrouting hook, differing only in priority and in what they match. One burst of four pings from 10.40.0.2.

Chain priorityRule matchesPackets counted
50 (before srcnat)ip saddr 10.40.0.0/244
100 (srcnat, the masquerade itself)ip saddr 10.40.0.0/241
400 (after srcnat)ip saddr 10.40.0.0/240
400 (after srcnat)ip saddr 172.17.0.0/164

The third row is the one people get wrong. A correct-looking rule, at the right hook, matching the address the traffic came from, counting zero. It counts zero because by priority 400 that traffic comes from somewhere else. The rewriting happened at 100, and the packet's source address now reads 172.17.0.2, which the fourth row proves by matching it and counting all four.

The rule is fine. Its priority is wrong. At the postrouting hook you have to decide whether you are talking about the address the sender used or the address the world will see, and your answer changes a number.

Both views of one ping

Finally, the prologue's opening question, answered with two captures of one event taken in two places.

# on the uplink, where the world sees it:
IP 172.17.0.2 > 1.1.1.1: ICMP echo request, id 63, seq 1, length 64
IP 1.1.1.1 > 172.17.0.2: ICMP echo reply,   id 63, seq 1, length 64

# inside the namespace, at the same moment:
IP 10.40.0.2 > 1.1.1.1: ICMP echo request, id 69, seq 1, length 64

The namespace is right about what it did. It sent a packet from 10.40.0.2, and that packet existed with that address on the wire between the namespace and the host. Somewhere in between, at one hook, four bytes changed, and an entry was written down so the change could be undone on the way back. That is all of it.

Try it

Give a namespace real internet access with one rule, then watch the bookkeeping. Replace wlp0s20f3 with your own uplink from ip route.

sudo ip netns add ns1

sudo ip link set in-ns1 netns ns1

sudo ip netns exec ns1 ip addr add 10.40.0.2/24 dev in-ns1
sudo ip netns exec ns1 ip link set in-ns1 up

Recap

Rewriting an address outbound is easy and useless on its own, because the reply has to find its way home. Conntrack supplies the memory: for every flow it stores an original tuple and a reply tuple, and the gap between the reply tuple and a plain swap is the rewriting. It also assigns a state, which is what makes stateful rules possible. Forwarding gets packets out of a machine; rewriting gets the answers back, and you can watch that by adding the pieces one at a time. Rewriting the destination has to happen at prerouting and the source at postrouting, because of where the routing decision sits. Masquerade is SNAT that picks the address at transmit time. The nat chain runs once per flow, so rule edits leave existing connections alone, and a rule placed after srcnat matching the original source address will match nothing at all.

Three, in both cases. The nat chain runs once per flow, and three connections are three flows wherever they go. They differ in source port, which is part of the tuple, so each gets its own conntrack entry and its own single trip through the rules.

The conntrack table. Each existing flow stored its rewriting decision in its reply tuple when its first packet went through, and later packets are rewritten from that entry without consulting the rules. Clear it with conntrack -D, narrowed with -s or -d to the affected flows.

Chapter 7

How Docker does it, and the three other ways

~12 min · CONTAINER · You have now built by hand every component a container runtime uses: namespaces, veth pairs, a bridge, forwarding, and one masquerade rule. This chapter opens a live Docker installation, finds those five things, and then asks what else you could have done instead.

Finding the cable

Start a container and look at it from inside.

$ docker run -d --rm -p 18080:80 --name netdoss alpine sleep 300
$ docker exec netdoss ip route
default via 172.17.0.1 dev eth0
172.17.0.0/16 dev eth0 scope link  src 172.17.0.2

Two routes, and you can read both. One on-link route for the subnet, installed by the kernel when the address was assigned, as in the namespace chapter. One default route pointing at 172.17.0.1, which the bridge chapter told you is the address on docker0 itself. The bridge is acting as an interface so the host can be the container's way out.

The container's eth0 is one end of a veth pair. The namespace chapter said the @ifN suffix names the peer, and you can read the same information as a number.

$ docker exec netdoss cat /sys/class/net/eth0/iflink
47

$ ip link show | grep '^47:'
47: veth5adafde@if2: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue master docker0 state UP

There it is. The container's eth0 has peer index 47, and interface 47 on the host is veth5adafde, a port on docker0. Those two commands are the most useful thing in this chapter. Given any container, they tell you which host interface carries its traffic, and that is where you attach a capture when you need to see what a container is really sending.

The host's own view confirms the shape.

$ ip -br addr show docker0
docker0          UP             172.17.0.1/16

A bridge with an address, veth ports, one namespace per container. The bridge chapter's lab, built by a daemon instead of by you.

The two rules

Everything else is the ruleset. Here is what Docker installed on the machine this document was written on, filtered to the parts that matter.

$ sudo iptables-save -t nat | grep -E 'MASQUERADE|18080'
-A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE
-A DOCKER ! -i docker0 -p tcp -m tcp --dport 18080 -j DNAT --to-destination 172.17.0.2:80

The first is the NAT chapter's masquerade rule, and you can read every clause. Traffic from the container subnet, leaving by any interface except the bridge itself, gets its source address rewritten. The exception matters. Container-to-container traffic stays on docker0 and must keep its addresses, because both ends already understand them.

The second is what -p 18080:80 means. Publishing a port is a DNAT rule at prerouting: anything arriving on port 18080 that did not come from the bridge has its destination rewritten to the container's address and port. No proxy process sits in the path and no forwarding daemon runs. Four bytes and a port number change at one hook, and conntrack remembers the change so the replies come back.

The filter side is where Docker becomes opinionated.

$ sudo iptables-save -t filter | grep -E '^:(FORWARD|DOCKER)'
:FORWARD DROP [0:0]
:DOCKER - [0:0]
:DOCKER-BRIDGE - [0:0]
:DOCKER-CT - [0:0]
:DOCKER-FORWARD - [0:0]
:DOCKER-INTERNAL - [0:0]
:DOCKER-USER - [0:0]

FORWARD DROP is the bridge chapter trap, installed by Docker itself. Docker sets the default for forwarded traffic to discard and then permits what it wants, which is the correct way round for a firewall and a real surprise for anyone who builds a bridge by hand afterwards. DOCKER-USER is the chain Docker promises never to touch, and it runs before Docker's own rules. If you need to add policy to a machine running containers, that is the supported place.

The other three ways

A bridge with NAT is one answer to "how does a container get on the network". It is the default because it works everywhere and asks nothing of the surrounding network. The alternatives matter, because each one removes a cost the default pays.

macvlan gives a container a virtual interface on a real NIC, with its own MAC address. It skips both the bridge and the NAT rule. The container appears on the physical network as a separate machine, takes an address from the real subnet, and is reachable from anywhere on it.

ipvlan does the same while sharing the parent's MAC address, telling children apart by IP address.

host mode, written docker run --net=host, skips the namespace. The container uses the host's network stack, sees the host's interfaces and binds the host's ports. Maximum performance, zero isolation, and port conflicts become real again.

There is a fourth option you have already used without noticing. --net=container:name puts a new container into an existing container's network namespace, so both see the same interfaces and reach each other on localhost. Hold on to that one. The pod-network chapter is built on it.

The macvlan surprise

macvlan has a behaviour that catches everyone once, and it is better seen than described. A parent interface holding 10.50.0.1, two macvlan children in separate namespaces at .11 and .12, and another machine further out at .254.

each child has its OWN hardware address:
  parent       16:31:1a:ea:6a:1d
  child mv1    3a:ae:16:59:94:07
  child mv2    ae:4b:cd:6d:60:93

child to child (10.50.0.11 -> 10.50.0.12):        0% packet loss
child to further out (10.50.0.11 -> 10.50.0.254): 0% packet loss
child to the PARENT HOST itself (-> 10.50.0.1):   100% packet loss

The container reaches the entire network except the one machine it is running on. This is deliberate, and the driver enforces it: a macvlan child and its parent cannot talk to each other in either direction. If your monitoring agent runs on the host and scrapes containers, macvlan breaks it, and no firewall rule will fix it, because the traffic never reaches a hook.

ipvlan behaves the same way for the same reason, which the capture confirms while also showing the MAC difference.

ipvlan children SHARE the parent's hardware address:
  parent       f2:fb:8f:6c:59:8d
  child iv1    f2:fb:8f:6c:59:8d
  child iv2    f2:fb:8f:6c:59:8d

child to child:                 0% packet loss
child to further out:           0% packet loss
child to the parent host:     100% packet loss

That MAC difference has a consequence outside the machine. With macvlan, the switch port your server is plugged into sees a new source MAC address for every container.

# what the next machine along learned, macvlan run:
10.50.0.11 lladdr 3a:ae:16:59:94:07
10.50.0.12 lladdr ae:4b:cd:6d:60:93

# the same experiment with ipvlan:
10.60.0.21 lladdr f2:fb:8f:6c:59:8d

Managed switches often limit how many MAC addresses a port may present, and disable the port when the limit is passed. Wireless is worse: 802.11 has no way to carry a second source MAC address on an authenticated link, so macvlan over wifi does not work at all. Those two facts are why ipvlan exists, and why the sidebar below uses a made-up parent instead of your laptop's wifi.

One more practical limit, found the hard way while preparing this chapter. A single parent interface cannot host both drivers. Adding a macvlan child to a parent that already has ipvlan children fails with RTNETLINK answers: Resource busy. Choose one driver per interface.

Recap

A Docker container is a namespace holding one end of a veth pair whose other end is a port on the docker0 bridge, and the bridge carries 172.17.0.1 so it can be the default route. Two rules do the rest: a masquerade at postrouting that excludes traffic staying on the bridge, and a DNAT at prerouting for every published port. Docker sets the forwarded-traffic default to discard and offers DOCKER-USER as the supported place for your own policy. The alternatives trade isolation for directness: macvlan gives each container its own MAC on the real subnet, ipvlan shares the parent's MAC, host mode skips the namespace. macvlan and ipvlan both make the container unreachable from its own host, by design and beyond the reach of any rule. And --net=container: puts two containers in one namespace, which is the next-but-one chapter in disguise.

Check yourself

1. Trace the path: an outside machine connects to your laptop on port 18080, published to a container's port 80. Name every address rewrite that happens to the request and to the reply, and say which hook each happens at.

Answer

One rewrite each way, and the second happens by itself. Inbound, at prerouting, DNAT changes the destination from the laptop's address and port 18080 to 172.17.0.2:80. The source is untouched, so the container sees the outside machine's real address. Outbound, the reply matches the flow's reply tuple and conntrack undoes the change, putting the laptop's address and port 18080 back as the source before it leaves.

The masquerade rule stays quiet, because its condition is ! -o docker0 and the reply goes out of the bridge. Check with conntrack -L during a connection and compare the two tuples, as in the NAT chapter.

The near miss is expecting a second explicit rule for the return path. There is none, and there never is. Every NAT rule you write describes one direction, and the reverse follows from the conntrack entry it created.

Chapter 8

Crossing machines: the overlay

~13 min · OVERLAY · Every chapter so far stayed inside one machine. The Docker chapter's container reached the internet by having its address replaced, which works and destroys its identity. Now two containers on two different machines have to reach each other as themselves, across a network that has never heard of either address.

Three ways out, and why one of them wins

Machine A runs containers in 10.244.1.0/24. Machine B runs containers in 10.244.2.0/24. The two machines reach each other on 192.168.100.0/24. A container on A sends a packet to 10.244.2.2, and A's default route hands it to a router with no entry for 10.244.0.0/16, which throws it away.

There are three families of answer.

Teach the network. Add a route on every machine and every router between them saying that 10.244.2.0/24 lives at 192.168.100.2. This is the fastest option by a wide margin, because nothing gets added to any packet. It requires that you control the routers, or that all your machines share one link so no router is involved. You will see it working in the pod-network chapter. Notice the reason it works there when you get to it.

Rewrite the addresses. Masquerade container traffic as it leaves each machine, as in the NAT chapter. This needs nothing from the network and it defeats the purpose. The receiving container sees the sending machine's address, so it cannot tell two senders apart, cannot apply policy per sender, and cannot start a conversation of its own.

Put the packet inside another packet. Wrap the whole thing, frame and all, in a fresh packet addressed from 192.168.100.1 to 192.168.100.2, which the network does know how to carry. The far end unwraps it and delivers the original, unmodified, with both addresses intact.

The third is encapsulation again, the mechanism from the prologue, applied at a scale it was not designed for. The network you hide inside is the underlay. The network you create on top is the overlay. It appeals because the underlay carries the traffic without being configured for it, and without knowing what it holds.

VXLAN

The common encapsulation is VXLAN, Virtual eXtensible LAN. It wraps a complete Ethernet frame in a UDP datagram, and it adds three things you need names for.

A VNI, or VXLAN Network Identifier, is a 24-bit number in the VXLAN header. It separates overlays that share an underlay: two VNIs are two independent virtual networks, even though their packets travel the same wires. Twenty-four bits gives about sixteen million of them, which was the original selling point against the 4096 available to older isolation schemes.

A VTEP, VXLAN Tunnel End Point, is the thing that wraps and unwraps. On Linux it is an interface you create.

The destination port is UDP 4789, assigned for this purpose. UDP was chosen over a protocol of its own so that the packets pass through ordinary firewalls and get spread across links by ordinary load-balancing hardware.

# ip link add vxlan0 type vxlan id 42 dev u1 remote 192.168.100.2 dstport 4789
# ip -d link show vxlan0
2: vxlan0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1450 ...
    vxlan id 42 remote 192.168.100.2 dev u1 srcport 0 0 dstport 4789 ttl auto ageing 300

One command creates a VTEP. id 42 is the VNI, dev u1 is the underlay interface to send on, and remote names the other end. Look at the MTU the kernel chose without being asked: 1450, where the underlay has 1500. That number is the subject of the last section of this chapter, and it is the commonest cause of a cluster network that appears to work.

What the underlay actually carries

Two containers, on two machines, one ping. This is the first packet, captured on the underlay.

ba:aa:b7:bd:d8:02 > 2e:26:91:a0:f3:90, ethertype IPv4 (0x0800), length 92:
    (tos 0x0, ttl 64, id 40272, flags [none], proto UDP (17), length 78)
    192.168.100.1.38934 > 192.168.100.2.4789: VXLAN, flags [I] (0x08), vni 42
        1e:f3:3e:8d:de:7c > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42:
            Request who-has 10.244.2.0 tell 10.244.1.0, length 28

Read it from the outside in, and count. An Ethernet frame between the two machines' interfaces, 92 bytes. Inside it an IP packet, 78 bytes, from 192.168.100.1 to 192.168.100.2, protocol UDP. Inside that, UDP to port 4789. Inside that, a VXLAN header carrying vni 42. And inside that, a complete second Ethernet frame with its own MAC addresses, carrying an ARP request. The frame chapter's protocol, running inside a tunnel, asking about an address the underlay has never heard of.

The arithmetic closes. The inner frame is 42 bytes, plus 8 for VXLAN and 8 for UDP is 58, plus 20 for the outer IP header is 78, plus 14 for the outer Ethernet header is 92. Every one of those numbers is in the capture.

The routes, and one odd-looking word

Encapsulation alone does not make a network. Something has to decide that 10.244.2.2 belongs in the tunnel. That is the routing chapter's routing decision, with entries you write.

# ip route     (on machine A)
10.244.0.0/16 dev vxlan0 proto kernel scope link src 10.244.1.0
10.244.1.0/24 dev cni0 proto kernel scope link src 10.244.1.1
10.244.2.0/24 via 10.244.2.0 dev vxlan0 onlink
192.168.100.0/24 dev u1 proto kernel scope link src 192.168.100.1

Read the third line. Machine B's container subnet is reachable via 10.244.2.0, which is machine B's own VTEP, out of the tunnel interface. The word onlink tells the kernel to treat that next hop as directly reachable even though no interface configuration says it should be. Without it, the kernel refuses the route as nonsensical. You will see onlink on every route a cluster network installs, and now you know it means "trust me, this next hop is reachable here".

ARP still happens, inside the tunnel, for that next hop, and the capture above shows it. The VTEP has its own forwarding database for deciding which machine to send an encapsulated frame to.

# bridge fdb show dev vxlan0
42:ba:e2:c2:82:91 dst 192.168.100.2 self
00:00:00:00:00:00 dst 192.168.100.2 via u1 self permanent

The first entry was learned: machine B's VTEP MAC address lives at 192.168.100.2. The second is the interesting one. An all-zeros MAC address is a catch-all entry meaning "anything you have no entry for, send there". That is how a broadcast inside the overlay gets delivered: the VTEP sends a copy to every machine in the catch-all list. With one remote, that is one copy. With fifty machines it is forty-nine copies of every broadcast, and that is why real cluster networks fill this table from a controller instead of relying on flooding.

The 50 bytes, and the failure they cause

Now the part that costs people days. The underlay interface has an MTU of 1500. Encapsulation adds 50 bytes. So the largest original packet that can make the trip is 1450, and the kernel set the VTEP's MTU to exactly that.

Here is the lab this chapter was built in. It contains the bug on purpose, because it is the bug everyone ships.

  u1     mtu 1500      the underlay
  vxlan0 mtu 1450      the tunnel, correctly sized by the kernel
  cni0   mtu 1500      the bridge the containers are actually plugged into

The containers hang off a bridge advertising 1500. They will happily generate a 1500-byte packet. It reaches the VTEP, which has to add 50 bytes, producing 1550, too large for the underlay. Depending on flags and configuration it gets fragmented, or thrown away with an error sent back, or thrown away silently.

The symptom is unmistakable once you have seen it and baffling before. Ping works perfectly. DNS works. Small HTTP requests work. Then a large response, or a database result set, or a container image pull, hangs forever with no error. Everything small succeeds because everything small fits. The threshold sits at 1450 bytes and nothing you test by hand goes near it.

The fix is to make every interface the containers touch agree with the tunnel: set cni0 and the container-side veth to 1450 as well. Real cluster networks do this for you, and get it wrong when the underlay turns out to be something other than they assumed. A cloud network with its own 1450, or a tunnel inside a tunnel, and the arithmetic has to be redone.

When something works for small things and hangs for large ones, measure the MTU along the whole path before you look at anything else. ping -M do -s 1422 sends a packet that must not be fragmented and comes to exactly 1450 bytes with its headers. If that fails and -s 1400 succeeds, you have found it.

Recap

Container addresses on one machine mean nothing to the network between machines, and there are three answers: teach the routers, rewrite the addresses and lose the sender's identity, or wrap each frame in a packet the network already understands. The third is an overlay riding on an underlay. VXLAN does it by putting a whole Ethernet frame inside UDP port 4789, tagged with a 24-bit VNI that separates independent virtual networks, and the wrapping device is a VTEP. A capture shows five nested layers with byte counts that add up. Routes carrying onlink send traffic into the tunnel, and the VTEP's own forwarding database maps inner MAC addresses to remote machines, with an all-zeros catch-all entry for flooding. The wrapping costs 50 bytes, so the tunnel's MTU is 1450. Any interface the containers touch that still says 1500 gives you a network where everything small works and everything large hangs.

Check yourself

1. Predict the value: your underlay has an MTU of 9000, jumbo frames. You build a VXLAN overlay on it. What MTU should the interfaces inside your containers carry, and what will ip link report for the VTEP?

Answer

8950 for both. The encapsulation overhead stays at 50 bytes whatever the underlay's size: 20 for the outer IP header, 8 for UDP, 8 for VXLAN, 14 for the inner Ethernet header. So the VTEP reports 9000 minus 50, and the container-facing interfaces have to agree with it.

Check the same subtraction in this chapter's capture: an inner frame of 42 became an outer frame of 92, and 92 minus 42 is 50. The kernel does this arithmetic for the VTEP by itself. It does not do it for your bridge, and that is the bug in the lab transcript above.

The near miss is giving 8950 to the VTEP and leaving the bridge at 9000 because "the kernel handled it". The kernel sized the interface it created and has no way to know which other interfaces feed it. That mismatch stays invisible until somebody sends more than the tunnel's MTU.

2. Here is a symptom. A newly built two-node cluster passes every check: pods ping across nodes, DNS resolves, small API calls succeed. Then image pulls hang at random percentages, and one service's large JSON responses never complete while its small ones always do. Name the measurement you take first, the exact command, and what the two outcomes tell you.

Answer

Measure the path MTU between two pods on different nodes with ping -M do -s 1422 <other pod>, which forbids fragmentation and produces a packet of exactly 1450 bytes including headers. If that fails while -s 1400 succeeds, the path cannot carry 1450 and something on it is smaller than you assumed.

Everything below the threshold fits in one packet and everything above it does not, so the failure sorts your traffic by size instead of by destination. That is why it looks random. Confirm by comparing the tunnel interface's MTU with the container bridge's, as in the transcript above.

The near miss is blaming the registry, the application, or packet loss. Loss would degrade small requests too, and an application fault would not track response size so closely. "Small works, large hangs" is close to a signature, and MTU is the first suspect and usually the only one.

Chapter 9

The Kubernetes pod network

~14 min · K8S · The overlay chapter built a network where containers on two machines reach each other as themselves. Kubernetes invents nothing beyond that. It adds a rule about what must be true, a contract for the program that makes it true, and a deliberate refusal to say how.

Four sentences that define everything

The Kubernetes network model is a short list of requirements. Paraphrased from the project's own wording:

  1. Every pod gets its own unique, cluster-wide IP address.
  2. All pods can communicate with all other pods, on the same node or on different nodes, without address translation.
  3. Agents on a node, the kubelet and system daemons, can reach all pods on that node.
  4. Containers within a pod share a network namespace and reach each other over localhost.

Rule 2 is the expensive one. It rules out the NAT chapter's approach: you may not masquerade pod-to-pod traffic, because the receiving pod has to see the sender's real address. Everything hard about cluster networking descends from that prohibition, and the overlay chapter's overlay exists because of it.

A pod is the unit those rules describe. It is one network namespace, with one address, shared by one or more containers. You have already built this by hand: the Docker chapter's --net=container:name, which put a second container into an existing container's namespace. Kubernetes does the same with one refinement. The namespace belongs to none of your containers. A tiny extra container that does nothing creates and holds it, called the sandbox or pause container, and your containers join it.

That indirection has a reason. If the namespace belonged to your first container, restarting that container would destroy the pod's network and change its address. Because it belongs to a process whose only job is to keep running, your containers can crash and restart as often as they like and the pod keeps its identity. The container runtime shows the arrangement plainly.

$ crictl inspectp <sandbox id>
    "network": "POD"

The address plan

Rule 1 demands cluster-wide unique addresses. The cheap way to guarantee uniqueness without a central allocator is to give each node a private slice, and Kubernetes calls it the PodCIDR. Here is a real two-node cluster.

$ kubectl get nodes -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.podCIDR}{"\n"}{end}'
netdossier-control-plane        10.244.0.0/24
netdossier-worker               10.244.1.0/24

podSubnet:     10.244.0.0/16      # the whole cluster's pod addresses
serviceSubnet: 10.96.0.0/16       # the Services chapter's territory

A /16 carved into /24s, one per node, 254 usable pods each. Each node allocates from its own slice with no coordination, and the slices cannot collide. It also keeps the routing chapter's routing tractable: to reach any pod you need one route per node.

The rule, proved

Rule 2 says no address translation between pods. You can check that. A pod on the worker node pings a pod on the control-plane node, and we capture on the worker's uplink, the actual wire between the two machines.

pod 10.244.1.3 on netdossier-worker (node address 172.19.0.3)
   --->  pod 10.244.0.2 on netdossier-control-plane (node address 172.19.0.2)

captured on the worker node's eth0:
IP 10.244.1.3 > 10.244.0.2: ICMP echo request, id 99, seq 0, length 64
IP 10.244.0.2 > 10.244.1.3: ICMP echo reply,   id 99, seq 0, length 64

Pod addresses, raw, on the wire between machines. Neither node's address appears anywhere. Set that beside the NAT chapter's capture, where the namespace's address was replaced by the host's before transmission, and one screenshot separates a container network from a cluster network.

An explicit exemption enforces the rule, and you can read it.

-A KIND-MASQ-AGENT -d 10.244.0.0/16 -j RETURN       # pod traffic: do NOT masquerade
-A KIND-MASQ-AGENT -j MASQUERADE                     # everything else: do

Two rules, in order. Anything destined for the pod subnet returns early and escapes untouched. Anything else, a pod reaching the internet, gets the NAT chapter's treatment. That pairing is how every cluster satisfies rule 2 while still letting pods reach the outside world.

The contract: CNI

Kubernetes has no networking code of its own. When the kubelet needs a pod to have a network, it runs a program and reads what it prints. That interface is CNI, the Container Network Interface, and it is deliberately small.

A CNI plugin is an executable. The runtime passes:

  • CNI_COMMAND — the operation: ADD, DEL, CHECK, GC, VERSION or STATUS
  • CNI_CONTAINERID — an identifier the runtime chose
  • CNI_NETNS — the path to the namespace to wire up
  • CNI_IFNAME — what to call the interface inside it, almost always eth0
  • CNI_PATH and CNI_ARGS — where to find other plugins, and extra key-value data

The network configuration arrives on standard input as JSON. The plugin prints a result as JSON on standard output and exits zero. That is the contract: environment variables in, JSON out, exit code decides.

Allocating addresses is a separate job called IPAM, IP address management, and it is usually a separate plugin. Plugins also chain: the configuration lists several, and each runs in turn on the result of the last. Here is the real configuration from the cluster above.

$ cat /etc/cni/net.d/10-kindnet.conflist
{
  "cniVersion": "0.3.1",
  "name": "kindnet",
  "plugins": [
    { "type": "ptp",
      "ipMasq": false,
      "ipam": { "type": "host-local",
                "dataDir": "/run/cni-ipam-state",
                "routes": [ { "dst": "0.0.0.0/0" } ],
                "ranges": [ [ { "subnet": "10.244.1.0/24" } ] ] },
      "mtu": 1500 },
    { "type": "portmap", "capabilities": { ... } }
  ]
}

Read it against the vocabulary. The main plugin is ptp. Its address allocation is handed to host-local, which gives out addresses from that node's PodCIDR and remembers them in a directory. A second plugin, portmap, runs afterwards and adds DNAT rules for any pod that asked for a host port. The Docker chapter's published ports, as a chained plugin.

Writing one

The contract is small enough that a working plugin fits on one screen. This one is real. It was run, and the output below is what it printed.

#!/bin/sh
set -e
CONF=$(cat)                                  # network config arrives on stdin
SUBNET=$(echo "$CONF" | sed -n 's/.*"subnet"[ ]*:[ ]*"\([^"]*\)".*/\1/p')
GW=$(echo "$CONF"     | sed -n 's/.*"gateway"[ ]*:[ ]*"\([^"]*\)".*/\1/p')
BR=$(echo "$CONF"     | sed -n 's/.*"bridge"[ ]*:[ ]*"\([^"]*\)".*/\1/p')
STATE=/var/lib/mini-cni; mkdir -p $STATE
HOSTIF="veth$(echo $CNI_CONTAINERID | cut -c1-8)"

case "$CNI_COMMAND" in
ADD)
  N=$(cat $STATE/last 2>/dev/null || echo 1); N=$((N+1)); echo $N > $STATE/last
  IP="$(echo $SUBNET | cut -d. -f1-3).$N"           # this is all IPAM is
  PREFIX=$(echo $SUBNET | cut -d/ -f2)
  ip link add "$HOSTIF" type veth peer name "$CNI_IFNAME" netns "$CNI_NETNS"
  ip link set "$HOSTIF" master "$BR"
  ip link set "$HOSTIF" up
  ip -n "$CNI_NETNS" addr add "$IP/$PREFIX" dev "$CNI_IFNAME"
  ip -n "$CNI_NETNS" link set "$CNI_IFNAME" up
  ip -n "$CNI_NETNS" link set lo up
  ip -n "$CNI_NETNS" route add default via "$GW"
  echo "$HOSTIF" > "$STATE/$CNI_CONTAINERID"
  cat <<RESULT
{"cniVersion":"1.0.0","interfaces":[{"name":"$CNI_IFNAME","sandbox":"$CNI_NETNS"}],
 "ips":[{"address":"$IP/$PREFIX","gateway":"$GW","interface":0}],

  ;;
DEL)
  H=$(cat "$STATE/$CNI_CONTAINERID" 2>/dev/null || echo "$HOSTIF")

What the real cluster did, which surprised me

The model says what must be true and refuses to say how. Look at how much room that leaves. The plugin above uses a bridge, as the bridge chapter taught. Here is what the real cluster's node looks like.

$ ip -br addr        # on netdossier-worker
eth0@if44          UP    172.19.0.3/16
veth2f03ea05@if2   UP    10.244.1.1/32
vetha4e15a39@if2   UP    10.244.1.1/32
veth9c04d18e@if2   UP    10.244.1.1/32

$ ip route
default via 172.19.0.1 dev eth0
10.244.0.0/24 via 172.19.0.2 dev eth0
10.244.1.2 dev veth2f03ea05 scope host
10.244.1.3 dev veth9c04d18e scope host
10.244.1.4 dev vetha4e15a39 scope host
172.19.0.0/16 dev eth0 proto kernel scope link src 172.19.0.3

There is no bridge. The ptp plugin, short for point-to-point, gives each pod its own veth pair and no shared L2 segment at all. Three oddities follow, and all three are deliberate.

The node-side veths all carry the same address, 10.244.1.1/32. A /32 is a prefix with no room for neighbours, so it makes no claim about a subnet. It exists to give the pod something to point a default route at. The same address on three interfaces is fine, because no two of them share a link.

Each pod has a host-scope route out of its own veth. Pod-to-pod traffic on the same node crosses no switch. It goes up into the node's routing table and back down a different veth. Every packet between two pods on one machine is routed, so the hooks chapter's forward hook sees it and the bridge chapter's bridge complications never arise.

And the cross-node entry is 10.244.0.0/24 via 172.19.0.2 dev eth0, a plain route. This cluster has no overlay at all. Both nodes are containers on one Docker bridge, so nothing gets encapsulated and the 50 bytes of overhead never apply. They share a link, so each can simply be told about the other's slice. The overlay chapter's first option, the one that needs the network to cooperate, and here the network is one bridge on a laptop, so it cooperates completely.

This is what the chapter exists to show you. The four rules constrain the outcome and say nothing about the mechanism. One cluster routes, another encapsulates, a third programs the switches, and a fourth replaces the whole packet path with small programs loaded into the kernel, which is the epilogue. When you debug a cluster you have never seen, the first question is never "how does Kubernetes networking work". It is ip route on a node, which tells you which of those four you are dealing with in about two seconds.

Recap

The Kubernetes network model is four requirements, and the expensive one says pods reach each other without address translation. A pod is one network namespace held by a do-nothing sandbox container, which several containers join and share: one address, one port space, localhost between them. Each node gets a PodCIDR slice, so addresses stay unique without coordination and routing needs one entry per node. A capture on the wire between two nodes shows pod addresses raw, and a two-rule masquerade exemption guarantees it. CNI is the contract: an executable, environment variables in, JSON out, with address allocation handed to an IPAM plugin and further plugins chained after. Forty lines of shell make a working plugin. And a real cluster may use no bridge and no overlay at all, because the model fixes the outcome and leaves the mechanism open.

1. Trace the path: a pod at 10.244.1.2 and a pod at 10.244.1.3 sit on the same node, under the ptp plugin shown above. Name every interface a packet between them crosses, and say which netfilter hooks it passes. Then say how the answer changes under a bridge-based plugin.

Answer

Under ptp: out of the sender's eth0, into its node-side veth, up to the node's routing table which matches 10.244.1.3 dev veth9c04d18e scope host, then out of that veth into the receiver's eth0. It is forwarded, so it passes prerouting, forward and postrouting.

The near miss is assuming same-node pod traffic always stays at L2. With ptp there is no shared L2 segment for it to stay on, and the node's routing table sits in the path. That is why ip route on a node is the first command to run: it tells you whether you are debugging a switch or a router.

2. Here is a symptom. Pods on the same node reach each other fine. Pods on different nodes cannot reach each other at all. Every attempt fails at once and completely. Chapter 10

Services: an address that belongs to nobody

~13 min · K8S · The pod-network chapter gave every pod a real address that really works. Pods are also deleted and replaced without warning, and the replacement gets a new address, so nothing can be built on those addresses. This chapter is how Kubernetes works around that, and it is made entirely of the NAT chapter.

Nobody has it

Create a Service and Kubernetes gives it a ClusterIP, from a range reserved for the purpose.

$ kubectl get svc web -o jsonpath='{.spec.clusterIP}'
10.96.212.51

Now go and find it. On a node that is actively serving that Service:

$ ip -br addr | grep -c 10.96.212.51
0

$ ip route get 10.96.212.51
10.96.212.51 via 172.19.0.1 dev eth0 src 172.19.0.3

No interface holds it. And the routing decision from the routing chapter, asked where to send it, falls through to the default route. It would hand the packet to the gateway, which would throw it away as an address nobody has heard of. By every mechanism in the first nine chapters, a packet to a ClusterIP is undeliverable.

It works anyway, because the packet never gets that far. The hooks chapter established that prerouting and output both run before the traffic is committed to an interface, and the NAT chapter established that prerouting is where destinations get rewritten. A ClusterIP is a virtual IP: an address with no owner, which exists only as a match condition in a DNAT rule, and which gets replaced by a real pod address before anything tries to route it.

The component that writes those rules is kube-proxy. It watches the API for Services and EndpointSlices, the objects listing which pod addresses currently back a Service, and rewrites the node's ruleset to match. Despite the name it proxies nothing and sits outside the data path. It is a rule-writing daemon, and once it has written the rules you could stop it and traffic would keep flowing.

The walk, in three chains

Here is the whole thing, captured from a live node. A Service with three backing pods. Start at the top.

-A KUBE-SERVICES -d 10.96.212.51/32 -p tcp --dport 80
    -m comment --comment "default/web cluster IP" -j KUBE-SVC-LOLE4ISW44XBNF3G

One rule per Service, matching its address and port, jumping to a chain named after a hash of the Service. That chain does the choosing.

-A KUBE-SVC-LOLE4ISW44XBNF3G ! -s 10.244.0.0/16 -d 10.96.212.51/32 -p tcp --dport 80
    -j KUBE-MARK-MASQ
-A KUBE-SVC-LOLE4ISW44XBNF3G -m comment --comment "default/web -> 10.244.1.2:80"
    -m statistic --mode random --probability 0.33333333349 -j KUBE-SEP-MQ4W7Q2CV67URU6Q
-A KUBE-SVC-LOLE4ISW44XBNF3G -m comment --comment "default/web -> 10.244.1.3:80"
    -m statistic --mode random --probability 0.50000000000 -j KUBE-SEP-MHDQ23KUGG7EGFMW
-A KUBE-SVC-LOLE4ISW44XBNF3G -m comment --comment "default/web -> 10.244.1.4:80"
    -j KUBE-SEP-OD4NQTAG4GNU2XE5

And the per-endpoint chains do the rewriting.

-A KUBE-SEP-MQ4W7Q2CV67URU6Q -s 10.244.1.2/32 -j KUBE-MARK-MASQ
-A KUBE-SEP-MQ4W7Q2CV67URU6Q -p tcp -j DNAT --to-destination 10.244.1.2:80

That last line is the Service abstraction. Everything else is bookkeeping around one DNAT.

The probabilities, and why they differ

Look at the three probabilities: 0.333..., 0.5, and none at all. That is neither a bug nor weighting. The rules are evaluated in order, and each one gates the traffic that reached it.

RuleTraffic reaching itProbabilityShare of the total
endpoint 1all of it1/31/3
endpoint 2the 2/3 that was not taken1/22/3 × 1/2 = 1/3
endpoint 3the 1/3 that remains1, no test1/3

The rule for the Nth endpoint out of M carries probability 1/(M−N+1), and the last carries none, because everything reaching it has to go somewhere. Add an endpoint and every probability changes, so kube-proxy rewrites the whole chain on any change.

One more detail. The value reads 0.33333333349, where one third would be 0.33333333333. The kernel stores the probability as a 32-bit fixed-point number, so the nearest representable value sits slightly above one third. Over a large number of connections the split comes out very slightly uneven, by about one part in ten billion. It matters to nobody, and it is a good reminder that these are real numbers in a real data structure.

Notice the limits of this load balancing. It is a per-connection random choice with no memory. It does not know how loaded the endpoints are, it does not retry a dead one, and it keeps a client on the same backend only when session affinity is configured. If one of your three pods is wedged but still passing its readiness check, a third of new connections go to a pod that cannot serve them.

The hairpin

Now the case that needs a second rewrite. A pod calls a Service, and the random choice lands on that same pod.

Left alone, the packet becomes source 10.244.1.3, destination 10.244.1.3. The pod receives a connection from itself and replies directly, inside its own namespace, so the packet never passes back through the node and the DNAT never gets undone. The client half of the pod sent to 10.96.212.51 and gets an answer from 10.244.1.3, which matches no connection it opened. The reply is discarded and the connection hangs.

The fix is to send the return trip back through the node by rewriting the source as well. KUBE-MARK-MASQ does that.

-A KUBE-MARK-MASQ    -j MARK --set-xmark 0x4000/0x4000
-A KUBE-POSTROUTING  -m mark ! --mark 0x4000/0x4000 -j RETURN
-A KUBE-POSTROUTING  -j MARK --set-xmark 0x4000/0x0
-A KUBE-POSTROUTING  -j MASQUERADE --random-fully

A mark is a 32-bit number attached to a packet in memory for its trip through the kernel. Nothing goes on the wire. The first rule sets bit 0x4000. Much later, at postrouting, the second rule sends unmarked packets away untouched and the last masquerades whatever is left. Marking and acting are separated because the decision, "this needs masquerading", gets made at a hook where masquerading is not allowed yet.

Here is the result, live. A pod curling its own Service, caught in the connection tracking table.

[NEW] tcp 6 120 SYN_SENT
      src=10.244.1.3 dst=10.96.212.51 sport=53702 dport=80  [UNREPLIED]
      src=10.244.1.3 dst=10.244.1.1  sport=80    dport=6243

Read it with the NAT chapter's method. The original tuple is what the pod sent: to the ClusterIP, from port 53702. A plain swap would give a reply tuple ending at the pod's own address, and both halves differ from that. The source of the reply is 10.244.1.3, so the DNAT chose this very pod. The destination of the reply is 10.244.1.1, the node's address on that veth, so the masquerade fired. Even the port changed, 53702 becoming 6243, which is --random-fully picking a fresh source port to avoid collisions between pods that happened to choose the same one.

Two rewrites, one conntrack entry, both readable in a single line of output. When somebody asks why their pod cannot call its own Service, that line is what you go and look at.

What it costs

Count the rules. One small cluster, one Service of your own, plus the built-in ones.

total nat rules on the worker:  58
of which KUBE-:                48

Forty-eight rules for three Services. The number grows with the number of Services plus the total number of endpoints, and the top-level KUBE-SERVICES chain is a linear list that a packet walks until it matches. At a few hundred Services this is invisible. At tens of thousands it is not, and the cost lands on the first packet of every new connection, which thanks to the NAT chapter is the only packet that pays.

There have been three answers, and which one you meet depends on the cluster's age and configuration.

The project has said the default will move to nftables in a future release, and advises setting the mode explicitly so an upgrade does not change it underneath you. Everything conceptual in this chapter still holds after that change: virtual address, random choice, DNAT, conntrack, hairpin masquerade. Only the data structure holding the rules differs.

A fourth answer discards the premise. Replace kube-proxy with small verified programs loaded into the kernel and attached much earlier in the packet path, so Service resolution happens before most of the stack runs. That is the epilogue's territory.

The name

One loose end, because it is where a Service request starts. Pods are configured to ask a cluster DNS server, which is itself a Service.

$ kubectl exec <pod> -- cat /etc/resolv.conf
search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5

The nameserver is a ClusterIP, so the first packet a pod sends goes through everything in this chapter before any name is resolved. The search list is what lets web mean web.default.svc.cluster.local. And ndots:5 says that any name with fewer than five dots gets tried against every search domain first, so looking up example.com generates four failed queries before the correct one. It is a well-known and frequently rediscovered source of DNS load.

Recap

A ClusterIP is owned by no interface and is not routable. It exists as a match condition in a DNAT rule at a hook that runs before the routing decision. kube-proxy writes those rules and stays out of the data path. The walk is three chains: one rule per Service selects a per-Service chain, which picks an endpoint through a cascade of probabilities, 1/(M−N+1) for the Nth of M, with the last carrying no test. A per-endpoint chain performs the DNAT. Conntrack stores the choice, so a connection stays with its backend and later packets consult no rules. When the chosen backend is the caller, a mark set at one hook triggers a masquerade at another, so the reply comes back through the node and both rewrites can be undone. The whole thing is readable in one conntrack line. Rules grow with Services plus endpoints, which is why ipvs and now nftables modes exist. And a pod's first packet is a DNS query to a ClusterIP, so all of this runs before any name is resolved.

Check yourself

1. Predict the value: a Service has five ready endpoints. Write the probability kube-proxy puts on each of the five rules, in order, and say what share of new connections each endpoint gets.

2. Here is a symptom. A pod reaches every other Service in the cluster. It cannot reach its own Service, the one whose endpoints include itself. Sometimes. Answer

The hairpin masquerade is not being applied. When the random choice lands on the calling pod, source and destination become the same address, the reply is generated inside the pod without passing back through the node, the DNAT never gets undone, and the client discards a reply that matches no connection it opened.

If the reply tuple's destination is still the pod's own address, the masquerade did not happen.

The near miss is blaming DNS or readiness, neither of which would give a failure rate matching the replica count so closely. "One failure in N, where N is the number of endpoints" is close to a signature for the caller being one of the endpoints.

Chapter 11 — epilogue

The whole tower, and one packet through all of it

~8 min · WIRE NETNS FILTER CONTAINER OVERLAY K8S · Our packet has been followed from a program's write() to a container on another machine. This chapter says the whole thing in one sentence, walks it once end to end, and then tells you honestly what was left out.

The sentence

Here is what this document exists to make readable. Every term in it was defined earlier, and you should get through it without stopping.

A curl inside a pod becomes a packet addressed to a ClusterIP that no interface owns; at the output hook a DNAT picks a real pod at random, and conntrack writes that choice into a reply tuple so it can be undone; only then does the routing decision run, sending the packet out of a veth into the node's routing table and across the underlay, wrapped in VXLAN or carried bare depending on what the network was willing to learn; and it arrives with its source address untouched, inside a namespace held open by a container that does nothing.

The tower

The walk

One curl http://web/, from a pod on node 1 to a pod on node 2, start to finish.

What this document left out

Six things, each real, each skipped on purpose, and each one you now have the vocabulary to go and read about.

IPv6. Everything here was IPv4. The concepts all still hold. Prefixes get longer, ARP gives way to a mechanism called neighbour discovery that does the same job with multicast instead of broadcast, and Kubernetes supports running both families at once. The netfilter hooks, conntrack, veth, bridges and VXLAN are unchanged. What changes is that address scarcity stops being a reason for NAT, so a dual-stack cluster often does no masquerading at all on the IPv6 side.

NetworkPolicy. Kubernetes defines an object for saying which pods may talk to which. Kubernetes does not implement it. The network plugin does, and a cluster whose plugin lacks support will accept your policy objects and silently enforce nothing. That is the most dangerous gap in this list. Where a plugin does implement it, the result is rules at the hooks chapter's hooks, matching on addresses the plugin knows belong to particular pods.

Ingress and the Gateway API. Everything here stayed inside the cluster. Getting traffic in from outside involves NodePort and LoadBalancer Services, which are more DNAT, and then a proxy that understands HTTP and can route on hostnames and paths. That is a different kind of object, working on the conversation instead of the packet.

Service mesh. A sidecar container in the pod, plus a redirect rule, the NAT chapter's fourth NAT operation, sending the pod's own traffic to that sidecar before it leaves. Once you know redirect exists and that containers in a pod share a namespace, the mechanism is plain. The complexity all sits in the policy layer above.

BGP and routed clusters. The overlay chapter's first option, taken seriously. Instead of encapsulating, run a routing protocol between your nodes and your physical routers so the underlay learns every PodCIDR. Calico does this in its default mode. It beats any overlay for speed, because nothing gets added to any packet, and it requires a relationship with whoever runs the network.

The hardware floor. SR-IOV, DPDK and kernel-bypass generally: giving a container a slice of a real NIC and taking the kernel out of the data path. Everything from the namespace chapter onwards is a cost, and at tens of gigabits per second that cost becomes the whole problem.

Where this went next

Two developments matter here, because they change the answers without changing the questions.

eBPF. Instead of registering rules at netfilter's five hooks, you can load a small verified program into the kernel and attach it much earlier, at the driver, before most of the stack has run. Cilium uses this to replace kube-proxy: the Service lookup becomes a hash-table lookup in a program attached near the NIC, and the Services chapter's chain walk never happens. The conceptual model still holds. There is still a virtual address, still a choice of backend, still a reverse translation on the way home. But none of the Services chapter's transcripts would appear on such a node, and iptables-save would show you almost nothing. If you ever meet a cluster whose Services work and whose ruleset is empty, this is the reason.

nftables everywhere. The kube-proxy mode from the Services chapter is the visible part of a slow migration off the older interface. Rule sets are becoming lookup structures instead of lists, which removes the scaling problem instead of working around it.

Both reward exactly the knowledge in this document. What makes a cluster network debuggable is not knowing which tool wrote the rules. It is knowing that a packet gets rewritten in at most three places, that the routing decision runs between two of them, and that a conntrack entry will tell you what happened to any flow you can name.

Recap

One packet leaves a pod as a segment inside a packet addressed to nobody. A random choice at a hook that runs before routing redirects it. Connection tracking remembers the redirection so it can be undone. The packet is then routed on its real destination to a node that owns that slice of the address space, crosses the underlay wrapped or bare depending on what the network was willing to learn, and arrives with its source untouched, because the model forbids anything else. Only three components rewrite addresses. Everything else reads, decides and forwards. What was skipped, IPv6, policy, ingress, mesh, routed clusters and hardware bypass, is reachable from here. What came next, eBPF and native nftables, moves where the rules live without changing what they have to accomplish.

Check yourself

1. Trace the path: a pod calls a Service whose only endpoint sits on another node. Name, in order, every point at which an address or a header field changes, and say which of them the destination pod can detect.

Answer

Three changes, and the destination pod detects none of them. At the output hook the destination goes from the ClusterIP to the pod address. At postrouting the masquerade rule is consulted and declines, because the destination sits inside the pod subnet, so the source is left alone. On the node's uplink the whole frame may get wrapped in a VXLAN datagram, and wrapping leaves the inner packet's TTL alone.

The destination sees the caller's real pod address and its own address as the destination, which is what it would see on a direct pod-to-pod connection. The pod-network chapter's cross-node capture is the evidence.

The near miss is expecting the destination to see the ClusterIP. It never appears on the wire past the first hook. The backend has no idea it was reached through a Service, and that is why a backend cannot log which Service name a client used.

2. Here is a symptom, and it is the last one. A cluster works. Pods reach each other across nodes, Services resolve and balance correctly. Then somebody runs iptables-save on a node to audit the rules and finds almost nothing: no KUBE-SERVICES, no KUBE-SVC- chains, nothing resembling the Services chapter. Nothing is broken. What is this cluster running, and what would you run instead to see the Service configuration?

Answer

An eBPF-based data path, almost certainly Cilium with kube-proxy replacement enabled. The Service lookup happens in a program attached near the driver, so no netfilter rules get created for it and iptables-save has nothing to show.

Inspect it with the plugin's own tooling. For Cilium that is cilium service list inside the agent pod, which prints the same virtual-address-to-backends mapping the chains encoded. Checking whether kube-proxy runs on the node at all is the quickest first confirmation.

The near miss is deciding the cluster is misconfigured and "fixing" it by installing kube-proxy, which would put two implementations of the same Service semantics on one node. The give-away is that everything works. An empty ruleset alongside working Services means the work happens somewhere iptables-save cannot see.

Glossary

Every term this document defines, grouped by the chapter that introduced it, in reading order. The wording matches each chapter's own list.

The prologue — two programs, one wire

interface
A named place where the kernel takes bytes to send and delivers bytes that arrived. It may or may not have hardware under it.
NIC
Network interface card: the hardware behind an interface that has hardware.
link
What an interface reaches directly, with nobody forwarding on its behalf.
header
A fixed set of agreed fields at the front of a message, read by the machinery that handles it.
payload
Everything after the header. Cargo, to the layer carrying it.
encapsulation
Making one layer's complete message into the next layer's payload. Envelopes inside envelopes.
frame
The L2 envelope. It crosses one link.
packet
The L3 envelope. It crosses many links and keeps its addresses the whole way.
segment
The L4 unit: one piece of a conversation between two programs.
L2 / L3 / L4
Layer 2, 3 and 4: one hop, end to end, and conversation. A way of filing ideas.

The frame chapter — the frame, the MAC and ARP

MAC address
Six bytes naming an interface on one link. It means nothing beyond that link.
unicast
Addressed to one interface.
broadcast
Addressed to ff:ff:ff:ff:ff:ff. Every interface on the link must accept it.
multicast
Addressed to a subscribed group.
broadcast domain
The set of interfaces a broadcast frame reaches. The boundary between reaching something by broadcast and needing a router.
EtherType
Two header bytes naming the payload's kind. 0x0800 IP, 0x0806 ARP.
MTU
Maximum transmission unit: the largest payload one frame will carry on this interface. Usually 1500.
ARP
Address Resolution Protocol. Broadcast question, unicast answer, mapping an L3 address to a MAC address.
neighbour table
The kernel's cache of those mappings, with states such as REACHABLE, DELAY and INCOMPLETE.

The routing chapter — the prefix and the routing decision

IP address
32 bits identifying a machine anywhere, instead of an interface on one link.
TTL
Time to live: a hop counter, decremented by every forwarder, discarded at zero. Loop insurance.
prefix length
The /24 in 192.168.1.110/24: how many leading bits are the network part.
netmask
The same information written as an address with the fixed bits set to 1.
subnet
The block of addresses a prefix describes.
CIDR
Classless inter-domain routing: the notation that lets the network and host split fall at any bit.
routing table
The kernel's list of prefixes and what to do with packets matching them.
longest prefix match
Among matching entries, the one with the most fixed bits wins.
default route
0.0.0.0/0: it matches everything, so it loses to everything.
next hop
A machine on this link that will carry the packet onward. The via in a route.
on-link
Reachable directly, with no next hop. Shown as scope link.
forwarding
Accepting a packet addressed to somebody else and sending it on. Gated by net.ipv4.ip_forward.

The namespace chapter — namespaces and veth

network namespace
A complete independent copy of the kernel's network state. Often shortened to netns.
container
A process started with its own set of namespaces, including a network namespace. No virtual hardware involved.
veth pair
Two interfaces created together and permanently wired to each other. A virtual cable.
peer
The other end of a veth pair. Named in the interface's @ifN suffix.
administrative state
Whether you asked the interface to work. Shown as the UP flag.
operational state
Whether it can. NO-CARRIER means nothing is plugged in at the far end.

The bridge chapter — the bridge

bridge
A software switch: a virtual device that forwards frames between the interfaces attached to it.
bridge port
An interface attached to a bridge, by setting the bridge as its master.
learning
Recording which port a source MAC address was last heard on.
flooding
Sending a frame out of every port but the one it arrived on, because the destination is unknown or is a broadcast.
FDB
Forwarding database: the bridge's MAC-address-to-port table. Learned entries age out; permanent ones do not.
ageing time
How long a learned FDB entry lasts without being refreshed. Default 300 seconds.
STP
Spanning Tree Protocol: loop detection between switches. Off by default on a Linux bridge, and correctly so for container use.

The hooks chapter — netfilter

netfilter hook
One of five fixed points in the kernel's packet path where registered code may inspect and decide.
prerouting / input / forward / output / postrouting
The five, named by position relative to the routing decision.
nftables
The modern configuration interface for netfilter, driven by the nft command.
table
A named container for chains, with an address family.
chain
An ordered list of rules.
base chain
A chain attached to a hook, declaring hook, priority and policy.
priority
The ordering number among chains on the same hook. Lower runs first. It has conventional names.
policy
The verdict for packets that reach the end of a base chain unmatched.
verdict
What a rule does: accept, drop, jump, or counter and continue.
iptables-nft
An iptables command that writes nftables rules. Identified by (nf_tables) in its version string.
br_netfilter
The module that makes bridged frames traverse the IP hooks. Gated by net.bridge.bridge-nf-call-iptables.

The NAT chapter — conntrack and NAT

conntrack
The kernel's table of in-progress flows. The memory that makes address rewriting reversible.
tuple
The fields identifying one direction of a flow: protocol, addresses, and ports.
original tuple
How the first packet of the flow looked.
reply tuple
What a returning packet must look like to belong to this flow. It differs from a plain swap by the rewriting applied.
state
new, established, related or invalid. What stateful rules match on.
SNAT
Source address rewriting to a specified address, at postrouting.
masquerade
SNAT that uses whatever address the outgoing interface currently holds.
DNAT
Destination address and port rewriting, at prerouting.
redirect
DNAT whose target is this machine.

The Docker chapter — container networking

published port
A DNAT rule at prerouting mapping a host port to a container address and port. No proxy involved.
DOCKER-USER
The chain Docker evaluates before its own rules and promises not to modify. Where your policy belongs.
macvlan
A virtual interface on a real NIC with its own MAC address. Real subnet, no NAT, unreachable from its own host.
ipvlan
The same idea sharing the parent's MAC address, telling children apart by IP. For links that will not tolerate extra MACs.
host mode
Running a container in the host's own network namespace. It gives up isolation and address rewriting, and port conflicts become real again.

The overlay chapter — the overlay

underlay
The real network between machines, which carries the encapsulated traffic and knows nothing about it.
overlay
The virtual network built on top, whose addresses exist only inside the tunnel.
VXLAN
Virtual eXtensible LAN: a complete Ethernet frame inside a UDP datagram on port 4789.
VNI
VXLAN Network Identifier. 24 bits separating independent overlays on one underlay.
VTEP
VXLAN Tunnel End Point: the thing that wraps and unwraps. On Linux, an interface.
onlink
A route flag meaning "treat this next hop as directly reachable even though nothing else says it is".
PMTU
Path MTU: the smallest MTU anywhere along a path, and therefore the real limit.

The pod-network chapter — the pod network

pod
One network namespace with one address, shared by one or more containers.
sandbox container
Also called the pause container. Does nothing, and holds the pod's namespace and address across restarts.
PodCIDR
The slice of the cluster's pod subnet allocated to one node.
CNI
Container Network Interface: the contract between a runtime and the program that wires a pod.
CNI plugin
An executable that reads environment variables and JSON on stdin and prints a result on stdout.
IPAM
IP address management: the separately-delegated job of choosing an address. host-local is the common implementation.
plugin chaining
Running several plugins in order, each on the previous one's result. How portmap adds host ports.
ptp
A CNI plugin that gives each pod its own veth pair with no shared bridge, using host-scope routes.

The Services chapter — Services

Service
A stable name and address for a set of pods that changes over time.
ClusterIP
The Service's virtual address, from a reserved range, owned by no interface.
virtual IP
An address that exists only as a match condition in a rule, never assigned to anything.
kube-proxy
The daemon that watches the API and writes the node's Service rules. Outside the data path.
EndpointSlice
The object listing which pod addresses currently back a Service.
mark
A number attached to a packet in memory for its trip through the kernel. Never transmitted.
hairpin
A pod reaching a Service whose chosen backend is itself. It needs a source rewrite to work at all.
session affinity
Optional configuration keeping one client on one backend. Off by default.

The epilogue — epilogue

neighbour discovery
IPv6's replacement for ARP. Same job, multicast instead of broadcast.
NetworkPolicy
A Kubernetes object describing permitted pod-to-pod traffic. The network plugin implements it, and a plugin without support ignores it silently.
eBPF
