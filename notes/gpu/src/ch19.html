Chapter 19

Observing inference: where the probes go

@@RT@@ · LLM EBPF TOOLS — The last two chapters ran one model in two servers. This one puts the whole document to work on them. It follows one request down through the layers that can observe it, writes a probe for the layer that sees each step, and then answers the question this document set out with: where can an eBPF program on the GPU go in a real inference server? Part of the answer is uncomfortable. In a stock vLLM install, almost no kernel can take a bpftime probe.

This chapter skips dashboards, alerting and distributed tracing back ends, and multi-GPU serving. Its two scripts have been checked against the source and the calling convention, but not run; the epilogue lists them with the other bench tests.

One request, five layers

Diagram 19.1 is one streaming request on a time axis: it waits in a queue, is prefilled in two chunks, and then gets one token per decode step. Under it are the five layers that can observe it, from the network down to the GPU. Each row marks what that layer sees.

vLLM's spans carry the same split as its metrics, per request: time in queue, time to first token, and time in model prefill and decode (vllm/tracing/utils.py:34–44). On one GPU, vLLM runs the model inside the engine-core process, titled VLLM::EngineCore (vllm/config/parallel.py:1040–1041, vllm/v1/engine/core.py:1370–1371, vllm/utils/system_utils.py:179–194), so that is the process the driver and GPU rows attach to.

A probe for each step

For llama.cpp, the step loop is a C function with a stable name, which makes it the best single place to probe. At this commit the programs submit a step with llama_process(ctx, LLAMA_PROCESS_TYPE_DECODE, batch): llama-server at tools/server/server-context.cpp:3682, llama-bench at tools/llama-bench/llama-bench.cpp:2186. The older llama_decode converts its batch and ends in the same method (src/llama-context.cpp:4383–4386, 4401–4404 and 4477–4483). One detail decides where the probe's end goes. The call returns before the GPU has finished: it queues the step and an asynchronous copy of the logits (line 1948), and the wait happens in llama_synchronize, which the server calls right after (server-context.cpp:3682–3685) and the sampler calls before it samples (common/sampling.cpp:594). So a step runs from llama_process's entry to the return of the next llama_synchronize on the same thread.

// llama_step.bt: one llama.cpp step, from llama_process(..., DECODE, ...)
// to the return of the llama_synchronize that waits for it.
// Run from ~/workspace/repos/llama.cpp.
uprobe:./build/bin/libllama.so:llama_process
/arg1 == 1/                 // LLAMA_PROCESS_TYPE_DECODE
{
	@t0[tid] = nsecs;
}

uretprobe:./build/bin/libllama.so:llama_synchronize
/@t0[tid]/
{
	@step_us = hist((nsecs - @t0[tid]) / 1000);
	delete(@t0[tid]);
}

Listing 19.1 — A step-time histogram for llama.cpp. Not yet run; it needs root.

The highlighted predicate keeps decode calls: arg1 is the second argument, the process type, and LLAMA_PROCESS_TYPE_DECODE is 1 (include/llama.h:296–299). Prefill and decode steps land in the same histogram as two clusters, decode steps near the bandwidth floor and prefill micro-batches far above it. The batch size itself now sits inside an opaque llama_batch_ext, so the script does not key by it. The probe works with or without CUDA graphs, with or without PTX, and on all three benches, because nothing in it touches the GPU.

For vLLM, the driver row gives the same signal. A pure-decode step is one replay of a full CUDA graph, so the gaps between graph launches in the engine-core process are the step times:

// vllm_graphs.bt: run as
//   sudo bpftrace vllm_graphs.bt (pgrep -f VLLM::EngineCore)
uprobe:/usr/lib/libcuda.so.1:cuGraphLaunch*
/pid == $1/
{
	if (@last) { @gap_us = hist((nsecs - @last) / 1000); }
	@last = nsecs;
}

Listing 19.2 — Gaps between CUDA graph launches in vLLM's engine core. Not yet run. libcuda.so.1 615.71.09 exports both cuGraphLaunch and cuGraphLaunch_ptsz, which the wildcard catches.

A mixed step replays one piecewise graph between each pair of attention layers, so its gaps are short and many. Expect the histogram to have two humps: steps, and pieces within steps.

Where a GPU probe can go

The bottom row of diagram 19.1 is where this document's eBPF lives, and it is the row with the most conditions. The attach-pipeline chapter (chapter 13) listed them: the kernel must arrive in a fat binary that bpftime sees being registered, it must carry PTX, it must be launched through one of the three launch functions bpftime replaces, and if it runs inside a CUDA graph, the graph must have been captured after the probe was attached. Here is what a serving stack ships.

So the honest summary is this. In llama.cpp built from source with PTX, almost every kernel can take a probe, and the probe-cost chapter's per-SM tail measurement (chapter 14) should work on mul_mat_vec_q as it did on the matvec, though it has not been run there yet. Its instances are C++ templates, so a probe names one by the mangled name that cuobjdump -symbols lists. In a stock vLLM install, the GPU row belongs to NVIDIA's own tools, and eBPF works in the four rows above it. Reaching vLLM's kernels with bpftime means rebuilding them with PTX, and reaching Triton's would need bpftime to hook cuModuleLoadData and cuLaunchKernelEx, and to get PTX from Triton's compile cache instead of the loaded image. That is a concrete extension, of the kind the finish line of this document asked for: adding an attach path to bpftime.

Try it

With the dGPU in Hybrid mode, start a llama-server with 4 slots on the Q8_0 file from ~/workspace/repos/llama.cpp, and attach listing 19.1 from the same directory in a second terminal:

./build/bin/llama-server -m qwen2.5-0.5b-instruct-q8_0.gguf \
    -np 4 -c 16384 --metrics
sudo bpftrace llama_step.bt

Send one request, then four at once, each asking for a few hundred tokens:

for i in 1 2 3 4
    curl -s localhost:8080/completion \
        -d '{"prompt": "Tell a story.", "n_predict": 300}' >/dev/null &
end

That loop is fish syntax. Run the probe once for a single request and once for the four, and before each, predict the decode cluster's step time from the first question below. Then compare the single-request cluster with llama-bench's tg128 from the llama.cpp chapter: the two should be close, since both time one token's step.

Recap

Five layers can observe a request: the socket, the server's own metrics and traces, the step loop, the driver, and the GPU. Only the socket sees what the user sees, and only the GPU layer sees inside a step. llama.cpp's step can be timed from llama_process's entry to the return of llama_synchronize, because the call itself returns before the GPU finishes; vLLM's from the gaps between CUDA graph launches in its engine-core process. A bpftime probe needs PTX, a hooked registration and launch, and a graph captured after attach. llama.cpp built from source meets all four; stock PyTorch, vLLM, cuBLAS, Triton and FlashAttention 3 kernels miss at least one, which leaves stock vLLM to host-side eBPF and NVIDIA's tools.

New words in this chapter

observation layer
One level of the stack a probe can attach to: socket, server, step loop, driver or GPU.
step probe
A probe that times each run of the model, from submission to the wait for its result.
reachable kernel
A kernel a bpftime probe can patch: PTX, a hooked registration and launch, and a graph captured after attach.

Check yourself

1. Predict the value: in the Try-it, one slot is generating with about 1,000 tokens of context, and then four slots are, each with about 1,000. Using the bandwidth floor alone, how long is a decode step in each case on the laptop, and how many tokens per second does the server produce?

Answer

About 2.5 ms and 2.7 ms, so about 400 and 1,500 tokens per second. A step reads the 525 MB of weights once, whatever the batch, plus each slot's cache: 1,000 tokens × 12,288 bytes ≈ 12 MB per slot in F16. One slot moves about 537 MB, 2.5 ms at 216 GB/s; four move about 574 MB, 2.7 ms, and produce four tokens per step.

Four users cost each other about 7% here, because the weights dominate and are shared; mul_mat_vec_q takes up to 8 columns and reads each weight block once for all of them. The near-miss is to expect the step to take four times as long.

2. A bpftime probe on a vLLM attention kernel loads without errors and never fires. Give three causes in the order you would check them, and how to check each.

Answer

First, the kernel has no PTX or never passes through bpftime's registration hook: run cuobjdump --list-ptx on the library it lives in, and if it is a Triton kernel, it was loaded with cuModuleLoadData as a cubin. Second, it is launched through a call bpftime does not replace: a uprobe on cuLaunchKernelEx* in libcuda.so.1 shows whether it fires.

Third, the kernel runs inside a CUDA graph captured before the probe was attached, which vLLM does at start-up; restart the server with the agent loaded. On an H100, FlashAttention 3's sm_90a code is a fourth cause. The near-miss is to suspect the eBPF program itself, which loaded fine.

3. A client measures a 99th-percentile ITL of 120 ms. The server's vllm:inter_token_latency_seconds says 30 ms. Where can the other 90 ms come from, and which layer settles it?

Answer

From between the engine and the client: the API server falling behind in turning tokens into chunks, a proxy that buffers the stream, or TCP holding small writes back, for example Nagle's algorithm waiting on a delayed acknowledgement. The engine's metric stops at the engine, before any of these.

The socket layer settles it. Timestamps of tcp_sendmsg on the server's connection show whether chunks leave every 30 ms. If they do, the delay is in the network or the proxy; if they leave in clumps, it is the API server. The near-miss is to tune the GPU, whose steps are already 30 ms.
