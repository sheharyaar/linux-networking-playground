Chapter 13

Getting inside someone else's kernel

@@RT@@ · EBPF ISA — The last chapter ended with a handler in shared memory: a kprobe on _Z11matvec_warpPKfS0_Pfii, and the eBPF bytecode to run there. This chapter follows that handler until the probe is running inside every thread of our kernel. Nine steps, all in the target process, most of them before main. Every one of them uses something from the language part (Part II).

The plan: edit the PTX, compile it again, swap the function

bpftime cannot change a kernel that is already loaded on the GPU, and it does not try to edit SASS. Instead it makes a second copy of the kernel with the probe built in, and arranges for launches to use the copy. The copy is made from the kernel's PTX, which the compiler chapter showed is stored in the fatbin next to the SASS. PTX is a documented text language, so a probe can be inserted with string edits, and ptxas then does the hard parts: register allocation and instruction scheduling for the kernel and the probe together.

Steps 1 and 2: catching the fatbin

The agent's GPU attach implementation installs Frida listeners on the runtime's registration functions: __cudaRegisterFatBinary, __cudaRegisterFunction, __cudaRegisterVar and __cudaRegisterFatBinaryEnd (bpftime/attach/nv_attach_impl/nv_attach_impl.cpp:369–390). It finds the first one with dlsym(RTLD_NEXT, …), which works only when the program uses the shared CUDA runtime. That is why every bpftime GPU example builds with nvcc -cudart shared. A statically linked runtime keeps these functions as local symbols, as the compiler chapter found with nm.

When a registration arrives, the listener walks the fatbin's entries, each starting with the magic number 0xBA55ED50, copies the bytes, and extracts every PTX entry (bpftime/attach/nv_attach_impl/nv_attach_impl_frida_setup.cpp:254–290). The SASS entries are ignored. If the fatbin has no PTX, there is nothing to patch, and the kernel runs unprobed.

There is a second way in, for programs that were already running or registered their fatbins before the probe was attached. When a probe is attached, bpftime starts a background scan of every ELF module loaded in the process, looking for .nv_fatbin and .nvFatBinSegment sections (nv_attach_impl.cpp:1800, started at line 227). Until that scan finishes, launches use the original kernels (nv_attach_impl_frida_setup.cpp:509–512). So the first launches after a late attach are not probed.

Step 3: the passes

The editing is done by passes, small shared libraries that bpftime loads with dlopen. Each exports two functions, print_config and process_input, and its configuration says which handlers it serves: the kprobe_entry pass takes section names matching ^kprobe/.*$ and attach type 8, the kretprobe pass takes ^kretprobe/.*$ and type 9 (bpftime/attach/nv_attach_impl/configs/ptxpass/kprobe_entry.json). For each probe and each kernel it names, bpftime sends the pass a JSON request: the whole PTX file, the kernel's name, the eBPF instructions, and the names of two symbols that the probe will need. The pass answers with new PTX. Answers are cached by the SHA-256 of the request (nv_attach_impl.cpp:889–1046).

The entry pass does two things (bpftime/attach/nv_attach_impl/pass/ptxpass_kprobe_entry/main.cpp:45–97). First it compiles the eBPF program with llvmbpf into a PTX function called __probe_func__ followed by the kernel's name, for target sm_61. Then it finds the kernel's body and inserts a call to that function just after the opening brace. The exit pass compiles its program the same way and inserts a call before every ret or exit in the body, keeping any predicate and any label on that line, so that branches to the epilogue still pass through the probe (pass/ptxpass_kretprobe/main.cpp:37–64). Here is what the two rules do to the real PTX of matvec_warp:

.visible .entry _Z11matvec_warpPKfS0_Pfii(
	.param .u64 _Z11matvec_warpPKfS0_Pfii_param_0,
	…
	.param .u32 _Z11matvec_warpPKfS0_Pfii_param_4
)
{
    call __probe_func___Z11matvec_warpPKfS0_Pfii;
	.reg .pred 	%p<13>;
	…
	setp.ge.s32 	%p1, %r2, %r14;
	@%p1 bra 	$L__BB1_10;      // rows past the end
	…
	setp.ne.s32 	%p12, %r3, 0;
	@%p12 bra 	$L__BB1_10;      // lanes 1-31 skip the store
	…
	st.global.f32 	[%rd35], %f8;

$L__BB1_10:
	call __retprobe_func___Z11matvec_warpPKfS0_Pfii;
	ret;
}

Listing 13.1 — lab/gpu/out/matvec.sm_89.ptx:119–261, with the two passes' text rules applied by hand. The bold lines are inserted; the two probe functions themselves are prepended to the file. This was not captured from a bpftime run; the bench test will produce the real file.

The kernel has one ret, and every early exit branches to the label in front of it. So the exit probe runs in all 131,072 threads, including the 31 lanes per warp that skip the store, and the entry probe runs in all of them too. A probe on a kernel is a probe on each of its threads.

The probe functions take no parameters. A kernel probe in the Linux kernel gets the registers of the probed function in its context argument. Here the call passes nothing, so the probe cannot read the kernel's arguments, such as the pointer to W or the value of n. What it can read comes from helpers: indices, the timer and the special registers. A third pass, kprobe_memcapture, adds a probe at every load and store for memory tracing, which is a different and much heavier tool.

Steps 4 to 6: trampoline, compile, load

The probe functions call helpers by name, _bpf_helper_ext_0502 and so on, and read two globals: constData, the GPU address of the request area in the shared segment, and map_info, a table describing up to 1,024 maps. All of these are defined in the trampoline, a CUDA file (trampoline/default_trampoline.cu) compiled to PTX and committed to the repository as a C string in trampoline_ptx.h. bpftime prepends that PTX to the patched file (bpftime/attach/nv_attach_impl/nv_attach_utils.cpp:19–22). Listing 6.3, the spinlock at the heart of helper calls, is from it.

Then the file is compiled for the GPU it will run on. bpftime rewrites the PTX's .target line to the detected architecture, sm_89 on the laptop, and compiles it with NVIDIA's PTX compiler library at -O3 (bpftime/attach/nv_attach_impl/nv_attach_fatbin_record.cpp:103–188). This is ptxas in library form. It allocates registers for each kernel and the probe it now calls, so the patched kernel can need more registers than the original, with the occupancy consequences of the scheduling chapter. Finally cuModuleLoadDataEx loads the result as a second module in the program's context, and bpftime copies the request-area address and the map table into the module's constData and map_info (nv_attach_fatbin_record.cpp:229–268). The original module is untouched, and both now exist side by side.

Steps 7 to 9: swapping the function at launch

The last step happens at every launch. bpftime replaces cudaLaunchKernel, cudaLaunchKernel_ptsz and cuLaunchKernel with its own versions, and hooks the graph-node calls that the host-side chapter described (nv_attach_impl.cpp:421–450). For a driver launch, its version finds the name of the CUfunction being launched, looks for a patched function with the same name, and if there is one, launches that instead, with the same grid, block and arguments (nv_attach_impl_frida_setup.cpp:489–527). Runtime launches are matched by the host stub's address, which step 1 recorded with the kernel's name, and relaunched through cuLaunchKernel with the patched function (nv_attach_impl_frida_setup.cpp:165–192). The patched kernel has the same parameter list as the original, because the probe lives inside the body, so the arguments fit unchanged.

Recap

bpftime makes a probed copy of a kernel and swaps it in at launch. Frida listeners on the registration functions catch each fatbin, which needs the shared CUDA runtime, and a late scan of loaded modules covers fatbins registered earlier. Only PTX entries are used: passes loaded with dlopen insert call __probe_func__<kernel> after the body's opening brace and call __retprobe_func__<kernel> before each ret or exit, with the probe compiled by llvmbpf for sm_61. The trampoline PTX adds the helpers and two globals; the file's target is rewritten to the device's, it is compiled with the PTX compiler library, and loaded as a second module. Launch hooks swap the CUfunction by name, with the same arguments; every thread runs both probes, and the probes cannot see the kernel's arguments.

New words in this chapter

pass
A bpftime plug-in, loaded with dlopen, that rewrites PTX for one kind of attach point.
trampoline
bpftime's PTX library of helpers and globals, prepended to every patched file.
late attach
Attaching after fatbins were registered, by scanning loaded ELF modules for them.
launch redirect
Replacing the launched CUfunction with the patched one of the same name.

Check yourself

1. Predict the value: after patching, ptxas reports 48 registers per thread for matvec_warp instead of 40. With 256-thread blocks on the laptop, how many blocks and warps fit per SM now, and how many waves does the 512-block launch take?

Answer

5 blocks, 40 warps, and 5.12 waves. A block needs 48 × 256 = 12,288 registers, and 65,536 / 12,288 = 5.33, so 5 blocks fit, against 6 before. That is 40 of 48 warps, 83% occupancy. 512 / (5 × 20) = 5.12 waves, against 4.27, so the launch now has six rounds, the last one almost empty.

For a memory-bound kernel, 40 warps may still hide latency well, so the time may barely change. The point is that a probe can cost time without executing a single slow instruction, by changing how the original kernel fits. The near-miss is to count only the probe's own instructions as its cost.

2. Your probe on a cuBLAS GEMV kernel, called from the lab program, never fires, while the same probe on matvec_warp works. Give three causes from this chapter that could explain it, and the order in which you would check them.

Answer

First the name: cuBLAS kernels have long templated C++ names, so copy the real one from cuobjdump -symbols. Second, PTX: run cuobjdump -lptx on the library. On this laptop's CUDA 13.4, every PTX entry in libcublas.so is for sm_120, and the SASS covers sm_75, 80, 86, 90, 100 and 120, so the laptop runs sm_86 SASS. bpftime would have to retarget sm_120 PTX to sm_89 by rewriting its .target line, which compiles only if those kernels use nothing newer. Third, the loading path: if cuBLAS loads its kernels through the driver without registering them, the registration hooks never see them, and only the late scan of loaded modules could.

The first two checks need no GPU. Whether cuBLAS's kernels are reachable at all is a bench test for this document. The near-miss is to blame the probe code, which ran fine on the other kernel.

3. NVBit edits SASS; bpftime edits PTX. Give one thing bpftime's choice buys and one thing it costs, with a concrete example of each from this chapter.

Answer

It buys a stable, documented language and a real compiler for the combined code. The pass inserts one line of text, and ptxas allocates registers and schedules the kernel and the probe together, for whichever generation is present, the same pass on Pascal, Ada and Hopper. NVBit has to work in each generation's undocumented SASS and save and restore state around each inserted call.

It costs the dependency on PTX and a recompile. A library that ships only SASS cannot be probed, the patched kernel's register allocation can change (question 1), and every patched module is compiled at start-up. The near-miss is to call one approach better. They make different trade-offs, which diagram 10.3 placed on either side of ptxas.
