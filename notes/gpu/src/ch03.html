Chapter 3

Memory and the bandwidth wall

@@RT@@ · HW — Last chapter put our matvec's warps on SMs and showed the SM hiding the wait for memory by switching warps. Hiding the wait does not shorten it. This chapter follows the 64 MiB of W from memory to the lanes, and ends with a number: the shortest time our matvec can possibly take on each bench.

Optional neighbour: The silicon (chapter 1) of the GPU-sharing dossier shows where the L2 slices and memory controllers sit on the die. This chapter only needs to know that they exist and how fast they are.

The ladder

A GPU has the same kind of memory ladder as a CPU, with a different emphasis. At the top are registers, private to one thread and free to use. Below them is the SM's 128 KB pool, split between L1 cache and shared memory. Below that is the L2 cache, one cache for the whole chip, shared by every SM. At the bottom is the global memory: the GPU's own DRAM, gigabytes of it, visible to every thread of every kernel. W lives there.

Two kinds of DRAM appear in our benches. GDDR (graphics double data rate) memory sits as separate chips on the board around the GPU. The laptop has 6 GB of GDDR6 on a 96-bit bus and the P5000 has 16 GB of GDDR5X on a 256-bit bus. HBM (high-bandwidth memory) is stacks of DRAM dies placed in the same package as the GPU, with a very wide bus. The H100 has 80 GB of HBM3 on a 5,120-bit bus. Bus width is most of the difference in speed between these three.

Two more names refer to places in that same DRAM, treated specially. Local memory is per-thread storage that lives in global memory. The compiler uses it when a thread's variables do not fit in registers. Constant memory is a small read-only region, 64 KB, with its own cache that is fastest when every lane of a warp reads the same address. The kernel's arguments are placed there, which is why the machine code in a later chapter reads the pointer W from c[0x0][0x160] and the size n from c[0x0][0x178]: bank 0 of constant memory, at fixed offsets.

Sectors, and why neighbouring lanes should read neighbouring bytes

Memory is never fetched one float at a time. The unit of transfer between DRAM, L2 and L1 is a sector of 32 bytes. Caches track memory in cache lines of 128 bytes, four sectors each. When a warp issues a load, the load/store unit collects the 32 lanes' addresses and works out which sectors they touch, then fetches each sector once. If neighbouring lanes read neighbouring 4-byte floats, 32 lanes touch exactly four sectors, one cache line, and every byte fetched is used. That is a coalesced access, and getting it is called coalescing.

Our two matvec kernels differ in exactly this. In the warp-per-row kernel, lane i of the warp reads W[row][j + i]: thirty-two neighbours. In the naive thread-per-row kernel, lane i is working on row row + i, so the warp's 32 addresses are 4096 × 4 = 16 KiB apart. Each lane lands in a different sector. One warp-wide load now fetches 32 sectors, 1,024 bytes, to deliver 128 useful bytes.

The naive kernel is saved partly by that last sentence. The same lane reads the next float of its row on the next iteration, which is in the sector it already fetched. If the sector is still in L1, the read is cheap. With dozens of resident warps each pulling 32 different lines through a 128 KB pool, many sectors are evicted before they are used again, and the extra traffic is real. How much it costs is a measurement, and the lab program makes it.

Shared memory has a different rule. It is split into 32 banks, each 4 bytes wide, and consecutive 4-byte words sit in consecutive banks. A warp can read 32 words in one go if they are in 32 different banks. If two lanes want different words in the same bank, that is a bank conflict, and the accesses to that bank are done one after another. The classic case is a warp reading one column of a 32 × 32 float tile: every element of a column is in the same bank, so a single read becomes 32. Our matvec does not use shared memory. The attention kernels of the language-model chapters do.

Bandwidth, and how many FLOPs a byte buys

Bandwidth is how many bytes per second a level of memory can deliver. Peak DRAM bandwidth is the bus width times the transfer rate. The H100's datasheet says 3,352 GB/s and the P5000's says 288 GB/s. NVIDIA does not publish a figure for the laptop chip, but 96 bits at 18 Gbit/s per pin gives about 216 GB/s, and the lab program will confirm the real one. A real kernel reaches perhaps 80 to 90% of peak.

Arithmetic is counted in FLOP, floating-point operations, and its rate in FLOPS, per second. A multiply-add counts as two FLOP. The laptop has 2,560 FP32 lanes at up to 2.345 GHz, each doing one multiply-add per cycle: 2,560 × 2 × 2.345 GHz ≈ 12 TFLOPS. Numbers come in several sizes. FP32 is the ordinary 4-byte float. FP16 is a 2-byte float with less range and precision. BF16, "brain float", is a 2-byte float with FP32's range and even less precision. Language models store their weights in BF16 more often than in anything else, and that halves the bytes of every W.

The ratio between the two is the key quantity. Arithmetic intensity is FLOP done per byte moved from memory. Our FP32 matvec does 2 FLOP per 4-byte weight: 0.5 FLOP per byte. The laptop can do 12,000 GFLOPS of arithmetic but only receive 216 GB of data per second. To keep its lanes busy, a kernel would need 12,000 / 216 ≈ 56 FLOP for every byte. Our matvec offers 0.5. The lanes will be idle more than 99% of the time, waiting for W, however good the code is.

The roofline

That argument has a standard picture, the roofline (Williams, Waterman and Patterson, 2009). The horizontal axis is arithmetic intensity, the vertical axis is attainable FLOPS, and both are logarithmic. A kernel can never beat bandwidth × intensity, which is the sloped line, nor the arithmetic peak, which is the flat line. The corner where they meet is the ridge point. A kernel to the left of the ridge is memory-bound: its speed is set by bandwidth, and only moving fewer bytes makes it faster. A kernel to the right is compute-bound: its speed is set by arithmetic, and only fewer or cheaper FLOP make it faster.

The roofline turns the prologue's sentence into a prediction. Our matvec must move at least 64 MiB of W plus 32 KiB of x and y, about 67.1 million bytes. At 216 GB/s that takes at least 311 µs on the laptop, and no kernel can beat it. The compiler, the warps, the registers and the scheduler all decide how close a kernel gets to 311 µs, and none of them can get below it. The same arithmetic gives the other two benches in the table below. Store W in BF16 instead and every number halves.

This chapter skips DRAM refresh, bank groups, and the memory controllers' scheduling. They explain why real kernels reach 80 to 90% of peak and not 100%, and nothing here needs more than that.

The GB/s column is 67.1 MB divided by the measured time, so you can read it straight against the 216 GB/s peak. Expect the two warp kernels and the cublasSgemv line, NVIDIA's library version, to land within shouting distance of each other and well below 216, and the naive kernel to land well below them. If a kernel ever prints more than the peak, W is not coming from DRAM. That happens when W is small enough to fit in L2, which is what the third question below is about.

Recap

W lives in global memory, the GPU's DRAM: GDDR on the laptop and the P5000, HBM on the H100. Memory moves in 32-byte sectors, so a warp's load is cheap when neighbouring lanes read neighbouring bytes (coalesced) and expensive when they are 16 KiB apart, as in the naive kernel. Arithmetic intensity, FLOP per byte, places a kernel on the roofline: our matvec does 0.5 FLOP per byte against a laptop ridge of 56, so it is memory-bound, and its time can never fall below bytes ÷ bandwidth, which is 311 µs on the laptop, 233 µs on the P5000 and 20 µs on the H100.

Check yourself

1. Predict the value: the same 4096 × 4096 matvec, but with W stored in BF16 and x and y kept in FP32. What is its arithmetic intensity, and its shortest possible time on the laptop and on the H100?

Answer

1 FLOP per byte; about 156 µs on the laptop and 10 µs on the H100. Each weight is now 2 bytes and still feeds one multiply-add, which is 2 FLOP. W shrinks to 33,554,432 bytes, plus the same 32 KiB of x and y: about 33.6 MB. That is 33.6 MB / 216 GB/s ≈ 156 µs, and 33.6 MB / 3,352 GB/s ≈ 10 µs.

The point stays far left of every ridge in the table, so the kernel is still memory-bound, and halving the bytes halves the time. The near-miss is to expect a gain from faster BF16 arithmetic. The arithmetic was never the limit.

2. A profiler reports, for the main load instruction of one matvec kernel, about 32 sectors requested per warp-wide load, and about 4 for another kernel. Both load one 4-byte float per lane. Which is the naive kernel, and what does its number cost?

Answer

The 32-sector one is the naive thread-per-row kernel. Its lanes read addresses 16 KiB apart, so each lane needs its own sector (diagram 3.2). The warp-per-row kernel's lanes read 32 neighbours, which is 4 sectors.

The cost is up to 8 times as many bytes moved per useful byte: 1,024 fetched for 128 used. The real penalty is smaller only to the extent that L1 still holds each sector when the lane comes back for its next float. Since the kernel is memory-bound, extra bytes become extra time almost one for one. The near-miss is "the naive kernel does more arithmetic". Both do the same 16.8 million multiply-adds.

3. "A matvec is memory-bound, so its time is set by DRAM bandwidth." Give a case from this chapter where the second half stops being true, and what sets the time instead.

Answer

When W is small enough to stay in the L2 cache from one call to the next. For example, a 1024 × 1024 FP32 W is 4 MiB, which fits in the H100's 50 MB L2. It does not fit in the P5000's 2 MB. Repeated calls then read W from L2, whose bandwidth is several times DRAM's, so the time is set by L2 bandwidth, and the measured "GB/s" can exceed the DRAM peak.

The kernel is still memory-bound: its intensity is still 0.5 FLOP per byte. What changed is which rung of diagram 3.1 the bytes come from. The other way out is the green point of diagram 3.3: reuse each weight for many vectors, which raises the intensity itself.
