Chapter 5

From .cu to machine code

@@RT@@ · CUDA ISA — Last chapter we wrote the matvec three times in CUDA C++. Before an SM can run any of them, the source has to become machine code, be packed into the executable, and be found again by the driver when the program starts. This chapter follows matvec_warp through all three steps, because each step is a place where bpftime later reaches in.

Two instruction sets, one virtual and one real

NVIDIA GPUs have two instruction sets, and the difference between them explains most of this chapter. PTX, Parallel Thread Execution, is a virtual instruction set. It looks like assembly, but it is written for an imaginary GPU with unlimited registers, and it stays stable from one hardware generation to the next. SASS is the real instruction set of one particular SM design: the bits the hardware decodes. NVIDIA documents its opcodes but not its encoding, and it changes with almost every generation. PTX is to SASS roughly what LLVM IR is to x86 machine code, except that PTX is a documented, versioned language that programs ship.

The compiler names targets in two matching spellings. A virtual architecture, compute_89, names a PTX feature level: the PTX may only use features that compute capability 8.9 has. A real architecture, sm_89, names a SASS target: code for that SM design. nvcc -arch=sm_89 is shorthand for "make PTX at compute_89, make SASS for sm_89 from it, and ship both".

The compilation trajectory

NVIDIA calls the path from .cu to executable the compilation trajectory. nvcc is a driver program that runs the real tools in order. nvcc --dryrun prints them without running anything. For the lab program they are:

$ nvcc -O3 -arch=sm_89 --dryrun matvec.cu -lcublas -o matvec 2>&1 | (tool names only)
gcc  cudafe++  gcc  cicc  ptxas  fatbinary  gcc  nvlink  fatbinary  gcc  g++

Listing 5.1 — the tools nvcc 13.4 runs, in order, on this laptop.

Each one has a single job. cudafe++ splits the source into its host half and its device half, and writes small host functions, host stubs, that stand in for each kernel on the CPU side: calling matvec_warp<<<…>>> in host code calls the stub. cicc is NVIDIA's device compiler, which NVIDIA calls NVVM. It is built on LLVM and turns the device half into PTX. ptxas is the PTX assembler: it turns PTX into SASS for one real architecture, allocating real registers and scheduling instructions. Its output is a cubin, an ELF file holding the SASS of one real architecture.

fatbinary packs cubins and PTX text together into a fatbin, a container that can hold code for several architectures at once, and the host gcc compiles that fatbin into the host object file as plain data. At link time nvlink runs a device-link step and fatbinary runs again on its output. That is why the finished executable holds two sm_89 cubins: the second is a small linked image whose temporary file is named …_dlink.sm_89.cubin. Last, g++ links everything, including the CUDA runtime. By default nvcc links the runtime statically into the executable, a detail that matters very much to bpftime, as the end of this chapter shows.

There is a second road to PTX that does not use NVIDIA's compiler at all. LLVM itself has an NVPTX backend, an LLVM target that emits PTX from LLVM IR, LLVM's own typed intermediate language. Clang can compile CUDA through it. That road matters twice here. It is how this document produces real Pascal PTX, since CUDA 13.4 can no longer target Pascal. And it is the road bpftime takes to turn eBPF bytecode into PTX.

$ clang -x cuda --cuda-gpu-arch=sm_61 --cuda-device-only -S -O3 matvec.cu -o matvec.sm_61.clang.ptx
clang: warning: CUDA version is newer than the latest partially supported version 12.9
$ head -9 matvec.sm_61.clang.ptx
//
// Generated by LLVM NVPTX Back-End
//

.version 8.8
.target sm_61
.address_size 64

	// .globl	_Z6matvec…        (one .entry per kernel follows)

Listing 5.2 — real Pascal PTX from clang 22 on this laptop. ptxas 13.4 refuses to assemble it: Value 'sm_61' is not defined for option 'gpu-name'.

What the executable carries

The fatbin ends up in a section of the executable's ELF file named .nv_fatbin, with a small descriptor in .nvFatBinSegment that points at it. readelf -S shows both on the lab binary. cuobjdump lists what is inside. Here is a build that targets two real architectures and ships PTX for one of them:

$ nvcc -O3 -gencode arch=compute_89,code=[sm_89,compute_89] \
           -gencode arch=compute_90,code=sm_90 matvec.cu -lcublas -o matvec_multi
$ cuobjdump -lelf -lptx matvec_multi
ELF file    1: matvec_multi.1.sm_89.cubin
ELF file    2: matvec_multi.2.sm_90.cubin
ELF file    3: matvec_multi.3.sm_89.cubin
PTX file    1: matvec_multi.1.sm_89.ptx
ELF file    4: matvec_multi.4.sm_90.cubin

Listing 5.3 — real output. Files 3 and 4 are the device-link images. The PTX file is the compute_89 PTX; cuobjdump labels it with the matching real name.

The kernels inside are named by their C++ mangled names. C++ encodes a function's parameter types into its symbol so that overloads get distinct names: _Z11matvec_warpPKfS0_Pfii is _Z, an 11-character name matvec_warp, then the parameter list: pointer to const float (PKf), the same again (S0_), pointer to float (Pf), int, int. c++filt undoes it. Mangled names are what the driver uses to find a kernel. They are also what you write in a bpftime probe's section name, so you will be reading them a lot.

From bytes in a file to a kernel on the device

The host stubs also contain a static constructor, which runs before main. It calls two functions in the CUDA runtime. __cudaRegisterFatBinary hands the runtime a pointer to the fatbin. __cudaRegisterFunction is then called once per kernel, with the address of the kernel's host stub and its mangled device name. From then on the runtime can turn "the host called the stub at this address" into "launch the device function with this name". The stub's own launch goes through the runtime too. In a CUDA 13 binary it calls an internal entry, __cudaLaunchKernel; older runtimes have the stub call the public cudaLaunchKernel. Which entry a binary uses matters to any tool that intercepts launches.

At the first real CUDA call, the runtime creates a CUDA context, the driver's per-process state for one GPU: its address space on the device, its loaded code, its queues. A loaded piece of device code inside a context is a module, and one kernel inside a module is a function. The runtime does this through the CUDA driver API, the C interface of libcuda.so, whose functions start with cu: cuModuleLoadData loads a module from bytes in memory, and cuModuleGetFunction finds a kernel in it by its mangled name. Programs that generate code at run time, like the Triton compiler in the language-model part (Part V), call those functions directly.

When the driver loads a module from a fatbin, it picks the code for this GPU. If there is a cubin whose SASS this GPU can run, it uses that. If there is none but there is PTX at or below this GPU's compute capability, the driver runs its own built-in copy of ptxas: JIT compilation, just in time. The result is saved in the compute cache, by default ~/.nv/ComputeCache, so the next run of the same program skips the compile. Since CUDA 12.2, loading is also lazy on Linux by default: a module is loaded only when one of its kernels is first launched.

One build detail decides whether a tool can reach those moments. Because nvcc links the runtime statically by default, __cudaRegisterFatBinary in the lab binary is a local symbol: nm marks it with a lower-case t. A preloaded library cannot interpose on a function that is not exported. Build with nvcc -cudart shared and the registration calls go through libcudart.so, where they can be hooked. bpftime's own examples are all built that way.

Try it

Build a binary with PTX only, no SASS, and watch the driver compile it. This needs the GPU on:

nvcc -O3 -gencode arch=compute_89,code=compute_89 matvec.cu -lcublas -o out/matvec_ptxonly
cuobjdump -lelf -lptx out/matvec_ptxonly     # only "PTX file" lines for the kernels
rm -rf ~/.nv/ComputeCache
time ./out/matvec_ptxonly 4096 4096 1         # first run pays for the JIT
time ./out/matvec_ptxonly 4096 4096 1         # second run finds it in the cache
CUDA_FORCE_PTX_JIT=1 ./out/matvec             # ignore the SASS and JIT anyway

Then check the symbol that bpftime needs: nm out/matvec | grep __cudaRegisterFatBinary shows t (local). Rebuild with -cudart shared and nm -D shows U __cudaRegisterFatBinary@libcudart.so.13: the binary now imports it from libcudart.so, where a preloaded library can intercept it. The same listing shows U __cudaLaunchKernel@libcudart.so.13, the CUDA 13 launch entry.

Recap

PTX is NVIDIA's stable virtual instruction set; SASS is the real one, different per SM design. nvcc runs cudafe++ to split the source, cicc (NVVM) to make PTX, ptxas to make SASS in a cubin, and fatbinary to pack cubins and PTX into a fatbin inside the executable's .nv_fatbin section. Clang, and anything else on LLVM, reaches the same PTX through the NVPTX backend. Before main, host stubs register the fatbin and every kernel's mangled name with the runtime. At the first launch the driver loads a module into the context, using matching SASS if it has it and JIT-compiling PTX into the compute cache if not; a statically linked runtime keeps the registration functions out of reach of a preloaded hook.

Check yourself

1. Predict the outcome: matvec_multi from listing 5.3 is copied to four machines: the laptop, an H100, a newer GPU of compute capability 10.0, and the customer's P5000. On each, which code runs, or what goes wrong?

Answer

The laptop runs the sm_89 cubin directly and the H100 runs the sm_90 cubin. The 10.0 GPU has no matching cubin, so the driver JIT-compiles the compute_89 PTX: PTX can be compiled for any compute capability at or above its own. The P5000 fails to launch, with CUDA's "no kernel image is available for execution on the device", because 6.1 is below every target in the fatbin.

The near-miss is "PTX runs anywhere". It only runs upward, from its virtual architecture to newer ones (diagram 5.3's alt, and the table). Pascal needs compute_61 or older PTX, or an sm_61 cubin, and CUDA 13.4 can make neither.

2. On a fresh machine, a program sits for about 40 seconds before its first kernel runs. The second run starts at once. Deleting ~/.nv/ComputeCache brings the 40 seconds back. What is happening, and how would you remove the delay for good?

Answer

The driver is JIT-compiling PTX at the first launch because the fatbin holds no SASS for this GPU, and then it caches the result (diagram 5.3, the else branch). Large libraries can take this long, because every kernel is compiled.

Removing the cache removes the stored result, so the compile happens again. The lasting fix is to build with a real architecture for this GPU, for example adding -gencode arch=compute_89,code=sm_89, so the driver finds SASS and skips the JIT. You can confirm it with cuobjdump -lelf: no ELF line for your sm_ means JIT. The near-miss is "the GPU or the driver warming up". Nothing warms up; a compiler runs.

3. "PTX is forward-compatible, so PTX shipped today will run on any newer NVIDIA GPU." Give two conditions under which that stops being true.

Answer

First, arch-specific targets. PTX built for a virtual architecture with an a suffix, such as compute_90a, may use instructions that exist only on that one design. Hopper's largest tensor-core matrix instructions are the best-known case, and that PTX cannot be compiled for any other GPU.

Second, the driver has to understand the PTX. PTX carries a .version line (9.4 from CUDA 13.4, 8.8 from clang 22). An older driver that predates that PTX version cannot JIT it, even on a GPU it supports. That is a live risk on a Pascal machine held on an old driver branch. The sentence is true for plain compute_XX PTX, compiled by a driver at least as new as the toolkit that wrote it.
