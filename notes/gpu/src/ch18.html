Chapter 18

One machine: llama.cpp and ggml

@@RT@@ · LLM — vLLM is built for a GPU server with many users. llama.cpp is built for one machine: a C and C++ program that runs a model from a single file on a laptop, an old workstation card or a CPU. Of the two, it is the only one that runs on the P5000. This chapter follows a decode step through it at commit ec7630a: the graph it builds, the file it reads, the quantized multiply and the instruction underneath, its CUDA graphs, and its server.

This chapter skips the CPU, Metal, Vulkan and ROCm backends, multimodal models, speculative decoding, the importance-matrix quantization types, and how quantization error is measured.

Two libraries: llama and ggml

llama.cpp is two layers. ggml is a tensor library: tensors, operations on them, a graph of operations, and backends that run a graph on a CPU or a GPU. libllama sits on top. It loads models, keeps the KV cache, and builds a ggml graph of the model for each batch, using the builder the transformer chapter (chapter 15) walked through (src/models/qwen2.cpp:53–154). The programs you run, llama-completion, llama-bench and llama-server, all submit work through libllama's llama_process, or the older llama_decode, which ends in the same place.

A call to llama_process splits its batch into micro-batches: up to 2,048 tokens per call by default, and 512 at a time on the device (common/common.h:453–454). For each micro-batch it builds the graph, and the CUDA backend walks it node by node. Each node becomes one kernel launch, or several nodes become one fused kernel, such as a matrix-vector multiply with its bias add (ggml/src/ggml-cuda/ggml-cuda.cu:4134–4142).

GGUF: one file holds the model

A llama.cpp model is one GGUF file, the format the transformer chapter downloaded. It starts with the four bytes GGUF and a version number, 3 (ggml/include/gguf.h:41–42). Then come key-value metadata (the architecture, the number of layers, the context length the model was trained with, the tokenizer's 151,936 tokens), a table of tensors with each one's name, shape, type and offset, and the tensor data, aligned to 32 bytes (line 46). By default llama.cpp maps the file into memory and copies the tensors to the GPU from there (common/arg.cpp:2693).

The tensor table is enough to know what a decode step reads, before running anything. Reading the first megabytes of the two official files of our model gives this:

Quantization: small integers with a scale

Each of these types stores weights as small integers in fixed-size blocks, with one or two scale factors per block. Q8_0, the transformer chapter's file, takes 32 weights, stores one FP16 scale d and 32 signed 8-bit integers, and a weight is d × q: 34 bytes per 32 weights, 8.5 bits per weight (ggml/src/ggml-common.h:251–256). Q5_0 does the same with 5-bit integers, 22 bytes per 32 weights. The k-quants work on super-blocks of 256 weights. Q4_K stores two FP16 numbers for the super-block, a 6-bit scale and a 6-bit minimum for each of its eight sub-blocks of 32, and 4 bits per weight: 144 bytes per 256, 4.5 bits per weight (ggml-common.h:320–338).

A name like Q4_K_M names a recipe for a whole file. Most tensors get Q4_K, and in 12 of the 24 layers, chosen by a fixed rule, attn_v and ffn_down get the larger Q6_K (src/llama-quant.cpp:452–454, 590–591 and 646–651). On Llama-3-8B the recipe averages 4.89 bits per weight (tools/quantize/README.md:167). But k-quants need each row's length to be a multiple of 256, and our model's rows have 896 entries, which is 3.5 × 256. The quantizer then falls back: Q4_K becomes Q5_0 and Q6_K becomes Q8_0 (llama-quant.cpp:396–418). Only ffn_down, whose rows have 4,864 = 19 × 256 entries, keeps its k-quants. The file's name says what was asked for; the tensor table says what you got.

One multiply, five kernels to choose from

Every matrix multiply in the graph goes through ggml_cuda_mul_mat (ggml-cuda.cu:1822–1875), which picks a kernel from the weight type and the number of columns in the batch.

Decode is the top-left cell. Before mul_mat_vec_q runs, ggml quantizes the activation vector too, to 8-bit integers in blocks of 32 with a scale (ggml/src/ggml-cuda/mmvq.cu:1506). Each thread then loads four weights and four activations packed into two 32-bit registers and multiplies them with one instruction, dp4a: four 8-bit products, summed into a 32-bit integer (vecdotq.cuh:246–258). The scales are applied once per block, in floating point. ggml calls dp4a from compute capability 6.1, Pascal's GP104, and multiplies byte by byte below that (common.cuh:51 and 740–746). A three-line kernel shows the instruction in PTX and in SASS:

// out[i] = __dp4a(w[i], x[i], 0);   nvcc 13.4, -arch=sm_89
PTX:   ld.global.u32   %r2, [%rd8];
       ld.global.u32   %r3, [%rd9];
       mov.u32         %r4, 0;
       dp4a.s32.s32    %r5, %r2, %r3, %r4;
SASS:  LDG.E R2, [R2.64] ;
       LDG.E R5, [R4.64] ;
       IDP.4A.S8.S8 R9, R2, R5, RZ ;

Listing 18.1 — dp4a in PTX and in Ada SASS, compiled for this chapter. The sm_90 build emits the same IDP.4A.S8.S8. CUDA 13 cannot target Pascal, so its SASS needs a 12.x toolkit.

This is the prologue's matvec again, with bytes in place of floats. Each weight is still used for one multiply-add, but it takes about a quarter of the FP32 matvec's bytes in Q8_0, a sixth in Q5_0 and a seventh in Q4_K. Decode is bound by bytes, so that is where the speed comes from.

Prefill is the matrix path. mul_mat_q multiplies tiles of quantized weights with tiles of the 512 activation columns, on int8 tensor cores from Turing on (mmq.cu:371–373), and with dp4a on Pascal (lines 375–387).

CUDA graphs, and the launch path on Hopper

llama.cpp builds ggml with CUDA graphs on (CMakeLists.txt:169–171), and ggml switches them off below Volta, so on the P5000 every kernel is launched one by one (ggml-cuda.cu:4430–4436). The environment variable GGML_CUDA_DISABLE_GRAPHS turns them off anywhere (common.cuh:1289). ggml captures a graph once two calls in a row have identical nodes: the same shapes, strides and data pointers (ggml-cuda.cu:2597–2637 and 4459–4481). After that it replays the graph until something changes, then runs one call directly and captures again. The part of the KV cache that attention reads is padded to a multiple of 256 tokens (src/llama-kv-cache.cpp:1265–1270), so a decode loop can replay one graph for up to 256 tokens. Every capture goes through the launch functions, so a probe loaded with the process sees each capture, as the host-side chapter (chapter 8) described.

Hopper adds programmatic dependent launch: a kernel may start before the kernel ahead of it in the same stream has finished, and waits inside for the data it needs. NVIDIA's guide says it is available from compute capability 9.0, and that the dependent kernel must be launched with the extensible launch call, cudaLaunchKernelEx. ggml uses it for every kernel whose PTX was compiled for 9.0 or newer (common.cuh:1670–1701). bpftime at commit a900f85 replaces cudaLaunchKernel, its _ptsz variant and cuLaunchKernel (nv_attach_impl.cpp:421–429), and nothing named LaunchKernelEx. So on an H100 build for 90, ggml's launches skip bpftime's redirect. GGML_CUDA_PDL=0 sends them through the normal launch (common.cuh:1693–1696). This follows from the source; it has not been run on an H100.

llama-server: slots in a fixed cache

llama-server serves several conversations at once, each in a slot. By default it creates 4 slots that share one cache (tools/server/server.cpp:160–165, common/arg.cpp:1403), and continuous batching is on (arg.cpp:2570). Each step, update_slots (tools/server/server-context.cpp:2793) adds one sampled token for every slot that is generating (line 3096), adds waiting prompt tokens until the batch holds 2,048 (line 3108), and calls llama_process. That is vLLM's step in miniature, with a batch size where vLLM has a token budget.

The cache is one buffer of token cells, allocated at start-up. Its size is -c, by default the context length the model was trained with, 32,768 here, reduced to fit free memory when --fit is on, which is the default (common/common.h:452 and 478). When a step finds no free cells, the server halves the batch and tries again (server-context.cpp:3728–3733). A request that arrives while all slots are busy is deferred until one frees up (server-context.cpp:2405–2407). A new request goes preferably to a slot whose last prompt shares at least 10% of its own, and the shared start is reused from that slot's cache (arg.cpp:3796–3797, common.h:697).

What llama-server reports

With --metrics (arg.cpp:3592), /metrics serves counters and gauges named llamacpp:… (tools/server/server-task.cpp:1523–1598): prompt_tokens_total and tokens_predicted_total, the seconds spent on each, n_decode_total for decode calls, average throughput in prompt_tokens_seconds and predicted_tokens_seconds, requests_processing, requests_deferred for requests waiting for a slot, and n_busy_slots_per_decode. There is no TTFT or ITL histogram. Each response carries a timings object instead, with prompt_ms, predicted_per_token_ms and cache_n, the prompt tokens reused from the cache (tools/server/server-common.cpp:84–95). prompt_ms is the prefill alone: its clock starts when a slot begins the prompt (server-context.cpp:3141, server-common.h:391–415). The time a request spent waiting for a slot appears nowhere per request, and that gap is one reason to probe, which is where the next chapter starts.

Try it

Build llama.cpp as in Before you start, with the architecture named. First check that the library carries PTX, which the next chapter's probes need, and count the dp4a instructions in it:

cuobjdump --list-ptx build/bin/libggml-cuda.so | head -3
cuobjdump -ptx build/bin/libggml-cuda.so | grep -c dp4a

Then, with the dGPU in Hybrid mode, compare the two files and the effect of CUDA graphs. Write down a prediction for each tg128 first, from the first question below:

./build/bin/llama-bench -p 512 -n 128 \
    -m qwen2.5-0.5b-instruct-q8_0.gguf,qwen2.5-0.5b-instruct-q4_k_m.gguf
GGML_CUDA_DISABLE_GRAPHS=1 ./build/bin/llama-bench -p 512 -n 128 \
    -m qwen2.5-0.5b-instruct-q8_0.gguf

The measured numbers will be below the ceilings. A token of this small model is a few hundred short kernels, and each one has a fixed cost that bytes do not explain. The run without graphs shows how much of that cost was on the CPU side.

Recap

llama.cpp is libllama on top of ggml: llama_process splits a batch into micro-batches, builds a ggml graph of the model for each, and the CUDA backend runs one kernel per node or per fused group. A model is one GGUF file whose weights are blocks of small integers with scales; Q4_K_M is a recipe, and for rows that are not a multiple of 256 its k-quants fall back to Q5_0 and Q8_0. Each multiply picks a kernel, dp4a vector kernels for decode and tiled kernels on tensor cores or dp4a for prefill, and CUDA graphs are captured once shapes repeat, except below Volta. On Hopper, ggml launches with cudaLaunchKernelEx, which bpftime does not hook. llama-server runs slots in a fixed cache, halves its batch when the cache is full, and reports throughput but no latency histograms.

Check yourself

1. Predict the value: using the tensor table above, roughly how many bytes does one decode step read from the Q4_K_M file, and what is the ceiling in tokens per second for one sequence on the laptop and on the P5000? The F32 vectors and the tokenizer are small enough to ignore.

Answer

About 392 MB, so about 550 tokens per second on the laptop and about 735 on the P5000. The tensors add up to about 485 MB, and the 94 MB Q5_0 embedding table is read one row at a time, which leaves about 392 MB. Most of it is Q5_0, plus the 145 MB Q8_0 output copy and the Q4_K and Q6_K ffn_down layers. 0.392 GB / 216 GB/s ≈ 1.8 ms, and 0.392 GB / 288 GB/s ≈ 1.4 ms.

The near-miss is to multiply 494 million weights by 4.89 bits, which gives about 300 MB and a ceiling near 715 tokens per second on the laptop. It uses a Llama-3-8B average for a file that is mostly Q5_0 and holds a second Q8_0 copy of the largest matrix.

2. A uprobe on cudaLaunchKernel during llama-bench's generation test shows a steady stream of calls on the P5000, and on the laptop a burst every now and then with almost nothing in between. Explain both.

Answer

ggml disables CUDA graphs below Volta, so on the P5000 every node of every token's graph is an ordinary launch: a few hundred calls per token, steadily. On the laptop, ggml captures a graph once two calls in a row have identical nodes, and replays it with one cudaGraphLaunch, which does not call cudaLaunchKernel.

The bursts are the captures, plus the step that runs directly before each one. They come when something in the graph changes, for example when the padded length of cache that attention reads crosses a multiple of 256 tokens. The near-miss is that the laptop's GPU is idle between bursts. It is busy the whole time, running kernels whose launches no longer pass through the probed function.

3. Users of a llama-server with 4 slots report a time to first token of several seconds, but every response's timings.prompt_ms is under 200 ms. Where did the time go, which metric shows it, and what would you change?

Answer

The time went to waiting for a slot. prompt_ms measures only the prefill, so a request that waited behind four long generations shows a small prompt_ms and a long TTFT. llamacpp:requests_deferred above zero, with requests_processing at 4, shows requests queueing.

More slots help, with -np, as long as the cache is large enough for them: each slot needs room for its context. So do shorter outputs, or a second server. The near-miss is to tune prefill, for example with a larger batch. Prefill was never the slow part.
