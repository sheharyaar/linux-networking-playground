Chapter 6

Reading PTX

@@RT@@ · ISA — Last chapter showed PTX as the point where NVIDIA's compiler and LLVM produce the same kind of text, and the point where bpftime will splice its code into ours. Now we learn to read that text, on the PTX of matvec_warp itself and on a few lines of the PTX that bpftime injects.

The frame of a PTX file

Every PTX file opens with three lines. .version 9.4 is the PTX ISA version, the edition of the language this file is written in; CUDA 13.4 writes 9.4, clang 22 writes 8.8, and bpftime's own trampoline file says 8.1. .target sm_89 is the virtual architecture, the feature level the code may use. .address_size 64 says pointers are 64 bits.

Then come functions. A kernel is declared with .entry: an entry point the host can launch. A device function that other device code calls is a .func. .visible makes the name visible outside this file, which is how the driver finds it by its mangled name. The kernel's arguments are declared in the .param state space, one line each, with the type of each argument:

.visible .entry _Z11matvec_warpPKfS0_Pfii(
	.param .u64 _Z11matvec_warpPKfS0_Pfii_param_0,     // const float *W
	.param .u64 _Z11matvec_warpPKfS0_Pfii_param_1,     // const float *x
	.param .u64 _Z11matvec_warpPKfS0_Pfii_param_2,     // float *y
	.param .u32 _Z11matvec_warpPKfS0_Pfii_param_3,     // int n
	.param .u32 _Z11matvec_warpPKfS0_Pfii_param_4      // int d
)
{
	.reg .pred 	%p<13>;
	.reg .f32 	%f<40>;
	.reg .b32 	%r<43>;
	.reg .b64 	%rd<40>;

Listing 6.1 — the head of matvec_warp, from nvcc -ptx -arch=sm_89 (CUDA 13.4). Comments added.

The four .reg lines declare virtual registers: as many as the code wants, each with a type. %p registers are predicates, one bit each. %f registers hold 32-bit floats, %r 32-bit untyped bits, %rd 64-bit values such as addresses. %r<43> means "43 of these". The PTX for this kernel uses about 140 virtual registers. ptxas will fit them into 40 real ones, the number cuobjdump reported in the SM chapter.

State spaces: every address says where it points

A state space is PTX's name for a kind of storage, and every load and store names one. .reg is registers. .param holds kernel and function arguments. .global is global memory. .shared is the block's shared memory. .local is per-thread memory in DRAM. .const is constant memory. So a load from global memory is ld.global, a load of an argument is ld.param, a store to shared memory is st.shared. The instruction's suffix then gives the type: ld.global.f32 loads one 32-bit float.

C pointers do not carry a state space, so PTX also has generic addresses, which can point into global, shared or local memory and are resolved by hardware. The kernel receives its pointers as generic addresses and converts them once at the top with cvta.to.global.u64, "convert address to the global space". After that it can use the faster ld.global directly.

Reading the body

The kernel's first job is to work out who it is. It reads special registers: read-only registers the hardware fills in for each thread. %tid is threadIdx, %ntid is blockDim, %ctaid is blockIdx and %nctaid is gridDim. Others give the thread's place in the hardware: %laneid its lane, %warpid its warp slot on the SM, %smid which SM it is running on, %globaltimer a 64-bit nanosecond clock and %clock64 the SM's cycle counter. Here is the C of listing 4.2 next to the PTX it became:

Listing 6.2 — source next to PTX, lines picked from the same nvcc -ptx output.

Branches work through predicates. setp.ge.s32 %p1, %r2, %r14 sets predicate %p1 to "warp ≥ d". @%p1 bra … is a guarded instruction: it runs only in the lanes whose %p1 is true. Any PTX instruction can carry a guard, branches and arithmetic alike, and this is the instruction-level form of the divergence in the SIMT chapter. Lanes that disagree about %p1 take the branch differently, and the hardware's active mask does the rest.

The inner loop shows two things that earlier chapters predicted. The addresses step by 128 bytes per copy, 32 lanes × 4 bytes, so each warp-wide load is one cache line: coalescing, visible in the offsets. And the loads are ld.global.nc. The .nc means non-coherent: the load may go through a read-only cache that does not keep up with writes made during the kernel. The compiler may only use it because const and __restrict__ promised that W and x do not change while the kernel runs. The float4 kernel's loads are ld.global.nc.v4.f32 {%f13, %f14, %f15, %f16}, [%rd35]: a vector load, four registers filled by one instruction. fma.rn.f32 is a fused multiply-add, one rounding for the whole a × b + c, rounding to nearest.

When threads must agree: atomics, fences and scopes

Our matvec never needs two threads to coordinate. bpftime does, so here is the minimum. An atomic instruction reads, modifies and writes one memory location so that no other thread's access can land in between. atom.global.cas.b32 is compare-and-swap, atom.global.add.f32 an atomic add, atom.global.exch.b32 an exchange.

A memory scope names the set of threads a guarantee covers. .cta is one block. .cluster is a group of blocks, on Hopper only. .gpu is every thread on this GPU. .sys is the whole system: this GPU, the host CPUs, and other GPUs. An atomic at .gpu scope is atomic for every thread on the device and makes no promise about the CPU. A fence, written membar in its oldest form, orders one thread's own memory accesses: everything before it becomes visible, to everyone in the named scope, before anything after it. membar.sys is the strongest. On Volta and later, PTX also has fence and loads and stores with acquire and release semantics, which give finer control. Pascal has only membar.

Now read the code bpftime injects when a GPU probe has to ask the host for something. This is its own PTX, from trampoline_ptx.h:

$L__BB2_2:
	atom.global.cas.b32 	%r11, [%rd8], 0, 1;   // take a lock: 0 → 1
	setp.eq.s32 	%p5, %r11, 1;                 // somebody else holds it?
	@%p5 bra 	$L__BB2_2;                        //   then spin
	st.u32 	[%rd1+12], %r5;                       // write the request
	st.u64 	[%rd1+16], %rd6;
	membar.sys;                                   // request visible system-wide
	st.global.u32 [%rd1], 1;                      // raise "request ready"
spin_wait:
	membar.sys;
	ld.global.u32 %r12, [%rd10];                  // read "answer ready"
	setp.eq.u32 p0, %r12, 0;
	@p0 bra spin_wait;                            // not yet: spin
	st.global.u32 [%rd10], 0;
	membar.sys;
	ld.u64 	%rd13, [%rd1+2097184];                // read the answer
	atom.global.exch.b32 	%r13, [%rd8], 0;      // release the lock

Listing 6.3 — bpftime/attach/nv_attach_impl/trampoline_ptx.h:100–122, comments added. The file declares .target sm_61.

Every piece is from this chapter. A compare-and-swap loop is a spinlock, and the lock is one word in global memory, so it serialises every thread on the GPU that reaches this code. The request is written to memory that the host can also see, and membar.sys makes sure the host sees the request before it sees the flag. Then the thread spins on a second flag until the host answers. Where that shared memory lives, and why the host can see it at all, is the next chapter's subject. Why this design costs so much is the probe-cost chapter's.

The same file also shows two state spaces in use for bpftime's own data: .visible .const .align 8 .u64 constData; holds the address of that shared region, and .visible .const .align 8 .b8 map_info[40960]; is a table of 1,024 map descriptors of 40 bytes each, in constant memory. And it reads the clock and the SM number the same way any kernel can: mov.u64 %rd1, %globaltimer; and mov.u32 %r1, %smid; (lines 1648 and 1830). NVIDIA's documentation warns that %smid and %warpid are volatile: a thread can be moved, for example when the GPU stops its block to run other work, so the value is "where I was when I read it".

Calls

A .func is called with call. Arguments and the return value travel through .param variables that the caller declares, and ptxas later decides which real registers carry them. bpftime's helpers are .funcs with names like _bpf_helper_ext_0502, which returns the value of %globaltimer. The probe compiled from your eBPF program also becomes a .func, and the bpftime chapters show the one-line call that is inserted into your kernel to run it.

Try it

Make PTX for all three generations, from one source, on the laptop:

nvcc  -O3 -ptx -arch=sm_89 matvec.cu -o out/matvec.sm_89.ptx
nvcc  -O3 -ptx -arch=sm_90 matvec.cu -o out/matvec.sm_90.ptx
clang -x cuda --cuda-gpu-arch=sm_61 --cuda-device-only -S -O3 matvec.cu -o out/matvec.sm_61.clang.ptx
grep -c 'ld.global.nc' out/*.ptx
diff <(grep -v '^//' out/matvec.sm_89.ptx) <(grep -v '^//' out/matvec.sm_90.ptx) | head

The sm_89 and sm_90 files differ in little more than the .target line: PTX is meant to be nearly the same everywhere. The clang file is laid out differently, because a different compiler wrote it, but it is the same language. The real differences between generations show up one level down, in SASS.

Recap

A PTX file declares its ISA version, its target and its address size, then .entry kernels and .func device functions with arguments in the .param space and unlimited typed virtual registers. Every memory instruction names a state space (.global, .shared, .local, .const, .param), and generic C pointers are converted once with cvta. Threads learn who they are from special registers such as %tid, %ctaid, %smid and %globaltimer. Branches are predicates plus guarded instructions. Coordination uses atomics and fences at a named scope, .cta to .sys, and bpftime's call to the host is a .gpu-wide spinlock and .sys fences around a request in memory both sides can see.

Check yourself

1. Predict the value: in the unrolled loop of listing 6.2, the address registers step by 512 bytes per loop iteration. For the float4 kernel, which loads 16 bytes per lane and is unrolled the same four times, what would you expect the step to be, and why?

Answer

2,048 bytes. Per copy of the loop body, each of the 32 lanes moves 16 bytes, so the warp advances 32 × 16 = 512 bytes. Four copies per iteration make 4 × 512 = 2,048. The PTX agrees: the float4 loads use offsets like [%rd38+-1024], two copies' worth (1,024 bytes) behind the address register.

The near-miss is 512, which is the step for the scalar loop. The rule behind both numbers is lanes × bytes per lane × unroll factor. It is worth being able to read a loop's stride straight out of PTX, because the stride is how you see whether a warp's loads are coalesced.

2. A probe uses atom.global.add.u64 at the default scope to count events into a counter in memory that the host can read directly. The host polls the counter while the kernel runs, and its last reading, taken as the kernel ends, is sometimes lower than the true count. Using diagram 6.2, what is missing?

Answer

System scope. A plain atom.global is atomic among GPU threads, at .gpu scope, and makes no promise about when or in what order a host thread sees the result. A host reading during the kernel can see stale values. For a true total, use atom.sys on memory the host can see, or read only after the host has synchronised with the kernel's end.

This is what membar.sys does in listing 6.3. The near-miss is to suspect lost atomic updates. Atomics on the GPU are never lost; the host is reading before the updates are guaranteed to be visible to it.

3. "PTX is the same on every GPU, so a PTX file written for Ada can be used for Pascal." Where does that stop being true? Use the table.

Answer

It stops at two points. First, the .target: PTX targeting sm_89 may use features that 6.1 lacks, and the driver will not JIT it downward at all (the compiler chapter's rule). Second, the instructions themselves. Code that uses fence, acquire loads or scoped loads needs sm_70 or later, and .cluster needs sm_90.

The language is shared; the feature set is versioned. That is exactly why bpftime compiles its trampoline for sm_61 and uses only membar and scoped atom, which work on all three benches (listing 6.3's .target sm_61).
