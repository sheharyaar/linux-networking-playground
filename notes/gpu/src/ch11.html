Chapter 11

Three generations: Pascal, Ada, Hopper

@@RT@@ · HW ISA — Every chapter so far has ended with a table across the three benches. This one puts them side by side on purpose: what stayed the same from 2016 to 2022, what the P5000 lacks, and what only the H100 has. It ends with the support matrix that decides which software runs where.

What stayed the same

Start with what did not change, because it is most of the machine. All three benches run warps of 32 threads. Each SM has 65,536 registers and 128 FP32 lanes. The P5000 and the laptop both have 20 SMs. The programming model, the grid, blocks, warps and shared memory, is the same, and so is the idea of PTX as a portable layer above each generation's SASS. Our three matvec kernels compile for all three from the same source. What changed is how much memory bandwidth feeds those lanes, what the SM can do besides FP32 arithmetic, and the tools and drivers that still support each one.

Diagram 11.1 puts the three benches on one roofline. From the P5000 to the H100, memory bandwidth grew 11.6 times, from 288 to 3,352 GB/s, and FP32 throughput 7.5 times. The tensor cores grew far more: the H100's dense FP16 matrix throughput is about 1,000 TFLOPS. Our matvec, at 0.5 FLOP per byte, sits on the sloped part of every roof, so on every bench its speed is set by bandwidth alone. The red point is a preview of the LLM chapters. Even 64 sequences decoding at once, which turns the matvec into a small matrix multiply with 64 FLOP per byte, leaves the H100 memory-bound.

Pascal: what the P5000 does not have

Pascal predates three things the rest of this document takes for granted. First, independent thread scheduling. A Pascal warp has one program counter for all 32 lanes. After a divergent branch, the hardware runs one path to completion, then the other, with no interleaving. The SASS shows it as SSY and SYNC where Ada and Hopper have BSSY and BSYNC. Code that waits inside a divergent branch for another lane of its own warp can hang on Pascal and work on Volta and later.

Second, tensor cores, and with them any fast low-precision path. On the P5000's GP104, FP16 arithmetic runs at 1/64 of the FP32 rate. What Pascal does have, from compute capability 6.1, is dp4a, an instruction that multiplies four pairs of 8-bit integers and adds the four products to a 32-bit sum in one step. That is why llama.cpp keeps a Pascal path: its quantised weights are small integers, and dp4a gives four multiply-adds per instruction (the llama.cpp chapter). Its build adds Pascal's 61-virtual only when the toolkit is older than CUDA 13 (llama.cpp/ggml/src/ggml-cuda/CMakeLists.txt:43–44).

Third, current software. CUDA 13.0 removed offline compilation for Pascal, so the P5000 needs a 12.x toolkit. The open kernel modules start at Turing, so it needs the proprietary module, and the R580 branch is reported as the last driver branch with Pascal support. Nsight Compute dropped Pascal in 2020.1, and vLLM needs compute capability 7.5. The P5000 customer runs llama.cpp.

For bpftime, Pascal is the baseline. Its kprobe pass compiles every eBPF probe to PTX for sm_61 (bpftime/attach/nv_attach_impl/pass/ptxpass_kprobe_entry/main.cpp:55), so the probe code itself uses nothing newer than Pascal. The final compile of the patched module is for the GPU it runs on. On the P5000 that compile needs a PTX compiler that still accepts sm_61, so expect to build bpftime against a CUDA 12.x toolkit there. That is untested here.

Ada: the laptop

The laptop's Ada SM is closest to the SM this document has been describing all along, so it needs the least new vocabulary. Compared with Pascal it has independent thread scheduling, a uniform datapath for values that are the same in every lane, and fourth-generation tensor cores that accept FP8 as well as FP16, BF16 and INT8. It also has cp.async, from the Ampere generation. A warp issues an asynchronous copy from global to shared memory and keeps working until it needs the data, instead of loading into registers and storing to shared memory itself. Its limits are lower than the other two in one place: 48 resident warps per SM against 64, as the scheduling chapter's occupancy sums showed.

What Ada lacks is everything in the next section. Code compiled for sm_90 or sm_90a does not run on it, because compute capability 8.9 is older than 9.0.

Hopper: what only the H100 has

Hopper adds a level to the scheduling hierarchy and two new ways to move data. A thread block cluster is a group of blocks that the work distributor guarantees to run at the same time on one GPC, a group of neighbouring SMs. The portable maximum is 8 blocks per cluster, and the H100 allows 16 if the kernel opts in. Blocks of one cluster can load, store and do atomics on each other's shared memory. That is distributed shared memory, faster than a round trip through global memory, and it gives blocks a way to cooperate that the scheduling chapter's blocks never had.

The Tensor Memory Accelerator (TMA) is an asynchronous copy unit. One thread describes a tile of a tensor of 1 to 5 dimensions. The TMA moves the tile between global and shared memory, or between the shared memories of a cluster, and counts the arriving bytes on an mbarrier, a barrier object in shared memory that warps wait on. The warps compute no addresses and issue no loads. A kernel can dedicate a few warps to issuing TMA copies and leave the rest to compute.

The compute side is wgmma, warpgroup matrix multiply-accumulate. A warpgroup is four contiguous warps whose first warp's rank is a multiple of 4. Together they issue one asynchronous matrix multiply on the tensor cores, reading its operands from shared memory, where the TMA left them; one operand may come from registers instead. Hopper's tensor cores also take FP8.

There is a catch in the target name. wgmma needs the target sm_90a, with a letter on the end. The PTX manual explains the suffix: generations normally follow an "onion layer model" in which code for one target runs on all later ones, and targets ending in a are the exception. PTX or SASS for sm_90a runs on compute capability 9.0 and nothing else, ever. A library shipped with only sm_90a code needs a rebuild for the next generation.

It matters for bpftime in a specific way. bpftime picks the target for its final compile from the device's compute capability, which on an H100 gives the string sm_90 (bpftime/attach/nv_attach_impl/nv_attach_utils.cpp:94–160). An application whose PTX uses wgmma cannot be compiled for sm_90. The environment variable BPFTIME_SM_ARCH overrides the choice, so expect to set it to sm_90a for such applications. This is also untested here, and it is the first thing to try on the H100.

Try it

Repeat the scheduling chapter's occupancy sum for the H100 from real register counts, without an H100. Ask ptxas for the resource use of each kernel for sm_90:

cd lab/gpu
nvcc -O3 -arch=sm_90 --resource-usage -c matvec.cu -o /dev/null 2>&1 \
    | grep -E 'entry function|registers'

You should see 29, 32 and 44 registers, the SASS chapter's numbers. Round up to multiples of 8, multiply by 256 threads, divide into 65,536, and cap at 64 warps and 32 blocks. You should get 8, 8 and 5 blocks per SM. Then explain why the float4 kernel gets more warps per SM on the H100, 40 against the laptop's 32, and yet a slightly lower share of the maximum, 62.5% against 67%.

Recap

All three benches share warps of 32, 65,536 registers and 128 FP32 lanes per SM, and the same programming model. From the P5000 to the H100, bandwidth grew 11.6 times and FP32 7.5 times, so our memory-bound matvec gains by bandwidth alone; even 64 decoding sequences stay memory-bound on the H100. Pascal lacks independent thread scheduling, tensor cores and current tools, has dp4a, and needs CUDA 12.x. Ada adds FP8 tensor cores and cp.async. Hopper adds clusters with distributed shared memory, the TMA with mbarriers, and wgmma, which needs the non-portable sm_90a target, a detail bpftime's automatic target choice does not handle.

New words in this chapter

dp4a
A Pascal-and-later instruction: four 8-bit multiply-adds into a 32-bit sum.
cp.async
An asynchronous copy from global to shared memory, from the Ampere generation.
thread block cluster
A group of blocks guaranteed to run at the same time on one GPC (Hopper).
GPC
Graphics processing cluster: a group of neighbouring SMs.
distributed shared memory
Loads, stores and atomics on the shared memory of another block in the cluster.
Tensor Memory Accelerator (TMA)
A per-SM unit that copies tensor tiles between global and shared memory.
mbarrier
A barrier object in shared memory that can count arriving bytes as well as threads.
warpgroup
Four contiguous warps that issue one wgmma together.
wgmma
Hopper's asynchronous warpgroup matrix multiply-accumulate, from shared memory.
sm_90a
An architecture-specific target: its code runs only on compute capability 9.0.

Check yourself

1. Predict the value: when a language model generates a token, each sequence uses each FP16 weight (2 bytes) for one multiply-add (2 FLOP), so a batch of B sequences reads each weight once for B multiply-adds. About how large must B be before the H100's FP16 tensor cores become the limit on speed?

Answer

About 300 sequences. The arithmetic intensity is 2B FLOP per 2 bytes, so B FLOP per byte. The tensor-core ridge is 1,000,000 GFLOPS / 3,352 GB/s ≈ 298 FLOP per byte (diagram 11.1). Below about 300 sequences, the weights take longer to read than to multiply.

It is an upper bound on the easy case. The cache of earlier tokens that the LLM chapters introduce adds bytes per sequence that are not shared across the batch, so in practice token generation stays memory-bound at even larger batches. The near-miss is to use the FP32 ridge of 20. Token generation runs on the tensor cores, whose roof is 15 times higher.

2. A team builds its kernels with -gencode arch=compute_90a,code=sm_90a only, and the library works on their H100s. What happens on a next-generation GPU with compute capability 10.0, and what would they need to ship to cover it?

Answer

It fails to load, with no kernel image for the device. The fatbin holds sm_90a SASS, which runs only on 9.0, and no PTX that the driver could compile for 10.0. Even compute_90a PTX would not help, because a targets are outside the onion layer model: their PTX cannot be compiled for later generations.

They need to add either SASS built for the new target, or plain compute_90 PTX as a fallback, which the driver can compile for anything newer. That fallback cannot use wgmma, so it will be slower. The near-miss is to think "PTX is forward compatible" covers every PTX. It covers PTX for targets without the a.

3. The P5000 customer asks for GPU probes on their llama.cpp server. List what has to be different on their machine from the laptop's setup, layer by layer.

Answer

The driver is the proprietary module from a branch that still supports Pascal, R580 or older. The toolkit is CUDA 12.x, for llama.cpp's 61-virtual build and for any ptxas or PTX compiler that must target sm_61. bpftime must be built against that toolkit, since its final compile targets the device's sm_61. For measuring, Nsight Systems 2025.3 or older and nvprof replace current Nsight tools.

What stays the same is the probe code. bpftime already compiles probes for sm_61, and helpers like %globaltimer and %smid exist on Pascal. The near-miss is to think the probe must change. The probe is fine; everything under it is older.
