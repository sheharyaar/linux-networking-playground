Chapter 2

Inside a streaming multiprocessor

@@RT@@ · HW — Last chapter grouped our matvec's threads into warps of 32. Now we find where a warp runs: the streaming multiprocessor, the unit a GPU is built from twenty copies of on the laptop and 132 on the H100.

Optional neighbour: the GPU-sharing dossier's The silicon (chapter 1) maps the whole die, with its graphics clusters, memory controllers and copy engines. This chapter zooms into one of the units on that map and looks at it as a programmer.

The chip is made of SMs

A GPU is mostly many copies of one block, the streaming multiprocessor, or SM. Each SM is a complete processor for warps: it fetches instructions, keeps the registers of every thread it is running, and has its own arithmetic units and its own on-chip memory. The laptop's RTX 4050 has 20 SMs. The customer's P5000 also has 20. An H100 SXM5 has 132. The rest of the die is wiring between the SMs and memory, plus a few fixed-function engines.

When a kernel launches, its threads are handed out to SMs in groups, and each SM runs many warps at once. A warp that has been placed on an SM is a resident warp. It stays on that SM, with its registers allocated there, until every thread in it has finished. Under normal running nothing moves it elsewhere.

One SM, opened up

An Ada SM is split into four SM sub-partitions, and almost everything is per sub-partition. Each one has a warp scheduler, which every cycle picks one resident warp that is ready to go and issues one instruction for it. That one chance per cycle to start an instruction is an issue slot. With four schedulers, an SM can start up to four warp-instructions per cycle.

Each sub-partition also has its own slice of the register file, the SM's store of registers for every resident thread: 16,384 registers of 32 bits, 64 KB per sub-partition and 256 KB for the whole SM. That is larger than the SM's cache, and it is the reason the next section works. Each sub-partition has 32 FP32 lanes, FP32 being the 4-byte floating-point format, and each lane does one multiply-add per cycle; on Ada, 16 of them can also do integer arithmetic. So one multiply-add instruction for a warp fills one sub-partition's lanes for one cycle.

The remaining units are fewer and more specialised. A tensor core does a small matrix multiply, for example 16 × 8 × 16, as one instruction for a whole warp. It matters enormously for matmul and not at all for our matvec. A special function unit, or SFU, computes things like exponentials, sines and reciprocal square roots. The language-model chapters need its exponentials. A load/store unit turns a warp's memory instructions into requests to the memory system.

Below the four sub-partitions sits one pool of fast on-chip storage, 128 KB on Ada. Part of it is the L1 cache, a cache of recently used memory, managed by hardware like a CPU's. The rest is shared memory, a scratchpad the kernel's own code reads and writes directly, which the threads of one launch group can use to hand data to each other. The kernel says how it wants the pool split, up to 100 KB of shared memory on Ada.

Latency hiding: why the register file is so big

A load from the GPU's main memory takes hundreds of cycles to come back. The microbenchmark papers in the reading list measure it per generation. A CPU core attacks that wait inside one thread, with caches, prefetching and out-of-order execution. An SM does something else: when one warp has to wait for its data, the scheduler issues an instruction from a different warp that is ready. If enough warps are resident, there is always one ready, and the arithmetic units never sit idle. This is latency hiding.

The switch costs nothing. A CPU switching threads has to save one set of registers and load another. An SM keeps the registers of every resident warp in the register file at the same time, so "switching" just means the scheduler picks a different warp's instruction on the next cycle. That is what the 256 KB of registers per SM buys.

Diagram 2.2 runs a tiny model of one scheduler. Every warp loops over the same five instructions: two independent arithmetic instructions, a load, then two instructions that use the loaded value and so must wait for it. The load takes 14 cycles here. Real memory takes far longer, which only makes the effect stronger.

The model also shows the limit. Eight warps leave six idle cycles in 44. An Ada sub-partition can hold at most 12 resident warps (48 per SM), and real latencies are much longer than 14 cycles. So warps alone cannot hide everything. The other half of the answer is giving each warp several independent loads in flight before it needs the first result. The compiler does this for our naive matvec by unrolling its loop. In the machine code for Ada, which a later chapter reads line by line, each thread issues twenty-two loads before its first multiply-add.

Occupancy, and the version number of an SM

Occupancy is the number of resident warps on an SM divided by the most the SM can hold. On Ada the maximum is 48 warps; on Pascal and Hopper it is 64. Several resources cap it, and registers are the first one you meet. The 65,536 registers of an SM are shared by every resident thread, so a kernel whose threads each need many registers fits fewer warps.

You can read the register count of every kernel out of the compiled file. For the three kernels of lab/gpu/matvec.cu compiled for Ada, cuobjdump -res-usage reports 38, 40 and 53 registers per thread for the naive, warp-per-row and float4 versions. Registers are handed out per warp, rounded up to a multiple of 8 per thread. The warp-per-row kernel then needs 40 × 32 = 1,280 registers per warp, and 65,536 / 1,280 = 51 warps would fit. The SM's cap of 48 binds first, so registers do not limit it. The float4 kernel rounds 53 up to 56, needs 1,792 per warp, and fits 36 warps: 75% occupancy before any other limit is applied. The scheduling chapter adds the other limits, and one of them lowers that number again.

Higher occupancy means more warps to choose from when hiding latency. It does not always mean faster code, because a kernel with fewer, busier warps and more loads in flight per warp can hide latency just as well.

Each SM design has a version number, its compute capability, written major.minor. Pascal's GP104 is 6.1, Ada is 8.9, Hopper is 9.0. The number decides which instructions exist and what every limit in this chapter is. The compiler spells it sm_61, sm_89, sm_90, and the compiler chapter explains why there is also a second spelling.

Recap

A GPU is mostly SMs: 20 on the laptop and on the P5000, 132 on an H100. An Ada SM has four sub-partitions, each with a warp scheduler that issues one instruction per cycle for one ready warp, a 64 KB slice of registers, and 32 FP32 lanes, over a shared 128 KB pool of L1 cache and shared memory. Because every resident warp's registers stay in the register file, switching warps is free, and the SM hides memory latency by always issuing from some warp that is ready. Occupancy, resident warps over the maximum, is capped by registers among other things; compute capability is the version number that fixes all these limits.

Check yourself

1. Predict the value: compiled for Hopper, matvec_warp4 uses 44 registers per thread. Using the allocation rule from this chapter, how many of its warps fit on one H100 SM by registers alone, and what occupancy is that?

Answer

42 warps, and 42 / 64 ≈ 66% occupancy. 44 is not a multiple of 8, so it rounds up to 48. A warp then needs 48 × 32 = 1,536 registers, and 65,536 / 1,536 = 42.7, which rounds down to 42: half a warp cannot be resident.

Two near-misses. Skipping the rounding gives 65,536 / (44 × 32) = 46.5, so 46 warps, and that is the mistake this question is built to catch. Dividing by 48, Ada's warp cap, is the other; Hopper's cap is 64. The register count comes from cuobjdump -res-usage on the compiled sm_90 file (the Try-it box). Diagram 7.3, in a later chapter, draws the whole staircase.

2. A profiler says all 48 warps on an SM are resident, but its schedulers issue an instruction on only a quarter of the cycles. What are the warps doing, and why would raising occupancy not help?

Answer

They are waiting. A scheduler can only issue from a warp whose next instruction is ready, and here most warps are stuck on a load whose data has not arrived (the grey cycles in diagram 2.2, with many more warps).

Occupancy is already at its maximum, 48 of 48, so there are no more warps to add. What helps is more independent work per warp before it needs the data, such as several loads in flight, or less waiting per load. The near-miss is "occupancy is too low": being resident and being ready are different states, and the profiler counted the first.

3. "Switching between warps costs nothing." Where does that stop being true?

Answer

It is true only between resident warps, because only their registers are already in the register file. A warp that is not yet on the SM cannot be switched in at all: it has to wait until enough resident threads finish to free their registers and their place.

The cost has also moved rather than gone away. Every resident warp occupies registers all the time, so a kernel pays for free switching with a cap on how many warps fit, which is occupancy. And switching between different programs that share one GPU is a real save-and-restore, which the GPU-sharing dossier's time-slicing chapter covers.
