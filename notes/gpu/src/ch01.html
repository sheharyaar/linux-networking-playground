Chapter 1

Four ways to be parallel

@@RT@@ · HW — Last chapter we chose our object: a matvec made of 16.8 million multiplications that do not depend on each other. This chapter asks how a machine can do many of them at once. The answer comes in four shapes, and the GPU uses a fifth that borrows from two of them.

Flynn's four boxes

In 1972 Michael Flynn sorted computers by two counts, and the sorting is still the clearest way in. The first count is instruction streams: how many separate sequences of instructions the machine follows at once, each with its own program counter. The second is data streams: how many separate pieces of data those instructions work on at once. One or many, times one or many, gives four boxes. This is Flynn's taxonomy.

SISD, single instruction stream and single data stream, is one plain CPU core running ordinary code. The inner loop of our matvec, sum += w[j] * x[j], compiled without vector instructions, does one multiply-add per instruction. SIMD, single instruction and multiple data, is one instruction that works on several numbers side by side. MIMD, multiple instructions and multiple data, is several independent processors, each following its own program: the eight cores of the laptop's Ryzen are MIMD. The fourth box, many instruction streams on one data stream, is almost never built, and nothing here needs it.

SIMD on the CPU you already have

The laptop's CPU is a Ryzen 7 8845HS, and it has AVX-512. A vector register is a wide register that holds several numbers. An AVX-512 register (zmm0 to zmm31) is 512 bits wide, which is sixteen 4-byte floats. Each slot is a lane. One instruction then works on all sixteen lanes at once. Here is one row of our matvec written with AVX-512 intrinsics, and the inner loop that gcc -O2 -mavx512f made of it:

__m512 acc = _mm512_setzero_ps();
for (int j = 0; j < n; j += 16)
    acc = _mm512_fmadd_ps(_mm512_loadu_ps(w + j), _mm512_loadu_ps(x + j), acc);
return _mm512_reduce_add_ps(acc);

    vmovups      (%rdi,%rax,4), %zmm2          # 16 numbers of the row of W
    vfmadd231ps  (%rsi,%rax,4), %zmm2, %zmm0   # 16 multiply-adds, one instruction

Listing 1.1 — one row of the matvec, as CPU SIMD. Compiled on this laptop with gcc.

Two things about SIMD matter for what follows. First, the program is written in vectors. The code says "sixteen at a time", the loop steps by 16, and the data has to be laid out so that sixteen useful numbers sit next to each other in memory. Second, lanes cannot easily go their own way. If some lanes should skip a step, the programmer uses a mask: a set of bits, one per lane, that switches lanes off for one instruction. AVX-512 has eight mask registers for this, k0 to k7. Every branch has to be turned into masks by hand or by the compiler.

SIMT: write one thread, run thirty-two

A GPU programmer writes code for one thread. A GPU thread is one running copy of the kernel's function, with its own registers and its own index number, and that index is how it knows which part of the data is its own. In our first kernel, thread number row computes y[row] with a plain scalar loop. Nothing in the source says "thirty-two at a time".

The hardware groups the threads anyway. Thirty-two threads with consecutive index numbers form a warp, and the GPU fetches and issues each instruction once for the whole warp. Each thread of the warp occupies one lane, so one multiply-add instruction does thirty-two multiply-adds, exactly as one AVX-512 instruction does sixteen. NVIDIA calls this SIMT, single instruction, multiple threads.

The difference from SIMD is where the grouping lives. In SIMD it is in the program: the code is written in vectors. In SIMT it is in the hardware, and the program describes one thread. Each lane can load from its own unrelated address, which SIMD can only do with special gather instructions. And each lane can take its own side of a branch, which SIMD handles only through masks the program builds. A GPU builds those masks itself.

When threads disagree: divergence

Lanes may disagree at a branch. Some threads of a warp take the if, the others take the else. That is divergence. The warp still issues one instruction at a time, so it runs the two sides one after the other. While it runs one side, the lanes that chose the other side are switched off by an active mask, the GPU's own per-lane on/off bits. When both sides are done, the paths meet again and the warp continues with all lanes on. That meeting point is reconvergence.

The cost is simple to state: a divergent branch costs the time of both sides added together, and every lane waits for the slower combination. Diagram 1.2 shows one warp running if (lane < 20) A(); else B();, where A takes 10 cycles and B takes 20.

Our matvec barely diverges, and you can check that in the source. The naive kernel's only branch is if (row >= d) return;, which with d = 4096 threads launched in groups of 256 is never true for any thread. The warp-per-row kernel ends with if (lane == 0) y[warp] = sum;, which idles 31 lanes for exactly one store. Divergence becomes expensive in code with data-dependent branches inside loops. It also matters to probes later: an eBPF program injected into a kernel runs in every lane, and an if in your probe diverges like any other.

One program counter per warp, or one per thread

How does the warp remember which lanes are waiting, and where? Before 2017, NVIDIA GPUs kept one program counter per warp, plus a small stack of masks that the compiler pushed at each branch and popped at each reconvergence point. Pascal works this way. Starting with Volta in 2017, and so on Ada and Hopper, each thread has its own program counter and call stack in hardware. This is independent thread scheduling. The warp still issues one instruction for the lanes that share a program counter, but the scheduler can now switch between the divergent groups whenever it likes, rather than finishing one side before starting the other.

That sounds like a detail until two lanes of one warp wait for each other. Suppose lane 0 takes a lock and lane 1 spins on it:

if (lane == 0) { lock(); work(); unlock(); }
if (lane == 1) { while (!try_lock()) ; work(); unlock(); }

Listing 1.2 — two lanes of one warp and one lock. Illustrative.

With one program counter per warp, the hardware runs one group of lanes until it reaches the reconvergence point. If it picks lane 1's spin loop first, lane 1 spins forever, because lane 0 can only run after lane 1's side is done, and lane 1's side is never done. On Pascal this kernel can hang. With independent thread scheduling the scheduler eventually runs lane 0, lane 0 releases the lock, and lane 1 gets it. This is why every warp-level intrinsic in modern CUDA takes an explicit mask of which lanes take part, and why code that sends one request at a time from a warp, as bpftime's helper calls do, walks the lanes in a deliberate loop.

Across warps, there was never any lockstep. Different warps are independent: one can be inside a branch while another is at the top of the loop. Counted warp by warp, a GPU is a MIMD machine with a very large number of instruction streams. Counted lane by lane inside one warp, it is SIMD with masks it manages itself. SIMT is the name for that combination.

Try it

See the SIMD width of the CPU you are sitting at, then compile the dot product yourself:

grep -o 'avx512[a-z_0-9]*' /proc/cpuinfo | sort -u   # avx512f = base set
gcc -O2 -mavx512f -S dot.c -o - | grep zmm           # dot.c = listing 1.1

Count the lanes: a zmm register is 512 bits, so 16 floats. A warp is 32 threads. The GPU's advantage does not come from wider lanes. It comes from how many warps one chip keeps in flight at once, which is the next chapter.

Recap

Flynn's taxonomy sorts machines by instruction streams and data streams: SISD is a scalar core, SIMD is one instruction over many lanes, MIMD is many independent programs. A GPU is SIMT: the program is written for one thread, the hardware groups 32 threads into a warp and issues each instruction once for all of them. When lanes disagree at a branch, the warp runs both sides one after the other under an active mask and reconverges afterwards, so divergence costs both sides' time. Since Volta, and so on Ada and Hopper but not on Pascal, each thread has its own program counter, which lets lanes of one warp wait on each other without hanging.

Check yourself

1. Predict the value: a warp runs if (lane < 8) A(); else B();. A takes 10 cycles and B takes 30. How many cycles does the warp spend in the branch, and what fraction of its lane-cycles do useful work?

Answer

40 cycles, and 62.5% of lane-cycles are useful. The two sides run one after the other (diagram 1.2), so 10 + 30 = 40. Useful lane-cycles are 8 × 10 + 24 × 30 = 800, out of 32 × 40 = 1280 available.

The near-miss is 30 cycles, "the slower side". That would be true only if the two groups of lanes ran at the same time. Within one warp they never do, even with independent thread scheduling: that feature lets the groups interleave, but each instruction still issues for one group at a time.

2. A kernel in which lane 1 of each warp spins on a flag that lane 0 sets inside an if finishes on the laptop and hangs on the customer's P5000. Same source, same data. What is different?

Answer

Pascal has one program counter per warp. If it starts lane 1's spinning side first, it will not run lane 0's side until the spinning side reaches reconvergence, which it never does. The warp hangs.

Ada has independent thread scheduling (listing 1.2 and the table above), so the scheduler eventually switches to lane 0's group, the flag is set, and the spin ends. The near-miss is "the P5000 is slower, so it is a timeout". No amount of waiting helps: lane 0's instruction is never issued at all.

3. "With SIMT the programmer writes scalar code, so warps never need to be thought about." Name two situations from this chapter where that sentence stops being true, and the mechanism behind each.

Answer

First, speed with data-dependent branches: lanes of one warp that disagree make the warp pay for both sides, because it issues for one group at a time under the active mask. Second, correctness when lanes of one warp wait on each other: on Pascal, one program counter per warp can hang such code. With independent thread scheduling it makes progress, but warp-level operations still need an explicit mask of participating lanes.

A third, which the next chapters add: which addresses neighbouring lanes load together decides how fast memory runs. The sentence is only safe for code whose lanes take the same path and never talk to each other.
