Chapter 8

The host side: streams, pinned memory, the launch path

@@RT@@ · CUDA — The language part (Part II) turned our matvec into SASS inside a fatbin, and showed the driver loading it into a context. Now the program runs it. This chapter is everything that happens on the host between "launch matvec_warp" and the first warp starting: the queues, the memory the host and the GPU can both see, and the path a launch takes down to the hardware.

Optional neighbours: the GPU-sharing dossier's How a launch reaches the silicon (chapter 2) follows the same launch below the driver, through channels and pushbuffers. The SR-IOV dossier's Just enough PCIe (chapter 1) covers the DMA and MMIO that this chapter uses as words.

Two APIs, one driver

The CUDA runtime is a convenience layer: every runtime call becomes one or more driver API calls. The runtime creates a context for you, the primary context, one per GPU per process. It loads modules from the registered fatbins, and it turns kernel<<<g, b>>>(args) into a driver launch. With the driver API you do each step yourself: cuCtxCreate or retain the primary context, cuModuleLoadData, cuModuleGetFunction to get a CUfunction, the driver's handle for one kernel in one loaded module, and cuLaunchKernel. Both roads end in cuLaunchKernel-like entry points in libcuda.so, which is why a tool that hooks the driver sees launches from both.

Streams and events

A stream is an ordered queue of GPU work: kernel launches, copies, memory sets. Work in one stream runs in the order it was queued, each item starting only after the one before has finished. Work in different streams has no order between them, so the GPU may run it at the same time. Every launch and every asynchronous copy names a stream; the fourth value inside <<<…>>> is the stream.

If you name none, you get the default stream, and it has a historical quirk. The legacy default stream waits for work in every other stream of the context and makes them wait for it, which serialises programs that thought they were concurrent. Compiling with --default-stream per-thread gives each host thread its own default stream that behaves like an ordinary one. The runtime then exports per-thread variants of its entry points, with a _ptsz suffix such as cudaLaunchKernel_ptsz, which is why bpftime hooks both names.

An event is a marker queued into a stream. When the GPU reaches it, it records a timestamp. cudaEventRecord queues one, cudaEventSynchronize waits until it has been reached, and cudaEventElapsedTime gives the milliseconds between two of them. The lab program times every kernel this way (matvec.cu:104–122): one event before 200 launches, one after, both measured on the GPU's own clock, so host-side noise stays out.

Memory the host and the GPU can both see

Copies between host and device are done by the GPU's copy engines, DMA engines that move data across PCIe while the SMs do other work. A DMA engine needs host memory that stays at a fixed physical address for the whole transfer. Ordinary pageable memory, from malloc, can be moved or swapped out by the host kernel at any time. So cudaMemcpy from a pageable buffer first copies it, with the CPU, into a hidden buffer the driver has locked, and DMAs from there. Pinned memory, also called page-locked, is host memory locked in place so that the copy engine can read it directly. cudaMallocHost allocates it; cudaHostRegister pins memory you already have. Pinned memory is what makes cudaMemcpyAsync truly asynchronous, and what lets copies overlap kernels.

Pinned memory can go one step further. Mapped memory, or zero-copy memory, is pinned host memory that is also mapped into the GPU's address space. A kernel can then load and store it directly: every access crosses PCIe, so it is slow for bulk data, but no copy is needed at all, and the host sees the writes. bpftime relies on exactly this. Its shared-memory segment, the one that holds the request area of listing 6.3, is registered in the target process with one call:

cudaError_t err =
        cudaHostRegister(base_addr, seg_size, cudaHostRegisterMapped);

Listing 8.1 — bpftime/runtime/src/bpftime_shm_internal.cpp:1243–1244. The whole bpftime shared segment, pinned and mapped into the GPU's address space.

Three more kinds complete the picture. Unified virtual addressing (UVA) puts host and device allocations in one 64-bit address space, so the value of a pointer says which memory it is in, and cudaMemcpy can work out the direction itself. Managed memory, from cudaMallocManaged, is a single allocation valid on both sides: pages move between host and GPU on demand, when one side touches a page the other side holds, through hardware page faults that Pascal introduced. And CUDA IPC lets one process share a device allocation with another, through a handle from cuIpcGetMemHandle that the other process opens. bpftime's GPU array maps use it: the bpftime process that loads the probe allocates them in device memory, and the process being probed opens them (runtime/src/bpf_map/gpu/nv_gpu_per_thread_array_map.cpp:74).

The launch, all the way down

Here is one launch of matvec_warp, from the call to the first warp. The runtime finds the CUfunction for the stub, packs the five arguments, and calls into the driver. The driver writes the launch, as GPU commands, into a pushbuffer: a ring of commands in memory the GPU can read, belonging to one hardware queue. Then it writes the new end position to a doorbell, a register on the GPU mapped into the process's address space. The GPU's front end sees the doorbell change, fetches the commands, and hands the grid to the block scheduler, which places blocks on SMs.

Notice what is missing. After setup there is no system call. The pushbuffer and the doorbell were mapped into the process when the context and its queues were created, so a launch is a few memory writes in user space. That is why a launch costs only a few microseconds of CPU time. It is also why a uprobe on cuLaunchKernel sees every launch and a probe in the host kernel sees none of them.

The time from the launch call to the first warp running is launch latency. On an idle GPU it is microseconds. When a stream already has work queued, the new kernel also waits for everything ahead of it. bpftime's launchlate example measures exactly this gap, with a uprobe on cudaLaunchKernel on the host side and a GPU probe at the kernel's entry. For a kernel like ours, which takes a few hundred microseconds, a few microseconds of launch cost is noise. For the tiny kernels a language model runs for each new token, which can take tens of microseconds each, the CPU's launch work can become the limit: the GPU finishes each kernel before the CPU has queued the next.

CUDA graphs: launch a whole sequence at once

A CUDA graph records a fixed sequence of kernels and copies, with their dependencies, once, and then launches the whole sequence with a single call. You can build one node by node, or capture it: begin capture on a stream, run your normal launches, end capture. The launches are recorded rather than run. cudaGraphInstantiate prepares the graph for launch, and cudaGraphLaunch runs it, as often as you like. The CPU cost of a hundred launches becomes the cost of one.

Graphs matter twice in this document. vLLM captures the step that makes each new token as CUDA graphs, which is a large part of why it is fast. And a graph launch does not call cudaLaunchKernel once per kernel, so a uprobe on that function sees nothing while a graph runs. A tool that wants to change which kernel runs has to act when the graph is built. bpftime does it in two places. Launches made during stream capture still go through its launch hooks, so the captured graph records the patched kernel. Graphs built node by node go through cuGraphAddKernelNode and the calls that set node parameters, which bpftime also hooks to swap in the patched kernel (attach/nv_attach_impl/nv_attach_impl_frida_setup.cpp:625–776). A graph captured before bpftime attached keeps the original kernel.

Try it

Measure the pageable penalty with the bandwidth test in CUDA's samples, or with ten lines of your own: time cudaMemcpy of 64 MiB from a malloc buffer, then from a cudaMallocHost buffer, using events as the lab does. Then look at where launches go with a uprobe, which needs nothing new:

sudo bpftrace -c './out/matvec_shared 4096 4096 20' -e '
  uprobe:/opt/cuda/lib64/libcudart.so.13:*LaunchKernel*,
  uprobe:/usr/lib/libcuda.so.1:cuLaunchKernel* { @[probe] = count(); }'

Use the -cudart shared build from the compiler chapter, or the runtime probe has nothing to attach to. The wildcards catch cudaLaunchKernel, __cudaLaunchKernel and their _ptsz twins. Which ones fire, and how often, tells you which entry a CUDA 13 binary uses. That is the same question bpftime has to answer on this laptop, so keep the output.

Recap

Runtime calls become driver calls, and every launch ends in a cuLaunchKernel-like entry of libcuda.so. Work is queued on streams, in order within a stream and unordered across them; events timestamp the GPU's progress. Copy engines DMA from pinned memory; pageable memory costs an extra CPU copy; mapped memory lets kernels read and write host memory directly, which is how bpftime's GPU code talks to the host; CUDA IPC shares device memory between processes, which is how its GPU maps cross from the loading process to the probed one. A launch is user-space writes to a pushbuffer and a doorbell, with no system call. CUDA graphs launch whole sequences with one call, and bypass per-kernel launch hooks.

Check yourself

1. Predict the value: on the laptop, copying W (64 MiB) to the GPU takes T₁ from pinned memory. The matvec on that W takes about 311 µs at best. If PCIe gives roughly 12 GB/s in practice, about how long is T₁, and how many matvecs on that W would the GPU need to run before copying it once is worth it?

Answer

About 5.6 ms, which is the time of roughly 18 matvecs. 67.1 MB / 12 GB/s ≈ 5.6 ms, and 5.6 ms / 311 µs ≈ 18. The copy moves the same bytes as one matvec, across a link about 18 times slower than the GPU's own memory.

This is why LLM servers load weights onto the GPU once and keep them there, and why anything that must cross PCIe per token, like a probe's call to the host, is expensive. The 12 GB/s is an assumption for a laptop link; measure yours. The near-miss is to compare against the GPU's arithmetic speed. The copy competes with memory bandwidth.

2. A program records CUDA graphs at start-up and replays them. A uprobe on cudaLaunchKernel shows a burst of calls at start-up and almost none afterwards, while nvidia-smi shows the GPU busy the whole time. What is happening, and where would a probe have to sit to see each kernel?

Answer

The burst is stream capture: during capture the launches are recorded into the graph, which is the only time the program calls cudaLaunchKernel. Afterwards each cudaGraphLaunch runs all of the recorded kernels without calling the launch function again (diagram 8.3).

To see each kernel you need to be inside the kernels themselves, which is what a bpftime GPU probe is, and the probe has to be in place when the graph is captured, because that is when the graph's kernels are chosen. A uprobe on cudaGraphLaunch fires once per replay, however many kernels the graph holds. The near-miss is that the probe is broken. It works; the call it watches stopped happening.

3. "A launch involves no system call." Where does the host kernel still take part in running a kernel, so that a tracepoint or kprobe in it would fire?

Answer

At setup and at the edges. Creating the context and its queues, allocating device memory, pinning memory with cudaHostRegister, and mapping the doorbell all go through ioctls on /dev/nvidia*. Waits can block in the host kernel: a synchronising call may sleep until an interrupt. Faults on managed memory are serviced by the driver in the host kernel.

The sentence is about the per-launch path of diagram 8.2: once the pushbuffer and the doorbell are mapped, queuing work is user-space stores. So kernel-side eBPF sees the program's setup, its waits and its page migrations, and never its launches.
