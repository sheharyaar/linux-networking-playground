Chapter 16

Prefill, decode and the KV cache

@@RT@@ · LLM — The last chapter ran the model for one new token. A real request runs it on a whole prompt first, then once per generated token, and the two runs have opposite characters: one is limited by arithmetic, the other by memory. This chapter names the two phases, introduces the cache that makes the second one affordable, and turns both into the latency numbers servers report: time to first token and time per token.

Two phases with opposite characters

A request arrives with a prompt of P tokens. The server first runs the model once over all P tokens together. This is prefill. Every weight matrix now multiplies a matrix with P columns, one per token, instead of a single vector: a matrix-matrix multiply, a GEMM. Each weight is read once and used P times, so in 16-bit the arithmetic intensity is about P FLOP per byte. A prompt of a few hundred tokens is already past the H100's tensor-core ridge, so prefill is compute-bound. Prefill leaves two results. Its logits for the last position give the first generated token. And every layer's key and value for every prompt position are kept, as the next section explains.

Then the server generates. Each step runs the model on one new token per sequence. This is decode, and for a single sequence it is exactly the last chapter's 169 matvecs: memory-bound, about 1 FLOP per byte. Decode repeats until the model emits an end-of-sequence token or reaches a length limit.

The two phases map onto the two numbers every LLM server reports. Time to first token (TTFT) is the time from the request's arrival to its first token: waiting in the queue, then prefill, then sampling. Inter-token latency (ITL), also called time per output token, is the time between later tokens, which is one decode step. vLLM measures TTFT from the moment the request arrived at the engine (vllm/v1/metrics/stats.py:473, with the arrival time set at vllm/v1/engine/input_processor.py:370), so queueing counts.

The KV cache

Diagram 15.2 showed that when a new token attends, the keys and values of the earlier tokens are exactly what they were when those tokens were new. So the server computes each token's key and value once, in every layer, and keeps them. The store is the KV cache. Each decode step writes one new key and value per layer and reads all the stored ones. Without the cache, step t would recompute keys and values for all t tokens so far, and generating n tokens would cost work growing with n².

The cache's size per token follows from the model's shape: a key and a value, in every layer, for every key-value head, of the head's length, in the cache's number format. For Qwen2.5-0.5B in 16-bit that is 2 × 24 layers × 2 heads × 64 × 2 bytes = 12,288 bytes per token. In llama.cpp the cache is two tensors per layer, one for keys and one for values, each with one row of 128 entries per token slot (llama.cpp/src/llama-kv-cache.cpp:233–234). It is F16 unless you choose otherwise (llama.cpp/common/common.h:589), and its size is printed at start-up (llama-kv-cache.cpp:300–303).

What one decode step reads

A server rarely decodes one sequence at a time. It runs a batch of B sequences in each step, and the weights are read once for the whole batch: every weight matrix multiplies a B-column matrix, and the intensity rises to about B FLOP per byte. The cache is different. Each sequence has its own keys and values, and each step reads all of them. So one decode step moves, at least, the weights once plus every cached token of every sequence in the batch.

Put numbers on it for Llama-3.1-8B in BF16 on an H100. The weights are about 16 GB. A token reads all of them except the embedding table, of which it reads one row, so about 15 GB, which take 4.5 ms to read at 3,352 GB/s. One sequence with 4,096 tokens of context adds 512 MiB of cache, another 0.16 ms. Sixty-four such sequences add 34 GB, 10.3 ms. So a step for 64 users takes at least about 15 ms instead of 5. Each user sees a token every 15 ms instead of every 5. The server makes 64 tokens per step instead of one, about 4,300 tokens per second instead of 200. Batching buys throughput with latency, and at long contexts the cache is most of what each step reads.

Prefill on the same machine is the other extreme. A 4,096-token prompt for Llama-3.1-8B is about 2 × 8 billion × 4,096 ≈ 66 TFLOP for the matrices, plus attention. Attention's work grows with P², because each of P tokens attends to all those before it, about P²/2 pairs. At the H100's roof of about 1,000 TFLOPS that is some 70 ms at best, and real kernels reach a fraction of the roof. So one long prompt takes as long as about 14 decode steps of a single sequence, or several of a full batch of 64, and every sequence in the same batch waits for it. That is the tension the next chapter's scheduler has to manage.

Where the time goes, for observation

Put the last two sections together and you have the map the language-model part (Part V) has been building towards. TTFT is queue time plus prefill. Prefill time is large GEMMs, whose speed is set by the tensor cores, plus attention over P²/2 token pairs. ITL is one decode step for the whole batch. It is set by memory: the weights once, through GEMV-like kernels with B columns, and the cache of every sequence, through attention kernels whose time grows with context. A probe that times the GEMMs and the attention kernels separately, for each step, can tell you which of those is moving when latency changes. The observing chapter builds exactly that.

Try it

llama.cpp's benchmark tool measures the two phases separately: pp is prompt processing, prefill, and tg is text generation, decode, both in tokens per second. With the dGPU in Hybrid mode, and before you run it, write down a prediction for tg128 from the first question of the transformer chapter (chapter 15):

cd ~/workspace/repos/llama.cpp
./build/bin/llama-bench -m qwen2.5-0.5b-instruct-q8_0.gguf \
    -p 512 -n 128 -ngl 99
./build/bin/llama-completion -m qwen2.5-0.5b-instruct-q8_0.gguf \
    -c 4096 -n 8 -p hi -ngl 99 -no-cnv 2>&1 | grep llama_kv_cache

The first line should show pp512 many times larger than tg128: prefill uses each weight 512 times per read, decode once. The second shows the cache's size line; check it against the table before you look.

Recap

A request is a prefill over its whole prompt, matrix-matrix work that is usually compute-bound and produces the first token, then one decode step per further token, matrix-vector work that is memory-bound. TTFT is queueing plus prefill; ITL is one decode step. The KV cache keeps every layer's key and value for every token, 12,288 bytes per token for Qwen2.5-0.5B and 131,072 for Llama-3.1-8B, so decode never recomputes them. A decode step reads the weights once for the whole batch and every cached token of every sequence, so batching raises throughput, costs latency, and is limited by cache memory. Prefill's attention grows with the square of the prompt length.

New words in this chapter

prefill
Running the model over the whole prompt in one pass; it fills the cache and yields the first token.
decode
One model step per new token per sequence, reading the cache.

General matrix-matrix multiply; GEMV is the matrix-vector case.

Arrival to first token: queueing, prefill and sampling.
inter-token latency (ITL)
Time between later tokens of one request: one decode step.
KV cache
The stored keys and values of every earlier token, in every layer.
batch
The set of sequences processed together in one step.
throughput
Tokens produced per second across all sequences.

Check yourself

1. Predict the value: what size does llama.cpp print for the KV cache of Qwen2.5-0.5B with a 4,096-token context and the default cache type, and how is it split?

Answer

48.00 MiB: 24 MiB of keys and 24 MiB of values. Each token slot holds 12,288 bytes across all layers, half keys and half values, and 4,096 × 12,288 bytes is 50,331,648 bytes, exactly 48 MiB.

The line also says 24 layers and F16 for both K and V. The near-miss is to use 14 heads. The cache stores the 2 key-value heads; the 14 query heads are computed each step and never stored.

2. On the H100, how many Llama-3.1-8B sequences of 4,096 tokens each can decode together in BF16 before the cache no longer fits, and what does that say about what limits a serving GPU?

Answer

Roughly 110. The weights take about 16 GB of the 80, and each sequence's cache takes 512 MiB, about 0.54 GB, so at most about 64 / 0.54 ≈ 119 fit before counting activations and the framework's own reserve. Batch 128 would need about 69 GB of cache: it does not fit.

Diagram 16.3 says a larger batch would still be under the tensor-core roof, so the GPU's arithmetic is not what stops it. Memory capacity for the cache is. That is why the next chapter's server spends so much effort managing cache memory, and why GQA's sevenfold saving matters. The near-miss is to answer with the roofline's ridge of about 300 sequences. The cache runs out first.

3. A user reports that TTFT for a 32,000-token document is far more than 8 times the TTFT for a 4,000-token one, while ITL afterwards is only somewhat worse. Explain both halves.

Answer

Prefill has two parts. The matrix part grows with the prompt length P, 8 times for 8 times the tokens. Attention compares each token with all those before it, about P²/2 pairs, so it grows 64 times. At 32,000 tokens attention is a large share of prefill, so TTFT grows much faster than 8 times.

Each decode step reads the weights once and the cache once. The cache is now 8 times larger, but the weights did not change, so the step grows by the cache's share only, and the user sees "somewhat worse". The near-miss is to call prefill purely compute-bound and linear. It is compute-bound, and its attention part is quadratic.
