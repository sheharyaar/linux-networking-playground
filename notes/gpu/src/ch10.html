Chapter 10

Measuring: the tools and what each one sees

@@RT@@ · TOOLS — Every number so far has been a prediction: 311 µs at best, 4.27 waves, mostly long_scoreboard stalls. This chapter is about the tools that turn predictions into measurements. Each one sees some layers of the system and is blind to others, and the most common measuring mistake is asking a question of a tool that cannot see the layer it is about.

Seven layers, six kinds of tool

Diagram 10.1 is the map for this chapter. The rows are the layers you might want to measure, from your program's own code down to single instructions inside a kernel, plus the device as a whole. The columns are the tools. Read it by row: first decide which layer your question is about, then pick a tool with a dot in that row. The last column, bpftime, is what the eBPF part (Part IV) builds; it is here to show which gap it fills.

The whole device: nvidia-smi, NVML, DCGM

nvidia-smi is a command-line front end to NVML, the NVIDIA Management Library. NVML reports device-wide numbers that the driver samples: memory used, clocks, power, temperature, PCIe traffic, and utilization. nvidia-smi dmon prints them once a second, and nvidia-smi pmon does the same per process.

The utilization number is the trap. NVML defines GPU utilization as the "percent of time over the past sample period during which one or more kernels was executing on the GPU" (/opt/cuda/targets/x86_64-linux/include/nvml.h:245). That is time with a kernel running, whatever the kernel uses. Our naive matvec, which leaves 4 of 20 SMs empty and the rest at 17% occupancy, shows 100% while its loop runs.

DCGM, NVIDIA's Data Center GPU Manager, adds profiling fields that answer the question people meant to ask. Field 1002 is the share of cycles in which an SM has at least one warp resident, field 1003 is occupancy, and field 1005 is the share of cycles in which the memory interface is busy. They are still device-wide and sampled, so they cannot tell one kernel from another, but they are cheap enough to export to Prometheus from every server, with NVIDIA's dcgm-exporter.

The timeline: Nsight Systems, NVTX and CUPTI

Nsight Systems, nsys, records a timeline of everything the program does with the GPU: each CUDA API call on each host thread, each kernel and copy on the GPU with its start and end time, and, if you ask, calls into OS libraries. It costs little per event, so you can trace a whole program run. Its default treats a CUDA graph as one item; --cuda-graph-trace=node shows each kernel in it, at higher cost. NVTX is a small annotation library: code that calls nvtxRangePush("load_weights") and nvtxRangePop() gets a named bar on the timeline. PyTorch exposes it as torch.cuda.nvtx.

Underneath Nsight Systems and Nsight Compute sits CUPTI, the CUDA Profiling Tools Interface. It is a library with several parts. The Activity API delivers buffered records of kernels and copies with GPU timestamps. The Callback API calls your function on entry to and exit from every CUDA API call. PC sampling and PM sampling read the hardware's samplers, and the range profiler collects counters. The tools load a small injection library into your process, and that library uses CUPTI. If you want an always-on timeline of every kernel in your own service, CUPTI's Activity API is the conventional answer. It works without changing kernels, and it sees start and end only.

One kernel, all its counters: Nsight Compute

Nsight Compute, ncu, answers "why is this kernel as fast as it is". It reads hundreds of hardware counters, but the hardware can count only a limited set at once, so ncu runs the kernel several times, one replay pass per group of counters. Before the first pass it saves all the GPU memory the kernel can reach; before each later pass it restores the part the kernel wrote, so every pass sees the same inputs.

Three defaults make ncu durations differ from real ones. It locks the GPU clocks, to boost by default in current versions. It flushes the caches before every pass. And it runs each profiled kernel alone, with kernels serialised. Its sections map onto this document's chapters. SpeedOfLight gives achieved compute and memory throughput as a share of peak, the two axes of the roofline in the memory chapter. LaunchStats and Occupancy give the limits of the scheduling chapter, and WarpStateStats its stall reasons. MemoryWorkloadAnalysis shows traffic through each cache level, and SourceCounters puts stall samples on individual SASS lines. Nsight Compute supports Turing and newer. For the P5000 it dropped Pascal in 2020.1, and the profiler for Pascal is the older nvprof from a CUDA 12.x toolkit, which CUDA 13.0 removed.

Correctness and instrumentation: compute-sanitizer, cuda-gdb, NVBit

compute-sanitizer runs a program under one of four checkers. memcheck finds out-of-bounds and misaligned accesses, racecheck finds races on shared memory, initcheck finds reads of device memory nobody wrote, and synccheck finds invalid uses of barriers. Run it on every new kernel once; it is slow, and it is right. cuda-gdb is gdb extended to stop inside kernels, switch between blocks and threads, and step through code. The 13.x release needs compute capability 7.5 or newer, so the P5000 needs a 12.x toolkit's version.

NVBit, from NVIDIA Research, is a library for writing your own instrumentation tools. An NVBit tool is loaded into the application. When each kernel's machine code is loaded onto the GPU for the first time, NVBit lets the tool inspect its SASS and insert calls to the tool's own device functions before or after chosen instructions. It needs no source and no PTX, so it works on any compiled application, and it supports compute capability 3.5 to 12.1, Pascal included. NVBit is bpftime's nearest relative, and the difference between them is where in the pipeline each one edits.

Host eBPF: what the kernel can see

From the host kernel, eBPF sees two layers. Uprobes on libcudart.so and libcuda.so see every API call with its arguments, as the host-side chapter showed. Each hit traps into the kernel, so a uprobe on a call made a hundred thousand times a second is a cost you can measure. Kprobes on the NVIDIA driver see its system calls. The open kernel module's ioctl handler is nvidia_unlocked_ioctl, so a kprobe there sees context creation, memory allocation, pinning, and the waits that sleep in the kernel. It does not see launches, which never enter the kernel. And nothing on the host sees what happens inside a kernel after it starts. That gap, the empty bottom-right of diagram 10.1, is what the eBPF part fills.

Try it

nvidia-smi comes with the driver, and compute-sanitizer and cuda-gdb with Arch's cuda package. Nsight Systems and Nsight Compute are separate installs (see Before you start). With the dGPU in Hybrid mode, run the lab program under each tool and keep the numbers next to the predictions:

# terminal 2, while terminal 1 runs ./out/matvec 4096 4096 2000
nvidia-smi dmon -s u

nsys profile -t cuda,nvtx -o /tmp/mv ./out/matvec
nsys stats /tmp/mv.nsys-rep
ncu -k matvec_warp -c 1 --section SpeedOfLight ./out/matvec 4096 4096 5
sudo bpftrace -e 'kprobe:nvidia_unlocked_ioctl { @ = count(); }' \
              -c './out/matvec 4096 4096 2000'

The last line puts the host-side chapter's claim (chapter 8) to the test. The program makes more than 8,000 launches. If the ioctl count stays far below that and does not grow when you change 2000 to 4000, launches bypass the host kernel.

Recap

Pick the layer first, then the tool. NVML and nvidia-smi see the whole device, and their "utilization" means only that some kernel was running; DCGM's profiling fields say how much of the SMs and memory were busy. Nsight Systems draws the timeline of API calls, kernels and copies, NVTX names ranges on it, and CUPTI is the library underneath. Nsight Compute replays one kernel per counter group, with clocks locked and caches flushed, to explain it. compute-sanitizer and cuda-gdb check and debug, NVBit rewrites SASS at load time, and host eBPF sees API calls and the driver's ioctls but nothing inside a kernel.

Check yourself

1. Predict the value: while the lab program loops on matvec_naive (16 blocks of 256 threads on 20 SMs), what does nvidia-smi show as GPU utilization, and roughly what would DCGM's fields 1002 (SMs with a warp) and 1003 (occupancy) show?

Answer

Utilization near 100%, field 1002 at most 80%, and field 1003 at most about 13%. A kernel is running almost all the time, which is all NVML's utilization measures. At most 16 of 20 SMs ever hold a block, so at most 16 / 20 = 80% of SM-cycles have a warp. Each busy SM holds 8 of 48 warps, and averaged over all 20 SMs that is 16 × 8 / (20 × 48) ≈ 13%.

The near-miss is to read 100% as "the GPU is full". It means "the GPU is never idle". The matvec chapter's fix, more and better-shaped blocks, would leave utilization at 100% and move the two DCGM fields up.

2. Nsight Compute reports a duration for matvec_warp that differs clearly from what the lab program's events report. Give two reasons from this chapter, and say which number you would quote as the kernel's speed.

Answer

First, ncu locks the clocks, to boost by default, while the laptop in the lab loop runs at whatever clock its power and temperature allow. Second, it flushes the caches before each pass, so the small vectors x and y that stay in L2 across the lab's 200 back-to-back launches start cold every time. A third, smaller one is that the lab averages 200 launches queued back to back, while ncu runs one kernel alone.

Quote the event timing as the speed, because it is the kernel running the way the program runs it. Use ncu for the reasons, such as achieved bandwidth and stall mix, which are ratios that hold up when the clocks are locked. The near-miss is to treat ncu's duration as the more accurate one because the tool is more detailed.

3. You want the GPU duration of every kernel, all the time, in a production vLLM server that replays CUDA graphs. Which tools from this chapter are out, and what are you left with?

Answer

Nsight Compute is out, because it replays and serialises kernels. compute-sanitizer and NVBit are out, because they cost far too much to leave running. NVML and DCGM have no per-kernel view. Uprobes on the launch functions see the moment of each launch and no GPU time at all, and with graphs they do not even see the launches (the host-side chapter's second question).

That leaves Nsight Systems for bounded windows of minutes, the CUPTI Activity API inside the process for an always-on timeline of kernel start and end times, and bpftime's GPU probes, which also see what happens inside the kernel at a cost that the probe-cost chapter (chapter 14) measures. The near-miss is to treat "always on" as a property of the tool. It is a property of its cost per event at your event rate.
