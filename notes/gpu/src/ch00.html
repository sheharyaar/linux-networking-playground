Chapter 0 · Prologue

One multiply, three ways to watch it

@@RT@@ · HW LLM — Where we are: nowhere yet. This chapter picks the one object every later chapter follows, a matrix-vector multiply, and sets out the three ways anyone can watch a GPU while it runs one.

The object we follow

A large language model writes text one piece at a time. Each piece is a token: a short run of characters, often a whole word, sometimes part of one. "Linux" might be one token or two ("Lin" and "ux"). To produce one token, the model runs a long, fixed sequence of arithmetic, and most of that arithmetic is a single operation repeated hundreds of times.

That operation needs three words. A vector is an ordered list of numbers. A matrix is a grid of numbers in rows and columns. A dot product multiplies two vectors of the same length element by element and adds up the results. The dot product of (1, 2, 3) and (4, 5, 6) is 1·4 + 2·5 + 3·6 = 32.

A matrix-vector multiply, written matvec from here on, takes a matrix W and a vector x and produces a vector y. Each number in y is the dot product of one row of W with x. If W has d rows and n columns, then x has n numbers and y has d. We write it y = W·x.

W = | 1 2 3 |     x = | 1 |     y = | 1·1 + 2·0 + 3·2 |  =  |  7 |
    | 4 5 6 |         | 0 |         | 4·1 + 5·0 + 6·2 |     | 16 |
                      | 2 |

Doing the same thing for many vectors at once, stacked side by side as the columns of a second matrix, is a matrix-matrix multiply, written matmul. A matmul is many matvecs that share one W.

Our matvec has d = n = 4096 and stores each number in 4 bytes. W is then 4096 × 4096 × 4 = 67,108,864 bytes, which is 64 MiB. Computing y takes 4096 × 4096 = 16,777,216 multiplications and as many additions. The program that does it is lab/gpu/matvec.cu, and every listing of machine code in this document was compiled from that one file.

One property of this operation decides how fast it can ever run, and you can see it already in the diagram. Every number in W is read from memory, used in exactly one multiply and one add, and never touched again. The arithmetic is trivial. The cost is moving 64 MiB to wherever the arithmetic happens. The memory chapter turns that sentence into a number, and the language-model chapters show that this number sets the speed of every LLM server that answers one user at a time.

Why a GPU

A GPU, a graphics processing unit, is a chip with thousands of small arithmetic units, built to run one short function over a large amount of data at once. It sits on the PCIe bus and has its own memory. In GPU programming the CPU side, with its operating system and its memory, is the host. The GPU with its memory is the device.

The function that runs on the device is a kernel. One launch of a kernel starts thousands of copies of the same function, and each copy works on a different part of the data. The word collides with the Linux kernel, so this document always says host kernel for the operating system. A bare "kernel" is always GPU code.

The CPU and the GPU are built for opposite goals. Latency is how long one piece of work takes from start to finish. Throughput is how much work finishes per second. A CPU core spends its transistors on latency: large caches, branch prediction, out-of-order execution, all so that one thread finishes soon. A GPU spends them on throughput: many simple units, and enough independent work queued up that some of it is always ready while the rest waits for memory. Our matvec is 16.8 million multiplications that do not depend on each other, and 4096 sums that can be split into pieces in any order we like. That is exactly the kind of work a GPU is for.

The software that makes an NVIDIA GPU programmable is CUDA. It is a dialect of C++ for writing kernels, a compiler for that dialect, and two libraries that every CUDA program loads. The CUDA runtime (libcudart.so) is the convenient API most programs call. Under it sits the CUDA driver library (libcuda.so), which talks to the GPU driver in the host kernel. The GPU-sharing dossier follows those two libraries down to the hardware in How a launch reaches the silicon (chapter 2). This document starts from the programmer's side and goes down from there.

Three ways to watch it

Suppose the matvec runs inside a program you did not write, and you want to know how long it takes and why. There are three places to stand.

On the host, watching the calls. A uprobe on cudaLaunchKernel in libcudart.so fires every time the program asks for a kernel to run. This is ordinary eBPF, and you already know how to write it. The problem is that a launch is asynchronous: the call puts the work in a queue for the GPU and returns, usually within a few microseconds. The GPU may not start the kernel for a long time after that. A host-side probe sees the request. The kernel's start, its running, and its end all happen somewhere the probe cannot see.

Asking the vendor. NVIDIA's profilers are the Nsight tools. The library under them is CUPTI, the CUDA Profiling Tools Interface. Together they read counters built into the GPU and record exactly when each kernel ran and what it did. They are precise and heavy. The detailed per-kernel tool replays each kernel several times to collect all its counters, which is not something you do to a production server. And they move on without old hardware: the current version of that detailed tool does not support the customer's Pascal card at all.

Inside the kernel. bpftime is a userspace eBPF runtime from the eunomia-bpf project. One of the things it can do is rewrite a kernel's GPU code while the program is loading it, so that an eBPF program you wrote runs inside that kernel, in every thread of the kernel, at the kernel's entry or exit. The probe can read the GPU's own clock and the thread's position on the chip, and write into maps that a host process reads. It sees what the first two places cannot: which threads of the kernel were slow, and where on the chip they ran.

Try it

The lab program compiles without a GPU. Running it needs the laptop GPU switched on (see the benches card).

cd lab/gpu
nvcc -O3 -lineinfo -arch=sm_89 matvec.cu -lcublas -o out/matvec
./out/matvec            # d = n = 4096, 200 runs of each kernel

It prints the GPU's name, the size of W, then one line per kernel: the time per run, how many gigabytes per second that time implies, and the largest difference from NVIDIA's own library. On this laptop the first line should start device: NVIDIA GeForce RTX 4050 Laptop GPU, sm_89 and go on to give two hardware counts that NVIDIA does not publish for this chip. Keep the output. The memory chapter predicts these numbers before you read them.

Recap

We follow one matvec, y = W·x, with W a 4096 × 4096 matrix of 4-byte numbers: 64 MiB of data and 16.8 million multiply-adds, with every number of W used exactly once. A GPU is a throughput machine on the PCIe bus; a kernel is the function it runs, launched from the host through the CUDA runtime and driver libraries. You can watch a kernel from the host, which sees only the asynchronous request; through NVIDIA's profilers, which are precise but heavy; or from inside the kernel with bpftime, which runs your eBPF in every thread of the kernel.

Check yourself

1. Predict the value: for our matvec (d = n = 4096, 4-byte numbers), how many multiply-adds are done per byte of W read? What happens to that ratio if you make W 8192 × 8192?

Answer

One multiply-add per 4 bytes, so 0.25 per byte, and it stays 0.25 at 8192 × 8192. The 4096 case is 16,777,216 multiply-adds over 67,108,864 bytes. The 8192 case is four times the work (67,108,864 multiply-adds) over four times the bytes (268,435,456).

The mechanism is in diagram 0.1: each number of W meets x once and is never used again, however big W gets. The tempting wrong answer is that a bigger matrix gives "more reuse". For a matvec it gives none. Only x is reused, once per row, and x is tiny next to W.

2. A uprobe on cudaLaunchKernel shows each call taking about 4 µs. The step of the program that makes those calls takes 30 ms of wall-clock time, and a CPU profile says most of that 30 ms is spent inside one other CUDA call. What is the program doing during that time, and why can the uprobe not tell you?

Answer

The program is waiting for the GPU. The GPU work is the 30 ms; the 4 µs is only the time to queue each launch.

Launches are asynchronous (diagram 0.3): cudaLaunchKernel appends to the GPU's queue and returns. The program then blocks in a call whose only job is to wait for the GPU to finish, and that call is where a CPU profile puts the time. The near-miss is "the driver is slow because that call takes 30 ms". The call does nothing while it waits. The time belongs to kernels the uprobe never saw run.

3. "A matmul is many matvecs that share one W, so it moves the same number of bytes per multiply-add as a matvec." Where does that sentence stop being true?

Answer

It stops being true as soon as the matmul reads each number of W once and uses it for all the vectors before moving on. With k vectors, each number of W then feeds k multiply-adds per read, so the ratio becomes 0.25 × k per byte instead of 0.25.

The sentence is true only for a matmul written as k separate matvecs, each one reading W again from memory. The condition that makes the reuse real is that a number of W stays somewhere fast while all k vectors use it. That condition is what the memory chapter is about, and batching many users' requests together in an LLM server is this same trick.
