Chapter 4

CUDA: writing the matvec

@@RT@@ · CUDA — The machine part (Part I) gave us warps on SMs, fed by a memory that puts a 311 µs floor under our matvec on the laptop. Now we write the matvec for that machine, three times. Each version fixes what the one before got wrong, and all three are in lab/gpu/matvec.cu.

The shape of a launch

A CUDA source file mixes host code and device code, and three keywords say which is which. A function marked __global__ is a kernel: it runs on the device and is launched from the host. A function marked __device__ runs on the device and can only be called from device code; our warp_sum helper is one. Anything unmarked is ordinary host code.

One launch creates a grid: every thread that launch will run. The grid is cut into thread blocks, usually just "blocks", of up to 1,024 threads each. A block is the unit placed on an SM: all its threads run on the same SM, can use the same shared memory, and can wait for each other. In NVIDIA's lower-level documents a block is called a CTA, a cooperative thread array, and the two names mean the same thing. Inside the block, the hardware cuts the threads into warps of 32, in order.

Each thread finds its place through four built-in variables. threadIdx is the thread's index within its block. blockIdx is the block's index within the grid. blockDim is the number of threads per block, and gridDim the number of blocks. Each has .x, .y and .z parts, for problems that are naturally two- or three-dimensional; a matvec only needs .x. The usual first line of a kernel turns them into one global index:

int row = blockIdx.x * blockDim.x + threadIdx.x;    // matvec.cu:45

The host starts a kernel with a launch configuration in triple angle brackets: matvec_naive<<<16, 256>>>(W, x, y, n, d) asks for 16 blocks of 256 threads. Two more optional values can go inside the brackets, the bytes of shared memory per block and a queue to launch into. The host-side chapter covers the second.

The host half

Device code can only read device memory, so the host has to put W and x there first. cudaMalloc allocates global memory and returns a device pointer. cudaMemcpy copies between host and device memory, in a direction you name. cudaFree gives the memory back. The lab program's main does exactly that (matvec.cu:153–159), launches each kernel, and copies y back to compare it with cuBLAS.

Errors need care because the launch is asynchronous. A bad launch configuration is reported by cudaGetLastError() straight after the launch. A fault while the kernel runs, such as reading outside an allocation, is reported by whatever CUDA call comes next, often a copy many lines later. The lab wraps every call in a CHECK macro that prints the file and line and exits, which is the minimum for code you want to debug.

Version one: a thread per row

__global__ void matvec_naive(const float *__restrict__ W, const float *__restrict__ x,
                             float *__restrict__ y, int n, int d)
{
	int row = blockIdx.x * blockDim.x + threadIdx.x;
	if (row >= d)
		return;
	float sum = 0.0f;
	for (int j = 0; j < n; j++)
		sum += W[(size_t)row * n + j] * x[j];
	y[row] = sum;
}

Listing 4.1 — lab/gpu/matvec.cu:41–52.

It is the C loop with the outer loop removed: the grid is the outer loop. __restrict__ promises the compiler that the three arrays do not overlap, and together with const that lets it read W and x through a read-only path; a later chapter shows the instruction this becomes. The if guards against a grid with more threads than rows. Its problem is the one diagram 4.1 marks in orange. Lanes of one warp walk 32 different rows in step, so every warp-wide load touches 32 sectors. It has a second, quieter problem, which the first question below asks you to find.

Version two: a warp per row, and a shuffle

Give each row to a whole warp. Lane i adds up columns i, i + 32, i + 64 and so on, so at every step the 32 lanes read 32 neighbouring floats, the coalesced pattern. Each lane ends with a partial sum of 128 products, and the 32 partial sums must be added into one.

Adding many values into one is a reduction. Within a warp it can be done without touching memory, with a warp shuffle: an instruction that lets each lane read a register of another lane in the same warp. __shfl_down_sync(mask, v, offset) gives each lane the value of v held by the lane offset places above it. The mask names the lanes taking part, all 32 here, which is the explicit mask the previous chapter said modern code must pass.

__device__ __forceinline__ float warp_sum(float v)
{
	for (int offset = 16; offset > 0; offset /= 2)
		v += __shfl_down_sync(0xffffffff, v, offset);
	return v;
}

Two more tools belong here, though this kernel does not need them. If a whole block, rather than one warp, shared a row, the warps would have to combine their results through memory they can all see. That memory is __shared__: a variable declared with that keyword lives in the SM's shared memory, one copy per block. And the warps would have to wait for each other between writing and reading it. __syncthreads() is that wait: a barrier that every thread of the block must reach before any of them continues. It covers one block only. Threads in different blocks have no barrier inside a kernel; the end of the kernel is the only point where all of them have finished.

Version three: sixteen bytes per lane

matvec_warp4 (matvec.cu:82–100) is version two with one change: it reinterprets W and x as arrays of float4, a 16-byte struct of four floats, so each lane loads four neighbouring floats in one instruction. A warp-wide load then fetches 512 bytes, four full cache lines, instead of 128. The bytes moved are exactly the same. What shrinks is the number of load instructions, and with it the address arithmetic and loop overhead per byte. It requires that every row starts on a 16-byte boundary, which holds because cudaMalloc returns well-aligned memory and n is a multiple of 4.

The loop for (j = lane; j < n; j += 32) is a small case of a common pattern. A grid-stride loop lets a fixed number of threads cover any amount of work: each thread starts at its own index and steps by the total number of threads, for (i = id; i < N; i += gridDim.x * blockDim.x). Our lanes stride by the 32 threads of their warp instead of the whole grid, but the idea is the same.

Or call the library

Most production code writes none of this. cuBLAS is NVIDIA's library of tuned dense linear algebra, following the old BLAS interface (Basic Linear Algebra Subprograms). Its matvec is called GEMV, general matrix-vector multiply, and its matmul GEMM, general matrix-matrix multiply. The lab calls cublasSgemv (S for single precision, FP32) as the correct answer and as the speed to beat. One trap: cuBLAS stores matrices column by column, the Fortran way, so our row-major W looks to it like the transpose, and the call asks for CUBLAS_OP_T (matvec.cu:166). LLM servers call cuBLAS, or its newer sibling cuBLASLt, for most of their matmuls, which is why knowing its names matters when you are looking for kernels to probe.

Recap

A launch creates a grid of blocks of threads; a block runs on one SM and can share shared memory and meet at __syncthreads(); the hardware cuts it into warps. Each thread finds its work from blockIdx, blockDim and threadIdx. The naive matvec gives each thread a row and loads uncoalesced; the warp version gives each warp a row, loads coalesced, and folds 32 partial sums with five warp shuffles; the float4 version moves the same bytes with a quarter of the load instructions. cuBLAS's sgemv is the reference, and GEMV and GEMM are the names to recognise in a server's kernel list.

Check yourself

1. Predict the value: the naive kernel is launched as 16 blocks of 256 threads on the laptop's 20 SMs. At most how many SMs have any work at all, and what is the best occupancy any SM can reach during that launch?

Answer

At most 16 SMs have work, so at least 4 sit idle, and the best occupancy is 8 / 48 ≈ 17%. A block is the unit placed on an SM and is never split across SMs, so 16 blocks can occupy at most 16 SMs. Each block is 256 / 32 = 8 warps, so an SM holding one block has 8 of its 48 warp places filled.

That is the quieter problem of listing 4.1: too little parallelism to hide latency (diagram 2.2), on top of uncoalesced loads. The near-miss is to think the 4,096 threads spread evenly over all 20 SMs. Threads only travel in blocks.

2. Someone tidies matvec_warp by deleting the if (lane == 0) in front of the final store, so all 32 lanes execute y[warp] = sum;. The results are now wrong by large, varying amounts. Using diagram 4.3, say what each row of y ends up holding.

Answer

Each row holds a partial sum from whichever lane's store the hardware happened to apply. After the five shuffles only lane 0 holds the whole row's total; lane k holds a sum over some subset of lanes, and the upper lanes hold little more than their own 128 products (diagram 4.3, the grey boxes). All 32 lanes store to the same address in one warp-wide instruction, and when lanes of one store collide, CUDA does not promise which value lands.

The near-miss is "a race between warps". No other warp writes y[warp]. The collision is inside one instruction of one warp, which is why the original code lets exactly one lane store.

3. "__syncthreads() makes every thread of the kernel wait for the others." Where does that stop being true, and what do you use when you need every thread of the grid to have finished a step?

Answer

It is true only within one block. __syncthreads() is a barrier for the threads of the block that calls it. Other blocks may not have started yet, because they are waiting for an SM, or may already have finished. A barrier across blocks inside one kernel could wait for blocks that cannot start until the waiting ones leave.

To make every thread finish a step, end the kernel and launch the next one. Launches on the same queue run in order, so the second kernel sees everything the first wrote. That boundary is the only grid-wide barrier this chapter gives you. The language-model chapters show that real servers split their work into many kernels partly for this reason.
