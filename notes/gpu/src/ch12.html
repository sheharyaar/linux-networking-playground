Chapter 12

eBPF without the kernel: bpftime

@@RT@@ · EBPF — The running-it part (Part III) ended with a gap: nothing on the host can see inside a running kernel. This part fills it with bpftime, an eBPF runtime that lives in user space and can compile eBPF programs into a GPU kernel's own code. This chapter is the runtime: which process does what, where maps live, and how an ordinary libbpf program ends up asking for a GPU probe without knowing it.

This chapter assumes kernel eBPF: programs, maps, helpers, libbpf skeletons, kprobes and uprobes. It skips bpftime's uprobe and syscall-tracing support, except where the GPU path reuses them, and its AMD backend.

What the kernel did for eBPF, and who does it now

In the kernel, eBPF rests on five services. The bpf() system call loads programs and creates maps. The verifier checks each program. The JIT compiles it to machine code. Map memory lives in the kernel. And attach mechanisms such as kprobes, uprobes and tracepoints run the program at the right moment. bpftime keeps the programs, the maps' semantics, the helper numbering and libbpf, and replaces each of the five services with code in user space. The table is the whole idea in one place.

Two processes and a segment

A bpftime session has two processes. The loader is an ordinary libbpf program, the kind you would run against the kernel, started with LD_PRELOAD=libbpftime-syscall-server.so. When libbpf calls bpf() or perf_event_open(), the preloaded library answers instead of the kernel. It writes the programs, the maps and the attach requests, which bpftime calls handlers, into a named shared-memory segment. The target is the program you want to observe, started with LD_PRELOAD=libbpftime-agent.so. When the agent starts inside it, it maps the same segment, compiles each program and hands each handler to the attach implementation registered for its type.

The segment is what lets this work without the kernel. It is a Boost.Interprocess shared-memory region whose name both sides take from BPFTIME_GLOBAL_SHM_NAME. Inside the target, the agent pins the whole segment and maps it into the GPU's address space, with the cudaHostRegister(…, cudaHostRegisterMapped) call of listing 8.1. So the segment is also memory that GPU code can read and write directly.

How a kprobe becomes a GPU probe

Here is the trick that lets an unmodified libbpf toolchain ask for a GPU probe. A probe on a GPU kernel is written as a kprobe on the kernel's mangled name:

SEC("kprobe/_Z9vectorAddPKfS0_Pf")
int cuda__probe()
{
	u32 pid = bpf_get_current_pid_tgid() >> 32;
	u64 ts = bpf_get_globaltimer();

Listing 12.1 — bpftime/example/gpu/cuda-counter/cuda_probe.bpf.c:36–40. A probe on the entry of the CUDA kernel vectorAdd(const float*, const float*, float*).

libbpf turns that section name into a perf_event_open() call on the kprobe event type, with the function name attached, and then attaches the program to the returned descriptor. In the loader, the syscall server records it as a kprobe handler carrying the name (bpftime/runtime/syscall-server/syscall_context.cpp:843–888). In the target, handler types are numbers, and a kprobe is BPF_TYPE_KPROBE = 8 (bpftime/runtime/include/bpftime_shm.hpp:59). The agent registers the GPU attach implementation for exactly the types ATTACH_CUDA_PROBE and ATTACH_CUDA_RETPROBE, which are 8 and 9 (bpftime/runtime/agent/agent.cpp:1039–1046). So every kprobe handler goes to nv_attach_impl, with the kernel name as its argument, and every kretprobe becomes a probe at the kernel's exit.

The cost of the trick is that there are no real kprobes in a bpftime session. Inside bpftime, a kprobe means a GPU kernel. A loader can still use the real kernel's eBPF for other programs: with BPFTIME_RUN_WITH_KERNEL=1, the syscall server passes ordinary kprobes through to the kernel, and treats only names that start with cuda_ as GPU probes.

The compiler, and the verifier that is not there

bpftime compiles eBPF with llvmbpf, its own library. llvmbpf translates eBPF bytecode into LLVM IR. From there, LLVM's x86 backend produces machine code for host probes, and LLVM's NVPTX backend produces PTX for GPU probes, the same road to PTX as the compiler chapter's clang line. The GPU path is the subject of the next chapter.

The verifier is the part to be careful about. bpftime can run programs through PREVAIL, a userspace eBPF verifier, but its build option ENABLE_EBPF_VERIFIER is off by default (bpftime/cmake/StandardSettings.cmake:95). When it is on, BPFTIME_VERIFIER_LEVEL chooses strict checking, warnings only, or none. In a default build, nothing checks that a probe terminates or stays inside its memory. In the kernel the verifier is what makes eBPF safe to load. Here a probe is code you inject into someone else's GPU kernel, with the same power as that kernel's own code. A loop that never ends hangs the kernel it is in. Helper 507 exits the calling thread on purpose. Treat a GPU probe the way you would treat a patch to the application, because that is what it is.

Maps: where the data lives

Ordinary maps, hash and array and ring buffer, live in the shared segment, and the loader reads them with libbpf as usual. GPU code can reach the segment through the mapping, but a hash table in it is a host data structure that needs host code to search it. So a lookup from a GPU probe in an ordinary map becomes a request to the host, through the protocol the next two chapters take apart.

bpftime therefore adds GPU maps, with type numbers from 1500 (bpftime/runtime/include/bpftime_shm.hpp:122–132). Their data lives where GPU code can index it directly. The per-thread array map gives every GPU thread its own copy of each value, like a per-CPU map with a GPU thread in place of a CPU. The loader allocates it in device memory with cuMemAlloc and shares it with the target through a CUDA IPC handle (bpftime/runtime/src/bpf_map/gpu/nv_gpu_per_thread_array_map.cpp:61–74). The shared GPU array map has one copy, and there are a GPU ring buffer and a GPU hash map. For platforms without CUDA IPC, such as NVIDIA's Tegra boards, host-memory variants do the same job through pinned, mapped memory.

The per-thread map has a sizing rule that matters for our matvec. Each value is stored once per GPU thread, for as many threads as BPFTIME_MAP_GPU_THREAD_COUNT allows. The default is 1,024 (bpftime/runtime/include/bpftime_shm.hpp:42–45). Our matvec_warp launch has 131,072 threads. Reading the map back is one copy of every thread's slot for the key, so the map also costs host time in proportion to the thread count.

Helpers: the same numbering, extended

Helpers are called by number, as in the kernel, and bpftime keeps the kernel's numbers for the ones it shares: 1 to 3 for map lookup, update and delete, 6 for bpf_trace_printk, 14 for bpf_get_current_pid_tgid, 25 for bpf_perf_event_output. GPU helpers start at 501. A program declares them as pointers to a number, the old way of declaring helpers, as in static const u64 (*bpf_get_globaltimer)(void) = (void *)502; (cuda_probe.bpf.c:31).

Try it

No GPU is needed to see the trick of this chapter. Read the cuda-counter example's three files side by side: cuda_probe.bpf.c (the probe, a kprobe and a kretprobe), cuda_probe.c (an ordinary libbpf loader with a skeleton), and vec_add.cu (the target). Then find the kernel name in the target as the compiler will mangle it:

cd ~/workspace/repos/bpftime/example/gpu/cuda-counter
nvcc -cudart shared -arch=sm_89 -c vec_add.cu -o /tmp/vec_add.o
cuobjdump -symbols /tmp/vec_add.o | grep -i vectorAdd

The name you see must match the string after kprobe/ exactly. A probe on a name that does not exist attaches to nothing while the loader reports success, so this check comes first, every time.

Recap

bpftime keeps eBPF programs, map semantics, helper numbers and libbpf, and moves the kernel's services into user space. A loader running under libbpftime-syscall-server.so writes programs, maps and handlers into a shared segment; an agent inside the target reads them, compiles programs with llvmbpf, and attaches them. A kprobe handler has type 8, the same number as ATTACH_CUDA_PROBE, so SEC("kprobe/<mangled kernel name>") means the entry of that GPU kernel. The verifier is off by default; ordinary maps live in the segment and cost a host round trip from the GPU, while GPU maps such as the per-thread array live in device memory and cost address arithmetic. GPU helpers 501 to 511 add timers, indices, special registers, a fence and thread exit.

Check yourself

1. Predict the value: you put a per-thread array map with 4 keys of 8-byte values on matvec_warp's 131,072 threads. How large must BPFTIME_MAP_GPU_THREAD_COUNT be, how much device memory does the map take, and how many bytes does one bpf_map_lookup_elem from the loader copy?

Answer

At least 131,072; the map takes 4 × 131,072 × 8 bytes = 4 MiB of device memory; one lookup copies 131,072 × 8 bytes = 1 MiB. Every key holds one 8-byte slot per thread, and the loader's lookup returns all of a key's slots at once, the way a per-CPU map returns one value per CPU.

With the default of 1,024 the trampoline prints a warning and computes addresses past the end of the buffer for every thread above 1,023, so the setting is not optional. The near-miss is to size the map by the number of warps or blocks. It is indexed by the global thread index.

2. A colleague loads a bpftime loader with an ordinary kernel kprobe on do_sys_openat2 next to a GPU probe, and the kernel kprobe never fires. Explain, and say what they could do.

Answer

Under the syscall server, every kprobe becomes a bpftime handler of type 8, and type 8 is the GPU probe. The request never reached the kernel; inside the target, bpftime looked for a GPU kernel called do_sys_openat2 and found none.

They can run the loader in bpftime's "run with kernel" mode, where ordinary kprobes go to the kernel and only names starting with cuda_ become GPU probes. Or they can split the two into separate loaders, one under bpftime and one plain. The near-miss is a missing symbol in the kernel. The kernel was never asked.

3. Why does a lookup in an ordinary hash map from a GPU probe need the host at all, when the map's memory is mapped into the GPU's address space?

Answer

Because mapped memory gives access to bytes, while a lookup needs an algorithm. The hash map is a host data structure in the segment, built with host pointers and searched by host code. GPU code could read its bytes, but it has no compiled lookup function that understands the layout, and the host might be changing the map at the same moment.

So the probe writes the key into the request area and waits while a thread in the agent runs the real lookup. GPU maps avoid this by having a layout that a GPU thread can index with arithmetic. The near-miss is "mapped memory is slow". It is slow, but the reason is that the GPU cannot run the lookup itself.
