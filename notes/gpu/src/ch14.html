Chapter 14

Writing GPU probes, and what they cost

@@RT@@ · EBPF TOOLS — The last two chapters took bpftime apart. This one uses it. We write a probe that measures what the scheduling chapter predicted for our matvec, the waves and the tail, and then work out what the probe costs, from the code that runs it. The chapter ends with the two extensions the finish line asked for: a new helper, and a new kind of attach point.

A probe for the tail

The scheduling chapter predicted that matvec_warp's 512 blocks run in about 4.27 waves on the laptop, with a partial last wave as a tail. A probe can check that from inside the kernel. Each warp of matvec_warp computes one row, so the probe records, for each row, when its warp started and finished and on which SM. The loader then reads the 4,096 records and prints the spread of start times, the length of the tail and the rows per SM. The files are in lab/gpu/probe/: the probe, a loader, and a Makefile that builds both with the system's clang, bpftool and libbpf.

struct {
	__uint(type, BPF_MAP_TYPE_GPU_ARRAY_MAP);   // 1503: one copy, in device memory
	__uint(max_entries, ROWS);
	__type(key, u32);
	__type(value, struct row_times);
} rows SEC(".maps");

int matvec_warp_entry()
{
	u32 row;
	struct row_times *t;

	if (lane0_row(&row))         // lanes 1 to 31 stop here
		return 0;
	t = bpf_map_lookup_elem(&rows, &row);
	if (!t)
		return 0;
	t->start_ns = bpf_get_globaltimer();   // helper 502
	t->start_sm = bpf_get_sm_id();         // helper 509
	return 0;
}

Listing 14.1 — lab/gpu/probe/matvec_tail.bpf.c:26–65. The exit probe, on kretprobe/ with the same name, writes end_ns and end_sm the same way.

Three choices in it come straight from the last two chapters. The map is a GPU array map, so a lookup returns a device pointer and the stores go to device memory without involving the host. Only lane 0 of each warp records, because the warp's 32 lanes run the same row in lockstep and one record per row is all the question needs. And it records the SM at both ends, so a block that was preempted and moved, as in the scheduling chapter, shows up instead of corrupting the timing. The helper lane0_row recomputes the row exactly as the kernel does, from the block index, the block size and the thread index (helpers 503, 504 and 505).

clang compiles the entry probe to 46 eBPF instructions with six helper calls, and llvm-objdump shows them in order: 505, 503, 504, then helper 1 for the map lookup, then 502 and 509. All six are on the "no" side of the last chapter's table: none of them needs the host.

Running it

bpftime itself must be built first (Before you start). Then the loader runs under the syscall server in one terminal, and the target under the agent in another, with the same segment name. Run the lab program with one iteration, so the map holds a single, clean launch of matvec_warp:

# terminal 1
cd lab/gpu/probe && make
BPFTIME_LOG_OUTPUT=console BPFTIME_GLOBAL_SHM_NAME=matvec_tail \
LD_PRELOAD=$HOME/workspace/repos/bpftime/build/runtime/syscall-server/libbpftime-syscall-server.so \
    ./matvec_tail

# terminal 2
BPFTIME_LOG_OUTPUT=console BPFTIME_GLOBAL_SHM_NAME=matvec_tail \
LD_PRELOAD=$HOME/workspace/repos/bpftime/build/runtime/agent/libbpftime-agent.so \
    ../out/matvec_shared 4096 4096 1

Before you run it, write down what the scheduling and tooling chapters predict. All 4,096 rows should be recorded. The kernel span should be close to the 311 µs floor plus whatever the probe adds. About 205 rows should land on each of the 20 SMs. The first bucket of start times should hold about 960 rows, the first wave of 120 blocks of 8 rows, and the later waves should blur, as the scheduling chapter said. The last 10% of rows should take a visible share of the span, which is the tail. No row should change SM on an otherwise idle laptop. Two things in this setup are untested: whether the system libbpf behaves like the one bpftime's examples build from its submodule, and whether a CUDA 13 launch reaches bpftime's hooks at all, the host-side chapter's open question.

What a probe costs

A probe's cost has four parts, and each comes from a mechanism you have already seen.

The first is instructions, paid by whole warps. Every thread executes the probe, and its first branch, if (tx & 31), splits each warp: 31 lanes return while lane 0 runs the rest. Under SIMT the warp as a whole waits for lane 0 (diagram 1.2), so every warp pays for the longest path once. Limiting the work to lane 0 saves memory traffic and map space, and saves no issue slots. The GPU helpers are separate functions in the trampoline, marked __noinline__, and the ones that return three values do so through pointers into the probe's stack, which in PTX is local memory: the STL and LDL of the SASS chapter.

The second is registers. ptxas compiles the kernel and the probe together, and the combined kernel can need more registers than the original, with fewer blocks per SM as a result (the last chapter's first question).

The third is the one that can be enormous: helpers that need the host. A lookup in an ordinary map, bpf_printk, bpf_get_current_pid_tgid, bpf_perf_event_output and helper 501 all go through make_helper_call. That function takes the active lanes of the warp one at a time. Each takes a single spinlock shared by every thread on the GPU, writes its request into the host-memory request area, sets a flag, and spins until the host answers (bpftime/attach/nv_attach_impl/trampoline/default_trampoline.cu:131–172). On the host, the agent's watcher thread checks the flag, handles at most one request, and then sleeps for a millisecond, every time round its loop (bpftime/runtime/src/attach/bpf_attach_ctx_cuda.cpp:118–276).

Put together, those two pieces of code serve at most one host call per watcher wake-up, about a thousand per second for the entire GPU, each taking up to a millisecond. While they wait, the other threads that want a host call spin on the lock, issuing atomic operations that use the SMs and the memory system. Diagram 14.2 draws five lanes asking at once.

The fourth is start-up. Every fatbin with a probed kernel is patched and compiled by the PTX compiler library at registration, before main, so a program with thousands of kernels starts noticeably slower. The cost is paid once per process; within a process, results are cached by hash.

The table gives one rule for writing probes: keep everything that runs per thread on the GPU, and let the loader do aggregation on the host. A probe that needs the process ID can have the loader write it into a GPU map once, instead of calling helper 14 in every thread. A probe that wants to print should count into a GPU map and let the loader print.

Adding a helper

The finish line asked for enough understanding to add a helper. Here is helper 512, which returns the SM's cycle counter. The PTX manual documents %clock64 as a 64-bit cycle counter. By contrast, it describes %globaltimer, behind helper 502, as a register "intended for use by NVIDIA tools" whose behaviour is target-specific, so a second clock is useful. The work has four steps, all of them in bpftime's tree.

First, implement it in the trampoline, next to the others, with the five 64-bit parameters every helper takes:

extern "C" __noinline__ __device__ uint64_t
_bpf_helper_ext_0512(uint64_t, uint64_t, uint64_t, uint64_t, uint64_t)
{
	// get this SM's cycle counter
	uint64_t cycles;
	asm volatile("mov.u64 %0, %%clock64;" : "=l"(cycles));
	return cycles;
}

Listing 14.2 — added to bpftime/attach/nv_attach_impl/trampoline/default_trampoline.cu, before bpf_main. The name is fixed: llvmbpf calls helper n as _bpf_helper_ext_%04u (bpftime/vm/llvm-jit/src/compiler_utils.hpp:39–44).

Second, regenerate trampoline_ptx.h. The trampoline's Makefile compiles the file with clang for sm_61, keeps the PTX up to bpf_main, and wraps it in a C string. It expects clang 17's output file names. With this laptop's clang 22, add --cuda-device-only and name the output yourself:

cd ~/workspace/repos/bpftime/attach/nv_attach_impl/trampoline
clang++ -S --cuda-device-only --cuda-gpu-arch=sm_61 -O2 \
    -U__FLOAT128__ -U__SIZEOF_FLOAT128__ default_trampoline.cu -o tramp.ptx
( echo 'static const char TRAMPOLINE_PTX[] = R"('
  grep -B 10000 "// .globl	bpf_main" tramp.ptx | grep -v "// .globl	bpf_main"
  echo ')";' ) > ../trampoline_ptx.h

Done in a scratch copy for this chapter, that produced _bpf_helper_ext_0512 as a short PTX function around mov.u64 %rd1, %clock64;. One difference to watch: clang 22 writes .version 8.8, where the committed header says .version 8.1, and a PTX compiler library older than CUDA 12.9 will refuse 8.8. That matters for the P5000's CUDA 12.x toolkit.

Third, tell llvmbpf the helper exists, by adding one line next to helper 511 in bpftime/attach/nv_attach_impl/pass/ptxpass_core/src/core.cpp:207–222:

vm.register_external_function(512, "get_clock64", (void *)test_func);

Without it, compiling a probe that calls 512 fails with "Ext func not found: _bpf_helper_ext_0512" (bpftime/vm/llvm-jit/src/compiler_utils.cpp:368), and the kernel runs unprobed. Fourth, rebuild bpftime and declare the helper in the probe, as the examples do: static const u64 (*bpf_get_clock64)(void) = (void *)512;. A helper that needs the host takes two more steps. Add a request kind to the trampoline's HelperOperation list and call make_helper_call with it. Then handle that request kind in the watcher thread's loop. Diagram 14.1 then applies to every call of it.

Adding a kind of attach point

The other extension is a new kind of attach point, such as a probe before every bar.sync, the PTX of __syncthreads. That is a new pass. A pass is a shared library that exports print_config, returning JSON with its name, attach type and name patterns, and process_input, taking the JSON request of the last chapter and returning new PTX. bpftime loads the libraries listed in BPFTIME_PTXPASS_LIBRARIES, colon-separated, or its built-in list, each with dlmopen in its own namespace (bpftime/attach/nv_attach_impl/nv_attach_impl.cpp:501–530).

The simplest way to give the new pass a name needs no change to libbpf or the loader. Claim a pattern inside the kprobe namespace, as the memory-capture pass does with ^kprobe/__memcapture$. The catch is the matching rule. For each handler, bpftime picks the first pass whose attach type and pattern match (nv_attach_impl.cpp:173–193), and kprobe_entry claims every ^kprobe/.*$ except __memcapture. Its exclusion list, in pass/ptxpass_kprobe_entry/main.cpp:29–30, must also exclude your new pattern, or the entry pass will take your probes first.

Recap

The tail probe records, per row, the start and end time and SM of the warp computing it, from lane 0 only, into a GPU array map, using only helpers that stay on the GPU. A probe costs instructions paid by whole warps, possibly registers and occupancy, start-up compile time, and above all host round trips: every host-call helper waits for the agent's watcher thread, which serves one request per wake-up and sleeps 1 ms between them, behind one lock for the whole GPU. So keep per-thread work on the GPU and aggregate in the loader. A new helper is a _bpf_helper_ext_05xx function in the trampoline, a regenerated trampoline_ptx.h, and a registration in the pass core. A new attach kind is a pass library with a name pattern that kprobe_entry must exclude.

New words in this chapter

host-call helper
A helper whose work is done by the agent's watcher thread on the host, through the request area.
watcher thread
The agent's host thread that serves GPU helper requests, one per wake-up.
helper 512
This chapter's new helper: it returns the SM's 64-bit cycle counter, %clock64.

Check yourself

1. Predict the value: a colleague adds bpf_printk in lane 0 at the exit of matvec_warp, one call per row. Using the model of diagram 14.2, about how long does one launch take now, against about 330 µs without the probe?

Answer

About 4 seconds. There are 4,096 rows, so 4,096 host calls. They are served one at a time, roughly one per millisecond, so the launch cannot finish in less than about 4.1 seconds, around 12,000 times slower. The lab program's default 200 iterations would then take more than 13 minutes.

Nothing about the GPU enters the answer, which is the point. The near-miss is to estimate the cost of a print as a few microseconds of PCIe traffic. The traffic is small; the wait for the watcher's next wake-up is what costs.

2. Restricting the probe to lane 0 does not save issue slots, as this chapter said. Then why do it, and what would go wrong if every thread wrote its own record into a per-thread array map instead?

Answer

It saves memory traffic and map space, and it records exactly the unit the question is about, a row. One record per row is 4,096 records of 24 bytes; one per thread is 131,072, each a store into device memory competing with the kernel's own loads, in a kernel that is memory-bound.

A per-thread array map would also need BPFTIME_MAP_GPU_THREAD_COUNT of at least 131,072 (the bpftime chapter's first question), and the loader would copy 32 identical-in-meaning start times per row. The near-miss is that "fewer lanes means a faster probe". The warp pays for lane 0's path either way.

3. You add helper 512 to the trampoline and regenerate the header, but forget the line in core.cpp. Where does it fail, and what do you see? Then: why is comparing two %clock64 values from a thread's entry and exit only meaningful if you also compare its two SM IDs?

Answer

It fails when the pass compiles the probe: llvmbpf has no helper 512 registered and reports "Ext func not found: _bpf_helper_ext_0512". The pass fails, that kernel is left unpatched, and the program runs without the probe, so you see the error only in bpftime's log.

%clock64 is a cycle counter on the SM that reads it, and different SMs' counters are not the same clock. If a preemption moved the block between entry and exit, the two readings come from different counters and their difference means nothing. Recording the SM at both ends, as the tail probe does, lets you discard those records. The near-miss is to treat %clock64 like %globaltimer, which is one clock for the whole GPU.
