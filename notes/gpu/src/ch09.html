Chapter 9

Scheduling, from grid to warp

@@RT@@ · HW TOOLS — The last chapter got our launch as far as the GPU's front end. This one follows it the rest of the way: who decides which kernel runs, which SM gets each block, and which warp issues on each cycle. It also finishes the occupancy sum that the SM chapter left open.

Optional neighbours: the GPU-sharing dossier's Time-slicing (chapter 4) and MPS (chapter 5) cover the top level of this chapter, sharing one GPU between processes, in depth. This chapter skips graphics work, MIG, and green contexts, CUDA's newer way to give a stream a fixed set of SMs.

Five levels, five clocks

Scheduling on a GPU happens at five levels, and each one works on its own time scale. At the top, contexts from different processes take turns. The GPU's runlist scheduler gives each context a time slice of the whole GPU, in the millisecond range, and two contexts never run kernels on the SMs at the same instant unless MPS has merged them. Within a context, streams feed a fixed set of hardware work queues. NVIDIA calls this Hyper-Q. A context gets 8 queues by default, and CUDA_DEVICE_MAX_CONNECTIONS sets anywhere from 1 to 32. When there are more busy streams than queues, two streams share a queue and their work is serialised, a false dependency that no line of your code asked for.

Below the queues, the GPU's front end takes kernels from the queues and hands them to the work distributor, the block scheduler. Up to 128 kernels can be resident on Ada and Hopper, and 32 on the P5000's compute capability 6.1. The work distributor places each block on an SM that has room for all of it. The block then stays on that SM until it finishes. At the bottom, each SM sub-partition's warp scheduler picks one eligible warp per cycle, as in the SM chapter.

Where a block fits: finishing the occupancy sum

The work distributor places a block on an SM only when four resources all have room for the whole block. These are warp slots (48 per SM on Ada), block slots (24 per SM), registers (65,536 per SM) and shared memory (100 KB per SM). The number of blocks that fit is the smallest of the four limits. A block is never split, so the remainder of a resource that cannot hold a whole block goes unused. That is the limit the SM chapter promised, and it lowers the float4 kernel's 36 warps.

You do not have to do this by hand. cudaOccupancyMaxActiveBlocksPerMultiprocessor does the same sum, and the lab program now prints its answer for each kernel (matvec.cu:189–196). NVIDIA's kernel profiler, which the tooling chapter uses, reports the four limits separately, as launch__occupancy_limit_registers, _warps, _blocks and _shared_mem, so you can see which one is binding.

Waves, and the tail

Our matvec_warp launch is 512 blocks. The laptop's 20 SMs hold 6 blocks each, 120 at a time. So the grid runs as 512 / 120 = 4.27 waves: four rounds in which every block slot of the GPU is busy, and a fifth in which only 32 blocks are left for 120 slots. The time when only that last partial wave is running is the tail. During it most of the GPU is idle while the kernel is still "running". NVIDIA's kernel profiler reports the number as launch__waves_per_multiprocessor, and its documentation warns that partial waves cause exactly this.

Real blocks do not run in lockstep rounds. A new block starts whenever an old one finishes, so the boundaries between waves blur after the first. The model is still the right first estimate, and the tail at the end is real. It costs most when there are few waves, because then the partial one is a large share of the whole. Now move the same launch to an H100. It has 132 SMs, and at sm_90's 32 registers per thread each SM holds 8 of these blocks: 1,056 slots. Our 512 blocks fill less than half of one wave.

There are three ways out of a tail. You can give the GPU more, smaller pieces of work, so the partial wave is a small share. You can do more work per launch, which is what batching does for LLM serving. Or you can write a persistent kernel: launch exactly as many blocks as fit at once, 120 on the laptop, and have each block loop, taking the next piece of work from a counter in global memory with an atomic add until none is left. A persistent kernel has no waves and no per-launch cost after the first. In exchange it holds every SM until it is done, so nothing else from the same context runs beside it. CUDA does not promise that 20 blocks land on 20 different SMs. bpftime's threadscheduling example reads %smid from inside the kernel and shows you where they went.

What a warp does while it waits

Once its block is placed, each warp is in one of a few states on every cycle. It can be selected, issuing an instruction. It can be eligible but not selected, ready while another warp of the same sub-partition issues. Or it can be stalled, because its next instruction cannot issue yet. A stall always has a reason, and NVIDIA's kernel profiler samples the warps' states and names the reasons. These are the stall reasons, reported as metrics like smsp__pcsamp_warps_issue_stalled_long_scoreboard and attributed to the instruction that was waiting.

Kernels side by side, and preemption

Two kernels in different streams of one context can be resident at the same time, but only if the first leaves room. Our 512-block matvec fills every slot for four waves. A second kernel's blocks get slots only as the first kernel runs out of blocks, so in practice concurrent kernels mostly overlap in each other's tails. Streams pay off most with small kernels that each fill only a few SMs, which is the shape of the work a language model does for each new token.

A running block can also be stopped. When a context's time slice ends, or cuda-gdb halts a kernel, the GPU preempts the running blocks: it saves each warp's registers and the block's shared memory to device memory, and restores them later. On Ada and Hopper this happens at instruction granularity. For Pascal the sources disagree. The GP104 whitepaper says Pascal preempts CUDA compute at instruction level. NVIDIA's Pascal tuning guide calls it a GP100 feature, and the P5000 is a GP104. The lab program now prints cudaDevAttrComputePreemptionSupported; run it on the P5000 before relying on either. A preempted block may resume on a different SM. That is why the PTX manual says %smid may change during execution, and why a probe should treat it as a sample.

Recap

Scheduling has five levels: contexts take time slices, streams map onto 8 to 32 hardware queues, kernels are taken from the queues, the work distributor places whole blocks on SMs with room, and warp schedulers pick a warp each cycle. A block fits only if warp slots, block slots, registers and shared memory all have room, so matvec_warp4 gets 4 blocks, 32 warps, on an Ada SM. A grid runs in waves; the partial last wave is the tail, and on an H100 our grid is less than one wave. Stalled warps carry reasons, and a memory-bound kernel should show long_scoreboard. Preemption saves running blocks, which may resume on another SM.

New words in this chapter

time slice
A turn of the whole GPU given to one context by the runlist scheduler.
hardware work queue (Hyper-Q)
One of up to 32 queues that a context's streams are mapped onto.
work distributor
The GPU unit that places blocks on SMs with room for them.
wave
One round of blocks that fills every block slot on the GPU.
tail
The end of a kernel, when only a partial wave runs and most SMs are idle.
persistent kernel
A kernel launched with exactly as many blocks as fit, each looping over work.
stall reason
Why a resident warp could not issue on a cycle, as sampled by NVIDIA's kernel profiler.
preemption
Saving a running block's state to memory so other work can use the SMs.

Check yourself

1. Predict the value: matvec_warp4 keeps its 56 registers per thread but is launched with blocks of 128 threads instead of 256, with twice as many blocks. How many blocks and warps fit on one Ada SM now, and why did the block size change the answer?

Answer

9 blocks of 4 warps, 36 warps, 75% occupancy. A block now needs 56 × 128 = 7,168 registers, and 65,536 / 7,168 = 9.14, so 9 blocks fit by registers. Warp slots allow 48 / 4 = 12 and block slots 24, so registers bind at 9. With 256-thread blocks only 4 fitted, 32 warps.

The block size changed the answer because a block is placed whole: smaller blocks waste less of the register file at the end. The near-miss is to think occupancy depends only on registers per thread. It depends on registers per block too, which is why block size is a tuning knob.

2. You run bpftime's threadscheduling probe against matvec_warp on the laptop and on an H100. The laptop shows all 20 SMs with about 25 or 26 blocks each. The H100 shows every SM with 3 or 4 blocks. A colleague concludes the H100 is "barely used". What do the two histograms show, and what can they not show?

Answer

They show placement: 512 / 20 ≈ 25.6 blocks per laptop SM over about 4.3 waves, and 512 / 132 ≈ 3.9 blocks per H100 SM in a single partial wave (diagram 9.2). A count of blocks per SM has no time in it, so it cannot show whether the blocks ran together, in waves, or in a tail.

Nor can it show whether 24 to 32 warps per SM were enough to keep the H100's memory busy, which is the question that matters for a memory-bound kernel. For that you need time: the kernel's duration against the 20 µs bandwidth floor of the memory chapter, or timestamps from %globaltimer in the probe. The near-miss is to read low occupancy as slow. It can be, and that is a measurement.

3. Your probe records %smid at a block's first instruction and again at its last, and on a shared GPU a few blocks report two different SMs. Is the probe broken?

Answer

No. Those blocks were preempted, most likely at the end of a time slice when another process had work on the GPU, and resumed on a different SM. The PTX manual documents that %smid may change during execution for exactly this reason.

Treat %smid as a sample taken when you read it, and read it once per event you care about. On a GPU used by one process the effect should be rare; on a shared GPU it is normal. The near-miss is to suspect the helper. Helper 509 reads the register correctly; the block moved.
