Chapter 20

Epilogue: traps, limits, what comes next

@@RT@@ · EBPF LLM — The matvec has made the whole trip: one line of CUDA, PTX and SASS, the SMs, a probe inside it, and every token a server produces. This last chapter collects what can still go wrong at each stage, what the tools cannot do, the tests this document has not been able to run, and two directions the field has taken since the hardware in it was new.

The trip, and the trap at each stage

Every chapter ended with a trap or two in its tables. Diagram 20.1 lines them up along the trip the matvec took, so that a symptom can be placed at its stage. Most of them have the same shape: a layer that looks transparent turns out to decide something. The build decides whether there is PTX. The runtime's linking decides whether registration can be seen. The launch call decides whether a hook runs. The capture time of a graph decides which kernels it holds.

Honest limits

bpftime's GPU probes, at commit a900f85, have five limits that no amount of care in the probe removes. A probe gets no arguments. It can read the block and thread indices, the block and grid sizes, the SM, warp and lane it runs on, and the global timer (helpers 502 to 511, attach/nv_attach_impl/pass/ptxpass_core/src/core.cpp:213–224), and its maps. The kernel's own parameters and registers are out of its reach. Helpers that call the host are served one at a time by a thread that sleeps a millisecond per loop, about a thousand calls per second for the whole GPU, as the probe-cost chapter (chapter 14) worked out from the source. The verifier is compiled out by default (cmake/StandardSettings.cmake:95), so a GPU probe is trusted code. Only kernels that arrive through a hooked registration, with PTX, are patched. And only the three replaced launch functions redirect to the patched copy.

This document has limits of its own. Its numbers are floors, computed from bytes and bandwidth, and every "Try it" asks you to measure where the floor is not the answer. Its Pascal and Hopper paths were checked against sources and documentation, but never run, because neither card was on the bench. And it is longer than planned, because each layer needed its mechanism explained before its probe could make sense; the reading times in the contents are measured from the text.

What came next: Blackwell's families

CUDA 12.9 added a third kind of target. Besides portable code and the architecture-specific a targets of the generations chapter (chapter 11), there are family-specific f targets: code built for compute_100f runs on any GPU of compute capability 10.x, today 10.0 and 10.3, and on future ones in the same family (NVIDIA's blog on family-specific features). Blackwell's fifth-generation tensor cores bring their own on-chip Tensor Memory, 512 columns by 128 lanes of 32-bit cells per block on sm_100a and sm_100f, used by the tcgen05 instructions (PTX ISA, section 9.7.18.1). ggml already lists NVIDIA's FP4 format among the types its quantized matrix kernel takes (ggml/src/ggml-cuda/mmq.cu:318–352).

For probing, this extends a rule the document already met with sm_90a. bpftime rewrites a kernel's PTX target to the detected architecture, without a suffix (nv_attach_utils.cpp:94–160), so any kernel whose PTX needs an a or f target is out of its reach, and those are the tensor-core kernels where the time goes. A bpftime that kept the suffix it found would close part of the gap. That is a small, concrete change of the kind this document's finish line asked you to be able to make.

What came next: the cache on the network

vLLM can run prefill and decode in different instances and move the KV cache between them, which it calls disaggregated prefilling. Its documentation gives two reasons: to tune TTFT and ITL separately, and to control the tail of ITL, which mixed steps like diagram 17.2's lengthen. It adds that the feature does not improve throughput (docs/features/disagg_prefill.md). The cache travels through a connector; NIXL, one of them, can use UCX, which runs over RDMA, and GPUDirect Storage.

For observation, this adds a sixth row to diagram 19.1, under the GPU and across machines: a request's keys and values crossing the network between its prefill and its first decode step. A TTFT now includes a transfer, and the tools for that row are the network's. The RDMA side is in the ConnectX and mlx5 chapter (chapter 5) of the SR-IOV dossier, which is where this document hands over.

Recap

The traps cluster between source and GPU: whether a build carries PTX, whether registration and launch pass through bpftime's hooks, and when a graph was captured. bpftime's probes get no arguments, call the host about a thousand times a second at most, run unverified by default, and reach only kernels with PTX and a hooked path. The document's Pascal and Hopper paths, its two step probes and its bench predictions wait to be run. Blackwell's family-specific and architecture-specific targets widen the set of kernels a target-rewriting tool cannot touch, and disaggregated serving puts part of TTFT on the network.

New words in this chapter

family-specific target
A CUDA target such as compute_100f whose code runs on every GPU of one compute-capability major version.
Tensor Memory
Blackwell's on-chip store dedicated to tensor-core operands, used by the tcgen05 instructions.
disaggregated prefilling
Running prefill and decode in separate vLLM instances and moving the KV cache between them.

Check yourself

1. Trace the path: a probe on a llama.cpp kernel prints on the laptop, but on an H100, with the same source tree, the same bpftime and a build for 90, it prints nothing. Go from the build to the launch, and name the most likely cause and its fix.

Answer

The build embeds PTX for compute capability 9.0, so the fat binary is registered and bpftime patches the kernel as before. At launch, ggml checks the kernel's PTX version, finds 90, and launches it with cudaLaunchKernelEx to use programmatic dependent launch. bpftime does not replace that call, so the original kernel runs and the patched copy never does.

Setting GGML_CUDA_PDL=0 sends launches through the ordinary path. The near-miss is sm_90a: ggml has no wgmma or TMA code at this commit, so its kernels build for plain sm_90, and bpftime can compile them.

2. A probe must record which row of W each warp of the matvec computes, and when it finishes. What can the probe read, what can it not, and how does the probe-cost chapter's probe get the row?

Answer

It can read the block and thread indices, the block and grid sizes, the SM, warp and lane ids, and the global timer, all through helpers, plus its own maps. It cannot read the kernel's arguments, such as the pointers to W and x, or its registers. So the probe computes the row.

The probe-cost chapter's probe lets only lane 0 of each warp continue, computes the row as block index × block size plus thread index, divided by 32, and writes the global timer and SM id into a GPU array map at that row. The near-miss is to reach for the kernel's own row variable, which lives in a register the probe never sees.

3. Of the traps in diagram 20.1, which ones would a pure CPU eBPF user, who has never written a GPU probe, also meet, and why?

Answer

The launch-path and measurement traps. A uprobe on cudaLaunchKernel misses graph replays and cudaLaunchKernelEx launches just as bpftime's hooks do, because it watches the same functions. NVML's utilization misleads anyone who reads it as SM activity, and a llama_process return is not the end of a step for any tool.

The PTX traps, the static-cudart registration trap, sm_90a, and the probe's missing arguments belong to code that runs inside the kernel. The near-miss is to think host-side eBPF escapes the GPU's asynchrony. Every host-side timestamp is a submission or a wait, never the work itself.
