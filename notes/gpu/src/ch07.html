Chapter 7

SASS: what the SM runs

@@RT@@ · ISA — Last chapter we read matvec_warp as PTX, the virtual instruction set that is the same on every bench. Now ptxas turns it into SASS for one real SM, and the three benches finally stop looking alike. This is the code the warp scheduler of the SM chapter issues.

What ptxas decides

PTX left four decisions open, and ptxas makes all of them. It maps about 140 virtual registers onto real ones, a job called register allocation. It chooses the real instructions. It orders them so that slow operations start early. And it writes, into every instruction, the timing hints the scheduler needs. The result for Ada is cuobjdump -sass's listing, and here is the start of matvec_warp:

/*0000*/        MOV R1, c[0x0][0x28] ;                    // stack pointer for local memory
/*0010*/        S2R R9, SR_CTAID.X ;                      // %ctaid.x
/*0020*/        S2R R2, SR_TID.X ;                        // %tid.x
/*0030*/        IMAD R9, R9, c[0x0][0x0], R2 ;            // blockIdx.x * blockDim.x + threadIdx.x
/*0040*/        SHF.R.U32.HI R9, RZ, 0x5, R9 ;            // / 32  -> warp
/*0050*/        ISETP.GE.AND P0, PT, R9, c[0x0][0x17c], PT ; // warp >= d ?
/*0060*/    @P0 EXIT ;
/*0070*/        LOP3.LUT R2, R2, 0x1f, RZ, 0xc0, !PT ;     // % 32  -> lane
/*0080*/        ULDC.64 UR4, c[0x0][0x118] ;
/*0090*/        BSSY B0, 0xaf0 ;                          // reconvergence point for what follows

Listing 7.1 — the first instructions of matvec_warp for sm_89, from cuobjdump -sass (CUDA 13.4). Encodings removed, comments added.

Read it against listing 6.2 and every line has a twin. S2R reads a special register: SR_TID.X is %tid.x. IMAD is integer multiply-add, and c[0x0][0x0] is blockDim.x, which lives in constant bank 0 next to the kernel's arguments; d is at c[0x0][0x17c]. ISETP sets a predicate, and @P0 EXIT is the guarded early return. Registers are named R0 to R254, predicates P0 to P6, and RZ and PT are a register that always reads zero and a predicate that is always true.

Two kinds of names have no PTX twin. ULDC and the UR4 it writes belong to the uniform datapath, which Turing introduced: a small set of registers and instructions for values that are the same in every lane of a warp, such as a base address. Computing such a value once per warp instead of 32 times saves ordinary registers and lane work. And BSSY B0, 0xaf0 with its later partner BSYNC B0 marks a convergence barrier: lanes that split up inside the region wait at BSYNC until all of them arrive. This is the reconvergence of the SIMT chapter, written as two instructions. Pascal SASS uses an older pair, SSY and SYNC, that pushes and pops the mask stack instead.

The loop, as the SM sees it

The PTX loop of listing 6.2 had four copies of "load, load, multiply-add". ptxas unrolled it again, to sixteen, and moved the loads up:

/*0450*/        LDG.E.CONSTANT R27, [R6.64+-0x100] ;      // W, copy 1
/*0460*/        LDG.E.CONSTANT R28, [R4.64+-0x100] ;      // x, copy 1
/*0470*/        LDG.E.CONSTANT R33, [R6.64+-0x80] ;
        …                                                 // 22 loads in a row
/*05a0*/        LDG.E.CONSTANT R15, [R4.64+0x400] ;
/*05b0*/        FFMA R28, R27, R28, R22 ;                 // first multiply-add
/*05c0*/        LDG.E.CONSTANT R22, [R6.64+0x480] ;
        …                                                 // loads and FFMAs interleaved
/*06d0*/        IADD3 R6, P2, R6, 0x800, RZ ;             // W pointer += 2,048 bytes
        …
/*07a0*/        FFMA R22, R29, R30, R24 ;                 // sixteenth multiply-add
/*07b0*/   @!P1 BRA 0x450 ;

Listing 7.2 — the main loop of matvec_warp for sm_89, abridged from 55 instructions.

This is latency hiding done by the compiler inside one warp. Twenty-two loads leave before the first multiply-add needs any of them, so each warp has many requests in flight at once, which is what the SM chapter said warps alone could not provide. LDG is a global load; .E means a 64-bit address; .CONSTANT is the read-only path that ld.global.nc asked for. FFMA is the FP32 fused multiply-add, one per lane, which on Ada fills one sub-partition's 32 lanes for a cycle. The pointer steps by 0x800, 2,048 bytes: 16 copies × 32 lanes × 4 bytes.

The tail is the shuffle tree of diagram 4.3, one instruction per step:

/*0af0*/        SHFL.DOWN PT, R3, R22, 0x10, 0x1f ;
/*0b10*/        FADD R3, R3, R22 ;
/*0b20*/        SHFL.DOWN PT, R0, R3, 0x8, 0x1f ;
/*0b30*/        FADD R0, R3, R0 ;
        …                                                 // offsets 4, 2, 1
/*0b90*/    @P0 EXIT ;                                    // every lane but lane 0 leaves
/*0bd0*/        STG.E [R2.64], R7 ;                       // lane 0 stores y[warp]
/*0be0*/        EXIT ;

Timing hints and scoreboards

A CPU core discovers at run time which instructions are ready, with large out-of-order hardware. An SM does very little of that, because the compiler has already written the answer down. Each SASS instruction on Volta and later carries control codes in spare bits of its 128-bit encoding. They are not shown by cuobjdump; the microbenchmark papers in the reading list decoded them. They say how many cycles to wait before this warp's next instruction can issue, whether the scheduler should prefer to switch warps here, and which scoreboard to use.

A scoreboard is a small counter the hardware keeps per warp for operations whose latency is not fixed, such as memory loads and shuffles. The instruction that starts such an operation names a scoreboard to set. The instruction that needs its result names the scoreboards to wait on. Until the data arrives, that warp is not ready, and the scheduler issues from another one. Fixed-latency arithmetic like FFMA needs no scoreboard: the compiler knows it takes a few cycles and writes a stall count instead.

Registers, spills and occupancy

Every register a thread holds is multiplied by every resident thread. Using more registers can make one warp faster, through more unrolling and more loads in flight, and the SM slower, through fewer resident warps. Diagram 7.3 draws the rule from the SM chapter for every register count from 16 to 128.

You can push back. -maxrregcount=N caps the registers of every kernel in a file. __launch_bounds__(threads, blocks) on one kernel tells ptxas to fit that many blocks of that size per SM. If the code needs more registers than allowed, ptxas stores some values in local memory and reloads them later. That is a spill, and spills go to DRAM, through the caches. Capping the lab kernels at 24 registers shows it:

$ nvcc -O3 -cubin -arch=sm_89 -maxrregcount=24 -Xptxas -v matvec.cu -o out/matvec.r24.sm_89.cubin

ptxas info : Used 24 registers, used 0 barriers, 88 bytes cumulative stack size, 384 bytes cmem[0]
ptxas info : Compiling entry function '_Z11matvec_warpPKfS0_Pfii' for 'sm_89'
    0 bytes stack frame, 0 bytes spill stores, 0 bytes spill loads
$ cuobjdump -sass -fun _Z12matvec_warp4PKfS0_Pfii out/matvec.r24.sm_89.cubin | grep -E 'STL|LDL' | head -3
        STL [R1+0x18], R8 ;
        STL [R1+0x18], R4 ;
        LDL.LU R16, [R1+0x18] ;

Listing 7.4 — a forced spill, on this laptop. STL and LDL are stores and loads to local memory, addressed from the stack pointer R1 that listing 7.1 set up first.

The warp kernel unrolled less and fitted into 24 registers. The float4 kernel did not, and now carries 55 local-memory instructions per thread. For a memory-bound kernel that is extra traffic on exactly the resource that sets its speed.

The same source on Hopper

Compile for sm_90 and the same loop is recognisable but not identical. Kernel arguments sit at different offsets, starting at c[0x0][0x210] instead of c[0x0][0x160]. Loads carry a memory descriptor, LDG.E.CONSTANT R17, desc[UR4][R6.64+-0x100], a uniform register that holds the access policy. And register counts drop: 29, 32 and 44 against 38, 40 and 53. That is the whole reason SASS is per architecture. The meaning of the program is fixed in PTX; how well it fits the hardware is decided again for each SM design.

Then build with -lineinfo and run nvdisasm -g -c on the cubin: each SASS instruction is tagged with the matvec.cu line it came from. Profilers use the same table to show a stall against a source line, and the tooling chapter leans on it.

Recap

ptxas turns PTX into SASS for one SM design. It allocates real registers, picks real instructions, orders them so that slow ones start early, and writes control codes into each instruction: stall counts for fixed-latency arithmetic, and scoreboards that variable-latency loads set and their consumers wait on. For our matvec on Ada it unrolled the loop sixteen times and issued twenty-two loads before the first FFMA, reconverged divergent paths with BSSY and BSYNC, and used the uniform datapath for warp-wide values. More registers mean fewer resident warps, and capping them causes spills to local memory, visible as STL and LDL. The same PTX on Hopper becomes different SASS with fewer registers.

New words in this chapter

register allocation
Mapping virtual registers onto the SM's real ones; done by ptxas.
uniform datapath
Registers (UR) and instructions for values shared by every lane of a warp; Turing and later.
convergence barrier
BSSY / BSYNC: where divergent lanes wait for each other to reconverge (Volta and later).
control codes
Bits in each SASS instruction, written by the compiler, giving stall counts, yield hints and scoreboards.
scoreboard
A per-warp counter set by a variable-latency instruction and waited on by the instruction that needs its result.
-maxrregcount / __launch_bounds__
Cap registers for a whole file / for one kernel, by block size and blocks per SM.
spill
A value moved from registers to local memory because the register budget ran out (STL, LDL).

Check yourself

1. Predict the value: in listing 7.2 each LDG loads one 4-byte float per lane. How many bytes does one warp have in flight just before the first FFMA issues, and how many such warps would one Ada SM need to have about 64 KB of loads outstanding?

Answer

2,816 bytes per warp, and about 24 warps. Twenty-two loads × 32 lanes × 4 bytes = 2,816 bytes, and 65,536 / 2,816 ≈ 23.3, so 24 warps.

That fits inside Ada's cap of 48, and this kernel can be fully resident (diagram 7.3), so there is room to spare. Why bytes in flight matter: to keep memory busy, a GPU must have outstanding at once roughly bandwidth × latency bytes, so deep load batches and many warps both count. The near-miss is to count only the 11 loads of W and forget the 11 of x. In this kernel x is loaded alongside W at every step, although it is tiny and nearly always comes from cache.

2. A colleague adds __launch_bounds__(1024, 2) to a kernel to "raise occupancy". It gets slower, and -Xptxas -v now reports spill stores and loads. Explain the chain from the attribute to the slowdown.

Answer

Two blocks of 1,024 threads is 2,048 threads per SM, so ptxas must fit every thread into 65,536 / 2,048 = 32 registers. If the code wants more, it spills the excess to local memory (listing 7.4). Local memory is DRAM, so a memory-bound kernel gains extra traffic on the resource that limits it, and the extra warps cannot make up for that.

On Ada there is a second problem: the SM holds at most 1,536 threads (48 warps), so the second block cannot be resident anyway, and the cap buys nothing. The near-miss is "more occupancy is always better". Occupancy only helps if latency was the limit and it does not add bytes.

3. "Reading SASS is pointless, because PTX already says what the program does." Name two things in this chapter that only the SASS shows, and why each matters to someone writing probes.

Answer

First, register counts and spills, and so occupancy. An injected probe adds code to the kernel and can push it over a register boundary (diagram 7.3), costing warps or causing spills that the PTX gives no sign of. Second, the real order of instructions: loads hoisted twenty-two deep, the loop unrolled sixteen times. A probe's timing and the kernel's own timing are both shaped by it.

Others count too: kernel arguments at architecture-specific constant-bank offsets, BSSY/BSYNC regions, and Hopper's memory descriptors. The sentence is right that the meaning is fixed in PTX. It is wrong that the cost is.
